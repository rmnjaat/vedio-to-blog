<Section id="s1" no="1" title="Caching at every level" crumb="1 Caching"
  dek="Before buying more machines, stop doing the same work twice. Every box on a Medium request’s route can keep a copy of something."
  meta="About 20 min · class 00:06–00:35 and Q&A 02:27–03:04">

<NotationKey />

A story goes viral. Thousands of readers open the same published post within the hour, and every one of those views travels the whole route: reader, load balancer, API server, Redis, database. Each hop costs time, and the shared cache and the database pay for every single view, even though the story hasn’t changed since it was published.

The cheapest capacity is work you don’t do twice. This section walks the route one box at a time and asks the same question at each: could the answer have been kept here?

</Section>

<Section id="s1-1" no="1.1" title="Where can a cache go?" crumb="1.1 Where a cache goes"
  dek="A cache is not a product. It is any saved copy that spares you an expensive piece of work."
  meta="About 3 min · class 00:06–00:09, Q&A 02:35 and 03:03">

Ask an engineer to “add a cache” to Medium and you will almost always get the same answer: a Redis instance next to the database. That is the most natural answer, and that is exactly why it is worth looking past. A single centralized remote cache is one option among many, and assuming it is the only one leaves most of the good places unused, including the ones that make the infrastructure cheaper. [[L-0017 L-0318]]

So for every place in the architecture, ask three things: what would you cache there, where exactly does that cache sit, and what does it save you, a computation or an I/O? [[L-0011]]

“Caching at multiple layers reduces latency” sounds like an answer, but it names no layer. Push until you can point at a box in the diagram and say what it stops doing. “The API server keeps the rendered story in its own memory, so it skips the call to Redis” is an answer. [[L-0012]]

The box doesn’t have to be anything called a cache. One team’s front end called a separate service that kept a copy of the data instead of calling the API server directly. That service was a cache: whenever you keep a copy of data to avoid an expensive computation or an expensive I/O, you are caching. [[L-0322]]

It is the same instinct as memoization in dynamic programming. Nobody wants to repeat a computation, which is why caches turn up everywhere. [[L-0377]] The only test is arithmetic: a cache helps when reading the saved copy is cheaper than the work it replaces. If it isn’t, it is just one more thing to keep fresh. [[L-0066]]

<RuleBox rule="A cache is ==anything that saves an expensive computation or an expensive I/O==." k="L-0058 L-0064 L-0069">

For every component on the request route, ask: can I cache something here, and would it make the system better? Different architectures have different boxes, and each box has some way to cache. If you take for granted that a cache is RAM-based and centralized, you will never find the other places.

<Desk><QuestionEveryBox /></Desk>
<Phone><QuestionEveryBox layout="phone" /></Phone>

</RuleBox>

<PauseAndThink k="L-0057 L-0013 L-0019 L-0025 L-0059 L-0062"

No. The API server’s own RAM, and even its disk, can hold copies, and both skip the network hop to Redis. What you give up is consistency between servers: two servers can hold different versions of the story for a while. For a published story, which almost never changes, that is fine. The next two parts show both.

</PauseAndThink>

<Section id="s1-2" no="1.2" title="The API server’s own memory" crumb="1.2 API server memory"
  dek="The closest cache to your code is the memory it is already running in."
  meta="About 5 min · class 00:09–00:21">

Every Medium API server already has RAM, and every request still crosses the network to Redis. The simplest cache there is a hash map in the API server’s main memory, kept alongside the centralized remote cache that sits next to the database. [[L-0013]]

<Figure id="fig-1a" max={640} no="Fig 1·a" k="L-0013 L-0018 L-0025" caption="Two kinds of cache. Left: a read answered by the shared Redis still crosses the network, one hop. Right: the same read answered from the API server’s own memory (the dot) never calls Redis or the database. For Medium, the dot can hold published stories. Redrawn from the class board at 00:30 and 00:32.">
<Desk><TwoKindsOfCache /></Desk>
<Phone><TwoKindsOfCache layout="phone" /></Phone>
</Figure>

The reason to do this is not consistency. It is performance: a read from the process’s own memory saves a network call to the remote cache, and that is an expensive call. It is an extremely useful hack and an underappreciated one. Many startups use it for the performance it buys, and the class described big companies as typically not bothering. Big companies do it too: Redis’s own documentation notes that many large applications cache in-process, which is why Redis 6 added server-assisted invalidation <Cite href="https://redis.io/docs/latest/develop/reference/client-side-caching/">redis.io</Cite>. [[L-0019 L-0022]]

It has three costs. Its size is limited by the memory the application itself needs. It is lost when the application goes down or crashes. And with several instances, each one holds a different cache, so they disagree. [[L-0014]]

The disagreement comes from how the copies are filled. An API server’s memory is local to that server and nobody else can read it. When the next request lands on a different server, that server misses, makes the database call, fills its own copy and returns. Keeping every copy fresh is hard: one server may have a hot entry refreshed often while another lags behind, and some readers see an older view than others. [[L-0018 L-0015]]

A centralized cache, one Redis that every instance calls, avoids this: every server sees the same copy. The price is the thing you came for, the local in-memory hop. [[L-0016]]

You can still have both in two situations. With **sticky sessions**, the load balancer always sends a given user’s requests to the same server, so that server can keep the user’s data in its memory, with the remote cache still alongside. If that server goes away, the load balancer moves the user to a new target <Cite href="https://docs.aws.amazon.com/elasticloadbalancing/latest/application/edit-target-group-attributes.html">docs.aws.amazon.com</Cite>, and that user’s local cache is simply rebuilt there. [[L-0020]] Or the data is nearly static: it barely changes, and serving a slightly old copy to some users for a while is fine. [[L-0023]]

Medium’s published stories are the second case. Once a story is published it is very unlikely to change, and updates to it are rare. Two API servers holding two different copies for a while hurts nobody, so Medium can keep published stories in API server memory. [[L-0025]]

What you have given up is strong consistency between the copies. Whether that is acceptable depends entirely on the use case. [[L-0021]]

It is also not a choice between local and remote. Real systems layer them: a local in-memory cache on each API server with the centralized cache behind it. [[L-0026]] Cache some of the information locally, not all of it, with an expiry. That saves the network call to the remote cache and also takes load off the Redis server. [[L-0027]]

An API server has very little RAM to spare, so the TTLs on the local cache and the way it is flushed matter a lot. Redis’s guidance for local caches is a good default: give every locally cached key a maximum TTL, even if the source key has none, and cap the local cache’s memory with an eviction policy <Cite href="https://redis.io/docs/latest/develop/reference/client-side-caching/">redis.io</Cite>. [[L-0028]]

How do the local copies learn that a story changed? One idea is to have every API server publish and subscribe to change events, so a write anywhere invalidates the copy everywhere. Redis 6 and later have a targeted version of this built in: with CLIENT TRACKING <Cite href="https://redis.io/docs/latest/develop/reference/client-side-caching/">redis.io</Cite>, Redis remembers which keys each client read and sends that client an invalidation when one of them changes, instead of broadcasting every change to everyone. <ForwardChip when="next week">keeping local caches in sync</ForwardChip> [[L-0046]]

Being creative about where performance comes from, as with the memory the server already has, is one of the most useful habits in this course. [[L-0024]]

<MarginNote title="Or run Redis on the box" why="skip unless picking a local cache" k="L-0029">

One option is to run a local Redis on each API server itself, instead of a hash map inside the application.

</MarginNote>

</Section>

<Section id="s1-3" no="1.3" title="The API server’s disk" crumb="1.3 API server disk"
  dek="The most ignored cache on the route is the mostly empty disk under every API server."
  meta="About 4 min · class 00:29–00:33">

The 20 GB disk on that same API server holds the operating system and a few jar files, and it is mostly empty. Cache on it too: a copy on the API server’s own disk saves the network trip to the database or to the central cache. This is the answer the question in 1.1 was fishing for, and on the class board it got two exclamation marks. [[L-0057]]

A cache does not have to fit in memory. The rule from 1.1 says it: anything that saves an expensive computation or an expensive I/O.

Every API server, an EC2 instance or a GCP VM, comes with an attached disk of 8 GB, 20 GB or so. It holds only the OS, bundles, jar files and Python packages, so typically 2–3 GB of a 20 GB disk are used and the rest is wasted. On AWS that root disk is usually an EBS volume. The disks physically attached to the host are called instance store <Cite href="https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/InstanceStorage.html">docs.aws.amazon.com</Cite>; AWS calls them ideal for buffers, caches and scratch data, and their contents are lost when the instance stops. [[L-0059]]

RAM is the opposite: scarce and expensive. Of 8 GB, the OS takes some, the application server takes more, other jobs take the rest, and little is left for a cache. Meanwhile the disk sits unused. So use the disk. [[L-0060]]

<Figure id="fig-1c" max={640} no="Fig 1·c" k="L-0059 L-0060 L-0061" caption="Left: on one API server, RAM is nearly all spoken for while the disk is mostly empty. Right: classic latency reference numbers on a log scale; the network round trip is the one a local cache avoids.">
<Desk><ApiServerSpace /></Desk>
<Phone><ApiServerSpace layout="phone" /></Phone>
</Figure>

Few people cache on disk, because they assume a cache has to be in memory to be fast. What matters is the network I/O it saves: a local disk read is much faster than the network call needed to read from a centralized cache, and the network is pathetically slow by comparison. [[L-0061]]

<SourceNote href="https://gist.github.com/jboner/2841832" site="jboner gist (latency numbers)" k="L-0061">

On cloud VMs the default disk (EBS, GCP Persistent Disk) is itself network-attached, and an uncached random SSD read (about 150 µs) is the same order as a round trip inside one datacenter (about 500 µs; classic c. 2012 figures). A disk cache wins mostly because the OS page cache <Cite href="https://www.kernel.org/doc/html/latest/admin-guide/mm/concepts.html">kernel.org</Cite> keeps recently read files in RAM, so a hot “disk” cache is served from memory, and because no shared remote service sits in the path. See also AWS on EBS volume types <Cite href="https://docs.aws.amazon.com/ebs/latest/userguide/ebs-volume-types.html">docs.aws.amazon.com</Cite>.

</SourceNote>

Use the disk cache where inconsistency between servers is acceptable, where you don’t need strong consistency across them. [[L-0062]]

**There is no central view.** Each server’s disk holds its own copy, so a request to one server may return something different from the same request to another. You have to be fine with that, and whether you are is entirely use-case specific. [[L-0067]]

The general lesson is the one behind this whole section. Real systems make you think at every step, so do it: reason about each component yourself instead of taking it for granted. [[L-0065]]

<MarginNote title="From practice: it worked wonders" why="skip unless you want proof it ships" k="L-0063">

When this idea came up in an earlier run of the class, an engineer at a large bank took it back to work, used the API servers’ disks as a cache to optimize his system, and reported that it worked wonders.

</MarginNote>

</Section>

<Section id="s1-4" no="1.4" title="Closer to the reader: the browser" crumb="1.4 The browser"
  dek="The fastest request for a Medium story is the one the reader’s browser never sends."
  meta="About 3 min · class 00:21–00:24, Q&A 02:59–03:04">

Two caches sit nearer the reader than anything you run: the browser and the CDN. This part takes the browser; the next takes the CDN. [[L-0041]]

The browser can cache static images, static assets and even some API responses, so the client doesn’t need to call the backend at all. [[L-0042]] You may also save the JWT token there, which saves a bunch of computation on every request. [[L-0043]] And web workers can do everything offline and sync back to the backend when the internet comes back. [[L-0044]] Open a Medium story a second time and the images appear instantly. That is not the CDN being fast: after the first load the browser serves them from its own cache, with no network call. [[L-0368]]

<SourceNote href="https://cheatsheetseries.owasp.org/cheatsheets/HTML5_Security_Cheat_Sheet.html" site="OWASP" k="L-0043">

A JWT is a self-contained credential rather than a cache: keeping it on the client lets the server verify it without a session-store lookup. Don’t keep it in localStorage, where any injected script can read it; OWASP recommends cookies with the HttpOnly flag.

</SourceNote>

Working offline and syncing later is how offline-first apps work. Every change is made locally and pushed to the backend periodically, or when the connection comes back, so the app feels very fast. The browser pieces for it are Service Workers plus Background Sync <Cite href="https://developer.mozilla.org/en-US/docs/Web/API/Background_Synchronization_API">developer.mozilla.org</Cite> and IndexedDB. [[L-0044]]

For data you choose to keep, the browser’s local storage is an excellent place to cache a fair amount of stuff. [[L-0045]] It is limited: not huge amounts, but a decent amount. In practice that is about 5 MiB per origin <Cite href="https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria">developer.mozilla.org</Cite>; it is synchronous, so large reads block the page, and writes past the quota throw an error. MDN recommends IndexedDB for large or performance-sensitive data. [[L-0367]]

Modern browsers expose it as the `localStorage` object, with `setItem` and `getItem`, and the class mentioned caching images there too. In fact it stores strings only <Cite href="https://developer.mozilla.org/en-US/docs/Web/API/Web_Storage_API">developer.mozilla.org</Cite>, so images belong in the browser’s HTTP cache or the Cache API rather than in `localStorage`. [[L-0370]]

```js
// cache the reader's "popular stories" list for this tab's next visit
localStorage.setItem('popular', JSON.stringify({ at: Date.now(), stories }));
const saved = JSON.parse(localStorage.getItem('popular') ?? 'null');
```

Client libraries do the same for API responses. React Query, for example, caches responses on the client, in the JavaScript runtime. [[L-0376]]

Recommendations are a good fit, and the idea was suggested in class from practice. One e-commerce team cached re-ranked product recommendations on category pages in the browser, mainly for how it felt rather than for latency. Re-ranking on every revisit confused shoppers; never updating for a full day lost the personalization. They ran experiments to find the right cache duration, refreshed the cached list on that timer, and accounted for the cache’s effect when building their training data. [[L-0047]]

The teacher restated it as a hack: hypothetically, Amazon could keep a user’s recommendations in the browser’s local storage and render from there, instead of making an expensive backend call each time, and refresh them periodically. [[L-0048]] Then he added a cheap trick that makes such a cache feel alive: if 50 recommended items are cached but the viewport shows 10, pick 10 at random on each view. The picks feel fast and fresh even though they change only once a day. [[L-0049]]

<MarginNote title="See it yourself" why="skip if you’ve done this" k="L-0369 L-0371">

Open the browser’s developer tools on an image-heavy page and go to the Network tab. Reload: the cached images show that their content was already there, with no network call. Then, in Chrome or Firefox, open the Application (or Storage) panel and click Local Storage on the left to see what any site is caching.

</MarginNote>

</Section>

<Section id="s1-5" no="1.5" title="The CDN, and caches closer still" crumb="1.5 The CDN"
  dek="A CDN caches bytes, not just images. And for the most popular content, there is a level beyond it."
  meta="About 5 min · class 00:24–00:29, Q&A 02:39–02:48">

Medium’s “popular stories” list is the same for everyone for minutes at a time, yet every reader’s request for it goes all the way to an API server.

A common misconception is that CDNs can only cache static things like images and video. A CDN is a proxy between the reader and your backend. Everything that passes through it is just bytes, so it can cache literally anything, API responses included. [[L-0051 L-0332]] It does obey the response’s cache headers and its own defaults: Cloudflare does not cache HTML or JSON <Cite href="https://developers.cloudflare.com/cache/concepts/default-cache-behavior/">developers.cloudflare.com</Cite> until you add a cache rule. And mark per-user responses `Cache-Control: private` <Cite href="https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching">developer.mozilla.org</Cite>, so that only the reader’s own browser keeps them and a shared cache never serves one reader’s page to another.

API responses that are near-static can be cached on the CDN, and then the request never reaches your backend, or even your centralized cache. The CDN keeps the response and serves it from its locations around the world. [[L-0053]] Normally a request goes reader, CDN, backend, database; when the CDN has the answer, your servers never see it. [[L-0055]]

<Figure id="fig-1d" max={640} no="Fig 1·d" k="L-0051 L-0053 L-0055 L-0056 L-0344 L-0346 L-0347" caption="Left: GET /popular is answered at the edge; only a miss goes on to the API server. The class example was search.abc.com/popular. Right: a very popular show answered by the reader’s ISP before the CDN is even asked. Left panel redrawn from the class board at 00:29.">
<Desk><CdnAndIsp /></Desk>
<Phone><CdnAndIsp layout="phone" /></Phone>
</Figure>

The class example was an endpoint like `https://search.abc.com/popular`, all the popular searches on a platform. For Medium it is `/popular`: cache it on the CDN and the CDN serves it directly. [[L-0056]] Giphy does this for the search results of its most popular terms. [[L-0054]] For content that does change, AWS recommends versioned file names over invalidation <Cite href="https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/Invalidation.html">docs.aws.amazon.com</Cite>: after an invalidation, browsers and intermediate caches may keep showing the old version, and invalidations cost money.

From practice, one team cached at two levels: a Cloudflare CDN cached whole responses, and Prerender.io cached their JavaScript, CSS and media. (What Prerender.io actually does is render JavaScript pages to HTML for crawlers and cache that HTML. <Cite href="https://docs.prerender.io/docs/how-does-prerender-work">docs.prerender.io</Cite>) [[L-0050]]

Where does a CDN keep all this? In the class’s view, on disk rather than in RAM: what CDNs cache is mostly images, video and gigantic responses, which you would not hold in RAM (the class added that it had no inside knowledge of how CDN providers do it). [[L-0333]] There is also little need for RAM there: SSDs perform relatively close to RAM, and a CDN is already close to the user, so it already has the latency benefit. [[L-0334]]

<SourceNote href="https://www.fastly.com/blog/how-our-solid-state-drives-result-cost-savings-customers" site="fastly.com" k="L-0333 L-0334">

Disk and SSD hold the bulk of a CDN’s cache, but RAM is still far faster: about 100 ns per memory reference against about 150 µs for a random SSD read (classic latency numbers <Cite href="https://gist.github.com/jboner/2841832">jboner gist</Cite>). CDNs keep hot objects in RAM as well; Fastly (2015) ran 384 GB of RAM plus 6 TB of SSD per server and kept commonly used data in RAM.

</SourceNote>

A tiered model, RAM first, then disk, then the central origin, was proposed in class. The answer was that CDNs can do that if they want, but there is no need: they might keep configuration in RAM, not the gigantic user data. [[L-0335]] As Fastly’s numbers above show, real CDN tiers do keep hot objects in RAM.

<ForwardChip block when="week 3 onward" k="L-0052 L-0331">CDNs in depth</ForwardChip>

### Beyond the CDN

People treat the CDN as the end of the line. It isn’t. Very popular shows can be cached inside ISPs, at points of presence nearer the users, which makes streaming faster and saves CDN cost. [[L-0344]] An ISP with decent-sized data centers, the class’s example was ACT, can serve a popular show from its own site, so users fetch it without going to the CDN at all, with very low latency. [[L-0346]]

This works because a show doesn’t change once it is live, so there is no inconsistency to worry about; Netflix works with ISPs and asks them to cache it. [[L-0347]] The class named Netflix as most likely the pioneer here, with a hedge. In fact Akamai placed servers inside ISPs’ networks <Cite href="https://en.wikipedia.org/wiki/Akamai_Technologies">en.wikipedia.org</Cite> from the late 1990s, and Netflix’s Open Connect <Cite href="https://about.netflix.com/en/news/how-netflix-works-with-isps-around-the-globe-to-deliver-a-great-viewing-experience">about.netflix.com</Cite> (2011) is the best-known single-provider version. [[L-0349]] Cloudflare’s engineering blog also describes how it speeds things up by working with ISPs; a search finds the posts. [[L-0348]]

The traffic is big enough to fight over. SK Broadband in South Korea sued Netflix in 2021 <Cite href="https://www.nippon.com/en/news/reu20211001KBN2GR2XS/">nippon.com</Cite>, citing the traffic from *Squid Game*. [[L-0345]]

Video streaming today is mostly a CDN problem and not that difficult. The course will give pointers to look up and implement rather than a full implementation.

</MarginNote>

<Section id="s1-6" no="1.6" title="The load balancer and the API gateway" crumb="1.6 LB and gateway"
  dek="Every request already passes through a load balancer. Sometimes the answer can wait there."
  meta="About 2 min · class 00:33–00:34, Q&A 02:27–02:36">

Every Medium request already passes through a load balancer. Load balancers and API gateways, nginx, AWS’s load balancer, API gateways in general, can cache responses too, like a CDN, so the request never reaches the backend, the centralized cache or the database. [[L-0068]]

The catch is invalidation. As taught in class, a load balancer’s cache can only be invalidated by time: there is no API to evict an entry, so you accept that a response stays cached for the configured TTL. [[L-0308]] The only lever you have is tuning that time. [[L-0309]]

<SourceNote href="https://docs.aws.amazon.com/apigateway/latest/developerguide/api-gateway-caching.html" site="docs.aws.amazon.com" k="L-0068 L-0308">

Reverse proxies (nginx proxy_cache <Cite href="https://nginx.org/en/docs/http/ngx_http_proxy_module.html">nginx.org</Cite>) and API gateways (Amazon API Gateway) can cache responses; AWS’s Application Load Balancer <Cite href="https://docs.aws.amazon.com/elasticloadbalancing/latest/application/introduction.html">docs.aws.amazon.com</Cite> does not cache at all. TTL is the main lever but not the only one. API Gateway caches GET responses for 300 s by default (up to 3600 s), can flush a stage’s whole cache, and lets an authorized client refresh one entry with `Cache-Control: max-age=0`. nginx takes the lifetime from `proxy_cache_valid` or the upstream’s headers, and purging entries is an NGINX Plus feature. CDNs such as CloudFront support invalidation <Cite href="https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/Invalidation.html">docs.aws.amazon.com</Cite>.

</SourceNote>

The same idea shows up in services you build yourself. If a service sits between the front end and several backends, takes one query and fans it out to many machines, it is a single point of contact, essentially an API gateway, and a natural place for a cache. [[L-0323]]

</Section>

<Section id="s1-7" no="1.7" title="Inside the database: materialized views" crumb="1.7 Materialized views"
  dek="Even the database can keep a copy: of a query’s answer instead of its tables."
  meta="About 4 min · class 00:16–00:20">

An author’s stats page on Medium joins users, stories, claps and follows on every load, and the numbers barely change during the day.

It is tempting to say that a database view is already a cache: it would spare the database from preparing and running the query each time, and the database keeps it current on every update. [[L-0030]]

<SourceNote href="https://www.postgresql.org/docs/current/rules-materializedviews.html" site="postgresql.org" k="L-0030">

A plain view stores only its query and re-runs it on every read, so it caches nothing. A materialized view does store results, but in PostgreSQL it is not kept current automatically: it stays as of the last `REFRESH MATERIALIZED VIEW`. (Oracle can refresh automatically; see its refresh options <Cite href="https://docs.oracle.com/en/database/oracle/oracle-database/19/dwhsg/refreshing-materialized-views.html">docs.oracle.com</Cite>.)

</SourceNote>

What actually does the caching is a **materialized view**. It stores the result of a query, for example a join of several tables plus some computation, as a separate, pre-joined and pre-computed table. Queries then run against the view instead of the base tables. [[L-0031]]

Joins are among the biggest performance costs in a relational database. If about 80% of your load comes from joining six tables, and that data doesn’t change often, store the joined result as its own table. [[L-0033]] What the view saves is exactly that: the expensive computation, the join above all. [[L-0040]]

<Figure id="fig-1e" max={700} no="Fig 1·e" k="L-0031 L-0033 L-0034 L-0035 L-0036" caption="The board’s example: per-subject marks joined with people, plus a derived total, stored as one table that queries hit directly. Medium’s version is author stats: users, stories and claps joined once, read many times.">
<Desk><MaterializedView /></Desk>
<Phone><MaterializedView layout="phone" /></Phone>
</Figure>

A view isn’t limited to joins. It can carry other computation too, such as added derived columns. [[L-0034]] The class board’s example: a raw table keeps marks for each subject in separate columns, and the view adds a derived `total` column and joins in the people’s other details. Every query runs against that view. [[L-0035]]

```sql
CREATE MATERIALIZED VIEW results_mv AS
SELECT p.name, p.city, m.maths, m.physics, m.chemistry,
       m.maths + m.physics + m.chemistry AS total
FROM marks m JOIN people p ON p.id = m.student_id;

REFRESH MATERIALIZED VIEW results_mv;  -- re-run the query, replace the stored rows
-- Medium: author_stats = users ⋈ stories ⋈ claps
```

Materialized views are mostly a feature of relational databases, though some non-traditional databases use them for performance too. [[L-0032]]

They have to be updated explicitly. “Refresh” is the official term, and the class named database triggers as the way to fire it. [[L-0036]]

<SourceNote href="https://www.postgresql.org/docs/current/sql-refreshmaterializedview.html" site="postgresql.org" k="L-0036">

“Refresh” is the right word; triggers are not the standard mechanism. PostgreSQL refreshes only on an explicit `REFRESH MATERIALIZED VIEW`, often run on a schedule; a plain refresh can block readers, and `REFRESH … CONCURRENTLY` avoids that but needs a unique index on the view. Oracle can refresh automatically <Cite href="https://docs.oracle.com/en/database/oracle/oracle-database/19/dwhsg/refreshing-materialized-views.html">docs.oracle.com</Cite> ON COMMIT or ON STATEMENT, and its fast refresh applies only the changes instead of recomputing the whole query.

</SourceNote>

That is also the limit. Materialized views pay off only when the data changes rarely; with data that changes often, the frequent refreshes slow everything down. [[L-0037]]

In the class’s view they are one of the most interesting database optimizations, and one that many backend and API engineers don’t really understand, while data engineers use them day in and day out to make analytical queries fast. [[L-0038]] Read about database views and materialized views, and then, most importantly, build one. Until you implement it, it is all theory. [[L-0039]]

</Section>

The centralized remote cache was there all along. [[L-0011 L-0013 L-0031 L-0045 L-0053 L-0057 L-0068]]

For every component on that route, the question from 1.1 still applies: can I cache something here, and would it make the system better? [[L-0069]]

Every cache is a trade-off: you gain some and lose some. With local copies you trade away strong consistency. If the data changes rarely, two copies don’t matter, and if serving slightly stale data for a while is acceptable, do it; for that kind of data, the class called it “the best thing ever”. [[L-0071]]

One team ran a configuration platform for other apps. Configs are tiny, but every read is on someone’s hot path: adding more than 3 ms of latency was a no-go for its customers. [[L-0315]]

Changes made in the control plane were snapshotted and pushed to S3. On boot, each application loaded the snapshot from S3 into an in-memory cache and also saved it to local disk. [[L-0314]] Mobile clients got the config through a CDN instead of S3: reads went to memory first, then disk, and if it was missing the client fetched it from the CDN in the background. [[L-0316]]

<Figure id="fig-1g" max={340} no="Fig 1·g" wide={false} k="L-0314 L-0315 L-0316 L-0320 L-0321" caption="Reads always hit memory; the disk path runs on every boot; a background thread keeps pulling the latest config.">
<ConfigPlatform />
</Figure>

Layering this deep (memory, disk, then CDN or S3) works here because configs need very little invalidation and the team could live with some inconsistency. [[L-0317]]

The interesting part is the fallback. The team treated a rarely used fallback path as an anti-pattern: it is hardly ever exercised or tested, so it can be stale or broken on the day it is finally needed, and they made the “fallback” part of the normal path instead. That is their rule, not a settled one: memory, then disk, then CDN is still a fallback chain, and the class called the design interesting rather than endorsing the rule. [[L-0319]] Here is how the design tries to keep every step exercised. When the application starts, memory is empty, so the disk path runs on every boot. If memory is flushed later, reads fall back to the same disk copy that was already proven at startup. [[L-0321]] Reads always go to memory, and a background thread fetches the latest config from the CDN, so the cache updates itself. Every change is committed to git and published to the CDN together, so neither can be forgotten. [[L-0320]]

</MarginNote>

<RecallQuestions>
  <RecallItem q="Why is a local RAM cache acceptable for a published Medium story but risky for its clap count?">

Each API server holds its own copy and no server sees the others’. A published story almost never changes, so two servers holding slightly different copies for a TTL hurts nobody. A clap count changes constantly, so different servers would show different numbers and a stale one would stay wrong until its entry expired.

  </RecallItem>
  <RecallItem q="Your API servers have 1 GB of free RAM and 17 GB of free disk. Which do you use for a cache of rendered stories, and what must be true of the data?">

The disk, the one people forget. RAM is scarce: what little is free is better kept for a few hot keys. The disk is large, already paid for, and a hot disk cache is mostly served from the OS page cache anyway. Either way the saving is the network call to Redis or the database. The data must tolerate inconsistency between servers: there is no central view, so it should change rarely, as rendered published stories do.

  </RecallItem>
  <RecallItem q="Name three caches a request for /popular could hit before it reaches your API servers.">

The reader’s browser (its HTTP cache or local storage), the CDN (a near-static response cached at the edge), and the load balancer or API gateway (a cached response with a TTL).

  </RecallItem>
</RecallQuestions>
