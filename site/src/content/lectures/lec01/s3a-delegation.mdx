<Section id="s3" no="3" title="Delegation" crumb="3 Delegation"
  dek="Publishing a story does too much inside one request. What to take out of the request, the two kinds of broker, and the Kafka essentials you need to design with."
  meta="About 25 min · class 01:05–01:37, Q&A 02:27–03:14"
  k="L-0010 L-0134">

Medium wants to show a small line under every author’s name: *74 essays*. There are two obvious ways to get that number, and both cost something. Count the author’s stories on every profile view, and every view pays for a join. Keep a stored count and update it when a story is published, and the publish request now carries one more write before it can answer.

This section is about a third option: do the update, just not while anyone is waiting for it.

</Section>

<Section id="s3-1" no="3.1" title="Not everything belongs in the request" crumb="3.1 Delegation"
  dek="Real time means inside the request. Keep only what the response needs there; hand the rest to a worker."
  meta="About 3 min · class 01:05–01:08 and the board at 01:17">

Suppose a publish request does everything before it answers: it validates the story, saves it, bumps the author’s count, and only then tells the writer it worked. Each of those steps adds to the time the writer waits, and each write lands on the database while the request is still open.

In this course’s view, handing work off is the most underrated way to get performance out of a system. [[L-0135]]

The principle has a memorable source. In a talk given at the start of the 2020 lockdown, a VP of Engineering at Hotstar described the rule Hotstar lives by to handle massive scale on its API side. (In the class’s telling, much of Hotstar’s famous scale is really its CDN’s work, Akamai’s; the API side is where this rule does its job.) [[L-0136]]

<RuleBox rule="Whatever does not need to be done ==in real time== should not be done in real time." k="L-0137">

The board called it *the mantra for performance*. Of everything a request has to do, do the essential part before the response and hand the rest to something that runs after it.

<Desk><DelegateSketch /></Desk>
<Phone><DelegateSketch layout="phone" /></Phone>

</RuleBox>

“Real time” has a precise meaning here: inside the request context. Of everything a request has to do, only what is extremely essential gets done in the request context. Everything else is delegated to a worker. [[L-0138]]

The request context ends the moment the client gets its response. Whatever happens after that point, the client never waits for. [[L-0145]]

What you get for it: responses are very fast, because the request does the bare minimum, so the user gets a good experience. The database sees very little load from inside the request, and everything else happens asynchronously. [[L-0139]] Using delegation to the fullest is, in this course’s view, what makes building systems at scale work. [[L-0140]]

Work that typically gets delegated: [[L-0171]]

- long-running tasks, such as spinning up an EC2 instance or encoding a video
- heavy computation queries
- batch and write: collect many small updates and write them together
- anything that can be eventual

</Section>

<Section id="s3-2" no="3.2" title="Medium’s total_blogs counter" crumb="3.2 The counter"
  dek="A count on every profile card, kept without a join and without slowing the publish."
  meta="About 5 min · class 01:07–01:12">

Medium shows how many essays an author has written right on the profile card. One way to serve that number: add a `total_blogs` column to the `users` table and add one to it (`count++`) every time the author publishes. [[L-0141]]

<Figure id="fig-3a" no="Fig 3·a" k="L-0141"
  caption="The number the users table has to supply. Redrawn from the class board at 01:05, with a made-up author.">
  <ProfileCard />
</Figure>

To be honest about the example: a join over the stories would give the same count. The use case is deliberately manufactured, a crude example chosen to have something small to delegate, and it leads into the Kafka part of this section. Storing the count pre-computed avoids the join and the runtime computation on every profile view. [[L-0142]]

The increment is not a critical update. Nobody is harmed if the card says 73 for a few seconds after the 74th story goes up, so it can be done asynchronously. That is exactly the kind of work delegation is for. [[L-0143]]

The core idea is **delegate and respond**. The client sends a request (①). The API server submits a task (②) and sends the response (③), and that is its whole job. The task goes into a buffer, and a set of workers take tasks from it, do the heavy lifting and update the database. [[L-0144]]

<Figure id="fig-3b" no="Fig 3·b" k="L-0144 L-0145 L-0146"
  caption="Delegate and respond. Only ① and ③ happen while the client waits; ② is dashed because nobody waits for it. Redrawn from the class board at 01:09, without the board’s line from the API server to the database: in this flow the API server doesn’t write.">
  <Desk><DelegateRespond /></Desk>
  <Phone><DelegateRespond layout="phone" /></Phone>
</Figure>

That buffer is usually called a **broker** (message broker, message stream: the same idea for now). It is a buffer that keeps the tasks and messages until a worker gets to them. [[L-0146]]

For Medium’s count, the flow is: the writer publishes, the API server puts an `ON_PUBLISH` message into a broker such as SQS or RabbitMQ and answers, and a worker reads the message and runs its business logic, an `UPDATE` query that does `total_blogs++`. Pages loaded after that show the new count. [[L-0147]]

<Figure id="fig-3c" no="Fig 3·c" k="L-0141 L-0147 L-0153"
  caption="Medium’s blog count via SQS. The API server drops ON_PUBLISH into the queue and answers; whichever worker takes the message runs total_blogs++. Redrawn from the class board at 01:11.">
  <Desk><BlogCountSqs /></Desk>
  <Phone><BlogCountSqs layout="phone" /></Phone>
</Figure>

The worker’s side is a few lines. Note that the `+ 1` happens inside the database’s own `UPDATE`, not as a read in the worker followed by a write; §4 comes back to why that matters.

```js
// the worker: runs outside any request, one message at a time
const msg = await queue.receive();          // { type: 'ON_PUBLISH', authorId }
await db.query(
  'UPDATE users SET total_blogs = total_blogs + 1 WHERE id = $1',
  [msg.authorId]
);
await queue.delete(msg);                    // "done" (more on this in 3.3)
```

Deleting a story works the same way in reverse: an `ON_DELETE` event is published and consumed, and its worker runs `total_blogs--`. [[L-0153]]

The writer sees the new count on their next page load, not the instant they press Publish, because the update runs after the response has gone out. [[L-0148]]

That is the trade. You accept a delay in processing. In return the API server doesn’t write the count itself, the request puts no synchronous write load on the database, and there are fewer concurrent writes, so the database experiences less load. [[L-0149]]

Why go to that trouble for a counter? Because, as this course puts it, the database is the most brittle component of your infrastructure. If it goes down, everything is done, so protect it. [[L-0150]] Treat it like an expensive iPhone you just bought: put a good cover on it, take great care of it, and put as little load on it as you can. [[L-0151]]

Everything here hinges on the box in the middle. The broker is the heart and soul of delegation as a principle, so the rest of this section is about brokers. [[L-0152]]

</Section>

<Section id="s3-3" no="3.3" title="Message queues" crumb="3.3 Queues"
  dek="Identical consumers taking turns at one queue, and what brings a message back when one of them dies."
  meta="About 6 min · class 01:11–01:14, Q&A 01:35–01:37 and 02:58–03:02">

The `ON_PUBLISH` message is now sitting in SQS. Who picks it up, and what happens if they crash halfway?

There are two kinds of broker: **message queues** and **message streams**. This part is about queues. Streams come in 3.5, and a third kind, plain broadcast, comes up in 3.8. [[L-0154]]

A message queue is a literal queue. Messages go in, and a set of consumers take them out. The consumers are **homogeneous**: every one of them does the exact same thing. [[L-0155]] Typical tasks: spin up an EC2 instance, update a count, send an email notification, send a reminder. [[L-0156]] SQS and RabbitMQ are message queues. [[L-0157]]

Consumers pull messages from the queue. It is almost never push-based; push-based consumption exists, but in very few places. [[L-0158]]

<SourceNote href="https://www.rabbitmq.com/docs/consumers" k="L-0158">

That holds for SQS: consumers poll with `ReceiveMessage`, and long polling waits up to 20 s for a message to arrive <Cite href="https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-short-and-long-polling.html">aws.amazon.com</Cite>. It holds for Kafka and Kinesis too. RabbitMQ, the other queue named here, works the other way: consumers normally subscribe and the broker pushes messages to them. Its documentation calls polling for single messages with `basic.get` “highly inefficient” and “strongly recommended against” outside integration tests.

</SourceNote>

The queue acts as a buffer: it keeps the messages while the consumers read them and do the heavy lifting. [[L-0160]] When a consumer reads a message, it reads it exclusively. That message will not go to any other consumer. All the consumers listen to the same queue and run the same business logic, so it doesn’t matter which one gets which message. [[L-0161]]

<SourceNote href="https://www.rabbitmq.com/docs/confirms" k="L-0161">

Exclusive is the intent, not a guarantee. SQS standard queues deliver at least once: “more than one copy of a message might be delivered” <Cite href="https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/standard-queues.html">aws.amazon.com</Cite>, and a message that isn’t deleted in time goes back to the other consumers <Cite href="https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html">aws.amazon.com</Cite>. RabbitMQ redelivers unacknowledged messages too. For `total_blogs++` a second copy means a double count, so make consumers idempotent: safe to run twice on the same message.

</SourceNote>

If a consumer fails in the middle of a message, you don’t replay it by hand. Retrying is a guarantee of the queue itself. SQS calls the mechanism the **visibility timeout**: a message handed to a consumer is hidden from the others, and if that consumer hasn’t deleted it when the timeout (typically 2 or 10 minutes) runs out, the message reappears at the front of the queue and another available consumer picks it up. [[L-0210]] The timeout is yours to configure: 10 seconds or 10 minutes, whatever the work needs. [[L-0364]]

<SourceNote href="https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html" k="L-0210">

The mechanism is right; the specifics differ. SQS’s default visibility timeout is 30 s, and it can be set anywhere from 0 s to 12 h <Cite href="https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/quotas-messages.html">aws.amazon.com</Cite>. AWS suggests about 2 minutes if you’re unsure, and a worker can extend the timeout while it works. The message becomes visible again, but a standard queue has no strict “front”, so it isn’t necessarily the next one out. Retries also stop where you tell them to: a redrive policy’s `maxReceiveCount` moves a message to a dead-letter queue after that many failed receives <Cite href="https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-dead-letter-queues.html">aws.amazon.com</Cite>.

</SourceNote>

So *not* deleting is the failure signal. A consumer says “done” by deleting the message after it has processed it, and you write that delete in your code; the queue gives you the API and you decide when to call it. Delete before the work and a crash loses the message. Delete after, and a crash only costs a retry. [[L-0212]]

Different queues provide different guarantees: SQS’s are not RabbitMQ’s. [[L-0211]] The idea travels, though. Features get copied from tool to tool, so learn the key term once (visibility timeout, in SQS) and look up the equivalent in whatever you use; the class named RabbitMQ and Google Pub/Sub as having one. [[L-0365]] Pub/Sub’s is the *ack deadline*: a subscriber must acknowledge a message within it <Cite href="https://docs.cloud.google.com/pubsub/docs/lease-management">cloud.google.com</Cite>. RabbitMQ’s is less direct: it has no per-message timeout, and it requeues any unacknowledged delivery when the consumer’s channel or connection closes <Cite href="https://www.rabbitmq.com/docs/confirms">rabbitmq.com</Cite>. SQS is the one the class has leaned on most in practice. [[L-0366]]

One thing a queue doesn’t show you is partitions. SQS may well partition internally, but nobody outside can tell, and there is no partition concept for you to design with. Keep that in mind for Kafka in 3.6. [[L-0372]]

<MarginNote title="Not the same queue" why="skip if that was never confusing" k="L-0215">

When a connection pool is full, extra requests wait in a queue. That wait queue is an in-memory data structure inside one process. A message broker is an infrastructure component: a separate process you spin up, which many processes talk to. Same word, two very different things.

</MarginNote>

</Section>

<Section id="s3-4" no="3.4" title="When one worker does two jobs" crumb="3.4 Two jobs"
  dek="Indexing every new story for search, and why bolting it onto the counter’s worker goes wrong."
  meta="About 4 min · class 01:14–01:18">

Medium also wants every new story to be searchable, which means indexing it in Elasticsearch so the search service can use it. The obvious move: the SQS worker that already does `total_blogs++` also writes the index entry. One message, one worker, two writes. [[L-0163]] (Even when that write succeeds, search is near real-time: Elasticsearch refreshes its indexes every second by default, so a new story can take about a second to become searchable. <Cite href="https://www.elastic.co/guide/en/elasticsearch/reference/current/near-real-time.html">elastic.co</Cite>)

It looks fine on a whiteboard. It goes wrong in two ways.

The first is people. The count belongs to the backend or analytics team, and the index belongs to the search team. Share one worker codebase between them and you get fights: one team’s change stops the other’s deployment, changes sit uncommitted, branches get messy and the code grows inconsistent. [[L-0164]] It is not a good design. There is no separation of concerns, and the worker is plainly doing work that two separate teams should own. [[L-0169]]

The second is machines. Suppose the worker crashes between its two writes.

<PauseAndThink
  q="The author has 74 stories, and search has 74 indexed. One worker handles a new publish by doing <code>total_blogs++</code> and then indexing in Elasticsearch. It crashes between the two writes, and the message is retried in full. What do the count and the index say now?"
  choices={[{ label: '75 and 75: the retry fixes it' }, { label: '76 and 75', correct: true }]}
  right="Right: the retry repeats the write that already worked."
  wrong="A retry runs the whole job again, including the part that succeeded:"
  k="L-0163 L-0165 L-0166 L-0167">

76 and 75. The first attempt left 75 and 74. The retry runs *both* writes again, so the count goes to 76 while the index catches up to 75. Retrying a two-step job repeats the step that already succeeded. Doing two things in one shot is a problem in any distributed system, which is why each job gets its own consumer next (3.5).

</PauseAndThink>

The crash left the count at 75 and search at 74. [[L-0165]] Retrying didn’t repair that: re-consuming the message ran `count++` a second time while the index finally caught up, so the count says 76 and search has 75. [[L-0166]]

This is general. Doing two things in one shot is always a problem in a distributed system, because machines go down between the two, and distributed transactions, which would make both writes succeed or fail together, are extremely costly. [[L-0167]] The usual practical workaround is the transactional outbox: the outgoing message is written to an outbox table in the same database transaction as the change, and a relay publishes it afterwards, so others see the change eventually rather than at once, and possibly twice. <Cite href="https://microservices.io/patterns/data/transactional-outbox.html">microservices.io</Cite>

So don’t make one worker do both. Give each job its own consumer of the same `ON_PUBLISH` event, so the counter and the search index each fail and retry on their own. A queue can’t do that, because each message goes to just one of its identical consumers. That calls for the second kind of broker.

</Section>
