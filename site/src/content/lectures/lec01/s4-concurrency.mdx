<Section id="s4-1" no="4.1" title="Why bother with concurrency" crumb="4.1 Concurrency"
  dek="Two readers clap at the same instant. A short taste of what goes wrong when two workers touch one number, and of the tools that keep it right."
  meta="About 2 min · class 01:44–01:46">

In §3 a worker took the `total_blogs` update out of the publish request. That worker is one machine, and so is each API server and the database; the next question is how much one machine can get through. That is concurrency, the heart and soul of building systems at scale. [[L-0009]]

Concurrency is how you get the most out of a single machine, whether that machine is an API server, a database or an async worker. You run several processes or several threads at once. Multiprocessing and multithreading both fall under it. [[L-0217]]

It brings two problems with it. The first is that threads have to talk to each other: “I’m done with this message, don’t process it again.” The second is that they must not use a shared resource at the same moment, whether that resource is a row in the database or a plain variable in memory. The board page for this part of the class fits on one sheet: [[L-0218]]

<Section id="s4-2" no="4.2" title="The lost update" crumb="4.2 The lost update"
  dek="Two claps at once, and a count that comes out one short without any error."
  meta="About 2 min · class 01:45–01:47 and 01:49–01:50">

Every Medium story shows how many claps it has. Say a story has 100, and two readers clap at the same moment. The count must become 102, not 101. [[L-0230]]

<PauseAndThink k="L-0219 L-0230 L-0231"
  q="A story has 100 claps. Two readers clap at the same instant, and each request reads the count, adds one and writes it back. What can the count end at?"
  choices={[{ label: 'Always 102' }, { label: '102 or 101', correct: true }]}
  right="Right: one clap can vanish without any error."
  wrong="Only if the two requests never overlap. When they do:">

101 is possible. If both requests read 100 before either one writes, both write 101 and one clap disappears. This is a **lost update**, and nothing reports an error. The same thing turns 2,000 increments into about 1,997. The fix belongs in the database: an atomic increment, or a properly isolated transaction (4.3).

</PauseAndThink>

The last step is the textbook form of the bug. A global `int count = 0`, two threads, each running `count++` a thousand times. You expect 2,000 and get something like 1,997, because `count++` is not atomic: it is a read, an add and a write, and the other thread can slip in between the read and the write. That is why concurrent systems are hard to build. They have to guarantee correct data (2,000, not 1,997) and high throughput at the same time. [[L-0219]]

<MarginNote title="Why isn’t count++ atomic?" why="skip if you already know" k="L-0220">

If you don’t come from a CS background, search for why `count++` isn’t thread-safe. In short, one line of code becomes three machine steps: load the value into a register, add one to it, store it back. A thread can be paused between any two of them, and another thread can run all three in that gap.

</MarginNote>

<AnimationClip clip="l01-count-race" no="Clip 4·1" k="L-0219 L-0230 L-0231"
  lead="Now run it a thousand times. Before you play it: how many of the 2,000 increments do you expect to lose?"
  caption="Two threads, 1,000 increments each, on one counter. Slowed down: two claps on a count of 100, both threads read 100, and one write overwrites the other, so the count says 101 instead of 102. At full speed that happens only a few times, silently, and the counter stops near 1,997. With each increment made one indivisible step, it lands on 2,000." />

The same counter can also go wrong the other way. In §3.7 the counter worker could receive the same `ON_PUBLISH` message twice, because Kafka delivers at least once, and consumers have to be fine with re-consuming a message. On `total_blogs` that is one count too many. The lost update is one count too few. The double count is handled in the consumer, which must tolerate a repeat. The lost update has to be fixed where the number lives: the fix lives in the database, as a transaction or an atomic operation. [[L-0196]]

</Section>

### Locks

The read, the add and the write that must not interleave form the **critical section**. Locks are one way to keep it correct: a lock protects the critical section. They come in two kinds, optimistic and pessimistic. This is only the gist. [[L-0221]]

<ForwardChip block when="weeks 3–6" k="L-0222">optimistic and pessimistic locking, in depth</ForwardChip>

The classic implementation wraps `count++` in a semaphore, so that only one thread at a time enters it and every other thread waits. The semaphore has to have a single permit for this to work. Java’s documentation calls a semaphore “initialized to one” a binary semaphore and says it can serve as a mutual-exclusion lock <Cite href="https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/Semaphore.html">docs.oracle.com</Cite>. For a plain counter you can skip the lock: an atomic increment such as `AtomicInteger.incrementAndGet()` does the read, add and write as one step <Cite href="https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/atomic/AtomicInteger.html">docs.oracle.com</Cite>. [[L-0223]]

```java
Semaphore gate = new Semaphore(1);   // one permit: one thread inside at a time
gate.acquire();
try { count++; } finally { gate.release(); }

// a plain counter needs no lock at all
AtomicInteger count = new AtomicInteger();
count.incrementAndGet();
```

A traffic signal at a crossroads works the same way. The middle of the junction is the shared resource, the critical section. One road’s signal turns green and its traffic uses the junction; the others are red and wait. Then that signal turns red and the next one turns green. [[L-0224]]

<Figure id="fig-4c" no="Fig 4·c" wide={false} k="L-0224 L-0225"
  caption="The junction is the critical section. One road has green; the other three wait at red.">
  <Desk><TrafficSignal /></Desk>
  <Phone><TrafficSignal layout="phone" /></Phone>
</Figure>

That is **pessimistic locking**: lock the other threads out while one of them uses the shared resource, and when it is done, give the next one its chance. [[L-0225]] It is implemented with mutexes and semaphores. [[L-0227]] Much of computer science works like this. It borrows from how people already behave, and you can see it in action on any street corner. [[L-0226]]

### Going lock-free [[rail: Lock-free]]

You can also avoid locks altogether. Lock-free data structures exist, and CRDTs are among them, some of the most brilliant data structures there are. They are advanced and aren’t covered in this course, but know that they exist. [[L-0228]]

<SourceNote href="https://crdt.tech/" k="L-0228">

These are two different families. CRDTs (conflict-free replicated data types) are replicated: copies on different machines are updated independently and merged later without coordination. “Lock-free data structures” usually means concurrent structures on a single machine, built on an atomic compare-and-swap, as in Java’s <Cite href="https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/atomic/AtomicInteger.html">AtomicInteger</Cite>.

</SourceNote>

### Medium’s claps

For Medium, the count doesn’t live in a thread’s memory. It lives in a row of the database, and that is where it gets protected:

<RuleBox rule="We protect our data through ==transactions== and ==atomic instructions==." k="L-0231">

Use the database’s transactions, with their ACID guarantees, or, short of transactions, the database’s atomic operations. For a counter, the atomic operation is a single statement, `claps = claps + 1`, which leaves the read, the add and the write to the database.

<Desk><ProtectTheData /></Desk>
<Phone><ProtectTheData layout="phone" /></Phone>

</RuleBox>

<SourceNote href="https://www.postgresql.org/docs/current/transaction-iso.html" k="L-0231">

A transaction by itself doesn’t save the clap if the app reads the count, adds one in code and writes it back. Under PostgreSQL’s default isolation level, READ COMMITTED, both requests can read 100 and both write 101. What works is an in-SQL increment (`UPDATE … SET claps = claps + 1`, which applies to the latest committed version of the row), `SELECT … FOR UPDATE` <Cite href="https://www.postgresql.org/docs/current/explicit-locking.html">postgresql.org</Cite>, or REPEATABLE READ or SERIALIZABLE with a retry.

</SourceNote>

```js
// unsafe, even inside a transaction under READ COMMITTED:
// both requests can read 100, and both write 101
const { rows } = await db.query('SELECT claps FROM stories WHERE id = $1', [storyId]);
await db.query('UPDATE stories SET claps = $1 WHERE id = $2', [rows[0].claps + 1, storyId]);

// safe: the database reads, adds and writes in one statement
await db.query('UPDATE stories SET claps = claps + 1 WHERE id = $1', [storyId]);
```

The §3 worker already used the safe shape: `total_blogs = total_blogs + 1` is the same in-SQL increment, so two workers handling two different `ON_PUBLISH` messages at once can’t lose one.

<RecallQuestions>
  <RecallItem k="L-0219" q="Two threads each run <code>count++</code> 1,000 times on a shared counter, and the result is 1,997. What happened to the other 3?">

They were lost updates. `count++` is a read, an add and a write. Three times, both threads read the same value before either wrote, so both wrote the same result and one increment overwrote the other. Nothing failed; the count is simply short.

  </RecallItem>
  <RecallItem k="L-0231" q="Why does wrapping the read, add and write in a transaction not by itself save the clap count under PostgreSQL’s default isolation, and what does?">

Under READ COMMITTED both transactions can still read 100 and both write 101: the transaction doesn’t stop two reads of the same value. What works is letting the database do the increment (`UPDATE stories SET claps = claps + 1`), locking the row with `SELECT … FOR UPDATE`, or a stricter isolation level with a retry.

  </RecallItem>
  <RecallItem k="L-0196 L-0230" q="How is the §3 double count different from the §4 lost update, and what does each need?">

The double count comes from at-least-once delivery: the same `ON_PUBLISH` message is processed twice, so the count is one too high. It needs consumers that tolerate a repeat. The lost update comes from two increments interleaving, so the count is one too low. It needs the increment to be one indivisible step: an atomic operation or a transaction that really isolates it.

  </RecallItem>
</RecallQuestions>
