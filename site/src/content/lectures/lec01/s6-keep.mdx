### Ten lines to keep [[rail: Heuristics]]

The same few ideas kept coming back, whatever box was on the board:

1. A cache is anything that saves an expensive computation or an expensive I/O, not only something that sits in RAM ([§1.1](#s1-1)). [[L-0058]]
2. Question every component and ask what it could do for you. If “cache” means central RAM to you, you will never think of caching on the API server’s disk ([§1.1](#s1-1)). [[L-0064]]
3. CS fundamentals go a long way. The hardware ceiling in [§2.2](#s2-2) comes straight from computer architecture. [[L-0085]] By the same token, so does the `count++` race in [§4.2](#s4-2).
4. Scale bottom up: the database and every other dependency first, then the API servers ([§2.4](#s2-4)). And protect the database, the most brittle part of the system ([§3.2](#s3-2)). [[L-0100 L-0150]]
5. Build the plain version first, such as two connections or one pool per shard, and add the proxy later ([§2.4](#s2-4)). [[L-0119]]
6. Whatever does not need to be done in real time should not be done in real time ([§3.1](#s3-1)). [[L-0137]]
7. Kafka is not salt to sprinkle over every design, and neither is any other tool. Don’t say “X doesn’t support Y” without checking what it supports today ([§3.8](#s3-8)). [[L-0200 L-0396]]
8. Always think about cost. A design that isn’t cost-efficient won’t see the light of day, however clever it is ([§3.8](#s3-8)). [[L-0206]]
9. Pick the channel the use case needs, and build the hello world of each one to really know it ([§5.7](#s5-7)). [[L-0278 L-0272]]
10. Look things up in the primary docs yourself. You often find something more interesting than what you went looking for. [[L-0004]]

<MarginNote title="Out of scope on purpose" why="skip unless you were wondering" k="L-0350 L-0351 L-0352 L-0353 L-0354 L-0355">

Security isn’t part of this course, because it isn’t high-level architecture. The exact list of topics the course covers is on the instructor’s website. [[L-0351]] Real system designers do have to care about security, but covering it opens a Pandora’s box of infrastructure security and cloud best practices that would pull the course away from its focus. [[L-0352]]

Application-security topics such as rate limiters, DDoS and SQL injection are standard and well documented elsewhere, so there is little this course could add. [[L-0353]] Handling DDoS essentially comes down to rate limiting: add a rate limiter at a different layer. [[L-0354]]

<SourceNote label="Correction" href="https://docs.aws.amazon.com/whitepapers/latest/aws-best-practices-ddos-resiliency/infrastructure-layer-attacks.html" k="L-0354">

Rate limiting helps against some application-layer (L7) floods, but not against the most common DDoS attacks. UDP reflection and SYN floods are infrastructure-layer attacks that fill the network before any limiter sees them. Mitigating them needs capacity that scales faster than the flood, absorbed or filtered upstream by CDN or anycast scrubbing, AWS Shield or <Cite href="https://developers.cloudflare.com/ddos-protection/about/attack-coverage/">Cloudflare</Cite>.

</SourceNote>

SQL injection has standard ways to prevent it, and for a CVE you know exactly how to patch. [[L-0355]] Compression is basic too, and not a deep topic for this course: there are three or four algorithms, so pick the one that suits you best. [[L-0350]]

</MarginNote>
