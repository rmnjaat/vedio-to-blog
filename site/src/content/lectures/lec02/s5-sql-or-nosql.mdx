<Section id="s5" no="5" title="Why they scale, and when to pick SQL" crumb="5 SQL or NoSQL"
  dek="No relations means no checks, so the data can spread out. Every database has a backstory, and there is a broad rule for choosing between correctness and ingestion."
  meta="About 7 min · class 00:40–00:47">

Slack's tables, the ones chapter 6 builds (users, channels, membership, messages), are relational in shape: a message belongs to a channel, a membership row joins a user to a channel. People say non-relational databases scale. Why do they, and does that mean Slack needs one?

The class asked the first half of that question itself, as the more fundamental question behind the four families: why do people say that non-relational databases scale? This short chapter answers it, then gives the lecture's broad rule for choosing.

</Section>

<Section id="s5-1" no="5.1" title="No relations, no checks" crumb="5.1 No relations"
  dek="What a foreign key makes the database check on every insert and delete, and why those checks tie the data to one place."
  meta="About 3 min · class 00:40–00:42">

Non-relational databases scale because there are no relations. [[L-0109]] The board added two more reasons that weren't spoken: in a non-relational store the data can be denormalized, and it is modelled to be sharded. [[L-0109]] Beneath the three reasons the board added, in pink: “We can also achieve [these] on SQL databases. So, saying SQL does not scale is not entirely correct.” Give up the constraints that don’t help you scale horizontally and a relational database partitions the same way ([1.3](#s1-3)). [[L-0024]]

What relational databases are good at comes from those relations: the foreign-key constraints ensure the data is correct. If a table has a non-null foreign key to another table, you are not allowed to insert a row whose referenced row doesn't exist. The database needs that other row to exist before it lets you insert this one. [[L-0110]] Deletion works the same way in reverse: until all the child entries are deleted, the parent entry can't be deleted. [[L-0111]]

<Figure id="fig-5a" no="Fig 5·a" k="L-0110 L-0111 L-0112 L-0116"
  caption="A foreign key from messages.channel_id to channels.id. It rejects a message for a channel that doesn't exist and blocks deleting a channel that still has messages. Split the two tables across machines and every such check becomes a cross-machine call.">
  <Desk><ForeignKeyChecks /></Desk>
  <Phone><ForeignKeyChecks layout="phone" /></Phone>
</Figure>

This is how a relational database keeps the system correct and the data strongly consistent: the system moves from one consistent state to another, and the database ensures it by enforcing relations and constraints on the data. [[L-0112]] Non-relational databases give up on that. Their attitude is: I don't care what you insert, I don't care whether that key exists or not, just insert the data you want. [[L-0113]]

That is the restricting factor for scaling a relational database: its relations and consistency guarantees need all the related data to be in one place. Non-relational databases typically don't give you those features, so they aren't bound by it. [[L-0116]] Which means the fix is simple if you want to scale a relational database this way: don't use foreign keys. Without constraints and foreign keys, you can partition a relational database exactly the way a non-relational database partitions its data, the point [1.3](#s1-3) made with <LectureLink lec="lec05" sec="s9-3">Lecture 03's sharded key-value store</LectureLink>. [[L-0116]]

</Section>

<Section id="s5-2" no="5.2" title="Every database has a backstory" crumb="5.2 Backstories"
  dek="Relational databases didn't choose wrong. They chose correctness for the jobs they were first built for, and every other database made its own trade."
  meta="About 2 min · class 00:41–00:43, 00:46">

So did relational databases make the wrong choice? Not as the lecture tells their backstory. They went for correctness because the first set of use cases they were built for were financial, where the correctness of the data mattered more than performing at scale. They chose data consistency and strong consistency over a high ingestion rate. That doesn't make them worse than non-relational databases. [[L-0114]]

Every database has a backstory like this, one that explains its design decisions, and you should be aware of it. [[L-0115]]

<Figure id="fig-5-backstory" no="Sketch 5·1" max={340} wide={false} k="L-0114 L-0115 L-0117" caption="Relational databases’ backstory, as the lecture tells it: built first for financial work, they kept correctness and traded away ingestion speed. Ask the same two questions of every database.">
  <Backstory />
</Figure>

That leads to a habit worth keeping. When a database claims to be great at something, understand why it is great at it and what it gives up to get there. Then see whether you can mimic the same thing on the database you already know, and that need not be a SQL database: it can be a non-relational one too. [[L-0117]]

And never get stuck on one technology: “I only use this database, every other database sucks.” Be flexible. Every database is unique in its own flavour. Look beneath the first layers of fancy UI and see why it gets the performance it gets. Throughout the course, every database decision weighs all these factors, so don't be rigid about a particular database, and don't decide to use NoSQL everywhere. [[L-0118]]

</Section>

<Section id="s5-3" no="5.3" title="SQL or NoSQL?" crumb="5.3 SQL or NoSQL?"
  dek="“The biggest question of all time”, answered broadly: correctness and its tooling on one side, gigantic fast ingestion and sharding on the other."
  meta="About 3 min · class 00:43–00:47, 00:53">

Now the biggest question of all time: SQL or NoSQL?

SQL's strength is data correctness, or consistency: strong consistency. When the correctness of the data is the most important feature of your application, you need ACID, and if you need ACID, go for SQL; don't look beyond it. The board's “when to use SQL?” list: ACID; relations and constraints; a fixed schema. [[L-0119]] SQL gives you the tooling to make sure your data never reaches an inconsistent or incorrect state: foreign-key checks, check constraints and the like. But it doesn't apply them for you. You have to apply them. [[L-0120]]

When should you use a non-relational database? A very simple way to look at it: when you have gigantic data to ingest at a fast pace. A huge influx of messages on Instagram, huge numbers of posts being written, logs being dumped, metrics. [[L-0121]] Those use cases don't optimise for correctness. It's okay if a piece of data is here or there, if an attribute is missing, if some data is lost: metrics ingestion, log ingestion, message ingestion. [[L-0122]] More exactly, such workloads relax constraints and cross-node consistency, but durability is still expected, especially for user messages. Cassandra, for example, records every write in an append-only commit log on disk, which keeps writes durable even after an unexpected shutdown <Cite href="https://cassandra.apache.org/doc/latest/cassandra/architecture/storage-engine.html">cassandra.apache.org</Cite>. [[L-0122]]

Cassandra is the class's example of a store built for this. It gives you sharding out of the box and drops those constraints, so it is very light on the database and heavily partitioned, or sharded. [[L-0123]] That is why messaging systems, live interactions, polls and the like typically keep their data in non-relational databases: sharding and partitioning come out of the box, and constraints are dropped. With SQL you would have to build those yourself. [[L-0124]]

The board's “when to use NoSQL?” list: there are no relations, the data can be denormalized, and the data can be sharded. [[L-0126]] Put together, as a very broad rule:

<RuleBox rule="When ==correctness and consistency== matter and you want the tooling out of the box, pick SQL. For a ==very high ingestion rate== and sharding out of the box, pick a non-relational store." k="L-0125">

The class gave this as “a very broad sense in which I'm putting it out”, not a law. Over the course, every database choice weighs all of these factors.

  <RecallItem k="L-0110 L-0111 L-0116" q="What exactly does a foreign key force the database to do on insert and on delete, and why does that tie the data to one place?">

On insert, it rejects a row whose referenced (parent) row doesn't exist. On delete, it refuses to delete a parent while child rows still point at it. Both checks need the related rows where the database can see them, so the guarantees need all the data in one place. Drop the foreign keys and a relational database can be partitioned like any non-relational store.

  </RecallItem>
  <RecallItem k="L-0121 L-0125" q="Give the class's broad rule for SQL vs a non-relational store, and one example workload on each side.">

When correctness and consistency matter and you want the tooling out of the box, SQL: data whose correctness is the whole point, like the financial use cases relational databases were built for. For a very high ingestion rate with sharding out of the box, a non-relational store: a huge influx of messages, logs or metrics. It is “a very broad” rule.
