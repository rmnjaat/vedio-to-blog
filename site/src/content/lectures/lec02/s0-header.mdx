This is day 2 of week 2, and the class has two halves. The first, about an hour and five to an hour and ten minutes, is a brief overview of the non-relational databases: where to use each type and, with more weight, where *not* to use it. [[L-0004 L-0001]]

That tour only scratches the surface. The families lay the foundation for what comes later, and each one is used again, in more granular detail, in the weeks ahead. <ForwardChip label="comes in Lectures 09 and 10" k="L-0003" /> Lecture 09 builds a Redis-like cache, and Lecture 10 builds storage from files and column formats. [[L-0003]]

The second half is a long design of Slack’s real-time communication, limited to text. Its promise: in this one design you can switch from one message delivery model to another and get something like Slack, something like WhatsApp or something like Zoom chat. Once Slack is done, those are a piece of cake. [[L-0004 L-0005]]

**How to use this page.** Each chapter is its own page, and the ten of them follow the class’s order. Chapters 1 to 5 are the database tour; chapters 6 to 10 are the Slack design, built up one decision at a time.

</MarginNote>

### Slack so far

Slack is new to the course, but most of what this page builds on is not. In <LectureLink lec="lec01" sec="s5">Lecture 02 (§5)</LectureLink> Medium learned the real-time channels: short polling, long polling, server-sent events and WebSockets. Two questions were left for this session there: how to scale WebSockets properly, and how a real-time product like Slack builds its messaging on them. <LectureLink lec="lec04" sec="s2">Lecture 01’s online/offline indicator</LectureLink> points here too: real presence indicators ride a persistent connection, the way Slack does it.

Two more pieces come back. <LectureLink lec="lec01" sec="s3-5">Lecture 02 (§3.5–3.7)</LectureLink> introduced Kafka, the message stream whose consumers pull, and <LectureLink lec="lec01" sec="s2-4">Lecture 02 (§2.4)</LectureLink> scaled a database with read replicas and sharding. Lecture 03 built a key-value store on MySQL and sharded it by key range, keys A to M on one database and N to Z on another (<LectureLink lec="lec05" sec="s9-3">Lecture 03, §9.3</LectureLink>). This page uses that store twice: as proof that relational databases scale too ([§1.3](#s1-3)), and as the key-value store with JSON values that makes document databases make sense ([§2.1](#s2-1)). <LectureLink lec="lec04" sec="s3">Lecture 01 (§3)</LectureLink> already weighed Redis against DynamoDB; both return as key-value stores in [§2.4](#s2-4).

So, as the class starts, Slack has nothing: no tables, no servers. [Chapter 6](#s6) begins with the requirements card, and every box after it is added for a reason.
