Your team is about to store every message of a Slack-like chat app. In the design review someone says: “Use NoSQL. Messaging systems always do. It scales.” Everyone nods. By the end of the first half of this lecture you won’t. You’ll ask which database, for what workload, and what it gave up to scale, and you’ll have your own answer for the messages. [[L-0002 L-0021 L-0124]]

Then a harder problem. Five people are in a Slack channel. A types “standup in 5” and presses Enter. B, C, D and E must see it at once, without refreshing, even though E’s app happens to be connected to a different server from the other four. And if anyone refreshes the page a second later, the message must still be there. [[L-0148 L-0243 L-0244]]

### Where you are

<LectureLink lec="lec05">Lecture 3</LectureLink> ended on a key-value store you built on one MySQL table and then split by key range, keys A to M on one database and N to Z on another. It also ended on a question: Redis keeps everything in memory, DynamoDB isn’t relational at all, so what did stores like these give up to be fast and big, and when is that trade worth it? [[L-0023]]

You have the pieces for the second problem too. <LectureLink lec="lec01">Lecture 2</LectureLink> kept a WebSocket open so a reader saw new claps without refreshing, and warned that the hard part of WebSockets is knowing which server holds which reader. It also introduced Kafka, the stream that keeps messages and lets each consumer read them at its own pace. <LectureLink lec="lec04">Lecture 1</LectureLink>’s green dot pointed here as well: production presence systems keep a persistent connection open, and this lecture builds Slack’s messaging on connections like that.

### What you’ll build

**Build 1, a field guide to the database families (chapters 1–4).** Take the slogan apart: why dropping relations lets data spread, and which of two “consistencies” gets traded away. Then meet document, key-value, column-oriented and graph databases, each through the one thing it does well and the one thing it gives up for it, and end with a rule for choosing SQL or not. [[L-0004 L-0109 L-0125]]

**Build 2, Slack’s real-time text chat (chapters 5–10).** The guide’s last question is the first Slack decision: which database holds the messages. Then the problem changes. Storing messages is the easy part; the hard part is moving one message to every member of a channel in a blink when the members sit on different servers. You build the tables, decide how a message is sent and what Slack promises about it, then connect the servers, first in the simplest way that works and then in a way that survives a hundred of them. [[L-0145 L-0147 L-0150]]

What carries over from the first build is the habit it drills: before you accept a design, ask what it gives up, and choose by the guarantee you owe, not by the tool you happen to like. [[L-0186]]

### What you’ll be able to do

- Answer “NoSQL scales” with the right questions, and say what each family gives up.
- Choose SQL or not for a workload, and shard by the key every operation uses.
- Design a chat schema where direct messages and unread counts need no extra machinery.
- Decide how a message is sent and stored from the guarantee the product owes.
- Scale real-time delivery past one server without wasting the connections it exists to serve.
- Name what can still go wrong, and what covers each failure.

### Before you start

You need SQL basics, sharding from Lecture 3, and what a WebSocket is from Lecture 2. Every box in the Slack design runs on a laptop. Each chapter opens with a small map of the design so far. When a “Pause and think” box asks you something, commit to an answer before you open it.
