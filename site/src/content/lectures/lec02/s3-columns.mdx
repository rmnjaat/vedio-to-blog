<Section id="s3" no="3" title="Column-oriented databases" crumb="3 Column stores"
  dek="Same table, two layouts on disk. Why an analytics query reads two files instead of every row, why warehouses compress so well, and why they are never the primary copy."
  meta="About 15 min · class 00:15–00:30">

Slack’s data team wants one number over billions of message rows, say the average message length per day. Every row also carries ids, the text and a handful of flags that this question never touches. How much of each row does the database have to read to answer it?

That is this page’s framing. The class asked the same question of a table with the same shape, a stock-market table, so this chapter uses the class’s example from here on.

</Section>

<Section id="s3-1" no="3.1" title="Rows and columns on disk" crumb="3.1 Rows and columns"
  dek="The same table can sit on disk row by row or column by column."
  meta="About 3 min · class 00:15–00:18">

Column-oriented databases exploit how people query the system. They are a type the teacher is personally a fan of. [[L-0050]] Strictly, “column-oriented” is a storage layout rather than a separate non-relational family: BigQuery <Cite href="https://docs.cloud.google.com/bigquery/docs/storage_overview">cloud.google.com</Cite> and Redshift <Cite href="https://docs.aws.amazon.com/redshift/latest/dg/c_columnar_storage_disk_mem_mgmnt.html">docs.aws.amazon.com</Cite> are SQL warehouses that store each column separately. “Wide-column” stores such as Cassandra are a different idea. [[L-0050]]

Start with the layout you already know. When we draw a table, we draw one row together, with all its columns side by side. In a row-oriented database that is also how it is stored: all the columns, the attributes, of a row sit together. [[L-0051]]

The running example is a table called `stock_ticks` that records the price of every listed stock, with the columns `symbol`, `price`, `name`, `exchange` and `timestamp`. Every tick adds an entry. [[L-0052]]

<Figure id="fig-3a" no="Fig 3·a" max={760} k="L-0051 L-0052 L-0053 L-0054" caption="Left: a row store keeps each row’s five values in one strip. Right: a column store keeps each column’s values together, so the lines R1, R2 and R3 cross every column block. On a phone the header says ts for timestamp. Redrawn from the class board at 00:18.">
  <Desk><RowVsColumn /></Desk>
  <Phone><RowVsColumn layout="phone" /></Phone>
</Figure>

In a row-oriented database, all five columns of a row are stacked one after another and persisted on disk as one row. So when you read, you read the complete row. Write a `SELECT` that names just two columns instead of a star, and the disk still reads the entire row; the engine then filters out what you need and serves it. [[L-0053]]

A column-oriented database does the opposite: it stacks the values of one column across many rows together. With three rows, the three values of column 1 sit together, then the three values of column 2, and so on. [[L-0054]]

A very crude, very naive way to picture it, and only a picture: one separate file per column. Line 1 of each file holds that column’s value for row 1, line 2 holds row 2, and so on. The file for column 1 has three lines for three rows, then there is a file for column 2 with its three values, and so on. [[L-0055]]

<Figure id="fig-3b" no="Fig 3·b" max={760} k="L-0055" caption="The naive model: one file per column. The values of row 2 are line 2 of every file. Real column stores are smarter than this, but it is enough to reason about which files a query must open.">

  <Phone><FilePerColumn layout="phone" /></Phone>
</Figure>

<Section id="s3-2" no="3.2" title="One query, two layouts" crumb="3.2 One query"
  dek="One day’s average price: the row store reads every column of every row; the column store opens two files."
  meta="About 4 min · class 00:18–00:22, Q&A 00:26">

Now a question for the table: the average price of the entire stock market for one day. The board framed it as a table with 100 columns on which you want to run analytics, with the query written like this: [[L-0056]]

```sql
SELECT avg(price) WHERE ts = '___';
```

Say about 10,000 companies are listed, so the date has about 10,000 entries. In a row store, the engine goes through each of those rows: it reads the row, sees all five columns, picks out the two it needs, `timestamp` and `price`, and averages them. [[L-0057]]

<PauseAndThink k="L-0053 L-0056 L-0057 L-0058 L-0059 L-0062 L-0071"
  q="<code>stock_ticks</code> has five columns (symbol, price, name, exchange, ts) and about 10,000 rows for today. You run <code>SELECT avg(price)</code> for today and name only those two columns. Does naming them make a row store read less from disk?"
  choices={[{ label: 'Yes: it reads only the two columns it was asked for' }, { label: 'No: it still reads every column of every row', correct: true }]}
  right="Right: projection filters after the read; the column store is the one that skips files."
  wrong="Naming columns changes what comes back, not what the disk reads in a row store.">

No. A row store keeps each row’s five values side by side, so it reads the whole row and only then picks out `price` and `ts`. It can’t jump to the next row’s price without passing over this row’s symbol, name and exchange. A column store opens two files, `price` and `ts`, and does no IO at all for the other three. With a hundred columns, the row store reads all hundred to use two.

</PauseAndThink>

<AnimationClip clip="l02-column-scan" no="Clip 3·1" k="L-0053 L-0056 L-0057 L-0058 L-0059 L-0062"
  lead="Five columns, 10,000 rows. How much does each layout read to answer one average?"
  caption="SELECT avg(price) on 10,000 rows: the row store reads every row whole and discards three columns; the column store opens two files. With 100 columns it is 100 against 2." />

So the row store reads `symbol`, `name` and `exchange` for nothing, and wastes disk IO on them. You didn’t project them in the `SELECT`, but the engine still has to skim through them to get to the next row. The board put the 100-column version bluntly: a row database “will go row by row reading all columns & discarding 98 of them”. [[L-0058]] Redshift’s documentation gives the same arithmetic: in a 100-column table, a query that uses five columns reads only about five percent of the data in a column store, while a row-wise database would also read the blocks holding the other 95 <Cite href="https://docs.aws.amazon.com/redshift/latest/dg/c_columnar_storage_disk_mem_mgmnt.html">docs.aws.amazon.com</Cite>. [[L-0058]]

Why can’t it just skip them? Because the row is the unit on disk. Unless the engine knows where this row ends, it can’t pick out the corresponding columns of the next one. [[L-0059]]

And real tables are far wider than five columns. Data warehouses have thousands of columns, and the teacher stressed that he was not exaggerating. [[L-0060]]

On a column store the same query reads exactly two files, `price` and `timestamp`. It does no disk IO at all for `symbol`, `name` and `exchange`. That is extremely efficient. [[L-0062]]

This was also asked in class: when a `SELECT` names specific columns, does the database still read all of them? In a row-oriented database, yes. The disk reads all the columns and the engine picks out the ones you need. In a column-oriented database it doesn’t: think of separate files, and you never spend time reading the columns you don’t need. [[L-0071]]

</Section>

<Section id="s3-3" no="3.3" title="Analytics, never the primary copy" crumb="3.3 Analytics only"
  dek="So why isn’t every database columnar? Because most applications read whole rows."
  meta="About 5 min · class 00:21–00:27">

So why isn’t every database columnar? Look at what the query did. If your use case is very likely to touch only a few of many columns, which is the classic analytics query, column-oriented databases work well. [[L-0061]]

That is where they thrive, on a few columns out of hundreds or thousands, and it is why they power data warehouses such as Amazon Redshift and Google BigQuery. [[L-0063]] In data engineering, file formats such as Parquet use the same column-oriented layout, so that you read the bare minimum to get things done. [[L-0064]]

The other direction fails. You can build a transactional application such as a blogging site on a column-oriented database, but you shouldn’t, because you are very likely to read the entire row. Rendering a user’s profile reads all of its 10 or 15 columns together, almost always: in most cases it is a `SELECT *`. [[L-0065]]

<RuleBox rule="Transactional reads whole rows: ==store by row==. Analytics reads a few of many columns: ==store by column==." k="L-0066">

The query decides the layout. A transactional app almost always wants every column of a row. An analytics query is very picky about columns: two, three or 10 out of a thousand.

<Desk><LayoutRule /></Desk>
<Phone><LayoutRule layout="phone" /></Phone>

</RuleBox>

Notice what changed. Only the way the data is stored on disk, and that alone gives a massive performance boost without touching the layers above. That is the beauty of having abstractions in the right place. [[L-0068]]

It isn’t free. Suggested in class: inserts would be too heavy in a column-oriented database. The teacher agreed: you get some, you lose some, and given the benefits it is fine. [[L-0072]] ClickHouse, for example, recommends inserting in batches of at least 1,000 rows, ideally 10,000 to 100,000, because each synchronous insert creates a new storage part on disk <Cite href="https://clickhouse.com/docs/best-practices/selecting-an-insert-strategy">clickhouse.com</Cite>. [[L-0072]]

That is also why you never see column-oriented databases used as the primary database. They serve analytics workloads, and the data warehouse is never the primary copy of the data. [[L-0073]] More exactly, a column-oriented warehouse is usually not the primary copy of transactional data: it is fed from the operational databases for analytics <Cite href="https://clickhouse.com/docs/best-practices/selecting-an-insert-strategy">clickhouse.com</Cite>. [[L-0073]]

The primary copy lives in the traditional databases: MySQL, PostgreSQL, MongoDB, DynamoDB and the rest. From there a job ingests the data into the column-oriented warehouse, just to power the analytics. [[L-0074]]

<Section id="s3-4" no="3.4" title="Compression and cost" crumb="3.4 Compression and cost"
  dek="A column of one kind of value compresses very well. What you pay for depends on the product."
  meta="About 3 min · class Q&A 00:27–00:30">

Does a column store take more space than a row store, or less? Much less. Each column holds one kind of value, so it can be compressed very heavily. Timestamps, for example, are almost discrete values rather than continuous ones. A row store’s data is heterogeneous, so compression still helps, but nowhere near as much. [[L-0075]] In the instructor’s experience, a 29x gain is normal. [[L-0076]]

How can the data shrink that much? Take the symbol column: Apple, Google and so on, a small set of discrete values repeated over and over. Instead of storing the full string each time, the store can represent each value with a small fixed-size code (the class said one byte, then corrected it to four). Because there is so little variation, the compression is very heavy. [[L-0077]] Parquet does exactly this with dictionary encoding: it builds a dictionary of the values in a column and stores small codes instead, then packs repeated codes with run-length encoding and bit-packing <Cite href="https://parquet.apache.org/docs/file-format/data-pages/encodings/">parquet.apache.org</Cite>. [[L-0077]]

<Figure id="fig-3d" no="Fig 3·d" max={340} wide={false} k="L-0075 L-0077 L-0078 L-0079 L-0080" caption="Top: a homogeneous column becomes small codes, then runs. Bottom: a row mixes a symbol, a price, a name, an exchange and a time, which compresses less. Values are illustrative.">
<WhyCompress />
</Figure>

General-purpose compression works really well on such data too: Huffman, Snappy and LZ compression, because the data is so homogeneous. It isn’t a string here, an integer there and a huge string after that; it is all very similar data. [[L-0078]]

You don’t have to do any of this yourself. You pass the normal strings, and the engine compresses them internally. A column with five or six distinct values can be represented in one byte per value. [[L-0079]] Read about run-length encoding once. [[L-0080]]

Cloud providers charge non-relational databases per read and write operation. Are column-oriented databases priced the same way? The class’s answer was no: column-oriented databases run continuously, so you pre-provision the capacity you need and pay for the servers you run. You are charged for IOPS, but it isn’t on-demand pricing per operation. [[L-0081]]

<SourceNote href="https://docs.cloud.google.com/bigquery/docs/estimate-costs" site="cloud.google.com (BigQuery pricing)" k="L-0081">

It depends on the product. Provisioned warehouses do charge for reserved servers, but BigQuery’s on-demand model bills each query by the bytes it reads, with capacity (slot) pricing as the reserved alternative. Redshift Serverless bills for compute actually used, per second, with optional reservations <Cite href="https://docs.aws.amazon.com/redshift/latest/mgmt/serverless-billing.html">docs.aws.amazon.com</Cite>.

</SourceNote>

Summed up in class as “reserved capacity”, and the teacher agreed it was put better that way. [[L-0082]] Reserved capacity is one pricing option, not the only one: as the note above says, BigQuery on demand bills per bytes read <Cite href="https://docs.cloud.google.com/bigquery/docs/estimate-costs">cloud.google.com</Cite>. [[L-0082]]

Back to Slack’s data team. The average message length per day touches two columns, the length and the date, out of many. It belongs in a column-oriented warehouse fed from the message store, not in the message store itself. Columns changed how one table sits on disk. The next family stores something else entirely: edges.

<RecallQuestions>
  <RecallItem k="L-0053 L-0058 L-0059 L-0062" q="A table has 100 columns and the query touches 2. Roughly how much does a row store read compared with a column store, and why can’t the row store skip?">

The row store reads all 100 columns of every row it scans and discards 98; the column store reads only the two columns’ files, about 2 of 100. The row store can’t skip because a row is stored as one unit on disk: without passing over the row it doesn’t know where it ends, so it can’t reach the next row’s columns.

  </RecallItem>
  <RecallItem k="L-0065 L-0066 L-0073" q="Why should a blogging app not run on BigQuery, even though BigQuery speaks SQL?">

A blogging app is transactional: rendering a profile or a post reads all of a row’s 10–15 columns, a `SELECT *`, which is exactly what a column layout is bad at; inserts are heavy too. Column stores are for analytics and are never the primary copy; the app’s data lives in MySQL, PostgreSQL and the like, and a job copies it into the warehouse.

  </RecallItem>
  <RecallItem k="L-0075 L-0077 L-0079" q="Why do column files compress so much better than rows?">

Each column holds one kind of value, often from a small set (stock symbols, near-discrete timestamps), so repeated values become small codes and runs. A row mixes strings, numbers and times, which compresses far less. The engine does this internally; you pass normal values.

  </RecallItem>
</RecallQuestions>
