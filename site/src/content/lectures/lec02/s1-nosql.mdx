Slack has to keep every channel's history so that anyone can scroll back through it. [[L-0148]] In a design review someone says: “Use NoSQL. It scales.” Is that an answer?

This page frames the first half of the lecture with that question. The class didn’t ask it about Slack. It asked it about databases in general, and the next five chapters answer it with the lecture’s own examples. The short answer is no. It is a label and a slogan, and the rest of this chapter takes both apart.

</Section>

<Section id="s1-1" no="1.1" title="Name the database, not the family" crumb="1.1 Name the database"
  dek="Replace “NoSQL” with the name of a database and the workload it was built for."
  meta="About 3 min · class 00:02–00:04 and 00:07">

“Always use a NoSQL database” is advice you will hear a lot. It isn’t true. Plenty of people promote their non-relational database as a challenger to the relational one, but most of the databases out there were built to solve very specific problems. [[L-0002]]

So the first habit of this lecture is about words. There shouldn’t really be a term like “non-relational” or “NoSQL” at all. It puts everything that isn’t MySQL, Postgres or Oracle under one blanket, a bit like sorting people into “technical” and “non-technical”, which is unfair to the second group. Name the specific type of database you mean. [[L-0008]]

The blanket hides real differences. Take the slogan from the design review: “NoSQL databases scale.” As a blanket statement it is wrong. You can build a non-relational database that doesn’t scale at all; that is entirely possible. [[L-0009]] And the ones that do scale, scale for something. Cassandra scales, but for a very specific workload. MongoDB scales for a very specific workload. DynamoDB scales for a very specific workload. [[L-0021]]

<Figure id="fig-1-names" no="Sketch 1·1" max={340} wide={false} k="L-0002 L-0008 L-0021" caption="“NoSQL” is one blanket over very different stores. Name the database and the workload it was built for; each type has its own chapter below.">
  <NamedStores />
</Figure>

That is why it is worth learning the types beyond the famous MySQL and Postgres: so you know where a particular type should be used, and where it shouldn’t. [[L-0010]]

What do these databases have in common, then? The very general distinction is that they are not relationally structured. Nothing stops anyone from structuring them relationally, and people do, which is why the space is messy. [[L-0012]]

This page follows the class’s own rule. “NoSQL” and “non-relational” appear in this introduction, because that is how people talk. After it, every database is named by its exact type. [[L-0011]]

</Section>

<Section id="s1-2" no="1.2" title="Two meanings of consistency" crumb="1.2 Two consistencies"
  dek="“They give up consistency” is the usual one-line answer. Which consistency?"
  meta="About 3 min · class 00:04–00:07">

Ask what non-relational databases trade away and the usual answer is one line. As a very broad separation, and one that is not always true, non-relational databases typically give up consistency to give you scalability. [[L-0013]]

The catch is the word “consistency”. There are two of them: consistency in the CAP theorem is different from consistency in ACID. Computer scientists are bad at naming things. [[L-0014]]

<Figure id="fig-1a" no="Fig 1·a" max={760} k="L-0014 L-0015 L-0016 L-0020" caption="Left: ACID’s consistency is about correctness; every transaction leaves the data in a correct state. Right: CAP’s consistency is about visibility; a read from another node right after a write either sees it (strong) or doesn’t yet (eventual). The replica catches up by pulling.">
  <Desk><TwoConsistencies /></Desk>
  <Phone><TwoConsistencies layout="phone" /></Phone>
</Figure>

Consistency in ACID is about the data being correct. You don’t mess with it: the database moves from one correct state to another. [[L-0015]]

Consistency in the CAP theorem is about visibility: once you write data, it is available to query right away. That is strong consistency, and it is the consistency non-relational databases give up. [[L-0016]] The precise name for CAP’s consistency is linearizability: if a read starts after a write has completed, it must see that write or a newer one. A database can be ACID and still not be linearizable <Cite href="https://martin.kleppmann.com/2015/05/11/please-stop-calling-databases-cp-or-ap.html">martin.kleppmann.com</Cite>. [[L-0016]]

What do they get in return? The class board put it like this: “In most cases, NoSQL databases provide scalability and availability by compromising consistency.” With multiple nodes, you can scale the system horizontally and stay highly available. [[L-0017]]

<Figure id="fig-1b" no="Fig 1·b" max={760} k="L-0017 L-0018 L-0019" caption="Left: one database instance holds everything, so one failure takes every request down with it. Right: the data is spread over nodes, and when one fails the others keep serving.">
  <Desk><OneVsSpread /></Desk>
  <Phone><OneVsSpread layout="phone" /></Phone>
</Figure>

Relational databases wanted all the data in one place, in one database instance. If that instance goes down, the system is down: it is no longer highly available. [[L-0018]] In practice a relational primary can have standby replicas that take over when it fails. PostgreSQL’s streaming replication is asynchronous by default, so a commit the standby hasn’t received yet can be lost when the primary crashes; synchronous replication makes each commit wait for the standby to confirm <Cite href="https://www.postgresql.org/docs/current/warm-standby.html">postgresql.org</Cite>. [[L-0018]]

Non-relational databases, in the general classification, spread the data out horizontally. If one node goes down, other nodes still serve the data, so there is almost never a complete downtime. [[L-0019]]

The price is strong consistency. They become eventually consistent: a write shows up everywhere, but not at once. Most non-relational databases are eventually consistent, but you will always find exceptions, because nothing here is standardised. [[L-0020]] DynamoDB is a good example of an exception. Its reads are eventually consistent by default, and a read that sets `ConsistentRead=true` returns the latest committed data, at twice the read cost <Cite href="https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/HowItWorks.ReadConsistency.html">docs.aws.amazon.com</Cite>. Reads from its global secondary indexes are always eventually consistent. [[L-0020]]

</Section>

<Section id="s1-3" no="1.3" title="Relational databases scale too" crumb="1.3 SQL scales too"
  dek="Is the review comment’s premise, “SQL doesn’t scale”, at least right? No: anything that shards, scales."
  meta="About 2 min · class 00:07–00:08">

So is the review comment at least right about relational databases? It is a very big misconception that relational databases don’t scale. You need to know how to use them. The class board boxed it: “NoSQL DBs scale does not mean SQL does not → anything that shards, scales.” [[L-0022]] Vitess is a real example. It is an open-source system that shards MySQL across many instances while applications query it as one database, and it served all of YouTube’s database traffic for over five years <Cite href="https://vitess.io/docs/overview/whatisvitess/">vitess.io</Cite>. [[L-0022]]

You have already seen it done. In <LectureLink lec="lec05" sec="s5-3">Lecture 03 (§5.3, range shards)</LectureLink> the key-value store on MySQL was split across databases: one held the keys from A to M, the other the keys from N to Z. That gave an almost highly available, horizontally scalable system, and the cost was consistency. That is exactly the move non-relational databases make. [[L-0023]]

<Figure id="fig-1c" no="Fig 1·c" max={340} wide={false} k="L-0022 L-0023 L-0024" caption="Lecture 03’s router, redrawn small: keys A–M go to one MySQL database, N–Z to another. The keys are examples; the ranges are Lecture 03’s. The box at the bottom is the class board’s wording.">
<AnythingShards />
</Figure>

So it is crude to say that only non-relational databases scale. Give up the constraints that stop a relational database from scaling horizontally, and you have a truly horizontally scalable relational database. [[L-0024]] Chapter 5 comes back to which constraints those are, and why dropping them is what lets the data spread ([§5.1](#s5-1)).

<RuleBox rule="Never believe a generic statement at face value, ==not even this one==." k="L-0025">

Whenever you hear a generic statement, from the teacher or from anyone, don’t take it at face value. Ask for it to be specific and contextual, and ask why it is being said, because you can always find a counter-example. That habit is what makes you a better engineer.

<Desk><NeverBelieveRule /></Desk>

</RuleBox>

Back to the design review. “Use NoSQL, it scales” names no database, no workload and no trade-off. If the label isn’t the point, what is? The next chapter starts with how each family lets you touch the data.

<RecallQuestions>
  <RecallItem k="L-0014 L-0015 L-0016" q="Which “consistency” do non-relational databases usually give up, and how is it different from the C in ACID?">

CAP’s consistency: a write is visible to every read right away (strong consistency, precisely linearizability). Most non-relational stores relax it to eventual consistency, where another node may return the old value for a while. ACID’s C is a different thing: every transaction moves the data from one correct state to another. A database can keep ACID and still not be linearizable.

  </RecallItem>
  <RecallItem k="L-0022 L-0023 L-0024" q="Give the class’s counter-example to “relational databases don’t scale”.">

Lecture 03’s key-value store on MySQL, sharded by key range: A–M on one database, N–Z on another. Giving up consistency across shards bought an almost highly available, horizontally scalable system, which is exactly what non-relational databases do. Anything that shards, scales; drop the constraints that stop horizontal scale and a relational database scales too.

  </RecallItem>
  <RecallItem k="L-0021 L-0025" q="Someone says “Cassandra scales”. What question should you ask back?">

For what workload? Cassandra, MongoDB and DynamoDB each scale for a specific workload, not for everything. A generic statement always has a counter-example, so ask for the context it holds in.

  </RecallItem>
