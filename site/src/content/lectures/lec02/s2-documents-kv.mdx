<Section id="s2" no="2" title="Documents and key-value stores" crumb="2 Documents and KV"
  dek="Two families defined by how you may touch the data: query inside a document, or only ever get and put by key. The restriction is what buys scale."
  meta="About 12 min · class 00:08–00:15, Q&A 00:47–00:53">

Every Slack user has a small settings blob: a theme, a time zone, notification rules. Do you store it as a document you can query and patch one field at a time, or as one opaque value under the key `user_id`?

That is this page’s framing; the class answered the same question in general. The two families in this chapter differ in exactly one thing, how you are allowed to touch the data, and that one restriction decides how far each can be spread over machines.

</Section>

<Section id="s2-1" no="2.1" title="Document databases" crumb="2.1 Documents"
  dek="The family closest to relational: JSON you can query inside and update one field at a time."
  meta="About 3 min · class 00:08–00:11">

<LectureLink lec="lec05" sec="s5">Lecture 03’s key-value store</LectureLink> kept each value as an opaque blob, and the wish that comes up next is to store JSON there and query inside it. That is exactly what a document database gives you. [[L-0028]]

Of the non-relational families, document databases are the one closest to the relational world, in the lecture’s view. The famous examples are MongoDB and Elasticsearch. [[L-0027]] They are mostly JSON-based. There is no hard and fast rule about that, but mostly JSON. [[L-0029]]

They support complex queries: aggregations in MongoDB, faceted queries in Elasticsearch. [[L-0030]] The key feature is that you can query on the attributes of a document: “give me all the documents that have this attribute set to this value”. You can do the same in Elasticsearch. [[L-0033]]

```js
// all users whose theme is dark: a query on an attribute inside the document
db.users.find({ "settings.theme": "dark" })

// change one field of one document, in place
db.users.updateOne({ _id: 7 }, { $set: { "settings.tz": "IST" } })
```

And you can make partial updates: in this document, update just this one attribute. [[L-0034]]

<Figure id="fig-2a1" no="Fig 2·a" max={340} wide={false} k="L-0034" caption="A partial update: the $set from the snippet above rewrites one field of the document, and nothing else in it moves. Section 2.3 puts the key-value version beside it.">
<PartialUpdate panels="doc" />
</Figure>

None of this is quite as powerful as a relational database, but it is close. So when a team moves a generic relational schema off SQL, it typically adopts a document database, because that gives it almost the features the relational database gave. You will almost never see a team jump straight to a key-value store. [[L-0031]]

</Section>

<Section id="s2-2" no="2.2" title="The lines are blurry" crumb="2.2 Blurry lines"
  dek="Where does “document” end and “key-value” begin? Nowhere in particular, so choose by features."
  meta="About 3 min · class 00:11–00:12, Q&A 00:50–00:51">

Where does “document” end and “key-value” begin? There is no rule that a document database can’t give you what a key-value store gives, or the other way round. DynamoDB is a key-value store, not a document database, yet it still lets you query within the document. [[L-0036]] More exactly, DynamoDB supports both the key-value and the document model <Cite href="https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Introduction.html">docs.aws.amazon.com</Cite>. You can filter on nested attributes, but the filter runs after the items have been read and costs the same read capacity, so an efficient query needs the key or a secondary index <Cite href="https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Query.FilterExpression.html">docs.aws.amazon.com</Cite>. [[L-0036]]

That is why no line separates document databases, key-value stores, columnar storage and the rest. The lines are very blurry, because the people building these databases keep entering each other’s space. [[L-0037]] So understand the access pattern and the features, such as complex queries and partial updates, which is why the previous part listed features rather than labels. [[L-0038]]

What you need to know as an engineer is which features you want from a database and which database gives you them. Generic statements about databases don’t work, because something true today can be completely false later. [[L-0039]]

MongoDB is the example. It started out saying “we are BASE, not ACID”. Now MongoDB is ACID compliant, maybe not as optimally as the SQL world, but compliant. [[L-0040]]

MongoDB offers ACID these days, so what is left of the SQL versus non-SQL difference? Its official documentation, as the class paraphrased it, says to use ACID sparingly. Across shards, ACID is implemented with distributed transactions, which slow down throughput. If you need it, use it, but only when you need it. [[L-0136]] MongoDB’s own wording is that a distributed transaction “incurs a greater performance cost over single document writes” and should not replace good schema design; single-document operations are always atomic, so keeping related data in one document often avoids a transaction at all <Cite href="https://www.mongodb.com/docs/manual/core/transactions/">mongodb.com</Cite>. [[L-0136]]

The general rule behind it: ACID within one shard, anyone can guarantee. ACID across shards is only done through distributed transactions, which slow the throughput down, so you avoid them when you need high throughput. [[L-0137]] The instructor recalls finding the same advice in WiredTiger’s documentation as well. [[L-0138]]

</Section>

<Section id="s2-3" no="2.3" title="Key-value stores: one key at a time" crumb="2.3 Key-value"
  dek="Every operation names one key. That restriction is exactly what lets a key-value store split into thousands of partitions."
  meta="About 4 min · class 00:12–00:15">

Now store the same settings blob under the key `user_id` in a key-value store. Examples are Redis, DynamoDB and Aerospike. [[L-0026]]

Key-value stores are more restrictive than document databases. Every operation you make, reads, writes, deletes, all of them, is key-wise: get a key, put a key, delete a key, insert a key, insert a value into the set at a key. [[L-0041]]

```text
GET  k           # get the value at a key
PUT  k v         # put a value at a key
DEL  k           # delete a key
SET  k v         # insert a key
SADD k member    # insert a value into the set at a key
```

That is very restrictive, because you never peek into the value. A key-value store is no use unless your use case fits exactly that access pattern. [[L-0032]] The value is a blob. If you want to update it, you read it, update it and write it back. No partial update is possible, while document databases typically give you one. [[L-0035]] Some key-value stores do have one: Redis hashes let `HSET` set individual fields of the hash stored at a key without rewriting the others <Cite href="https://redis.io/docs/latest/commands/hset/">redis.io</Cite>. [[L-0035]]

<Figure id="fig-2a" no="Fig 2·a" max={760} k="L-0034 L-0035" caption="Left: the document database changes one field in place. Right: the key-value store only knows whole values, so the API server gets the value, changes it and puts it all back.">
  <Desk><PartialUpdate /></Desk>
  <Phone><PartialUpdate layout="phone" /></Phone>
</Figure>

The restriction buys something big. Because everything is key-wise, you can shard the database very easily: you never have to make a cross-shard query. [[L-0042]] Redis Cluster shows the mechanics. It splits keys over 16,384 hash slots and implements every single-key command, but a multi-key operation works only when all its keys hash to the same slot <Cite href="https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/">redis.io</Cite>. [[L-0042]]

Cross-shard queries come from range operations and the `IN` operator. Ask for “all documents where id in 1, 2, 3”, and if 1 is on one database, 2 on another and 3 on a third, you have a cross-shard query, which is very expensive. [[L-0043]]

<Figure id="fig-2b" no="Fig 2·b" max={340} wide={false} k="L-0042 L-0043 L-0044 L-0047" caption="A get by key touches one shard. An IN over three ids may touch three, and the caller waits for the slowest. Ids 1, 2 and 3 are placed one per shard for the example.">
<OneKeyVsIn />
</Figure>

A key-value store rules that out: all it offers is “here is a key, give me the value”, one key per operation. So you can partition it very heavily, thousands and thousands of partitions, without any hiccups. [[L-0044]]

<RuleBox rule="The more complex the queries, ==the less you can distribute the data==." k="L-0045">

Complex queries cross shards, and cross-shard queries are expensive. Key-wise access never crosses a shard, so the data can be split thousands of ways.

<Desk><DistributeRule /></Desk>
<Phone><DistributeRule layout="phone" /></Phone>

</RuleBox>

Document databases sit further along. They typically do support cross-partition operations, but those get really expensive. [[L-0046]] A key-value store is the other extreme: by limiting access, you get massive parallelism. With many databases, each one answers its own queries in parallel without waiting for the others. You get the best performance, and you pay for it with restricted access. [[L-0047]]

This is the beauty of computer science: every single thing is a trade-off. You get something, you lose something. [[L-0048]]

<Section id="s2-4" no="2.4" title="Key-value is an access pattern" crumb="2.4 An access pattern"
  dek="“Key-value” describes how you use a store, not how it stores. Two key-value stores can behave nothing alike."
  meta="About 3 min · class Q&A 00:47–00:48, 00:51–00:53">

<LectureLink lec="lec05" sec="s5">Lecture 03</LectureLink> built a key-value store on a relational database, and key-value stores have no relations. Is that what decides whether a key-value store goes on SQL or on a non-relational database? No. Key-value stores are databases in their own league. Key-value is an access pattern, and it does not define the store underneath. [[L-0139]]

DynamoDB and Redis are both key-value stores, with different storage engines: Redis keeps the data in memory, DynamoDB on disk. What changes is the storage layer under the same access pattern. [[L-0140]] Memory doesn’t have to mean volatile. Redis can persist with RDB snapshots, on by default, or an append-only file; with the AOF’s default policy of syncing every second you can lose about one second of writes in a crash <Cite href="https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/">redis.io</Cite>. <LectureLink lec="lec04" sec="s3">Lecture 01 (§3, “Redis or DynamoDB?”)</LectureLink> compared the two for the online indicator. [[L-0140]]

So for a key-value use case, once correctness is settled, you can pick a specialised store such as DynamoDB or Redis if its features fit. Understand the features you need, because you may not need to build a key-value store from scratch the way <LectureLink lec="lec05" sec="s5">Lecture 03 (§5)</LectureLink> did. [[L-0141]]

Would a key-value store on a relational database, DynamoDB and Redis then all scale the same? No. It depends on what you store, how you access it, the throughput, and how you partition and shard the data, among a ton of other factors. You can’t use a database as a black box. [[L-0142]] For example, store massive blob values, say 4 MB each, and relational databases would “cry their heart out”, while DynamoDB would work better. [[L-0143]]

<SourceNote href="https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Constraints.html" site="docs.aws.amazon.com (DynamoDB quotas)" k="L-0143">

A single DynamoDB item is capped at 400 KB, attribute names included, so a 4 MB value can’t be stored in DynamoDB at all, and neither DynamoDB nor a relational database is a good blob store. Keep large values in object storage and store the key or pointer in the database; AWS suggests S3 for this <Cite href="https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/bp-use-s3-too.html">docs.aws.amazon.com</Cite>.

</SourceNote>

The class’s point stands: the performance characteristics vary with what you store and how you query it. Store small values and the picture changes again. [[L-0143]]

<MarginNote title="The NAND gate of databases" why="skip unless you like first principles" k="L-0128 L-0129">

A question about graph databases (chapter 4) ended here. Suggested in class: if a graph database stores each node’s neighbours as a list of ids, then it is basically a key-value store. The instructor agreed, and went further: you can model every database on a key-value store. [[L-0128]]

The key-value store is the NAND gate of databases. Just as AND, OR, NOT and every other gate can be built from NAND gates, every database in the world can be modelled on top of a key-value store, though maybe not as performantly. [[L-0129]] CockroachDB is a working example: its SQL layer turns SQL statements into key-value operations on a sorted key-value map split into ranges <Cite href="https://docs.cockroachlabs.com/docs/stable/architecture/overview">cockroachlabs.com</Cite>. [[L-0129]]

</MarginNote>

Back to the settings blob. If the app only ever loads and saves it whole, one value under `user_id` in a key-value store fits, and it spreads over as many partitions as you like. If you want to ask “which users chose the dark theme?” or patch one field, a document database fits. Documents and key-value stores differ in how you address the data. The next family keeps the table and changes how it sits on disk.

<RecallQuestions>
  <RecallItem k="L-0042 L-0043 L-0044 L-0045 L-0046" q="Why can a key-value store run thousands of partitions when a document store struggles to?">

Every key-value operation names exactly one key, so it lands on exactly one shard and never needs a cross-shard query. Document stores allow ranges, `IN` and other complex queries that can touch many shards and wait for all of them, which gets really expensive as the partitions multiply. The more complex the queries, the less you can distribute the data.

  </RecallItem>
  <RecallItem k="L-0035" q="A teammate wants to update one field of a 2 KB value in a plain key-value store. What actually happens?">

The store sees the value as an opaque blob, so there is no partial update: the application reads the whole 2 KB value, changes the field, and writes the whole value back. A document database could change the one field in place. (Some key-value stores add structure for this, such as Redis hashes with `HSET`.)

  </RecallItem>
  <RecallItem k="L-0139 L-0140 L-0142" q="“Redis and DynamoDB are both key-value stores, so they behave the same.” What’s wrong with that?">

Key-value is only the access pattern. Underneath, the storage engines differ: Redis keeps data in memory, DynamoDB on disk. How each performs and scales depends on what you store, how you access it, the throughput and how it is partitioned, so you can’t treat either as a black box.

  </RecallItem>
</RecallQuestions>
