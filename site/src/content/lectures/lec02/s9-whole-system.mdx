Put it together. A user opens Slack in a browser tab. Messages arrive, a badge counts the unread ones, someone starts typing in #general. What does the browser hold open to make all of that live, and which box on the board does what? This chapter draws the whole system on one page, then answers the questions the class asked once it was drawn: what if a real-time message is lost, is it safe to put the edge servers on the internet, and what happens to a message when a database node dies mid-write.

<Section id="s9-1" no="9.1" title="One WebSocket per product" crumb="9.1 One WebSocket"
  dek="Every real-time feature shares one socket, and the fleet that holds those sockets gets a name."
  meta="About 7 min · class 02:20–02:25, Q&A 03:09–03:10">

A page with a live chat, a notifications badge and a typing indicator: one socket, or three?

The key element of any real-time communication is a socket, a persistent connection, and for text that means WebSockets. The class's recap put the design decision in one sentence on the board: “Every user will have 1 websocket connection open with our backend infrastructure and that will be used for anything and everything realtime.” [[L-0319]]

<Figure id="fig-9a" no="Fig 9·a" panels={2} k="L-0319 L-0323 L-0327 L-0330"
  caption="Left: one user, one WebSocket to the backend, a persistent TCP connection that carries everything real-time. Right: those connections land on a fleet of edge servers, and every real-time service goes through them. Redrawn from the class board at 02:20–02:24.">
  <Panel><OneSocket /></Panel>
  <Panel><EdgeFleet /></Panel>
</Figure>

The class gave that fleet a name. The servers every user connects to over a WebSocket are the **edge servers**: a fancy name, a persona for the servers everyone talks to. [[L-0323]] (Not a CDN edge; [7.4](#s7-4) made the same point.) Any service that wants to talk to users in real time, chat, notifications or anything else, sends its information through these edge servers. [[L-0330]]

Why one connection and not one per feature? The reason given in class was a client-side limit. Clients, browsers and Android apps alike, cap how many concurrent TCP connections they open to one backend domain: from a browser, at most six. That figure is the HTTP/1.1 limit per host; over HTTP/2 all of a page's requests share one multiplexed connection. <Cite href="https://www.rfc-editor.org/rfc/rfc9113">RFC 9113</Cite> [[L-0320]] Browsers enforce the limit, the class said, so that people don't abuse it: without it “you could easily do a DDoS”. The cap is mainly there to be gentle with servers and the network, though, rather than as a DDoS defence. <Cite href="https://www.rfc-editor.org/rfc/rfc9112#section-9.4">RFC 9112 §9.4</Cite> [[L-0321]] The class put the number at six or eight: six for Chrome, eight for Firefox. [[L-0322]]

The argument then ran like this. A WebSocket is a persistent TCP connection, so it permanently takes one of those six, leaving five for every REST call and for loading images, videos and the rest. [[L-0324]] Take a page with 100 images of the same size. With no WebSocket open, the browser loads six at a time; with one WebSocket, five at a time; with two, four. Each extra WebSocket cuts how fast the page can talk to the backend. [[L-0325]] And even if the page fires 100 HTTP requests in parallel, the browser sends six, then the next six, and so on. That holds over HTTP/1.1; over HTTP/2 the browser sends them all at once as streams on one connection, up to the server's advertised limit on concurrent streams. <Cite href="https://www.rfc-editor.org/rfc/rfc9113">RFC 9113</Cite> [[L-0326]]

<SourceNote href="https://chromium.googlesource.com/chromium/src/+/refs/heads/main/net/socket/client_socket_pool_manager.cc" site="chromium.googlesource.com" k="L-0322 L-0324 L-0325">

Chrome and Firefox both allow 6 concurrent HTTP/1.1 connections per host; Firefox's `max-persistent-connections-per-server` is 6, not 8. <Cite href="https://raw.githubusercontent.com/mozilla-firefox/firefox/main/modules/libpref/init/all.js">Firefox prefs</Cite> WebSockets are counted in a separate pool, 255 per host in Chrome (“WebSocket connections are long-lived, and should be treated differently”) and 200 in Firefox, so an open WebSocket does not take one of the six and does not slow image loading. Over HTTP/2 all requests share one multiplexed connection anyway. <Cite href="https://www.rfc-editor.org/rfc/rfc9113">RFC 9113</Cite> One WebSocket per product is still the right advice, for other reasons: every extra socket is another long-lived connection the server must hold, and another reconnect the client must handle.

</SourceNote>

So the rule stands, with the reason in the note above: every good product has just one WebSocket connection, and anything and everything real-time goes through it. You can have many; it isn't recommended. [[L-0327]] On Instagram, to take the lecture's illustration, the live chat messages and the heart animation in a live video would all go over that same WebSocket connection. [[L-0328]] Creating a separate WebSocket for every real-time feature is, in the class's words, “the worst way to build a system”: as taught, it cuts how many API calls the browser can make in parallel and slows down the product. The note above explains why that particular harm doesn't hold; the cost on the server and in reconnect handling does. [[L-0329]]

Is the limit per tab, or per domain? It is per host name, the full domain including sub-domains, so chat.google.com, Gmail and Meet each get their own six connections. The host name matters. [[L-0434]] The class answered only the host part; whether tabs share the limit was left unanswered.

</Section>

This is the last diagram the class drew. The overall architecture has three kinds of thing: normal API servers, the partitioned database, and clients holding WebSocket connections to edge servers. Between the edge servers sits the real-time Pub/Sub from chapter 8 ([8.4](#s8-4)), and beside them the Balancer that tells each client where to connect ([8.6](#s8-6)). [[L-0335]]

  <Desk><Architecture /></Desk>

Follow one message. With persistence level 2, where asynchronous persistence is acceptable as in a WhatsApp-like app, it travels over the WebSocket to an edge server and into Kafka; consumers persist it in the database asynchronously, and the message also goes straight to the other connected users. The board's recap lists what the edge server does when A sends to B: “1. Persist message in Kafka 2. Find B in the local pool 3. Send message to B.” For Slack, the message would go the way of [7.3](#s7-3) instead, persisted synchronously first and only then handed to the edge servers for the other users. [[L-0338]]

There is a clear split. A normal messaging service handles HTTP requests: loading a channel's messages, scrolling back through history, and on the board, “unimportant messages that are loaded when channel is clicked, eg: Muted channels”, in short “anything related to messaging that is NOT ‘pushed’”. Everything real-time happens over the WebSocket. [[L-0339]] Behind the API box is the schema from chapter 6, and its first insight still carries the design: a DM is just a channel with two people. The channel row has a small type field so the UI can render a DM as a DM, and messages only ever reference a channel ([6.4](#s6-4)). [[L-0310]]

<h3 id="s9-2-why-kafka">Why Kafka, when Slack was drawn synchronous?</h3>

Chapter 7 drew Slack with synchronous persistence, type ①, and that is the instructor's preference here. This diagram uses Kafka, type ②, on purpose. The asynchronous Kafka route is possible for Slack too: any implementation is possible, depending on the guarantees. [[L-0236]] The lecture deliberately keeps its designs conflicting and never converges on one, so that you think about every single decision you take. [[L-0238]] There is no one way to build it. Whatever guarantees you have, you build it that way. [[L-0331]]

<RuleBox rule="This architecture covers almost every messaging system: ==change only the guarantees==." k="L-0340">

Asynchronous persistence, a storage layer, a partitioned database and a real-time Pub/Sub between the edge servers. For Slack, WhatsApp or Zoom chat, swap the persistence path and keep the rest.

<Phone><GuaranteesDial layout="phone" /></Phone>

</RuleBox>

That is how to design an architecture that covers almost all types of messaging systems. Change the guarantees, for WhatsApp or for Zoom, and everything else stays the same. [[L-0340]] It is the promise from the start of the lecture made concrete: in this one design you can switch from one message delivery model to another, and get something like WhatsApp, something like Slack or something like Zoom chat. Once Slack is done, the others are a piece of cake. [[L-0005]]

<Section id="s9-3" no="9.3" title="When a real-time message is lost" crumb="9.3 Lost messages"
  dek="Persistence is guaranteed; the real-time push is not. What the client does about it."
  meta="About 4 min · class 02:25–02:30, Q&A 02:42–02:43">

Redis Pub/Sub keeps nothing. What if a push doesn't arrive?

Start with what is promised. The board wrote it under the Kafka path as an insight: “Messages once sent will always be persisted, there will not be any DB level runtime exception like Unique Key failed, etc.” [[L-0332]] One practical detail keeps that true. A Kafka consumer can see a record twice: if it crashes after processing a batch but before saving its offset, its replacement reads them again. Writing each message keyed by its unique message id turns that redelivery into a harmless overwrite. <Cite href="https://kafka.apache.org/43/design/design/">kafka.apache.org</Cite> [[L-0332]]

The real-time half has no such promise. Redis Pub/Sub gives no persistence ([8.4](#s8-4)): only the servers connected at that moment receive a message, so there is a chance that a message is lost and not delivered in real time. [[L-0344]]

So in this system the message is guaranteed to be persisted, but the notification to the other users isn't? Correct. The message might get lost while Redis passes it to an edge server, and the user sees it when they refresh. For an enterprise application, guaranteed persistence is the part that matters more. [[L-0379]]

<AnimationClip clip="l02-missed-message" no="Clip 9·1"
  k="L-0344 L-0379 L-0332 L-0334 L-0345"
  lead="WS2 blinked for one second while A posted. When does E see the message?"
  caption="The message is stored through Kafka, but Redis pushes it while WS2 is disconnected and keeps nothing; E's client fetches the last 50 on a timer and the message appears." />

A message that wasn't delivered in real time can't simply stay missing. The board's answer is the channel scroll API, the REST one: when the user clicks the channel, the client loads its messages through it, and the missing message is there. [[L-0333]] For a transient problem, when sockets drop for a moment, the board lists two fixes: “1. Remember we have correction job! … 2. Buffer the messages in another kafka and when sockets are back up, we replay them.” [[L-0334]]

The correction job can be small. Run periodic background refreshes of the Slack channel: a little JavaScript thread on the client that every so often fetches the channel's last 50 messages, checks whether any were missed, and renders them, mimicking the notification the user never got. [[L-0345]] You may have seen WhatsApp say “checking for new messages”. In the lecture's reading, that is this pattern: a new WebSocket connection was just established, and the client is asking the backend whether there is anything to fetch. [[L-0346]]

<MarginNote title="Build it: three clients" why="skip if you’ve used Redis Pub/Sub" k="L-0343">

To understand Redis Pub/Sub, write a small hello world. Spin up a small Redis server locally, connect three clients to it, and see how it functions. [[L-0343]] Then disconnect one, publish, and reconnect it: the message never arrives, because there was nothing to replay.

```sh
# clients 1 and 2, one terminal each
redis-cli SUBSCRIBE c1
# client 3
redis-cli PUBLISH c1 "standup in 5"
```

</MarginNote>

</Section>

<Section id="s9-4" no="9.4" title="Exposing the edge servers" crumb="9.4 Exposing the edge"
  dek="Public IPs or a load balancer, what may live on an exposed box, and why the client's channel list can't be trusted."
  meta="About 9 min · class Q&A 02:31–02:45">

What exactly is an edge server, and is it okay to hand its IP address to clients?

Edge servers are normal WebSocket servers: a Node.js process running Socket.IO, for example. That's it. [[L-0352]]

Can clients connect to their IPs directly? There are multiple ways to do it. A lot of people expose edge servers over the internet, and in the class's view there is no harm in that; you can also put them behind a load balancer. [[L-0353]] This lecture's case study does the second: Slack terminates its WebSocket connections on proxies in several regions close to users, first HAProxy and now Envoy, and forwards them to its backend WebSocket services. <Cite href="https://slack.engineering/migrating-millions-of-concurrent-websockets-to-envoy/">slack.engineering</Cite> [[L-0353]]

<MarginNote title="From practice: the interviewer" why="skip unless an interviewer said so" k="L-0354">

An interviewer once told a learner that exposing server IPs invites misuse. The instructor's view was blunt: interviews don't know real-world systems, big companies publicly expose the IP addresses of their edge servers, and there is nothing wrong with this architecture. That is the lecture's opinion. Exposing edge servers directly is a legitimate option, but it doesn't describe the case study, since Slack puts Envoy proxies in front of its WebSocket servers <Cite href="https://slack.engineering/migrating-millions-of-concurrent-websockets-to-envoy/">slack.engineering</Cite>, and the interviewer's concern is a fair trade-off to talk through. [[L-0354]]

</MarginNote>

A load balancer adds a hop. In the instructor's experience every relay hop adds about three to five milliseconds, so for ultra-low-latency real-time communication, such as streaming a live class, he exposes the IP addresses directly; elsewhere a load balancer is fine. [[L-0355]] Behind a load balancer, WebSocket connections are always sticky: one connection from the user to the load balancer, and another from the load balancer to a WebSocket server. [[L-0356]] That is how a proxy that terminates the connection works, Envoy or an L7 balancer. An L4 balancer such as AWS NLB instead forwards the flow: “each individual TCP connection is routed to a single target for the life of the connection”, so the WebSocket stays pinned to one server without being terminated at the balancer. <Cite href="https://docs.aws.amazon.com/elasticloadbalancing/latest/network/introduction.html">docs.aws.amazon.com</Cite> [[L-0356]]

An edge server exposed on the internet faces a ton of security threats, so it is hardened and goes through a very high security review: you change the route tables, hide all the ports, prevent SSH and block a lot of things on the machine. [[L-0357]] And one rule is fixed: **whenever a server is exposed on the internet, you don't put any credentials on it.** The edge server has zero credentials, in the class's words, never talks to the database directly and has no idea what the database is. The instructor never connected his edge servers to a database, and kept this design that way knowing someone would ask. [[L-0358]] The only thing it holds is something safe to push with, a Kafka connection string. If the server is compromised, all you lose is that string, and the Kafka is internal to the infrastructure, so no one outside can talk to it. [[L-0359]]

<Figure id="fig-9c" no="Fig 9·c" panels={2} k="L-0353 L-0355 L-0356 L-0357 L-0358 L-0359 L-0375"
  caption="Two ways in. Left: the edge server faces the internet directly, hardened, holding only a Kafka connection string (the note below suggests making it write-only) and never a database credential. Right: behind a load balancer, a few milliseconds more per hop and a sticky connection; as a private server it can ask a membership API before serving a private channel.">
  <Panel><Exposed /></Panel>
  <Panel><BehindLb /></Panel>
</Figure>

Why, then, is it fine to keep the edge servers public? Because there is no sensitive information on them: a route from the Balancer service that hands out IP addresses, a bunch of TCP connections, and one Kafka connection string that, as the class put it, holds no secret and only pushes messages. [[L-0383]]

<SourceNote href="https://kafka.apache.org/43/security/security-overview/" site="kafka.apache.org" k="L-0383">

A Kafka credential is still a secret: a compromised edge server can reach the internal Kafka and inject messages that consumers trust and persist. Kafka can authenticate clients (SSL or SASL) and authorise reads and writes per client, so give the edge a least-privilege credential, for example write-only to one topic, and have the consumers validate what they read. Losing it is far less damaging than losing database credentials.

</SourceNote>

With nothing critical on the server, the worst an attacker can do is a DDoS. All they get is one machine that tells them the IP addresses of the edge servers, and a simple rate limiter can prevent a DDoS. [[L-0360]]

<SourceNote href="https://docs.aws.amazon.com/whitepapers/latest/aws-best-practices-ddos-resiliency/infrastructure-layer-attacks.html" site="docs.aws.amazon.com" k="L-0360">

With nothing sensitive on the edge server, DDoS is indeed the main risk, but a rate limiter handles only some request floods. The most common attacks, UDP reflection and SYN floods, are infrastructure-layer floods. Mitigating them takes network capacity that scales faster than the attack, to absorb or filter it upstream, which an application rate limiter cannot provide.

</SourceNote>

So there is no rule that a WebSocket server must always sit behind a load balancer. If you can ensure the security of a publicly exposed server, you are fine. There are hundreds of ways to build a system: know which guarantees you are providing, and keep it simple. [[L-0361]] Put as a trade-off: a public edge server can be attacked, and a load balancer in front of it adds one more hop, about five milliseconds of extra latency by the instructor's estimate. If that latency is acceptable, use the load balancer; if not, keep it public. Both are fine. [[L-0382]]

<PauseAndThink k="L-0368 L-0373 L-0374 L-0375"
  q="Each edge server learns a user's channels from what the client sends after connecting. Private channels now exist. Is the client's list good enough to decide who receives a private channel's messages?"

No. A malicious user can claim membership of a channel they're not in and receive its messages. The instructor built the design this way on purpose to provoke the question, and the flaw is broken access control (the note below). Relying on the client is fine while membership isn't sensitive. When it is, as with private channels, the edge server checks membership with a backend API (or the database), which means putting it behind a load balancer as a private server rather than a public one.

</PauseAndThink>

<h3 id="s9-4-membership">Trusting the client's membership</h3>

In [8.5](#s8-5) each edge server learned which Slack channels its users are in from the users themselves. Since that membership information comes from the end users, the question followed: how do you deal with bad actors, for example once private channels are introduced? [[L-0373]]

If the edge servers trust the client's membership claims, a user can falsely claim “I am part of this channel. Give me all the messages.” and start receiving messages they should never see. The instructor called this a man-in-the-middle attack, and said he had designed it this way on purpose, to provoke exactly these questions. [[L-0374]]

<SourceNote href="https://top10.owasp.org/2021/A01_2021-Broken_Access_Control" site="owasp.org" k="L-0374">

A user claiming a channel they are not in is an authorisation flaw, broken access control (A01 in OWASP's 2021 list and in the current <Cite href="https://top10.owasp.org/2025/">2025 list</Cite>), not a man-in-the-middle attack, which intercepts traffic between two parties <Cite href="https://community.owasp.org/attacks/Manipulator-in-the-middle_attack">owasp.org</Cite>. The baseline is “except for public resources, deny by default”: check membership on the server side.

</SourceNote>

Relying on the client to report membership is one way, not the only way. Another is for the edge server itself to call the backend API periodically and pull which of its connected users are in which channels. That can't be done from a publicly exposed server; it can if the server is private. [[L-0368]] So if membership is critical, as with private channels, don't trust the client. Rely on a backend API call for membership: make the edge server private, put it behind a load balancer, and let it talk to the database or call an API for channel information. Panel b of Fig 9·c draws that row. [[L-0375]]

</Section>

<Section id="s9-5" no="9.5" title="Durability, and a shared database" crumb="9.5 Durability"
  dek="Who replicates a message, when a write counts as accepted, and why the workers and the API servers can share one database."
  meta="About 5 min · class Q&A 03:02–03:06">

A database node dies in the middle of a write. Is the message gone?

Asked in class, assuming the message store had master-slave replication: where is replication? This store is just sharded. You can have replicas if you want, but a typical sharded setup works, and the instructor saw no need for replication there. [[L-0420]] The follow-up changed the answer. To avoid losing a write when a node dies mid-write, important data is stored with standby nodes and a replication factor of three: each write goes to three data nodes, so if one goes down, the others serve the data. DynamoDB does exactly this internally. [[L-0421]]

Reading Kafka again is not the way back. Once the workers have processed the messages, you can't recover a lost write by reading from Kafka: those messages are already processed. [[L-0422]]

<SourceNote href="https://kafka.apache.org/intro" site="kafka.apache.org" k="L-0422">

Kafka does not delete events when they are consumed. A topic keeps them for its retention period, and they can be read as often as needed, so a consumer can rewind and reprocess. The real point stands: the durability of the write should come from the database's own replication, not from re-reading Kafka.

</SourceNote>

A tempting idea, suggested in class: let the workers push each message to two or three database instances across regions. That is worse. The worker doesn't do that; the database's storage engine does. A write comes to one data node, which replicates it to two others, so if one node goes down, another serves the data. [[L-0423]]

<Figure id="fig-9d" no="Fig 9·d" k="L-0421 L-0424 L-0425"
  caption="Ack after replication. The worker writes to one node, nodes 2 and 3 copy it, and only then is the write acknowledged to the worker. A write lost before that point was never accepted. The note below gives DynamoDB's actual rule, two of three.">
  <AckAfterReplication />
</Figure>

A replicated database never acknowledges, never commits, a write until it has been written in three different places. In the class's words, “your DB would never say that I am done unless it is written in three different places”. A write lost before replication was simply never accepted. When you write to DynamoDB, it is written internally to three storage nodes, and only after all three complete does it say the write is complete. [[L-0424]]

<SourceNote href="https://www.usenix.org/system/files/atc22-elhemali.pdf" site="usenix.org (DynamoDB, ATC '22)" k="L-0424">

A synchronously replicated database acknowledges a write once the configured replicas, often a majority quorum, have persisted it. DynamoDB keeps three replicas of each partition in different Availability Zones and acknowledges when two of the three have the log record. Asynchronous replication, PostgreSQL's default, acknowledges earlier and can lose recent writes on failover. <Cite href="https://www.postgresql.org/docs/current/warm-standby.html">postgresql.org</Cite> The core lesson stands: the storage engine replicates, not the workers.

</SourceNote>

Also suggested in class: the worker holds the message until the database commits it, retries otherwise, and if the worker goes down, the message is reprocessed. The instructor confirmed only one part of that, that the database acknowledges the write to the worker. [[L-0425]]

<h3 id="s9-5-shared-db">One database for workers and API servers</h3>

In Fig 9·b the workers write to the same database the API servers read from. Is sharing a database a problem? No, sharing a database is perfectly fine. Making the workers call the API so that the API writes to the database adds an unnecessary network call and needless complication. [[L-0426]]

The instructor dislikes the anti-pattern in which every microservice needs its own database. He puts performance and cost efficiency first and is happy to share a database. That is the lecture's opinion. The pattern's catalogue lists what each side buys: a database per service means one service's schema changes don't affect the others and each service can pick the store that suits it, while a shared database brings schema-change coordination and services interfering with each other at runtime. <Cite href="https://microservices.io/patterns/data/database-per-service.html">microservices.io</Cite> <Cite href="https://microservices.io/patterns/data/shared-database.html">microservices.io</Cite> [[L-0427]] Business and product come first and engineering second: do whatever keeps cost down and gets maximum performance, because the business is what keeps engineers employed. [[L-0428]]

<MarginNote title="Further viewing" why="skip unless you are deciding this now" k="L-0429">

The instructor's YouTube series on microservices (17 or 18 videos) covers shared versus separate databases as a pattern, with its advantages and disadvantages. Two of the videos are on this topic. [[L-0429]]

</MarginNote>

The pieces are all on the board. Two features the class asked about, deleting a message and putting messages in order, need no new boxes, and that is chapter 10.

<RecallQuestions>
  <RecallItem q="Does an open WebSocket slow down a page's image loading? What did the class say, and what is actually true?" k="L-0324 L-0325 L-0327">

The class said yes: a WebSocket takes one of the browser's six connections per domain, so images load five at a time instead of six. In fact browsers count WebSockets in a separate pool (255 per host in Chrome, 200 in Firefox), so an open WebSocket doesn't take one of the six, and over HTTP/2 all requests share one connection anyway. One WebSocket per product is still right: each extra socket is another long-lived connection for the server and another reconnect for the client.

  </RecallItem>
  <RecallItem q="What is on an exposed edge server, and what must never be?" k="L-0358 L-0359 L-0383">

A route from the Balancer, a bunch of TCP connections and one Kafka connection string to push messages with, ideally a least-privilege, write-only credential. Never database credentials: the edge server never talks to the database and doesn't know what it is. The machine itself is hardened, with ports hidden and SSH blocked.

  </RecallItem>
  <RecallItem q="Who should replicate a message for durability, the worker or the database, and when is the write acknowledged?" k="L-0423 L-0424">

The database's storage engine: the write goes to one node, which replicates it to the others. Workers writing to several instances themselves is worse. The write is acknowledged only once it is on the required replicas; the class said all three, and DynamoDB in fact acknowledges at two of three. A write lost before that was never accepted.

  </RecallItem>
