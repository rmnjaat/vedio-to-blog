<Section id="s5" no="5" title="“Design Slack.” Where do you even start?" crumb="5 Slack’s rows" meta="About 6 min">

“Design Slack” means the whole product, every feature of it, and that is too much to design well. Pick one part and do it really well: Slack’s real-time communication, text only, the kind of messages you also see on Teams or Instagram. What you build here also powers multiplayer games and live polls. But don’t start with WebSockets; start with the simplest thing, the schema, for these features only. A schema names entities and attributes; it doesn’t commit you to a relational database. [[L-0149 L-0151 L-0152 L-0153]]

<Section id="s5-1" no="5.1" title="Who is in which channel?" crumb="5.1 Membership">

A first sketch has three tables: `users` with an id, a name and an optional nickname; `channels` with an id and the organisation it belongs to; and `messages`, each holding the id of the channel it was sent in. It can’t answer one question yet: which users are part of which channel? That has to be stored somewhere, in a table that joins users to channels. [[L-0154 L-0155]]

Most people would call it `user_channel`. But what *is* a user channel? And if tomorrow you map three things, is it `user_channel_message`? Call it **`membership`**. A noun gives the table a persona, and a thing with a persona naturally grows attributes: how far this user has read, whether they muted the channel. With `user_channel` you never think of adding a column. [[L-0156 L-0157 L-0158]] That pays off in 5.4.

</Section>

Who sent it and the text, certainly. The destination is the hard part, because a message goes either to a channel or to a single user.

Every draft treats a direct message as a special case, and special cases are where the trouble comes from. Ifs and elses are the worst thing you can build into how data is stored. [[L-0165 L-0171]]

Give the two people a common channel. Every message then has exactly one `channel_id`, whether it was sent to #general or to one person.

<Section id="s5-3" no="5.3" title="What kind of row is a chat between two people?" crumb="5.3 DMs are channels">

That piggybacks on what already exists, channels and messages, instead of special-casing anything. (Making that two-person channel a pub/sub topic as well would be an unnecessary complication.) [[L-0167 L-0168]]

It is how Slack’s API works: every channel-like thing is a *conversation*, whether a public channel, a private one or a DM (`is_im`), and `conversations.open` opens or resumes a DM and returns its channel ID <Cite href="https://docs.slack.dev/reference/objects/conversation-object">docs.slack.dev</Cite>. The UI renders it as a direct message; underneath, it is a channel. A DM and a channel message are both just a message with a sender and a destination. Only the rendering differs. [[L-0169 L-0170]]

The rendering is why the channel gets a `type`: `reg`, `grp` or `user`, the last meaning a DM, which puts channels in the top half of the sidebar and DMs below. Why not call a two-person private channel a DM? Because a private channel can gain members later and a DM can’t, so the UI must tell them apart. Messages also carry `created_at`, so scrolling a channel means walking its messages in time order. [[L-0172 L-0173 L-0431 L-0432 L-0433]]

<Section id="s5-4" no="5.4" title="You open a channel with 100 new messages. Where do you land?" crumb="5.4 Checkpoint">

Exactly where you stopped reading. That is the payoff of the noun. Because `membership` doesn’t restrict you, it can hold a **checkpoint**: for this user in this channel, how far they have read, as a timestamp or a message id, whichever granularity you choose. Opening a channel moves it to the newest message. [[L-0175 L-0177 L-0178]]

From that one column come the unread badge, the “you last read until here” line and the jump to it. Slack exposes the same thing as a conversation’s `last_read`, moved by `conversations.mark` <Cite href="https://docs.slack.dev/reference/methods/conversations.mark">docs.slack.dev</Cite>. Muted, favourited, notification settings: all describe how one user relates to one channel, so they go on membership too, the key table of the system. [[L-0176 L-0179 L-0180]]

It also explains what Slack doesn’t do. Back from a vacation, you see something like 200 unread messages, none replayed over a socket: the app loads them with ordinary API calls, and the checkpoint says where the unread part begins. WhatsApp keeps messages on your phone, so it has to deliver them there. [[L-0437 L-0438 L-0439]]

<RuleBox label="The rule to keep" rule="Name tables as ==nouns==, and ==piggyback== on what you have instead of writing ifs and elses." k="L-0181 L-0157">

The noun let membership grow a checkpoint, mutes and favourites without a new table. Piggybacking made a DM a channel with two people, so messages need no special case.

</RuleBox>

</Section>

<Section id="s5-5" no="5.5" title="Which shard does a message go to?" crumb="5.5 Shard key">

A workspace has many channels and each channel has many messages, so shard by `channel_id`: a channel’s messages sit in one database, and scrolling never crosses shards. Slack chose the same key for message data when it moved to Vitess, to spread the load more evenly <Cite href="https://slack.engineering/scaling-datastores-at-slack-with-vitess/">slack.engineering</Cite>. Because a DM is a channel, that one rule places every message. Now someone presses send. [[L-0313 L-0314 L-0315]]

</Section>
