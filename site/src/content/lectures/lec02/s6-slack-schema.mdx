<Section id="s6" no="6" title="Slack: the problem and the schema" crumb="6 Slack schema"
  dek="Cut “design Slack” down to real-time text chat, then build the tables. Membership is a noun, a direct message is a two-person channel, and a checkpoint drives unread counts."
  meta="About 18 min · class 01:00–01:17, Q&A 03:07–03:09, 03:12–03:13">

“Design Slack” is the whole product, every feature of it. Where do you even start?

The second half of the class starts by cutting that down to one part, then builds the tables for it before anything travels over a network. This chapter is that first step: the scope, the requirements, and a schema that turns out to carry more of the design than it seems.

</Section>

<Section id="s6-1" no="6.1" title="One part of Slack, done well" crumb="6.1 The scope"
  dek="Not the whole product: real-time text chat in one organisation, with the decisions explained, and the schema first."
  meta="About 4 min · class 01:00–01:03, 00:01">

System design, as the class framed it at the very start, is about recognising patterns, the Lego blocks, and assembling them into a running system. [[L-0006]] The second half of the class puts that to work: it designs Slack's real-time communication. [[L-0145]]

<MarginNote title="Patterns, like people" why="skip unless you like the analogy" k="L-0007">

The instructor's aside: computer science mirrors how people operate. We work on patterns, learn from them and iterate, and in his telling the von Neumann architecture of the first CPUs has many similarities to how the brain functions.

</MarginNote>

The instructor dislikes the framing “design Slack”, the entire product. Pick one part of it instead, and do it really well. [[L-0146]] The part is Slack's real-time communication, text only and nothing more: the kind of messages you see on Teams, Instagram or Facebook. It is kept simple on purpose, so the foundational building blocks, the small nitty-gritty details and the way each design decision gets made stay visible. [[L-0147]]

The requirements are short. There is one organisation on Slack, with multiple users (its employees) and multiple channels. A user can direct-message another user or post a message in a channel. The chat has to be real time. And historical messages can be scrolled: open a channel and scroll back through its older messages. [[L-0148]]

<Figure id="fig-6a" no="Fig 6·a" max={340} k="L-0147 L-0148"
  caption="The whole brief: five requirements, text only. Everything in chapters 6 to 10 serves this card.">
  <RequirementsCard />
</Figure>

The same architecture builds a lot more than chat: multiplayer games, real-time interactions, real-time polls, creator tools. [[L-0149]] The plan is to brainstorm channels, messages, checkpoints and real-time communication, reach WebSockets, and then scale them. The highlight is how each decision gets made, not a diagram of boxes. [[L-0150]]

Jumping straight to WebSockets is not a good idea. Cover the basics first, then WebSockets, then their scaling. [[L-0151]] So start with the simplest thing, the schema, and design it for these features only, nothing else. [[L-0152]]

One clarification before any tables. Designing a schema means naming the entities and their attributes. It does not mean you are using a relational database. The database is picked afterwards, by the guarantees you want to give, and [7.1](#s7-1) picks it. [[L-0153]]

</Section>

<Section id="s6-2" no="6.2" title="Who is in which channel: membership" crumb="6.2 Membership"
  dek="A first schema, the question it can't answer, and why the table that answers it should be called a noun."
  meta="About 2 min · class 01:03–01:06">

A first schema, suggested in class: a `users` table with an ID, a name and an optional nickname; a `channels` table with an organisation ID and a channel ID; and a `messages` table that holds the channel ID the message was sent in. That's okay, the reply went. What else? [[L-0154]]

There is a question it can't answer yet: how do you know which users are part of which channel? That has to be stored somewhere. The answer suggested in class was a **membership** table, and the name was praised: the person who suggested it hadn't seen the board, which already used that word. [[L-0155]]

<Figure id="fig-6c-start" no="Fig 6·b, so far" max={340} k="L-0156 L-0157"
  caption="Three tables so far. The join table gets a noun, membership, rather than the easy name user_channel. The board first wrote user.channel and renamed it.">
  <SchemaStart />
</Figure>

A lot of people would name that table `user_channel`, and the instructor is against it. It's the easy way to name things, but what *is* a user channel? If tomorrow you store a mapping of three things, will you call the table `user_channel_message`? The board itself first wrote `user.channel` before renaming it `Membership`. [[L-0156]]

The rule behind it: when you design a schema, everything should be an entity, named as a noun wherever possible. A noun gives the table a persona of its own. `membership` stores membership information, such as “this user is part of this channel”. [[L-0157]]

And a noun makes extension natural. Call it `membership` and adding columns comes easily: how far this user has read, whether they're active, how they interact with the channel. Call it `user_channel` and you don't think of adding another attribute at all. [[L-0158]] That pays off in 6.5.

</Section>

<Section id="s6-3" no="6.3" title="Where do direct messages go?" crumb="6.3 Direct messages"
  dek="A message goes to a channel or to one person. Five drafts of the messages table, each rejected for a concrete reason."
  meta="About 6 min · class 01:05–01:12">

A message goes either to a channel or to one person. So what does the `messages` table hold? It holds who sent the message and the text. The class worked through the destination in a sequence of drafts, and the board keeps their order.

<PauseAndThink k="L-0159 L-0161 L-0165 L-0168 L-0171"
  q="A message goes either to a channel or to one person, so messages gets both a nullable channel_id and a nullable receiver_id, exactly one filled. Is that a sound design?"
  choices={[{ label: 'Yes: one column is always null, and that’s fine' }, { label: 'No: it invites broken rows and special cases', correct: true }]}
  right="Right: nothing stops a row with both null, and every query must ask which one is set."
  wrong="It works on the happy path, but nothing forbids an orphan row with both columns null.">

No. Nothing stops a row where both are null: an orphan message that belongs nowhere. Every query and every piece of business logic must then ask which column is set, which is the ifs and elses the class kept meeting in the other drafts (two tables, a receiver array, prefixed ids, a type enum). The way out is to stop treating a DM as special: a DM is a channel with two people, so every message has one `channel_id`. 6.4 builds it.

</PauseAndThink>

The first draft, suggested in class, put both a channel ID and a receiver (user) ID on the message, one of them always null: channel messages fill one, direct messages the other. What is the disadvantage? [[L-0159]] If you allow either column to be null, you also allow a row where both are null, inserted because of some glitch. That row belongs nowhere: an **orphan row** problem. [[L-0161]] If you do keep two either/or columns, the database can still forbid that row: PostgreSQL's `num_nonnulls()` lets a check constraint require exactly one of them to be set <Cite href="https://www.postgresql.org/docs/current/functions-comparison.html">postgresql.org</Cite>. The final design avoids the problem altogether.

```sql
-- exactly one destination per row: no orphan messages
CHECK (num_nonnulls(channel_id, receiver_id) = 1)
```

The drafts, with the reason each one fails:

- **Two tables**, one for channel messages and one for direct messages, suggested in class. Then migrations get difficult: add a new attribute to messages and you have to add it to both tables. [[L-0160]]
- **A receiver array**: store the receiver as an array of every receiving user. It was raised and dropped in the same breath, because it breaks as soon as users are added to the channel. There has to be a better way. [[L-0162]]
- **`from` and `to`**, where `to` is a channel ID or a user ID told apart by a prefix such as `CH-` or `usr-`. Now every query needs string processing to decide whether to join with `channels` or with `users`. That is a poor implementation, and you can't write efficient queries on it. [[L-0163]]
- **A receiver-type enum** next to `to`, channel or user. Its proposer argued it filters a little better than parsing prefixes, but it is a variation of the same thing: `to` can no longer have a foreign-key check saying it references `channels`, because it may point at a user. [[L-0164]] A polymorphic `to` also forces ifs and elses into the business logic (if this, then that; else the other), and the code gets complicated. [[L-0165]]
- **The message shouldn't know where it is going**: treat routing as control information, handled in code rather than in the database. But without the destination stored, how do you render all the messages of a channel? You still need that. [[L-0166]]
- **A common channel for the two people in a DM, also used as a pub/sub topic.** The first half of that is the answer, and the class kept it. The publisher-subscriber part is an unnecessary complication: focus on the first part. [[L-0167]]

</Section>

<Section id="s6-4" no="6.4" title="A DM is a channel with two people" crumb="6.4 DMs are channels"
  dek="The last draft's good half. Piggyback on channels, give the channel a type, and the whole schema fits on one board."
  meta="About 3 min · class 01:12–01:14, 02:19, Q&A 03:07–03:09">

So the way to model it: a direct message is a channel with two people. This piggybacks on what already exists, channels and messages, instead of special-casing DMs. [[L-0167 L-0168]]

This isn't made up: it is how Slack's API works. If you use the Slack API to DM a particular user, you first create a channel with that user and then write on it. The UI renders it as a direct message, but behind the scenes it is a channel. [[L-0169]] Slack's documentation puts it this way: every channel-like thing is a *conversation*, whether a public channel, a private channel, a DM (`is_im`) or a multi-person DM (`is_mpim`). `conversations.open` opens or resumes a DM and returns its channel ID, and `chat.postMessage` can also take a user ID and open the DM if needed <Cite href="https://docs.slack.dev/reference/objects/conversation-object">docs.slack.dev</Cite>.

In the end a DM and a channel message are both a message, with a sender and a receiver. Only the rendering differs, on the UI side; the way you store it doesn't. [[L-0170]] Always look for a general way to store things rather than specific cases: if this, go here; if that, go there. Ifs and elses are the worst when it comes to databases. [[L-0171]]

The channel gets a `type`: a group, a user (a DM) or a regular channel. Every message carries a `channel_id` pointing at its channel, so DMs need nothing extra, and the type is what lets the UI put direct messages in the bottom half of the sidebar and channels in the top half. [[L-0172]] Messages also carry a timestamp of when they were created, `created_at`, so you scroll a channel's history by iterating through that channel's messages. [[L-0173]]

That is the whole schema: `users`; `channels` with their `type`; membership information in `membership`; and `messages` that point at a channel. [[L-0174]] When the class recapped the design later, the first point on the board was this one: DMs are channels with two people, so only channels need modelling well. The channel row has a small `type` field saying whether it is a DM so the UI can render it accordingly, and messages simply reference the channel. [[L-0310]] The recap board then wrote the schema out formally. A workspace has multiple channels, each with multiple messages, [[L-0313]] so the recap's tables are:

- `workspace`: `id`, `name`
- `channels`: `id`, `workspace_id`, `name`, `type` (the `type` added live)
- `messages`: `id`, `channel_id`, `message`, `user_id`, `ts`
- `membership`: `channel_id`, `user_id`, `checkpoint`

Next to the schema above, the recap's version adds a `workspace` table and calls the message timestamp `ts`. [[L-0310]]

### Why a type, and not private/public?

Asked in class: why store a channel type at all? Why not just mark a channel private or public, and treat a DM as a private channel with two members? [[L-0431]] Because then you can't tell a channel with two people from a DM, and the two render differently. [[L-0431]] A private channel created with two people can get more members later. A DM can't: you can't add people to it. That is why the UI needs the type. [[L-0432]]

Every combination can exist: a private channel with two people, a public channel with two people, a DM between two people. And tomorrow a DM might be allowed to become private or public. An explicit type keeps the schema extensible. [[L-0433]]

</Section>

<Section id="s6-5" no="6.5" title="The checkpoint" crumb="6.5 The checkpoint"
  dek="Because the table is a noun, it can hold how far each user has read each channel. That one column drives unread counts, and Slack never replays old messages over the socket."
  meta="About 3 min · class 01:14–01:17, Q&A 03:12–03:14">

You open a channel with a hundred new messages. Where does Slack take you?

Here is the payoff of naming the table `membership`. A noun doesn't restrict you, so it can hold a **checkpoint**: for this user in this channel, the point up to which they have read. [[L-0175]] Slack exposes exactly this: the conversation object's `last_read` is “the timestamp for the last message the calling user has read in this channel”, and `conversations.mark` moves that read cursor to a given message <Cite href="https://docs.slack.dev/reference/methods/conversations.mark">docs.slack.dev</Cite>.

The checkpoint is what you see in the UI. The unread message count. The “you last read until here” line. And when you click a channel with a hundred new messages, being taken to that point. [[L-0176]]

<Figure id="fig-6d-2" no="Fig 6·d, continued" panels={2} k="L-0175 L-0176 L-0177"
  caption="The badge, the “last read” line and the jump all come from one column, membership.checkpoint. Opening the channel moves it to the newest message.">
  <Panel><Sidebar again /></Panel>
  <Panel><OpenChannel /></Panel>
</Figure>

Whenever you open a channel, the checkpoint moves to its bottom, to the last message read. It can store a timestamp or a message ID; that depends on the implementation. [[L-0177]] The granularity is a choice: time-level, “I read till this time”, or message-level, “I read till this message”. [[L-0178]]

The same goes for everything else about how a user relates to a channel. Muted the channel? Store it on membership. Favourited it? Store it on membership: there's no need for a separate favourites table. Notification settings, the same. [[L-0179]] Because it holds every interaction a user has with a channel, membership becomes the key table of the system. [[L-0180]]

<RuleBox rule="Name things as ==nouns==, and ==piggyback== on what you already have instead of writing ifs and elses." k="L-0181 L-0157">

The two takeaways of the schema. A noun gives a table a persona and room to grow (membership gained a checkpoint, mutes and favourites without a new table). Piggybacking made a DM a channel with two people, so messages need no special case.

### Old messages don't come over the socket

That closes a loop raised at the very end of the class. WhatsApp keeps your messages on your device; Slack keeps them in its backend database. So it was suggested that Slack should load old messages with API calls, not over the WebSocket, and the instructor agreed. [[L-0437]] On Slack you never see old messages replayed to you. Come back from a vacation, log in, and you just see something like 200 unread messages to go through; none of them were relayed over the WebSocket. The checkpoint on membership is what makes that work. [[L-0438]] WhatsApp is different: it has to deliver those messages to your device, because that is where they are stored. [[L-0439]]
