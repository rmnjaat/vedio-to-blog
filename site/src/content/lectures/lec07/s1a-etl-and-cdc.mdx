The multi-user blogging app has grown. The CEO wants detailed reports on how people use it and has hired analysts to produce them. The analysts know SQL very well. Production runs on a transactional database, MongoDB say, and it holds everyone’s personal data.

So the analysts need a copy of the data of their own, in a database they can query, and it has to be complete. This chapter is about getting that copy out without losing anything on the way.

</Section>

<Section id="s1-1" no="1.1" title="Day zero: dashboards on the production database" crumb="1.1 Day zero"
  dek="Before there is a warehouse, the dashboard reads production. That works for a while, then three things break it."
  meta="About 4 min · class 00:04–00:08">

Start with the blogging app on day zero, nothing fancy. There is a database and an API server. Users never reach the database directly: the API server talks to it, every request and response goes through the API, and the API hides the database’s details and complexity. [[L-0012]]

Measurement usually comes later. In this course’s telling, a company that has just launched rarely focuses on analytics or metrics; things like DAU, MAU or Google Analytics get added once some people use the product. [[L-0013]] Then, to understand how people actually use it, the company starts measuring: the number of blogs published, how many users are active, how many people leave a like in the first hour. [[L-0014]]

At this stage there is no data warehouse and nothing fancy. A visualization tool such as Grafana, Metabase or Tableau connects straight to the production database and fires its queries there to draw the charts. [[L-0015]] The usual first step away from that is a read replica. Analytics is the most common reason teams add one: a production database is tuned for many small, fast transactions, and heavy dashboard queries against the primary slow the app down <Cite href="https://www.metabase.com/glossary/read-replica">metabase.com</Cite>. [[L-0015]]

<Figure id="fig-1a" max={620} no="Fig 1·a" k="L-0012 L-0015 L-0018" caption="Day zero. Readers reach MongoDB only through the API; the dashboard (blue) fires its queries straight at production, which holds personal data. The dashed path is the usual first step: point the dashboard at a replica. Redrawn from the class board at 00:05.">
<Desk><DayZero /></Desk>
<Phone><DayZero layout="phone" /></Phone>
</Figure>

As a rule of thumb from experience, not a measured limit, this works very well for a Series A company, up to roughly 10,000–50,000 users. What actually runs out is not a user count but headroom: how expensive the dashboard queries are against what the database has to spare. [[L-0016]]

Then the business grows, and important decisions need data behind them. The CEO wants very detailed reporting on particular user behaviour, so the company recruits an insights team: business analysts, who need data to analyse the business. [[L-0017]]

Handing them the production database is very risky, even with read-only access, because it holds critical information, including personally identifiable information. [[L-0018]] GDPR’s data-minimisation principle asks that personal data be “adequate, relevant and limited to what is necessary” for the purpose <Cite href="https://gdpr-info.eu/art-5-gdpr/">gdpr-info.eu</Cite>, and analytics copies often drop or mask PII columns for that reason. [[L-0018]]

There is a second problem. Production may well be a NoSQL database like MongoDB, chosen because it sounded cool or fancy, or because it suited the use case really well. [[L-0019]] The analysts, though, are champs at SQL: they write very complex SQL queries with ease. [[L-0020]]

That they know SQL is not an assumption about these analysts; it is a hard truth about the field. Every data warehouse (Redshift, BigQuery) and every data lake format supports SQL queries, because everyone in the analytics domain is familiar with SQL. [[L-0021]] Strictly, a lake format such as Apache Iceberg is a table format, not a database: engines like Spark, Trino or Presto read the tables and provide the SQL <Cite href="https://iceberg.apache.org/">iceberg.apache.org</Cite>. And Redshift is based on PostgreSQL but stores data in columns and leaves out OLTP features, so its SQL differs from PostgreSQL’s in places <Cite href="https://docs.aws.amazon.com/redshift/latest/dg/c_redshift-and-postgres-sql.html">docs.aws.amazon.com</Cite>. [[L-0021]]

Give SQL analysts direct access to MongoDB and they will have no idea what to do with it. [[L-0022]] MongoDB does offer a read-only SQL Interface for BI tools today, MongoSQL over JDBC and ODBC <Cite href="https://www.mongodb.com/docs/sql-interface/">mongodb.com</Cite>, but that only answers the language problem. The personal data and the load on production remain. [[L-0022]]

So the company starts writing a pipeline: take the data out of MongoDB and put it into MySQL, because that is the one SQL database it knows. It is still early, and nobody cares much about proper data analysis yet. The next question is the real one: how does the data get from MongoDB to MySQL? [[L-0023]]

</Section>

<Section id="s1-2" no="1.2" title="The obvious pipeline: API events through Kafka" crumb="1.2 API events"
  dek="Publish an event whenever a blog is published, and let a consumer write the copy. It works, and it drifts."
  meta="About 4 min · class 00:08–00:11, Q&A 02:43–02:46">

We know Kafka. So the natural progression is this: whenever a blog is published, the API server publishes an event to Kafka, and a consumer reads it and writes it into MySQL in a particular format. [[L-0024]] (Kafka’s topics, partitions and consumer groups are in <LectureLink lec="lec01" sec="s3-6">Lecture 2</LectureLink>.)

Before judging it, set the bar. The analytics copy cannot have data misses. It doesn’t have to be real time, but it must be consistent with the source, eventually. The business makes decisions on this data, and the analysts only have access to the copy, never to production: if the copy is wrong, the decisions are made on wrong data. [[L-0025]]

<PauseAndThink k="L-0025 L-0026 L-0027 L-0028 L-0346"
  q="The API publishes a Kafka event whenever a blog is published, and workers write it into the analytics MySQL. Kafka itself never loses a message. Can the analytics copy still end up missing changes?"
  choices={[{ label: 'No: if Kafka keeps every event, the copy is complete' }, { label: 'Yes: some changes never become events', correct: true }]}
  right="Right. Events are application context, and the analytics copy needs raw data. Anything that changes the database without a matching event (a counter, a background job, a crash between the write and the publish) is missing from the copy."
  wrong="Kafka can only deliver what was published. A views++ has no event, a background job that aggregates likes never calls the API, and an API that saves a row and crashes before publishing loses that event. The copy drifts with no error anywhere.">

List what changes the database, not what the API announces. That gap is why 1.3 reads the database itself.

</PauseAndThink>

What goes wrong? The class board listed four problems, in this order: events have the context of the application; events might not contain all the data; everything might not have an event; and what if the change is done but sending the event failed (consistency). The figure numbers them as they are explained below. [[L-0026 L-0027 L-0028]]

**Not everything has an event** (① in Fig 1·b). Events are specific to the application: they hold the context of a use case, while analytics wants raw data. “Blog published” may have an event, and so may “user profile updated”. A minor change such as `views++` on a post does not. [[L-0026]] Some changes never pass through the API at all. An asynchronous worker that periodically aggregates the like count of a post changes the database outside any request, so there is no API event for it, yet you want that change in the copy too. [[L-0346]]

<Figure id="fig-1b" max={680} no="Fig 1·b" k="L-0024 L-0026 L-0027 L-0028 L-0049 L-0345 L-0346" caption="The event pipeline and its four leaks: ① changes with no event, ② events too thin to use, ③ a save whose event never leaves, ④ a new table nobody wired up. Kafka never reads MySQL here: workers consume what the API published. Redrawn from the class board at 00:08–00:09.">
<Desk><EventLeaks /></Desk>
<Phone><EventLeaks layout="phone" /></Phone>
</Figure>

**Events don’t carry all the data** (②). A “blog published” event may hold only the blog’s id. Then the consumer needs complex logic to go back to the database and fetch the rest, which puts unnecessary load on it. Pass the entire blog object instead and every message becomes huge, and the consumer pays for it in network I/O. [[L-0027]] Martin Fowler names the two styles: an *event notification* often carries just an id and a link back, so receivers call the source for details; *event-carried state transfer* puts the changed data in the event, so receivers don’t need to contact the source <Cite href="https://martinfowler.com/articles/201701-event-driven.html">martinfowler.com</Cite>. Full-object events have a ceiling too: Kafka caps a record batch at about 1 MB by default (`message.max.bytes`, as of Kafka 4.3), so very large events need config changes or a different design <Cite href="https://kafka.apache.org/43/configuration/broker-configs/">kafka.apache.org</Cite>. [[L-0027]]

**The change is saved, but the event never leaves** (③). The API writes the row, then crashes before it publishes. The database has the change; the copy never will. [[L-0028]] This is the *dual write*: there is no transaction that spans both the database and Kafka, so one write can succeed without the other. The transactional outbox pattern avoids it by storing the message in the same database transaction as the data and relaying it to the broker afterwards <Cite href="https://microservices.io/patterns/data/transactional-outbox.html">microservices.io</Cite>. [[L-0028]]

**It doesn’t keep up with the schema** (④). Feed a warehouse from API events, and every new table or use case means asking yourself: have I added its event to Kafka or not? That is very inefficient. [[L-0049]]

Events through Kafka sound like the obvious answer, and they are not. There has to be a better, much more seamless way. [[L-0028]]

One clarification, because the picture invites a wrong reading: in this design Kafka never reads MySQL, or any database. The workers consume the events the API server published; when they touch a database, it is to fetch what the event left out. [[L-0345]]

</Section>

<Section id="s1-3" no="1.3" title="Change data capture: read the source of truth" crumb="1.3 CDC"
  dek="Stop asking the API what changed. Ask the database."
  meta="About 5 min · class 00:10–00:15">

**CDC** stands for change data capture: any change in the data is captured. [[L-0029]] Instead of relying on events from the API server, a CDC tool relies on the actual source of truth, the database itself. That one choice is what makes CDC invaluable, and in this course’s view everyone uses it. [[L-0031]]

A CDC tool typically (it is not a hard rule) lets you configure three things: your source databases, your transformation logic and your sink databases. It pulls the data from the source and puts it into the sink in the format you want. [[L-0032]]

<Figure id="fig-1c" max={680} no="Fig 1·c" k="L-0029 L-0031 L-0032 L-0041 L-0042" caption="The same app with CDC. The tool reads MongoDB’s log (dashed: the tool starts it), optionally transforms the rows, and writes them into MySQL in your format. Inset: three changes to Blogs, three events. Redrawn from the class board at 00:11–00:13.">
<Desk><CdcReads /></Desk>
<Phone><CdcReads layout="phone" /></Phone>
</Figure>

Because it works on the database itself, it doesn’t matter whether the application has an event. A change your application server has no event for is still captured and pushed to the other database. [[L-0033]] And if the API server crashes while pushing an event, you lose nothing, because the pipeline never depended on that event. This is the highlight of change data capture. [[L-0034]]

Take a `Blogs` table: every insert, update or delete on it gives you one CDC event, one per changed row (or document). [[L-0041]]

<AnimationClip clip="l07-events-vs-cdc" no="Clip 1·1" k="L-0026 L-0028 L-0033 L-0034 L-0040 L-0065 L-0346"
  lead="Before you play it: the API saves a post and crashes before publishing its event. A worker bumps a like count with no event at all. Which copy ends up complete?"
  caption="The event pipeline misses every change that has no event or whose event was lost; CDC reads the database’s log, copies all four, and, after the CDC tool has been down, resumes from its checkpoint. Read the source of truth, not the API’s events." />

The sink doesn’t have to be a database. It can be Kafka, SQS, Kinesis, a local disk or one of many databases: whatever the tool’s plugins support. You can also do it your own way: pick an appropriate sink, such as a broker, and write your own, more complex transformations behind it. [[L-0042]] Put together, CDC is a great way to build replication across databases with some basic transformation in between. [[L-0043]]

Two open-source tools to know are Airbyte and Debezium. Install one locally and play with it: see how it is configured, what format the data arrives in, and how you transform it and push it somewhere. Airbyte is the easiest to set up. [[L-0030]] Know Airbyte’s CDC limits before you try it: most sources support CDC only on tables with a primary key, views aren’t supported, only inserts, updates and deletes are captured (TRUNCATE and ALTER don’t appear), and a newly added table needs a refresh before CDC tracks it <Cite href="https://docs.airbyte.com/platform/understanding-airbyte/cdc">docs.airbyte.com</Cite>. [[L-0030]]

<LectureLink lec="lec08" sec="s4-5">Lecture 5</LectureLink> used CDC once, as one way to get a configuration change from a database onto a broker. This is the closer look it promised.

</Section>

<Section id="s1-4" no="1.4" title="How a CDC tool reads, and where to point it" crumb="1.4 How CDC reads"
  dek="Scan the rows or tail the log, keep a checkpoint, and read from a replica."
  meta="About 6 min · class 00:12–00:14, Q&A 00:20–00:22, 00:28–00:29 and 02:41–02:43">

What does “reads the database” actually mean? At heart, a CDC tool keeps track of three things: what it is reading, where it is writing, and what its checkpoint is. How it does that has no hard and fast rule. [[L-0055]] Very commonly (again, not a rule; some plugins work other ways) it keeps track internally of how far it has read: up to which rows, and which column was updated. [[L-0035]] A log doesn’t hold the full history, so tools begin with an initial snapshot, a full SELECT of each table, and then stream changes from the log position recorded at that moment. Debezium does this when it first starts <Cite href="https://debezium.io/documentation/reference/stable/connectors/mysql.html">debezium.io</Cite>, and so does Airbyte’s first CDC sync <Cite href="https://docs.airbyte.com/platform/understanding-airbyte/cdc">docs.airbyte.com</Cite>. [[L-0035]]

There are two ways to read. One is to iterate the tables row by row. [[L-0036]] Polling like this needs a column like `LAST_UPDATE_TIMESTAMP` on every table, cannot see rows deleted since the last poll, and misses intermediate updates between two polls <Cite href="https://debezium.io/blog/2018/07/19/advantages-of-log-based-change-data-capture/">debezium.io</Cite>. [[L-0036]]

The other is the commit log, or binlog: the write-ahead log, where every commit is appended. The CDC tool literally reads that log and pushes the changes to the other database. [[L-0037]] MySQL, for example, holds a transaction’s changes until COMMIT and then writes the whole transaction to the binary log before the commit completes, so the binlog is in commit order. It exists for replication and point-in-time recovery, which is why CDC tools read it <Cite href="https://dev.mysql.com/doc/refman/8.4/en/binary-log.html">dev.mysql.com</Cite>. [[L-0037]]

<Figure id="fig-1d" max={640} no="Fig 1·d" k="L-0036 L-0037 L-0038 L-0072" caption="Left: scanning rows sees only what is still there, so a row deleted between scans never reaches the copy. Right: tailing the log sees every commit in order and remembers a checkpoint; c5 and c6 are one transaction, written together at commit.">
<Desk><TwoWays /></Desk>
<Phone><TwoWays layout="phone" /></Phone>
</Figure>

Which way you get depends on the bindings a database offers. MongoDB might choose not to expose its commit log, so CDC iterates its collections. Elasticsearch doesn’t offer one, so CDC iterates. MySQL has binlog support and exposes its log, so CDC reads it directly. [[L-0038]]

<SourceNote href="https://debezium.io/documentation/reference/stable/connectors/mongodb.html" site="debezium.io" k="L-0038">

How CDC reads depends on what the database exposes: MySQL’s binlog <Cite href="https://debezium.io/documentation/reference/stable/connectors/mysql.html">debezium.io</Cite>, PostgreSQL’s logical decoding and MongoDB’s change streams give a log; stores without one, like Elasticsearch, can only be re-scanned <Cite href="https://docs.airbyte.com/integrations/sources/elasticsearch">docs.airbyte.com</Cite>. MongoDB does expose its changes: Debezium’s MongoDB connector uses change streams, which need a replica set or a sharded cluster. A standalone server has no oplog, but a one-member replica set works.

</SourceNote>

For you, it doesn’t matter how the data is read. You configure a database as the source, another as the sink, and a transformation on the tool, and the data flows. [[L-0039]]

If the source database is down, nothing is captured. Once it is back up, the tool resumes from where it stopped: that is the job of these tools. [[L-0040]] Resuming needs the log to still be there. A PostgreSQL replication slot keeps all the WAL its consumer still needs, even while the CDC tool is down. That is how it resumes, but an abandoned slot can fill the disk, so cap it with `max_slot_wal_keep_size` and drop slots you no longer use <Cite href="https://www.postgresql.org/docs/current/warm-standby.html">postgresql.org</Cite>. MySQL purges old binlogs; if Debezium restarts after its position was purged, it needs a new snapshot (`snapshot.mode=when_needed` takes one automatically) <Cite href="https://debezium.io/documentation/reference/stable/connectors/mysql.html">debezium.io</Cite>. [[L-0040]]

That checkpoint is why CDC doesn’t lose data: it keeps track of which rows, documents or entities it has captured and pushed, and does that checkpointing for you, in sequence. [[L-0065]] It prevents loss, not duplicates. After a crash, Debezium’s consumers see every event at least once <Cite href="https://debezium.io/documentation/faq/">debezium.io</Cite>, and PostgreSQL may resend recent changes after a server crash, so make the sink apply changes idempotently, for example as an upsert by primary key. [[L-0065]]

Transactions fit this well. A transaction is an atomic unit: it may run ten SQL statements, but they are written to the log in one shot when it commits, and CDC reads them from there. [[L-0072]] The order in which transactions commit and land in the log is the order in which CDC reads them and pushes them into the other database. [[L-0073]] One detail for when you build on it: CDC emits one event per changed row, not one per transaction. Debezium can add BEGIN and END boundary events with transaction ids (`provide.transaction.metadata`, off by default), so a consumer can regroup a transaction <Cite href="https://debezium.io/documentation/reference/stable/connectors/postgresql.html">debezium.io</Cite>. [[L-0072]]

### Reading in practice

The most basic configuration reads through the database’s own client: a Postgres client, for Postgres. Some plugins instead extract the WAL files and process them; it depends on the plugin you use. [[L-0054]] The client is the better way. If the binlog or commit-log format changes tomorrow, the client handles the decoding and your plugin doesn’t need updating. [[L-0056]] Nor does it put much load on the database, because it is just a sequential read. [[L-0057]]

You can take even that load off the master. You don’t have to configure CDC on the master: spin up a new replica and point CDC at it. [[L-0058]] Check your database first. On MySQL, the replica must write the changes it receives into its own binlog (`log_replica_updates`, on by default in 8.4) <Cite href="https://dev.mysql.com/doc/refman/8.4/en/replication-options-binary-log.html">dev.mysql.com</Cite>; on PostgreSQL, a logical slot on a standby needs version 16 or later, and 17 adds failover slots so the tool can carry on after a promotion <Cite href="https://debezium.io/documentation/reference/stable/connectors/postgresql.html">debezium.io</Cite>. [[L-0058]] One replica is enough: all replicas hold the same data, so there is no need to read from every one of them. [[L-0342]]

<MarginNote title="Several CDC instances" why="skip unless you run CDC at high volume" k="L-0343 L-0344">

Several CDC instances can read the same source, active-standby or all active: “active standby both works” came up inside the question itself, so who said it is unclear. [[L-0343]] A single log stream has one active reader, though. In PostgreSQL only one receiver may consume a slot at a time <Cite href="https://www.postgresql.org/docs/current/logicaldecoding-explanation.html">postgresql.org</Cite>, so “all active” means each instance takes its own slice of the tables, with its own slot or offset, and a standby takes over on failure. [[L-0343]]

With several tables, instances can read them in parallel. They keep their read position, the last point read and committed, in a small database of their own, and contend for work with simple remote locks: normal synchronisation primitives. Remote locks are built in <LectureLink lec="lec08" sec="s6">Lecture 5</LectureLink>. [[L-0344]]

</MarginNote>
