This is day 1 of week 5, and week 5 is about storage engines, the lecture’s favourite topic: databases, distributed storage and query engines, a subject that rewards a deep understanding. [[L-0001 L-0002]]

The board’s agenda had two items: designing a distributed cache, plus ETL and tiered storage. Almost all the papers behind this lecture are about distributed storage. [[L-0003]] So far in the course, change data capture (CDC) had only been written into designs as a box; this session goes deeper into it. Tiered storage is taught from practice, from something built on top of it in production, which is where you learn what happens behind the scenes. [[L-0007 L-0008]]

The order is unusual. ETL comes first, only as an introduction “to form the dots”, the way the Kafka essentials did in Lecture 2. Its practical use comes later, when the course designs Amazon’s order system: one very detailed example that shows how data pipelines are built in general, because they all derive from one or two basic ideas. [[L-0009 L-0010]] <ForwardChip label="back in" when="Lecture 2" lec="lec01" sec="s3-6">Kafka essentials</ForwardChip> The two halves were not connected in class, and this page does not invent a link between them. Tiered storage, too, appears here only as one diagram in 1.5; it is introduced here and built in a later week.

The cache is a favourite discussion too: lots of brainstorming and critical questions, down to the nitty-gritty details that matter. [[L-0079]] The design has two brainstorms. The low-level implementation on one machine comes first (chapters 2–4); after the break comes the distributed design, with routing, consistent hashing and distributed hash tables (chapters 5–6). [[L-0082]] Throughout, the design draws on a reading of the Redis source and of how Redis made each decision (more in 2.1).

### Our Redis so far

So far in this course the cache has always been a box someone else built. In Lecture 1 the green dot’s heartbeats lived in a store with a TTL, Redis or DynamoDB, and the blog got one shared cache. In Lecture 2 that shared Redis sat next to Medium’s database, called by every API server. Lecture 3 built a key-value store on top of MySQL, looked at how Redis expires keys lazily and by sampling, and grew the store with replicas and range shards. Lecture 5 built a load balancer as a proxy, saw that DNS answers rather than forwards, then used Redis as the lock store and five independent Redis nodes for Redlock.
