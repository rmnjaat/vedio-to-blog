<Section id="s3" no="3" title="When the cache is full: eviction and expiry" crumb="3 Eviction and expiry"
  dek="Which key goes when memory runs out, and how expired keys disappear, without spending memory on bookkeeping."
  meta="About 25 min · class 00:58–01:18, 01:34–01:38, Q&A 01:45–01:47, 02:49">

A write arrives, and the check from chapter 2 fails: `total_size + b > maxmemory`. Our Redis is full. Before the new value can go in, some key has to go. Which one?

This chapter answers two questions about what leaves the cache. Eviction: which key to drop when memory runs out. Expiry: how keys whose TTL has run out actually disappear. Both answers keep their bookkeeping inside the per-key wrapper from chapter 2, and both are priced in bytes.

</Section>

<Section id="s3-1" no="3.1" title="LRU, LFU, and where their bookkeeping lives" crumb="3.1 LRU and LFU"
  dek="The two policies everyone names. Before choosing one, decide where its per-key information lives."
  meta="About 4 min · class 00:58–01:02">

Once the size counter shows the cache is full, total size beyond the configured cap, it is time to evict keys. The two strategies everyone names first are LRU and LFU. [[L-0133]]

**LRU**, least recently used, keeps for every key the last time it was accessed. When the cache is full, it removes the key that was used least recently. [[L-0134]]

**LFU**, least frequently used, keeps how often each key is used. When the cache is full, the key used least frequently is evicted. [[L-0135]]

Either way, every key needs a little information: when it was last used, or how often. Before deciding how to implement either policy, decide where that information is stored. [[L-0136]]

It is tempting to reach for a separate data structure that finds the eviction candidates, such as a priority queue ordered by frequency. [[L-0137]] Hold that thought; 3.2 puts a price on structures like it. There is already a place for per-key information: the wrapper around the value from [§2.3](#s2-3). Next to the type, keep a few **LRU bits**. [[L-0138]]

<Figure id="fig-3a" no="Fig 3·a" max={660} k="L-0138 L-0139 L-0142 L-0143"
  caption="The struct that grows, stage 2. The wrapper gains one field for eviction, updated on every access. Top bar: the split as taught, 4 type bits and 28 LRU bits in one 32-bit integer. Bottom bar: current Redis, 4 type bits, 4 encoding bits and a 24-bit LRU/LFU field in one word of the object header.">
  <Desk><StructStage2 /></Desk>
  <Phone><StructStage2 layout="phone" /></Phone>
</Figure>

How many bits? As taught, Redis stores 4 type bits and 28 LRU bits per object (28 is the figure on the board; 24 was mentioned first). Look at the sum: 4 + 28 is 32 bits, one integer of metadata per key, which keeps it very space efficient. The current Redis source packs that word a little differently: a 4-bit type, a 4-bit encoding and a 24-bit LRU/LFU field share one 32-bit word of each object header <Cite href="https://raw.githubusercontent.com/redis/redis/unstable/src/object.h">object.h</Cite>. [[L-0139]]

This is not a Redis quirk. Any database you pick keeps something like it: compact metadata inside the per-key object it already has. [[L-0140]] And it shows why wrapping the value in an object was a good decision: every piece of meta information a key needs, its type, its eviction bits and, in 3.5, its expiry, attaches to one place. [[L-0141]]

Every time a key is accessed, its bits are updated: a `++` for frequency, or a fresh timestamp. [[L-0142]] The same field serves either policy. Under LRU it stores a timestamp; under LFU it stores a frequency. [[L-0143]] Redis’s LFU is subtler than a plain `++`. Its 24 bits hold a 16-bit time and an 8-bit logarithmic (Morris) counter that saturates around a million hits and decays over time, tuned with `lfu-log-factor` and `lfu-decay-time` <Cite href="https://redis.io/docs/latest/develop/reference/eviction/">redis.io</Cite>. [[L-0143]]

</Section>

<Section id="s3-2" no="3.2" title="The textbook LRU, priced in bytes" crumb="3.2 Textbook LRU"
  dek="The interview answer is a hash map plus a doubly linked list. In a cache, count what it costs."
  meta="About 5 min · class 01:01–01:07, Q&A 01:46">

With the information stored, the next question is how to implement LRU or LFU. Is a priority queue the best way to know which key to evict? [[L-0144]]

The answer everyone gives is a hash map plus a doubly linked list. The list’s nodes hold the entries, and the map stores each key’s node address. A get or a put finds the node through the map, unlinks it and moves it to the head of the list in O(1); a size variable tells a put when the list is full; and removing a key is O(1) through the map as well. [[L-0145]] Because every access brings its node to the head, the order of the list tells you which key to evict: the one at the tail. [[L-0146]]

<PauseAndThink k="L-0145 L-0147 L-0148 L-0149 L-0152"
  q="A textbook LRU keeps a doubly linked list node per key: next, prev and value pointers. Your keys look like a → 2. Is that bookkeeping worth it in a cache?"
  choices={[{ label: 'No: the pointers cost more than the data', correct: true }, { label: 'Yes: it’s O(1), so it’s the standard answer' }]}
  right="Right, as the lecture argues: 12 bytes of overhead for 5 bytes of data. Redis skips the list and keeps a few bits in each object instead. Some caches, such as Memcached, do pay for the list (see “More precisely” below)."
  wrong="Not for a memory-bound cache. It is O(1) in time, but each node costs 12 bytes with 4-byte pointers (24 with 8-byte ones). Key a is 1 byte and the value 2 is 4 bytes: more bookkeeping than data.">

Price a design in bytes before you take the interview answer.

</PauseAndThink>

Price it. The list needs one node per key-value pair, and every node holds a next pointer, a previous pointer and a value pointer: 4 + 4 + 4 = 12 bytes of overhead for every pair. That is with 4-byte pointers; on a 64-bit machine each pointer is 8 bytes, about 24 bytes per key before the allocator’s own overhead. [[L-0147]]

Now store the key `a`, a 1-byte character, with the value `2`, a 4-byte integer. Five bytes of data carry 12 bytes of overhead whose only job is tracking recency. [[L-0148]]

<Figure id="fig-3b" no="Fig 3·b" max={720} k="L-0145 L-0146 L-0147 L-0148"
  caption="The textbook LRU and its bill. The map finds a key’s node in O(1); an accessed node moves to the head, so the tail is the next to evict. Each node is three pointers: 12 B with 4-byte pointers, 24 B with 8-byte ones, for a key and value that together take 5 B. Redrawn from the class board at 01:04.">
  <Desk><TextbookLru /></Desk>
  <Phone><TextbookLru layout="phone" /></Phone>
</Figure>

That is a huge waste of memory, and it marks the difference between the theoretical implementation that is usually taught (“just use a linked list”) and what real caches do. [[L-0149]]

<SourceNote href="https://raw.githubusercontent.com/memcached/memcached/master/doc/new_lru.txt" site="memcached docs" k="L-0149">

A linked-list LRU does cost pointers per key, and Redis avoids it by sampling (3.3). But caches such as Memcached accept the overhead: Memcached keeps a doubly linked LRU list per slab class, and its `lru_maintainer` mode splits it into HOT, WARM and COLD lists. MySQL’s InnoDB buffer pool is managed as an LRU list too <Cite href="https://dev.mysql.com/doc/refman/8.4/en/innodb-buffer-pool.html">dev.mysql.com</Cite>. Production caches do pay for a linked-list LRU when they judge it worth it; Redis chose not to <Cite href="https://redis.io/docs/latest/develop/reference/eviction/">redis.io</Cite>.

</SourceNote>

It is not that linked lists are never used. They are used where memory is not the constraint, and a cache is a very memory-intensive application, so the linked-list approach suits other kinds of programs better. [[L-0150]] The Linux kernel, for one, is filled with linked lists built exactly this way. When the operating system boots it creates at least 52,000 of them in memory: a number relayed second-hand in class, from a Linux kernel contributor. [[L-0151]]

Redis does not maintain such a list for eviction, because of the extra memory. Redis, or any in-memory cache, would rather spend its memory on user data than on this meta information. [[L-0152]] In real-world implementations of eviction, a lot of databases choose not to use a linked list or anything like it. Some do and some don’t: Memcached and InnoDB’s buffer pool keep LRU lists (InnoDB with midpoint insertion, 3.4), while Redis samples instead. [[L-0153]]

The same bargain shows up with LFU. An LFU that runs in O(1) time exists, and its memory consumption is very high. When you want better time you give up space; when you are constrained on space you trade it back for time. That is why people don’t use it in a cache. [[L-0238]]

<Section id="s3-3" no="3.3" title="Random eviction" crumb="3.3 Random eviction"
  dek="Keep nothing at all, evict any key, and fit more keys into the same memory."
  meta="About 5 min · class 01:06–01:10, Q&A 01:45–01:46, recap 01:33">

Redis supports all three policies: LRU, LFU and random. It implements LRU and LFU very efficiently on those per-key bits, with a superb algorithm the class did not go into (“It would take me three years to talk about it”). [[L-0154]] The full menu in Redis today: `noeviction`; `allkeys-lru`, `allkeys-lfu` and `allkeys-random`; their `volatile-` variants, which only consider keys that have a TTL; `volatile-ttl`; and, since Redis 8.6, a least-recently-modified pair, `allkeys-lrm` and `volatile-lrm` <Cite href="https://redis.io/docs/latest/develop/reference/eviction/">redis.io</Cite>. [[L-0154]]

The third strategy is the most memory-efficient. Instead of keeping extra information to find the least recently or least frequently used key, pick one key at random and evict it. Nothing extra is needed at all. [[L-0155]]

The risk is plain: pure random eviction may delete a key that should have stayed in the cache. If that key is used often, it costs one cache miss; the next read fetches it and puts it back. [[L-0156]]

What it saves is the per-key information, so you can fit more key-value pairs into the same amount of space just by switching to random eviction. [[L-0157]]

It works in production. When one production cache’s eviction strategy was switched to random, the cache could ingest a large number of keys with only a very small rise in its miss ratio, and that balanced things out. [[L-0158]]

It does rely on luck: one of the most important keys can be evicted. But what are the odds that your most important key is the one evicted every time eviction runs, when the cache holds millions of keys? Low. [[L-0159]] And with no bookkeeping, eviction is very fast: not optimal, but fast. [[L-0160]]

That is the trade-off. Evicting the true least recently used key needs extra space to keep track of recency. Give up the absolute correctness of the choice and eviction gets faster, because there is nothing to compute, maintain or store. Computer science is full of trade-offs like this. [[L-0161]]

How does Redis run LRU on 28 bits without a list? That algorithm was called too deep to cover live; it would take a couple of hours on its own. It is less deep than that sounds: the Redis docs explain it in a few paragraphs <Cite href="https://redis.io/docs/latest/develop/reference/eviction/">redis.io</Cite>, and the note below gives the gist. [[L-0236]]

And can you get LRU or LFU under tight memory at all, designed at a high level? The answer given was blunt: “You cannot do that.” The real implementation is very deep, so go with random, which is very low on memory, needs no additional data, and only risks deleting an important key. [[L-0237]]

<SourceNote href="https://redis.io/docs/latest/develop/reference/eviction/" site="redis.io" k="L-0237">

Under memory constraints you can still have LRU or LFU, approximately: keep a few bits of access time or frequency per key, and at eviction time sample a handful of keys and evict the worst of them. That is what Redis does. It samples `maxmemory-samples` keys (default 5), evicts the one idle longest (or with the lowest LFU counter), and since Redis 3.0 keeps a pool of good candidates. With 10 samples the result is very close to true LRU.

</SourceNote>

To sum up the board’s recap: when the cache is full, evict with one of three strategies, LRU, LFU or random. Random has zero memory overhead. It trades the correctness of the system, since it may delete the most important key, for fitting more data, and if that works for your workload the overall benefit can be significant. How do you know the cache is full? The board’s recap gave two ways: a cap on the max number of keys in the cache (the hash table), or a cap on the cumulative size of the values inserted, `total_size += sizeof(obj)`, which is what zmalloc keeps by wrapping malloc ([§2.6](#s2-6)). You can trigger eviction only when you know the cache is full. (The key-count cap was on the board only, not in the audio.) [[L-0208]]

<Section id="s3-4" no="3.4" title="LRU or LFU? Follow the key’s life" crumb="3.4 LRU or LFU"
  dek="The names are easy. The differentiator is how a key is read over time."
  meta="About 7 min · class 01:09–01:18, Q&A 02:49–02:50">

When would you use LRU, and when LFU, and why? The question is not only about caches; it applies wherever either algorithm could run. [[L-0162]]

One answer suggested in class: LRU for streaming-like workloads, LFU when some things need to be accessed again and again, offered with an honest admission of being a bit confused. [[L-0163]] That confusion is universal. Anyone can expand the names, least recently used and least frequently used, but what is usually missing is a concrete differentiator that says where to use which. Even the person teaching this only understood it after writing an LRU and an LFU by hand. [[L-0164]]

The clincher came from class too. LFU makes more sense where you scan a lot of data. Under a recency policy, one scan, say a scan query over a database, can wipe out earlier entries that were used far more often. A frequency policy keeps the heavily used items, because one read each does not outweigh their counts. [[L-0165]] Databases meet exactly this problem. MySQL’s InnoDB buffer pool makes its LRU scan-resistant with midpoint insertion: a new page enters at the head of an “old” sublist (3/8 of the pool by default) and is promoted only if it is read again <Cite href="https://dev.mysql.com/doc/refman/8.4/en/innodb-buffer-pool.html">dev.mysql.com</Cite>. [[L-0165]]

<PauseAndThink k="L-0165 L-0167 L-0168 L-0169 L-0172"
  q="A Wikipedia cache holds evergreen pages that are read all day. Then a nightly report scans every article once (or the World Cup sends a burst to a few pages). Which policy keeps the evergreen pages?"
  choices={[{ label: 'LRU: recent is what matters' }, { label: 'LFU: frequent is what matters', correct: true }]}
  right="Right: the evergreen pages have high counts, so one-off reads don’t push them out. When the burst passes, they are still there."
  wrong="Wrong here: the scan touches thousands of pages once, so they are all “recent”. LRU evicts the evergreen pages to hold them, and the morning traffic misses.">

It depends on the key’s life. Keys that are hot and then forgotten (news, a trending song) suit LRU; keys whose past popularity predicts their future suit LFU.

</PauseAndThink>

<AnimationClip clip="l07-lru-vs-lfu" no="Clip 3·1" k="L-0165 L-0167 L-0168 L-0169"
  lead="A nightly report scans every article once. Which cache still holds the evergreen pages in the morning?"
  caption="One burst of one-off reads flushes the evergreen pages from LRU but not from LFU, so LRU misses the next morning. When past popularity predicts the future, frequency wins. Redis approximates both by sampling." />

An analogy helps, about human behaviour rather than a use case: the stock market. You buy a stock with full faith in it. It rises, you are happy, and then it falls. You can sell on its recent performance, or hold it because it did well before and you trust it will rise again. Holding it is LFU. You are not going by recency bias; you are betting that what did well in the past will do well in the future. If it rises again you are happy; if it falls again, you wish you had evicted it. [[L-0166]]

So use LFU when you trust that a key is worth keeping even though its access has recently dipped: what was accessed often in the past will be accessed often again. [[L-0167]] Wikipedia is the example. It runs a ton of cache, and a page that is not read much right now but was read very often in the past should stay in memory. [[L-0168]] During the FIFA World Cup everyone opens FIFA pages. That recent spike should not evict the other top pages, which were visited far more often; once the fad passes they will be read at the same rate again. That is where LFU fits. [[L-0169]]

LRU fits the opposite pattern: a key read very aggressively at first, followed by a slump. [[L-0170]] Social media trends work this way. A song goes viral, everyone makes reels with it, and it sits in a cache at YouTube or Instagram; once the fad is over nobody picks it, and dropping it from the cache is fine. [[L-0171]] The classic example is Google News. You rarely read week-old news, mostly news a day or two old at most, so very recent items are the ones most likely to be read again. [[L-0172]] The board’s recap lists CDN next to Google News as an LRU example. [[L-0162]]

<Figure id="fig-3c" no="Fig 3·c" max={720} k="L-0166 L-0168 L-0170 L-0172"
  caption="Two access patterns, as drawn on the class board. LRU (news): a sharp spike that decays into a long flat tail. LFU (Wikipedia): a zig-zag line that keeps rising, like a stock chart; the stock you hold through a dip is LFU. Redrawn from the class board at 01:12 and 01:17.">
  <Desk><AccessPatterns /></Desk>
  <Phone><AccessPatterns layout="phone" /></Phone>
</Figure>

Another way to say it, also suggested in class: LFU pays off when the popularity of keys is very asymmetric, a few keys used by everyone and the rest not, and LRU when it is not. The refinement: with LFU you keep a popular key even when it has not been accessed recently, the way you hold the stock that gave good returns in the past. [[L-0351]]

Neither always wins. In most production systems you would not even see a difference between LRU and LFU; in some extreme cases the difference is significant. [[L-0173]] Which is why the choice starts with the key, not the algorithm:

<RuleBox rule="==Understand the life cycle of a key== before you pick a policy." k="L-0174">

Before configuring LRU or LFU, spend time understanding your application and your users’ behaviour: how a particular key is accessed, and how its life runs in your system. Then decide.

</RuleBox>

<Section id="s3-5" no="3.5" title="Expiry without extra structures" crumb="3.5 Expiry"
  dek="A key’s TTL runs out. Who deletes it, and what does that cost in memory?"
  meta="About 6 min · class 01:34–01:38">

Expiry answers to the same budget as everything else in an in-memory cache: every design decision must use the bare minimum of bytes. If handling TTLs required storing a lot of data, it would be futile, spending a lot of memory on something that is not that critical. [[L-0210]]

Key expiry is not new. Lecture 3 built it for the key-value store and looked at how Redis does it; the same apparatus is reused here. <ForwardChip label="back in" when="Lecture 3" lec="lec05" sec="s8-1" k="L-0211">how Redis expires keys</ForwardChip> [[L-0211]]

First, store the minimum: the key’s absolute expiry time, in the per-key object, next to the LRU bits. [[L-0213]] The obvious way to clean up is a priority queue of keys ordered by expiry, freed from the head. The board gave it its due, simple and consistent, but it is an additional data structure that needs a lot of pointers, so it is out. [[L-0214]]

<Figure id="fig-3d" no="Fig 3·d" max={720} k="L-0213 L-0214"
  caption="Expiry: the queue we don’t build. Left: a priority queue ordered by absolute expiry time, freed at the head; simple and consistent, but one more structure with pointers for every key. Right: the struct that grows, stage 3: one more number in the wrapper. Left panel redrawn from the class board at 01:35.">
  <Desk><ExpiryQueue /></Desk>
  <Phone><ExpiryQueue layout="phone" /></Phone>
</Figure>

What deletes an expired key, then? First, **lazy deletion**. When a key is accessed and its object’s expiry time is earlier than the current time, the key has expired, and it is deleted right then. [[L-0215]] The delete is `zfree`, the counterpart of `zmalloc`: it decrements the total size and frees the object. [[L-0216]] In memory that is just a free call, which is cheap, and since keys in a cache are very likely to be read, most keys are deleted this way. [[L-0217]]

That leaves the keys that expire and are never read again. For them, use **sampling**: among the keys that have an expiration set, sample exactly 20, delete the ones that have expired, and repeat until fewer than 25% of a sample are expired-but-not-deleted. [[L-0218]]

<SourceNote href="https://raw.githubusercontent.com/redis/redis/unstable/src/expire.c" site="expire.c (Redis source)" k="L-0218">

That is the classic rule. Since Redis 6.0 the active expiry cycle walks the table of keys with a TTL incrementally, with a cursor, 20 keys per loop, and keeps going while more than about 10% of the checked keys are expired (tunable with `active-expire-effort`), within a CPU-time budget <Cite href="https://raw.githubusercontent.com/redis/redis/6.0/00-RELEASENOTES">Redis 6.0 release notes</Cite>.

</SourceNote>

Memory leaks this way, but not permanently: every expired key is eventually deleted, either by a later read or by another round of sampling. [[L-0219]]

Redis chose lazy deletion plus sampling because neither one needs an additional data structure: Redis has no priority-queue implementation for TTLs. That is how it fits a large amount of data into a small amount of RAM. Every single bit matters. [[L-0220]] It does keep one index for expiry, though: `db->expires`, a second table of just the keys that have a TTL, which the active cycle walks <Cite href="https://raw.githubusercontent.com/redis/redis/unstable/src/server.h">server.h</Cite>, and the Redis docs note that setting an expire costs memory. [[L-0220]]

The board summed it up in one line: every cache server runs a cleanup process that frees expired keys, `free(obj)`, after which the garbage collector picks them up. In a C cache like Redis there is no garbage collector to wait for: the cleanup calls `free` (through `zfree`), which hands the memory back to the allocator at once. Nor is it a separate process: Redis runs its active expiry inside its main event loop <Cite href="https://raw.githubusercontent.com/redis/redis/unstable/src/expire.c">expire.c</Cite>. [[L-0212]]

<RecallQuestions>
  <RecallItem q="Where do the LRU bits and the expiry time live, and why not in a separate structure?">

In the per-key wrapper, `MyValue`, next to the value pointer and the type: `lru_bits` (a timestamp under LRU, a counter under LFU) and `expires_at`. A separate structure, a linked list for recency or a priority queue for expiry, costs pointers for every key: 12 bytes of list node for 5 bytes of data in the example. A memory-bound cache would rather spend those bytes on user data.

  </RecallItem>
  <RecallItem q="A cache of news articles: LRU or LFU, and what single observation would change your answer?">

LRU. News is read hard for a day or two and then forgotten, so recency predicts the next read. Switch to LFU if you see keys whose past popularity predicts their future, evergreen articles read again and again, or regular scans that would flush them out of a recency-based cache.

  </RecallItem>
  <RecallItem q="What deletes an expired key that nobody ever reads again?">

Not lazy deletion, which only runs when a key is accessed. The sampling pass does: it samples 20 keys that have a TTL, frees the expired ones with `zfree`, and repeats while more than 25% of a sample were expired (about 10% in Redis 6.0 and later). Until a sample catches it, the key leaks memory, but not forever.

  </RecallItem>
</RecallQuestions>
