<Section id="s4" no="4" title="How full is the box?" crumb="4 How full" meta="About 7 min">

Every write puts more into the cache’s memory, and so far nothing takes anything out. This chapter finds out what happens when memory runs out, why that must never happen to a cache, and how the cache can know where it stands, cheaply, on every single write.

<Section id="s4-1" no="4.1" title="What happens when the heap runs out?" crumb="4.1 Out of memory">

Every wrapper and every value lives on the heap: `malloc` in C, `new` in Java, whatever your language uses. [[L-0100]] So what happens when the heap is exhausted?

“The eviction policy runs” is the tempting answer. But eviction is the cache’s own policy, and it runs only if the cache was written to run it. The question is about the program underneath. [[L-0101]] Make it concrete: a loop mallocs 1 MB on every pass, forever, on a machine with 1 GB of RAM. After 1,024 passes everything is used. What happens on pass 1,025? [[L-0102]]

`malloc` returns NULL, and a careful program checks and refuses the write; or, on Linux, the kernel’s OOM killer ends the process outright. [[L-0338 L-0104 L-0341]]

So at the limit, either a write fails or the process dies. For a cache, the second is the disaster. It must keep running no matter what, so it must never reach that point. It has to cap its own memory, and that raises a first question: how does it know how much memory it is using? [[L-0106 L-0107]]

</Section>

<Section id="s4-2" no="4.2" title="Can’t you just ask the operating system?" crumb="4.2 Ask the OS?">

A command that reports a process’s memory certainly exists. The kernel is what knows the number, though, so every check is a system call, a trip into the kernel. The cache would need the answer on every write, and paying a system call each time would slow it right down. [[L-0108 L-0109]]

So the cache keeps its own count. [[L-0110 L-0113]] Multiplying the number of keys by a size per key won’t do, because values differ wildly in size. A running counter is better: `size += n` every time something is added. [[L-0111]] But add how much? [[L-0112]]

<PauseAndThink k="L-0112 L-0118 L-0119"

  choices={[{ label: 'Yes: the wrapper is what the key costs' }, { label: 'No', correct: true }]}
  right="Right."
  wrong="Look at what the wrapper’s pointer leads to.">

`sizeof` measures the wrapper: the pointer and the type, 16 bytes. The Bloom filter it points to is a separate block of memory, a megabyte the counter never sees. With enough such keys, the count is off by gigabytes.

</PauseAndThink>

</Section>

<Section id="s4-3" no="4.3" title="Every byte comes from somewhere. Where?" crumb="4.3 One place to count">

So where does every byte come from? C makes it visible, but the same holds in any language. [[L-0114]] `malloc` takes the number of bytes you want and returns an address you can use. It hands out memory from the process’s heap and asks the operating system for more only when its own free memory runs low. [[L-0115]] `free` gives a block back, marking it reusable. [[L-0116]] Adding a key means a `malloc` for its wrapper. [[L-0117]] And that Bloom filter didn’t appear from nowhere either. Storing it took a `malloc` call of its own. [[L-0119]]

Everything the cache stores, wrappers, Bloom filters, sets, lists, the nodes of a linked list, is allocated by the same `malloc` and released by the same `free`. [[L-0120]] So count there: `size += b` on every `malloc`, `size -= b` on every `free`. The total then includes the values themselves, not just their wrappers. To make sure that line runs on every allocation, write your own wrapper around `malloc`, and one around `free`. [[L-0120 L-0121]]

That wrapper is exactly what Redis has. It is called `zmalloc`, it has the same signature as `malloc`, and in the Redis code base you never see `malloc`, only `zmalloc`. [[L-0122 L-0126]]

```c
size_t total_size = 0;  // bytes held, all of them

void *zmalloc(size_t b) {
    size_t *p = malloc(sizeof(size_t) + b);  // room to note the size
    if (p == NULL) return NULL;              // caller refuses the write
    *p = b;
    total_size += b;
    return p + 1;
}

void zfree(void *o) {
    if (o == NULL) return;
    size_t *p = (size_t *)o - 1;             // the size noted at malloc
    total_size -= *p;
    free(p);
}
```

`free` needs to know how many bytes to subtract, and a pointer alone doesn’t say, so this `zmalloc` notes each block’s size in a small header in front of it. (Real allocators can often report a block’s size themselves; Redis uses that when it can.)

Now `total_size` always says how much memory the cache holds, with no system call. Redis does still ask the OS now and then, which is fine for an occasional check; the counter is what it relies on. [[L-0123 L-0124]] And notice why the wrapper matters. The naive way puts a count update next to every `malloc` call. With `malloc` at, say, 50,000 places in a code base, forget one and the count is wrong for good. The wrapper does it in one place. [[L-0125]]

The cap is a number you choose when you start the cache: say 1 GB, even if the machine has 32 GB. In Redis it is the `maxmemory` setting; left at 0, the default on 64-bit machines, there is no limit at all. [[L-0127]] Enforcing it takes one check before allocating. If `total_size + b` would pass the cap, refuse the write with an error, or make room first: drop a key, then allocate. [[L-0128 L-0129]]

```c
// our design: the cap inside the wrapper
void *zmalloc(size_t b) {
    while (total_size + b > maxmemory)
        if (!evict_a_key()) return NULL;     // nothing left: refuse
    ...                                      // then as above
}
```

That is a fine design. Redis splits the same two jobs differently: its `zmalloc` only counts, and the `maxmemory` check runs once per command, before the command executes. Under an eviction policy it evicts keys until usage is back under the cap; under the default, `noeviction`, it refuses the write with an error, the other branch of our design. [[L-0122 L-0129 L-0154]] Because the check runs once per command, not inside every allocation, a single command can push memory briefly past the cap: `maxmemory` is a soft limit. [[L-0127]]

Nothing here is fancy: a counter, a wrapper, one comparison. Yet it tells you exactly when the cache is full and exactly where eviction plugs in. Big systems are built on simple solutions like this one. [[L-0130 L-0132]]

<MarginNote title="Go deeper: what really happens at the limit" why="skip unless you write C" k="L-0339 L-0341 L-0358 L-0359">

Linux overcommits memory by default: `malloc` can succeed with no physical memory behind it, because pages are only allocated when first touched. So the OOM killer strikes later, with SIGKILL, which no handler can catch. A `ulimit` instead makes `malloc` fail with ENOMEM, and SIGABRT comes only from the program calling `abort()`. A segfault comes only from using an unchecked NULL.

</MarginNote>

So the cache knows the moment it is full. Something has to go. Which key? [[L-0133]]
