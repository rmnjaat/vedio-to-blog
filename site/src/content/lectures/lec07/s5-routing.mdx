<Section id="s5" no="5" title="Many nodes: splitting the keys and finding them" crumb="5 Routing"
  dek="One node can’t take the load. Split the keys across nodes, and then decide who tells a client where its key lives."
  meta="About 15 min · class 01:50–02:07, Q&A 02:29–02:32">

Our Redis is done as a single box: it stores typed values, counts its bytes, evicts, expires, speaks a lean protocol and takes turns on one thread. Now the blog app grows past it. One node can no longer handle the load, or hold the data.

This chapter splits the keys across several nodes and then faces the question that splitting creates: when a client wants a key, how does it find the node that has it?

</Section>

<Section id="s5-1" no="5.1" title="Why distribute, and splitting the keys" crumb="5.1 Splitting the keys"
  dek="Run the same single-node cache several times, and give each copy its own slice of the keys."
  meta="About 3 min · class 01:50, 01:55–01:57, board 02:07">

Make the cache distributed when one node is not enough: when it can’t handle the load, or can’t hold the data. The cache is then spread across multiple machines. [[L-0241]] The design has five aspects, in this order: storage, routing, availability, reliability and scaling. [[L-0242]]

Storage comes first, and it is the simplest. Take the exact same single-node cache from chapters 2–4, run several instances of it, and give each one a mutually exclusive subset of the keys: say A to J on the first, K to T on the second, U to Z on the third. The ranges are only an example; the point is that the key space is split into slices that don’t overlap. [[L-0243]] <ForwardChip label="back in" when="Lecture 3" lec="lec05" sec="s9-3" k="L-0243">range shards and routing</ForwardChip>

<Figure id="fig-5a" no="Fig 5·a" max={340} k="L-0243"
  caption="The key space split into three slices that don’t overlap, one per copy of the same single-node cache. Redrawn from the class board at 01:55.">
  <KeyRanges />
</Figure>

This is the question that came up back in [§2.2](#s2-2), when the cache was still one machine: what if there are several? The answer then was to finish the single node first and think of sharding when distributing. This is that sharding. [[L-0089]]

The board put the whole idea in one line. A distributed cache is multiple single cache servers working together as a single coherent cache, for example behind a proxy. [[L-0263]]

</Section>

<Section id="s5-2" no="5.2" title="The routing problem" crumb="5.2 Routing"
  dek="A client wants the key kiwi. Which of the three nodes does it talk to?"
  meta="About 3 min · class 01:56–01:59">

Splitting storage adds a routing problem. When a client wants to store or read a key, how does it know which node, cache 1, 2 or 3, owns that key’s range? [[L-0244]]

<PauseAndThink k="L-0244 L-0245 L-0246 L-0248"
  q="Three cache nodes own key ranges a–j, k–t and u–z. A client wants <code>kiwi</code>. Does it need a central routing table that every request goes through?"
  choices={[{ label: 'No: there are several places routing can live', correct: true }, { label: 'Yes: someone central has to know who owns what' }]}
  right="Right. Four, in fact: a proxy, a smart client, any node forwarding, or a node that redirects you. Each trades a network hop against how much the client must know."
  wrong="That is one option, not the only one. A central router (a proxy) works, and a load balancer is exactly that. But the table can also live in the client, or the nodes can forward or redirect for you.">

The bank visit in the next section lays out the four.

</PauseAndThink>

The first idea suggested in class is a central place, exposed to clients, that stores the mapping from key range to node: A–J on C1, K–T on C2, U–Z on C3. A client’s first request goes there to learn where to talk. [[L-0245]] That works, and it raises a sharper question, the right one to ask: does that routing layer answer the client with where to go, or does it forward the request itself? Both have pros and cons, and different systems do it differently. [[L-0246]]

None of this is special to caches. The routing challenge holds for any distributed storage system: storage split across N mutually exclusive subsets, and a client that must reach the right one. [[L-0247]]

</Section>

<Section id="s5-3" no="5.3" title="Four ways to route: a visit to the bank" crumb="5.3 Four ways"
  dek="You walk into a bank with a form. Who takes it to the right desk?"
  meta="About 7 min · class 01:59–02:06">

There are four ways to route a request (a fifth is welcome), and each one is something you already do at a bank. These four everyday practices translate as they are into communication in distributed systems, and every distributed system uses one of them. [[L-0248]]

**1 · Proxy.** At the bank door stands a peon who, for a commission (call it a bribe), gets your work done. You talk only to the peon; you know nothing about how many desks or departments are inside. That is the standard proxy. [[L-0249]] A load balancer works exactly this way: one point of entry, responsible for getting every request done, and it can serve as the routing layer. [[L-0256]] A distributed cache behind such a proxy is the board’s definition from 5.1: many single servers working as one coherent cache. [[L-0263]] <ForwardChip label="back in" when="Lecture 5" lec="lec08" sec="s5-7" k="L-0256">what a load balancer is</ForwardChip>

**2 · Smart client.** A long-time customer knows the bank and walks straight to the right desk. Here the routing information lives in the client itself: it knows all the nodes, and no router is needed. [[L-0250]] The trade-off: if responsibilities move between desks, when the topology changes, every client has to be told. That burden is acceptable, but it is the disadvantage. In return there is no intermediate hop, so you save the bribe, which here is network latency. [[L-0251]]

**3 · Forwarding.** No peon. You go to the nearest desk, and it is that desk’s responsibility to forward your request to the desk that can handle it, get the response and send it back to you. There is no central authority: any node takes responsibility for forwarding. [[L-0252]] The internet itself works this way: you connect to a machine, it forwards your packets to another, and so on, and the response comes back the same way. [[L-0258]] IPFS, the InterPlanetary File System, was given as the example, with BitTorrent on the same kind of overlay network. Strictly, their Kademlia-based lookups are iterative: a queried node returns peers closer to the key and the requester contacts them itself, which is closer to the redirect way below than to forwarding <Cite href="https://docs.ipfs.tech/concepts/dht/">docs.ipfs.tech</Cite>. [[L-0253]]

<MarginNote title="Go deeper: overlay networks" why="skip unless you want peer-to-peer routing" k="L-0254">

The class pointed to a long video series on IPFS and BitTorrent-style overlay networks, where nodes route requests for each other. Chapter 6 comes back to these as distributed hash tables.

</MarginNote>

**4 · Redirect.** You go to the nearest desk and it says: “I’m busy, go to counter number 13.” You then go to that counter yourself. This is what DNS does: the DNS server returns the IP address, and you connect to it directly. [[L-0255]] <ForwardChip label="back in" when="Lecture 5" lec="lec08" sec="s5-2" k="L-0255">DNS answers; it doesn’t forward</ForwardChip>

<Section id="s5-4" no="5.4" title="Which way for a cache?" crumb="5.4 For a cache"
  dek="Now pick one for our Redis, and see which one Redis picked."
  meta="About 6 min · class 02:04–02:08, Q&A 02:29–02:32">

Which of the four is right? None of them, in general.

<RuleBox rule="There is ==no one right routing approach==: pick your battles." k="L-0257">

Each way has advantages and disadvantages. Make the client smarter to save a network hop. Add a proxy hop to make things easier for clients. For gigantic decentralised systems like Bitcoin or BitTorrent, let nodes forward for each other. Or make it like DNS: the node tells you where to go, and you connect directly. Pick your favourite; whatever works, works for you.

<Desk><PickYourBattle /></Desk>
<Phone><PickYourBattle layout="phone" /></Phone>

</RuleBox>

For a cache, a central proxy or router that holds the routing table and forwards requests for you, much like a load balancer, would work. A smart client holding the routing information would also work, with the disadvantage that clients must learn about every change in the topology. [[L-0259]] Forwarding by any node is what you typically would not use for a cache: it brings far too many complications. [[L-0260]]

<Figure id="fig-5c" no="Fig 5·d" max={640} k="L-0263 L-0269"
  caption="A distributed cache behind a proxy. Hash routing lets a hash of the key name the node; range routing gives each node a range of keys. Redrawn from the class board at 02:07, with the board’s own split (a–j, k–p, q–z) rather than the a–j, k–t, u–z used earlier in this chapter; the board’s second range, written [j–p], is a slip of the pen for [k–p].">
  <Desk><ProxyCache /></Desk>
  <Phone><ProxyCache layout="phone" /></Phone>
</Figure>

Whichever way you route, something has to decide which node owns a key. With range-based routing, ownership comes from key ranges, cache 1 owning A to J and so on; with hash-based routing, the hash of the key picks the owner. Chapter 6 takes the hash way much further. [[L-0269]]

And Redis? Redis uses the redirect way. When you fire a write at a replica, it returns the master’s IP address and asks you to write on the master, because replicas don’t take writes. It does this for replicas, not on every request. [[L-0261]]

<SourceNote href="https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/" site="Redis Cluster specification" k="L-0261">

In Redis Cluster, a node that doesn’t own a key’s hash slot replies with a redirect such as `-MOVED 3999 127.0.0.1:6381`, and the client retries at that address. A standalone Redis replica just refuses writes <Cite href="https://redis.io/docs/latest/operate/oss_and_stack/management/replication/">replication</Cite>, and clients learn the master’s address from Sentinel <Cite href="https://redis.io/docs/latest/operate/oss_and_stack/management/sentinel/">Sentinel</Cite>.

</SourceNote>

Why redirect rather than put a load balancer in front? To keep the infrastructure simple: there is no need for another component when the node itself can take care of it. [[L-0323]]

For reads, both ways exist in Redis: Redis Sentinel addresses the problem, and Redis now also has a proxy that holds routing information. Redis keeps evolving; the lecture was 100% sure only about the write-on-replica redirect, not sure how routing works in today’s Sentinel setup, and suggested watching talks on it. [[L-0324]] For the record, Sentinel does monitoring, failover and service discovery: clients ask Sentinels for the current master’s address. It does not route reads, and open-source Redis has no built-in routing proxy <Cite href="https://redis.io/docs/latest/operate/oss_and_stack/management/sentinel/">redis.io</Cite>. [[L-0324]]

Nor do you have to pick only one. A real system can mix two or more of the four, using a different one for different operations. [[L-0325]]

Returning the master’s address when a write hits a read replica was called the most common way: almost all databases adopt it. [[L-0326]]

<SourceNote href="https://www.postgresql.org/docs/current/hot-standby.html" site="PostgreSQL docs · Redis docs" k="L-0326">

That overgeneralises. Many databases reject a write on a replica with an error rather than returning the primary’s address: a PostgreSQL hot standby errors on INSERT, UPDATE and DELETE, and a standalone Redis replica rejects writes <Cite href="https://redis.io/docs/latest/operate/oss_and_stack/management/replication/">redis.io</Cite>. Drivers, Sentinel or connection strings find the primary. Address-returning redirects, like Redis Cluster’s `MOVED`, are one approach, not “almost all”.

</SourceNote>

The alternative is exactly that: discard the write, return an error, and say “go find the master node.” Databases are like people here: some say “go find it on your own”, others kindly tell you where to go. [[L-0327]]

Step back and the four ways are a general lens. Any distributed system’s routing layer can be built on one of them, and it is simple, and fun, to build. [[L-0262]]

<RecallQuestions>
  <RecallItem k="L-0249 L-0251" q="In the bank analogy, what is the “bribe”, and which routing way avoids paying it?">

The bribe is the extra network hop, the latency of going through a middleman. The proxy (the peon at the door) charges it on every request. The smart client avoids it by walking straight to the right desk.

  </RecallItem>
  <RecallItem k="L-0251 L-0259" q="Why is a smart client harder to run when nodes come and go?">

The routing table lives in every client. When a node joins or leaves, or a range moves, every client must be told, and until it is, it sends requests to the wrong node. A proxy only has one table to update.

  </RecallItem>
  <RecallItem k="L-0261" q="What does a Redis Cluster node answer when you send it a key it doesn’t own?">

A redirect, `MOVED`, with the key’s hash slot and the address of the node that owns it; the client retries there. That is the redirect way: like DNS, the node tells you where to go and you connect yourself. (A standalone replica, by contrast, simply refuses a write.)

  </RecallItem>
</RecallQuestions>
