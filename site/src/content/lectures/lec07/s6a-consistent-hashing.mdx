<Section id="s6" no="6" title="Consistent hashing, DHTs and staying up" crumb="6 Consistent hashing"
  dek="Adding a node with hash % N moves half the data. Consistent hashing decides ownership so only a slice moves. Then: running it in production, its weak spots, the general idea (DHTs), and replicas."
  meta="About 30 min · class 02:07–02:30, Q&A 02:32–02:39, 02:50–02:52">

Our Redis now runs on three nodes. Each owns a slice of the keys, and a router, wherever it lives, knows who owns what. Then the blog app grows again and the three nodes can’t keep up.

The fix sounds trivial: add a fourth node. This chapter is about why it isn’t, the one idea that makes it cheap, what that idea does *not* do for you, and how the cluster stays up when a node dies.

</Section>

<Section id="s6-1" no="6.1" title="Who owns a key?" crumb="6.1 Ownership"
  dek="Hash routing spreads keys evenly, until you add a node and half of them have to move."
  meta="About 5 min · class 02:07–02:12">

Three nodes are no longer able to handle the load, so we want to add a fourth. How do you add it? [[L-0265]]

This is where consistent hashing comes in: “quote unquote, the most famous algorithm of all time”, and one with tons of misconceptions around it. This chapter sorts them out one at a time, starting from what the router does with a key. [[L-0266]]

In **hash-based routing**, the router applies a simple hash function to every key that comes in. The result tells it which node to forward the request to, and the router forwards it there. [[L-0267]] That step is how you define *ownership* of a key: the node a key is routed to is the node that owns it. Ownership of a key is the key concept of this whole chapter. [[L-0268]]

Chapter 5 used the other way. With range-based routing, ownership comes from key ranges: keys A to J are owned by cache 1, the next range by cache 2, U to Z by cache 3. With hash-based routing, the hash of the key picks the owner. [[L-0269]]

Hash-based routing is by far the most common, because a hash function spreads the load almost uniformly across the nodes. It isn’t random; it is uniform enough, and deterministic: the same key always lands on the same node. [[L-0270]] <ForwardChip label="back in" when="Lecture 2" lec="lec01" sec="s2-4" k="L-0270">sharding with hash(user_id) % N</ForwardChip> Real systems do it in more than one way. Redis Cluster, for one, doesn’t use a ring at all: it maps every key to one of 16,384 hash slots, `CRC16(key) mod 16384`, assigns slots to master nodes, and moves whole slots when it reshards <Cite href="https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/">redis.io</Cite>. [[L-0270]]

Now take six keys, K1 to K6, and two caches, cache 0 and cache 1. Pass each key through the hash function: K1, K2 and K6 land on cache 0, and K3, K4 and K5 on cache 1. Three to three, a near-equal distribution. [[L-0271]]

Then add a third cache. The function changes from `hash % 2` to `hash % 3`, and because the function changed, data has to move: you literally go through every single key in the system and work out where it goes now. It is a small, hypothetical example, but it shows how cruel this gets once you scale up and down. [[L-0272]]

The pain is not the hash; it is that changing N changes almost every owner. Consistent hashing changes only a few.

</PauseAndThink>

Look carefully at the new table. K1 was on cache 0 and stays there. K3 and K4 stay on cache 1. But K2 moves from cache 0 to cache 2, K5 from cache 1 to cache 0, and K6 from cache 0 to cache 2: three keys, each copied off one node and onto another. [[L-0273]]

The distribution is still equal, yet adding one node forced three of the six keys, 50% of the data, to move between nodes. That data movement is the pain point of plain hash-based routing. If anything, 50% is the lucky case: with `% N` → `% (N+1)`, a key stays only when both remainders agree, and on average about N/(N+1) of all keys move, two thirds when going from 2 nodes to 3 <Cite href="https://en.wikipedia.org/wiki/Consistent_hashing">Wikipedia</Cite>. [[L-0274]]

Every one of those moves is a copy over the network, and rebalancing a lot of data over the network is very slow. Consistent hashing exists to make adding a node cheaper. [[L-0290]]

<Section id="s6-2" no="6.2" title="What consistent hashing is, and isn’t" crumb="6.2 What it is"
  dek="A sorted array and a binary search that decide who owns a key. Nothing else."
  meta="About 6 min · class 02:12–02:17, 02:21">

Three myths first. Consistent hashing is not a service, and not a microservice. Nor is it a magical solution that solves all your problems. [[L-0275]]

<RuleBox rule="Consistent hashing solves for ==ownership==. Nothing else." k="L-0277 L-0278">

It helps you determine who owns what, done and dusted; that is all it does. It does not move your data, it does not migrate anything, and it gives you no uptime guarantees. Those are jobs you do yourself, and the rest of this chapter does them.

<OwnershipRule />

</RuleBox>

So keep the two apart in your head: the ring tells the router which node owns a key. Getting the key’s data onto that node, and keeping the node alive, are separate problems. Consistent hashing doesn’t do data movement or data migration for you, and it doesn’t do uptime guarantees. [[L-0278]]

It is not even really a data structure. It is a simple technique, implemented as a simple array with a binary search, and it takes hardly any space. [[L-0279]]

Everyone draws it as a ring, because that is the simplest way to picture it. The implementation looks different, and the blog post below has it. [[L-0281]]

<MarginNote title="See it yourself: a ring in Python" why="skip unless you want the code" k="L-0280">

There is a detailed blog post, with Python source code and a worked example, on implementing your own consistent hashing: on arpitbhayani.me under blogs (search for “Arpit Bhayani consistent hashing”). It is also in this course’s pre-reads. [[L-0280]]

</MarginNote>

The things that will own keys, here the cache nodes, are placed on the ring by passing each node’s identifier through the hash function; the output is the node’s position. [[L-0282]] The ring is the hash function’s output range, 0 to 2<sup>n</sup>. The example uses 2<sup>4</sup>, so 16 positions; in reality the range is as large as 2<sup>128</sup>, a gigantic value. [[L-0283]] Hash cache 1 and it lands on 3; cache 2 lands on 12, cache 3 on 5 and cache 4 on 10. Each node sits at that position on the ring. [[L-0284]]

To find a key’s owner, the router hashes the key and picks the first node to the immediate right of that position, going clockwise. That node owns the key. [[L-0288]] Key K1 hashes to 0. The first node clockwise from 0 is at 3, which is cache 1, so K1 is owned by cache 1 and its data goes there. [[L-0289]]

<Figure id="fig-6b" no="Fig 6·b" max={360} k="L-0282 L-0284 L-0288 L-0289"
  caption="The ring decides ownership. Nodes sit where their ids hash; a key belongs to the first node clockwise. The bubble is the myth the rule box answers. Redrawn from the class board at 02:16.">
  <OwnershipRing />
</Figure>

Where does the ring live? Wherever routing lives (the four places in [5.3](#s5-3)). If the client holds the routing, it is stored in the client; if a proxy routes, in the proxy; in a DNS-like routing component, there. [[L-0285]] And it is just routing information. For four nodes you store an array of four elements, and that’s it: no linked list, nothing else. [[L-0286]]

So all consistent hashing does is replace the routing table, the who-owns-what mapping that the router or a smart client uses to forward requests, with a more elegant mapping. It is still not a service. [[L-0287]]

<Figure id="fig-6c" no="Fig 6·c" k="L-0279 L-0282 L-0286 L-0288"
  caption="The ring is the picture; four numbers in a sorted array are the implementation. A key past the last position wraps around to the first, which is what makes the array a ring.">
  <Desk><RingAndArray /></Desk>
  <Phone><RingAndArray layout="phone" /></Phone>
</Figure>

In code, the lookup is a binary search for the first position at or after the key’s hash, wrapping to the start when it runs off the end:

```python
import bisect
ring = [3, 5, 10, 12]    # sorted positions
node = {3: 'cache 1', 5: 'cache 3',
        10: 'cache 4', 12: 'cache 2'}

def owner(h):            # h = hash(key)
    # first position >= h
    i = bisect.bisect_left(ring, h)
    # past the end: wrap to index 0
    return node[ring[i % len(ring)]]
```

`owner(0)` is cache 1, as on the ring, and so is `owner(13)`: past 12 the search wraps around to 3. [[L-0288]]

Why trust this narrow description over the many grander ones? It comes from use: consistent hashing run in production, which is where the confidence about what it does, and what it does not, comes from. [[L-0300]] There are tons of misconceptions floating around the internet. Stay away from them, and understand the one problem it solves and how it solves it. [[L-0301]]

</Section>

<Section id="s6-3" no="6.3" title="Adding and removing nodes" crumb="6.3 Add, remove"
  dek="A new node takes one slice from one neighbour. A removed node hands one slice to the next."
  meta="About 5 min · class 02:17–02:21">

Back to growing the cluster. Four nodes now sit on the ring, and we scale up to five. Cache 5 is passed through the hash function and lands on 1, so it sits at 1 on the ring. Key K1, at 0, used to go to cache 1. Its first node clockwise is now cache 5: the ownership has changed. [[L-0291]]

<Figure id="fig-6d" no="Fig 6·d" k="L-0291 L-0292"
  caption="Adding cache 5 at position 1. K1’s owner changes from cache 1 (faint arrow) to cache 5 (green); only the slice between 12 and 1 changes hands. Redrawn from the class board at 02:19.">
  <Desk><AddCache5 /></Desk>
  <Phone><AddCache5 layout="phone" /></Phone>
</Figure>

As soon as the ring changes, a new request for K1 goes to cache 5. Look carefully at which keys move: only those in the range cache 5 now covers, the positions after 12 up to 1, which used to go to cache 1 and now go to cache 5. Keys between 1 and 3 still go to cache 1. All other keys remain unaffected; they aren’t even touched. That is minimal data transfer. [[L-0292]]

Only the nodes right before and after the position where the new node is placed are affected; no one else is. You do the bare minimum of data transfer, at the place where the node was added. [[L-0293]]

That is the benefit of consistent hashing, the whole of it: it ensures you do only minimal data transfer when you scale up or scale down. There is no magic sauce behind it. It is very simple, and very beautiful in hindsight. [[L-0294]]

Watch the two schemes side by side on the same six keys:

  lead="Six keys, two nodes, add a third. How many keys move with % N, and how many on the ring?"
  caption="With hash % N, adding a node rechecks every key and about half move; on the ring only the new node’s slice moves, all from one neighbour. On average % N moves about N/(N+1) of keys, a ring about 1/(N+1)." />

Removing a node is the same move in reverse. Say four nodes carry decent traffic, but the cluster is over-provisioned and you want to remove one, cache 1, to save cost. There are two cases: a graceful termination and an abrupt removal. [[L-0295]]

On the ring, the answer to “who owns K1 now?” is simple. Key K1, which used to go to cache 1, now goes to the next node clockwise, cache 3. [[L-0296]]

When you terminate cache 1 gracefully, you first take a snapshot of it, copy its data to cache 3, and only then remove it from the ring. Requests that now land on cache 3 find their data and don’t cause cache misses. That is how it is done operationally. [[L-0297]]

The second case is abrupt: the server goes down, or is deleted out from under you. All the load for the range that used to go to cache 1 suddenly goes to cache 3, and you should be okay with that. [[L-0298]]

Either way, all the other keys remain unaffected, so the data transfer is minimal again. [[L-0299]]

<Section id="s6-4" no="6.4" title="Never add a blank node" crumb="6.4 No blank nodes"
  dek="The ring changes ownership instantly. The data doesn’t follow by itself."
  meta="About 3 min · class 02:21–02:23, Q&A 02:36–02:37, 02:50–02:51">

Traffic is peaking, and you add cache 5 to the ring. What does it have in it?

<PauseAndThink k="L-0278 L-0302 L-0303"
  q="Traffic is peaking, so you start a new, empty cache 5 and put it on the ring. Consistent hashing means only a slice of keys move. Is that enough?"
  choices={[{ label: 'Yes: the ring handles it' }, { label: 'No: load the data first', correct: true }]}
  right="Right. Snapshot cache 1, build cache 5 from it, then add it to the ring, then delete the moved keys from cache 1."
  wrong="The ring only changes who owns the slice. The data isn’t on cache 5, so every request in that slice misses and falls through to the database at the worst moment.">

Consistent hashing decides ownership. Moving the data is an operational step you run yourself.

</PauseAndThink>

Start a blank cache server and add it to the ring, and the keys it now owns go to it, but there is nothing there. Every one of those requests is a cache miss, and the misses become higher load on the backend systems behind the cache. [[L-0302]]

So, step by step, this is how you spin it up. Take a snapshot of cache 1, the node that owns the slice today. Create cache 5 from it. Add cache 5 to the ring, so that when a request for K1 arrives there, the data is there. Then slowly delete the moved keys from cache 1, which is no longer their first owner. [[L-0303]]

Whether to delete is a choice. If you have a replication factor set up, you may keep the data on cache 1 anyway, because the data is copied to the following nodes regardless (replicas come in [6.7](#s6-7)). Without replication, you take the snapshot, create the node, then delete the keys that are no longer needed. [[L-0352]]

For a stateful system like this cache, that is about as simple as data movement gets. One quick snapshot of one node, one load of the new node from it: efficient, and nothing fancy. Keep that simplicity in mind; the next section is about a technique that gives it up. [[L-0333]]
