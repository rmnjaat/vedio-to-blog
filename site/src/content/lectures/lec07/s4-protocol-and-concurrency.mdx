<Section id="s4" no="4" title="Talking to the cache, and taking turns" crumb="4 Protocol and concurrency"
  dek="How other systems reach the cache (all of it is TCP; the question is the format), and how one node stays correct when two clients touch the same key."
  meta="About 25 min · class 01:18–01:34, 01:38–01:50, Q&A 02:52–03:04">

The blog app’s API servers will call our cache thousands of times a second. Chapters 2 and 3 built what happens inside the box: a hash table, typed values, a byte counter, eviction and expiry. Two questions are left before the box is useful. What do the API servers speak to it? And what happens when two of them change the same key at the same instant?

The first half of this chapter answers the first question; the second half, from 4.5, answers the second. Both stay on one node. Many nodes wait for chapter 5.

</Section>

<Section id="s4-1" no="4.1" title="Which protocol? It’s all TCP" crumb="4.1 It’s all TCP"
  dek="HTTP, WebSockets, gRPC or your own format. Underneath, every one of them is a TCP connection."
  meta="About 4 min · class 01:18–01:22, recap 01:32–01:34">

Communication is about how you let some other system talk to your system: here, to your cache. So, which protocol should a single-node cache expose to the services that use it? [[L-0176]]

The first answer people give is TCP, and that answer turns out to be right underneath everything else: whatever format you pick, it rides on a TCP connection. [[L-0177]] A second answer suggested in class is HTTP, because then the server can stay stateless: it doesn’t need to remember anything about the client between requests, unlike WebSockets. [[L-0178]]

Then what is HTTP’s disadvantage? The tempting reply is that the payload is huge, because the value fetched from the cache can be large. But that is true of anything you use: the value has to be transferred whatever the protocol, so it isn’t what makes HTTP worse. The overhead is somewhere else, and 4.3 shows exactly where. [[L-0179]]

The options on the table are HTTP, WebSockets, gRPC, or writing your own protocol. Why not write your own? [[L-0180]] Before choosing, notice what they share. HTTP, gRPC and a custom protocol are all just TCP connections. There is nothing fancy about any of them; they differ only in the format the data is wrapped in: HTTP’s text, gRPC’s format, or your own. [[L-0181]]

<Figure id="fig-4a" no="Fig 4·a" max={640} k="L-0181 L-0182 L-0179"
  caption="The API talks to the cache over TCP, whichever box you tick. The speech bubble is the tempting answer; the value costs the same bytes under every protocol. The board’s “3/2” note (3-way handshake, 2-way teardown) is the class’s per-request cost of HTTP/1.1 (see “More precisely” below). Redrawn from the class board at 01:21.">
  <Desk><ProtocolChoices /></Desk>
  <Phone><ProtocolChoices layout="phone" /></Phone>
</Figure>

Where HTTP does hurt, as the class put it, is the connection. With stateless HTTP/1.1, each request establishes a TCP connection with a three-way handshake, sends the data, gets the response and terminates the connection with what the class called a two-way teardown (the board wrote 3/2 beside the connection: 3-way handshake, 2-way teardown). So every time an API server talks to the cache it re-establishes the connection: a three-way handshake and a two-way teardown every time, very unperformant, very inefficient. HTTP/1.1 might not be the best choice for a cache. [[L-0182]]

<SourceNote href="https://www.rfc-editor.org/rfc/rfc9112" site="RFC 9112 (HTTP/1.1)" k="L-0182">

HTTP/1.1 reuses TCP connections by default: “HTTP/1.1 defaults to the use of persistent connections”, so one connection carries many requests and responses. Its overhead for a cache is the text request line and headers on every call, and one outstanding request per connection, not a new handshake per request. (Closing a TCP connection takes a FIN and an ACK in each direction <Cite href="https://www.rfc-editor.org/rfc/rfc9293">RFC 9293</Cite>.)

</SourceNote>

Why TCP and not UDP? The cache needs a connection with state, guaranteed delivery and acknowledgments. UDP is fire and forget, and we don’t want that: we don’t want to lose data, because the cache is a “quote unquote database”. [[L-0205]]

</Section>

<Section id="s4-2" no="4.2" title="From practice: HTTP typed by hand" crumb="4.2 HTTP by hand"
  dek="A TCP-only sensor, a Flask server and netcat. HTTP turns out to be text the server agrees to read."
  meta="About 6 min · class 01:22–01:30, Q&A 01:49–01:50">

A case from 2015 makes the “it’s all TCP” point concrete. A small team was building an IoT application. Its backend was a Python Flask HTTP server. Its sensors had no Python or JavaScript to make HTTP requests: the backend understood HTTP, the sensors understood only TCP. So what do you do? The fix came from first principles, out of a networking course rather than experience. [[L-0183]]

The experiment: use netcat to open a raw TCP connection from the client to the Flask server, `nc localhost 3000`, and type bytes into it directly. [[L-0184]]

Every HTTP call you have made shows request headers going in and response headers coming out. That raises the question the experiment answers: how does a web server know that what it received is an HTTP request? [[L-0185]] Once a client has a TCP connection it can send any data at all, say the five bytes `A R P I T`. It is the server’s responsibility to understand what you said, and a web server understands data sent in the HTTP format. [[L-0186]]

And that format is very textual. An HTTP request is a line like `GET /hello.html HTTP/1.1\r\n` followed by header lines such as `User-Agent: …`, all plain text sent over the TCP connection. [[L-0187]]

So first, send something that isn’t HTTP. Typing `This is a sample\r\n` into the raw connection came back with error code 400, bad request syntax: the server was parsing the bytes as an HTTP request and rejecting them. [[L-0188]] Then type a request in the format the HTTP specification describes, `GET /hello HTTP/1.1\r\n`, and the Flask handler’s hello-world comes back. It is a raw TCP connection carrying data in a particular format, with no Python or request library on the client side. [[L-0190]] It worked against Flask’s lenient development server. Strictly, an HTTP/1.1 request must carry a `Host` header, and the headers end with an empty line (CRLF CRLF); a strict server answers 400 Bad Request without `Host` <Cite href="https://www.rfc-editor.org/rfc/rfc9112">RFC 9112</Cite>. [[L-0190]]

```text
This is a sample                      → 400 Bad Request

GET /hello HTTP/1.1                   → 200 OK: hello world

GET /user?name=arpit HTTP/1.1         → Requested for name = arpit

POST /login HTTP/1.1
Content-Type: application/x-www-form-urlencoded
Content-Length: …

username=…&password=welcome           → login successful
```

That solved the IoT problem. A device that can only open TCP connections can fire HTTP requests at a backend written in Python without the Python requests library, Node.js’s Axios or Java’s Spring Boot. [[L-0191]] The same goes for anything else HTTP does. A request with query parameters worked, [[L-0194]] and so did a basic POST: `POST /login HTTP/1.1` with `Content-Type` and `Content-Length` headers and a body `username=…&password=welcome`, which returned “login successful”. [[L-0192]]

The point of telling a naive, fresher’s experiment is the habit behind it: think from first principles. [[L-0189]] Can the trick be used as a general hack? Yes: it is just raw text that you send and your server understands. [[L-0240]]

<MarginNote title="See it yourself" why="skip if you’ve done it">

Run any small web server on your machine, open `nc localhost 3000` (use your server’s port), type `GET / HTTP/1.1`, a `Host: localhost` line and an empty line, and watch the raw response come back. Then type nonsense and watch the 400.

</MarginNote>

</Section>

<Section id="s4-3" no="4.3" title="Your own protocol, or gRPC" crumb="4.3 Own protocol or gRPC"
  dek="To store a = 1, all that text goes over the wire. Define a leaner envelope, or use one that keeps the connection open."
  meta="About 7 min · class 01:28–01:34, Q&A 03:03–03:04">

Now look at the same text through the cache’s eyes. To store just key `a` with value `1`, you send the request line and all the header jargon with it. That is a huge chunk of overhead along with every single message, and the more data there is in a request, the more your cache server has to process. It works, and highly optimised it can be fine. Can you do better? [[L-0193]]

<PauseAndThink k="L-0181 L-0182 L-0193 L-0195 L-0199 L-0201"
  q="To store <code>a = 1</code>, should the API servers talk to the cache over HTTP?"
  choices={[{ label: 'Yes: HTTP is standard and every client speaks it' }, { label: 'No: keep a connection open and use a lean format', correct: true }]}
  right="Right, as the lecture argues. Redis defined RESP: “SET a 1” is 27 bytes, length-prefixed and quick to parse. gRPC is the other good choice if your clients support it."
  wrong="It works, and kept-alive connections avoid a new handshake per call. But every “set a 1” carries a request line and headers, over 100 bytes of text for a few bytes of data, and the cache has to parse all of it.">

Every option is just TCP. What differs is the envelope around your bytes and whether the connection stays open.

</PauseAndThink>

You can define your own protocol. Redis did: it implemented its own protocol specification, called **RESP**. Just as HTTP is a specification that any server claiming to understand HTTP follows, all Redis clients speak RESP. [[L-0195]] RESP sends a command as an array of length-prefixed strings, so it is binary-safe and fast to parse. And Redis also accepts plain “inline” commands typed into telnet, the very trick of the netcat demo <Cite href="https://redis.io/docs/latest/develop/reference/protocol-spec/">redis.io</Cite>. [[L-0195]]

<Figure id="fig-4b" no="Fig 4·b" k="L-0193 L-0195"
  caption="Bytes on the wire for set a 1. The HTTP request is illustrative, built for this page: a request line and three headers carry a 9-byte body. RESP’s *3 says three parts follow, and each $n says how many bytes the next part has.">
  <Desk><BytesOnWire /></Desk>
  <Phone><BytesOnWire layout="phone" /></Phone>
</Figure>

Redis isn’t alone: Memcache also has its own protocol that all its clients use. [[L-0196]] Underneath a custom protocol is just raw TCP. Whatever bytes you send, the handler you wrote interprets them; you play by your own rules. [[L-0197]] That is why Redis chose its own format: it puts the format in its own hands, so data can be sent however it wants, without hiccups. [[L-0198]]

The other strong option is **gRPC**. It works on HTTP/2, so it keeps the connection alive instead of terminating it, and it compresses the objects it sends, which makes it very optimised for data transfer over the network: “best of all worlds”. [[L-0199]] In detail, gRPC frames each message with a 1-byte compressed flag and a 4-byte length, usually carrying compact binary Protobuf; compressing the message itself is optional and happens only when a `grpc-encoding` header is set <Cite href="https://github.com/grpc/grpc/blob/master/doc/PROTOCOL-HTTP2.md">grpc/grpc</Cite>. [[L-0199]]

Which to pick depends on how complex or simple your use case is and how you want clients to talk to the cache. In some cases you may open all three and make it configurable. The board’s summary: every protocol has its pros and cons, but one server can support all three ways of communication by abstracting out the implementation over one shared hash table. [[L-0200]]

<Figure id="fig-4c" no="Fig 4·c" max={560} k="L-0200"
  caption="One server, three doors, one table. Requests in any format end up in the same in-memory hash table. Redrawn from the class board at 01:33.">
  <Desk><ThreeDoors /></Desk>
  <Phone><ThreeDoors layout="phone" /></Phone>
</Figure>

Which is better is subjective. What isn’t is the connection:

<RuleBox rule="Don’t open a new connection per call: ==keep one open==, and pick the format your clients can speak." k="L-0201">

Creating HTTP connections every time might not be the best idea; keeping a connection open, with gRPC or a custom format, is fine. Use gRPC if your clients support it well; otherwise define your own format, as Redis does.

<Desk><KeepItOpen /></Desk>
<Phone><KeepItOpen layout="phone" /></Phone>

</RuleBox>

The recap at the end of this part of the class listed the choices over TCP as three: completely stateless HTTP/1.1, where you connect, query, get the response and disconnect each time; gRPC, which is stateful, runs on HTTP/2, keeps the connection open, is highly compressed and uses Protobuf; or your own custom format. [[L-0206]]

<SourceNote href="https://www.rfc-editor.org/rfc/rfc9112" site="RFC 9112 · gRPC protocol doc" k="L-0206">

Over TCP the usual choices are HTTP/1.1 (text, with keep-alive connections, not a connection per request), gRPC (HTTP/2, binary Protobuf, multiplexed) <Cite href="https://github.com/grpc/grpc/blob/master/doc/PROTOCOL-HTTP2.md">grpc/grpc</Cite>, or a custom binary or text protocol like Redis’s RESP.

</SourceNote>

If you are just starting out, or only want to prototype, use gRPC and get started without thinking too much about it. [[L-0207]]

<MarginNote title="Connection pools aren’t a language feature" why="skip unless you’ve wondered" k="L-0370 L-0371 L-0372 L-0373">

Keeping connections open is what a connection pool does, and pooling is not a property of the programming language. It is tempting to call it a property of the database; it belongs to the application logic or library you write. [[L-0370]]

A connection pool is just multiple TCP connections established with the database plus a queue to manage them; you may find a library that manages it for you. [[L-0371]] You can write your own in a day: all you need is a blocking queue. [[L-0372]]

The only requirement is that the database keeps a connection open and doesn’t terminate it unless you ask it to. [[L-0373]] Servers do close idle connections in practice: MySQL closes a non-interactive connection idle longer than `wait_timeout` (default 28,800 s, eight hours), so pools validate or refresh idle connections <Cite href="https://dev.mysql.com/doc/refman/8.4/en/server-system-variables.html">dev.mysql.com</Cite>. [[L-0373]]

<Section id="s4-4" no="4.4" title="The single node so far" crumb="4.4 The node so far"
  dek="One page of recap before the cache has to take turns."
  meta="About 2 min · class 01:32–01:34">

Here is everything on one node. Data lives in an in-memory hash table. Its values are wrapper objects, a struct holding a type and the data, and the type decides which operations a key supports: a list here, a set there. The bare minimum is `GET`, `PUT` and `DEL`, and you can always extend that to complex structures. [[L-0204]] Clients reach it over TCP, in one of the three formats from 4.3. When the cache is full it evicts by LRU, LFU or random, with random costing zero memory overhead ([§3.3](#s3-3)); and it knows it is full from zmalloc, which wraps malloc and keeps the running total ([§2.6](#s2-6)). <Section id="s4-5" no="4.5" title="Concurrency: lock, compare-and-swap, or one thread" crumb="4.5 Concurrency"
  dek="Two clients update the same key at the same instant. Three ways to stay correct, and what each costs."
  meta="About 9 min · class 01:38–01:45, Q&A 01:47–01:48, 02:52–02:54">

Before concurrency, one word on scaling. On a single node it is easy, because there is only one option: vertical scaling, adding more RAM, CPU and network to the box. [[L-0221]]

Now the classic problem. Two or more update or delete operations on the same key `k` reach the cache server at the same time: two threads trying to update the same thing. There are three ways to handle it: pessimistic locking, optimistic locking, or single-threadedness. [[L-0223]]

### Pessimistic locking

**Pessimistic locking** wraps the critical operation in a lock that a thread must take before it proceeds: `ACQ_LOCK()`, `DELETE K`, `REL_LOCK()`. When two threads come together, one of them goes in while the other waits; take `a = 10` with one thread setting it to 20 and another to 30, and one waits for the other to finish. On a single node threads coordinate with mutexes or semaphores. [[L-0224]] <ForwardChip label="back in" when="Lecture 3" lec="lec05" sec="s2" k="L-0224">the airline check-in, built with locks</ForwardChip>

<Figure id="fig-4e" no="Fig 4·e" max={620} k="L-0224"
  caption="Pessimistic locking: only one thread is inside the locked step at a time. Two writers on a = 10: one goes in, the other waits (red) until the lock is released. Redrawn from the class board at 01:39.">
  <Desk><Pessimistic /></Desk>
  <Phone><Pessimistic layout="phone" /></Phone>
</Figure>

If mutexes, semaphores and atomic variables are unfamiliar, read about them; the board adds atomic variables to keep track of locks. A Java `synchronized` block is almost exactly this: pessimistic locking. [[L-0226]]

### Optimistic locking

**Optimistic locking** starts from the opposite belief: there is very little chance of concurrent access, so don’t proactively take locks. Ensure only that if two threads do touch the same thing at the same time, just one of them succeeds. [[L-0227]]

The idea is to make updates conditional. Instead of `update a = 20` and `update a = 30`, fire `update a = 20 where a = 10` and `update a = 30 where a = 10`. If both run at once, one sets `a` to 20, and the other finds that `a` is no longer 10 and does nothing. [[L-0228]]

That only works if the check and the write happen as one step, with nothing else running in between. It is done with a standard instruction called **compare-and-swap**: `CAS(a, 10 → 20)` changes `a` to 20 only if it is currently 10. [[L-0229]]

Compare-and-swap is done at CPU level, with native instructions. Every language gives you a nice wrapper over it, such as Go’s atomic library or C++’s Boost, and if your processor (ARM, Intel, AMD) provides a CAS instruction, the compiler leverages it. [[L-0230]] It is the best way to implement an optimistic lock because the instruction is atomic: while it runs nothing else can, and the operating system does not context switch in the middle of it. [[L-0231]] An exercise worth an evening: write a simple optimistic-locking implementation yourself and play with compare-and-swap until it clicks. It is very easy. [[L-0232]]

### No threads at all

The third way questions the premise. Concurrency problems arise because several threads can be scheduled and run in parallel. What if you don’t support threads at all? Then you need no concurrency control. **This is what Redis did.** [[L-0233]] Precisely, Redis is “mostly single threaded”: commands run on one main thread, while background threads handle work such as `UNLINK`’s lazy freeing, and optional I/O threads can do socket reads, writes and parsing <Cite href="https://raw.githubusercontent.com/redis/redis/unstable/redis.conf">redis.conf</Cite>. [[L-0233]]

<ForwardChip label="go deeper" when="free Redis-internals videos" k="L-0234">how single-threaded Redis works</ForwardChip>

As told in class, the engineers who built Redis challenged every single decision. What if we take locks? What if we avoid locks by using atomic instructions? What if we need no locks at all, and go single threaded? [[L-0235]]

Doesn’t one thread make the cache slow when two servers update different keys? No. Single-threaded systems are not blocked; that is how such concurrent systems are built, and the videos above show how. [[L-0239]]

There is a real cost, though. A single-threaded cache wastes CPUs: on a machine with 32 cores, Redis uses only one, and the other 31 sit idle. [[L-0354]] To use the hardware, people run several shards of the cache on the same machine, say eight. [[L-0355]]

<Figure id="fig-4g" no="Fig 4·g" max={640} k="L-0354 L-0355"
  caption="One thread, many cores, drawn with eight. Left: a single-threaded cache keeps one core busy. Right: eight single-threaded shards on the same box use them all.">
  <Desk><OneThreadCores /></Desk>
  <Phone><OneThreadCores layout="phone" /></Phone>
</Figure>

And the single thread is what makes the rest of the single-node design work. Everything built in chapters 2 and 3, the malloc counter included, is correct because the cache is single threaded. Make it concurrent and `total_size += b` from two threads would cause massive havoc; one thread also saves the cost of context switches. [[L-0356]] So single threading simplifies a great deal without losing concurrency, and it under-uses the hardware, which you win back by putting several Redis nodes on one machine. There are trade-offs everywhere. [[L-0357]]

<Section id="s4-6" no="4.6" title="From class: the double-booked seats" crumb="4.6 Double-booked seats"
  dek="A question carried over from Lecture 3’s seat exercise: shared locks, and the same seat sold twice."
  meta="About 5 min · class 02:57–03:03">

Locks in a real database come back in one last question from class, about Lecture 3’s seat-allocation exercise. It belongs to databases rather than to our cache, so it sits in a side note.

<MarginNote title="Shared locks and the double booking" why="skip unless you did the Lecture 3 exercise" k="L-0361 L-0362 L-0363 L-0364 L-0365 L-0366 L-0367 L-0368 L-0369">

The setup: 120 seats, 120 people, and an implementation that took shared locks, which ended up handing the same seats to many people. When a transaction holding a shared lock updates the row, the lock is elevated to an exclusive lock. [[L-0361]] So that should not have happened. The first thing to check is the isolation level. [[L-0362]] To debug locking, use MySQL’s administrative console rather than a UI: it shows which row holds which lock. [[L-0363]]

The guess at the bug offered in class, reduced to two transactions on one row: both take a shared lock. T2 writes first, so its lock is elevated to exclusive. T1 still holds its shared lock; it waits until the exclusive lock is released and then writes to the same row, overwriting it. [[L-0364]]

<SourceNote href="https://dev.mysql.com/doc/refman/8.4/en/innodb-locking.html" site="MySQL 8.4 reference manual" k="L-0364">

With shared locks, two transactions that both try to update the same row deadlock: each one’s request for an exclusive lock waits on the other’s shared lock, and InnoDB rolls one of them back <Cite href="https://dev.mysql.com/doc/refman/8.4/en/innodb-deadlock-example.html">deadlock example</Cite>. Double booking usually means the availability check used a non-locking read, and the update did not re-check the condition <Cite href="https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html">consistent reads</Cite>.

</SourceNote>

The overwrite, in this explanation, happens because the waiting transaction does not re-evaluate its statement after the lock is released: “most probably what is happening behind the scene”. [[L-0365]]

<SourceNote href="https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html" site="MySQL 8.4 · PostgreSQL docs" k="L-0365">

In InnoDB, a REPEATABLE READ snapshot applies to SELECT statements, “not necessarily to DML statements”: UPDATE and DELETE act on the latest committed row versions. PostgreSQL under READ COMMITTED re-evaluates the WHERE clause after waiting <Cite href="https://www.postgresql.org/docs/current/transaction-iso.html">postgresql.org</Cite>. An overwrite happens when the UPDATE has no condition on the seat’s state (just `WHERE id = ?`) after a stale snapshot read, not because the database skips re-evaluation. Put the condition in the UPDATE itself, e.g. `WHERE seat_free = 1`.

</SourceNote>

The explanation assumed REPEATABLE READ, called in class almost the most common isolation level out there, and the explanation was flagged plainly as a guess that might be wrong. [[L-0366]] REPEATABLE READ is InnoDB’s default <Cite href="https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-isolation-levels.html">dev.mysql.com</Cite>; PostgreSQL defaults to READ COMMITTED, so it isn’t the most common across databases <Cite href="https://www.postgresql.org/docs/current/transaction-iso.html">postgresql.org</Cite>. [[L-0366]]

[[L-0367]] It could also simply be a bug. In most cases, in the class’s view, the deadlock file’s data is very hard to interpret, and that is the gap between practical understanding and production, where things go berserk and nobody knows what is happening. [[L-0368]]

One correction to a common fear: a deadlock does not crash the database or the program. It terminates a transaction. [[L-0369]]

<RecallQuestions>
  <RecallItem k="L-0182 L-0193 L-0195" q="Why does HTTP cost a cache more than RESP, even on a kept-alive connection?">

Every HTTP request carries a text request line and headers: storing `a = 1` takes over 100 bytes, and the cache has to parse all of it. RESP sends the same command as three length-prefixed strings, 27 bytes, quick to parse. (The class also charged HTTP/1.1 a new TCP handshake per request; in fact HTTP/1.1 keeps connections alive by default, so the headers are the real cost.)

  </RecallItem>
  <RecallItem k="L-0228 L-0229 L-0231" q="Two clients send <code>update a=20 where a=10</code> and <code>update a=30 where a=10</code>. What does each see, and what instruction makes that safe?">

Whichever runs first sets `a` to 20. The other finds `a` is 20, not 10, and changes nothing; it can re-read and retry or give up. Compare-and-swap makes it safe: `CAS(a, 10 → 20)` checks and writes as one atomic instruction, so nothing can slip in between the check and the write.

  </RecallItem>
  <RecallItem k="L-0354 L-0355 L-0356" q="Redis uses one core of 32. Why is that acceptable, and how do people use the rest?">

One thread needs no locks or atomics: the single-node design, down to the `zmalloc` counter, is correct without concurrency control, and there are no context switches. Single-threaded systems aren’t blocked by many clients. To use the other cores, people run several shards of the cache on the same machine.

  </RecallItem>
</RecallQuestions>
