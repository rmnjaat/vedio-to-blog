### Eleven decisions [[rail: Decisions]]

Every step of the build was a decision with a cost. Here they are in the order the page made them:

1. **Storage** ([§2.2](#s2-2)): a hash map from key to value; when a value outgrows its block, double it and move. Cost: an occasional expensive reallocation.
2. **Type metadata** ([§2.3](#s2-3)): the key stays a plain key; the value sits in a wrapper with a 4-bit type. Cost: 4 bits per key.
3. **Memory accounting** ([§2.6](#s2-6)): every allocation goes through zmalloc, which keeps `total_size`, so no system call per check. Cost: one counter and one wrapper.
4. **Eviction** ([§3.3](#s3-3), [§3.4](#s3-4)): LRU or LFU on a few bits in the wrapper, or random with nothing stored. Cost: correctness of the choice against bytes per key.
5. **Expiry** ([§3.5](#s3-5)): an absolute expiry time in the wrapper, removed by lazy deletion plus sampling, with no priority queue. Cost: a temporary leak.
6. **Protocol** ([§4.3](#s4-3)): one open TCP connection and a lean format of your own, or gRPC. Cost: bytes on the wire and parsing.
7. **Concurrency** ([§4.5](#s4-5)): one thread, no locks. Cost: one core of many.
8. **Partitioning** ([§5.1](#s5-1)): each node owns a mutually exclusive slice of the keys. Cost: someone must know who owns what.
9. **Routing** ([§5.4](#s5-4)): a proxy, a smart client, forwarding or a redirect. Cost: network hops against what the client must know.
10. **Rebalancing** ([§6.3](#s6-3)): consistent hashing, so adding a node moves only one slice. Cost: data still has to be moved, by you.
11. **Availability** ([§6.7](#s6-7)): a replica per node, or copies on the next nodes of the ring, and an append-only file for durability. Cost: extra nodes and disk.

### Eight heuristics [[rail: Heuristics]]

The same few ideas carried the whole lecture:

1. Rely on the source of truth. Capture changes from the database itself, not from events the API server remembered to send ([§1.3](#s1-3)). [[L-0031]]
2. In memory, be cautious about every single byte and bit, because RAM is costly. Reduce space to the bare minimum you can work with ([§2.3](#s2-3)). [[L-0098]]
3. Big systems are built on very simple solutions: one counter in one wrapper around malloc tells you exactly when to evict ([§2.6](#s2-6)). [[L-0130]]
4. Understand the life cycle of a key, and how your users access it, before you pick LRU or LFU ([§3.4](#s3-4)). [[L-0174]]
5. Creating a connection for every call might not be the best idea. Keep one open: gRPC if your clients support it well, your own format otherwise, as Redis does ([§4.3](#s4-3)). [[L-0201]]
6. There is no one right routing approach. Each has its pros and cons, so pick your battles ([§5.4](#s5-4)). [[L-0257]]
7. Consistent hashing solves for ownership, and nothing else: it tells you who owns what ([§6.2](#s6-2)). [[L-0277]]
8. Think operationally. Before you adopt a technique for a stateful system, count how many places you would have to copy data from, and how complicated that gets ([§6.5](#s6-5)). [[L-0353]]
