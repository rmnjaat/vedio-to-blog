<Section id="s7" no="7" title="The home page is slow. What’s in the row?" crumb="7 The row" meta="About 7 min">

The home page lists the posts published in the last seven days, each with its title and a short excerpt. This is the query the blog shipped with:

```sql
-- the home page, version 1
SELECT * FROM blogs
WHERE published_at > :week_ago
  AND NOT is_deleted
ORDER BY published_at DESC;
```

It looks harmless, and while the table was small it was. As posts pile up, it becomes the slowest page on the site.

<Figure id="fig-7-sofar" max={640} no="Fig 7·a" caption="The blog so far. Marked new: rows are soft-deleted, and a background job moves them to an archive before hard deleting them in small batches.">

<Phone><SoFarBlog stage={1} layout="phone" /></Phone>
</Figure>

The SQL is four lines and nothing in it looks expensive. So where is the time going?

</Section>

<Section id="s7-1" no="7.1" title="What is the list query paying for?" crumb="7.1 The bill">

Two things, and neither shows in the SQL.

First, `SELECT *` asks for every column, including `body`: thousands of words per post, on a page that shows a title and two lines. Every matching row drags its whole post along for nothing. [[L-0198]]

Second, the filter. In version 1, `published_at` went in as text, exactly as the editor sent it: `'02-04-2022 09:01:36'`, day first. Text in that order doesn’t sort by date. To answer `published_at > :week_ago`, the database has to parse the string into a date on every row it checks, and an ordinary index on the text can’t answer the comparison. [[L-0203 L-0204 L-0205]]

Both costs come from the same place: decisions about the row that nobody made on purpose. Take the first one first. The body is big and the bio is small, yet both are just text columns. Should the database store them the same way?

</Section>

<Section id="s7-2" no="7.2" title="Why don’t bio and body live the same way?" crumb="7.2 bio and body">

`bio` is about 140 characters. `body` can run to thousands of words. [[L-0189]] They shouldn’t be stored the same way, and the database already knows it.

A row-oriented database, which is what MySQL and PostgreSQL are, keeps a row’s columns together on disk, so one read brings back the whole row. Short columns that most reads need, such as a name, an email or a bio, belong right there: a `VARCHAR` stays inline with the rest of the row. [[L-0190 L-0192 L-0196]] A very large value is different. The engine stores it **out of line**, somewhere else on disk, and keeps only a pointer in the row. [[L-0193]]

<Figure id="fig-7b" max={620} no="Fig 7·b" k="L-0189 L-0192 L-0193" caption="Long text vs short text. A large body lives elsewhere on disk with only a reference in the row; a short bio is stored with the other columns.">
<Desk><LongShortText /></Desk>
<Phone><LongShortText layout="phone" /></Phone>
</Figure>

How and when that happens depends on the engine. MySQL’s InnoDB moves long `TEXT`, `BLOB` and `VARCHAR` values off the page behind a 20-byte pointer when the row is too big to fit <Cite href="https://dev.mysql.com/doc/refman/8.4/en/innodb-row-format.html">dev.mysql.com</Cite>. PostgreSQL compresses or moves any wide value out of line once a row passes about 2 kB, and fetches it only if a query asks for that column <Cite href="https://www.postgresql.org/docs/current/storage-toast.html">postgresql.org</Cite>. [[L-0193]]

Why not keep everything inline and save the extra read? Because rows have to stay bounded. An InnoDB row must fit in about half of a 16 KB page. Small rows also mean more of them per page, so scans touch fewer pages. And a 5,000-character body isn’t 5,000 bytes: in MySQL’s `utf8mb4` a character can take up to four bytes, so it can be 20,000. [[L-0195 L-0197]] Keep the row to what most reads need: very large text in a long-text column, everything else short. [[L-0199]]

That fixes the first cost. The list doesn’t need the body, so stop asking for it. The excerpt it does need is short text, so give it its own short column, filled when the post is saved, and select only what the page shows. The out-of-line body is read only when someone opens a post. [[L-0194 L-0198]]

The rows the list reads are now small. The second cost is still there: every row’s date is parsed from text before it can be compared. How should `published_at` sit on disk?

</Section>

<Section id="s7-3" no="7.3" title="How should published_at sit on disk?" crumb="7.3 Dates">

Not as text. There are several better ways to store a date and time; here are three. [[L-0200]]

<Figure id="fig-7c" max={740} no="Fig 7·c" k="L-0200 L-0201 L-0209 L-0216 L-0217" caption="Three ways to store the same instant, 2 April 2022 09:01:36 UTC: the database’s native type, an epoch integer, and a custom integer that keeps only the date.">
<Desk><ThreeDates /></Desk>
<Phone><ThreeDates layout="phone" /></Phone>
</Figure>

**The native type.** Every database has a date-time column, and it is the most convenient choice. Your language hands you a date object, and the value reads at a glance in any SQL console. [[L-0201 L-0208]] The major engines store it in compact binary, 5 bytes for a MySQL `DATETIME` and 8 for a PostgreSQL `timestamp`, and compare and index it efficiently <Cite href="https://dev.mysql.com/doc/refman/8.4/en/storage-requirements.html">dev.mysql.com</Cite>. Every engine has its own format, though, so find out how yours stores a date. [[L-0202 L-0206 L-0207 L-0208]]

**An epoch integer.** Make `published_at` an integer column and store the epoch, as the heartbeat store did in chapter 2. [[L-0209 L-0210 L-0054]] It is small, 4 bytes, or 8 for a 64-bit value. A comparison is a plain integer comparison, the cheapest thing a computer does. [[L-0211 L-0213]] What it costs is readability: nobody can look at `1648890096` and tell you the date. [[L-0212]]

Either one fixes the second cost. Here is the home page with both fixes:

```sql
-- the home page, version 2
SELECT id, title, excerpt FROM blogs
WHERE published_at > :week_ago   -- native date-time or epoch integer
  AND NOT is_deleted
ORDER BY published_at DESC;
```

The list now reads short rows and compares dates without parsing a string.

For a home page, either choice is fine. But picture a heavier workload, one that compares dates across huge numbers of rows all day long. There, the native type can be too slow, and epoch integers too hard for people to read. What then?

</Section>

<Section id="s7-4" no="7.4" title="What if neither format fits?" crumb="7.4 Neither fits">

One team at the bus-booking site Redbus hit exactly that, as an engineer who worked there tells it. In 2016 they had a table that stored dates as date-times. The workload was closer to analytics than to live transactions: queries comparing dates across huge numbers of rows, all day. At that volume the date comparisons themselves had become the bottleneck. Epoch integers would have sped them up, but the engineers debugged by reading values straight from their SQL tools, and epoch numbers would have made that miserable. [[L-0214 L-0215 L-0227]]

So they dropped a constraint they didn’t need. They needed the date, never the time. They stored it as an integer in `YYYYMMDD` form: `20220402` for 2 April 2022. [[L-0216 L-0217]]

<PauseAndThink k="L-0218 L-0221 L-0222"
  q="Is <code>20220402</code> faster to compare than an epoch integer like <code>1648890096</code>?"
  choices={[{ label: 'Yes: it is a custom, optimised format' }, { label: 'No: both are plain integers', correct: true }]}
  right="Right. The win was somewhere else."
  wrong="Not faster. To the database both are just integers.">

Against epoch there is no speed difference at all. What `YYYYMMDD` buys over epoch is **readability**: anyone can read `20220402` in a console. Against the date-time column Redbus had, it bought the speed they needed *and* stayed readable. The price is flexibility: the time of day is gone, which Redbus knew it would never need.

</PauseAndThink>

The move worth copying is not the format but the reasoning. There is no rule that says “always native” or “always epoch”. Look at what your queries need, and which constraints you can drop. `YYYYMMDD` integer keys are common in data warehouses for the same reason. [[L-0219 L-0220 L-0223]]

Whatever you pick, two details come with it. The first is time zones. An epoch integer has no zone, so display is easy: render it in the viewer’s local time. Native types usually normalise to UTC, or store no zone at all. Time zones burn a lot of teams, so store UTC, and keep the writer’s original zone in its own column if you need it. [[L-0224 L-0225 L-0226]] The second is range. A signed 32-bit count of seconds runs out on 19 January 2038; a 64-bit integer doubles the size and removes the limit. Dates before 1970 are simply negative. MySQL’s `DATETIME` covers the years 1000 to 9999, and PostgreSQL’s `timestamp` 4713 BC to AD 294276. Check your own database’s documentation for these. [[L-0231 L-0232 L-0233 L-0234 L-0235 L-0236]]

The home page is fast again. A week later, one of the posts on it goes viral. Now the pressure isn’t on the list. It is on the page for that one post, which starts loading thousands of times a minute.
