<Section id="s4-1" no="4.1" title="The write rate: 6 million a minute" crumb="4.1 Write rate">

Chapter 2 imagined 100,000 people online. A successful app has ten times that, so take a million.

Every 10 seconds is 6 beats a minute per user. 6 × 1,000,000 = **6 million writes a minute**, about 100,000 every second, each one an update.

</PauseAndThink>

The data for those million users is about 8 MB. The work on it never stops. Tiny data with an enormous write rate is the textbook case where **storage is not the problem; computation is**. [[L-0103 L-0104 L-0105]]

How hard that bites depends on the store. In Redis’s own benchmarks a single node handles roughly a hundred thousand simple `SET`s a second, so it is within range, with little headroom <Cite href="https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/benchmarks/">redis.io</Cite>. A disk-based relational database committing 100,000 durable single-row updates a second is a much harder ask. [[L-0104]] You might ask: didn’t chapter 3 just pick Redis or DynamoDB? It did. But plenty of teams start with the relational database they already run, and the cost this chapter is about is easiest to see there. So follow one heartbeat into the case where it hurts most: **a classic relational database such as PostgreSQL behind the API**. Everything you learn carries over to Redis, DynamoDB or any store you reach over a network.

The usual answer to a write load like this is to split the data across machines, with sharding and partitioning. That comes in <LectureLink lec="lec01">Lecture 2</LectureLink> and later. [[L-0106]] Before reaching for it, look at a cost almost everyone ignores. It hides on the one line of the diagram nobody thinks about: the line between the API server and the store. [[L-0107]] What does one write actually spend its time on?

</Section>

<Section id="s4-2" no="4.2" title="The cost of opening a connection" crumb="4.2 Connection cost">

Follow one heartbeat. It reaches the API server as an HTTP request over the client’s TCP connection. To write it, the API server opens a *second* TCP connection, to the database. [[L-0108]]

Opening that connection costs a three-way handshake: three trips before the write can even be sent. Closing it afterwards costs a teardown: two more trips in the simple count. The one request and one reply you wanted are wrapped in five trips of ceremony. The real bill is higher still, because the database’s login exchange comes on top of TCP, and TLS too if the connection is encrypted. [[L-0109 L-0110]]

And the write itself? It updates one row by its primary key. The database finds that row almost instantly and does the bare minimum. So most of each heartbeat’s time goes not into the write but into building and tearing down the connection around it. [[L-0111]]

The database pays as well. To accept a connection it reads the handshake, spends CPU and network buffers, authenticates the caller, and sets up a thread, or in PostgreSQL a whole new server process <Cite href="https://www.postgresql.org/docs/current/connect-estab.html">postgresql.org</Cite>. Each of those costs memory as well as CPU. At 100,000 writes a second, the database spends its day saying hello and goodbye. [[L-0116 L-0117]]

Almost all of that cost comes from opening and closing. What if the connection never closed?

</Section>

<Section id="s4-3" no="4.3" title="How a connection pool works" crumb="4.3 The pool">

Nothing forces a connection to close after one query. Open a few connections once, keep them open, and hand them out to requests as needed. This is a **connection pool**. With one-row updates, where setup is most of the cost, it is the obvious fix. [[L-0112]]

Say the API server opens three connections when it boots. A request arrives, takes a free connection, marks it busy, runs its query and gives it back. The connection is already open, so the write is one request and one reply. The handshake and the teardown are gone. [[L-0113 L-0114]]

  lead="Five writes, without and with a pool. Count the trips each write makes before you play it."
  caption="The same five queries: faster calls, and a database that no longer opens and closes a connection for each one." />

Two things improve at once. Each API call gets much faster. And the database’s load drops even though it runs exactly the same number of queries, because it no longer does the connection work around each one. [[L-0115 L-0117]]

The gain is largest when queries are tiny. A big report that joins a dozen tables runs long enough that connection setup is a rounding error. A one-row update by primary key is the opposite. Whenever you fire many small queries at a database, a pool is almost always worth having. If your codebase has none, measure what adding one gives you. [[L-0129 L-0130 L-0131]] This holds whatever store you chose: Redis clients pool, and so do MySQL and PostgreSQL drivers. [[L-0119]]

A pool of three serves three requests at the same time. What happens when a fourth arrives?

</Section>

<Section id="s4-4" no="4.4" title="Pool settings: min, max and idle timeout" crumb="4.4 Pool settings">

To answer that, look at what a pool is. It isn’t a new service. It is a library inside the API server’s own process. [[L-0126 L-0127]]

At boot it opens a few connections and puts them in a **blocking queue**. A caller takes a connection if one is free, or waits until someone puts one back. There are many implementations, and the idea stays this small. [[L-0128]]

```python
import queue

class Pool:
    def __init__(self, connect, size):
        self.idle = queue.Queue()   # blocking
        for _ in range(size):       # at boot: open `size`
            self.idle.put(connect())

    def get(self):                  # waits while none is free
        return self.idle.get()

    def release(self, conn):
        self.idle.put(conn)         # back in line
```

So the fourth request either waits or gets a new connection. Step through the life of one server’s pool to see both.

A pool, then, has three settings. A **minimum** it opens at boot. A **maximum** it may grow to. An **idle timeout** after which unused connections close. A server doesn’t always hold its maximum; that is only the most it will ever hold, and the real number follows the traffic. [[L-0118 L-0123 L-0125 L-0141 L-0142]] Waiting has a limit too. HikariCP, a widely used Java pool, makes a caller wait up to 30 seconds by default, then fails the request with an error. [[L-0135]]

The quickest way to feel this is to watch it. Write a hello-world API against a local PostgreSQL with a pool, send it a burst of requests, and change the minimum, maximum and idle timeout. You will see connections open, wait and close. [[L-0318]]

<MarginNote title="Go deeper: a minimum below the maximum?" why="a real-world tuning disagreement" k="L-0157">

A common convention is a small minimum, 3 or 5, because the pool can always open more on demand. HikariCP recommends the opposite: leave the minimum unset so the pool is fixed-size, minimum equal to maximum, since opening connections during a burst is exactly the latency a pool exists to avoid. Either way, its idle timeout (10 minutes by default) only retires connections when the minimum is below the maximum.

</MarginNote>

One question is left from the stepper. If more connections mean fewer waits, why cap the pool at all? Because the database at the other end has a limit of its own, and you don’t run one API server.

</Section>
