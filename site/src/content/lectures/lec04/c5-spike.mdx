<Section id="s5-1" no="5.1" title="How many connections can a database give?" crumb="5.1 The limit">

Stay with the relational database from chapter 4, where this limit bites hardest. Every database caps the connections it will hold. The defaults are lower than people expect: PostgreSQL’s `max_connections` is typically 100, with a few reserved for administrators <Cite href="https://www.postgresql.org/docs/current/runtime-config-connection.html">postgresql.org</Cite>. Managed services publish their limit, often as a formula; Amazon RDS derives it from the instance’s memory, because every connection costs memory. Run the database yourself and you benchmark the number on your own hardware, under your own load. [[L-0124 L-0146 L-0147 L-0148]]

For a store like this one, that number is often the first wall you hit. Each read and write touches one row by key, so the queries themselves are cheap and the bottleneck moves to the connections and the network carrying them. When you size the database, the concurrency you need decides how big it must be, not the 8 GB of data. [[L-0136 L-0137 L-0143 L-0144]]

A different workload hits a different wall. A report joining 10 or 15 tables runs long enough that connection setup doesn’t matter; it is limited by the database’s CPU and memory. There are only four things that can run out on a machine, CPU, memory, disk and network, and every scaling decision is about one of them. The heartbeat store is network-bound; a big report is CPU- and memory-bound; a data warehouse is disk-bound. [[L-0145 L-0151 L-0152 L-0153 L-0154 L-0155]]

</Section>

<Section id="s5-2" no="5.2" title="Ten servers, one budget, and a spike" crumb="5.2 The budget">

Now put pools and the limit together.

10 servers × 100 connections = 1,000, the database’s whole budget. The 20 new servers start, try to open their pools, and are refused. Their requests wait, time out and fail, at exactly the moment you added them to absorb a spike.

</PauseAndThink>

A misconfigured pool quietly caps how many servers you can ever run: the most you can have is the database’s limit divided by each server’s share. That is the other half of the earlier advice. A pool is almost always worth having; a pool configured without looking at the database is a trap. [[L-0320]]

It fails the other way too. A pool allowed to grow without a cap lets a few busy servers take every connection. And with a long idle timeout, a server that was busy ten minutes ago keeps hogging connections it no longer uses, while the load balancer sends new users to a server that can’t get any, and those users see an outage. [[L-0321]]

</Section>

<Section id="s5-3" no="5.3" title="How do you size a pool you can’t predict?" crumb="5.3 Sizing">

Start from the budget. Divide the database’s maximum connections by the most servers you will ever run: 1,000 connections and up to 100 servers gives each server a maximum of **10**. [[L-0158]] Many teams set it a little higher, say 15, because one server is sometimes busier than the rest; it is a common practice, not a standard. Know what it costs: if every server can reach 15, a busy moment can ask the database for 1,500 connections, and it refuses the extra ones with an error. [[L-0159]]

Then start conservative and let measurements move you. A small minimum, a maximum inside the budget, an idle timeout that is neither so short that connections keep reopening nor so long that idle ones pile up. Put telemetry on the pool, and a week of production traffic tells you where to move each number. [[L-0160 L-0161 L-0322 L-0323]]

The number to watch first is the average time a query takes, because the connections you need are roughly your throughput multiplied by that time. Watch alongside it how long requests wait for a connection and how often the pool is saturated. If query time rises, find out why before you grow the pool: past a point, more connections make a database slower, not faster <Cite href="https://github.com/brettwooldridge/HikariCP/wiki/About-Pool-Sizing">HikariCP wiki</Cite>. [[L-0324 L-0325]]

If the fleet truly needs more concurrent connections than one database can hold, the first answer is a bigger database. Past what one machine can give, you split the data across several (sharding, in <LectureLink lec="lec01">Lecture 2</LectureLink>), which is why a design that has to grow should be able to scale out, not only up. [[L-0136 L-0138 L-0156]] When the fleet is large or unpredictable, there is also a structural fix: put a central pooler such as PgBouncer or Amazon RDS Proxy between the servers and the database. It multiplexes many servers onto a few database connections and queues the excess. That pooler *is* a separate service, and it exists for precisely this problem. [[L-0126 L-0127]]

<MarginNote title="Go deeper: a festival doubles your traffic" why="planning for a known spike" k="L-0162 L-0163 L-0164 L-0165">

If you know a spike is coming, scale the database up before it, then back down after; the database must support the concurrency you are aiming for, however wasteful that feels for one weekend. On many managed databases a size change means a restart, so do it ahead of time. Then raise the pools’ maximums to match. A far better answer to flash crowds comes later in the course, with flash sales. Until then: know your costs, and have the monitoring to decide.

</MarginNote>

</Section>

<Section id="s5-4" no="5.4" title="Where else have you seen this dot?" crumb="5.4 Same pattern">

Step back from the green dot and look at what you built: things that are alive say so every few seconds, silence for long enough means dead, and something cheap forgets the silent ones. That pattern is everywhere.

In a distributed system, every node sends heartbeats to a central tracker, and a node whose beats stop is marked down. Building your own cloud out of machines, that is how you learn a machine has died. Building your own load balancer, the same signal tells you to stop sending requests to a backend that has gone quiet. Protocols differ; the design is the same. [[L-0132 L-0133]]

<Figure id="fig-5c" no="Fig 5·c" k="L-0132 L-0133" caption="The dot’s pattern, reused. Left: nodes beat to a tracker, and a node that goes quiet is marked down. Right: backends beat to a load balancer, which stops routing to one that goes quiet. Real load balancers usually ask instead, with health checks.">

<Phone><HeartbeatsReused layout="phone" /></Phone>

Real load balancers usually run the check in the other direction, because unlike a server talking to a laptop, they *can* open connections to their backends: an AWS Application Load Balancer asks each target every 30 seconds by default and takes it out after two failures <Cite href="https://docs.aws.amazon.com/elasticloadbalancing/latest/application/target-group-health-checks.html">AWS docs</Cite>. You will build one in <LectureLink lec="lec08">Lecture 5</LectureLink>. [[L-0133]] That is the reason to learn designs this way: remember the pattern and the property it needs, not a question and its answer. [[L-0134]]
