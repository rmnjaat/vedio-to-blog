<Section id="s5-1" no="5.1" title="Database connection limits" crumb="5.1 Connection limits">

Every database caps the connections it will hold, and the cap is lower than most people expect. Stay with the relational database from chapter 4, where this limit bites hardest. PostgreSQL’s `max_connections` is typically 100, with a few reserved for administrators <Cite href="https://www.postgresql.org/docs/current/runtime-config-connection.html">postgresql.org</Cite>. Managed services publish their limit, often as a formula. Amazon RDS derives it from the instance’s memory, because every connection costs memory. Run the database yourself and you benchmark the number on your own hardware, under your own load. [[L-0124 L-0146 L-0147 L-0148]]

For a store like the dot’s, this number is often the first wall you hit. Each read and write touches one row by key, so the queries are cheap, and the bottleneck moves to the connections and the network that carries them. So when you size this database, the number of concurrent connections you need decides how big it must be, not the 8 GB of data. [[L-0136 L-0137 L-0143 L-0144]]

Other workloads hit other walls. Only four things can run out on a machine: CPU, memory, disk and network. Every scaling decision is about one of them. The heartbeat store runs out of network. A report joining 10 or 15 tables runs out of CPU and memory, and its connection setup doesn’t matter. A data warehouse runs out of disk. [[L-0145 L-0151 L-0152 L-0153 L-0154 L-0155]]

Say your database allows 1,000 connections. That sounds like plenty. Whether it is depends on how the fleet of API servers shares them, and the fleet doesn’t stay the same size.

</Section>

<Section id="s5-2" no="5.2" title="What breaks in a traffic spike" crumb="5.2 Traffic spike">

10 servers × 100 connections = 1,000, the database’s whole budget. The 20 new servers start, try to open their pools, and are refused. Their requests wait, time out and fail, at exactly the moment you added them to absorb a spike.

</PauseAndThink>

A misconfigured pool quietly caps how many servers you can ever run. The most you can have is the database’s limit divided by each server’s share. So chapter 4’s advice needs its other half: a pool is almost always worth having, and a pool configured without looking at the database is a trap. [[L-0320]]

It fails the other way too. A pool with no cap lets a few busy servers take every connection. And with a long idle timeout, a server that was busy ten minutes ago keeps connections it no longer uses. Meanwhile the load balancer sends new users to a server that can’t get any, and those users see an outage. [[L-0321]]

So you can’t pick a pool size by looking at one server. How do you size it?

</Section>

<Section id="s5-3" no="5.3" title="How to size a pool" crumb="5.3 Sizing">

Start from the budget. Divide the database’s maximum connections by the most servers you will ever run. 1,000 connections and up to 100 servers gives each server a maximum of **10**. [[L-0158]]

Many teams set it a little higher, say 15, because one server is sometimes busier than the rest. That is a common practice, not a standard, and it has a cost. If every server can reach 15, a busy moment can ask the database for 1,500 connections, and it refuses the extra ones with an error. [[L-0159]]

Then start conservative and let measurements move you. A small minimum. A maximum inside the budget. An idle timeout neither so short that connections keep reopening nor so long that idle ones pile up. Put telemetry on the pool, and a week of production traffic tells you where to move each number. [[L-0160 L-0161 L-0322 L-0323]]

Which numbers? First the average time a query takes, because the connections you need are roughly your throughput multiplied by that time. Alongside it, how long requests wait for a connection, and how often the pool is full. If query time rises, find out why before you grow the pool. Past a point, more connections make a database slower, not faster <Cite href="https://github.com/brettwooldridge/HikariCP/wiki/About-Pool-Sizing">HikariCP wiki</Cite>. [[L-0324 L-0325]]

What if the fleet truly needs more connections than one database can hold? The first answer is a bigger database. Past what one machine can give, you split the data across several, with sharding in <LectureLink lec="lec01">Lecture 2</LectureLink>. That is why a design that has to grow should be able to scale out, not only up. [[L-0136 L-0138 L-0156]] When the fleet is large or unpredictable, there is also a structural fix. Put a central pooler such as PgBouncer or Amazon RDS Proxy between the servers and the database. It multiplexes many servers onto a few database connections and queues the excess. That pooler *is* a separate service, and this problem is the reason it exists. [[L-0126 L-0127]]

<MarginNote title="Go deeper: a festival doubles your traffic" why="planning for a known spike" k="L-0162 L-0163 L-0164 L-0165">

If you know a spike is coming, scale the database up before it, then back down after; the database must support the concurrency you are aiming for, however wasteful that feels for one weekend. On many managed databases a size change means a restart, so do it ahead of time. Then raise the pools’ maximums to match. A far better answer to flash crowds comes later in the course, with flash sales. Until then: know your costs, and have the monitoring to decide.

</MarginNote>

With the pools sized, the dot is finished. Before leaving it, look at the shape of what you built, because you will meet it again.

</Section>

<Section id="s5-4" no="5.4" title="The heartbeat pattern elsewhere" crumb="5.4 Same pattern">

Strip the dot down to its idea. Things that are alive say so every few seconds. Silence for long enough means dead. Something cheap forgets the silent ones. That pattern is everywhere.

In a distributed system, every node sends heartbeats to a central tracker, and a node whose beats stop is marked down. If you build your own cloud out of machines, that is how you learn a machine has died. If you build your own load balancer, the same signal tells you to stop sending requests to a backend that has gone quiet. The protocols differ; the design is the same. [[L-0132 L-0133]]

<Figure id="fig-5c" no="Fig 5·c" k="L-0132 L-0133" caption="The dot’s pattern, reused. Left: nodes beat to a tracker, and a node that goes quiet is marked down. Right: backends beat to a load balancer, which stops routing to one that goes quiet. Real load balancers usually ask instead, with health checks.">
<Desk><HeartbeatsReused /></Desk>
<Phone><HeartbeatsReused layout="phone" /></Phone>
</Figure>

Real load balancers usually run the check the other way round. Unlike a server talking to a laptop, they *can* open connections to their backends. An AWS Application Load Balancer asks each target every 30 seconds by default and takes it out after two failures <Cite href="https://docs.aws.amazon.com/elasticloadbalancing/latest/application/target-group-health-checks.html">AWS docs</Cite>. You will build one in <LectureLink lec="lec08">Lecture 5</LectureLink>. [[L-0133]] This is why it pays to remember a design as a pattern and the property it needs, not as a question and its answer. [[L-0134]]

Look at what the dot never had to answer. Its data was one integer per user, thrown away after 30 seconds. Lose all of it and the next round of beats rebuilds it. So it never asked what a delete should mean, what belongs inside a row, or when to keep a copy of data. Most data isn’t that cheap. The second build is data that people care about.
