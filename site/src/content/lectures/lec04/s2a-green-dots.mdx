The product team’s brief is one line. Show a list of users, each with a green dot if they are online and a grey dot if they are offline, the way Facebook and Twitter do. This chapter builds that indicator, one question at a time, and each question forces exactly one part of the design. [[L-0021]]

</Section>

<Section id="s2-1" no="2.1" title="The brief, and the core" crumb="2.1 The core"
  dek="Start where 1.1 said to start: pick the core, and ask what it must hold to draw one dot."
  meta="About 3 min · class 00:13–00:24">

On the board the list is four rows: user 1 and user 4 are green, user 5 and user 3 are grey. It is day one of the course, so scale stays out of focus on purpose. [[L-0021]]

<Figure id="fig-2a" max={320} no="Fig 2·a" k="L-0021" caption="What the user sees: four rows in the board’s order, two online, two offline. Day one: no focus on scale yet. Redrawn from the class board at 00:15 and 00:22.">
<WhatUserSees />
</Figure>

This is the spiral approach from [§1.1](#s1-1) in practice. Pick the database as the core of the system, since it is the easiest place to start, and ask: to render one user with a green or a grey indicator, what do I need to store? [[L-0033]]

The first answer is the obvious one. For every user, store the user ID as an integer (a fair assumption) and whether they are online as a boolean: true for online, false for offline. [[L-0034]]

Now look at how this data will be used. You get the status of a set of users, get the status of one user, and update the status of one user. That is a classic **key-value** access pattern. It names the access pattern, not a database: the board says plainly that we still have not picked which database to use. [[L-0035]]

<Figure id="fig-2b" max={360} no="Fig 2·b" k="L-0034 L-0035" caption="Storage first, database later: user (int) → online/offline (bool), read and written by key. The access pattern is decided; the database is not. Redrawn from the class board at 00:22.">
<StorageFirst />
</Figure>

The schemas on these pages are drawn as tables only to help you see them. A table does not mean a relational database; model it however you want. Likewise, SQL here is just an easy way to explain an idea, not a claim that only SQL is used. [[L-0050]]

</Section>

<Section id="s2-2" no="2.2" title="Reading many dots at once" crumb="2.2 Batch reads"
  dek="A friends list shows many users at once. The endpoint should be shaped for that screen, not for one user."
  meta="About 3 min · class 00:23–00:26">

A friends list on screen renders four users. Who reads their status from the database? An API server, so the API server needs an endpoint. The first idea is the plain one: given one user ID, return that user’s status. [[L-0036]]

With only that endpoint, rendering four users takes four API calls from the front end. That is a very poor experience, and so many API calls also burden the backend. [[L-0037]]

So the first critical design decision is to expose a **batch endpoint**. It accepts a bunch of user IDs and returns the status of every one of them. The front end makes one network call for the same information, and the backend does the heavy lifting. [[L-0038]]

<Figure id="fig-2c" max={660} no="Fig 2·c" k="L-0036 L-0037 L-0038 L-0039" caption="Four calls or one. Left: a single-user endpoint costs one call per dot. Right: one batch call carries every user on screen, and one reply carries every status. Redrawn from the class board at 00:24; the right panel’s reply is added.">
<Desk><FourCallsOrOne /></Desk>
<Phone><FourCallsOrOne layout="phone" /></Phone>
</Figure>

The board’s interfacing diagram is the user (with a device) ⟷ API server ⟷ database, both arrows double-headed. [[L-0039]]

The board writes the endpoint as `GET /status/users?ids=u1,u2,u3,u4`: for all the IDs provided, return each one’s online or offline status. That settles the reading side. Knowing *why* an endpoint is exposed in a certain way, instead of just drawing a box labelled “API”, is the kind of detail this course cares about. [[L-0039]]

</Section>

<Section id="s2-3" no="2.3" title="Who says a user is alive?" crumb="2.3 Push, not pull"
  dek="The server can’t reach out to a browser, so each client has to keep saying it is alive."
  meta="About 3 min · class 00:26–00:28, Q&A 03:03–03:05">

Reading is solved. Now something has to keep each user’s status up to date. There are two ways to get that information: the server can **pull** it, or each client can **push** it. [[L-0040]]

Pull would mean the API server calling each client and asking “are you alive? are you alive?”. That is not possible: HTTP is stateless and there is no persistent connection, so the API server cannot talk to the client. The client has to talk to the server. The board adds an exception: *unless there is a persistent connection*. [[L-0041]]

That exception has a name. WebSocket gives a client and a server two-way communication over one connection; before it, getting updates from a server meant polling it over HTTP <Cite href="https://www.rfc-editor.org/rfc/rfc6455.html">RFC 6455</Cite>. This design stays with plain HTTP calls from the client. [[L-0041]]

<Figure id="fig-2d" max={440} no="Fig 2·d" k="L-0040 L-0041 L-0042" caption="Users push; the server can’t pull. Each client sends its own heartbeats in blue. The dashed pull back to the clients is crossed out: over plain HTTP the server cannot start the conversation. Redrawn from the class board at 00:26.">
<Desk><UsersPush /></Desk>
<Phone><UsersPush layout="phone" /></Phone>
</Figure>

So the client pushes. Every client periodically makes a **heartbeat** API call to the backend that says “I am alive”. [[L-0042]] The name comes from the human heart: as long as it keeps beating, you are alive, and when it stops, you are dead. [[L-0043]]

The endpoint is `POST /heartbeat`. Each call marks whichever user is authenticated on that request as alive. [[L-0044]]

<MarginNote title="Is HTTP really stateless?" why="skip if the pull step made sense" k="L-0330 L-0331 L-0332 L-0333 L-0335 L-0336">

HTTP is designed to be stateless: you send one request, you get one response, deal done. You can still keep the underlying connection open, with the keep-alive header. Keep-alive is a connection-level header, and HTTP/2 and HTTP/3 forbid it, so it matters only for HTTP/1.x <Cite href="https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Keep-Alive">MDN</Cite>. [[L-0330]]

HTTP/2 keeps its connections persistent. WebSocket is not HTTP, but it also keeps a persistent connection, and no rule says a connection must always be closed. A WebSocket does start life as HTTP: its opening handshake is an HTTP Upgrade request <Cite href="https://www.rfc-editor.org/rfc/rfc6455#section-1.7">RFC 6455 §1.7</Cite>. [[L-0331]]

In the simple picture, the client sends a request, the server responds and closes the connection; with the keep-alive header the server doesn’t close it, and if neither side closes it, it stays open. [[L-0332]]

<SourceNote href="https://www.rfc-editor.org/rfc/rfc9112#section-9.3" site="RFC 9112 §9.3" k="L-0332">

HTTP/1.0 closed the connection after each response unless Keep-Alive was negotiated. HTTP/1.1 keeps connections open by default until one side closes them or a timeout hits, and HTTP/2 connections are always persistent; the Keep-Alive header is forbidden there <Cite href="https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Overview">MDN</Cite>.

</SourceNote>

Even so, think of HTTP as stateless: it keeps your design simple. When you genuinely need state, there are better tools, such as WebSockets or MQTT. [[L-0333]] <ForwardChip when="Lecture 9, week 5" k="L-0334">a system that keeps HTTP/2 connections stateful on purpose</ForwardChip>

Can HTTP run without TCP? HTTP runs on top of TCP. HTTP/1.1 and HTTP/2 do; HTTP/3 runs over QUIC, which is carried in UDP datagrams <Cite href="https://www.rfc-editor.org/rfc/rfc9114">RFC 9114</Cite>. [[L-0335]]

There is no fixed tie between them. HTTP is a specification for messages and TCP is a layer-4 protocol, so in principle you can send HTTP messages over UDP too. What HTTP does need underneath is a reliable, ordered transport, and over UDP that is what QUIC provides <Cite href="https://www.rfc-editor.org/rfc/rfc9000">RFC 9000</Cite>. [[L-0336]]

</MarginNote>

</Section>

<Section id="s2-4" no="2.4" title="Why the beat must repeat" crumb="2.4 Periodic beats"
  dek="A client can announce that it is online. It can’t reliably announce that it is gone."
  meta="About 4 min · class 00:27–00:31">

Why send heartbeats over and over? A common idea is that two calls are enough: one when the user comes online or logs in, and one “I’m offline” call at logout. [[L-0045]]

<PauseAndThink k="L-0045 L-0046 L-0047 L-0048"
  q="Your app sends “I’m online” when a user logs in and “I’m offline” when they log out. A user’s laptop battery dies mid-session. What do their friends see, and is the two-call design enough?"
  choices={[{ label: 'Grey: the app goes offline when the laptop does' }, { label: 'Green, until something else notices', correct: true }]}
  right="Right. The server only hears what the client sends, and a dead client sends nothing."
  wrong="Not quite. Nothing on a dead laptop can send “offline”, so nothing tells the server.">

A client can announce coming online but can’t reliably announce going offline: a crash, a dead battery or a pulled plug sends nothing. So the client sends a heartbeat every few seconds, and the server treats silence for “long enough” (30 s here) as offline. How long is long enough is a product decision.

</PauseAndThink>

The two-call design fails on a very common case. A user’s app says “I’m online”, then the machine crashes, the battery runs out or someone pulls the plug. The user is offline, but the UI keeps showing them online because the offline call never came. You can tell the server when you come online; you can’t promise a call just before the device dies, because you are not in control of that moment. This fundamental limitation is why heartbeats must be **periodic**. [[L-0046]]

From there the design converges naturally: as long as heartbeats keep arriving, the user is online, and if the backend doesn’t receive one for long enough, it marks the user offline. [[L-0047]]

<Figure id="fig-2f" max={360} no="Fig 2·f" k="L-0044 L-0047 L-0048" caption="A periodic pulse into POST /heartbeat. Offline means no heartbeat for long enough, and “long enough” is subjective: here 30 s, with a beat every 10 s. Redrawn from the class board at 00:29–00:30.">
<PeriodicPulse />
</Figure>

“Long enough” is subjective, as the board says, so it is business logic you configure per system. For one system it might be 10 minutes without a heartbeat; for others 10 seconds or a minute. This design marks a user offline after **30 seconds** of silence, with clients sending a heartbeat **every 10 seconds**. [[L-0048]]
