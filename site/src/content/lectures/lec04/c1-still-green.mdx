<Section id="s1" no="1" title="Why is the dot still green?" crumb="1 Still green" meta="About 6 min">

A product team hands you a one-line brief. Show a list of users, with a green dot next to everyone who is online and a grey one next to everyone who isn’t, the way Facebook and Twitter do. [[L-0021]] There is no scale target and no deadline. Just the dot.

Where do you start? Not with boxes and arrows. Start with the one thing the feature can’t exist without. For the dot, that is the data. Then add each other part only when a question forces it in. Growing a design outward from its core like this is called the spiral approach. [[L-0022 L-0023]]

The core isn’t always the data. In a chat app it can be the communication layer, the open connections everything else hangs off. [[L-0024]] And there is another way to build: ship the simplest whole system that works, watch which part breaks first under real load, fix that part, and repeat. That incremental loop suits a product whose shape you don’t know yet, like a startup’s first app. Most projects mix the two. [[L-0025 L-0027 L-0028]]

This is the design almost everyone writes first. By the end of the chapter it will be broken.

<Figure id="fig-1-sofar" max={640} no="Fig 1·a" caption="The design you would write first: the app says “online” at login and “offline” at logout, and the server keeps one true/false per user. This chapter breaks it.">
<Desk><SoFarDot stage={0} /></Desk>
<Phone><SoFarDot stage={0} layout="phone" /></Phone>
</Figure>

So start where the spiral says to: with the data. What does one dot need?

</Section>

<Section id="s1-1" no="1.1" title="What does one dot need?" crumb="1.1 One dot">

Two things: the user’s ID, an integer, and whether that user is online, a boolean. [[L-0033 L-0034]]

Now ask how that data gets used. The screen reads the status of many users at once, sometimes of just one. The app updates the status of one user. Every access goes through the user’s ID. This shape is called a **key-value access pattern**. [[L-0035]]

Notice what that sentence doesn’t name: a database. You know how the data is read and written before you know where it lives. Keep that order. The store gets picked later, once you know what you need from it. [[L-0029]]

Something has to serve those reads, so an API server sits between the screen and the data. The first endpoint anyone writes takes one user ID and returns one status. [[L-0036]] But the screen is a friends list. Four friends on screen means four calls: a slower screen for the user, and four times the requests for your backend. [[L-0037]]

<Figure id="fig-1b" max={660} no="Fig 1·b" k="L-0036 L-0037 L-0038 L-0039" caption="Four calls or one. A single-user endpoint costs one call per dot; a batch endpoint carries every user on screen in one call and every status in one reply.">
<Desk><FourCallsOrOne /></Desk>
<Phone><FourCallsOrOne layout="phone" /></Phone>
</Figure>

So shape the endpoint for the screen that calls it. A **batch read**, `GET /status/users?ids=u1,u2,u3,u4`, returns every status in one reply. The front end makes one call, and the backend does the work. [[L-0038 L-0039]]

Reading is settled. Writing is the harder half. Someone has to set that boolean to true when a user arrives and to false when they leave. Who tells the server?

</Section>

<Section id="s1-2" no="1.2" title="Who tells the server?" crumb="1.2 Who tells?">

The obvious answer is the app itself. When the user logs in, the app calls the server: “I’m online.” When they log out: “I’m offline.” Two calls per session, and the boolean is always right. That is the design in Fig 1·a. [[L-0045]]

Always right, as long as every session ends with a logout.

The “offline” call never leaves the machine. The server still holds `online = true`, and every friend keeps seeing green, for hours, for someone who is gone.

</PauseAndThink>

A crash, a dead battery and a pulled plug all look the same from the server: nothing arrives. A client can announce that it has arrived. It can’t promise to announce that it is leaving, because it doesn’t control the moment it dies. [[L-0046]]

So the client can’t be trusted to say goodbye. Could the server find out on its own?

</Section>

<Section id="s1-3" no="1.3" title="Can the server check instead?" crumb="1.3 Server checks?">

The idea: every few seconds, the server asks each client, “Are you still there?” This is a **pull** model. The opposite, where each client keeps reporting on its own, is **push**. [[L-0040]]

Pull fails over plain HTTP, and the reason is direction. In HTTP the client starts every conversation and the server only answers. On top of that, your user’s laptop sits behind a home or office router that accepts no incoming calls. The server has no way to reach it. [[L-0041]]

You might ask: doesn’t HTTP keep connections open? It can. Keep-alive and HTTP/2 reuse one TCP connection for many requests. But on that connection the client still asks and the server still answers. Reuse saves the cost of reconnecting. It doesn’t let the server speak first. A WebSocket does: it is a connection both sides keep open for messages in either direction. [[L-0330 L-0331 L-0332]]

<Figure id="fig-1d" max={440} no="Fig 1·c" k="L-0040 L-0041 L-0042" caption="Clients push; the server can’t pull. Each client sends its own beats (blue). The pull back to the clients is crossed out: over plain HTTP the server cannot start the conversation.">
<Desk><UsersPush /></Desk>
<Phone><UsersPush layout="phone" /></Phone>
</Figure>

With plain HTTP, then, the client has to push. Every client calls `POST /heartbeat`, again and again. Each call marks the user logged in on that request as alive. [[L-0042 L-0044]] The name fits: while a heart keeps beating, its owner is alive. [[L-0043]]

<MarginNote title="Go deeper: how real chat apps hold the line open" why="skip unless you build presence" k="L-0101 L-0102">

Production presence systems keep a persistent connection open instead of sending REST heartbeats. WebSocket is one way; Facebook built Messenger’s on MQTT because it uses little bandwidth and battery. The server still learns that a device died from silence: these connections carry their own small keep-alive pings, and when the pings stop, the server closes the connection and marks the user offline. <LectureLink lec="lec01">Lecture 2</LectureLink> covers WebSockets, and <LectureLink lec="lec02">Lecture 4</LectureLink> builds Slack’s real-time messaging on those persistent connections.

</MarginNote>

But one beat proves very little. It says “I was alive a moment ago.” How often must the beats come, and how much silence means someone has gone?

</Section>

<Section id="s1-4" no="1.4" title="How much silence means gone?" crumb="1.4 How much silence">

A single beat at login would be no better than the login call. The beats have to keep coming, because silence is now the only way the server learns that someone left. Beats arriving: online. No beat for long enough: offline. [[L-0046 L-0047]]

“Long enough” has no technical answer. It is a product decision. One product can live with ten minutes; another wants ten seconds. Here, clients beat **every 10 seconds**, and a user counts as offline after **30 seconds** of silence. The gap lets one or two late or lost beats pass without turning a live user grey. [[L-0048]]

Here is the same dead battery, played twice: first with login and logout calls, then with beats.

The beats fix the lie, on one condition. To say “30 seconds have passed”, the store must know *when* the last beat arrived. Right now it holds a boolean, and `true` has no time in it.

</Section>
