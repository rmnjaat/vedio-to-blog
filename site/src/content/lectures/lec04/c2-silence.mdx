<Section id="s2" no="2" title="Who deletes the silence?" crumb="2 Silence" meta="About 7 min">

The 30-second rule needs the time of the last beat, and the store only holds a boolean. So the row has to change. Once it does, a second question follows from it, the one this chapter is named for: when a user goes quiet, who removes what they left behind?

Start with the row. What should it remember?

</Section>

<Section id="s2-1" no="2.1" title="What should a row remember?" crumb="2.1 The row">

When the last beat arrived. Instead of `online = true`, the table becomes `pulse(user_id, last_heartbeat)`. Every `POST /heartbeat` overwrites that user’s row with the current time. [[L-0049 L-0051]]

<Figure id="fig-2b" max={560} no="Fig 2·b" k="L-0049 L-0051 L-0052 L-0053 L-0054" caption="The pulse table and the two rules. Every beat rewrites one row’s last heartbeat; reading a status applies two rules.">
<Desk><PulseTable /></Desk>
<Phone><PulseTable layout="phone" /></Phone>
</Figure>

A user’s first beat finds no row to update. So write it as an upsert: insert the row, or update it if it already exists, in one atomic statement. [[L-0051]]

```sql
-- every POST /heartbeat (PostgreSQL)
INSERT INTO pulse (user_id, last_heartbeat)
VALUES (:uid, :now)
ON CONFLICT (user_id) DO UPDATE
SET last_heartbeat = EXCLUDED.last_heartbeat;
```

Reading a status now takes two rules, applied to every ID in a batch call. No row: the user never came online, so offline. A last heartbeat more than 30 seconds old: offline. Anything else: online. [[L-0052 L-0053]]

The time is stored as **epoch seconds**, the number of seconds since 1 January 1970. It is a plain integer. [[L-0054]] That integer comes back in chapter 7, when the blog has to store dates.

Now watch the table over time. Every user who ever sends a beat gets a row, and nothing ever removes it. A billion users means a billion rows, kept forever. Is that a problem?

</Section>

<Section id="s2-2" no="2.2" title="A row for every user, forever?" crumb="2.2 Forever?">

Don’t guess. Count.

<PauseAndThink k="L-0055 L-0056 L-0057"
  q="One row per user: a 4-byte user ID and a 4-byte timestamp. There are a billion users. Do you need special storage for this table?"
  choices={[{ label: 'Yes: a billion rows needs a big cluster' }, { label: 'No: it fits on one cheap machine', correct: true }]}
  right="Right. Do the multiplication before you buy anything."
  wrong="Not this time. Multiply it out before you reach for a cluster.">

Two 4-byte integers is 8 bytes a row, and 8 bytes × 1 billion rows = **8 GB**. Your phone holds 128 GB. A cheap server holds 8 GB in RAM.

</PauseAndThink>

A billion users is about an eighth of the world’s population, and the whole table still fits on a cheap machine. [[L-0055 L-0056]] The 8 GB is raw payload, so the real number is higher. A database adds bookkeeping to every row: PostgreSQL spends a 23-byte header plus a 4-byte pointer on each one <Cite href="https://www.postgresql.org/docs/current/storage-page-layout.html">postgresql.org</Cite>. A production schema would also use an 8-byte timestamp. Call it a few times 8 GB. The conclusion holds: **storage is not this system’s problem**. [[L-0057 L-0058]]

So the table doesn’t need shrinking. Ask anyway: could it be smaller? It is a cheap question to ask at every step, and worth writing down what you considered. [[L-0059 L-0060]] Here it finds something.

Look at who those billion rows belong to. At any moment, most of them are people who are offline. Their rows only say “last seen long ago”. Why keep them at all?

</Section>

<Section id="s2-3" no="2.3" title="Why keep rows for people who left?" crumb="2.3 Rows who left">

You don’t have to. The screen shows only green or grey, and an old timestamp and a missing row both mean grey. So let a missing row mean offline. A row then exists only while its user is online. [[L-0061 L-0062]]

The table now holds exactly the people online right now. If 100,000 of the billion are active, that is 100,000 rows: about **800 KB**. [[L-0065]]

<Figure id="fig-2c" max={600} no="Fig 2·c" k="L-0055 L-0056 L-0057 L-0065" caption="How big is it? Every user with a row: 8 GB for a billion, less than the phone in your pocket. Only online users with a row: 800 KB for 100,000 of them.">
<Desk><HowBig /></Desk>
<Phone><HowBig layout="phone" /></Phone>
</Figure>

The new rule has a price. It only holds if rows disappear on time: 30 seconds after a user’s last beat, their row must be gone. Nothing in the design deletes anything yet. So who does?

The answer most people give first is a **cron job**: a small process that wakes every few seconds, finds rows whose last heartbeat is older than 30 seconds, and deletes them. Reads get simpler too: row present, online; row absent, offline. On a product’s first day, it would work. [[L-0063 L-0064]]

<PauseAndThink k="L-0063 L-0064 L-0066 L-0067"
  q="A teammate proposes exactly that cron job. It is twenty lines of code. Would you ship it?"
  choices={[{ label: 'Yes: it is simple and it works' }, { label: 'Not before asking what it costs to run', correct: true }]}
  right="Right. The code is the cheap part."
  wrong="The code is cheap. Running it is not.">

A cron job is a separate process. Someone has to host it and keep it running, because if it stops, offline users turn green again. Its uptime now matters as much as the API’s. It needs its own monitoring and alerts, and it has edge cases: a run that overlaps the next one, a run that dies halfway. That is a lot of ownership for one `DELETE`.

</PauseAndThink>

Every box on a diagram is something you build, deploy and get paged for. More boxes don’t make a better design, and often they make a worse one. [[L-0066 L-0067]] So before adding the cron job, ask whether something you already run could do the deleting. One thing you run already holds every one of these rows: the store. Can it forget on its own?

</Section>

<Section id="s2-4" no="2.4" title="Can the store forget on its own?" crumb="2.4 Forget on its own">

Some stores can. You write a key with a **time to live (TTL)**, and the database deletes the key when the time runs out. With a store like that, writing your own deleter is reinventing the wheel. [[L-0068]]

<Figure id="fig-2d" max={660} no="Fig 2·d" k="L-0062 L-0063 L-0066 L-0068 L-0070" caption="Who deletes? Left: a cron job is a new process to host, keep up and monitor. Right: a store with a TTL deletes the key itself, and nothing new runs.">
<Desk><WhoDeletes /></Desk>
<Phone><WhoDeletes layout="phone" /></Phone>
</Figure>

The whole design now fits in a few lines. On every heartbeat, set the user’s key with a 30-second TTL. Each beat pushes the expiry 30 seconds further out. When the beats stop, the key expires. Key present: online. Key absent: offline. The store does the deleting. [[L-0070]]

That turns the requirement for the store into one line: **key-value access plus expiry**. Two common stores offer both: Redis and DynamoDB. [[L-0069]]

Each one hides a trap in how it expires. In Redis, a plain `SET` clears any expiry the key had, so every write must carry the TTL again. DynamoDB deletes expired items in the background, “typically within a few days”, and keeps returning them to reads until then <Cite href="https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/TTL.html">AWS docs</Cite>. So with DynamoDB you store an `expires_at` time and treat a passed one as offline. [[L-0070]]

```text
# Redis, on every POST /heartbeat (EX 30 on every write)
SET presence:42 1 EX 30
# status: key present = online
EXISTS presence:42

# DynamoDB: write expires_at = now + 30
# status: online only if expires_at > now
```

<MarginNote title="Go deeper: what if the product wants “last seen”?" why="a requirement that changes the design" k="L-0305">

This brief has only green and grey. If the product also wants “last seen 5 minutes ago”, the way WhatsApp shows it, you can’t delete rows any more: you keep one per user, and the last heartbeat *is* the last-seen time. That is fine, because storage was never the problem; 8 GB is small. Deleting rows here was a way to practise asking “can this be smaller?”, not a necessity.

</MarginNote>

So the store needs a key, a value and a timer. Redis has all three. So does DynamoDB. You can only put one in the box. Which one?

</Section>
