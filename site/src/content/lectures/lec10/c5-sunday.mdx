<Section id="s5-1" no="5.1" title="Who applies the changelog?" crumb="5.1 The job">

Not the API servers; they are busy serving. Spin up a separate server for a scheduled batch job, a cron job, that runs when the changelog arrives. It holds the changelog, downloads the current dictionary from S3, builds the updated file and uploads it. It has to build a whole file: an S3 object can’t be patched, only replaced whole. [[L-0120 L-0121 L-0122]]

</Figure>

The quickest idea is to append the changelog to the end of the dictionary; it isn’t sorted anyway. But then apple is in the file twice, the file grows every week forever, and the brief said no repeated entries. [[L-0124]] Comparing a hash of every entry against the new one, or generating a diff, is extra work for nothing: the changelog already says exactly what changed. [[L-0126]] It is easy to build complex systems and hard to build simple ones; think only about what you really need. [[L-0127]]

What you really need seems simple: the index already knows where apple is, so go there and write the new line over the old one. [[L-0125 L-0128]]

</Section>

In an editor you press Enter and the lines below move down, because the text lives in memory. A file on disk gives you no such operation. It is easy to say “I would replace it”; picture the code you would actually write, `seek(0); write(...)`, and the break is obvious. [[L-0130 L-0131 L-0132 L-0133]]

<Section id="s5-3" no="5.3" title="A new file, then. Can you build it in one pass?" crumb="5.3 The merge">

So write a new file: go through the dictionary, write each entry to the new file, put each change where it belongs, and carry on to the end. That sounds naive. It isn’t. It is the merge step of merge sort, the best approach for this design, and it works in one pass when both files are sorted. [[L-0136 L-0137 L-0139]]

That is the question from chapter 1, answered. Sorting didn’t matter for lookups, because the index goes straight to an offset. It matters for the update. Keep the dictionary sorted, sort the changelog too (it is small, so sort it in memory), and the job is a textbook merge of two sorted lists into a third. [[L-0140 L-0141 L-0142]]

Keep one pointer in each file. Compare the two words: write the smaller one to the new file and move that pointer. When the words match, write the changelog’s meaning and move both. [[L-0143]]

```python
d, c = dictionary.readline(), changelog.readline()
while d and c:
    if d.word < c.word:      # the smaller word goes out
        new.write(d); d = dictionary.readline()
    elif d.word > c.word:    # a word the dictionary didn't have
        new.write(c); c = changelog.readline()
    else:                    # same word: the changelog's meaning wins
        new.write(c); d = dictionary.readline(); c = changelog.readline()
while d:                     # changelog used up: the rest follows
    new.write(d); d = dictionary.readline()
while c:
    new.write(c); c = changelog.readline()
```

Nothing is loaded into memory: the job reads both files line by line and writes a third, each file once. [[L-0145]] And the output comes out sorted, ready as next week’s input: sort the dictionary once, and from then on the merge keeps it sorted for free. [[L-0309 L-0310 L-0311]]

The rule underneath is worth keeping on its own: **never overwrite a record in place when its size can change.** A write that runs past its slot destroys what follows, so a change goes into a new file. [[L-0146]]

It has a cost you can compute. The merged dictionary is about a terabyte too, and both sit on the job server at once, so that one server needs at least 2 TB of disk. One server, once a week: fine. [[L-0147]] The new file is complete, with a fresh index and a fresh header, since the index size changes with every update. [[L-0148]]

The new dictionary is ready on the job server. Every API server, meanwhile, is still serving last week’s file, with last week’s offsets in its memory.

</Section>
