### Heuristics to keep [[rail: Heuristics]]

The same rules of thumb came back again and again, whichever engine was on the board:

1. Keep it simple: that is where you see the power and the beauty of a system, and simple systems are the hard ones to build ([2.1](#s2-1), [5.1](#s5-1)). [[L-0040 L-0127]]
2. Reads slow? Think indexing ([2.1](#s2-1)). [[L-0046]]
3. Do the number crunch: what looks huge, a terabyte file of 170,000 words, needed an index of only a few megabytes ([2.3](#s2-3)). [[L-0060]]
4. Build a file format from compartments plus a header that says where each one lies ([3.3](#s3-3)). [[L-0083]]
5. Think about cost first: the bare minimum things, at the bare minimum cost ([4.1](#s4-1)). [[L-0100]]
6. Pin down the properties you need before you pick a technology ([4.2](#s4-2)). [[L-0106]]
7. Never write in place; write a new file or a new entry ([5.3](#s5-3)). [[L-0146]]
8. We control our own infrastructure: a routine deployment can do the reload ([6.4](#s6-4)). [[L-0198]]
9. Append, no matter what ([7.2](#s7-2)). [[L-0213]]
10. Keep the sawtooth under the disk cap ([8.4](#s8-4)). [[L-0245]]
11. Know exactly how many bytes to read, and check the CRC before you trust them ([9.1](#s9-1), [9.2](#s9-2)). [[L-0254 L-0267]]
12. High throughput with persistence means an append-only file somewhere: look for it ([10.2](#s10-2)). [[L-0280]]
