<Section id="s10" no="10" title="It’s called Bitcask" crumb="10 Bitcask"
  dek="One map of keys in memory, append-only files on disk, merges in the background, a CRC on every record: that is Bitcask. What it can’t do, where it runs, and how it differs from the LSM trees coming next week."
  meta="About 13 min · class 02:32–02:41, Q&A 02:43–02:46, 02:51">

The design is complete: a map in memory, small append-only files with one active, merge and compaction in the background, and a CRC on every record. Before it gets its name, two questions. What is its one hard limit, and what does it give in return?

</Section>

<Section id="s10-1" no="10.1" title="What we built: one map, many files" crumb="10.1 What we built"
  dek="Every key in memory, pointing at its latest record in any file; writes only to the active one."
  meta="About 4 min · class 02:32–02:37">

Put everything together. Every operation is a key-value record in the format of chapter 9, appended one after another. One file would grow too big, so files rotate: whenever a file reaches its threshold, writing moves to a new one, and only one file is active at any point in time; the rest are just available for reads.

That changes what the in-memory hash table holds. It used to store a key and an offset. Now, for each key, it stores the file the key is in, the size of the record, the offset, and a timestamp for conflicts and meta information. Entries can point into any file, but writes always go to the active file. [[L-0268]]

<Figure id="fig-10a" no="Fig 10·a" k="L-0268 L-0269"
  caption="Each map entry names the file, the entry size, the offset and the timestamp of the key’s latest record. K1 points into a read-only file, K2 into the active one. A get is one lookup, one seek and one read. Redrawn from the three prepared slides shown in class at 02:33, merged into one view.">
  <Desk><OneMapManyFiles /></Desk>
  <Phone><OneMapManyFiles layout="phone" /></Phone>
</Figure>

This sounds very fancy: O(1) put, O(1) delete, O(1) get. So what is the limitation? **All the keys must fit in memory.** Values are flushed to disk, but the in-memory structure holds every key with its offset. On disk there are keys and values; in memory, keys and offsets. So the number of keys you can fit in memory decides how many keys this database can store. [[L-0269]]

The strengths come from doing the bare minimum disk I/O. You get very high write throughput and very low write latency. A read is one memory lookup and one random read, then the data goes back and the disk returns to writing. [[L-0270]]

That also means **I/O saturation**: the physical device’s I/O is saturated, and the network’s too, and that is a good thing. Nothing sits waiting for I/O; you are getting the most out of the underlying hardware. [[L-0271]]

And backups are easy. The data is just normal files, so copy them, and you have a backup. [[L-0272]]

</Section>

<Section id="s10-2" no="10.2" title="Bitcask, Riak and Uber" crumb="10.2 Bitcask and Riak"
  dek="An embedded database, made distributed by Riak."
  meta="About 4 min · class 02:37–02:40">

The database we just designed is called **Bitcask**. It is an **embedded database**. [[L-0273]]

Embedded means it isn’t a central server. Bitcask is not like a MySQL server that is spun up and that everyone connects to; it is closer to a library inside your program. SQLite is an embedded database too, and Bitcask has no separate server. [[L-0274]] SQLite is the classic example of this serverless style: the application process reads and writes the database file directly, with no separate server process <Cite href="https://www.sqlite.org/serverless.html">sqlite.org</Cite>.

As taught, Bitcask is used by Uber in production, for its main ride-hailing service. [[L-0275]] Because Bitcask is embedded, Uber doesn’t run it on its own: Uber uses **Riak** as its main database, and Riak is a simple key-value store that uses Bitcask as its back end. [[L-0276]] The note below narrows the first half of that: Bitcask did run at Uber through Riak, but in dispatch services, not under the core trip data.

<SourceNote href="https://riak.com/posts/technical/ubers-ringpop-and-riak/" site="riak.com" k="L-0275 L-0276">

Around 2015 Uber used Riak, whose default storage backend is Bitcask <Cite href="https://docs.riak.com/riak/kv/latest/setup/planning/backend/index.html">docs.riak.com</Cite>, for parts of its new dispatch services. Its core trip data lived in Postgres and then moved to Schemaless, a MySQL-based store <Cite href="https://www.uber.com/blog/schemaless-part-one-mysql-datastore/">uber.com</Cite>. So Bitcask ran at Uber through Riak, but not as the store of the main ride-hailing data.

</SourceNote>

The relationship has a familiar shape. Elasticsearch is an HTTP wrapper over Lucene; in the same way, Riak is a wrapper over Bitcask. [[L-0277]]

Riak’s job is to make Bitcask distributed. The data is split into mutually exclusive sets, and Riak adds what a single embedded store doesn’t have. The list as given in class: master-slave architecture, consensus, a proxy to connect seamlessly and route requests, consistent hashing, data movement. The note below corrects the first item: Riak has no master, and any node can route a request. Underneath, Bitcask does what it is good at, getting the most out of the disk when storing and retrieving data. [[L-0278]]

<ForwardChip block label="back in" when="Lecture 9" lec="lec07" sec="s6-2" k="L-0278">consistent hashing</ForwardChip>

<SourceNote href="https://docs.riak.com/riak/kv/latest/learn/concepts/clusters/index.html" site="docs.riak.com" k="L-0278">

Riak is masterless. Keys are hashed onto a ring split into partitions owned by vnodes; each write goes to the owning vnode and the next N−1, and any node can coordinate a request <Cite href="https://docs.riak.com/riak/kv/latest/learn/why-riak-kv/index.html">docs.riak.com</Cite>. Partitions are disjoint key ranges, but each key is stored on N vnodes, and each partition runs its own Bitcask instance underneath <Cite href="https://docs.riak.com/riak/kv/latest/setup/planning/backend/bitcask/index.html">docs.riak.com</Cite>.

</SourceNote>

Look back at the design and one piece carries it: the append-only file is the magic behind getting the most out of cheap commodity hardware. [[L-0279]]

That gives a heuristic worth keeping. Whenever a system claims high throughput with persistence, it is using an append-only file or something similar. If it isn’t, doubt the high-throughput claim. [[L-0280]] Treat it as a strong heuristic, not a law: many high-throughput persistent systems do use append-only logs, but throughput also comes from batching, group commit, relaxed sync (Cassandra, for one, can acknowledge writes before its periodic commit-log sync) and in-memory designs <Cite href="https://cassandra.apache.org/doc/latest/cassandra/architecture/storage-engine.html">cassandra.apache.org</Cite>.

<RuleBox rule="Whenever a system claims ==high throughput with persistence==, look for an append-only file." k="L-0280">

If it isn’t there, ask how the system gets its throughput.

<Desk><ThroughputRule /></Desk>
<Phone><ThroughputRule layout="phone" /></Phone>

</RuleBox>

That is what Bitcask is about. It is really simple, yet it covers the intricate details: data integrity checks, the record format, merge and compaction, and getting the most out of cheap commodity hardware. It is heavily used in production through Riak, and most Riak setups have Bitcask as their back end. [[L-0281]]

<Section id="s10-3" no="10.3" title="Bitcask vs LSM, and build it yourself" crumb="10.3 Bitcask vs LSM"
  dek="How Bitcask differs from memtables and SSTables, why it comes first, and a week-long project."
  meta="About 5 min · class 02:40–02:41, Q&A 02:43–02:46, 02:51">

Right after the reveal comes an obvious question: when people talk about LSM trees, SSTables and memtables, is that this same process, or is there something extra? The big difference, as taught: in an SSTable design you also keep values in memory, while Bitcask does not. SSTables are also sorted, and that sorting leverages something else, which is covered in depth next week. [[L-0288]]

<SourceNote href="https://cassandra.apache.org/doc/latest/cassandra/architecture/storage-engine.html" site="cassandra.apache.org" k="L-0288">

In an LSM engine only the memtable (recent writes) is in memory; SSTables are sorted, immutable files on disk, written when a memtable is flushed. Every write first goes to an on-disk commit log. Bitcask, by contrast, keeps every key (not values) in memory <Cite href="https://docs.riak.com/riak/kv/latest/setup/planning/backend/bitcask/index.html">docs.riak.com</Cite>.

</SourceNote>

The second difference is persistence. Bitcask writes every write to disk immediately, by default: it prioritises persistence while still getting the most out of the disk. A memtable buffers writes and writes them later, so if memory goes down, data can be lost. [[L-0289]]

<SourceNote href="https://docs.riak.com/riak/kv/latest/setup/planning/backend/bitcask/index.html" site="docs.riak.com" k="L-0289">

Bitcask appends every write straight to its data file, while an LSM engine appends it to a write-ahead log and buffers it in a memtable, which the log can fully recover <Cite href="https://github.com/facebook/rocksdb/wiki/Write-Ahead-Log-%28WAL%29">RocksDB wiki</Cite>. In both, crash durability depends on how often the log is synced: Bitcask’s default (`sync_strategy` none) leaves flushing to the OS, and `o_sync` forces a sync on every write at a throughput cost; Cassandra’s default periodic sync can lose up to 10 s <Cite href="https://cassandra.apache.org/doc/latest/cassandra/architecture/storage-engine.html">cassandra.apache.org</Cite>.

</SourceNote>

Bitcask was taught first on purpose, as the foundation. Next week moves on to SSTables, memtables, LSM trees, and high-throughput systems such as counting. [[L-0290]]

<ForwardChip block when="week 6" k="L-0290">SSTables, memtables, LSM trees, counting at high throughput</ForwardChip>

A learner in the class pointed out that Martin Kleppmann’s book also covers Bitcask in its storage chapter, and found that understanding Bitcask first made the other storage engines easy to follow. [[L-0291]] It is simple and beautiful, which is how it struck the instructor in a college storage paper-reading course. [[L-0292]] There is a Bitcask paper, a search away, and it is worth reading. [[L-0282]]

Reading isn’t the main recommendation, though: implement it, then benchmark it against on-disk and in-memory key-value stores, on magnetic disks and on SSDs. That benchmark is where the claim about getting the most out of the hardware and saturating I/O comes from: the instructor built one about five years ago and ran that benchmark. [[L-0284]]

<MarginNote title="Project: build your own Bitcask" why="skip unless you’ll build it this week" k="L-0283 L-0285">

Build put, get and delete over an append-only file; the in-memory map; file rotation; a merge process; the CRC record format from chapter 9. It isn’t really difficult, and building it gives a much deeper understanding of file I/O and of getting maximum performance out of a disk. It also surfaces the devils in the details: do you merge files in the same process or a different one? How do you update the in-memory index while a merge runs? Spare about one week for it. [[L-0283]]

To benchmark it, set up Prometheus on a machine, monitoring the store continuously while it runs. The suggestion in class was two weeks, then one week of your time: implement it, and measure. [[L-0285]]

</MarginNote>

<RecallQuestions>
  <RecallItem k="L-0269" q="What bounds how many keys a Bitcask node can hold, and why not values?">

Memory. The map keeps every key in RAM, with its file id, size, offset and timestamp, so the keys that fit in memory are the keys you can store. Values never live in the map: they are on disk, and the map only points at them.

  </RecallItem>
  <RecallItem k="L-0278" q="What does Riak add on top of Bitcask, per the note in 10.2?">

Distribution. Riak hashes keys onto a ring of partitions owned by vnodes, stores each key on N of them, and lets any node coordinate a request; there is no master. Each partition runs its own Bitcask underneath to read and write the disk.

  </RecallItem>
  <RecallItem k="L-0288 L-0289" q="Give two differences between Bitcask and an LSM engine, as corrected in the notes.">

Memory: Bitcask keeps every key in RAM; an LSM engine keeps only the memtable, its recent writes, and its SSTables are sorted, immutable files on disk. Write path: Bitcask appends straight to its data file; an LSM engine appends to a commit log first, then buffers in the memtable. In both, how often the log is synced decides what a crash can lose.

  </RecallItem>
</RecallQuestions>
