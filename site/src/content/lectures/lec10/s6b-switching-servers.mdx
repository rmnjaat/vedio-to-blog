<Section id="s6-4" no="6.4" title="A reload is a boot: trigger a deployment" crumb="6.4 Deploy"
  dek="Servers already read meta.json when they start. So don’t teach them to reload: start new ones."
  meta="About 9 min · class 01:37–01:44, Q&A 01:47–01:52 and 03:00–03:01">

Here is the hint that cracks it: what happens when an API server boots?

`meta.json` is a static file that holds the path of the dictionary to serve. When an API server boots, it reads `meta.json`, sees the path, reads the dictionary at that path, builds its index and starts serving. [[L-0177]]

So once the path in `meta.json` has been updated, what you need is a reload of the API servers, and a reload is literally what happens on boot. Reloading the servers is equivalent to doing a deployment: a freshly started server reads `meta.json`, goes to the path, reads the file and its index, builds the hash map and starts serving requests. [[L-0178]]

You don’t need anything else. The update job includes the AWS SDK and triggers a deployment through your deployment pipeline. With rolling deployment configured, the pipeline takes down one server and spins up another; the new machine reads the metadata file on boot, gets the new path, reads that file and serves it. [[L-0183]] Rolling deployment comes out of the box from cloud providers: the load balancer stays as it is, and servers are removed and added one at a time. [[L-0183]] On AWS, for example, an EC2 Auto Scaling instance refresh does this; with a minimum healthy percentage of 100 percent it launches the new instances before terminating the old ones, so capacity never drops <Cite href="https://docs.aws.amazon.com/autoscaling/ec2/userguide/instance-refresh-overview.html">aws.amazon.com</Cite>. [[L-0183]]

During the roll there is inconsistency. For a while some requests reach servers whose index was built on the old data, and others reach new servers on the new data. But no garbage is served, because the new data is in another file at another path: every server’s index matches the file it reads. You are serving eventually consistent data, and that is fine, because meanings don’t change drastically. [[L-0184]]

Any deployment strategy is fine. Trigger the deployment with whatever you already use, the cloud provider’s or a Jenkins job, and it takes effect seamlessly. One deployment invocation replaces the API endpoints, the reactive Pub/Sub and all the rest: throw them out of the window. [[L-0185]]

Is there something better than a whole redeployment, a new VM for every server, when only the startup routine (read the meta file, build the index, serve) needs to run again? Three ways come to mind. One: give the API servers endpoints that trigger a reload, which is the reactive approach again. That works, but ways like it make things a little more complicated. [[L-0197]]

Or ask why the API servers should read the index from S3 at all. Send the index data itself in the update you push to them: it is only 1.7 MB, by the estimate in [2.3](#s2-3), so nothing needs reloading. [[L-0199]] There are many ways to change this design. The deployment is the one picked here because it makes a point.

The point: thinking of a deployment as the way to reload your API servers is an out-of-the-box approach that a lot of engineers just don’t think about. The cost stays the same, and you avoid polling the metadata file and building reactive Pub/Sub. We control our own infrastructure, and we can use it to get things done. [[L-0198]]

<MarginNote title="Reload by deploying" why="skip if the rule above already convinced you" k="L-0308">

From the instructor’s own practice: for a couple of services, the first thought was to add Redis Pub/Sub and expose APIs to reload the data; in the end, a triggered deployment did the job. As engineers we are so used to writing code to solve a problem that we forget the infrastructure is ours: no new code, and no extra component to maintain. [[L-0308]]

</MarginNote>

The prepared notes for this design cover the same flow in more detail: the changelog, the merge, the trouble with uploading to the same path, the transition, reactive Pub/Sub, the parallel setup (what was just built), and portability by adding a header. [[L-0186]]

Their `Updating the dictionary` page lays the update job out as a procedure, in this order: spin up a new server; download the dictionary locally; download the changelog; merge in O(n), creating a new dictionary and index locally; upload the new dictionary and the new index to S3. How is the merge O(n)? The dictionary is sorted and the index is sorted, so the merge is the merging of two sorted lists ([5.3](#s5-3)). [[L-0196 L-0310]]

<Section id="s6-5" no="6.5" title="Why this matters: cold data you can still query" crumb="6.5 Why it matters"
  dek="Two hours on a word dictionary bought one capability: pointed reads on cheap storage. That is the base of multi-tiered storage and data lakes."
  meta="About 4 min · class 01:44–01:48, Q&A 02:58–03:00">

Why spend so long on a word dictionary? Look at what was built: the ability to fire seamless, pointed GET requests on S3 (GET, not PUT) that read only the bare minimum amount of data needed. A simple key-value format to start with, more complex later, but already a way to get one key from S3 without reading the entire file. That has huge applications. [[L-0188]]

Take Amazon orders. How likely are you to open an order you placed six months ago? Highly unlikely. So push orders older than six months to S3. That doesn’t mean users never look at them: they can still go back and check what they ordered. A recent order is served from the hot database, say MySQL; an old one is read from S3. [[L-0189]]

But you can’t just dump everything on S3 in a JSON file. You need the ability to make pointed queries on S3, order ID in, order details out, and that is exactly what this design gives you. [[L-0190]]

This simple system, a word dictionary on S3, lays the foundation for **multi-tiered storage**, because the data you move to S3 doesn’t lose the ability to be queried. It is a classic cold-storage mechanism: move data from the hot tier to the cold tier to save cost, and instead of just archiving it, keep a seamless way to query it on S3. [[L-0191]]

<ForwardChip block when="week 6" k="L-0191">tiered, cost-efficient storage for Amazon orders</ForwardChip>

In most places, dumping on S3 means archival. Here S3 is cheap storage. Keeping very infrequently accessed data on S3 trades time for money: the hot database answers fast, S3 relatively very slowly, but the hot database gets smaller, and that is a significant saving. [[L-0192]] The latency is acceptable because the reads are infrequent. S3 isn’t free to call (S3 requests and network I/O cost money, and S3 takes its own sweet time), but its storage is very cheap. [[L-0192]]

The same ability runs through data engineering. Data lakes store huge amounts of data on very cheap storage while keeping the ability to query it. [[L-0193]] In the lecture’s words, Apache Hudi does exactly this behind the scenes, its table format being this kind of stored index, and Hive partitions are exactly this too: the foundation for querying huge data on cheap storage. [[L-0194]] Strictly, they are the same family of idea rather than the same mechanism. A Hudi index maps each record key to the *file* that holds it (not to a byte offset), with Bloom-filter and record-level indexes that let lookups avoid scanning every data file <Cite href="https://hudi.apache.org/docs/indexes">hudi.apache.org</Cite>; Hive partitions are a directory layout by column value. [[L-0194]]

That is the word dictionary on S3, from deciding to development to deployment and a seamless transition. The thread through all of it: keep things really simple rather than over-complicated. [[L-0195]]

<RecallQuestions>
  <RecallItem k="L-0157 L-0158 L-0184" q="Apple was at offset 100 in last week’s file. Why can a same-path upload return bytes from another word, and why can’t a new-path upload?">

At the same path, the server’s index still says “offset 100, 1,024 bytes”, but the file there is now the new one, where apple sits somewhere else; the read returns whatever is at byte 100, possibly from mid-word. With a new path, an old server keeps reading the old file its index was built from, and a new server builds its index from the new file. Every index always matches the file it reads.

  </RecallItem>
  <RecallItem k="L-0196" q="List the four steps of the weekly update, in order.">

Merge the dictionary and the changelog into a new file; upload it to a new S3 path; update `meta.json` with that path; and only then trigger the deployment of the API servers, which read `meta.json` as they boot.

  </RecallItem>
  <RecallItem k="L-0183 L-0184" q="The rolling deployment leaves some servers on the old file for a while. Why is that acceptable here?">

Because no one gets garbage: each server reads the file its index was built from, so an answer is either last week’s meaning or this week’s. The data is eventually consistent, and a word’s meaning doesn’t change drastically from one week to the next, so a few minutes of mixed answers do no harm.

  </RecallItem>
</RecallQuestions>
