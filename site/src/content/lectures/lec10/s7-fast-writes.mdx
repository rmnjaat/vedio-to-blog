<Section id="s7" no="7" title="Fast writes on a cheap disk" crumb="7 Fast writes"
  dek="The second engine must take writes as fast as a magnetic disk allows, and lose nothing. Append every put to the end of one file, make delete a put, and keep one map in memory for reads."
  meta="About 22 min · class 01:52, 01:59–02:14, Q&A 02:46–02:49">

The dictionary changed once a week, and every read could afford a trip to S3. The second engine is the opposite. Writes arrive all the time, each one must be safe on disk the moment it is acknowledged, and the disks are the cheapest kind there is.

The tools are the same ones: a file, byte offsets, and a small map in memory. What changes is the order in which they are used.

</Section>

<Section id="s7-1" no="7.1" title="The problem, and how a magnetic disk works" crumb="7.1 The disk"
  dek="Cheap disks hold the world’s data, and on them, moving the head is what costs time."
  meta="About 4 min · class 01:52, 01:59–02:03">

Design a super fast key-value store on very commodity hardware: cheap magnetic hard disks. It must support put, get, update and delete, with full persistence. That is asking for the best of everything. It is also a database most people use without knowing it, with O(1) reads, writes and deletes plus persistence, and building it means going deeper into the file format than the plain lines of the dictionary, to get the maximum out of the disk. The approach is very similar to the word dictionary. [[L-0200]]

Start with the hardware. In the storage hierarchy, from CPU caches through memory, SSDs and magnetic disks down to tape, SSDs sit closer to memory than magnetic hard disks do, both in speed and in cost. [[L-0201]] We are all used to SSDs, but they are very costly compared with magnetic disk storage, so huge amounts of data are stored on magnetic disks, not on SSDs. [[L-0202]]

A magnetic disk is the classic disk-based storage: a head moves across while the disk spins underneath it. [[L-0203]] When you read a byte offset in a file, that offset is translated into a physical place: this disk, this sector, this offset inside the sector. [[L-0204]]

<Figure id="fig-7a" no="Fig 7·a" k="L-0201 L-0202 L-0203 L-0204 L-0206"
  caption="A magnetic disk: the platter spins and the head moves to the sector that holds the bytes. Beside it (below it on a phone), where SSDs sit between memory and hard disks. Redrawn from the class board at 02:03."
  >
  <Desk><MagneticDisk /></Desk>
  <Phone><MagneticDisk layout="phone" /></Phone>
</Figure>

To serve a read, the disk rotates and the magnetic head physically moves to that location. It reads that part and sends it to the device driver, and from there it goes up to user space. Every new read somewhere else needs another movement. [[L-0205]] That mechanical movement, moving the head and rotating the disk, is the most time-consuming part of disk I/O. [[L-0206]] So the question for every operation is: how little can it make the disk move?

</Section>

<Section id="s7-2" no="7.2" title="Put: append, never seek" crumb="7.2 Put"
  dek="Every put goes to the end of one file, where the head already is."
  meta="About 6 min · class 02:02–02:08, Q&A 02:46–02:49">

How would a put look? The store has to support only put, get and delete. But it must not miss out on persistence: when a put arrives, it is flushed to disk immediately. [[L-0207]]

It is tempting to reach for a structure like a memtable or an SSTable, where writes go into a sorted map held in memory first. That doesn’t fit the requirement as set: every put must be persisted to disk immediately. [[L-0208]] (How real memtable engines handle persistence comes back in [10.3](#s10-3).)

So keep a ledger: one file, a write-ahead-style log, where every change is appended at the end instead of being placed where it belongs. [[L-0209]]

Appending is what suits a magnetic disk best. The head is already where the last write ended, so there is no seek for the head to make and no waiting for the disk to spin round to the right sector; you just add more blocks at that point. Append only, zero seek, no big mechanical movement: the best you can do. [[L-0210]]

<Figure id="fig-7b" no="Fig 7·b" k="L-0210 L-0211 L-0213"
  caption="Four puts, appended in order. The update K1 V1′ doesn’t touch the first K1 entry; it goes to the end like everything else. The dot marks where the file starts. Redrawn from the class board at 02:08."
  >
  <Desk><AppendOnly /></Desk>
  <Phone><AppendOnly layout="phone" /></Phone>
</Figure>

Put `K1 V1` appends the key and value to the end of the file. Put `K2 V2` and put `K3 V3` create new entries after it, in order. [[L-0211]]

Should the store also remember, somewhere in memory, the address where each key’s entry starts on disk? That is the right instinct, and it waits until get. First get the maximum performance out of put. [[L-0212]]

Now update a key: put `K1 V1′`. You don’t go back, find the old K1 and change it. The new entry is appended like any other, and the old one simply becomes obsolete. Any put that comes is appended, no matter what. [[L-0213]]

That is how you get the maximum performance out of the put operation on a cheap magnetic disk. [[L-0214]]

In code, the whole put is a few lines: open the file for appending, write the record, and force it to disk before you answer.

```python
f = open("001.data", "ab")        # "a": append-only mode
f.write(record)                   # always lands at the end
f.flush(); os.fsync(f.fileno())   # persist immediately, then ack
```

Creating an append-only file takes nothing special. When you open a file you pick a mode: `r`, `w`, `r+`, `w+`, or `a`, which is append-only. You don’t reserve space up front, say a contiguous 1 GB, and track how much of it you have written; you open the file and start writing. Laying the file out on disk, and breaking it into pieces where needed, is the file system’s job, done through the system calls behind file I/O. [[L-0209 L-0293]]

Nor does the file system do it poorly. In most cases file systems (BTRFS, NTFS, ext2/3/4, whichever you use) don’t allocate files back to back. When a file is created a large chunk is marked for it, and new files are placed in decent free space, spaced out a bit, so a file growing slightly larger is not a problem. [[L-0294]]

</Section>

<Section id="s7-3" no="7.3" title="Delete: a put with a special value" crumb="7.3 Delete"
  dek="If you can only write at the end, a delete has to be written at the end too."
  meta="About 2 min · class 02:08–02:10">

The store only ever appends. K2 was written a while ago, further up the file. How do you delete K2?

<PauseAndThink k="L-0215 L-0216 L-0217 L-0218 L-0223"
  q="Your store only ever appends to the end of its file. K2 was written earlier. How do you delete K2?"
  choices={[{ label: 'Append a new K2 entry with a special “deleted” value', correct: true }, { label: 'Go back to K2’s entry and overwrite its value with −1' }]}
  right="Right. DEL K2 = PUT(K2, −1). The newest entry for K2 says it’s gone, and the in-memory map drops K2."
  wrong="That is a write at an earlier location, which an append-only file never does. You’d also be paying a seek for a delete.">

Delete is a put. Appends are O(1), so delete is O(1) too. The dead entries are cleaned up later, when old files are merged ([chapter 8](#s8)).

</PauseAndThink>

It is tempting to go back to K2’s entry and set its value to something that never occurs, −1 if values are always positive. But this is an append-only file: you cannot write to any other location. [[L-0215]]

<ForwardChip block label="back in" when="Lecture 3" lec="lec05" sec="s6-2" k="L-0215">delete as an update to −1, in the MySQL key-value store</ForwardChip>

An append-only file lets you read anywhere in what was written before, but you cannot write to anything before the end. Random reads, yes; random writes, no. [[L-0216]]

So reason from what is allowed. The only thing you may do is append, so append something that says K2 is deleted: an entry for K2 with a marker value. Delete is a put with a special value, `DEL K2 = PUT(K2, −1)`. [[L-0217]]

Put was O(1), the bare minimum, so a delete implemented as a put is just as efficient. Put and delete are both solved. [[L-0218]]

<RuleBox rule="==Append, no matter what==: every put, update and delete goes to the end of the file." k="L-0213 L-0216">

An append-only file can be read anywhere but written only at its end, and that is the most a magnetic disk can give a writer.

<Section id="s7-4" no="7.4" title="Get: an in-memory map to the latest offset" crumb="7.4 Get"
  dek="K1 is in the file twice. One small hash table in memory says which entry counts."
  meta="About 4 min · class 02:10–02:14">

K1 now appears twice in the file, and K2 has a −1 after it. How does a get find the right entry, fast?

The naive way: start at the top, look at every entry, and return the latest one for the key. That is very poor, and get deserves the best performance too. [[L-0219]]

An SSTable-like structure keeps suggesting itself here as well, but what is needed is a simple hash table. An SSTable and a hash table are very different things. [[L-0220]]

Keep an **in-memory hash table** that maps each key to the offset of its latest entry in the file: the offset, not the value. It is updated as soon as an entry is appended, and a get goes straight to that offset. [[L-0221]] It is the same move as the dictionary’s index in [2.3](#s2-3): a small map in memory pointing into a big file.

Put now has two steps, in this order: write the entry to disk and note its offset, then update the hash table. Put `K1 V1` lands at O1 and K1 points at O1; K2 points at O2, K3 at O3. Put `K1 V1′` is appended at O4 first, and then K1 is repointed to O4. [[L-0222]]

Delete removes the key’s entry from the in-memory hash table. If a key has no entry in the hash table, it does not exist. [[L-0223]]

Get looks the key up in the hash table. No entry: return 404, not found. An entry: go to that offset in the file and read the value. One memory lookup, one disk read, and the data goes back. [[L-0224]]

The map lives in memory, so it has one weakness. If the machine dies, the hash table is gone. The file is safe on disk, though, so on restart you go through the entire file and rebuild the index. That can take a long time, and for this design that is accepted. [[L-0225]]

With this design, get, put and delete are each O(1): each does the bare minimum the disk has to do. That is the maximum you can get out of a cheap magnetic disk, with full persistence for reads, writes, updates and deletes. [[L-0226]]

<RecallQuestions>
  <RecallItem k="L-0206 L-0210" q="Why is an append the cheapest write a magnetic disk can do?">

Because moving the head and waiting for the platter to spin round are the slow part of disk I/O, and an append needs neither: the head is already where the last write ended, so the new bytes go down right there. Zero seek, no big mechanical movement.

  </RecallItem>
  <RecallItem k="L-0217 L-0223" q="How is a delete stored in an append-only file, and how does the map reflect it?">

As a put with a special value: `DEL K2 = PUT(K2, −1)` appends a K2 entry with the marker at the end of the file. The in-memory map drops K2, so a later get finds no entry and returns 404 without touching the disk.

  </RecallItem>
  <RecallItem k="L-0225 L-0222" q="After a crash, what must the store do before it can answer a get, and what does that cost?">

Rebuild the map: read the whole file from the top, pointing each key at the latest offset it sees and dropping keys whose latest entry is −1. Until that scan finishes the store can’t answer, so a restart takes a long time; the design accepts that.

  </RecallItem>
</RecallQuestions>
