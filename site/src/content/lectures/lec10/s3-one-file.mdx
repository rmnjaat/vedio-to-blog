<Section id="s3" no="3" title="One file you can ship" crumb="3 One file"
  dek="The index made two files, and the brief said one. Putting both in one file raises a new question: where does the index stop? The answer is the header, the trick behind every file format."
  meta="About 15 min · class 00:35–00:50, Q&A 03:02">

The dictionary is now two files: `index.dict`, a couple of megabytes of words and offsets, and `data.dict`, the terabyte of meanings. A partner downloads it to use it somewhere else. The brief from chapter 1 said one file.

This chapter puts the two back into one, and finds that the hard part isn't joining them. It is telling the reader where one part stops and the next begins.

</Section>

<Section id="s3-1" no="3.1" title="Two files break portability" crumb="3.1 Two files"
  dek="Join the index and the data, and the reader needs to know where the index stops. Five ways to tell it, and what each one costs."
  meta="About 7 min · class 00:35–00:41">

Two files, an index and a `data.dictionary`, break portability. Anyone who copies the dictionary has to copy both and keep them together, and the whole point of portable was that the dictionary is literally one file. So it has to become one. [[L-0064]]

The first idea is to not persist the index at all: ship only the data file and build the index in memory every time a server starts. It works, but every startup then iterates through the entire terabyte of data just to rebuild something that hasn't changed. The file changes once a week, so the work is avoidable. Store the index. [[L-0065]]

So merge the two files: concatenate the index and the data into one gigantic file, index first. That brings a new challenge. When the reader opens this file, how does it know where the index ends and the data begins? [[L-0066]]

<Figure id="fig-3a" no="Fig 3·a" k="L-0066 L-0067 L-0068"
  caption="Index and data concatenated into one file. The open question is the zigzag: where does the index stop? Under the bar, the first two answers from class. Redrawn from the class board at 00:36–00:38.">
  <Desk><OneFileBoundary /></Desk>
  <Phone><OneFileBoundary layout="phone" /></Phone>
</Figure>

It matters more than it looks. Say both parts are CSV lines and the server reads the file line by line into its hash map at boot. Nothing tells it to stop after the last index entry, so it carries on into the data: `apple,a fruit` gets read as one more entry, and apple's offset in the map is replaced by "a fruit". The reader has to know when to stop. [[L-0070]]

Several answers came up in class, and each was tested against that one question.

**A special line.** Put a separator line, or some special marker, between the index and the data. It works, and it was called a good approach that can be improved: the reader still has to look at every line to find the marker. [[L-0067]]

**A fixed region.** Pre-allocate space for the index: the first 2 MB of the file are the index, a little more than today's 1.751 MB, since few new words get added each week. The reader then knows the first 2 MB are index without looking for anything. “A very nice hack”, in the lecture's words, though it wastes a little space, and the push was to be more frugal. [[L-0068]]

**A stack.** Write the data from the top of the file down and the index from the bottom up. That still leaves the original problem: on the day the two meet, how do you know where one finished and the other begins? The gap between them is unused space until then, and the fallback, once more, was a separator. [[L-0069]]

**A number at the start.** Reserve a specific position at the very beginning of the file for the boundary information, and update it as data is added. That one is interesting, and the next section refines it. [[L-0071]]

A number at the start. Store the byte offset (here, the index size) in a small fixed-size header, and the boundary is never searched for. Without it, the reader would load data lines into the map as if they were index entries. That header is the trick behind every file format ([3.2](#s3-2)).

</PauseAndThink>

<Section id="s3-2" no="3.2" title="A fixed-size header" crumb="3.2 The header"
  dek="Store the boundary as a number, not a marker. Sixteen bytes at the front of the file tell the reader what it holds and how to read it."
  meta="About 6 min · class 00:41–00:46, Q&A 03:02">

Refine the last idea. Instead of storing a separator, store the byte offset directly at the start of the file. That removes the need for a separator altogether. When the reader opens the file, its first step is to read that first chunk, and from it, it knows exactly where the data begins. [[L-0072]]

That first chunk is a **header**, and it is the classic mechanism of file formats everywhere: PNG, JPG, MP3, AVI. The first few bytes contain meta information about everything else in the file, and what exactly they hold depends on the format, as its creator specified it. [[L-0073]] Not every format puts this directory at the front, though: a ZIP archive ends with its central directory, and MP4 muxers usually write the `moov` index at the end, with a “faststart” pass to move it to the beginning (<Cite href="https://pkware.cachefly.net/webdocs/casestudies/APPNOTE.TXT">ZIP APPNOTE</Cite>, <Cite href="https://ffmpeg.org/ffmpeg-formats.html">ffmpeg formats</Cite>). [[L-0073]]

Our file has more than one section, an index and the data, so the header stores the information about each of them. [[L-0074]] And the header has a fixed size: it can't grow beyond it, because the reader has to know how many bytes to read before it knows anything else. [[L-0075]]

Three fields go in it. The first 8 bytes hold a name that tells the decoder “this is our dictionary”: `OUR_DICT`. [[L-0077]] PNG does the same: its first bytes say PNG, and an MP3 starts with bytes of its own. Precisely, every PNG file begins with the same 8-byte signature, hex `89 50 4E 47 0D 0A 1A 0A`, which contains the letters “PNG” and lets the decoder recognise the file (<Cite href="https://www.w3.org/TR/png-3/">PNG specification</Cite>). [[L-0078]] Your own database would start with its own magic bytes, spelling its name, say `AODB` (the example said in class; the board’s scrawl reads `AOBB`), and its decoder would recognise an `AODB` file and know what components it holds. [[L-0079]]

The next 4 bytes hold a **version**, because one format can have variants. Version 1 might store the index first and then the data; version 2 the data first and then the index. The decoder reads the version and acts accordingly. [[L-0080]]

The last 4 bytes hold the **index size**: how big the index is, the integer for 1.75 MB in our case. Storing the start offset of the data would work too; the board first had that line and replaced it with the size. [[L-0076]] It is the size of the index stored *in this same file*, not the location of some other file: read the header, get the index size, read that many bytes, and you have the index. [[L-0076]]

  caption="The dictionary’s header: 8 bytes of name, 4 of version, 4 of index size, 16 bytes in all. Below, the same fields to scale, then the index and the data. Redrawn from the class board at 00:44.">
  <HeaderBytes />
</Figure>

That is a fixed-width header of 16 bytes: 8 for the name, 4 for the version, 4 for the index size. [[L-0081]] A binary header also has to fix the byte order of its integers, or a decoder that assumes the other order reads garbage sizes. PNG stores multi-byte integers most significant byte first; Parquet stores its 4-byte metadata length little-endian (<Cite href="https://www.w3.org/TR/png-3/">PNG</Cite>, <Cite href="https://parquet.apache.org/docs/file-format/">Parquet</Cite>). [[L-0081]]

```c
struct dict_header {          /* 16 bytes, fixed */
  char     magic[8];          /* "OUR_DICT"          */
  uint32_t version;           /* 1: index, then data */
  uint32_t index_size;        /* bytes of index that follow */
};
/* then: index[index_size]   word,offset lines   */
/* then: data …              word,meaning lines  */
```

Now walk a server through boot. It reads the first 16 bytes of the file as the header. The first 8 say it is our dictionary; the next 4 are the version; the next 4 are the index size. It reads exactly that many bytes as the index and builds a hash table from them. Everything after that is data, and the offsets in the index point into it. [[L-0082]]

The same logic holds for every file format: a fixed header first, which says how to find each part that follows. [[L-0082]]

<Section id="s3-3" no="3.3" title="Every file format is a header and sections" crumb="3.3 File formats"
  dek="You have just designed a file format. So has everyone who wrote a PNG decoder."
  meta="About 4 min · class 00:46–00:50">

Look at what the 16 bytes bought. The dictionary is shippable again, and it got there the classic way any custom file format is built: divide the file into compartments, here the index and the data, and keep a header that tells you where each compartment lies. Because of the one portability constraint, the dictionary became a single file instead of several. [[L-0083]]

<RuleBox rule="Divide the file into ==compartments==, and put a ==fixed-size header== first that says where each one lies." k="L-0083">

That is how every custom file format is built, and it is what made the dictionary shippable as one file.

<Desk><CompartmentsRule /></Desk>
<Phone><CompartmentsRule layout="phone" /></Phone>

</RuleBox>

Other formats are built from sections too. A JPG has its frames; in an MP4, the header says where the video part is and where the audio part is, the video holding its first, second, third frames and the audio its waveform information. [[L-0084]]

That is also why one file with a header ships so easily, across systems or to end users: anyone who has the decoder can read it. [[L-0085]]

Parquet, which you meet in data engineering, also has headers and information. Strictly, Parquet keeps that information in a footer: the file starts with the magic `PAR1`, then the column chunks, then the file metadata and its 4-byte length, then `PAR1` again. Writing the metadata after the data allows a single pass when writing, and a reader reads the footer first to find the column chunks it needs (<Cite href="https://parquet.apache.org/docs/file-format/">parquet.apache.org</Cite>). [[L-0086]]

<Figure id="fig-3d" no="Fig 3·d" k="L-0086 L-0087"
  caption="Where the locating information lives. PNG and our dictionary put it first; Parquet and ZIP keep it at the end of the file. JSON has none, so a reader parses all of it. New figure.">
  <Desk><HeaderOrFooter /></Desk>
  <Phone><HeaderOrFooter layout="phone" /></Phone>
</Figure>

JSON has no header. A JSON file is a simple text file, so to get any information out of it you read the entire file and let the JSON decoder parse the curly braces, the quotes and the strings into an in-memory dictionary first. [[L-0087]]

CSV in general does not have a header either, whereas formats like PPT and PDF do, and you can define your own custom format. Note that CSV's “header” is something else: RFC 4180 allows an optional first line of column names, signalled by the `header=present` parameter of `text/csv`, which names columns but doesn't say where data lies (<Cite href="https://www.rfc-editor.org/rfc/rfc4180">RFC 4180</Cite>). And PDF does start with a `%PDF` version header, but a reader finds its catalog through the trailer at the end of the file (<Cite href="https://www.loc.gov/preservation/digital/formats/fdd/fdd000030.shtml">Library of Congress</Cite>). [[L-0088]]

Every file format has its own **encoder** and **decoder**. The encoder creates a file in that specific format; the decoder decodes it. That holds for image, video, audio, any format. [[L-0090]]

<MarginNote title="A homemade image format" why="skip if you only want the dictionary" k="L-0089">

The instructor once tried to write an image format of his own, and that is how he got to know how file formats and their headers work. [[L-0089]]

</MarginNote>

Remember the early-internet message “this web browser does not support TIF format”? It means the browser has no decoder for that format: given that set of bytes, it does not know how to interpret them. [[L-0091]] It is still true for TIFF. As of October 2026, MDN lists Safari as the only browser that displays TIFF natively; the others need special libraries or add-ons (<Cite href="https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Formats/Image_types">MDN</Cite>). [[L-0091]]

<RecallQuestions>
  <RecallItem k="L-0067 L-0072" q="Why does a separator line between the index and the data cost more at boot than a byte offset in a header?">

With a separator, the reader has to check every line it reads for the marker, and it only learns where the index ends when it finds it. With a number in a fixed-size header, it reads a few bytes first, then exactly that many bytes of index, and knows everything after is data. Nothing is searched for.

  </RecallItem>
  <RecallItem k="L-0081 L-0076" q="What three fields are in the dictionary’s 16-byte header, and which one lets the reader skip straight to the data?">

An 8-byte name (`OUR_DICT`), a 4-byte version and a 4-byte index size. The index size does it: after the 16 bytes come exactly that many bytes of index, and the data starts right after them.

  </RecallItem>
  <RecallItem k="L-0091 L-0090" q="What does “this browser does not support TIF” tell you about the browser, in this chapter’s terms?">

That it has no decoder for the TIFF format. Every format has an encoder that writes it and a decoder that reads it; without the decoder, the browser has the bytes but doesn’t know how to interpret them.

  </RecallItem>
</RecallQuestions>
