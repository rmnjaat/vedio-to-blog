How likely are you to open an Amazon order you placed six months ago? Not very. Yet every one of those orders still sits in the main database, on fast and expensive machines, next to the orders people check every day. Move the old ones to S3 and they cost a fraction as much. But S3 holds files, not tables: you can’t just dump the orders there and still ask for order 1234 without reading everything. [[L-0189 L-0190 L-0192]]

This lecture builds the answer twice, out of nothing but files. [[L-0002]]

The first build is a toy with real numbers. A publisher hands you a dictionary, 170,000 English words with their meanings, 1 TB in all, and wants an API that returns the meaning of any word. You may not use MySQL, Postgres, MongoDB, Redis, Elasticsearch or any other database. Whatever you build lives in plain files. [[L-0003 L-0012]]

### Where you are

<LectureLink lec="lec07">Lecture 9</LectureLink> built a cache like Redis: one hash table in memory, every byte counted, then a ring of nodes, and an append-only file that only mattered after a restart. Everything lived in RAM, which is why it was fast, and why it had a ceiling. <LectureLink lec="lec09">Lecture 7</LectureLink> put Instagram’s photos in S3 because it is dirt cheap, and fetched each photo whole. <LectureLink lec="lec05">Lecture 3</LectureLink> built a key-value store on one MySQL table and let the database do the hard parts.


### What you’ll build

**Build 1, a dictionary on S3 (chapters 1–6).** Read-mostly, updated once a week, and it has to ship as one file. You start with a plain text file and a lookup that reads half a terabyte. Each chapter fixes the problem the last one left: how to find one word, how to keep it one file, where the file lives when a hundred servers need it, how to change it on Sunday, and how every server moves to the new version without a single user reading garbage. At the end you meet the old orders again. [[L-0013]]

**Build 2, a key-value store on cheap disks (chapters 7–10).** Now the data is written all day: puts, updates and deletes, each safe on disk before it is acknowledged, on the magnetic disks that hold most of the world’s data because SSDs cost too much. It is a database many people use without knowing it. You design put, get and delete, then deal with the disk filling up and a crash tearing a record in half, and only then find out what it is called. [[L-0200]]

The tools in both builds are the same few: a file, byte offsets, and a small map in memory. What changes is how hard the writes push.

### What you’ll be able to do

- Size an index before you build it, and decide from the number where it lives.
- Read a few bytes from one huge file on S3, and say what storage can stand in for S3.
- Apply a batch of changes to a big file without ever corrupting what is being served, and move a fleet onto the result.
- Design a store that takes writes as fast as a cheap disk allows, and say what it costs in memory and disk.
- Catch a half-written record instead of serving it.

### Before you start

You need a load balancer with API servers behind it, a hash map, and what a byte offset in a file is. Python sketches show the code; any language works the same way.

Each chapter opens with a small map of what has been built so far. When a “Pause and think” box asks you something, commit to an answer before you open it.
