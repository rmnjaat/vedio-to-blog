<Section id="s8" no="8" title="A month later the disk is nearly full. What is filling it?" crumb="8 The disk fills" meta="About 7 min">

Say the store has run for a month on a 1 TB disk. Its one file has filled most of it, and most of what is in it is dead: old values that were overwritten, and keys that were deleted. Nothing ever leaves the file, because the only thing the store knows how to do is append.

<Section id="s8-1" no="8.1" title="What could go wrong?" crumb="8.1 Weak spots">

Three things. First, a restart is slow: the map is rebuilt by reading every file, and until that finishes the store answers nothing. Real Bitcask’s merge writes a small hint file next to each file it produces, holding each key with the position and size of its value <Cite href="https://riak.com/assets/bitcask-intro.pdf">Bitcask paper</Cite>, and on restart the map is rebuilt from those instead <Cite href="https://docs.riak.com/riak/kv/latest/setup/planning/backend/bitcask/index.html">docs.riak.com</Cite>. [[L-0227]]

Second, every key has to fit in memory: not the values, but every key with its offset. Keep that one in mind. [[L-0228]]

Third, the file grows without limit, and one day the disk is full. [[L-0229]] That one needs fixing now.

Start by keeping several files and writing to only one at a time; the others become immutable and can be cleaned up at leisure. Reads still go wherever the key is. [[L-0230 L-0231 L-0232]]

</Section>

<Section id="s8-2" no="8.2" title="How big should one file get?" crumb="8.2 Rotation">

  right="Right."

Small, around 100 MB to a few GB, with a new file started each time the current one fills up. A file of hundreds of gigabytes can’t be cleaned up or rebuilt in pieces.

</PauseAndThink>

One huge file can’t be indexed in parallel on restart, and cleaning it up means chewing through all of it at once. [[L-0233 L-0234]] So start a new file as soon as the current one crosses 100 MB or 1 GB; real Bitcask does it at 2 GB by default <Cite href="https://docs.riak.com/riak/kv/latest/setup/planning/backend/bitcask/index.html">docs.riak.com</Cite>. [[L-0236]]

The files are numbered in order, 001, 002, 003, 004. At any moment exactly one is **active** and takes every write; the rest are read-only, but can still be read. Each time the active file crosses its limit, a new one starts. That is **file rotation**. [[L-0237 L-0238]]

  <Phone><FileRotation layout="phone" /></Phone>
</Figure>

One thing changes in memory. An offset alone no longer says where a key is, so the map stores the file and the offset: `K1 → f1, O4`. A get finds the key, goes to that file at that offset, and reads. [[L-0239]]

</Section>

<Section id="s8-3" no="8.3" title="Who clears out the dead entries?" crumb="8.3 Compaction">

The read-only files are full of waste. K1 was overwritten later, so its old entry is **stale**. K2 was deleted, so both its entries are dead. [[L-0240]]

While the active file keeps taking writes, a separate process, **merge and compaction**, reads the read-only files and writes one new file that combines them, leaving the stale and deleted entries out. Three read-only files become one. Once the new file is written, the old ones are deleted for good. [[L-0241 L-0295]]

How do you merge them? Not with chapter 5’s two pointers: these files are in write order, not sorted. Read the entries into a temporary hash table, where a later entry for a key replaces the earlier one and a delete removes the key, then copy the records it points at into the new file. The table belongs to the merge alone, and holds positions, not values. [[L-0243 L-0296]]

```python
tmp = {}                                 # key -> (file, offset) of its latest record; not the index
for rec in records(read_only_files):     # oldest file first, in write order
    if rec.is_delete:
        tmp.pop(rec.key, None)           # a delete removes the key
    else:
        tmp[rec.key] = (rec.file, rec.offset)   # a newer entry replaces the older one
live = [(k, pos) for k, pos in tmp.items()      # still the latest? the active file
        if index.get(k) == pos]                 # may have rewritten or deleted it
write(merged_file, live)                 # copy only those records to the new file
repoint_index(merged_file, live)         # repoint only those, if still unchanged
delete(read_only_files)
```

The last lines are the delicate ones. While the merge ran, the active file kept taking writes, so some keys it copied may have been written again or deleted since. Copy and repoint a key only if the map still points at the entry being copied; the newer write wins. Every entry that did move sits in a different file at a different offset, so the map has to be repointed for each of them, without a get ever seeing a key that points at nothing. [[L-0242]]

</Section>

<Section id="s8-4" no="8.4" title="How often should that run?" crumb="8.4 The sawtooth">

Plot disk usage over time. Writes push it up; each merge and compaction drops it sharply; then it climbs again. It draws a **sawtooth**. [[L-0244]]

<AnimationClip clip="l10-sawtooth" no="Clip 8·1" k="L-0244 L-0245 L-0246 L-0247 L-0248"
  lead="Halve the merge frequency. Does the peak go up or down, and what is the line it must never cross?"
  caption="Disk usage climbs with writes and drops at each merge and compaction: a sawtooth under the 1 TB cap. Merge too often and the CPU is busy merging; too rarely and a peak hits the cap and the store crashes." />

The disk has a hard ceiling: when usage reaches 1 TB, the next append fails and the store stops taking writes. Merge too often and the CPU spends its time collecting garbage instead of doing real work; merge too rarely and the peaks climb toward the cap. The shape of the sawtooth decides how often merges must run, and how the database performs. [[L-0245 L-0246]]

That gives the design two knobs: how often merge and compaction runs, and how big a file may grow before rotation. Set them by watching the sawtooth while the store runs, and if you ship a store like this, expose both as settings. [[L-0247 L-0248]]

With rotation and compaction, the store keeps its O(1) operations and stops eating the disk. Each get still costs one seek on a magnetic disk, and never more than one <Cite href="https://docs.riak.com/riak/kv/latest/setup/planning/backend/bitcask/index.html">docs.riak.com</Cite>. On SSDs the gain is smaller but real: flash can’t overwrite in place either, so appending is still the pattern it handles best. [[L-0249 L-0250]]

One assumption has been hiding since chapter 7. Every “append K1 V1” has treated a write as something that either happens or doesn’t. What if the power fails halfway through one?

</Section>
