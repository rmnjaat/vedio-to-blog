<Section id="s3-4" no="3.4" title="GitHub does exactly this" crumb="3.4 GitHub"
  dek="Attach an image to a GitHub issue and watch four network calls: the same pre-signed upload, with a CDN URL handed back."
  meta="About 12 min · class 00:44–00:57">

System design is all about building blocks. Once you know how a solution works, you can Ctrl-C, Ctrl-V it anywhere you need it. Instagram’s image upload and GitHub’s issue attachments, which look like very different products, are one and the same. [[L-0087]]

Open any repository’s issues, start a comment, and attach an image with the browser’s Network tab open. A 179 KB PNG fires four network calls. The first goes to GitHub’s upload policy endpoint for assets (<code style={{whiteSpace:'normal'}}>github.com/<wbr/>upload/<wbr/>policy/<wbr/>assets</code>, as read off the screen). It registers the intent to upload: in effect, it asks GitHub’s image upload service, “I want to upload something.” [[L-0088]] That first request carries only metadata: the image’s name, its size (183,938 bytes, which is 179 KB), its content type `image/png` and an authentication token. The image itself is not sent yet. [[L-0089]]

The response is where it gets interesting. It contains a signed upload URL, and that URL is not GitHub’s: it is S3’s. The response, generated with S3, has everything the frontend needs to upload the image directly to S3. [[L-0090]] It also has an asset `href`, which is what the image URL is going to be. Look carefully and it is a CDN URL, on `user-images.githubusercontent.com`. That is GitHub’s CDN alias, just as `edge.arpitbhayani.me` was in [2.4](#s2-4), and the path contains the image ID, `221335625`. [[L-0091]] (Two details from GitHub’s own docs: image attachments are capped at 10 MB <Cite href="https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/attaching-files">docs.github.com</Cite>, and since May 2023 new attachments in private repositories can be viewed only after logging in; before that, anyone with the direct URL could open them. <Cite href="https://github.blog/changelog/2023-05-09-more-secure-private-attachments/">github.blog</Cite>)

What did GitHub’s backend do when it got that first call? It made a database entry (optional), took a random image ID, `221335625`, and built a path in its S3 bucket: a folder, then the ID, then `.png`. It created a pre-signed URL for that path. And it did not expose the S3 path: it exposed the CDN URL, which is exactly the URL used to render the image. [[L-0092]] GitHub inserts that URL into the comment as standard markdown with an exclamation mark at the beginning, which means “render this as an image”. [[L-0093]]

Now the upload itself. The response’s `form` object contains what S3 needs. When uploading directly to S3, you pass these fields in the body of the HTTP POST, and that is how S3 knows this is a pre-signed upload. The details are specific to S3, but GCP and Azure blob storage have equivalent patterns: the concept and the logic stay the same. [[L-0094]] On Google Cloud, a signed URL can be valid for at most 7 days, and anyone holding one can use it; on Azure, SAS tokens are generated client-side and not tracked by the service, and Microsoft recommends the user-delegation kind, signed with Entra ID credentials. <Cite href="https://docs.cloud.google.com/storage/docs/access-control/signed-urls">cloud.google.com</Cite> <Cite href="https://learn.microsoft.com/en-us/azure/storage/common/storage-sas-overview">learn.microsoft.com</Cite>

So where is the pre-signed URL? The upload URL in the response is just the normal endpoint of GitHub’s S3 bucket. What makes the upload pre-signed is the set of fields in the POST body. [[L-0095]] Field by field:

- **`key`** is the path in the bucket where the pre-signed URL was generated and where the image will land. It is the same path you saw in the CDN URL. [[L-0096]]
- **`acl: public-read`** makes the created object readable by everyone, with no authentication and no special credentials. ACLs can be changed. [[L-0097]] (That was true of GitHub’s bucket at the time. As of Oct 2026, new S3 buckets default to “Bucket owner enforced”, with ACLs disabled, and an upload that specifies an ACL other than `bucket-owner-full-control` fails with <code style={{whiteSpace:'normal'}}>400 AccessControlListNotSupported</code>; AWS recommends bucket policies instead. Today the usual approach is a private bucket read through a CDN, as in [3.5](#s3-5). <Cite href="https://docs.aws.amazon.com/AmazonS3/latest/userguide/about-object-ownership.html">docs.aws.amazon.com</Cite>)
- **`policy`** is the signed part, often loosely called the certificate. It is signed with the key held on the API server, and it embeds the expiration. So S3 needs no database to store the time and no timer: once the time has passed, it simply refuses the upload. JWTs work the same way. [[L-0098]] (Precisely: the policy carries the expiry and the upload conditions, and `X-Amz-Signature` is the signature over it, made with the backend’s AWS credentials, so S3 checks validity statelessly from the request itself. <Cite href="https://docs.aws.amazon.com/boto3/latest/reference/services/s3/client/generate_presigned_post.html">docs.aws.amazon.com</Cite>) One limit worth knowing: a presigned URL can’t outlive the credentials that signed it. With an IAM user’s keys it can last up to 7 days; signed with temporary role credentials, it expires when the role session ends (about 6 hours for EC2 instance roles). <Cite href="https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html">docs.aws.amazon.com</Cite>
- **The rest** (`X-Amz-Algorithm`, `X-Amz-Credential`, `X-Amz-Date`, `X-Amz-Signature`) are parameters AWS wants in the request. [[L-0099]]

The second step is the upload. The frontend makes a POST to <code style={{whiteSpace:'normal'}}>github-<wbr/>production-<wbr/>user-<wbr/>asset-<wbr/>…</code>, a host on `s3.amazonaws.com`, which is S3’s URL, with form data copied from the first response (key, ACL, policy, algorithm, content type and so on) plus the file: the actual image bytes, about 173 KB of PNG. The image goes straight to S3. [[L-0100]] What GitHub does after that, such as rendering the image in the comment, is its own logic and not our concern. What makes this flow special is how much bandwidth it saved. [[L-0101]]

Then open the image URL. It goes to the CDN, <code style={{whiteSpace:'normal'}}>user-<wbr/>images.<wbr/>githubusercontent.<wbr/>com</code>. The first time, the CDN doesn’t have that path, so it goes to the origin GitHub configured for it, the S3 bucket, reads the key, caches it and forwards it to the user. The next load comes from the CDN and is noticeably faster. [[L-0102]]

Image upload practically everywhere works this way, Instagram and GitHub alike: it is always a pre-signed URL, because it saves a ton of bandwidth, and that is why everyone prefers it. [[L-0103]] (It is the common default for user images. Many services mix it with uploads proxied through their own servers where validation is needed; Microsoft’s guidance describes exactly that hybrid, and says data written directly should be validated before the application uses it. <Cite href="https://learn.microsoft.com/en-us/azure/storage/common/storage-sas-overview">learn.microsoft.com</Cite>)

Submitting the issue is the last piece, and it is publishing an Instagram post. First the image is uploaded to S3, ready to be published; then a separate call publishes the post that refers to it. GitHub’s attachment upload is Instagram’s image upload, same flow. [[L-0104]] What that second call stores is the next chapter.

<MarginNote title="See it yourself" why="skip if you’ve read a presigned POST before" k="L-0088">

Open a draft issue on any repository you own, open DevTools → Network, and attach an image. Find the four calls: the metadata POST to github.com, the S3 POST with the form fields and file, the PUT that confirms, and later the GET on <code style={{whiteSpace:'normal'}}>user-<wbr/>images.<wbr/>githubusercontent.<wbr/>com</code>. Click the S3 POST and read its form data: `key`, `policy` and the `X-Amz-*` fields are all there.

</MarginNote>

<Section id="s3-5" no="3.5" title="What direct upload raises" crumb="3.5 What it raises"
  dek="Who checks the photo, how the app learns its URL, why not link to S3, and how a CDN reads a bucket nobody else can."
  meta="About 7 min · Q&A 00:57–01:04">

The photo is in S3. Who checks it, how does the app show it, and why not just link to S3?

**Moderation.** Content moderation is a different system, done with asynchronous processing. If moderation must happen in the request context, before the photo may be published, then you can’t upload directly to S3. That is why most moderation happens after the image is published, or almost on the fly. [[L-0105]] S3 itself provides the natural trigger: event notifications publish “object created” events to Lambda, SQS, SNS or EventBridge, at least once and usually within seconds. <Cite href="https://docs.aws.amazon.com/AmazonS3/latest/userguide/EventNotifications.html">docs.aws.amazon.com</Cite>

**The CDN URL in the upload response.** It comes from the image upload service. The path stays the same; you prefix it with your CDN endpoint instead of the bucket. In other words, replace the S3 bucket name with your CDN host, and that is your CDN path: plain string concatenation. [[L-0106]]

Why send a CDN URL at all, when the client asked for a pre-signed S3 URL? So the frontend knows what URL to render. S3 is not public: you can’t just call the S3 URL and get the data. Reading is allowed only for the CDN. [[L-0107]] (That is the recommended *configuration*, CloudFront origin access control plus a bucket policy, not something inherent to S3; the GitHub demo itself uploaded with `acl: public-read`, which makes that object readable straight from S3. <Cite href="https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-restricting-access-to-s3.html">docs.aws.amazon.com</Cite>) With origin access control the bucket stays private and its policy allows only the `cloudfront.amazonaws.com` service principal, for one specific distribution, to read objects. <Cite href="https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-restricting-access-to-s3.html">docs.aws.amazon.com</Cite>

It is tempting to skip the CDN and render images straight from S3: it is blob storage, after all, and the photos are already there. In this design you can’t: the bucket is private (see above). The reply in class was left unfinished, “it is not meant for…”, and ended on “a CDN is not a blob store”. [[L-0108]] (In general S3 can serve images directly, as public objects or through presigned URLs; here the bucket stays private and the CDN, which is a cache, serves them. <Cite href="https://docs.aws.amazon.com/AmazonS3/latest/userguide/ShareObjectPreSignedURL.html">docs.aws.amazon.com</Cite>)

**Why is a CDN faster than S3?** A question like “a CDN node in Mumbai or S3 in Bangalore?” is too specific to answer in general: if Akamai has an edge server in Bangalore, the CDN. The key reason is geography, though there may be other optimizations too; benchmark it and find out. [[L-0109]] Another remark from the class: even if location were the only gain, reading every photo straight from S3 would still cost a lot. [[L-0110]]

On geography, the numbers are lopsided. Akamai has at least 18 locations in India (one in Bhopal, three in the north, two in the northeast, three in the west and four in the south), while AWS has only two, now three, data centres there. The CDN is much closer to users: you don’t have to go to Bangalore to read the photo; it is served right where you are. [[L-0111]] (Precisely: S3 lives in AWS’s two Regions in India, Mumbai and Hyderabad, while CDNs have edge PoPs in many Indian cities. <Cite href="https://docs.aws.amazon.com/global-infrastructure/latest/regions/aws-regions.html">docs.aws.amazon.com</Cite>) As of October 2026, AWS lists those two Regions, with three Availability Zones each, while its own CDN, CloudFront, lists standard edge locations in 7 Indian cities plus embedded PoPs in 46 more. <Cite href="https://aws.amazon.com/cloudfront/features/">aws.amazon.com</Cite>

Storage differs too. CDNs might keep content on local disks, might have a bunch of SSDs; we don’t know. S3, being an ocean of data, doesn’t store on SSDs: that would be very costly. [[L-0112]] (The S3 half is on record: AWS has said S3 is built on hard disk drives, millions of them, and that disks growing in capacity but not in speed shapes its design. S3 also offers a separate high-performance class, S3 Express One Zone. <Cite href="https://www.allthingsdistributed.com/2023/07/building-and-operating-a-pretty-big-storage-system.html">allthingsdistributed.com</Cite>)

And they promise different things. S3 gives you a “nine nines guarantee, something like that”; a CDN gives you a different guarantee, better response time. [[L-0113]]

<SourceNote href="https://docs.aws.amazon.com/AmazonS3/latest/userguide/DataDurability.html" k="L-0113">

S3 Standard is designed for 99.999999999% (eleven nines) durability and 99.99% availability over a year, storing objects across at least three Availability Zones. Durability (not losing data) and availability (being reachable) are different promises; a CDN’s promise is lower latency from nearby edges.

</SourceNote>

If you want to squeeze out performance, benchmark and see what works best for you. If the CDN doesn’t work best for you, that’s okay, but then you pay S3’s egress cost and should be fine with that. [[L-0114]] On AWS, putting CloudFront in front of S3 also changes the bill: transfer between CloudFront and an AWS origin such as S3 is waived, so you pay CloudFront’s delivery price instead of S3’s internet egress. <Cite href="https://aws.amazon.com/cloudfront/pricing/">aws.amazon.com</Cite>

**How the CDN reads a private bucket.** For public objects it needs nothing; it can read them directly. For a private bucket, the CDN’s AWS integration lets you upload an AWS access key and secret key to the CDN, so it can read the private images. [[L-0115]] (That is how third-party CDNs do it. CloudFront instead uses origin access control: it signs its requests to the bucket with SigV4 as the CloudFront service principal, and no keys are handed over. <Cite href="https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-restricting-access-to-s3.html">docs.aws.amazon.com</Cite>)

It is tempting to assume the CDN goes through the same dance as the client: generate a signed URL, then fetch with it. It doesn’t. It holds the access and secret keys and does a normal S3 read with the AWS SDK, not via a URL. [[L-0116]] (On the wire that is an authenticated HTTP request, signed with SigV4, with the signature in the `Authorization` header. <Cite href="https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-restricting-access-to-s3.html">docs.aws.amazon.com</Cite>)

Keys on the CDN are one way, and maybe not the only one. Almost everyone puts a CDN in front of S3, so CDNs have native S3 integrations and S3 supports seamless CDN integration, without you wiring up authenticated requests every time. [[L-0117]] On AWS, that native integration is origin access control: the bucket stays private, its policy allows the CloudFront service principal for one specific distribution, CloudFront signs every request it sends to S3, and no access keys are uploaded to the CDN. <Cite href="https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-restricting-access-to-s3.html">docs.aws.amazon.com</Cite>

<RecallQuestions>
  <RecallItem q="A 5 MB upload goes through your API servers. Which problem is real and which isn’t: a crash mid-upload, or bandwidth?" k="L-0071 L-0072">

Bandwidth is real. A steady stream of 5 MB requests fills the API servers’ network cards, which have a physical limit, so every other API call on those servers suffers, and their memory needs go up. A crash mid-upload is not a real problem: the server returns a 5xx and the client retries.

  </RecallItem>
  <RecallItem q="Walk through the two phases of a pre-signed upload and say what each one sends over the wire." k="L-0081 L-0082 L-0089 L-0100">

Prepare: the client asks the image upload service, sending only metadata (name, size, type); the service picks a random image ID, signs a short-lived URL for that exact S3 path and returns it (GitHub also returns the future CDN URL). Upload: the client sends the photo’s bytes straight to S3 with that URL (a PUT, or a POST with the signed form fields, as GitHub does). Your servers carry metadata only.

  </RecallItem>
  <RecallItem q="Why does the upload response include a CDN URL and not just the S3 key, and what would break if the bucket were made public instead?" k="L-0106 L-0107 L-0083">

The frontend needs a URL it can render, and the bucket is private: only the CDN may read it, so an S3 URL would be refused. The CDN URL is the same path with the bucket swapped for the CDN host. Making the bucket public for uploads would let anyone store their data on your bill; making it public for reads would bypass the CDN, so you’d pay S3’s egress and lose the nearby edges.

  </RecallItem>
</RecallQuestions>
