<Section id="s7" no="7" title="The hashtag page: what to store" crumb="7 The hashtag page"
  dek="A page that looks too simple to design. What it shows, who owns which part, and the one document that renders it in a single read."
  meta="About 20 min · class 01:55–02:06, 02:18–02:19; Q&A 03:11–03:16">

Tap `#sunset` on Instagram. A page opens: the tag, “1.2m photos”, and a grid of the top 100. It has to render instantly, and there is one of these pages for every one of millions of hashtags.

The photos are handled: chapters 3 to 6 got them uploaded, stored and served. This chapter decides what the hashtag page needs stored. The next one finds out how much machinery hides behind one number on it.

</Section>

<Section id="s7-1" no="7.1" title="The page, and its boundary" crumb="7.1 The page"
  dek="What the hashtag page shows, which part is yours, and which part belongs to another team."
  meta="About 5 min · class 01:54–01:59 and 02:19–02:20">

This half of the lecture looks like a very simple problem, and scale isn’t even on the table. Yet go one level deeper, into how you would actually build it, and hidden components turn up and a lot of assumptions get busted. [[L-0002]]

The problem: on Instagram, tapping a hashtag opens a page dedicated to it. The page shows the hashtag, the number of photos tagged with it and, to keep it simple, exactly the top 100 of those photos. The goal is the best user experience when this page renders. [[L-0211]]

<Figure id="fig-7a" no="Fig 7·a" k="L-0211 L-0212"
  caption="The hashtag page: the tag, its photo count and a grid of the top 100. Everything on it is what the storage has to supply. Redrawn from the class board at 01:54.">
  <Desk><HashtagPage /></Desk>
  <Phone><HashtagPage layout="phone" /></Phone>
</Figure>

Two assumptions fix the edges of the problem. There are millions of hashtags. And a data-science team runs a service that generates the top 100 photos for each hashtag and notifies you whenever it does. How it picks them (trending, likes, comments, shares) is their headache. It is a black box, and you don’t build it. [[L-0212]]

A quick brainstorm of what the design will have to deal with: storage; counting, at large volume; inter-service communication, from the post service to the hashtag service; and, more important than all of them, a super-fast response time. For a moment the board also carried “atomicity, partial update”. [[L-0213]]

It is tempting to start maintaining the top-100 array yourself, updating it whenever an uploaded photo gets more popular. You don’t have to care about that. The boundary says the data-science team computes the top photos for you, so don’t assume otherwise. [[L-0217]]

That generalises into a habit. Respect the boundary you have set: a component you declared a black box is not yours to design, so don’t assume or redesign how it works. You are the owner of this page; the top 100 is someone else’s job. It is worth saying twice, because the pull to design the black box anyway is strong. [[L-0218]]

</Section>

<Section id="s7-2" no="7.2" title="Design from the page you render" crumb="7.2 From the page"
  dek="Start from what the screen shows, not from the tables you already have: one document per hashtag."
  meta="About 5 min · class 01:57–02:01">

How would you store this, and where?

It is tempting to start from the data you already have: a tags table with a tag ID and a name, and each photo’s tags stored in the photos table. The photos table is out of the question. Think about the page you have to render. Besides, the photos table has no hashtag column: hashtags are part of the caption. [[L-0214]]

<RuleBox rule="Design the storage ==from the page you must render==." k="L-0215 L-0218 L-0228">

Ask what you need to store in order to render *this* page, and nothing more. Don’t add requirements halfway through, because they need a different design, and don’t redesign the parts you declared a black box. You own the page; design for the page.

<Desk><PageToDoc /></Desk>
<Phone><PageToDoc layout="phone" /></Phone>

</RuleBox>

So the question to ask is: what are you storing in order to render this page? [[L-0215]]

The proposals that lead there are worth following. First, a tag table plus a key-value store; but that is already two databases. Then one store, keyed by the hashtag, holding its metadata and a photo count that goes up whenever a photo with that tag is posted. The total count belongs there because it is exactly what the page renders. [[L-0216]]

The top 100 fits in the same document, as an array. An array of what: photo URLs, or post IDs? Post IDs. Why a photo URL? Post ID 1, post ID 2, and so on. [[L-0219]]

```js
// one document per hashtag: everything the page renders, nothing else
{
  "tag": "sunset",
  "total_photos": 1200000,
  "top_100": [9182736455, 9182736112, /* … 98 more post IDs */]
}
```

Why post IDs? A post ID is the data from which everything else can be derived, the photo URL included: the rule of [chapter 4](#s4) again, store what you can’t derive. And it reduces the space the hashtag document needs. [[L-0221]] Image IDs alone would be ambiguous, because building a photo’s path needs the user too. The post ID solves that problem. [[L-0223]]

There is a method behind asking “why post IDs?” more than once. Think through all the possibilities before you settle. If you don’t consider the alternatives, whatever you thought of first seems optimal, but it might not be. [[L-0220]]

</Section>

<Section id="s7-3" no="7.3" title="Top 100: post IDs or whole posts?" crumb="7.3 IDs or posts"
  dek="Small and always fresh, or one read and fast. The page you promise decides."
  meta="About 6 min · class 02:00–02:06">

The document can hold the post IDs, or it can hold the posts themselves: the actual row, the JSON response the post service would send. [[L-0222]]

<PauseAndThink k="L-0222 L-0224 L-0225 L-0226 L-0230 L-0231 L-0232 L-0233 L-0234"
  q="The hashtag document holds the top 100. Should it hold post IDs, or full copies of the posts?"
  choices={[{ label: 'Post IDs, always' }, { label: 'It depends on what the page shows', correct: true }]}
  right="Right. Space, speed, freshness and consistency trade against each other; the UX decides."
  wrong="Not quite. IDs are a fine default, but they cost a second read on every render. Whole posts win when nothing on the page can go stale.">

It depends. Post IDs are small, cheap to cache and always fresh, but every render makes a second call to the post service. Whole posts render in one read but take more space, and every like or caption edit must be copied into each hashtag document. If the page shows only photos and a tap opens the post, the copy has nothing to go stale and is the fast choice; if it shows live like counts, IDs are safer. Know the pros and cons, and pick by the experience you promise.

</PauseAndThink>

The first way stores only the post IDs. [[L-0229]] Its advantage is that it needs less space, and because the document is small it is very lightweight to cache. [[L-0230]] Every render reads the post table, the source of truth, so the page always shows the latest data. [[L-0232]] The cost is a second read. To render, you first read the hashtag database, then go to the post service (or the post database) for everything the UI needs: likes, comments, shares, the caption, the photo URL. That is another database call on every render. [[L-0231]]

<Figure id="fig-7b" no="Fig 7·b" k="L-0229 L-0224"
  caption="Two ways to hold the top 100: only the post IDs, or a copy of each whole post. Redrawn from the class board at 02:05; its notes on each approach are the rows of the table below.">
  <Desk><TwoWays /></Desk>
  <Phone><TwoWays layout="phone" /></Phone>
</Figure>

The second way copies the actual post information (the ID, the caption, whatever the post table holds) into the hashtag document. That is a denormalized way of storing things. It bloats the database, though with only 100 entries per hashtag that might be just fine. [[L-0224]] It needs more space, but retrieval is very fast: go to this one database, read this one document, return it. There is no extra call to the post DB. This is the advantage most people see first. [[L-0225]]

Its problem is consistency. When a post changes (say it gets more likes), every copy of it in every hashtag document has to be updated, and that can become a pain point. [[L-0233]] MongoDB’s data-modelling guide makes the same trade explicit: duplicating data removes the need for joins on reads, but “if the duplicated data is updated often, using a reference … may be a better approach” <Cite href="https://www.mongodb.com/docs/manual/data-modeling/concepts/embedding-vs-references/">mongodb.com</Cite>.

Whether that pain is real depends on what you promise. You might not show like and comment counts on the hashtag page at all: just the list of photos, and tapping one opens the post page. That is very much possible, and then the simple denormalized copy works without any worry about consistency. [[L-0234]]

There is no one way to build this system. Which option you pick depends on the experience and the guarantees (the SLAs) you give your users, so know the critical pros and cons of each. [[L-0226]]

One idea raised in class: Instagram can show all the photos for a hashtag, not only a top 100. True, and out of scope: this design does the top 100. [[L-0227]] Don’t add new requirements to a system halfway through designing it, because they need a different design. Stick to the constraints you stated. [[L-0228]]

<Section id="s7-4" no="7.4" title="One document, one read: and how big is it?" crumb="7.4 One read, and size"
  dek="Why the top 100 is copied into the hashtag database, and the arithmetic that says the copies are cheap."
  meta="About 6 min · class 02:18–02:19 and 02:26–02:27; Q&A 03:11–03:16">

Why put the top 100 in the hashtag document at all, when the data-science service already has it?

Because the key requirement is a super-fast response. You want to render this page in one shot, so every piece of information needs to be in one document. If the count came from one service, the top 100 from another and the rest from a third, the response time would grow. On a critical path, do the bare minimum of network I/O. The board summed it up as one request, `GET /hashtag/<tag>`, answered in a single response that is pre-computed and pre-evaluated: the core of the system. [[L-0257]]

That is why the top 100 photos are stored in the hashtag database itself, instead of calling the data-science service at read time. The popularity service may well keep the top 100 in its own database; the hashtag service still copies the data, formats and structures it its own way, and stores it in its own database, to guarantee a fast response when someone opens the page. [[L-0258]] How the top 100 reaches the hashtag service is part of the whole design, in [9.1](#s9-1).

Should old hashtags be garbage-collected? Random junk tags keep piling up, and one idea raised in class was a TTL of seven or eight days. You typically wouldn’t delete them. If a hashtag’s data is deleted and the tag later grows popular, its old data is gone; and each document is small anyway. [[L-0342]]

How small? Work it out. A hashtag of about 32 characters is 32 bytes. The total count is an integer, 4 bytes. A hundred post IDs at 4 bytes each are 400 bytes. That makes 436 bytes per document; round it to 512 bytes, half a KB. Two hashtags are 1 KB, and 2,000 hashtags are 1 MB. [[L-0343]] With 64-bit post IDs, the size of a `BIGINT` <Cite href="https://dev.mysql.com/doc/refman/8.4/en/integer-types.html">dev.mysql.com</Cite> and of the IDs Instagram mints (Lecture 6), the same sum is 32 + 4 + 100 × 8 ≈ 836 bytes: about 1 KB per hashtag document.

```js
// one hashtag document
//   tag            ~32 characters            32 B
//   total_photos   4-byte integer             4 B
//   top_100        100 post IDs × 4 B       400 B
//                                           436 B  ≈ 512 B (half a KB)
//   with 64-bit IDs: 32 + 4 + 100 × 8 B  ≈  836 B  ≈ 1 KB
//
// 2 documents ≈ 1 KB      2,000 documents ≈ 1 MB
// 10^9 documents × 512 B = 5.12 × 10^11 B ≈ 500 GB
```

One extrapolation offered in class went further: even a billion hashtags would come to about half a gig, which should be fine. (The reply was a joke: then show that number to your investors and ask for more money.) [[L-0344]]

<SourceNote href="https://www.nist.gov/pml/owm/metric-si-prefixes" k="L-0344">

A billion half-KB documents is 10<sup>9</sup> × 512 B, about 5 × 10<sup>11</sup> B: roughly 500 GB, half a terabyte, not half a gigabyte. The last line of the comment block above is the check.

</SourceNote>

Which is exactly the lesson: as an engineer, do the calculation. The jumps from a thousand to a million, and from a million to a billion, are very large, yet they are easy to treat as nothing. [[L-0345]]

What if a hashtag needed a million popular images instead of 100? Going from the top 100 to the top 1 million scales the requirement by a thousand X. [[L-0347]]

<SourceNote href="https://www.nist.gov/pml/owm/metric-si-prefixes" k="L-0347">

From the top 100 to the top 1 million is 10<sup>6</sup> ÷ 10<sup>2</sup> = 10<sup>4</sup>: a 10,000× jump, not 1,000×.

</SourceNote>

One proposal: keep the first page in the hashtag document, and put the rest in a paginated store (say, a linked list behind the same store), served only when someone scrolls that far, which is rare. [[L-0348]] Don’t store the million inside the document: nobody will ever scroll through them all, so keep just the first page there. [[L-0349]]

Because you design the storage from the page you must render, and this page needs one hashtag’s tag, photo count and top 100, fast. The photos table isn’t shaped like that page, and it doesn’t even have a hashtag column: hashtags are part of the caption. So you store one document per hashtag holding exactly what the page shows.

Post IDs. Every render reads the posts from the source of truth, so the like counts are always the latest. You give up the one-read render: each page view is a second call, to the post service, for likes, comments, caption and URL. Whole posts would render in one read, but every new like would have to be copied into every hashtag document that holds the post.
