Someone posts a sunset captioned `#sunset #sun #nature`. Three hashtag documents must each gain one photo, and millions of posts arrive like this every day.

Adding one to a number sounds like the easiest part of the design. It is the part with the hidden components.

</Section>

<Section id="s8-1" no="8.1" title="The count doesn’t need to be real time" crumb="8.1 Not real time"
  dek="Take the update out of the request, read posts off Kafka, and add them up in memory before writing."
  meta="About 2 min · class 02:06–02:08">

Every hashtag has an entry in the store, and its total photo count has to go up every time someone posts a photo with that hashtag: `count++`. [[L-0235]]

One idea raised in class: the count doesn’t need to be real time, so the updates can be applied in batches. <ForwardChip label="from" when="Lecture 2" lec="lec01" sec="s3-1" k="L-0236">whatever doesn’t need real time shouldn’t be real time</ForwardChip> [[L-0236]]

Batches of what, read from where? The post service, where the post is made, pushes the post to Kafka [[L-0237]]: the same topic [6.1](#s6-1) drew for search, notifications and analytics.

So the first sketch is a consumer on that topic. It extracts the hashtags from each post, holds the posts in memory for a while, and then commits aggregated counts to the database. In a batch of 1,000 posts it might see 10 with hashtag A, 10 with hashtag B and 20 with hashtag C: three writes instead of forty. [[L-0238]]

At Instagram’s volume there is more than one consumer, each reading its own share of the topic’s partitions. Which posts end up on which consumer depends on one choice: the topic’s partition key.

</Section>

<Section id="s8-2" no="8.2" title="Which partition key?" crumb="8.2 Partition key"
  dek="The post topic is keyed by user. Counting needs every post of a hashtag in one place. Those two don’t fit."
  meta="About 6 min · class 02:08–02:11; Q&A 02:50–02:51">

What would be the partitioning key of this Kafka topic?

A first doubt is that hashtag makes a poor key because there are so many hashtags. The number of values is not the problem. A key just passes through the hash function, which picks one partition. [[L-0239]] Partitioning by hashtag does not mean one partition per hashtag. It is hash-based partitioning, so three partitions can hold millions of hashtags. (The class called this “week two”; on this site it is Lecture 2.) <ForwardChip label="from" when="Lecture 2" lec="lec01" sec="s3-6" k="L-0251">topics, partitions and keys</ForwardChip> [[L-0251]]

The same goes for user IDs. Partitioning by user ID doesn’t mean a partition per user. It is one topic with many partitions: say 1,000 partitions for 1 million users, each partition handling about 1,000 users. [[L-0310]]

<PauseAndThink k="L-0239 L-0240 L-0241 L-0242 L-0244 L-0249 L-0251"
  q="Counting needs every <code>#sunset</code> post on one server. The post topic is keyed by <code>user_id</code>. Should you just change its key to the hashtag?"
  choices={[{ label: 'No: the post topic can’t be keyed by hashtag', correct: true }, { label: 'Yes: then each hashtag lands on one partition' }]}
  right="Right. A post with three hashtags has three keys, and the topic belongs to everyone."
  wrong="Not quite. Hashing copes with millions of hashtags; what it can’t do is give one post three keys or re-key a topic other teams depend on.">

No, for two reasons, and neither is “there are too many hashtags” (hashing maps millions of keys onto a few partitions). First, one post carries several hashtags, so it has no single key. Second, search, notifications and analytics already read this topic; you can’t change it for them, and writing to a second Kafka from the post service brings back the dual-write problem. So you add an adapter: extract the hashtags and re-publish one event per hashtag to a topic keyed by hashtag ([8.3](#s8-3)).

</PauseAndThink>

The real problems with hashtag as the key of the post topic are two. First, a post you publish carries several hashtags, so a post has no single hashtag to be keyed by. [[L-0240]] Second, the counting consumer has to read the topic the post service already publishes every post to. Otherwise the post service has to write to two different Kafkas, and the distributed-consistency problem creeps in. <ForwardChip label="from" when="Lecture 2" lec="lec01" sec="s3-4" k="L-0241">two writes, one crash</ForwardChip> [[L-0241]]

So the post topic is partitioned by user ID or post ID. Say user ID: all of a user’s posts go to one partition. [[L-0242]]

But for batching to work, all the posts of a particular hashtag have to come to one server. Otherwise you cannot batch efficiently. [[L-0243]] (Each server can still sum its own batch per hashtag, so a hot tag spread over k servers costs about k writes per batch interval rather than one per post. Partitioning by hashtag makes the aggregation complete, and gives each counter a single writer, which avoids contention on hot rows. <Cite href="https://kafka.apache.org/43/streams/developer-guide/dsl-api/">kafka.apache.org</Cite>)

Picture three `#sunset` posts from three users. They sit on three partitions and reach three different servers. Each server holds one `#sunset`, so there is nothing to batch: each writes one at a time, and the database load doesn’t go down at all. The topic has to be partitioned by user ID, but the counting has to be batched by hashtag. The notes write the challenge down plainly: the `POST_PUBLISH` topic is partitioned by `post_id` or `user_id`. [[L-0244]]

<Section id="s8-3" no="8.3" title="The adapter: re-partition by hashtag" crumb="8.3 The adapter"
  dek="Leave the post topic alone. Read it, split each post into one event per hashtag, and publish those on a topic keyed by hashtag."
  meta="About 9 min · class 02:11–02:17 and 02:23–02:25">

Post 31 is published with three hashtags: `#sunset`, `#sun` and `#nature`. The topic is partitioned by user ID. How should post 31 be routed? [[L-0247]]

One idea comes up first: Redis Pub/Sub, with a channel for every hashtag. It doesn’t work. There are millions and millions of hashtags; each one cannot be a channel, and you would be overkilling the infrastructure. [[L-0245]] (The rejection is right, but mostly for the next reason. The cost argument is overstated: Redis channels aren’t provisioned resources, and `PUBLISH` costs O(N+M), where N is the number of clients subscribed to the channel and M the number of subscribed patterns, so millions of channel names aren’t expensive in themselves. The real problems are at-most-once delivery and push-based flow control, which [8.5](#s8-5) takes apart. <Cite href="https://redis.io/docs/latest/develop/pubsub/">redis.io</Cite>)

And what if that Redis goes down? Then there is data loss, because Redis Pub/Sub doesn’t persist anything: it is real-time Pub/Sub. [[L-0246]] (Precisely: the messages in flight are lost, because Pub/Sub stores none. Redis *Streams*, unlike Pub/Sub, persist messages and support at-least-once delivery with consumer groups, so they are the Redis option when messages must survive a subscriber being down. <Cite href="https://redis.io/docs/latest/develop/pubsub/">redis.io</Cite>)

The proposal that cracks it: let the consumers of the user-ID topic parse each post’s hashtags and write them into another Kafka, partitioned by hashtag. Each hashtag is funnelled to one place, much as a search index works. That is exactly the point. [[L-0248]]

<AnimationClip clip="l09-hashtag-repartition" no="Clip 8·1" k="L-0247 L-0249 L-0250"
  lead="Post 31 carries three hashtags. How many messages does it become, and on how many counting servers can #sunset land?"
  caption="Keyed by user, #sunset is spread over three servers that write one at a time. An extractor re-publishes one event per hashtag on a topic keyed by hashtag, so one server batches it: count += 3." />

That re-keying step is the **adapter**. Consume the post messages partitioned by user ID, re-ingest them into another Kafka partitioned by hashtag, and process them there. A hashtag extractor reads the caption, extracts the hashtags and writes one message per hashtag into the new topic. For batching and counting to work you need an event per hashtag: a post with 8 hashtags becomes 8 events. [[L-0249]]

The full counting path, then: several hashtag-extractor consumers read the user-ID topic and write one message per hashtag to the hashtag-partitioned topic. The counting service’s workers consume that topic, batch, and update the counts with `count += n`, where n depends on the batch, instead of `count++` for every post. [[L-0250]]

  caption="The adapter. Redrawn from the class notes at 02:34, with the printed “Image Service” corrected to post svc.">
  <Desk><Adapter /></Desk>
  <Phone><Adapter layout="phone" /></Phone>
</Figure>

Stated as a write flow: whenever a post is published, the post service pushes a message to Kafka. That one message is consumed by the hashtag extractor, which extracts the hashtags from the caption and, if there are n of them, creates n entries in another topic, `POST_HASHTAG`, partitioned by hashtag. (The printed notes label the first box “Image Service”; the flow starts at the post service, as was corrected on the board.) [[L-0267]]

That second topic can live in the same Kafka cluster: it is just another topic. Keeping it separate is about separation of concerns. Each entry is a (hashtag, post) tuple, `<#sunset, post_1729>`, and the notes call the step repartitioning and reindexing. [[L-0269]]

This is a standard adapter pattern, and you only find it by going into the granular details of the implementation. The first instinct is to partition the post topic by hashtag. You can’t: search, analytics and notifications already consume that topic and depend on it. So you add an adapter, two Kafkas joined by a simple processor that only re-partitions the messages. It is a very common practice. [[L-0254]] (“Adapter” is the lecture’s label: the classic Adapter pattern converts one interface into another, and stream frameworks call this step re-keying or repartitioning. Kafka Streams has it built in: `groupBy`, which picks a new key before aggregating, “always causes data re-partitioning”. <Cite href="https://kafka.apache.org/43/streams/developer-guide/dsl-api/">kafka.apache.org</Cite>)
