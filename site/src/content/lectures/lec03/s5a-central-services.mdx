<Section id="s5" no="5" title="Central services: Amazon and Flickr" crumb="5 Central services"
  dek="Two ways to make one place responsible for IDs without making every request wait on it: Amazon hands out ranges, Flickr turns MySQL’s auto-increment into a ticket machine."
  meta="About 36 min · class 00:59–01:36, Q&A 02:21–02:24">

Amazon’s order service and its payment service both need an ID on every request. Each runs on many servers, and the orders database is sharded, so no single database’s auto-increment can be trusted ([§1.2](#s1-2)).

[Chapter 3](#s3-6) showed that one ID server gives clean IDs and a network call on every request. This chapter is two real designs that keep the one-place idea and get rid of most of that cost.

</Section>

<Section id="s5-1" no="5.1" title="How to read someone else’s design" crumb="5.1 Reading a design"
  dek="Before four company designs, one way to read them: for what they gain, not for what you would have done instead."
  meta="About 2 min · class 00:51, 01:02, 01:20–01:21">

Everything so far was the core idea behind ID generation, built from scratch. The company designs that follow each show what one real choice gains and what it gives up. [[L-0097]]

Read them for the beauty of the design, and take their good parts. It is easy to list faults, such as “a MySQL query for every ID sounds slow”, and it is fine to see them, but it was their decision, made with their constraints. [[L-0160]] It is like neighbours fighting: you may think both are wrong, but it’s their life. Let them do it, and pick the best parts. [[L-0161]]

There are videos about the first design, Amazon’s; this page goes into how to implement it. If you have done the airline check-in from Lecture 3, it is a piece of cake. [[L-0108]]

</Section>

<Section id="s5-2" no="5.2" title="Amazon: hand out ranges, not IDs" crumb="5.2 Amazon’s ranges"
  dek="One row per service, one locked update per batch, and a server that asks again only when its range runs low."
  meta="About 8 min · class 00:59–01:08">

Amazon’s team explained this design in a public tech talk, and the account here is first-hand: it comes from sitting right next to the team that built the service, at their tech talks and in questions put to them. [[L-0101]] In that account, Amazon assigns a globally unique ID to every order placed. The system has high throughput, and the same ID service also hands out IDs to many other internal services, orders being just one of them, so the IDs had to be unique. [[L-0102]]

The design leans on **batching**, which the lecture counts among the big levers for performance. [[L-0103]] It is also small: you can write the whole service in about 150 lines of Python, “not even exaggerated”. Scaling it means handling a few more cases here and there, nothing difficult. Write it yourself. [[L-0104]]

The architecture, as described: plain API servers exposing ID-generation endpoints, put behind a load balancer, with a database behind them. [[L-0105]] In the lecture’s telling, that database is a classic relational one, with no fancy non-relational store; in its view there is no reason to complicate things. [[L-0106]]

The core idea is the one you used in [§2.6](#s2-6), where the counter went to disk once every thousand IDs instead of on every ID. Here, instead of calling the remote ID service every time a server needs an ID, the server gets a **batch** of IDs in one call. [[L-0107]]

Say two services use it, orders and payments, each on its own set of servers. Neither cares about monotonicity. They need uniqueness, as simple as that. [[L-0109]] The ID service’s table holds one row per service, one for orders and one for payments, so each service’s IDs come from its own counter. [[L-0118]]

Walk through it. When an orders server boots, it has no IDs to work with, so it asks the ID service: “I just booted up. Can you give me 500 IDs?” The request reaches an API server, which fires one SQL query on the table: the stored value for orders goes from 0 to 500, and the range 0–500 goes back to the server. [[L-0110]]

Only the start and the end go back, not 500 individual IDs. They are just integers, so there is no reason to send that much data over the network. [[L-0111]]

When orders server 2 boots and asks for 500 more, the stored value goes from 500 to 1000, and server 2 gets [500, 1000). Server 1 holds 0 to 500, server 2 holds 500 to 1000. The payments row moves on its own: a payments server that asks for 2000 gets [0, 2000). [[L-0113]]

A server doesn’t ask again for every ID. It loads a range once and refills when it is about to run out: with 490 of its 500 used, it asks for another 500 and might get 3000–3500, because other servers took the ranges in between. Then it carries on from that range. [[L-0119]]

The hand-out itself must be atomic, so two servers asking at the same moment can never get the same range. Select the current value `FOR UPDATE` inside a transaction, then update it to the new value. [[L-0112]] If that looks familiar, it should: it is Lecture 3’s airline check-in transaction, Ctrl-C, Ctrl-V. Read in a transaction, atomically add however many IDs were requested, and send back the old value and the new one as the range. [[L-0121]]

```sql
-- id_ranges(service, counter):
-- one row per service
BEGIN;
SELECT counter FROM id_ranges
  WHERE service = 'orders'
  FOR UPDATE;   -- say 500, now locked
UPDATE id_ranges
  SET counter = counter + 500
  WHERE service = 'orders';
COMMIT;
-- reply [500, 1000): old and new value
```

<Section id="s5-3" no="5.3" title="What ranges buy, and what they cost" crumb="5.3 Ranges: gains and costs"
  dek="The orders database is free to shard, and the ID service sees one tiny update per batch. A crash throws a range away, and that is fine."
  meta="About 6 min · class 01:04–01:11">

Once a server holds a range, it stops thinking about IDs. Orders arrive from the outside world, the server pulls the next ID from the range in its memory, and writes the order into its own orders database without worrying about anything else. Those are globally unique IDs, and a service can prefix them if its conventions call for it. [[L-0114]]

That is the real gain: the central ID service **decouples** the system. ID generation is separate from the orders database, so the orders database can be sharded and scaled horizontally, with every shard accepting writes, and no server calls the ID service for each ID. [[L-0115]]

The 500 in the walkthrough is only a small example. By the same account, real batches are 10,000, 50,000 or 100,000 IDs, depending on the service’s throughput. [[L-0116]]

The cost is on a crash. If a server gets a range and then crashes, that range is gone. So batch size is a trade-off: too small, and servers make network calls too often; too large, and a crash throws away a big range. Each service tunes the maximum batch size to its own throughput. [[L-0117]]

And there is no order across servers. Server 1 may be issuing 3,042 while server 2 issues 612. The design hands out unique IDs in batches, and that’s all it promises. [[L-0120]]

It is really simple to build. The database is the single source of truth on a single server, so it never has to gossip with anyone, and it scales easily because each request is one tiny update, not even a full read. [[L-0122]]

One database is also one box that can fail. Flickr’s design in [section 5.7](#s5-7) runs two for exactly that reason. [[L-0175 L-0176]]

A tempting fix for the wasted ranges: keep track, in a database, of how much of its range each server has used, so that after a restart it resumes where it stopped. With batches of 10,000, a server that used 100 and crashed loses 9,900 IDs forever. [[L-0123]]

In fact it isn’t worth it. Keeping track of every single used ID is a massive overhead, and a big-integer (2^64) ID space will never run out, not even at Amazon’s scale. [[L-0124]] Think about practicality at every step. Nobody cares about using every single integer; it is just a few ranges of numbers lost. [[L-0125]]

<MarginNote title="Number sense" why="skip if numbers bore you" k="L-0126 L-0127">

We tend to underestimate numbers. A million and a billion are both huge, and the difference between them, 999 million, is itself almost a billion. [[L-0126]] A four-byte integer gives about 4 billion IDs: imagine 4 billion Amazon orders. If even that runs out, move to 64 bits, a range big enough that you never worry about it. [[L-0127]] (About 4.29 billion is the unsigned figure; a signed 32-bit INT stops at about 2.1 billion <Cite href="https://dev.mysql.com/doc/refman/8.4/en/integer-types.html">dev.mysql.com</Cite>.)

</MarginNote>

</Section>

<Section id="s5-4" no="5.4" title="Ranges from a queue?" crumb="5.4 A queue of ranges"
  dek="The ranges don’t have to come from a database. What they need is one atomic step, wherever it lives."
  meta="About 2 min · class Q&A 02:22–02:24">

Does the hand-out have to be an API call to a database? One idea: let the ID generator keep producing ranges and push them into a queue, and let the servers read from the queue. That works, with one condition: servers read a batch of IDs at a time, not one ID at a time. [[L-0302]]

<MarginNote title="Variants: a queue, Redis, DynamoDB" why="skip unless SQL isn’t your store" k="L-0302 L-0303">

Reading ranges from a queue moves the atomicity to the queue’s reads. The core property you need is an atomic read of the next range, and the database, a queue, DynamoDB or Redis can each give it. [[L-0303]]

<SourceNote href="https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/standard-queues-at-least-once-delivery.html" k="L-0303">

Any store with an atomic increment-and-return can hand out ranges: a SQL transaction, a DynamoDB atomic counter, Redis `INCRBY`. A queue needs more care. SQS standard queues deliver at least once, so a range can occasionally be delivered twice, and a redelivered range would produce duplicate IDs unless consumers deduplicate. A DynamoDB counter fails the safe way: a retried increment can over-count, which only wastes a range <Cite href="https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/WorkingWithItems.html">aws.amazon.com</Cite>.

</SourceNote>

</MarginNote>

The lesson generalizes. Focus on the core property you need; if any system out there gives it to you, that system is good enough. [[L-0304]]

<RuleBox rule="Find the ==core property== you need, here an atomic increment, and use any system that gives it." k="L-0304">

Amazon gets it from a `SELECT … FOR UPDATE` transaction, Flickr (next) from an upsert, and a queue, Redis or DynamoDB would do too, as long as no range is ever handed out twice.
