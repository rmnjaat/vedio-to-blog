<Section id="s7" no="7" title="Instagram: Snowflake inside the database" crumb="7 Instagram"
  dek="Same idea, different home. Instagram packed time, shard and sequence into 64 bits inside a database function, so no API server knows anything about IDs."
  meta="About 18 min · class 02:03–02:18, Q&A 02:15–02:25">

Instagram wants Twitter-style IDs: 64 bits, time on the left, made without asking anyone. But it refuses to run a new service for them, and its database is already split into thousands of shards. Snowflake put the ID logic in the API servers ([§6.3](#s6-3)). Instagram found a third home for it.

Every part is one you have already built: time on the left ([§3.3](#s3-3)), a small integer ([§4](#s4)), a static counter ([§2.3](#s2-3)) and a custom epoch ([§6.6](#s6-6)).

</Section>

<Section id="s7-1" no="7.1" title="Three requirements" crumb="7.1 Requirements"
  dek="Sortable by time, 64 bits, and no new service."
  meta="About 3 min · class 02:03–02:05">

In the lecture’s view, Instagram’s early ID scheme is a brilliant piece of optimization. Instagram described it in its engineering blog <Cite href="https://instagram-engineering.tumblr.com/post/10853187575/sharding-ids-at-instagram">instagram-engineering</Cite>, and it shows how much someone with decent, not even deep, knowledge of databases can get out of one. [[L-0255]]

Instagram wanted Snowflake’s kind of ID, but it makes the ID inside the database, while the row is being inserted. The API servers have no Snowflake logic at all. (Strictly, Instagram didn’t run Twitter’s code. It built its own Snowflake-like 64-bit layout as a function written in PL/pgSQL, Postgres’s procedural language <Cite href="https://www.depesz.com/2015/10/30/is-c-faster-for-instagram-style-id-generation/">depesz.com</Cite>.) [[L-0256]]

So the two differ in where the ID is born. Twitter makes it in the API servers; Instagram makes it in the database. [[L-0257]]

Instagram’s requirements, as on the board:

1. **IDs sortable by time.** The use case is Twitter’s: process the most recent items, find trending hashtags, push new posts into users’ feeds. Batch jobs over recent data, and pagination ([§8](#s8)), both need it. [[L-0258]]
2. **64 bits**, so the IDs are efficient on indexes. [§4](#s4-2) showed why every index pays for the size of the ID. [[L-0259]]
3. **No new service** to build and run. [[L-0260]]

</Section>

<Section id="s7-2" no="7.2" title="41 | 13 | 10" crumb="7.2 41 | 13 | 10"
  dek="Instagram keeps Snowflake’s time field and swaps the machine and counter for a shard and a sequence."
  meta="About 2 min · class 02:05">

Instagram tweaked Snowflake’s layout. The first 41 bits are milliseconds counted from a custom epoch in 2011, which gives a massive range to play with ([§6.6](#s6-6) worked out why). The epoch constant in Instagram’s published function, 1314220021721, is 24 August 2011, not the 1 January 2011 written on the board <Cite href="https://www.depesz.com/2015/10/30/is-c-faster-for-instagram-style-id-generation/">depesz.com</Cite>. [[L-0261]]

The next 13 bits are the **DB shard ID**. Instagram’s database was already sharded; [§7.3](#s7-3) shows which shards these are. [[L-0262]]

The last 10 bits are a **per-shard sequence number**: a static counter, one per shard, just like the counter of [§2.3](#s2-3). [[L-0263]]

<Section id="s7-3" no="7.3" title="Logical shards on physical servers" crumb="7.3 Logical shards"
  dek="Thousands of small databases on a handful of machines: a migration costs more, and moving load gets easy."
  meta="About 5 min · class 02:05–02:09">

Before the function, the shards it numbers.

<MarginNote title="Watch first" why="skip if you have seen the sharding video" k="L-0265">

The video on sharding and partitioning in this week’s readings, on the instructor’s YouTube channel, is the background for this section. What follows is a glimpse of it.

</MarginNote>

Instagram runs **Postgres**. [[L-0266]]

It splits its data into many **logical shards**, also called partitions, placed on far fewer **physical** database servers. A physical server is the actual machine your database runs on: the database server you spin up. Inside it, each database you create with `CREATE DATABASE` is a logical partition. [[L-0267]] In Instagram’s own Postgres setup each logical shard was a schema, such as `insta5`, holding the same set of tables, and several thousand of them were mapped in code to far fewer physical servers <Cite href="https://instagram-engineering.tumblr.com/post/10853187575/sharding-ids-at-instagram">instagram-engineering</Cite>. [[L-0267]]

There are thousands of logical shards, at most 2^13 = 8,192, since that is all 13 bits can name, on a few physical servers, say 10 or 15. [[L-0268]]

<Figure id="fig-7b" no="Fig 7·b" k="L-0267 L-0268"
  caption="One physical server holding several logical shards, each a database of its own with the same tables. Thousands of them on “say, 10 or 15” servers; Instagram’s post says only “far fewer” physical servers. Redrawn from the class board at 02:05.">
  <Desk><LogicalShards /></Desk>
  <Phone><LogicalShards layout="phone" /></Phone>
</Figure>

On one server you run `CREATE DATABASE insta1`, `CREATE DATABASE insta2`, `CREATE DATABASE insta3`, and so on; another server holds, say, `insta2000` and `insta5000`. [[L-0269]] Every logical shard has exactly the same tables with exactly the same schemas. Only the data differs. [[L-0270]]

That has a cost. A migration, such as adding a column, must run on every logical database on every physical server: thousands of times, about 8,000. [[L-0271]]

And it has a benefit. When one server runs hot, a small logical shard can be dumped with the SQL dump commands and loaded onto another server, and the load is balanced. [[L-0272]]

<Figure id="fig-7c" no="Fig 7·c" k="L-0272 L-0274 L-0275"
  caption="Moving a hot shard. (a) One logical shard on server 1 runs hot, and a new server 2 stands empty. (b) The shard is dumped and loaded onto server 2 whole, with no row-by-row picking.">
  <Desk><MoveHotShard /></Desk>
  <Phone><MoveHotShard layout="phone" /></Phone>
</Figure>

So scaling the database horizontally is easy: spin up a new physical server, take a logical shard and move it there. [[L-0274]] Without logical shards you would have to go through every row, extract the rows that need to move, and move them. A separate logical shard is dumped quickly and loaded quickly, which makes moving it easy. [[L-0275]]

<ForwardChip block when="week 5 · Lecture 9" k="L-0273">logical partitions and moving them between servers, once more and in depth</ForwardChip>

That is Instagram’s structure: a handful of database servers (“say, 10 or 15”; the exact count could not be checked, and Instagram’s post says only “far fewer” than the logical shards <Cite href="https://instagram-engineering.tumblr.com/post/10853187575/sharding-ids-at-instagram">instagram-engineering</Cite>), together holding thousands of logical databases. The **DB shard ID** inside an Instagram ID is the number of one of those logical shards, at most 2^13 = 8,192, followed by the per-shard sequence number. (Instagram’s physical servers run Postgres, though the same picture holds for MySQL servers <Cite href="https://www.depesz.com/2015/10/30/is-c-faster-for-instagram-style-id-generation/">depesz.com</Cite>.) [[L-0276]]

<Section id="s7-4" no="7.4" title="A function as the column default" crumb="7.4 next_id()"
  dek="Insert a photo without an ID, and the database computes a Snowflake-style ID for it."
  meta="About 6 min · class 02:09–02:15">

The brilliant move uses **stored procedures** (the class called it PL/SQL), the thing most of us neglected in college and assumed we would never use. Instagram’s is a function written in PL/pgSQL, Postgres’s procedural language ([§7.1](#s7-1)). [[L-0277]]

In each logical database, say `insta5`, the photos table’s `id` column is declared `bigint not null` with `default insta5.next_id()`. When a photo is inserted without an ID, the database invokes that function, and whatever it returns is used as the ID. [[L-0278]]

Each logical database has its own `next_id`, with its own shard ID hard-coded inside: 5 for `insta5`. So the function has to be created in every single database. [[L-0279]]

Here is the board’s code, in the order Postgres needs it (the board showed the table first):

```sql
-- PL/pgSQL. The board wrote CREATE DATABASE insta5; in Postgres each logical shard is a schema.
CREATE SCHEMA insta5;
CREATE SEQUENCE insta5.table_id_seq;

CREATE OR REPLACE FUNCTION insta5.next_id(OUT result bigint) AS $$
DECLARE
    epoch    bigint := 1314220021721;   -- Instagram's custom epoch, in ms
    seq_id   bigint;
    now_ms   bigint;
    shard_id int    := 5;               -- hard-coded: this is shard 5
BEGIN
    SELECT nextval('insta5.table_id_seq') % 1024 INTO seq_id;
    -- left blank on the board; this page's completion:
    SELECT FLOOR(EXTRACT(EPOCH FROM clock_timestamp()) * 1000) INTO now_ms;
    result := (now_ms - epoch) << 23;
    result := result | (shard_id << 10);
    result := result | (seq_id);
END;
$$ LANGUAGE plpgsql;

CREATE TABLE insta5.photos (
    id bigint NOT NULL DEFAULT insta5.next_id(),
    caption text
    -- … the other columns of the photos table
);
```

`insta5.next_id` returns a big integer, `result`, and declares four variables: `epoch`, `seq_id`, `now_ms` and `shard_id`, which is 5. `epoch` is Instagram’s custom epoch in milliseconds: 1314220021721 is 24 August 2011, not 1 January <Cite href="https://www.depesz.com/2015/10/30/is-c-faster-for-instagram-style-id-generation/">depesz.com</Cite>. [[L-0280]]

First, `seq_id` gets `nextval('insta5.table_id_seq')`, taken `% 1024`. The sequence increments atomically, however many transactions come in at once, and `% 1024` (2^10) cuts it down to the 10-bit per-shard sequence number. [[L-0282]]

Then `result := (now_ms - epoch) << 23`. `now_ms` is the database’s current epoch millisecond; minus the custom epoch, it is the milliseconds since 24 August 2011, and shifting left by 23 (13 + 10, the bits still to fill) puts them in the top 41 bits. [[L-0283]]

Last, `result := result | (shard_id << 10)` sets the next 13 bits to 5, the shard ID, and `result := result | seq_id` fills the last 10. [[L-0284]]

Every time a photo is inserted without an ID, the database invokes this function. It builds the ID and returns it as `result`, and that is what gets inserted. Instagram does Snowflake IDs in a database stored procedure. [[L-0285]]

That is why it is so efficient: you don’t need any ID logic on the API side, because it is all offloaded to the database. You do a normal insert, as you always would, without passing an ID. Where the database would have auto-incremented, it now invokes the function. [[L-0287]]

<RuleBox rule="Put the ID ==where the data is==: no ID logic on the API side." k="L-0287">

Do a normal insert without an ID, and let the database call the function where it would have auto-incremented. The API tier stays a plain API tier: no counter, no machine ID, no service to call.

Implement this yourself; don’t only read about it. Start your favourite database, MySQL, Postgres, anything, and write it. It is very easy, and the previous batch was amused at how easy it was the first time they tried. (On MySQL, which doesn’t allow a stored function as a column default, a `BEFORE INSERT` trigger can set the ID instead <Cite href="https://dev.mysql.com/doc/refman/8.4/en/data-type-defaults.html">dev.mysql.com</Cite>.) [[L-0286]]

Instagram still does this, says the lecture: its posts still carry integer IDs generated exactly this way. [[L-0288]]

<Section id="s7-5" no="7.5" title="A sequence is the static counter" crumb="7.5 Sequences"
  dek="What table_id_seq is, what it isn’t, and why it has to live on disk."
  meta="About 4 min · class 02:12–02:13, Q&A 02:15–02:16, 02:19–02:21 and 02:24–02:25">

Every database has a **sequencer**; it is how auto-increment IDs are made. It is a sequence that increments atomically and returns the next number each time it is invoked. `nextval` is that call. [[L-0281]] That is exactly PostgreSQL’s model. MySQL has no separate sequence objects; InnoDB keeps a per-table auto-increment counter instead, though the atomic-counter idea is the same <Cite href="https://dev.mysql.com/doc/refman/8.4/en/innodb-auto-increment-handling.html">dev.mysql.com</Cite>. [[L-0281]]

It is tempting to read `insta5.table_id_seq` as a column of the photos table. [[L-0289]] It isn’t one. It is a sequence object. When you create an ID column with auto-increment, the database quietly creates a sequence behind it with a unique name, and every new ID is a `nextval` on it. Instagram has no auto-increment column, so it creates its own sequence explicitly and uses it in place of the default one. `table_id_seq` is the name Instagram gave it, but you can name a sequence anything. In PostgreSQL, `serial` is literally shorthand for this: a `CREATE SEQUENCE` named `tablename_colname_seq`, plus a `NOT NULL` column whose default is `nextval('tablename_colname_seq')` <Cite href="https://www.postgresql.org/docs/current/datatype-numeric.html">postgresql.org</Cite>. [[L-0290]]

Another tempting reading: every table gets a sequence when it is created. [[L-0296]] Only an auto-increment column creates one. Otherwise you create sequences explicitly, with any name, as many as you want, and a table isn’t limited to one auto-incrementing column: you could have three. (That holds in PostgreSQL; MySQL allows only one `AUTO_INCREMENT` column per table <Cite href="https://dev.mysql.com/doc/refman/8.4/en/create-table.html">dev.mysql.com</Cite>.) [[L-0297]]

So the sequencer does exactly what the static counter did in [§2.3](#s2-3): it increments atomically and hands out values, which gives the thread safety the ID needs. Like any PostgreSQL sequence, it never hands a value back, even when the inserting transaction aborts, so sequences have gaps; the docs say they cannot give “gapless” sequences <Cite href="https://www.postgresql.org/docs/current/functions-sequence.html">postgresql.org</Cite>. An ID doesn’t mind a gap. [[L-0298]]

One more tempting idea: keep the sequence in a cache instead of on disk. [[L-0306]] It has to be persistent. If it weren’t, a database reboot would start it from zero, which is [§2.4](#s2-4)’s reboot problem all over again. Leave the optimization to the database, which flushes periodically and so on: just create a sequencer and let it generate values. For example, MySQL writes its auto-increment counter to the redo log every time it changes, so it survives restarts, but after a crash before that log is flushed, a recently allocated value can be handed out again <Cite href="https://dev.mysql.com/doc/refman/8.4/en/innodb-auto-increment-handling.html">dev.mysql.com</Cite>. A PostgreSQL sequence can pre-allocate values per session (`CACHE`), and values a session never used are lost when it ends, leaving holes <Cite href="https://www.postgresql.org/docs/current/sql-createsequence.html">postgresql.org</Cite>. [[L-0307]]

</Section>

<Section id="s7-6" no="7.6" title="What moving it into the database buys" crumb="7.6 What it buys"
  dek="The API tier loses its limit; the ceiling moves to the database."
  meta="About 1 min · class 02:16–02:17">

Notice what changed: Instagram just lifted Snowflake’s logic out of the API servers and put it in the database. True, and that is the point. With the logic in the database there is no limit on API servers: 10,000 of them, or 50,000. The ceilings move to the database instead: at most 2^13 = 8,192 logical shards (about 8,000 databases, a huge number) and 1,024 IDs per shard per millisecond. [[L-0291]]

Twitter, by contrast, is limited to 2^10 = 1,024 API servers because of its 10-bit machine ID. (Strictly, the cap is on Snowflake generator processes; Twitter ran Snowflake as its own service <Cite href="https://github.com/twitter-archive/snowflake/tree/snowflake-2010">github.com</Cite>.) [[L-0292]]

<RecallQuestions>
  <RecallItem k="L-0262 L-0274 L-0276" q="What do Instagram’s 13 middle bits identify, and why couldn’t they be a machine ID?">

The logical shard, one of up to 2^13 = 8,192 small databases, that made the ID. The ID is made inside that shard’s database, by that shard’s own function and sequence, and shards move between physical servers when one runs hot. A machine ID would change with every move; the shard number stays with the data.

  </RecallItem>
  <RecallItem k="L-0279" q="Why does <code>insta5.next_id()</code> need its own copy in every logical database?">

Its shard ID is hard-coded inside it (5 for `insta5`), and it reads its own shard’s sequence. So each logical database needs its own copy, created in every one of the thousands of databases.

  </RecallItem>
  <RecallItem k="L-0307 L-0298" q="Why must the sequence persist, and which earlier problem in this lecture is that?">

A sequence kept only in memory would restart from zero after a database reboot and hand out IDs that were already used. That is the reboot problem of [§2.4](#s2-4), where the in-memory counter went back to 0. The database persists the sequence and optimizes the flushing itself.

  </RecallItem>
</RecallQuestions>
