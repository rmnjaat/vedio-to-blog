A shop’s orders table has outgrown one MySQL server. It now lives on two, both in master mode, so a new order can be written to either. Each server auto-increments on its own: 1, 2, 3, 4 on the left, 1, 2, 3, 4 on the right. Order 3 now means two different orders.

This chapter states the problem that picture raises, shows why the database’s own IDs stop working, and sets the starting point for everything after it: one small function.

<Section id="s1-1" no="1.1" title="What an ID is, and the job" crumb="1.1 The job"
  dek="An ID is whatever makes one thing distinguishable from every other. The job is a function that never repeats itself."
  meta="About 3 min · class 00:00–00:03">

An ID gives uniqueness to something: a row, a document, an object, an event. Anything that lets you pick out exactly one of them is its ID. [[L-0008]]

So the problem is easy to say. Assign a globally unique ID to anything that asks for one. Put as code: write a function that returns something unique every single time it is invoked. [[L-0009]]

<Figure id="fig-1a" max={360} wide={false} no="Fig 1·a" k="L-0087" caption="Two masters, one ID space. Both masters accept writes and neither asks the other, so both count 1, 2, 3, 4 and order 3 exists twice. Redrawn and extended from the class board at 00:45 (D-11), where the two databases were drawn as plain cylinders.">
<TwoMasters />
</Figure>

It sounds trivial, and that is exactly why distributed ID generation is one of the most misunderstood topics around. The usual reflex, roughly, is that auto-increment already solves it and that IDs are no big problem. [[L-0002]]

Most teams never meet the problem until they hit scale. But with how far the internet now reaches, most companies hit that scale sooner than they think, and that is where distributed ID generators come in. [[L-0003]]

There are two more reasons to learn it in depth. The computer science behind the solutions is beautiful: the ways engineers solved this are worth seeing for their own sake. [[L-0004]] And once you understand how IDs are made, you notice side effects of good ID schemes that most people never think about. Chapter 8 is one of them, fast pagination. [[L-0005]]

</Section>

<Section id="s1-2" no="1.2" title="Where the database’s own IDs stop working" crumb="1.2 Database IDs"
  dek="Auto-increment is correct on one machine. Two masters that don’t talk to each other break it."
  meta="About 3 min · class 00:45–00:49">

But MySQL and MongoDB already give every row an ID. Why build anything?

Because of the picture above. Shard the database, or run it multi-master, with two MySQL servers both in master mode and writes landing on either. The two servers don’t talk to each other, so each auto-increments 1, 2, 3, 4 on its own, and the IDs collide. [[L-0087]]

Once your databases run multi-master, you can no longer rely on the IDs they hand out. You need your own ID logic, for example one that includes the machine’s ID, so each entry is unique across all of them. That is where distributed ID generators come in, and you would typically find custom ID logic in any multi-master setup. The company designs in chapters 5 to 7 show it in practice. [[L-0088]]

A single MySQL server never has this problem. Its IDs come out 1, 2, 3, 4, 5, 6 because it is one machine and the ID logic is part of its database engine: one engine owns the counter. [Section 3.7](#s3-7) comes back to exactly this. [[L-0083]]

<PauseAndThink k="L-0087 L-0088 L-0091"

  choices={[{ label: 'Yes: each master hands out its own numbers' }, { label: 'No: both masters issued 1 to 4', correct: true }]}
  right="Right. Both masters count 1, 2, 3, 4 without asking each other, so order 3 exists twice."
  wrong="Each master’s numbers are unique only on that master. Nothing stops the other one handing out the same 3.">

One setting fixes it: step by 2 and start one master at 1, the other at 2, so one issues odd IDs and the other even. It works, with one catch the lecture comes back to: if one master is down for a while, the two sequences drift far apart ([section 5.8](#s5-8)). Flickr runs exactly this ([section 5.7](#s5-7)).

</PauseAndThink>

One fix: let each master auto-increment by the number of masters. With two, one hands out 0, 2, 4 and the other 1, 3, 5, and they never meet. It can be done, with a slight disadvantage the lecture returns to later, and it is exactly what Flickr ships in [section 5.7](#s5-7). [[L-0091]]

</Section>

<Section id="s1-3" no="1.3" title="A function, not a service" crumb="1.3 A function first"
  dek="The reflex answer is a new microservice. Start smaller."
  meta="About 2 min · class 00:03–00:04">

The reflex answer to “we need unique IDs” is “I’ll write an ID microservice.” Many people start there, building a new service for ID generation straight away.

Don’t jump to it. Start with an ID function that is part of your own application logic, called locally on every request. A central ID service is an evolution you reach later. Constraining the problem to one local function is what builds the foundation for everything else in this lecture. [[L-0010]]

<RuleBox rule="Start with ==a function, not a service==." k="L-0010">

Write ID generation as a function in your own business logic, invoked locally per request. A central ID service comes later in the evolution.

<FunctionFirst />

</RuleBox>

The lecture closes on the same point from the other side. In its view, the first instinct for ID generation is a microservice, and good engineers instead look at the problem and its most efficient solution; not every solution needs a new service. [Section 6.7](#s6-7) picks this up after Snowflake. [[L-0241]]

<h3 id="s1-check">Check yourself</h3>

Answer in your head, or out loud, before opening each one.

<RecallQuestions>
  <RecallItem q="Two MySQL masters each accept inserts with AUTO_INCREMENT. Why do IDs collide, and why doesn’t a single MySQL have this problem?">

The two masters don’t talk to each other, so each counts 1, 2, 3, 4 on its own and both hand out the same numbers. A single MySQL is one machine: the counter lives inside its one database engine, so every insert gets the next value from the same place.

  </RecallItem>
  <RecallItem q="Name the one setting change that keeps two masters’ IDs apart. What does it give up?">

Step by the number of masters, with a different start on each: with two, one issues 1, 3, 5 and the other 2, 4, 6. IDs stay unique. What it gives up is order across the two: if one master is down or busier for a while, its numbers fall far behind the other’s.

  </RecallItem>
  <RecallItem q="Why does the lecture start from a local function instead of an ID service?">

A function inside the application, called locally per request, is the simplest thing that can work and the foundation every later design builds on. A central service is an evolution that comes later; reaching for a microservice first skips the question of what the problem actually needs.

  </RecallItem>
</RecallQuestions>

So: one function, called on every request, that must never return the same value twice. Build it.
