Every database hands you IDs for free, until there is more than one database. In this lecture you write the replacement yourself: one small function, `get_id()`, that must never return the same value twice, on any machine, ever. You will break it again and again, and each time the fix is the smallest change that works. Then you watch Amazon, Flickr, Twitter and Instagram answer the same question, and find that each of them runs a version of the function you just built. [[L-0009 L-0088]]

### Where you are

<LectureLink lec="lec01">Lecture 2</LectureLink> scaled a blog’s writes by sharding, and warned that letting several databases accept writes brings conflicts. It also showed `count++` losing an update when two threads run it at once, and the atomic increment that fixes it. <LectureLink lec="lec05">Lecture 3</LectureLink> locked a row with `SELECT … FOR UPDATE` so that 120 passengers could not book one seat, and wrote a key-value store whose `PUT` was a single upsert. <LectureLink lec="lec08">Lecture 5</LectureLink> put a load balancer in front of a fleet, asked of every box what happens when it is the only one and it dies, and ended on exactly the picture above.

All three come back here. This time the thing many machines fight over is a number.

### What you’ll build

**Part 1, `get_id()` from scratch (chapters 1–5).** The function starts as one line. Each chapter adds a condition the last version can’t survive: a second machine, threads, a reboot, a disk that can’t keep up, a need to know which ID came first, and a question about how big an ID may be. [[L-0010]]

**Part 2, four companies (chapters 6–10).** Amazon, Flickr, Twitter and Instagram each needed unique IDs at a scale you can feel. Each design reuses a piece you built in Part 1, and each one makes a different choice about where the ID is born. Along the way, one design turns out to make a common query much cheaper, which nobody planned for. [[L-0005]]

### What you’ll be able to do

- Write an ID generator that stays unique across machines, threads and reboots, without a disk write per ID.
- Say how much order IDs from many machines can promise, and what strict order would cost.
- Work out what an ID’s size does to every index on a table.
- Choose between ranges from a service, ticket databases, a 64-bit time-first layout and an ID made inside the database.
- Page through millions of rows without each page getting slower than the last.

### Before you start

You need primary keys and indexes, threads and an atomic increment, `SELECT … FOR UPDATE`, and a load balancer. A little binary helps: 2^10 = 1,024, and what a left shift does.

Each chapter opens with the ladder of `get_id()` versions so far, with the newest rung shaded. When a “Pause and think” box asks you something, commit to an answer before you open it. And build every version yourself as you go. None of them is fancy, and building them is what makes the reasons stick. [[L-0007]]
