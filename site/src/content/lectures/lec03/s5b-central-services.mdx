<Section id="s5-5" no="5.5" title="Flickr: MySQL as the ticket server" crumb="5.5 Flickr’s ticket server"
  dek="If MySQL already counts, let MySQL be the ID service: a separate database with one table and one row."
  meta="About 7 min · class 01:17–01:23, 01:26–01:27, Q&A 01:32–01:33">

Flickr was the big photo site before Instagram, where a great deal got posted before Instagram took over. [[L-0151]] Flickr launched in February 2004 and was among the most popular sites on the web by 2007, three years before Instagram existed, so think of it as the Instagram of the 2000s <Cite href="https://en.wikipedia.org/wiki/Flickr">wikipedia.org</Cite>.

Its problem was the one from [§1.2](#s1-2), exactly. The database was sharded and ran in multi-master mode, so a write could go anywhere, and auto-increment on every shard would hand out conflicting IDs. To guarantee uniqueness, Flickr needed its own ID generation. [[L-0152]] Its engineering blog also says why not UUIDs: they index badly ([§4.2](#s4-2)). [[L-0153]]

So Flickr built a central **ticket server**, an ID generation service, on top of MySQL. Whoever needs an ID makes a query to MySQL and gets one. [[L-0159]] The idea is disarmingly simple: if MySQL already gives you auto-increment IDs, why can’t MySQL itself be the ID service? It also answers an earlier question: could the database itself be the ID generator? Here it is. [[L-0163]]

It is a separate database. The photos live in the sharded photos database; the ticket database exists only to lend out its auto-increment. [[L-0164]]

<Figure id="fig-5b" no="Fig 5·b" k="L-0159 L-0174 L-0175"
  caption="Posting a photo: the photo server first gets an ID from the ticket server (1), then stores the photo under it in the sharded photos database (2). One ticket server is one box that can fail. Redrawn from the class board at 01:26.">
  <Desk><FlickrFlow /></Desk>
  <Phone><FlickrFlow layout="phone" /></Phone>
</Figure>

Follow one request. A user posts a photo, and the request reaches a photo-service API server. That server fires a request to the MySQL ticket server, gets an ID back, and then stores the photo in the sharded photos database. [[L-0174]]

The ticket database has one table, `tickets`, with two columns. `id` is a BIGINT, unsigned, not null, auto-increment, and the primary key; a big integer means a 2^64 space. `stub` has a unique key. [[L-0162]]

<Figure id="fig-5c" no="Fig 5·c" k="L-0162 L-0166 L-0172"
  caption="The whole ID service is this one row. The stub value is a constant whose only job is to collide with the unique key. Redrawn from the class board at 01:21 and 01:26.">
  <Desk><TicketTable /></Desk>
  <Phone><TicketTable layout="phone" /></Phone>
</Figure>

How do you get IDs out of a table like that? The naive way: whenever someone needs an ID, delete the row and insert a new one. Inserting a row without an `id` makes auto-increment fill in the next value, so each delete-and-insert yields the next ID. [[L-0165]]

But you can’t insert a row with no values at all; you have to pass something. That is the only reason `stub` exists. The name sounds fancy, but it is a normal dummy column holding a dummy value, nothing special. In the query it is a hard-coded constant, literally any string, and its one job is to make the database break the unique constraint so that the update fires atomically. [[L-0166]]

</Section>

<Section id="s5-6" no="5.6" title="Upsert: one statement instead of delete + insert" crumb="5.6 Upsert"
  dek="Insert, and if the key is already there, update instead. MySQL has two ways to say it, and one is much cheaper."
  meta="About 4 min · class 01:22–01:27, Q&A 01:31–01:33">

Delete-then-insert can run in one transaction, but that is extremely costly on the database. Or it can become an **upsert**, because delete plus insert is an upsert. [[L-0167]] A single upsert statement replaces the pair: one statement that inserts, or updates the row that is already there <Cite href="https://dev.mysql.com/doc/refman/8.4/en/insert-on-duplicate.html">dev.mysql.com</Cite>.

What is an upsert? You try to insert something. If it already exists, you update it instead; if it doesn’t, you insert it. [[L-0168]]

MySQL offers two ways. The first is `INSERT … ON DUPLICATE KEY UPDATE`: it tries to insert the values you give it, and if that fails on a unique key constraint, it runs the update you passed. The classic upsert. [[L-0169]] It reports 1 affected row for an insert, 2 for an update and 0 if the row was set to its current values, and MySQL advises: “In general, you should try to avoid using an ON DUPLICATE KEY UPDATE clause on tables with multiple unique indexes.” <Cite href="https://dev.mysql.com/doc/refman/8.4/en/insert-on-duplicate.html">dev.mysql.com</Cite>

The second is `REPLACE INTO`, written like `INSERT INTO`; it came up in Lecture 3’s key-value store on a relational database. It does an upsert too, but internally it deletes the old row and inserts a new one. [[L-0170]] Because it rebuilds the row, any column you don’t list goes back to its default, and it fires DELETE triggers as well as INSERT triggers <Cite href="https://dev.mysql.com/doc/refman/8.4/en/replace.html">dev.mysql.com</Cite> <Cite href="https://dev.mysql.com/doc/refman/8.4/en/create-trigger.html">dev.mysql.com</Cite>.

That delete makes it slower. A first-hand benchmark of the two on a MySQL server found `REPLACE INTO` about 32× slower than `ON DUPLICATE KEY UPDATE`. Either works; what matters is doing an upsert. [[L-0171]]

<SourceNote href="https://dev.mysql.com/doc/refman/8.4/en/replace.html" k="L-0171">

`REPLACE INTO` deletes and re-inserts the row, so it is usually slower than `INSERT … ON DUPLICATE KEY UPDATE`; ~32× was one measurement on one setup. It also resets the columns you don’t supply. Prefer `ON DUPLICATE KEY UPDATE` unless you actually want a fresh row.

</SourceNote>

Here is the query in its upsert form. Insert the constant `'a'` into `stub`. The row with `'a'` already exists, so the insert hits the unique key and `ON DUPLICATE KEY UPDATE` `id = id + 1` runs instead: the id goes from 74 to 75, and that is your ID. The next call gives 76, then 77, 78, and so on. [[L-0172]]

<SourceNote href="https://code.flickr.net/2010/02/08/ticket-servers-distributed-unique-primary-keys-on-the-cheap/" site="code.flickr.net" k="L-0172">

Flickr’s published query is the other form: `REPLACE INTO Tickets64 (stub)` `VALUES ('a');` followed by `SELECT LAST_INSERT_ID();`. `REPLACE` removes and re-inserts the single `'a'` row, so auto-increment hands out the next value. In the upsert form, a duplicate on the unique key turns the insert into an `UPDATE` of the old row <Cite href="https://dev.mysql.com/doc/refman/8.4/en/insert-on-duplicate.html">dev.mysql.com</Cite>. The `REPLACE` form matters with two servers (5.7): auto-increment values follow the server’s step and offset <Cite href="https://dev.mysql.com/doc/refman/8.4/en/replication-options-source.html">dev.mysql.com</Cite>.

</SourceNote>

```sql
-- the upsert form above: the insert
-- collides on stub, so the update runs
INSERT INTO tickets (stub) VALUES ('a')
  ON DUPLICATE KEY UPDATE id = id + 1;
-- 74 → 75, then 76, 77 …

-- Flickr's published form
REPLACE INTO Tickets64 (stub)
  VALUES ('a');
SELECT LAST_INSERT_ID();
```

Either way, Flickr leans on MySQL’s own transactions and atomicity to produce IDs; both upsert forms are atomic. It is the same trick as the upsert in Lecture 3’s key-value store. [[L-0173]]

</Section>

<Section id="s5-7" no="5.7" title="Two ticket servers, odd and even" crumb="5.7 Odd and even"
  dek="One ticket server is a single point of failure. Two, stepping by 2 from different starts, never collide and never need to talk."
  meta="About 3 min · class 01:26–01:29">

Look at Fig 5·b again: there is one ticket server. If it goes down, ID generation is gone. It is a single point of failure. [[L-0175]]

The fix is two ticket databases behind a load balancer, so that if one goes down the other handles the load. It looks like [§3.7](#s3-7)’s problem of two servers that had to gossip, but here nobody needs monotonicity, so they don’t have to talk. It is also the idea suggested in class back in [§1.2](#s1-2): step by the number of servers. [[L-0176 L-0091]] Flickr chose this deliberately. At its write volume, “replicating between the boxes would be problematic, and locking would kill the performance of the site” <Cite href="https://code.flickr.net/2010/02/08/ticket-servers-distributed-unique-primary-keys-on-the-cheap/">code.flickr.net</Cite>.

How do two servers stay unique without talking? Increment by 2 instead of 1. One database generates odd IDs, the other even IDs. [[L-0177]]

<Figure id="fig-5d" no="Fig 5·d" k="L-0176 L-0177 L-0178 L-0179"
  caption="Both ticket servers step by 2, one starting at 1 and one at 2. Round robin alternates between them, so IDs come out 1, 2, 3, 4 … and no value is ever issued twice. Redrawn from the class board at 01:31.">
  <Desk><OddEven /></Desk>
  <Phone><OddEven layout="phone" /></Phone>
</Figure>

These are real MySQL server settings. `auto_increment_increment` is how much to add each time, set to 2 on both. `auto_increment_offset` is the starting point: 1 on one server, 2 on the other. [[L-0178]]

```ini
# ticket server 1
auto_increment_increment = 2
auto_increment_offset    = 1

# ticket server 2
auto_increment_increment = 2
auto_increment_offset    = 2
```

Put the load balancer in round-robin mode and requests alternate: the first goes to server 1 and gets 1, the second to server 2 and gets 2, the third gets 1 + 2 = 3, then 4, 5, 6, 7, 8. The IDs come out almost monotonic. [[L-0179]] In practice the two sides drift: when Flickr wrote up the design it had a few hundred thousand more odd-numbered objects than even ones, “but this hurts no one” <Cite href="https://code.flickr.net/2010/02/08/ticket-servers-distributed-unique-primary-keys-on-the-cheap/">code.flickr.net</Cite>.

The single point of failure is solved. If one server goes down, the other carries on, and ID generation continues without a hiccup. [[L-0180]]

</Section>

<Section id="s5-8" no="5.8" title="When the odd server comes back" crumb="5.8 Coming back"
  dek="A server that was down resumes where it stopped. The IDs look strange and are still correct; a reset is optional and only for looks."
  meta="About 7 min · class 01:29–01:36, Q&A 02:21–02:22">

Say the odd server dies after issuing 5. Every request now goes to the even server: 6, 8, 10 … all the way to 202. Then the odd server comes back.

<PauseAndThink k="L-0181 L-0182 L-0183 L-0187 L-0188"

No ID has been issued twice. If the jump bothers you, restart both servers above the max plus a buffer (241 and 242) and round robin looks tidy again. That is optional, for looks, not correctness. Flickr itself lets the two sides drift.

</PauseAndThink>

The odd server resumes where it left off, because MySQL is a persistent store: the counter isn’t only in memory. So it issues 7 while the even one issues 204, then 9, 206, 11, 208. That is a huge gap between neighbouring IDs, but it breaks no constraint. It just doesn’t look pleasing. It is a matter of aesthetics, not correctness: every ID is still unique. [[L-0181]] InnoDB writes the current maximum auto-increment value to the redo log on every change, which is why a restarted ticket server resumes where it stopped. After a crash before the redo log is flushed, though, a recently issued value can be issued again <Cite href="https://dev.mysql.com/doc/refman/8.4/en/innodb-auto-increment-handling.html">dev.mysql.com</Cite>.

If the gap bothers you, there is an optional fix. Take the maximum ID issued so far, 202, add a buffer, say up to 240, and restart the two servers at 241 and 242. Round robin then continues 241, 242, 243, 244. [[L-0182]]

That reset is purely for aesthetics. It has nothing to do with correctness, and nothing to do with strict monotonicity, which is still not guaranteed. Nearly monotonic IDs are simply a good byproduct to have. [[L-0183]] Pretty simple, and pretty brilliant in its own way. [[L-0184]]

Who does the reset? A database server going down is a big deal, so an SRE or DevOps engineer will be looking into it, and they reconfigure the servers. Or automate it: find the active server, find the max IDs, add a buffer, set the values, and do a quick process restart on each server. [[L-0185]] The settings are MySQL-specific, so look up how to change `auto_increment_offset` on your platform.

Which value to reset to is the architect’s call: you are the one designing the system. Reset to the safest value, safely beyond every ID issued in the past. This is why [§2.6](#s2-6) spent time on starting from the safest value. [[L-0186]]

It is tempting to object that without the reset, the IDs aren’t monotonically increasing: the odd server restarting at 7 after the even one reached 202. In fact, monotonicity was never enforced here. Nothing in this design promised it; it was a nice byproduct of round robin. [[L-0187]] Not everyone needs monotonic IDs, and it is fine not to have them. A social media site has no reason to care. [[L-0188]]

Do the two servers have to gossip to agree on a reset, and would they use Lamport clocks for it? It isn’t clear that Flickr specified anything, and as far as the lecture knew, Lamport clocks are something quite different, not used for gossip. [[L-0299]] Flickr’s post never mentions gossip at all, and Lamport clocks, logical clocks for ordering events, can in fact appear inside gossip-based systems <Cite href="https://code.flickr.net/2010/02/08/ticket-servers-distributed-unique-primary-keys-on-the-cheap/">code.flickr.net</Cite>.

In the lecture’s reading, Flickr only said, abstractly, that the servers need to gossip, and how is up to you. It can be as simple as network calls to check each other’s greatest IDs, agree on a value and add a buffer: your own small gossip. [[L-0300]]

<SourceNote href="https://code.flickr.net/2010/02/08/ticket-servers-distributed-unique-primary-keys-on-the-cheap/" site="code.flickr.net" k="L-0300">

Flickr’s two ticket servers never coordinate. The odd/even offsets keep their IDs unique, and the two sides are allowed to drift apart; Flickr does no reset. If you do want the cosmetic reset, note that `auto_increment_increment` and `auto_increment_offset` are dynamic MySQL variables <Cite href="https://dev.mysql.com/doc/refman/8.4/en/replication-options-source.html">dev.mysql.com</Cite>, so they can be changed at runtime; the process restart described above is one way to do it, not the only one.

</SourceNote>

Whatever mechanism you use, the two servers must end up agreeing on the value each one will pick. [[L-0301]] That agreement matters only for the optional reset; the odd/even split itself needs no agreement to stay unique.

<RecallQuestions>
  <RecallItem k="L-0111 L-0117" q="Why does Amazon’s ID service return a range’s start and end instead of a list of IDs, and what happens to the rest of the range if the server crashes?">

IDs are just integers, so start and end describe the whole range; sending every ID would waste network for nothing. If the server crashes, the unused rest of its range is lost for good. That is accepted: with a 2^64 space nobody misses a few ranges, and tracking every used ID would be a massive overhead. The batch size trades call frequency against how much a crash throws away.

  </RecallItem>
  <RecallItem k="L-0166 L-0172" q="What is Flickr’s stub column for?">

Nothing but collisions. You can’t insert an empty row, so each request inserts the same constant (`'a'`) into `stub`, which has a unique key. The insert collides with the existing row, and the upsert (`ON DUPLICATE KEY UPDATE`, or Flickr’s `REPLACE INTO`) makes auto-increment hand out the next ID atomically.

  </RecallItem>
  <RecallItem k="L-0181 L-0182 L-0183 L-0187" q="The odd server died at 5 and the even one reached 202. Is “7, 204, 9” a bug? What would you change, and why is it optional?">

Not a bug: every ID is still unique, and order was never promised. If you want tidy IDs, take the max (202), add a buffer and restart both servers at the safest value, 241 and 242, so round robin reads 241, 242, 243 … It is optional because it changes only how the IDs look, not whether they are correct.

  </RecallItem>
</RecallQuestions>

Both designs still keep a service that someone has to run. Twitter’s answer removes it.
