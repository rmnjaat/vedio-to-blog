<Section id="s6" no="6" title="Snowflake: IDs without a service" crumb="6 Snowflake"
  dek="Twitter’s 64-bit layout puts time, machine and counter in one integer, with no service in the path. Discord and Sony reuse it with a different start date."
  meta="About 20 min · class 01:36–01:44, 01:54–02:03, Q&A 02:16–02:18 and 02:28–02:29">

Tweets are one of the highest-throughput writes in the world, and they spike whenever something big happens and everyone tweets at once. Amazon’s ranges and Flickr’s ticket servers ([§5](#s5)) both keep an ID service that someone has to run and scale. In a path this busy, that service is one more thing to scale. [[L-0211]]

This chapter takes the service away. Every building block is one you have already made: time on the left ([§3.3](#s3-3)), the static counter ([§2.3](#s2-3)), a small integer ([§4](#s4)).

</Section>

<Section id="s6-1" no="6.1" title="Twitter’s Snowflake" crumb="6.1 Snowflake"
  dek="Logic, not a service: one integer that carries its own time, machine and counter."
  meta="About 3 min · class 01:36–01:38">

After two central ID services comes a third approach: **decentralized** ID generation. It is a piece of logic, not a service. Twitter’s version is called **Snowflake**. (Twitter’s own 2010 Snowflake was in fact a network service that its servers called <Cite href="https://github.com/twitter-archive/snowflake/tree/snowflake-2010">github.com</Cite>. Running the same logic as a library inside every server is how many others use it, and it is the version this chapter builds.) [[L-0189]]

Twitter still uses it, and in the lecture’s view it is one of the best ID generation systems out there. [[L-0190]]

<MarginNote title="Why “Snowflake”?" why="skip unless you are curious about the name" k="L-0191 L-0192">

The name is read here as a nod to real snowflakes: almost every snowflake in the world is unique, no two exactly the same, and the algorithm produces IDs that are likewise unique. Twitter never explained the name, so treat that as an interpretation. If you want the physics, Numberphile has a video on why real snowflakes (not the IDs) are unique.

</MarginNote>

Every tweet ID is a Snowflake. Discord and Instagram adopted the same idea: Discord in [§6.6](#s6-6), Instagram in the whole of [§7](#s7). [[L-0193]]

A Snowflake is **64 bits**, and it is kept that small on purpose. [[L-0194]] At Twitter’s scale the size matters. Every tweet ID is stored, ingested and indexed again and again, and 128 bits (16 bytes) instead of 64 would double the space every one of those copies needs. Small IDs are storage efficiency and compute efficiency at scale ([§4.2](#s4-2) showed why every index pays for the ID). [[L-0195]]

It is very much like MongoDB’s ObjectId from [§4.5](#s4-5), time first and then a few tie-breakers, only smaller: 8 bytes instead of 12. [[L-0196]]

</Section>

<Section id="s6-2" no="6.2" title="41 | 10 | 12" crumb="6.2 41 | 10 | 12"
  dek="Time on the left, a machine ID, and a counter. What each field allows, and when it would run out."
  meta="About 5 min · class 01:38–01:42, Q&A 02:01">

The first 41 bits are milliseconds counted from an epoch. Time sits on the left side, always: it is the most significant part of the number, so it moves the ID forward every millisecond. [[L-0197]]

The next 10 bits are the **machine ID**, the ID of the server generating the ID. That is the API server, not the database server. (In Twitter’s original design these 10 bits named a Snowflake server process, because Snowflake ran as its own service <Cite href="https://github.com/twitter-archive/snowflake/tree/snowflake-2010">github.com</Cite>.) [[L-0199]]

The last 12 bits are a **per-machine counter**: the same static counter from [§2.3](#s2-3), one variable per server, atomically incremented every time an ID is made. 41 + 10 + 12 is 63, so the top bit stays 0 and keeps the ID a positive 64-bit integer. [[L-0203]]

<Figure id="fig-6a" no="Fig 6·a" k="L-0197 L-0199 L-0202 L-0203 L-0205"
  caption="Snowflake’s 64 bits: an unused top bit, 41 bits of time, 10 of machine, 12 of counter. Time on the left orders the IDs; the right-hand fields break the tie. Redrawn from the class board at 01:36.">
  <Desk><SnowflakeBits /></Desk>
  <Phone><SnowflakeBits layout="phone" /></Phone>
</Figure>

To make an ID on demand, inside the request handler, a server needs only three things. The current time, which it has. Its own machine ID: every machine is given a unique one to start with. And its per-machine counter. Nothing else, and nobody else to ask. [[L-0204]]

The field widths set the limits. Ten bits of machine ID allow at most 2^10 = 1,024 machines; past that the field would overflow. (Strictly, that caps the number of generator processes. Twitter’s API servers could grow on their own, because Snowflake was a separate tier <Cite href="https://github.com/twitter-archive/snowflake/tree/snowflake-2010">github.com</Cite>.) [[L-0202]]

<PauseAndThink k="L-0202 L-0205 L-0206 L-0207"
  q="Snowflake gives 10 bits to the machine ID and 12 bits to a per-machine counter. Could one machine ever run out of IDs within a single millisecond?"
  choices={[{ label: 'Only above 4,096 IDs in one millisecond', correct: true }, { label: 'Only above 1,024' }]}
  right="Right: 2^12 = 4,096 counter values per millisecond per machine. That’s about 4 million IDs a second from one machine."
  wrong="Not quite: 2^10 = 1,024 is the number of machines the 10-bit field can name. It’s not the per-millisecond limit.">

A real generator that does hit 4,096 in one millisecond just waits for the next one. Nobody fires 4 million tweets a second at one machine, so the headroom is huge.

</PauseAndThink>

Twelve bits of counter give 2^12 = 4,096 values. 2^10 is 1,024, then 2,048, then 4,096. So one machine can make 4,096 unique IDs in one millisecond before it could see a collision. [[L-0205]]

That is humongous throughput: the system was built tolerant enough to be well prepared for future scale. For comparison, the requirement Twitter wrote down for Snowflake was a minimum of 10,000 IDs per second per process <Cite href="https://github.com/twitter-archive/snowflake/tree/snowflake-2010">github.com</Cite>. [[L-0206]]

So when would Snowflake ever see a collision? Only if one machine handled more than 4,096 requests in one millisecond. Counted per second, that is 400,000 requests per second, and no one does that. With at most 1,024 machines, Twitter is safe at the scale it handles. [[L-0207]]

<SourceNote href="https://github.com/twitter-archive/snowflake/tree/snowflake-2010" k="L-0207">

One Snowflake generator can issue up to 4,096 IDs per millisecond, which is about 4 million per second, not 400,000. The conclusion stands, with about ten times more room than that.

</SourceNote>

</Section>

<Section id="s6-3" no="6.3" title="Where Snowflake runs" crumb="6.3 Where it runs"
  dek="Request in, ID made, row stored. No call to anyone in between."
  meta="About 3 min · class 01:38–01:39, 01:42–01:43 and 01:55–01:57">

Follow one tweet. You send a REST request to create it, and it lands on one of Twitter’s ordinary API servers. The server does basic validation (tweet ID, user ID, text, tags), makes the tweet ID with Snowflake, and stores the tweet in the tweets database, which is massively partitioned. (In Twitter’s 2010 design that “makes the ID” step was a call to a separate Snowflake service <Cite href="https://github.com/twitter-archive/snowflake/tree/snowflake-2010">github.com</Cite>.) [[L-0200]]

As this design is taught, Snowflake is not a service at all. It is a library inside the API servers: normal integers and normal bit manipulation. [[L-0201]]

<Figure id="fig-6b" no="Fig 6·b" k="L-0200 L-0201"
  caption="The design as taught: each API server makes the tweet ID itself while storing the tweet. Twitter’s own 2010 Snowflake ran as a separate service (see the note below). Redrawn from the class board at 01:39.">
  <Desk><SnowflakeInApi /></Desk>
  <Phone><SnowflakeInApi layout="phone" /></Phone>
</Figure>

<SourceNote href="https://github.com/twitter-archive/snowflake/tree/snowflake-2010" k="L-0201">

Twitter’s Snowflake ran as a separate network service, a Thrift server written in Scala. Twitter has since retired that open-source release; the repository was archived in 2021 <Cite href="https://github.com/twitter-archive/snowflake">github.com</Cite>. The same bit layout is often built as a library inside app servers instead, as Sony’s <Cite href="https://github.com/sony/sonyflake">Sonyflake</Cite> is.

</SourceNote>

The benefit is what is missing. There is no moving component and no central ID service to talk to. A request comes in, the server makes a Snowflake ID, stores the row in the database, done: no network call, no extra service to build and scale out, no extra load on a database. (That holds for the library form. Twitter’s own Snowflake servers won the same way in a different sense: they never had to coordinate with each other <Cite href="https://github.com/twitter-archive/snowflake/tree/snowflake-2010">github.com</Cite>.) [[L-0210]]

This is why Twitter scales. Firing tweets is one of the highest-throughput workloads there is, and a separate set of ID services would itself need scaling, with all the work that goes with it. Snowflake avoids that tier. (Twitter did run and scale a Snowflake tier; what kept it easy was that its nodes need no coordination.) [[L-0211]]

</Section>

<Section id="s6-4" no="6.4" title="Making one: a few lines of bit arithmetic" crumb="6.4 Bit arithmetic"
  dek="Shift the time left, OR in the machine and the counter."
  meta="About 2 min · class 01:42–01:43, Q&A 02:17">

You can write Snowflake in about three lines of code, even one if you like it terse. [[L-0208]]

Take the current time, the machine ID, and the static counter, incremented atomically. Shift the time left by 23 bits, OR the parts together, and that is the ID. Plain bit manipulation. [[L-0209]]

<SourceNote href="https://github.com/twitter-archive/snowflake/tree/snowflake-2010" k="L-0209">

Twitter’s shift is 22, the 10 machine bits plus the 12 counter bits: ID = (ms_since_epoch &lt;&lt; 22) | (machine_id &lt;&lt; 12) | sequence. A shift of 23 is 13 + 10, Instagram’s layout in [§7](#s7) <Cite href="https://www.depesz.com/2015/10/30/is-c-faster-for-instagram-style-id-generation/">depesz.com</Cite>.

</SourceNote>

```python
# The core, with Twitter's layout: 41 | 10 | 12, so time shifts by 22.
# (A shift of 23 belongs to Instagram's 41 | 13 | 10, in §7.)
EPOCH = 1288834974657            # Twitter's epoch, in ms (4 Nov 2010)

def snowflake(now_ms, machine_id, counter):
    return ((now_ms - EPOCH) << 22) | (machine_id << 12) | (counter & 4095)
```

That is the whole idea. A generator you would run adds two guards around it (added on this page; they are not part of the three lines). If 4,096 IDs are used up within one millisecond, it waits for the next millisecond. If the clock steps backwards ([§3.6](#s3-6)), it refuses to issue IDs until time has caught up, as Twitter’s did <Cite href="https://github.com/twitter-archive/snowflake/tree/snowflake-2010">github.com</Cite>:

```python
# The page's additions: the two guards a real generator has.
last_ms, seq = -1, 0

def next_id():
    global last_ms, seq
    with lock:                                   # one counter per machine, changed atomically
        now = current_ms()
        if now < last_ms:
            raise ClockMovedBackwards()          # refuse until time passes last_ms
        if now == last_ms:
            seq = (seq + 1) & 4095
            if seq == 0:                         # all 4,096 used in this millisecond
                while now <= last_ms:
                    now = current_ms()           # wait for the next one
        else:
            seq = 0
        last_ms = now
        return ((now - EPOCH) << 22) | (MACHINE_ID << 12) | seq
```

Where does `MACHINE_ID` come from? It has to be unique per machine, and it can be assigned, for example by ZooKeeper when a machine spins up. [[L-0293]]

</Section>

<Section id="s6-5" no="6.5" title="Roughly sortable" crumb="6.5 Roughly sortable"
  dek="Time on the left buys rough order for free. Rough, not strict."
  meta="About 4 min · class 01:43–01:44, Q&A 02:17–02:19 and 02:28–02:29">

The beauty of Snowflakes is that they are roughly sortable. The leftmost 41 bits move forward every millisecond, so IDs come out almost ordered, and that byproduct is what makes pagination so efficient ([§8](#s8)). Twitter promised exactly this much: IDs “k-sorted” within about a second, not strict order <Cite href="https://github.com/twitter-archive/snowflake/tree/snowflake-2010">github.com</Cite>. [[L-0198]]

Even within one millisecond there is a pattern: IDs from the machine with the smaller machine ID are smaller, and IDs from the machine with the larger machine ID are larger. [[L-0213]]

You can check this on any tweet. Click it and look at the link: the tweet ID in it is an integer, a Snowflake, and its top bits are the epoch millisecond when the tweet was made. [[L-0214]]

<Figure id="fig-6c" no="Fig 6·c" k="L-0214 L-0215"
  caption="Decoding a Snowflake. The ID 1627179151913938944 is an example built for this page from the timestamp 1,676,784,716,000 ms (19 February 2023), machine 7 and counter 0, with Twitter’s layout and epoch. Shift right by 22 and add the epoch to get the time; mask the middle 10 bits for the machine and the low 12 for the counter. A real tweet ID from any link decodes the same way.">
  <Desk><DecodeTweetId /></Desk>
  <Phone><DecodeTweetId layout="phone" /></Phone>
</Figure>

So given IDs alone, you can tell whether a tweet was made before or after a certain time, or before or after a certain ID, without reading a single timestamp column. That makes pagination super efficient, a very interesting byproduct of roughly sortable IDs. [§8](#s8) is about exactly that. [[L-0215]]

Roughly is the word to keep. Snowflake is not strictly monotonic and doesn’t promise to be: some IDs can come out of order. If a business case really needs strict order, auto-increment is the way to go. (Auto-increment on one database hands out increasing values, but concurrent transactions can still commit out of ID order <Cite href="https://dev.mysql.com/doc/refman/8.4/en/innodb-auto-increment-handling.html">dev.mysql.com</Cite>; [§9.1](#s9-1) comes back to which systems need this.) [[L-0294]]

A tempting idea: route requests round robin, and Snowflake IDs will increase. Not necessarily. Round robin decides which machine answers next; it doesn’t make the machines’ clocks agree, and [§3.5](#s3-5) showed what four clocks do to time-first IDs. [[L-0312]]

You cannot guarantee monotonicity in a distributed setup. Clocks go out of sync, and enforcing order across machines becomes extremely inefficient; that is “written in stone”. So you give up that constraint and take the most you can get: rough sortability. [[L-0313]]

</Section>

<Section id="s6-6" no="6.6" title="A custom epoch: Discord and Sony" crumb="6.6 Custom epoch"
  dek="Nothing forces the clock to start in 1970. Start it on your launch day and the 41 bits last decades longer."
  meta="About 5 min · class 01:54–01:56, Q&A 02:01–02:03">

Epoch milliseconds are a timestamp counted from the epoch, 1 January 1970. [[L-0236]]

But nothing enforces 1970 in those first 41 bits. If your company starts in, say, 2011 or 2015, why start your time from 1 January 1970? You can pick a custom epoch and reclaim the range between 1970 and your start, so your IDs last longer. [[L-0237]]

Why that helps is easiest to see with a real number. On 19 February 2023 the epoch second was 1676784716; add three zeros and you have the epoch millisecond, 1,676,784,716,000. [[L-0253]] Forty-one bits hold at most 2^41 ≈ 2.2 × 10^12, and 1.68 × 10^12 is already about 76% of that. A company that starts counting at 1970 today has wasted most of its range and runs out soon. Start from zero on your launch day and let time count up 1, 2, 3 from there, and the whole range is yours. [[L-0252]]

Put another way, as one summary goes: a custom epoch is just subtracting the start time from now. Your counted time moves at exactly the rate real time does, only from a smaller start, and that gives a massive range. [[L-0254]]

How much more? Roughly 35 more years of IDs, give or take, or 45 if you start today. [[L-0238]] Here is the arithmetic. 2^41 ms is about 69.7 years, from whichever epoch you choose. Counted from 1970 the bits run out in 2039; counted from 2015 they last until about 2084.

<Figure id="fig-6d" no="Fig 6·d" k="L-0237 L-0238 L-0252 L-0253"
  caption="The same 41 bits, two starting points. Counted from 1970 they run out in 2039, and by February 2023 about 76% was gone. Counted from 2015, Discord’s epoch, they last until about 2084; Discord’s docs count one more bit, which stretches it further (see below). Twitter’s own epoch is 4 November 2010 (Fig 6·c).">
  <Desk><EpochRunway /></Desk>
  <Phone><EpochRunway layout="phone" /></Phone>
</Figure>

**Discord** uses exactly Twitter’s structure, but its epoch starts at the first second of 2015, because the company started in 2015. Its documentation describes the details: a 42-bit timestamp in milliseconds since the start of 2015, a 5-bit worker ID and a 5-bit process ID where Twitter has one machine field, and a 12-bit increment. Its HTTP API sends these IDs as strings <Cite href="https://docs.discord.com/developers/reference">docs.discord.com</Cite>. [[L-0239]] The 42 is not a contradiction of the 41 above: Discord’s table counts the timestamp from bit 63, the top bit Twitter leaves unused, so the same layout reads as 42 bits. Kept as 41, as in Fig 6·d, a 2015 epoch lasts to about 2084; using that 42nd bit doubles the range, to about 2154.

**Sony**, the TV company, uses a Snowflake-based implementation too. Sonyflake is open source on GitHub, written in Go, and its core is about five lines of bit manipulation. Its default layout is different from Twitter’s: 39 bits of time in 10 ms units (about 174 years), an 8-bit sequence (256 IDs per 10 ms) and a 16-bit machine ID (65,536 machines) <Cite href="https://github.com/sony/sonyflake">github.com</Cite>. [[L-0240]]

</Section>

<Section id="s6-7" no="6.7" title="No moving parts, and an opinion about microservices" crumb="6.7 No moving parts"
  dek="Why the simplest design here is also the one that scales."
  meta="About 2 min · class 01:56–01:57">

The class board summed up Snowflake’s benefits as a list: **no moving part**; **no service**; **just a function call** (a library); **no extra load on the database**. The logic is handled by the API servers, which the board called excellent. [[L-0210]]

Here is the counterintuitive part. Whenever ID generation comes up, the first instinct is “I’ll write a microservice that does that”. In the lecture’s view, good engineers don’t start there: they look at the problem and at the most efficient way to solve it, and not every solution needs a service. This is the habit [§1.3](#s1-3) started from. [[L-0241]]

Every system and every solution is contextual. It depends on your organization’s context, on your engineers’ expertise and on the support you get from management. [[L-0242]]

So if everyone around you is proposing a microservice and you believe something like Snowflake is far better for your case, bring the change with data. Show the numbers; if they hold, people adopt it. [[L-0243]]

<MarginNote title="The lecture’s view on microservices" why="skip unless you are arguing about it at work" k="L-0244">

The opinion, stated bluntly: microservices are an overkill in most cases, and you shouldn’t fall into the trap of building one for every problem. A milder version is mainstream. Martin Fowler observes that “almost all the successful microservice stories have started with a monolith that got too big and was broken up”, and that early on “the premium of microservices is a drag you should do without” <Cite href="https://martinfowler.com/bliki/MonolithFirst.html">martinfowler.com</Cite>.

</MarginNote>

<RuleBox rule="Simple systems scale: understand the context and ==build only what you need==." k="L-0245">

Understand the context, then build what you really need to build, and keep it simple. Snowflake is the example: a few lines inside the server where a service could have been. Not every problem needs a new service.

<RecallQuestions>
  <RecallItem k="L-0202 L-0205 L-0207" q="With 41 | 10 | 12, how many generators can there be, and how many IDs can each make per millisecond? What happens on the 4,097th?">

2^10 = 1,024 generators (machines, as taught), each making 2^12 = 4,096 IDs per millisecond, about 4 million a second. The 4,097th request in the same millisecond would wrap the counter and risk a collision, so a real generator waits for the next millisecond before issuing it.

  </RecallItem>
  <RecallItem k="L-0237 L-0238 L-0252" q="Why does a 2015 epoch give Discord decades more IDs than a 1970 one?">

41 bits of milliseconds last about 69.7 years from whatever start you pick. Counted from 1970 that ends in 2039, and by 2023 about 76% of the range was already used. Counted from Discord’s 2015 start, the same 69.7 years run to about 2084: the 45 years between 1970 and 2015 are no longer wasted. (Discord’s docs also count the unused top bit, 42 bits, which stretches that to about 2154.)

  </RecallItem>
  <RecallItem k="L-0198 L-0213 L-0294 L-0313" q="What does “roughly sortable” promise, and what does it not?">

It promises that IDs made in a later millisecond are almost always larger, so sorting by ID roughly sorts by creation time (Twitter promised within about a second). It does not promise strict order: machines’ clocks drift, so two IDs made close together on different machines can come out in the wrong order. Where strict order is required, use a single authoritative sequence such as auto-increment.

  </RecallItem>
</RecallQuestions>
