<Section id="s2" no="2" title="Building getid(), one constraint at a time" crumb="2 Building getid()"
  dek="One function, six versions. Each new condition (another machine, threads, a reboot, a busy disk) breaks the last version, and the smallest change fixes it."
  meta="About 25 min · class 00:04–00:25 and Q&A 00:52–00:54">

`getid()` runs inside every request handler of a service. It must return a value nobody has ever received before, from any machine, ever.

This chapter writes it six times. Each version survives one more condition than the last: a second machine, threads, a reboot, a busy disk. Each time, the fix is the smallest change that removes the new collision.

</Section>

<Section id="s2-1" no="2.1" title="Version 1: the current millisecond" crumb="2.1 Epoch ms"
  dek="Time is unique and always moves forward. Return it."
  meta="About 2 min · class 00:04–00:06">

Start with the simplest thing that could work. Time is unique and always moves forward, so the ID function can just return the current epoch millisecond: [[L-0011]]

```js
func get_id() {
  return get_epoch_ms();   // e.g. 1729
}
```

That should work. But something must break, otherwise everyone would be using it. [[L-0012]]

The first price is granularity. Using epoch milliseconds means the function can never be invoked twice within the same millisecond; if it is, both calls get the same value, and you have to go down to micro- or nanoseconds. [[L-0013]]

<Figure id="fig-2a" max={360} wide={false} no="Fig 2·a" k="L-0011 L-0013" caption="Version 1. One machine, one clock: the ID is the current epoch millisecond. Redrawn from the class board at 00:04 (D-01).">
<OneMachine />
</Figure>

So version 1 is correct on exactly one machine, as long as the code is never called twice within one millisecond. [[L-0013]]

</Section>

<Section id="s2-2" no="2.2" title="More machines, then threads" crumb="2.2 Machines, threads"
  dek="Every collision has a cause. Put the cause into the ID."
  meta="About 4 min · class 00:05–00:10">

The service now runs on two machines. Both can run the function within the same millisecond, and both return the same value, 1729. The IDs collide and are no longer globally unique. [[L-0014]]

The fix is to concatenate the machine ID with the epoch millisecond: `m1-1729` on one machine, `m2-1729` on the other, unique across both. (`m1`, `m2` is only a naming choice; use whatever identifies a machine.) [[L-0015]]

```js
func get_id() {
  return concat(machine_id, get_epoch_ms());   // m1-1729, m2-1729
}
```

That is the standard move for resolving collisions: whenever you see one, add to the ID the thing that led to it. Two machines collided, so the machine goes into the ID. [[L-0016]]

<RuleBox rule="Whenever you see a collision, ==add the thing that led to it==." k="L-0016">

Then look for a cheaper alternative to adding it: a counter instead of the thread ID, a flush every N instead of every time. Both come later in this chapter.

<AddTheCause />

</RuleBox>

Threads break it again. If the program runs threads on several cores, the function can run twice within the same millisecond on the same machine, and two threads both produce `m1-1729`. [[L-0017]]

Thread IDs are typically integers the operating system assigns to each thread; `t1`, `t2` here are just shorthand. [[L-0018]] Following the rule, the first fix is to add the thread ID: machine ID, thread ID and epoch millisecond, giving `m1-t1-1729` and `m1-t2-1729`. [[L-0019]]

```js
func get_id() {
  return concat(machine_id, thread_id, get_epoch_ms());   // m1-t1-1729, m1-t2-1729
}
```

<Section id="s2-3" no="2.3" title="A static counter, and time drops out" crumb="2.3 Static counter"
  dek="Appending every cause makes IDs long. One shared counter beats any number of threads, and then the time part has nothing left to do."
  meta="About 5 min · class 00:10–00:15">

There is a second way to separate threads. Instead of the thread ID, add a counter; a common practice is one that resets every few minutes. [[L-0020]] It matters because always appending the thing that led to the conflict leads to gigantic IDs. A counter avoids that. [[L-0021]]

The counter is a **static counter**: one globally allocated variable that every thread can reach. Think of it as living on the heap; strictly, a static variable has static storage duration <Cite href="https://en.cppreference.com/w/cpp/language/storage_duration">cppreference.com</Cite>, not heap storage, but the point is the same: there is one copy per process, shared by all threads. Increment it atomically every time the function is invoked and no two threads can get the same value. [[L-0022]]

So `getid()` becomes the machine ID, the timestamp and the counter, incremented on every call. One machine produces `m1-1729-01`, `m1-1729-02`, `m1-1729-03`, then `m1-1730-…` once the millisecond moves on. With an atomic increment there is never a collision on one machine, however many threads call it. [[L-0023]]

```js
int counter = 0;                 // static: one per process, shared by every thread
func get_id() {
  return concat(machine_id, get_epoch_ms(), counter++);   // m1-1729-01, m1-1729-02 …
}
```

The increment must be thread-safe, and `counter++` is not atomic by default. Wrap it in a lock or mutex, or use your language’s native atomic library. It is the same `count++` race as in Lecture 2. [[L-0024]]

When to reset the counter, every few minutes or every few seconds, is business logic. IDs stay unique anyway, because the millisecond part keeps moving forward, as long as the counter never goes past its integer limit. [[L-0025]]

That gives two ways to beat thread collisions: append the thread ID, or use an atomically incremented static counter, which works no matter how many threads there are. [[L-0026]]

Now look at the counter again. It already increases on every call. With an atomically increasing counter, the time part is redundant: the counter alone gives 1, 2, 3, … So drop time, and the IDs get shorter: machine ID plus counter, `m1-01`, `m1-02`, `m1-03`. [[L-0027]]

```js
int counter = 0;
func get_id() {
  return concat(machine_id, counter++);   // atomic increment; m1-01, m1-02 …
}
```

Its one limit is size: the counter can hit the integer limit, which is about 4 billion. With 2^64 it is such a massive number that you might never hit it. [[L-0028]]

Machine ID concatenated with an atomically incremented static counter solves uniqueness. [[L-0029]]

</Section>

<Section id="s2-4" no="2.4" title="Surviving a reboot" crumb="2.4 Reboots"
  dek="A counter in memory forgets everything when the process restarts."
  meta="About 4 min · class 00:14–00:17 and Q&A 00:52–00:54">

The machine restarts at 3 a.m. The static counter lived in volatile memory with no persistence, so it resets to 0, and the machine hands out `m1-01`, `m1-02` again: IDs it already issued. The logic is no longer unique. [[L-0030]]

The root cause is where the counter is stored: volatile memory. [[L-0031]] So one idea is to back the counter up to a file on the machine, and that is the right direction, because volatility is the problem. [[L-0032]]

The logic then becomes: when the process starts, load the counter from disk. On every call, increment it, immediately save it to disk (open a text file and dump the number in, say), and then concatenate as before. The business logic stays the same; on the class board this step was labelled *fault tolerance*. [[L-0033]]

```js
int counter = load();            // once, at process start
func get_id() {
  counter++;
  save_counter(counter);         // on every call
  return concat(machine_id, counter);
}
```

One detail decides whether this really survives a crash. A plain `write()` normally lands in the operating system’s page cache, and only `fsync()` flushes it to the storage device so it can be read back after a crash or reboot <Cite href="https://man7.org/linux/man-pages/man2/fsync.2.html">man7.org</Cite>. That flush is also the expensive part of “save the counter on every ID”. [[L-0033]]

Loading the counter once, when the process starts or the machine boots, is fine. [[L-0034]]

It is tempting to skip saving altogether: on restart, read the largest ID already stored in the database (the max row ID) and carry on from there. [[L-0098]] In fact that is `load()` by another name: loading from disk or from the database is one and the same, you start from that point. And it quietly assumes an entry is written to the database for every ID generated, so that the max row is the last ID. This logic deliberately doesn’t assume that, because writing back to the database is expensive, and many IDs are never written anywhere: they are attached to something and passed along, like a request ID. [[L-0099]]

</Section>

<Section id="s2-5" no="2.5" title="A disk write on every ID" crumb="2.5 Disk writes"
  dek="Saving on every call is correct, and it turns every ID into a disk IO."
  meta="About 4 min · class 00:17–00:22">

Now the service calls `getid()` thousands of times a second. Saving the counter on every call means a disk IO per ID. At that rate the disk takes a lot of pressure from a great many micro disk IOs. [[L-0035]]

That is problem one. Problem two is latency: every ID now waits on a disk IO instead of being served from memory. [[L-0036]]

<PauseAndThink k="L-0035 L-0036 L-0037 L-0038 L-0040 L-0041"
  q="getid() saves its counter to disk on every call so a reboot can’t reissue IDs. At thousands of calls a second the disk is drowning. Can you touch the disk far less often without ever reissuing an ID?"
  choices={[{ label: 'No: skip a save and a reboot repeats IDs' }, { label: 'Yes: there are at least two ways', correct: true }]}
  right="Right. The disk only needs to know a value you haven’t handed out yet. It doesn’t need the exact current one."
  wrong="That’s true only if a restart begins exactly at the saved value. Start somewhere safer and the saves can be rare.">

Two ideas from class. A **boot counter**: read a number from the file at startup, add one, write it back once, and put it in the ID, so the in-memory counter can restart at 0 (the cost is a longer ID). A **bank of IDs**: save “current + 1000” and serve the next thousand from memory, writing again only when they run out. The second is flush-every-N, the next step.

</PauseAndThink>

The first idea adds a third part to the ID: a **boot counter**. At server startup, read it from the file, increment it and write it back, once. Each startup of the server is now represented by a new value, and the ordinary counter can start from 0 in memory and never be saved per call. Nothing is written to disk while IDs are handed out. [[L-0037]]

It has two costs. The increment at startup has to be atomic (it can be made atomic), and the ID gets longer. [[L-0038]] It is a really good approach, because it tackles the disk IO problem head on. Only the long ID might become a problem, though not a big one, and that cost is what [chapter 4](#s4) is about. [[L-0039]]

The second idea is a **bank of IDs**. When you read the counter, say it is 1, add 1000 to it and store that. Then serve IDs from memory, and when you reach the stored value, read and add 1000 again: a thousand IDs in memory for each disk write. [[L-0040]]

Put differently, you write to disk periodically, at a certain frequency, instead of every time, and the number of disk IOs collapses. Remember this one: it comes in handy at two different places. On this page those are the next section and Amazon’s ID service in [section 5.2](#s5-2). [[L-0041]]

</Section>

<Section id="s2-6" no="2.6" title="Flush every N, restart from the safest value" crumb="2.6 Flush every N"
  dek="Write the counter every N IDs. After a crash, start where no issued ID can be."
  meta="About 5 min · class 00:22–00:25">

Written as code, the bank of IDs is a **flush frequency**. Instead of saving the counter every time, write it to disk only every N IDs, for example every 1000. That cuts disk IO by a factor of 1000, a massive performance gain. [[L-0042]]

At startup the counter starts at `load()` plus the flush frequency, to stay clear of anything already issued. On each call it increments, and if the counter mod N is 0, it is written to disk. [[L-0043]]

```js
const N = 1000;                       // flush frequency
int counter = load() + N;             // at startup: past anything issued before
func get_id() {
  counter++;
  if (counter % N == 0) save_counter(counter);   // one disk write per N IDs
  return concat(machine_id, counter);
}
```

Here is why the startup line adds N. Take a flush frequency of 3. Machine `m1` hands out 1, 2, 3; 3 mod 3 is 0, so 3 is flushed. Then 4, 5, 6, and 6 is flushed. Then 7, 8, and the machine crashes. The last value on disk is 6, but 8 was already handed out. Restarting from 6 would generate 7 and 8 again, which is wrong. [[L-0044]]

<PauseAndThink k="L-0044 L-0045 L-0046 L-0048"
  q="The counter is flushed every 3 IDs. The disk holds 6. The machine handed out 7 and 8, then crashed. On reboot, which ID does it hand out first?"
  choices={[{ label: '7: carry on from the disk value' }, { label: '10: last flush + 3 + 1', correct: true }]}
  right="Right. 6 + 3 + 1 = 10. Before the next flush the machine could have reached 8 at most, so 10 is safely past anything it issued."
  wrong="7 and 8 already went out before the crash. Starting from the disk value hands them out a second time.">

The disk can only say “at least 6 went out”. Anything up to the next flush may already be in someone’s hands, so the restart jumps past the whole window and pays for it with a few unused numbers.

</PauseAndThink>

So on recovery, start from the **safest value**: the last flushed value, plus the flush frequency, plus one. In the example that is 6 + 3 = 9, plus 1: 10. The machine hands out `m1-10`, `m1-11`, `m1-12`, and flushes again at 12. The code says the same thing: `load() + N` gives 9, and the first `++` hands out 10. [[L-0045]]

Some integers are never handed out: here, `m1-09`. Had the crash come before 8 went out, both 8 and 9 would be lost. That is fine. The correctness of the system matters more than using every single integer. [[L-0046]]

Two habits come out of this, and they are the key design constraints for any distributed ID generator.

First, don’t do IO every time. Add a periodicity factor, and keep it as simple as a mod operation: count, take the counter mod N, write. Don’t reach for a thread with a timer. [[L-0047]]

Second, whenever a machine recovers, start from the safest value. Always think of correctness first. [[L-0048]]

<RecallQuestions>
  <RecallItem q="Why did the time part become redundant once the counter was atomic?">

Time was there to make values differ from call to call. An atomically incremented counter already differs on every call, on one machine, however many threads ask. With the machine ID in front, machine plus counter is unique on its own, so the timestamp only made the ID longer.

  </RecallItem>
  <RecallItem q="A boot counter and flush-every-N both cut disk writes. What does each cost?">

The boot counter writes once per startup, but the increment at startup must be atomic and every ID carries a third part, so IDs get longer. Flush-every-N keeps the ID short but writes only every N IDs, so after a crash it must skip ahead to the safest value and some integers are never used.

  </RecallItem>
  <RecallItem q="N = 1000, the last value on disk is 5000, and the machine crashed. What is the first ID it may issue after restart, and why?">

6001: the last flushed value plus N plus one, 5000 + 1000 + 1. Before the crash the counter could have reached anything up to 5999 without another flush, so anything lower might repeat an ID already handed out. In code, `load() + N` gives 6000 and the first `++` returns 6001.

  </RecallItem>
</RecallQuestions>

Every ID is now unique. None of them says which came first. That is the next constraint.
