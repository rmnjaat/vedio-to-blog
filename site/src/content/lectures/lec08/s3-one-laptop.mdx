Chapter 2 decided *which* backend gets a request. This chapter opens the box that does the deciding. Picture one LB server at `10.0.0.1:9000`, three backends at `10.0.0.7`, `.8` and `.9` on port `8081`, and a browser asking for `/index.html`. What exactly happens to the bytes?

<Section id="s3-1" no="3.1" title="Why build one" crumb="3.1 Why build one"
  dek="Boxes anyone can draw. The ten lines inside the box are what set you apart."
  meta="About 3 min · class 00:40–00:43, with 00:01 and the board at 00:35">

This lecture works through a realistic load balancer design and, briefly, the source code of a tiny load balancer written for the class. The point is to see the core logic instead of drawing boxes. The code is in no way production-ready. [[L-0006]]

Drawing boxes is something anyone can do (“a two-year-old kid can do that”). Understanding the granular implementation is the differentiating factor. [[L-0007]]

The core turns out to be small: hardly ten lines of code, and even ten is an exaggeration. Most people never think of writing one. Yet an engineer wrote NGINX, and everyone now uses it as a reverse proxy. [[L-0008]]

Before any drawing, the board listed what the design has to do: [[L-0087]]

- balance the load
- with a tunable algorithm
- and scale beyond one machine

This cohort takes the load balancer low level first, then fits it into the high-level picture, including why one server can’t be the load balancer (that is the next chapter). Earlier cohorts started from the high level and ran out of time. [[L-0099]]

The habit behind it: find time to implement everything you see. You will learn details most people don’t know. [[L-0098]]

<MarginNote title="A first load balancer, from practice" why="skip unless you want the story" k="L-0095 L-0096 L-0097">

The instructor built a first load balancer in plain Go around March 2021, during COVID, while preparing their first cohort, so they could show a real demo. They had read a few papers on load balancers but wanted the practical experience, and were thrilled when it first ran. [[L-0095]]

It balanced load across servers with several algorithms: consistent hashing, round robin, weighted round robin and static routing. [[L-0096]]

Benchmarked against Nginx and HAProxy, it came out five to six times faster than Nginx. That was no breakthrough: going deep into Nginx showed that Nginx and HAProxy do far more than a simple load balancer does. [[L-0097]]

</MarginNote>

<Section id="s3-2" no="3.2" title="Two kinds of server, two TCP connections" crumb="3.2 Two connections"
  dek="Fix the terms, then follow one request: it costs the LB server two TCP connections and one entry in a hash table."
  meta="About 9 min · class 00:43–00:52">

Two terms first. The **LB server** is the machine that runs the load balancer; the load balancer itself is just a process on that machine. [[L-0100]] The **backend servers** are where the requests go: the payment service, the auth service, the profile service. To the load balancer you are building, they are a black box. [[L-0101]]

Spinning up a load balancer means a VM starts and runs the load-balancing process. That process is a normal TCP server, not even an HTTP server. [[L-0102]]

Start from day zero, as in [§1.2](#s1-2): a single LB machine with the static IP address `10.0.0.1`, which does not change. [[L-0103]] Don’t think about scale yet: as chapter 1 put it, scale on day zero is the worst way to build a system. Think simple. [[L-0104]]

Behind it sit the backends. Each runs a normal HTTP server (Flask, Spring Boot, any framework) that serves `/index.html` with “hello world” and listens on port `8081`. [[L-0105]] To connect to any server you need its IP address and its port; here the three backends are `10.0.0.7`, `10.0.0.8` and `10.0.0.9`. [[L-0106]] The load balancer stores that list of backends as `ip:port`. It is the same list you fill in on a cloud console when you choose which servers sit behind a load balancer. [[L-0107]]

Now a request. When a client (a user, or another server) “sends a request to the load balancer”, it establishes a TCP connection with it. So the LB server must listen on a TCP port, say `9000`. [[L-0108]] The request lands on the LB server for a simple reason: the load balancer’s address is the only one the client has. [[L-0109]] The backends accept HTTP requests on `8081`, and HTTP runs over TCP. [[L-0110]]

When a connection arrives, the LB server first picks a backend with its load-balancing algorithm. With the simplest one, a random strategy, it picks one of the three at random. [[L-0111]] Then it opens a TCP connection of its own, to the chosen backend, say `10.0.0.7:8081`. So one request from a client sets up **two TCP connections**: client to load balancer, and load balancer to backend. [[L-0112]]

The LB server has to remember which connection goes with which. It keeps a map from each **source** TCP connection to its **target** TCP connection. [[L-0113]] The source connection is the one between the client and the LB server; the target connection is the one between the load balancer and the backend. On the board the map read `{ tcp1 → tcp2, tcp3 → tcp4 }`. [[L-0114]]

This is exactly how the first version of that Go load balancer was thought out: first principles, nothing fancy. [[L-0115]]

Where does the map live? In an in-memory hash table on the LB server. You don’t need a database for it, and you couldn’t use one: a TCP connection lives on this server, so there is nothing to store anywhere else. [[L-0116]]

</Section>

<Section id="s3-3" no="3.3" title="Copy one socket to the other" crumb="3.3 Copy both ways"
  dek="Bytes arrive on tcp1. The LB server looks up tcp2 and writes them there, without reading what they say."
  meta="About 4 min · class 00:52–00:55, Q&A 01:05–01:06">

Bytes arrive on the source connection. The LB server looks up the map and forwards whatever it received, bluntly, to the target connection. [[L-0117]] Strictly, a TCP proxy copies a byte stream, not packets: the kernel reassembles the bytes on one socket and cuts them into new packets on the other, and Go’s `io.Copy` works the same way, reader to writer (<Cite href="https://pkg.go.dev/io#Copy">pkg.go.dev</Cite>).

The load balancer doesn’t care what protocol is inside: HTTP, WebSocket, RTMP, ICMP. It reads from one socket and writes to the other. [[L-0118]] One limit on that list: it holds for protocols carried over TCP. ICMP belongs to the IP layer and never rides inside TCP, so it can’t pass through a TCP proxy, and neither can UDP-based protocols (<Cite href="https://www.rfc-editor.org/rfc/rfc792">RFC 792</Cite>).

What the backend receives is a well-formed HTTP request, so it understands it, generates the response and sends it back on the connection the request came in on. The LB server sees data on tcp2, looks up tcp1, forwards it there, and the client has its response. [[L-0119]]

Read from the client’s socket and write to the backend’s; read from the backend’s socket and write to the client’s. That is exactly what a load balancer does: two lines of code, and done. [[L-0120]] A second client is handled the same way on its own pair of connections, tcp3 to tcp4. [[L-0121]]

Between the load balancer and the API server there are no REST calls. It is a normal TCP connection, and the load balancer copies anything across it, from one side to the other: HTTP, RPC calls, whatever the client sends. [[L-0139]]

So building a single-machine load balancer from first principles is really easy. It is just a mapping: “when I get something on this TCP connection, send it to that TCP connection”. Scaling it is a separate matter. [[L-0125]]

<Section id="s3-4" no="3.4" title="Reading the code" crumb="3.4 The code"
  dek="A tiny Go load balancer: an accept loop, a strategy, a dial, and two copies in two goroutines."
  meta="About 9 min · class 00:56–01:05, Q&A 01:04–01:08">

Put in one sentence, the design is: keep a load-balancing algorithm configuration, and when a connection comes in, pick a backend server according to it and forward the request. [[L-0124]]

The code shown in class is `lb.go` in the ARLB repository, an “experimental reverse proxy and load balancer” written in Go. The LB server listens on port `9090`. Four backend servers are hardcoded: Flask hello-world processes from one code base, on four local ports (`8081` to `8084` on screen). The aim was to test load balancing, not to scale anything. [[L-0126]]

The main loop is a small infinite `for` loop around `listener.Accept`, which waits for an incoming client connection. Each accepted connection is wrapped as a source connection, with a request ID for logging, and handed to a `proxy` function. [[L-0127]] In `proxy` the first step is to pick the backend: `lb.strategy.GetNextBackend` returns a host and port according to the strategy (round robin, consistent hashing, and so on), and the LB server dials a TCP connection to it. [[L-0128]]

```go
// lb.go, trimmed and lightly simplified from the screen
ln, _ := net.Listen("tcp", ":9090")
for {
    srcConn, _ := ln.Accept() // wait for a client
    go lb.proxy(IncomingReq{srcConn: srcConn, reqId: uuid.NewString()})
}

func (lb *LB) proxy(req IncomingReq) {
    backend := lb.strategy.GetNextBackend(req)
    backendConn, err := net.Dial("tcp", backend.String())
    if err != nil {
        req.srcConn.Write([]byte("backend not available"))
        return
    }
    backend.NumRequests++
    // two goroutines: each io.Copy blocks until EOF
    go io.Copy(backendConn, req.srcConn) // request: client → backend
    go io.Copy(req.srcConn, backendConn) // response: backend → client
}
```

With a source connection and a backend connection in hand, the load balancer calls `copy` (which copies from one file to another) twice: from the source to the backend for the request, and from the backend to the source for the response. Each call runs in its own goroutine. [[L-0129]] The reason is that `copy` blocks. Without its own goroutine, the first call would hold `proxy` until the connection ended, and the response would never be read. [[L-0130]]

`copy` keeps copying, continuously, from one connection to the other until it receives EOF. [[L-0140]] It returns only then, so you can’t wait on it in line: the two copies run as two goroutines in parallel, one per direction. [[L-0141]]

The code’s limits are stated openly: it is not an efficient implementation, and it spins up as many goroutines as it likes. [[L-0131]]

The strategies in the repository are round robin, static and hashed. Round robin’s `GetNextBackend` keeps the index of the last backend it used and takes the next one, `(index + 1) mod n`, which gives 1 2 3, 1 2 3 (the same one integer as in [§2.2](#s2-2)). [[L-0133]]

```go
s.Index = (s.Index + 1) % len(s.Backends)
```

The consistent-hashing strategy is a little more complex, but still simple; the instructor’s blog walks through it. [[L-0134]] <ForwardChip when="Lecture 9" k="L-0134">consistent hashing, used again</ForwardChip>

A run loop listens on an events channel, so the load balancer can handle three commands at runtime: exit, add a backend, and change the strategy (on screen: `case CMD_Exit`, `case CMD_BackendAdd`, `case CMD_StrategyChange`). [[L-0136]]

### Counting connections [[rail: Counting connections]]

Least connections ([§2.4](#s2-4)) needs a count per backend, which raises a question: how does the count go down when a user disconnects? This basic load balancer doesn’t keep connection counts at all. It tracks one statistic per backend, the number of requests handled so far, to check that round robin really spreads them. Other statistics can be updated the same way, once a backend has been picked. [[L-0137]]

As for knowing that a connection has ended, the answer given was that it “raises a panic”, an exception you can catch and use to update the load balancer’s in-memory state. [[L-0138]] In Go, nothing actually panics: `io.Copy` returns, with a nil error at EOF or with an error such as a connection reset, and that return is the place to update counters (<Cite href="https://pkg.go.dev/io#Copy">pkg.go.dev</Cite>).

</Section>

<Section id="s3-5" no="3.5" title="Build it locally" crumb="3.5 Build it locally"
  dek="You don’t need three servers. Four processes on one laptop are a load balancer you can break and fix."
  meta="About 4 min · class 00:55–00:56 and 01:02–01:08">

“I don’t have three servers.” You don’t need them. Start a process as the LB server on port `9000`, in Go, C++, Java or Python, and start the backends as processes on other ports of the same machine: `8081`, `8082` and `8083` on localhost. One machine can’t have three processes listening on `8081`, which is why each gets its own port. No cloud, no VMs, no Docker. [[L-0123]]

With basic networking knowledge, a load balancer like this is about a five-hour project. There is no magic sauce; everything else is the load-balancing strategy. [[L-0132]]

Be curious, and go deep into the systems you use. You may land in a spot where you have to write a very lightweight proxy because the existing proxies aren’t performant enough. [[L-0135]]

The same goes well beyond load balancers. Even a CDN, a non-distributed one (nobody is asking you to distribute it), can be built in hardly an hour if you know how content is served, cached and processed. It is difficult to scale, not to build. [[L-0142]]

<RuleBox rule="There is a difference between ==building and scaling==: everyone can build it locally; few get to scale it." k="L-0144 L-0125">

Very few people get the chance to scale systems, but every one of us can build them. Docker started with someone building it locally, and you need multiple machines only to scale. A single-machine load balancer, built from first principles, is just a mapping: “when I get something on this TCP connection, send it to that one”. So there is no excuse not to build.

Scaling is where this load balancer runs into trouble, and it shows up as soon as you count connections.

<PauseAndThink k="L-0112 L-0122 L-0145"
  q="Your LB server can hold 10,000 TCP connections. How many clients can it serve at the same time?"
  choices={[{ label: '10,000' }, { label: 'About 5,000', correct: true }]}
  right="Right: every client costs two connections."
  wrong="Count again: each client needs two connections on the LB server, not one.">

Each proxied request uses one connection from the client to the LB server and a second from the LB server to a backend, so half the budget goes to backends. 10,000 ÷ 2 = 5,000 clients. One LB server is a bottleneck, so you’ll need many, and that is where the control plane in [§4](#s4) comes from.

</PauseAndThink>

<RecallQuestions>
  <RecallItem k="L-0112 L-0113 L-0116" q="Name the two TCP connections behind one proxied request, and the one data structure the LB server needs.">

The source connection, from the client to the LB server, and the target connection, from the LB server to the chosen backend. The LB server keeps a map from each source connection to its target connection in an in-memory hash table; a database would be useless, because the connections only exist on that machine.

  </RecallItem>
  <RecallItem k="L-0129 L-0130 L-0141" q="Why does each <code>io.Copy</code> run in its own goroutine?">

`io.Copy` blocks: it keeps copying until it receives EOF, and only then returns. Called inline, the request copy would hold the function until the client disconnected, and the response copy would never start. In two goroutines the two directions run in parallel.

  </RecallItem>
  <RecallItem k="L-0118 L-0139" q="Can this load balancer forward a WebSocket? A DNS query over UDP? Why?">

A WebSocket, yes: it runs over TCP, and the LB server copies the bytes without parsing them, whatever the protocol inside. A DNS query over UDP, no: this is a TCP proxy, and a protocol that doesn’t ride on TCP (UDP-based protocols, or ICMP) never reaches its sockets.

  </RecallItem>
