### Ten lines to keep [[rail: Heuristics]]

The same few ideas kept coming back, whichever box was on the board:

1. Assume anything and everything will go wrong, then check whether your code and your system handle it ([§1.1](#s1-1)). [[L-0029]]
2. Start from the day-zero architecture, one machine, one server, one database, one cache, and scale each component from there; one engineer’s approach, “take it with a pinch of salt” ([§1.2](#s1-2)). [[L-0030]]
3. Every layer must scale out, and know your unit economics: how many requests one server handles, so you can scale linearly ([§1.3](#s1-3)). [[L-0041]]
4. It is always about money: does the infrastructure get used well? ([§2.3](#s2-3)) [[L-0066]]
5. Think about practicality whenever you suggest a design idea. The load balancer can’t stop to ask every server for its CPU ([§2.5](#s2-5)). [[L-0082]]
6. Everyone can build it locally; few get to scale it. So build it ([§3.5](#s3-5)). [[L-0144]]
7. Make systems reactive rather than polling-based ([§4.5](#s4-5)). [[L-0181]]
8. Reuse existing tools ([§4.6](#s4-6)), and don’t add boxes for their own sake: every service is a network hop ([§5.7](#s5-7)). [[L-0192 L-0342]]
9. To synchronize two things, use the nearest storage they share ([§6.2](#s6-2)). [[L-0308]]
10. Edge cases are minimized, never claimed fully covered; the one line people miss makes all the difference, most likely the release-on-failure branch of acquire ([§7.3](#s7-3)). [[L-0322]]

Two papers sit under the two halves of this lecture. Google’s Maglev paper, where much of the load balancer design comes from ([§5.4](#s5-4)) [[L-0229]], and Google’s Chubby paper, a lock service for loosely coupled distributed systems, still in production ([§7.5](#s7-5)). [[L-0284]]

<MarginNote title="A learning habit, from practice" why="skip unless you want the habit" k="L-0240 L-0324 L-0325 L-0327">

The aim of the class is to understand the intuition behind a design, not to mug things up; a session gets stretched rather than compromise on quality to get there. [[L-0240]]

At the time of this class the instructor was writing their own `malloc`, to see how memory management happens at the OS level: how a program gets memory, and where exactly the heap lives in RAM. [[L-0324]] A suggestion from class, that this would mean writing your own inodes, was corrected: inodes belong to the file system, while `malloc` is in-memory allocation. [[L-0325]]

The habit behind it: find the scrappiest way to build something, and study whenever possible. That morning, before class, it was the official documentation of the system calls that allocate memory, read until 8:45, time traded for what would otherwise go to Netflix. [[L-0327]]
