<Section id="s6" no="6" title="Remote locks" crumb="6 Remote locks"
  dek="Three consumers, one queue that protects nothing, and no access to its server. Lock across machines through the network: what to store, why it must expire, and how not to delete someone else’s lock."
  meta="About 30 min · class 02:05–02:35, Q&A 02:35–03:06">

The load balancer is finished, and every box in it now runs on many machines. Many machines bring a new kind of trouble: two of them can touch the same thing at the same time. Picture a remote queue, queue 7, whose only API is `pop`, and that `pop` is not thread safe. Three consumers on three machines read from it, and only one of them may read at a time. Nothing about the queue will help you.

</Section>

<Section id="s6-1" no="6.1" title="Why lock across machines" crumb="6.1 Why lock"
  dek="Two distributed transactions want the same row. Something outside both of them has to say who goes first."
  meta="About 3 min · class 00:02–00:04 and 02:05–02:07">

Imagine two transactions running in a distributed fashion, both trying to update the same row. One of them has to stop the other. More generally, whenever several processes must coordinate so that the data stays consistent, you need a lock they all respect. In a distributed setup, with no single database to lean on, many more challenges come in. [[L-0010]]

That is why remote locks and distributed locks are among the most important things in distributed systems: they form the heart and crux of data correctness and consistency. [[L-0011]]

The chapter goes in this order. First why you need a lock, which is the more important question, then how to implement one using Redis. [[L-0012]] Redis is only the example. What matters is the core property a system needs before it can act as a lock manager, the core access pattern, so that you could build your own lock manager if you didn’t want to use Redis. [[L-0013]]

The previous lecture taught database locking through an airline check-in system. Distributed locking is taught here with a synchronization example that is very hypothetical on purpose. [[L-0014]]

<ForwardChip block label="from" when="Lecture 3" k="L-0014">locking the airline seats: row locks inside one database</ForwardChip>

A **lock manager** is a remote machine that keeps track of which item is locked by which machine, so that it can coordinate: because this item is locked, you can’t do that operation on it. [[L-0241]]

<Figure id="fig-6a1" no="Fig 6·a" wide={false} k="L-0241"
  caption="Each machine asks; the lock manager remembers which item each machine has locked. Redrawn from the class board at 02:05.">
  <LockManager />
</Figure>

In the airline check-in system, rows were locked exclusively, so that other transactions couldn’t even read them. Somewhere in the database’s memory it was recorded that this row is locked by that transaction. Everything lived in one machine and one process, so the bookkeeping was just memory updates. With many machines that have to coordinate, there is no shared memory to record it in, and that is why you need a remote lock manager. [[L-0242]]

</Section>

<Section id="s6-2" no="6.2" title="Threads, processes, machines" crumb="6.2 Threads, processes, machines"
  dek="Two things that must take turns coordinate through the nearest storage they share: memory, then disk, then only the network."
  meta="About 4 min · class 02:06–02:10, Q&A 02:45–02:50">

Each transaction in the airline check-in system is a thread. When threads must take turns (one takes a lock on something, the others can’t), they synchronize through something in memory: a mutex, a semaphore, explicit locking, atomic instructions. What do threads have in common? RAM. [[L-0243]]

Now two processes. On Ubuntu you install or upgrade packages with `sudo apt-get upgrade`, and if you run it in two terminals at once, the second one refuses. At most one `apt-get upgrade` may run at any moment, because two would leave the package database in an inconsistent state. As taught, the mechanism is a file on disk: when the process starts, it checks whether the `dpkg` lock file exists. If it does, the process exits; if not, it creates the file, does its work, and deletes the file when it is done. [[L-0245]] Precisely, dpkg doesn’t check whether the file exists: it takes an `fcntl` lock on `/var/lib/dpkg/lock` (after `lock-frontend`), and the kernel drops that lock when the process exits, so a crash never leaves a stale lock behind (<Cite href="https://salsa.debian.org/dpkg-team/dpkg/-/raw/main/doc/spec/frontend-api.txt">dpkg frontend spec</Cite>, <Cite href="https://man7.org/linux/man-pages/man2/fcntl_locking.2.html">fcntl(2)</Cite>).

<MarginNote title="Two apt-gets, from practice" why="skip unless you like the origin" k="L-0244">

Around 2008–2009, in the first year of college, the class had just been introduced to Ubuntu and taught to install packages. The instructor opened two terminals and ran `apt-get upgrade` in both, expecting it to go twice as fast. The second one failed every time: the dpkg lock file exists, and it couldn’t move forward. So you can’t run several instances of it. [[L-0244]]

</MarginNote>

Put the two side by side and a ladder appears. Threads synchronize through memory. Processes synchronize through the disk, because that is the closest storage shared between processes. And machines? They share no RAM and no disk. What they share is the network, and that is where remote locks come in. [[L-0246]]

<PauseAndThink k="L-0243 L-0245 L-0246 L-0308 L-0312"
  q="Threads in one process coordinate through memory. Two <code>apt-get</code> processes coordinate through a lock file on disk. What can two separate machines coordinate through?"
  choices={[{ label: 'A shared disk' }, { label: 'Only the network', correct: true }]}
  right="Yes: the network is the only thing they share."
  wrong="Two machines don’t share a disk (or RAM). The only thing between them is the network.">

Use the nearest storage the parties share: memory for threads, the disk (strictly, a kernel-held file lock) for processes, and for machines only the network. That is why locks across machines live in a remote lock manager reached over the network. It is also why they cost so much more than a mutex: a network round trip against a few nanoseconds of in-memory signalling.

</PauseAndThink>

  <Phone><SharingLadder layout="phone" /></Phone>
</Figure>

The example is taken from real life on purpose: practical examples beat theory any day. [[L-0247]]

The principle came back in the Q&A, restated as a rule and endorsed: to synchronize two entities, look for the nearest storage they share. Two threads share RAM, so a mutex or a semaphore. Two processes have separate RAM, so the disk. Two machines share an external store, or, put simply, “anything over a network.” [[L-0308]]

<RuleBox rule="To synchronize two things, use ==the nearest storage they share==." k="L-0308 L-0246">

Threads share memory (mutex, semaphore). Processes share the disk. Machines share only the network, so they need a remote lock.

<Desk><NearestStorage /></Desk>
<Phone><NearestStorage layout="phone" /></Phone>

</RuleBox>

What about synchronizing two whole distributed systems, say two clusters doing different kinds of work? “Distributed system” is a vague term, but the answer is the same: they are still machines on a common network, so a shared store reached over the network, such as Redis or a database, does the job. Whenever several machines are involved, synchronization is over the network, because the network is the only thing they share. [[L-0309]]

It is tempting to think a mutex would be harder to build than a network lock. In fact a mutex is two lines of code in C: everything is in one RAM, the coordination is between threads, and that is peanuts. [[L-0311]] The network is the costliest channel there is, the worst mode of communication. A polling loop that asks Redis again and again makes a network call every time, while in-memory signalling costs the operating system almost nothing. Prefer signalling to network calls any day. [[L-0312]]

So if the critical section lives on one single server, use the normal local primitives: `synchronized`, a mutex, atomic instructions. You don’t need Redis for that. [[L-0313]]

</Section>

<Section id="s6-3" no="6.3" title="A queue that protects nothing" crumb="6.3 Unprotected queue"
  dek="Queue 7 hands a message to anyone who asks. You can’t change it and can’t reach its server. One consumer at a time, please."
  meta="About 4 min · class 02:09–02:14, Q&A 02:40–02:43 and 03:04–03:06">

Here is the example. Hypothetically, someone built a very stupid remote queue that gives zero protection. Any consumer that asks makes an API call, the queue does `queue.pop` and returns the result. `queue.pop` is not thread safe, so if several consumers fire at the same moment, some of them may get the same message. [[L-0248]]

You are stuck with this queue. Call it queue 7. It is remote, like SQS, but forget SQS’s guarantees: this one gives none. Three consumers read from it. Throughput doesn’t matter, but exclusivity does: while one consumer is reading from the queue, the others can’t, and only when it is done may another read. [[L-0249]]

  <Desk><QueueSeven /></Desk>
  <Phone><QueueSeven layout="phone" /></Phone>
</Figure>

<PauseAndThink k="L-0248 L-0249 L-0250 L-0251 L-0252 L-0253 L-0254"
  q="Queue 7 is remote and hands a message to any consumer that asks. You can’t change the queue or touch its server. Can a <code>synchronized</code> block around <code>queue.pop()</code> in your consumer code keep two of your three consumers from reading at once?"
  choices={[{ label: 'Yes: synchronize the pop' }, { label: 'No: the consumers are on different machines', correct: true }]}
  right="Right. synchronized only coordinates threads that share memory."
  wrong="A synchronized block only works inside one process. Your consumers run on three machines.">

The obvious routes each fail on a constraint: a synchronized block (different machines), a lock on the queue’s server (no access), a gatekeeper layer in front (just another layer to protect), a process on the queue’s machine (still no access). What’s left is a lock manager the consumers all reach over the network: a store holding “queue 7 → consumer 1”.

</PauseAndThink>

Each of these ideas fails on one of the constraints. A synchronized block around the queue’s `get` or `pop` doesn’t work: the queue is remote and the consumers run on different machines. [[L-0250]] A lock taken on the server where the queue runs isn’t possible: the queue is a black box, you can’t change it, and you can’t access its server. [[L-0251]] An intermediate layer in front of the queue that lets one request through at a time was rejected too: it just adds one more layer in front of a queue you already have, while the goal is to implement a lock manager. [[L-0252]] And another process on the queue’s machine is out for the same reason as the server lock: for the consumers the queue is a black box exposing a single API call, and that call is unprotected. [[L-0253]]

Because the queue gives no protection and all you have is its network interface, you must implement the protection you need yourself. That is the remote lock. [[L-0259]]

### Real queues, and why the lock still binds [[rail: Real queues]]

The queue is deliberately hypothetical: it gives zero protection, and it was chosen as a constraint to understand remote locks, not as a design to re-architect real systems around. Some real queues hide a message from the other consumers as soon as one consumer receives it. Oracle Cloud’s (OCI) queue was the example raised in class (<Cite href="https://docs.oracle.com/en-us/iaas/Content/queue/overview.htm">docs.oracle.com</Cite>), and SQS works the same way: a received message stays invisible to other consumers for its visibility timeout, 30 seconds by default, and reappears if it isn’t deleted in time (<Cite href="https://docs.aws.amazon.com/AWSSimpleQueueService/latest/APIReference/API_ReceiveMessage.html">docs.aws.amazon.com</Cite>). That is not part of this example. [[L-0302]]

<ForwardChip block label="from" when="Lecture 2" k="L-0302">SQS’s visibility timeout: a received message is hidden from other consumers for a while</ForwardChip>

Real queues such as RabbitMQ, SQS and Kafka give the guarantee that a message is not handed to multiple consumers, so you don’t have to build anything around them. [[L-0303]]

<SourceNote href="https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/standard-queues-at-least-once-delivery.html" site="aws.amazon.com" k="L-0303">

RabbitMQ, SQS and Kafka keep two consumers from receiving a message at the same time, but they deliver at least once: a message can come back, even to another consumer, so processing must be idempotent. An SQS standard queue can return a copy of a message if a server was unavailable during the delete, and a message becomes visible again if processing outlasts its visibility timeout (<Cite href="https://docs.aws.amazon.com/AWSSimpleQueueService/latest/APIReference/API_ReceiveMessage.html">ReceiveMessage</Cite>). RabbitMQ likewise says consumers “must be prepared to handle redeliveries” (<Cite href="https://www.rabbitmq.com/docs/confirms">rabbitmq.com</Cite>); Kafka’s delivery semantics are described in its <Cite href="https://kafka.apache.org/43/design/design/">design docs</Cite>.

</SourceNote>

A fair objection: nothing connects Redis (or whatever store holds the lock) to the queue, so a consumer could simply read without taking the lock. It could, and then the same message could reach two consumers, which is exactly what must not happen. The protection holds because you write the consumer code yourself, and that code first takes the lock, then reads the message. That is the problem statement. [[L-0304]]

Can one consumer read many messages in parallel? It depends on the queue’s guarantees, and SQS, RabbitMQ and Kafka each differ; this hypothetical queue lets a consumer read one message. [[L-0334]] SQS, for instance, lets a consumer read 10 messages in one call; such details are in each queue’s documentation. [[L-0336]] How a queue lets many consumer threads read for maximum throughput is queue internal, a different discussion. [[L-0335]]

<Section id="s6-4" no="6.4" title="A database as lock manager, and why locks must expire" crumb="6.4 Lock in a database"
  dek="Store two things, the resource and its owner. Then ask what happens when the owner dies holding it."
  meta="About 4 min · class 02:14–02:18, Q&A 02:38–02:40 and 02:47–02:48">

The three consumers have to coordinate among themselves. So use a database as the lock manager. Create a key for the resource, say `Q7`, and store against it the consumer that is currently allowed to read from the queue. If the value is consumer 1, consumer 1 reads. Consumers 2 and 3 see a name that isn’t theirs and don’t read. [[L-0254]]

When consumer 1 is done, it removes its name. The entry is open again, and consumers 2 and 3 compete to put their name in. Say consumer 3 wins: it reads the next message, and the other two see consumer 3’s name and wait. [[L-0255]] This is a classic lock manager, and it stores exactly two things: what the resource is, and who owns it. [[L-0256]]

There is a catch. What if consumer 1 takes the lock and dies before it can delete it? Then nobody ever deletes it, and the lock is held perpetually by a consumer that no longer exists. So every lock entry needs a TTL, an automatic expiration: if the entry hasn’t been deleted after some time, it deletes itself. [[L-0257]]

<Figure id="fig-6b2" no="Fig 6·d" k="L-0254 L-0256 L-0257 L-0258"
  caption="The lock lives in a store every consumer can reach. Consumer 1’s name is in it, so consumer 1 reads; the others wait. The entry carries a TTL so a dead holder can’t keep it. Redrawn from the class board at 02:14–02:17.">
  <Desk><QueueSeven state={2} /></Desk>
  <Phone><QueueSeven layout="phone" state={2} /></Phone>
</Figure>

So the store must give you three things: key-value access, atomic instructions (so two consumers can’t both take the lock) and TTL. Redis gives all three, which is why the most common remote lock is built on Redis; the class called it Redlock. [[L-0258]] Precisely, the common remote lock is a single Redis instance taking `SET key value NX EX ttl`, and Redlock is the name of its multi-instance version, the subject of [§7](#s7) (<Cite href="https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/">redis.io</Cite>).

Notice the order the store was chosen in. First, what must be stored (the resource and its owner). Then the edge case (a holder dying without releasing). Then the features required from the database (key-value access, atomic instructions, TTL). Only then a database that offers them: Redis. [[L-0260]] Redis isn’t the only choice; DynamoDB is another. Redis is popular because it is in memory, and so fast. [[L-0262]]

In Redis the entry says: this resource is owned by this consumer right now, with an expiration of five minutes. On the board it read `queue7 : consumer 2`, `ex : 300`. If consumer 2 doesn’t delete it within five minutes, it expires on its own, so no lock is held forever and the system keeps moving. [[L-0263]]

### Could it be MySQL? [[rail: MySQL as lock store]]

Yes. The lock is just a row, and MySQL gives you atomicity, so it can be the lock store, provided you take care of TTL yourself. [[L-0296]] MySQL also has named locks built in: `GET_LOCK('q7', timeout)` returns 1 when it gets the lock, and the lock is released by `RELEASE_LOCK()` or implicitly when the holder’s session ends, normally or abnormally, so a crashed holder leaves no perpetual lock. It is local to a single `mysqld` (<Cite href="https://dev.mysql.com/doc/refman/8.4/en/locking-functions.html">dev.mysql.com</Cite>).

A cron job that expires stale locks can provide the TTL. [[L-0297]] The general lesson: focus on the core properties you need from a database, not on the database. If ZooKeeper gives you those properties, use it; if Redis, DynamoDB or MySQL does, use that, and then pick the stack you are comfortable with. [[L-0298]]

### Doesn’t the TTL cap how long I can work? [[rail: TTL limits]]

It does. A TTL bounds how long a process can hold the lock. But every implementation has this limit, and the alternative is the bigger risk: a perpetual lock, a lock or a consumed message that is never deleted, and the entire system stalls. [[L-0310]] Long jobs don’t need a long TTL, though. The holder can extend its lease while it is still working: Redis suggests a Lua script that resets the TTL only if the key still holds the holder’s value, and the DynamoDB lock client does the same with periodic heartbeats against a lease, for example a 3-second heartbeat on a 10-second lease (<Cite href="https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/">redis.io</Cite>, <Cite href="https://aws.amazon.com/blogs/database/building-distributed-locks-with-the-dynamodb-lock-client/">aws.amazon.com</Cite>).
