<Section id="s5-4" no="5.4" title="The whole design" crumb="5.4 Whole design"
  dek="Every box on one page, and the two paths through it: the request path a client takes, and the config path a change takes."
  meta="About 4 min · class 01:50–01:54, Q&A 03:25">

Put every piece on one page.

The final design has several LB servers, the orchestrator, the configuration database, an LB console where developers make changes directly, and a Prometheus server. Every server sends its vitals (CPU, memory, disk and so on) to Prometheus periodically, so all telemetry lands in one central place. The prepared page put the scaling rule in one line: scaling will happen on CPU, memory and the number of TCP connections. Where do we have this data? The monitoring component, Prometheus. [[L-0185]] The orchestrator periodically queries Prometheus to see whether the LB servers need to scale; when it sees the need, it scales them and makes an entry in the CoreDNS server. [[L-0222]]

<Figure id="fig-5c" no="Fig 5·c" k="L-0222 L-0225 L-0226 L-0229"
  caption="The request path is the only blue line, ① to ⑤; the config path is dashed, Ⓐ to Ⓓ, because no request waits on it. The thin control lines are the orchestrator’s health checks (hb), its query to Prometheus and its writes to CoreDNS, and Prometheus scraping every machine (drawn here to the backends) and feeding autoscaling, which acts through the LB console APIs: its arrow points into the console box. The board wrote “leaderElec” above the orchestrator. Redrawn from the class’s prepared page shown at 01:51.">
  <Desk><FinishedDesign /></Desk>
  <Phone><FinishedDesign layout="request" /><FinishedDesign layout="config" /></Phone>
</Figure>

**The request path.** The client is anyone who needs a human-readable name resolved. Its request for, say, `payments.lb.google.com` goes to CoreDNS ①, which returns an IP address ②. The client connects to that LB server ③. The LB server picks a backend by its balancing strategy ④, the backend does whatever processing it needs, and the response goes back to the user ⑤. [[L-0225]]

**The config path.** Whenever the configuration changes, because a health check failed, autoscaling kicked in, or a developer changed something, the change is written to the database Ⓐ. Then either CDC kicks in Ⓑ, or the LB server or the orchestrator pushes a message to the Redis broker. Because it is a real-time Pub/Sub, the message reaches all the LB servers at once Ⓒ, and each updates its in-memory copy of the configuration Ⓓ. [[L-0226]] (Redis Pub/Sub delivers at most once, so a server that was disconnected re-pulls the full config when it reconnects; see the note in [§4.5](#s4-5).)

<MarginNote title="Read next: the Maglev paper" why="skip unless you read papers" k="L-0229">

Much of this design is taken from Google’s Maglev paper, “Maglev: A Fast and Reliable Software Network Load Balancer” (<Cite href="https://research.google/pubs/maglev-a-fast-and-reliable-software-network-load-balancer/">research.google</Cite>). In the lecture’s view it is really easy, not difficult at all; it was one of the first papers the instructor ever read. After this chapter it will make a lot more sense, and it gives more granular detail on the parts covered here. [[L-0229]]

</MarginNote>

That is the load balancer: an extremely low-level implementation in [§3](#s3), then a high-level design. A few things on the drawing are sneak peeks of what comes in later weeks, and locks come next, in [§6](#s6). [[L-0230]]

</Section>

<Section id="s5-5" no="5.5" title="Who watches the watcher?" crumb="5.5 Watcher"
  dek="The orchestrator runs as a leader with working followers. It holds no state, so a follower takes over in seconds; one tiny global monitor ends the recursion."
  meta="About 6 min · Q&A 03:15–03:17, 03:23–03:25 and 03:34–03:36">

The orchestrator now updates the database, DNS and the LB fleet. What if it goes down?

One proposal from class: run three orchestrators with the same code, two of them idle until the active one fails. The refinement: not idle. [[L-0352]] Without that, the orchestrator is a single point of failure, and its going down is not fine. The fix is leader–follower: one master, and followers that do the grunt work instead of waiting. If the master goes down, a follower automatically takes its place, with one or two seconds of downtime. That is leader election. [[L-0351]]

<Figure id="fig-5d" no="Fig 5·d" k="L-0351 L-0352 L-0366 L-0367 L-0379 L-0380 L-0381"
  caption="The leader has just failed (red), and a follower takes over as leader. It copies nothing first, because every piece of state is in the config database; it simply starts sending the health checks. Above the orchestrators sits one global monitor with a standby, the base of the recursion.">
  <Desk><BaseOfRecursion /></Desk>
  <Phone><BaseOfRecursion layout="phone" /></Phone>
</Figure>

Every component of this design is highly available: the backend clusters through autoscaling, the LB servers, the database, the orchestrator through leader election, and, as listed in class, CoreDNS through leader election. [[L-0353]] CoreDNS doesn’t need an election, in fact: it is stateless, so you run several replicas and clients list several nameservers, up to three, tried in order (<Cite href="https://man7.org/linux/man-pages/man5/resolv.conf.5.html">man7.org</Cite>).

Leader election is a way to get high availability. The alternative is a human who spins up a replacement server when one goes down. Leader election automates that whole process: when one node goes down, another takes its place on its own. [[L-0354]] ZooKeeper documents a standard recipe for it: each candidate creates an ephemeral, sequential znode, and the one with the lowest sequence number is the leader. When the leader fails, its ephemeral znode disappears, and the candidate watching that znode takes over, without every candidate waking up at once (<Cite href="https://zookeeper.apache.org/doc/current/recipes.html">zookeeper.apache.org</Cite>).

<ForwardChip block label="later in the course" k="L-0354">leader election, in depth</ForwardChip>

Do the leader and its followers need to replicate state between themselves? No, because the orchestrator is stateless. All the state, the IPs of the LB servers and the backend servers among it, is in the database. The orchestrator keeps nothing in memory; it just fires queries to check whether the LB servers need to scale up or down. [[L-0366]] After a failover the new leader simply starts making the health-check HTTP requests. The servers don’t need to know who the leader is: they answer whoever asks. [[L-0367]]

Then who monitors and scales the orchestrator itself? It runs in multi-node mode, one master and several followers, so if the master goes down a follower takes over, and the orchestrator as a whole never goes down. [[L-0379]]

And above it, as in any infrastructure, there is always a global monitoring service, something like Prometheus, watching all the VMs and the key components, including the master orchestrators. It has its own leader and very minimal duties: check each master, and react if something goes down. The probability of that going down is minimized by having a standby. (From the recording it isn’t clear whether “that” is the master orchestrator or the monitor.) [[L-0380]]

That monitor is the base condition of the recursion: an orchestrator for the orchestrators, which watches their master nodes and triggers a leader election or adds worker nodes when needed. It is the final level, because its responsibilities are so small. [[L-0381]]

</Section>

<Section id="s5-6" no="5.6" title="Public front doors, private load balancers" crumb="5.6 Front doors"
  dek="Users resolve the public name and land on an API gateway. The gateway reaches the load balancer by its private name, through CoreDNS."
  meta="About 5 min · class 01:56–01:59, Q&A 03:17–03:21">

A customer types `payments.google.com`. Do they ever see `payments.lb.google.com`?

External end users don’t use your CoreDNS. The DNS address configured in their operating system points to public DNS, Route 53 for example, not to a private DNS server. [[L-0236]] More precisely, their machine asks a public recursive resolver, which asks the domain’s authoritative DNS service, such as Route 53, for the answer (<Cite href="https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/Welcome.html">aws.amazon.com</Cite>).

If a load balancer serves external users, it is public. Then the private CoreDNS doesn’t come into the picture at all: the load balancer’s name is resolved by public DNS, like any public name. [[L-0237]]

Does adding LB servers then update public DNS? “Kind of.” There is an intermediate proxy layer in between that takes care of it. There are seven different layers in which resolution happens, left out here to keep the design simple; every LB server still has a domain name, just not necessarily a public one. The details are proprietary, and the Maglev paper explains more. [[L-0238]]

<ForwardChip block label="not covered in class" k="L-0238">the other proxy layers (“seven more”); start with the Maglev paper</ForwardChip>

So the design so far oversimplified one thing. The LB servers are not the first layer of interaction: there are more machines and proxies in front of them, and it is the architecture you define that decides what is private and what is public. [[L-0356]]

Here is the usual shape. You don’t expose `payments.lb.google.com` to users; you expose `payments.google.com`. In public DNS, `payments.google.com` points to the API gateway’s IP address, so the user’s TCP connection goes to the API gateway. The gateway’s configuration says “if you get this path, forward it to this load balancer”. [[L-0357]] The load balancer has a domain name, and when the API gateway opens its TCP connection to it, the private CoreDNS comes into the picture. That is two layers: the API gateway for public calls, the load balancer private. [[L-0358]] You can add three or four more, because the API gateway is typically not the first point of entry, as most people think. [[L-0359]]

<Figure id="fig-5e" no="Fig 5·e" k="L-0236 L-0356 L-0357 L-0358 L-0359 L-0361"
  caption="Public on the left of the dashed line, private on the right. The gateway resolves the load balancer’s name in the private CoreDNS, as any client would. The ghosted boxes are the proxy layers that often sit in front of the gateway; they are not covered here.">
  <Desk><FrontDoor /></Desk>
  <Phone><FrontDoor layout="phone" /></Phone>
</Figure>

None of this is forced. On AWS, GCP and elsewhere you can put the LB’s address straight into public DNS, bypass the API gateway, and expose `payments.lb.google.com` to the internet, and that is fine. In reality you expose payments and keep the load balancers private. Either way, whoever connects to the LB servers has to talk to the DNS that holds their name: the private one for a private load balancer. [[L-0361]]

One summary was offered in class, tied back to an earlier discussion: choose what needs the least configuration and accepts a compromise under partition while keeping the rest of the good properties. It got no direct answer, and it is left here as the class’s open thought. [[L-0360]]

</Section>

<Section id="s5-7" no="5.7" title="What a load balancer is, and is not" crumb="5.7 Is and is not"
  dek="A load balancer spreads load over identical servers. Sessions fit inside it; extra services and authentication don’t."
  meta="About 5 min · class 01:59, Q&A 03:08–03:10 and 03:21–03:23">

Three tempting requests: put sessions in the load balancer, put authentication in it, and is a load balancer just a reverse proxy?

First, what it is for. A load balancer balances across a homogeneous set of servers. It is not an API gateway. Every service has its own load balancer, with its own LB servers and its own entries in CoreDNS. [[L-0239]]

**Sessions.** To keep one user on one server, should you add a separate session service, or route a user’s requests to the same server with consistent hashing? Consistent hashing, in the load balancer. A separate service adds a network hop, for nothing. [[L-0340]] nginx, for instance, offers `hash $key consistent`, which uses ketama consistent hashing, so adding or removing a server remaps only a few keys, where a plain hash can remap most of them (<Cite href="https://nginx.org/en/docs/http/ngx_http_upstream_module.html">nginx.org</Cite>). Consistent hashing is not a service. It is a normal array of data in the LB server’s memory: a request comes in, the LB server finds where to send it, and sends it. [[L-0341]] (Round robin needs no session service either: one integer, as in [§2.2](#s2-2).)

Don’t add services, random boxes, to a design for the sake of it. Every service is a network hop and slows things down; unless there is a very good justification, find the shortest path possible. [[L-0342]] Every network call adds roughly three to five to 10 milliseconds of latency, and at scale teams optimize for every microsecond and challenge every single network hop. [[L-0343]] For scale, a round trip inside one datacenter is about 0.5 ms (Jeff Dean’s figures, around 2012; <Cite href="https://gist.github.com/jboner/2841832">github.com</Cite>), and AWS describes latency between Availability Zones in a region as single-digit milliseconds (<Cite href="https://docs.aws.amazon.com/whitepapers/latest/aws-fault-isolation-boundaries/availability-zones.html">aws.amazon.com</Cite>). So a 3–10 ms budget per service hop covers much more than wire time: serialization, TLS, queueing and the handler itself.

<MarginNote title="From practice: four services, petabytes" why="skip unless you count services" k="L-0344">

A good architecture the instructor has seen had only four microservices, and it handled petabytes of data. [[L-0344]]

</MarginNote>

**Reverse proxy.** Load balancers are reverse proxies: a load balancer balances load across a homogeneous system, which is exactly what a reverse proxy does. If you have used a load balancer, you have used a proxy; “reverse proxy” is the generic term, and an nginx reverse proxy is no different in kind. [[L-0362]] API gateways are powered proxies. [[L-0363]]

**Authentication.** User authentication doesn’t belong in the load balancer. It is part of the business logic: when money moves from A to B, verifying that it really is A making the transfer is the service’s job, and the load balancer doesn’t care. The backend service handles it and sends the user an error such as 404 or 403. [[L-0364]] Some managed load balancers can take on the login step itself: an AWS Application Load Balancer can authenticate users through an OIDC identity provider or Amazon Cognito before forwarding, and passes the signed user claims to the targets in the `x-amzn-oidc-data` header (<Cite href="https://docs.aws.amazon.com/elasticloadbalancing/latest/application/listener-authenticate-users.html">aws.amazon.com</Cite>). Deciding whether A may pay B stays in the service.

<RecallQuestions>
  <RecallItem k="L-0216 L-0218 L-0225" q="Walk the request path for <code>payments.lb.google.com</code> in four steps, and mark which steps DNS is not part of.">

(1) The client asks CoreDNS for the name. (2) CoreDNS answers with one LB server’s IP, and the client caches it. (3) The client connects to that LB server itself. (4) The LB server picks a backend by its strategy, proxies the request, and the response comes back through it. DNS is not part of steps 3 and 4: it never sees the request, so it is not a proxy and not a bottleneck on the request path.

  </RecallItem>
  <RecallItem k="L-0231 L-0232 L-0220" q="A cached IP points at a dead LB server. What does the client do, and why not wait for the TTL?">

In the class’s design, when the connect fails, the client invalidates its cached entry at once and asks CoreDNS again, which gives it another LB server’s IP. Waiting for the TTL would leave the site unavailable to that client for no reason; you react when it hurts, the way you go to the dentist with a toothache instead of waiting for the next check-up.

  </RecallItem>
  <RecallItem k="L-0366 L-0367 L-0351" q="Why can the orchestrator’s followers take over in seconds without copying any state?">

Because the orchestrator is stateless. Every LB server and backend IP, and the configuration, lives in the database, so a new leader has nothing to catch up on. It simply starts sending the health-check requests, and the servers answer whoever asks; they don’t need to know who the leader is.

  </RecallItem>
</RecallQuestions>
