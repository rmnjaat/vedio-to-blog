You are about to design something that runs on many machines. Where do you start, and what does “distributed” even promise?

This chapter answers both before any box is drawn. The load balancer built in the chapters after it is built exactly this way: one machine first, then each part scaled, broken and fixed in turn.

<Section id="s1-1" no="1.1" title="What “distributed” means" crumb="1.1 Distributed"
  dek="Not a bunch of machines: one coherent system, from the outside."
  meta="About 3 min · class 00:09–00:12">

“Distributed systems” is, in this lecture’s view, one of the most misused terms in the age of social media: people call anything a distributed system. It isn’t that simple. [[L-0021]]

What a distributed system gives you is the ability to **abstract out the distributedness**. Behind it, a huge set of machines each do their own job; to an outsider it is one single coherent system. The board put it in one line: multiple components on multiple machines form a single coherent system, which solves a bigger problem. [[L-0022]]

The outsider is contextual. It may be an end user, another microservice or an internal portal; whoever it is, the complexity of running on different machines is hidden from them, and they see one system. [[L-0023]]

Facebook.com is one website to its users, and a college student may well think they could build it. At scale, though, many different kinds of services have to interact just to render a simple home feed. That hidden cooperation is what a distributed system is about. [[L-0024]]

It is tempting to think that any set of remote machines talking to each other is a distributed system. It isn’t: many people believe they have one when all they have is a bunch of remote machines talking to each other. What it takes to deserve the name is the subject of [1.3](#s1-3). [[L-0035]]

<MarginNote title="Why this subject gets skipped" why="skip unless you like the history" k="L-0002 L-0003">

In the instructor’s own degrees, distributed systems was one of the most neglected subjects: no one wanted to take it. Yet as soon as people enter industry, distributed systems are everywhere. [[L-0002]] The core algorithms in the literature are the theoretical foundation; it is when real systems are discussed that you see how those pieces fit into place. [[L-0003]]

</MarginNote>

### Love it, hate it

A professor who had published many papers on distributed systems used to say that you fall in love with distributed systems if you understand them well, and you hate them when you understand them well. [[L-0025]]

The hate part: imagine a distributed transaction during which things break, and the data lands in an inconsistent state you never considered while designing. That is data corruption. The love part: when you start building one, it is great, because you can scale horizontally. [[L-0027 L-0028]]

The reason for the hate is on the board: “The best and the worst thing about distributed systems is: anything that could go wrong would go wrong.” Murphy’s law. A condition you were sure would never happen happens the next day and takes your system down, and if you don’t handle such a scenario, you are not guaranteeing the correctness of your system. [[L-0026]]

<RuleBox rule="Assume ==anything and everything will go wrong==, then check whether your code and your system handle it." k="L-0029 L-0026">

This is the key idea for approaching any distributed system, taken literally. Every condition you were tempted to skip as “never happens”: a crash, a slow response, a cut network link. Write it down, then ask what your code does when it happens.

<Section id="s1-2" no="1.2" title="Day zero, then scale each component" crumb="1.2 Day zero"
  dek="Start with one of each. Grow by a loop, not by a plan for a million users."
  meta="About 3 min · class 00:12–00:15 and 00:44">

<NotationKey />

A team is about to build “for a million users”, and it is their first day. Where should they start?

What follows is one engineer’s approach, “so take it with a pinch of salt”, though it has worked extremely well for the truly distributed systems it was used on. Always start with the **day-zero architecture**, and don’t overcomplicate it: one machine, one server, one database, one cache. That’s it. [[L-0030]]

Then **scale each component independently**, see how it performs under load, rectify the system, re-architect, and repeat. [[L-0031]]

  <Phone><DayZeroLoop layout="phone" /></Phone>
</Figure>

When you watch how the system performs under load, the high-level picture isn’t where the trouble is. The **low-level details** are the pain points. That is where the time goes: understanding what happens at the code level in the service you wrote, what is going wrong, and how to fix it. The load balancer in this lecture is taken down to that level. [[L-0032]]

This is the **incremental approach** to system design, and since system design is about building distributed systems, it fits. In complex systems you will always see people iterate this way: day zero, then scale independently, step by step. [[L-0033]]

It is like looking at a culture under a microscope. You zoom in and find something; you zoom further into finer detail and see a whole new world. Each turn of the loop zooms in on granular details and fixes them. [[L-0034]]

The opposite habit gets a blunt verdict: thinking about scale on day zero is the worst way to build a system. Think simple. The load balancer starts exactly this way, as one machine, in [3.2](#s3-2). [[L-0104]]

</Section>

<Section id="s1-3" no="1.3" title="Every layer must scale out" crumb="1.3 Every layer"
  dek="Autoscaled API servers are one layer. Check all of them, and know what one server can carry."
  meta="About 3 min · class 00:14–00:18">

“We have autoscaling on the API servers, so we’re horizontally scalable.” This section is about why that sentence isn’t enough.

Why build a distributed system at all? It handles scale with a large number of machines, but more importantly it must be **horizontally scalable**: that is precisely why you build one. The board’s list under “Why distributed systems?” reads: scale, horizontal scalability, fault tolerance. [[L-0036]]

Horizontal scalability doesn’t come from having more machines, or from a set of API servers that scale automatically. Nor does it mean an autoscaling policy that triggers and adds servers when load rises; it is much more than that. Think of every single layer in your architecture, and check whether each one scales horizontally. [[L-0037 L-0040]]

A layer that is not horizontally scalable is, in the lecture’s words, a single point of failure. [[L-0038]]

<SourceNote href="https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Concepts.MultiAZSingleStandby.html" site="docs.aws.amazon.com" k="L-0038">

A layer that cannot scale horizontally is a **bottleneck**; if it also has no standby or failover, it is a single point of failure. An RDS Multi-AZ database is the counter-example: AWS keeps a synchronous standby in another Availability Zone for automatic failover, but notes that this “isn’t a scaling solution”, because the standby can’t serve reads. Redundancy (no single point of failure) and scale-out (more capacity) are separate properties.

</SourceNote>

Right from the database: database, cache, stateful services, stateless services, API servers, load balancer, CDN. Every single component of whatever system you design needs to be horizontally scalable. [[L-0039]]

### Know what one server can carry

Horizontal scalability also implies that you know the **unit economics** of your service: how many requests each of your servers can handle. That number is what lets you do **linear amplification**, adding machines in proportion to load, and linear amplification is a requirement for a good distributed system. The load may be API load, processing load or something else; what matters is how much of it each machine can take. [[L-0041]] Requests are not the only possible unit: Google’s SRE book warns that queries per second is a poor capacity measure when different queries cost different amounts, and recommends measuring capacity directly in resources, with CPU consumption alone working well as the provisioning signal in most cases (<Cite href="https://sre.google/sre-book/handling-overload/">sre.google</Cite>).

Without that number you are playing with fire: adding machines without much thought, leaking money in most cases, and either under-provisioning or over-provisioning. [[L-0042]]

The number varies with the service, which is why you have to understand the limitation of each server, across all the layers: database, API server, everything. “My API servers scale, so I’m a distributed system” is not a distributed system. [[L-0043]]

The rule has an escape hatch, added straight away. In some cases you cut corners: a database that isn’t horizontally scalable is perfectly fine as long as it can handle the load. [[L-0044]]
