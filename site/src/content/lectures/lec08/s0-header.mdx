Your payments service runs on three servers behind one name. One of them crashes. For how many seconds do customers’ payments keep failing, and what decides that? The answer sits inside a rectangle that almost every system diagram has and almost nobody opens: the one labelled “load balancer”. [[L-0046 L-0170]]

Somebody wrote that box. It is a program, and its core is about ten lines of code. In this lecture you write it, then keep it working: one address that never changes, requests spread sensibly over the servers behind it, and as few failed requests as possible when a server dies, when one machine is no longer enough, or when one of the machines you added to fix that dies too. ### Where you are

Every lecture so far has drawn this box without opening it. <LectureLink lec="lec04">Lecture 1</LectureLink>’s day-zero design already had users, a load balancer, an API server and a database, and its heartbeat story ended on a promise: the signal that turns a silent user grey is the one a load balancer uses to stop sending requests to a dead server. <LectureLink lec="lec01">Lecture 2</LectureLink> scaled the Medium-like blog’s API servers out behind a load balancer and sized the fleet by dividing the peak load by what one machine can serve. <LectureLink lec="lec05">Lecture 3</LectureLink> locked airline seats inside one database, which kept track of who held each lock by itself. <LectureLink lec="lec02">Lecture 4</LectureLink> pushed Slack’s messages between servers through a real-time Pub/Sub.

Each of those pieces turns up again here, inside the box or right next to it.

### What you’ll build

**Build 1, a load balancer (chapters 1–5).** It starts as one process on a laptop that copies bytes between two connections. Then it runs out of room, and you grow it into a fleet of machines that must agree, at every moment, on which servers are alive. Every machine you add raises the question this lecture keeps asking: what happens when *this one* dies? [[L-0029]]

**Build 2, a lock across machines (chapters 6–8).** Once work runs on many machines, two of them can reach for the same thing at the same moment, and no single database is there to keep them apart. Three consumers on three machines read from a remote queue that hands the same message to anyone who asks, and you can’t change the queue. You build a lock they all respect, with nothing shared between them but the network, and then ask Build 1’s question of it: what if the lock’s own server dies? [[L-0011 L-0248]]

The two builds share one habit. After every line of the design, assume something lags or dies right there, and check that the system still holds. [[L-0274]]

### What you’ll be able to do

- Explain what a load balancer does to every byte of a request, and build one on a laptop.
- Pick a balancing algorithm from the shape of your servers and your traffic.
- Keep a fleet of load balancers in step with the backends, without a window of errors when one dies.
- Point clients at many machines through one name, and say what DNS does and doesn’t do.
- Find the single point of failure in a design, and say whether a fix buys capacity or survival.
- Lock a shared resource across machines safely, and say what it costs to make that lock survive a crash.

### Before you start

You need the basics of TCP (a connection between an IP address and a port), HTTP running over TCP, and threads. The code is short Go and Python; any language with sockets and threads works the same way. [[L-0123]]

Nothing here needs a cloud account. The load balancer runs as four processes on one laptop, and the last chapter’s five lock servers as five processes on one laptop. Each chapter opens with a small map of the design so far. When a “Pause and think” box asks you something, commit to an answer before you open it. [[L-0321]]
