<Section id="s7-1" no="7.1" title="What does a plain DEL delete?" crumb="7.1 Release">

<PauseAndThink k="L-0268 L-0269"
  q="Consumer 1 takes the lock with a five-minute expiry, but its job takes six. When it finishes, it releases with a plain <code>DEL queue7</code>. Is that safe?"
  choices={[{ label: 'Yes: it is releasing its own lock' }, { label: 'No', correct: true }]}
  right="Right."
  wrong="It was its lock five minutes ago.">

At five minutes Redis expires the key, and consumer 2’s next `SET` succeeds. At six minutes consumer 1’s `DEL` removes consumer 2’s lock, while consumer 2 is still working.

</PauseAndThink>

So the first rule of releasing: **never delete a lock that isn’t yours**. Before deleting, read the key and delete it only if it still holds your token. [[L-0270]] That is why the value is a token and not just “locked”: it is how a consumer recognises its own lock.

</Section>

<Section id="s7-2" no="7.2" title="Check the owner in your own code. Is that enough?" crumb="7.2 One step">

Written in Python, the check looks harmless:

```python
if r.get("queue7") == token.encode():   # still mine?
    r.delete("queue7")                   # … then release
```

Now imagine the program stalls for a moment between those two lines. `GET` returns consumer 1’s token. Right then, the key expires; consumer 2 takes the lock; and then consumer 1’s `delete` runs, removing consumer 2’s lock. The condition was true when it was checked and false when it was acted on. [[L-0271]] Edge cases like this are where distributed systems get their reputation: miss one, and your system is simply not correct. [[L-0272]]

The check and the delete have to be one step that nothing can come between, and only Redis can make it one. Redis runs Lua scripts sent with `EVAL`, and while a script runs, Redis runs nothing else, so no other consumer can take the lock halfway through. It behaves a little like a transaction. [[L-0273]] Lua itself is nothing special here; the atomicity comes from Redis running the script inside the server. Your program stays in Python and sends the script like any other command. [[L-0299 L-0300]]

```python
RELEASE = """
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
end
return 0
"""
r.eval(RELEASE, 1, "queue7", token)   # 1 if released, 0 if the lock wasn’t ours
```

  caption="The lock expires under consumer 1, consumer 2 takes it, and consumer 1’s blind DEL removes consumer 2’s lock. The replay checks the owner and deletes in one atomic step." />

The habit behind this fix is worth more than the fix. When you design a distributed system, imagine that after every single line, something lags or goes down, and check that the system still holds. “I’ll take a lock” is not a design; the lines around it are. [[L-0274]]

<MarginNote title="Go deeper: the job really needs six minutes" why="skip unless your jobs run long" k="L-0310">

A TTL caps how long you may hold a lock, and every lock with expiry has that cap; without it you risk a lock nobody ever frees. Long jobs don’t need a long TTL, though. Keep the TTL short and let the holder extend it while it is still working: in Redis, a small script that resets the expiry only if the key still holds its token. The DynamoDB lock client does the same with heartbeats against a lease, for example a heartbeat every 3 seconds on a 10-second lease.

</MarginNote>

</Section>

<Section id="s7-3" no="7.3" title="Does the lock have to live in Redis?" crumb="7.3 Other stores">

No. What you need is the three properties from chapter 6, key-value access, an atomic way to take the lock, and expiry, and anything that offers them will do. Think in properties, then pick the stack you are comfortable with. [[L-0013 L-0298]]

**A MySQL row** works: the lock is one row, and the database’s atomicity makes taking it safe, as long as you handle expiry yourself. A cron job that clears stale locks will do it, coarsely, since a stale lock survives until the next run; checking an `expires_at` column in the statement that takes the lock is tighter. MySQL also has named locks built in: `GET_LOCK('queue7', 10)` returns 1 when you get the lock, and the lock is released when your session ends, normally or not, so a crashed holder process frees it (a holder whose machine vanishes frees it only when MySQL drops the idle connection, which you should set to a short timeout). It lives on a single MySQL server. [[L-0296 L-0297]]

**A server that accepts one connection at a time** works too, and you already have most of the code. Take chapter 1’s accept loop, and instead of handing each connection to a goroutine and looping back, accept one connection and serve it until it closes. The server writes one byte, “granted”, to the connection it accepts, and every client blocks reading that byte before it touches the queue. Whoever has received it holds the lock until it closes the connection. It is a fundamental idea, and a few hours of work to build. [[L-0289 L-0291 L-0295]]

<Figure id="fig-7b" wide={false} no="Fig 7·b" k="L-0289 L-0291" caption="A lock with no Redis: a TCP server that serves one connection at a time. It has accepted consumer 1’s connection and sent it “granted”: that is the lock. The other consumers are connected too, but wait in the server’s backlog for their own “granted”.">
<OneConnectionLock />
</Figure>

Two details decide whether it holds up. The other clients aren’t turned away: the operating system completes their connections and parks them in the server’s backlog. Their `connect` has already succeeded, which is why they must wait for the byte: until it arrives, an open connection means nothing. Once the backlog is full, new clients are refused or simply left retrying, depending on the operating system. And if the holder’s *process* crashes, its connection closes and the lock is free; but if the holder’s *machine* dies or drops off the network, the server’s socket can stay open for a long time (TCP keepalive is off unless the program turns it on, and Linux’s default waits two hours before the first probe. Go’s listener does turn it on, and even then a dead peer takes a couple of minutes to notice), so this lock needs a timeout of its own. [[L-0293]]

Look at what Redis, the MySQL row, `GET_LOCK` and the one-connection server have in common. Each lock lives on exactly one server.

</Section>
