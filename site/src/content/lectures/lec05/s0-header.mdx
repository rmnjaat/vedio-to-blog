A flight has 120 seats. All 120 passengers reach the airport at the same moment, walk up to 120 kiosks and tap “check in” together. Each kiosk has to give its passenger one seat, and no seat may end up with two passengers. [[L-0069 L-0063]]

You will write that booking code, and the first versions will look correct. Run them with 120 people at once and they aren’t. This lecture finds out why, and fixes it one SQL clause at a time.

### Where you are

<LectureLink lec="lec04">Lecture 1</LectureLink> built a green dot and a blog on top of a database, and treated that database mostly as a place to put rows. <LectureLink lec="lec01">Lecture 2</LectureLink> showed the first crack: two readers clap on a post at the same instant, both read 100, both write 101, and one clap disappears without an error, because reading a value and writing it back is not one step. You saw the general cure, a lock around the critical section, and that the database has guarantees of its own. [[L-0022 L-0018]]

This lecture opens the database up. What exactly does it give you when many transactions reach for the same rows, what does each tool cost, and which one fits which job?

### What you’ll build

**Build 1, the airline check-in (chapters 1–4).** Six small versions of one booking program, each run with 120 passengers at once. You watch the early ones fail, find the gap they fail in, and change the query a few words at a time until it is correct, and then until it is fast. Then you look at where else the same shape turns up. [[L-0070 L-0125]]

**Build 2, a key-value store on one MySQL table (chapters 5–9).** The check-in leaves one loose end: a seat held while someone pays has to be released by itself if the payment never comes. Values that must vanish on their own after a set time are what a key-value store with a TTL is for. <LectureLink lec="lec04">Lecture 1</LectureLink>’s green dot leaned on one. Here you build one, `GET`, `PUT`, `DELETE` and per-key expiry, on a single MySQL table, so that every decision inside it shows up as a SQL clause you can read and cost. Row fights are no longer the main danger. The danger is quieter: a query that reads every row to find a few, a 10 MB value sent across the network for nothing, a disk write that buys nothing. [[L-0005 L-0168 L-0172 L-0346]]

The first build teaches what one SQL clause can do to correctness and speed. The second makes that a habit: before you accept a query, ask what each part of it costs.

### What you’ll be able to do

- Make “give each person any free item” correct under heavy concurrency, then fast, and say when a request must wait for one specific item instead.
- Tell waiting from deadlock, and know what the database does when transactions lock each other out.
- Recognise the systems that need locking before you write a line of them.
- Design per-key expiry on a disk-based table so that cleanup stays cheap.
- Count the network trips and disk writes behind a query, and remove the ones you don’t need.
- Grow a single-node store with replicas and range shards, and say what still holds once it is split.

### Before you start

You need SQL basics (`SELECT`, `UPDATE`, primary keys, indexes) and what a transaction is: begin, commit, abort. The check-in demo is a small Go program that runs one goroutine per passenger; any language with threads works the same way. [[L-0071]]

Everything here runs on a laptop: one MySQL server for both builds, and two (plus a replica) for the last exercise. You don’t build the airline: you build only the part you want to understand, the database part, as a small prototype. [[L-0059]] Each chapter opens with a small map of the design so far. When a “Pause and think” box asks you something, commit to an answer before you open it.
