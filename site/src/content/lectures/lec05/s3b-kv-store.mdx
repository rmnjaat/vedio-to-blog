<Section id="s3-5" no="3.5" title="Put is an upsert" crumb="3.5 Put"
  dek="The second put of the same key must replace the value. Reading first costs a round trip; one upsert statement doesn't."
  meta="About 10 min · class 01:50–02:02, 02:04–02:06, Q&A 03:01–03:04">

`PUT k1 v1`, then `PUT k1 v2`. The obvious implementation of a put is an insert that passes all three columns: the key, the value and `expired_at`. [[L-0204]]

```sql
INSERT INTO store VALUES ('k1', 'v1', e);   -- PUT k1 v1: the row is inserted
INSERT INTO store VALUES ('k1', 'v2', e);   -- PUT k1 v2: fails, k1 already exists
```

The first put inserts the row. The second fires the same insert again, and it fails, because the key is the primary key and `k1` already exists. [[L-0205]]

Two fixes are tempting. One adds a WHERE clause about expired values to the insert. That misses the point: when you do a put, you expect it to replace the value that is there. [[L-0206]] The other marks the old row as expired and inserts a new row with the same key. That still has to read the key first, and the key is the primary key: two rows with it cannot exist. [[L-0209]]

The naive fix that works: GET the key every time, then UPDATE if it exists or INSERT if it doesn't. Now every put is a get plus a put, and fetching the key is pure overhead. The lecture's word for it is pathetic: it slows the system down by a massive margin. [[L-0207]] It is also racy: two concurrent puts can both see "key absent", and one INSERT then fails on the primary key <Cite href="https://www.postgresql.org/docs/current/sql-insert.html">postgresql.org</Cite>.

So state what a put needs: insert if the key does not exist, update if it exists, without getting the key first. [[L-0208]] The devil lies in the details. People draw boxes and never think about implementation; think about the implementation and you see how costly get-then-write is. [[L-0210]]

<PauseAndThink k="L-0205 L-0207 L-0208 L-0211 L-0212 L-0215 L-0216 L-0328"
  q="<code>PUT k1 v1</code> inserts a row. <code>PUT k1 v2</code> runs the same INSERT and fails: the key is the primary key. How should a put work?"
  choices={[{ label: 'Read the key first, then INSERT or UPDATE' }, { label: 'One statement that inserts, or updates if the key exists', correct: true }]}
  right="Right. An upsert does both atomically, in one round trip."
  wrong="Works, but costs: a read plus a write is four network trips instead of two, a transaction wrapped around both, and a race when two puts both see the key as absent.">

Every major database has an upsert, with its own spelling: MySQL `INSERT … ON DUPLICATE KEY UPDATE` (or `REPLACE INTO`, which deletes and re-inserts), PostgreSQL `INSERT …` `ON CONFLICT (key) DO UPDATE`. The database still reads the row, but your API server doesn't fetch it over the network.

</PauseAndThink>

The answer proposed in class: insert the row, and if it exists, update it. That is an upsert, done at the database level. [[L-0211]] Upserts are atomic: one SQL query, wrapped in a transaction, with no need to get the row, check whether it exists and then write it inside a transaction of your own. [[L-0212]]

Check whether the database you choose supports upserts. In Postgres, as the lecture put it, you just replace INSERT with UPSERT. [[L-0213]] Every database supports it, each with its own clause: Postgres calls it upsert; MySQL has `REPLACE INTO` or `ON DUPLICATE KEY UPDATE`. Pick whatever your database supports. [[L-0216]]

<SourceNote href="https://www.postgresql.org/docs/current/sql-insert.html" k="L-0213 L-0216">

PostgreSQL has no `UPSERT` keyword. You write an INSERT with `ON CONFLICT (key) DO UPDATE`, setting `value = EXCLUDED.value`, where `EXCLUDED` is the row proposed for insertion (`MERGE` is an alternative); the code below has the full statement. In MySQL, an INSERT with `ON DUPLICATE KEY UPDATE` modifies the existing row in place, while `REPLACE INTO` "either inserts, or deletes and inserts" <Cite href="https://dev.mysql.com/doc/refman/8.4/en/replace.html">dev.mysql.com</Cite>, so for a put that replaces a value, `ON DUPLICATE KEY UPDATE` avoids the extra delete.

</SourceNote>

```sql
-- MySQL: update in place                                   saves: a network round trip
INSERT INTO store (`key`, value, expired_at) VALUES ('k1', 'v2', e) AS new
  ON DUPLICATE KEY UPDATE value = new.value, expired_at = new.expired_at;

-- MySQL, as on the board: REPLACE INTO store VALUES ('k1', 'v2', e);  -- deletes and re-inserts

-- PostgreSQL
INSERT INTO store (key, value, expired_at) VALUES ('k1', 'v2', e)
  ON CONFLICT (key) DO UPDATE SET value = EXCLUDED.value, expired_at = EXCLUDED.expired_at;
```

With an upsert, `PUT k1 v1` stores `v1` with its expiration, and a later `PUT k1 v2` just replaces it with `v2`: update if the key exists, insert if it doesn't ([Fig 3·a, step 5](#fig-3a/step-5)). [[L-0214]]

Why is it faster? The database still reads the row. What you avoid is the network IO of bringing the data to your API servers, a whole round trip, and a gigantic transaction wrapped around the get and the write. [[L-0215]] Native upsert statements keep the database's throughput really high and its load at a bare minimum. [[L-0218]] Update needs nothing new: you update directly, so put and update are the same operation. [[L-0219]]

### Counting the trips [[rail: Counting the trips]]

A common production variant checks for the row with `SELECT TOP 1 1 … WHERE …`, which returns a 1 if the row exists, and then inserts or updates. Count the network trips: a request and a response for the check, then a request and a response for the write. Four, against two for the upsert. [[L-0328]]

<Figure id="fig-3c" no="Fig 3·c" k="L-0207 L-0215 L-0328 L-0329 L-0330"
  caption="Two trips or four. Get-then-write crosses the network four times, and the second crossing may carry a large value. TOP 1 1 shrinks that reply but keeps the round trip. The upsert crosses twice.">
  <Desk><TwoOrFourTrips /></Desk>
  <Phone><TwoOrFourTrips layout="phone" /></Phone>
</Figure>

The database spends very little time evaluating `TOP 1 1` or doing the insert or update. The bulk of the time goes on the network. [[L-0329]] So `TOP 1 1` does save something, since it doesn't read a huge value back to the client, but it still spends a round trip on the network, and the upsert saves that too. [[L-0330]] People forget about upsert: a bunch of production systems, in the lecture’s experience, do get-then-set instead. [[L-0331]]

### Two puts on one key [[rail: Two puts on one key]]

What if two puts for the same key arrive at once? This is where the two halves of the lecture meet. Use the locks from [chapter 1](#s1-3), or play with isolation levels ([§1.6](#s1-6)). The SQL database already gives you these guarantees, so leverage them; you don't have to reimplement them. [[L-0233]]

One option is to take an exclusive lock with `FOR UPDATE NOWAIT`, so a put fails at once ("kill myself") if someone else is updating the key, and then do the update. `NOWAIT` is a hypothetical pick here, "just for fancy", with no specific reason. [[L-0234]]

```sql
BEGIN;
SELECT `key` FROM store WHERE `key` = 'k1' FOR UPDATE NOWAIT;  -- fail at once if another put holds k1
UPDATE store SET value = 'v2' WHERE `key` = 'k1';
COMMIT;
```

There is no right choice between `SKIP LOCKED`, `NOWAIT` and plain waiting here. It depends on the guarantees you want your database to provide. [[L-0235]]

You can do it, but it isn't the core transactional database itself. [[L-0267]] And it is limited by memory: all the keys need to fit in memory, and they must be flushed to disk from time to time. [[L-0268]]

Two optimizations of this kind were promised for weeks 5 and 6 of the class, without being named there. In this course, Lecture 9 builds an in-memory store and Lecture 10 an append-only one. <Section id="s3-6" no="3.6" title="Get filters expiry in SQL" crumb="3.6 Get"
  dek="An expired row stays on disk until the cleanup runs. Filter it in the query, so its value never leaves the database."
  meta="About 3 min · class 01:58–02:01, 02:07">

A GET arrives for a key whose value is 10 MB and which expired a minute ago. The cleanup job hasn't run yet, so the row is still there ([3.4](#s3-4)). Where does the code notice?

<PauseAndThink k="L-0220 L-0221 L-0222 L-0223 L-0263"
  q="A GET asks for a key whose 10 MB value expired a minute ago; the cleanup job hasn't run yet. Where should the code notice it's expired?"
  choices={[{ label: 'In the API server: fetch the row, compare expired_at with now' }, { label: 'In the SQL: AND expired_at > now()', correct: true }]}
  right="Right. The expired row never matches, so neither the disk read of the value nor the transfer happens."
  wrong="No. It works, but the database reads 10 MB from disk and ships it across the network, only for the API to throw it away.">

One clause saves the network IO of both machines and the database's read of a huge value. It's the chapter's rule in one line: think about what every clause costs. One catch for your implementation: if keys without a TTL store NULL in `expired_at`, this condition hides them too. Use a far-future value, or also accept `expired_at IS NULL`.

</PauseAndThink>

The proposal in class put the check in the API server: run `SELECT * … WHERE key = 'k1'`, compare `expired_at` with now, and answer "key does not exist". It's wasteful. With a 10 MB value, you transfer 10 MB to your API only to realize the key has expired. [[L-0220]]

Filter in the database instead. Add `AND expired_at > now()` to the query, and expired keys are never read out of the database. [[L-0221]]

```sql
SELECT * FROM store
WHERE `key` = 'k1'
  AND expired_at > now();   -- saves: network IO, and the disk read of the value
```

What that one clause saves is heavy network IO. If your values are gigantic, you save a ton of it, because you aren't even reading the expired value out of the database. It saves the network bandwidth of the server and of the database, and the disk IO time the database would spend reading a humongous value. [[L-0222]]

<RuleBox rule="Micro decisions matter: think about ==the devil in every single line==." k="L-0223">

Everyone writes inserts and simple selects. Performance comes from the curiosity to ask what each line costs: network, disk, rows. Micro-optimizations like this one make a database far more performant. [[L-0223]]

<Section id="s3-7" no="3.7" title="The cleanup job and the last clause" crumb="3.7 Cleanup"
  dek="A cron job hard-deletes expired and deleted rows in batches. One more clause on the user's delete skips the disk writes for keys that have already expired."
  meta="About 8 min · class 02:06–02:08, 02:19–02:22, Q&A 02:22–02:27, 02:37–02:40">

The store now has three columns and three queries. Who removes the expired rows, and when?

TTL approach 1 is batch deletion with a cron job. Every 10 minutes, say, a job fires a hard delete, `DELETE … WHERE` `expired_at < now()`, on the whole table. [[L-0236]] Between two runs an expired key still exists, which is why a GET must filter it, as in [3.6](#s3-6). [[L-0201]]

<Figure id="fig-3d" no="Fig 3·d" k="L-0236 L-0201"
  caption="Batch deletion with a cron job. Each run hard-deletes every expired row; between runs the rows are still on disk, so every read filters them out. Redrawn from the class board at 02:07.">
  <Desk><CronBatch /></Desk>
  <Phone><CronBatch layout="phone" /></Phone>
</Figure>

One more clause goes on the user's delete. So far it was `SET expired_at = -1` for the key, `WHERE key = 'k1'`. Add `AND expired_at > now()`: delete a key only when it is not already expired. [[L-0258]]

```sql
UPDATE store SET expired_at = -1
WHERE `key` = 'k1'
  AND expired_at > now();   -- saves: two disk IOs when the key has already expired
```

One catch the lecture leaves open: if keys without a TTL store NULL, `expired_at > now()` is NULL for them, not true, so deleting a no-TTL key would silently do nothing. Store a far-future sentinel for "no expiry", or add `OR expired_at IS NULL` to the condition <Cite href="https://dev.mysql.com/doc/refman/8.4/en/working-with-null.html">dev.mysql.com</Cite>.

Why the clause? If the key has already expired, there's no need to write its row. The update is still fired for every user delete, but for an expired key the clause doesn't match, so the update does no disk IO, and the batch job removes the row anyway. As it was summed up in class: heads you win, tails you win. [[L-0259]] It saves two disk IOs, not one, because there is also an index on `expired_at` that would otherwise be updated along with the row. [[L-0260]] That saving relies on the index on `expired_at` existing, and in this design it does. [[L-0266]]

Don't confuse the two conditions. `expired_at > now()` is not the batch delete: it is the delete a user triggers, and it soft-deletes only keys that haven't expired yet. `expired_at <= now()` is the batch cleanup, a separate job that hard-deletes everything already expired. [[L-0294]] Behind both is one idea: do disk IO only when it is needed; otherwise, don't do it. [[L-0262]]

<MarginNote title="Where this clause came from" why="skip" k="L-0261">

This delete clause turned up in Apache Ignite's code, where it looked odd at first: why is it there? Mimicking the load showed what a nice optimization it is. [[L-0261]]

</MarginNote>

Here is the whole store: [[L-0263]]

```sql
-- expired_at is the column the slides call "ttl"
-- batch cleanup (cron): expired and soft-deleted rows
DELETE FROM store WHERE expired_at <= now();

-- get: never make a network IO for an expired key          saves: network IO
SELECT * FROM store WHERE `key` = 'k1' AND expired_at > now();

-- put
INSERT INTO store VALUES ('k1', 'v2', e) AS new
  ON DUPLICATE KEY UPDATE value = new.value, expired_at = new.expired_at;

-- delete: soft, and only if still live                     saves: disk IO
UPDATE store SET expired_at = -1 WHERE `key` = 'k1' AND expired_at > now();
```

The cleanup deletes everything whose `expired_at` is at most now, which covers expired and soft-deleted rows alike. The GET adds `expired_at > now()`, so you never make a network IO for something already expired. GET has the same catch as the delete: it must also return keys that have no TTL, so use a far-future sentinel for "no expiry", or test `expired_at IS NULL` as well <Cite href="https://www.postgresql.org/docs/current/functions-comparison.html">postgresql.org</Cite>. [[L-0263]]

On disk, then, you batch: a delete is expensive enough that it waits for the cron job, and reads work around the rows it hasn't reached yet. What if the store lived in memory instead, where a delete costs almost nothing? That is how Redis expires keys, in [chapter 4](#s4).

<RecallQuestions>
  <RecallItem k="L-0191 L-0195" q="Why does <code>DELETE … WHERE</code> <code>now() - created_at &gt;= ttl_sec</code> scan the whole table while <code>DELETE … WHERE</code> <code>expired_at &lt;= now()</code> doesn’t?">

The first condition is computed for each row from two columns and the clock, so no index can answer it and every row is read on every run. The second compares one stored column with a value, so the index on `expired_at` finds the expired rows as a range and the job reads only those.

  </RecallItem>
  <RecallItem k="L-0328 L-0215" q="Count the network trips for a put done as SELECT-then-INSERT/UPDATE, and as an upsert.">

Four for SELECT-then-write: the SELECT and its reply (possibly carrying a large value), then the INSERT or UPDATE and its ack. Two for an upsert: one statement and its ack. `SELECT TOP 1 1` makes the first reply small but still costs the round trip, and the network is where most of the time goes.

  </RecallItem>
  <RecallItem k="L-0258 L-0259 L-0260 L-0236" q="A user deletes a key that expired an hour ago. What does <code>AND expired_at &gt; now()</code> save, and what removes the row?">

The clause doesn't match an expired key, so the UPDATE writes nothing: no write to the row and none to the `expired_at` index, two disk IOs saved. The row is still removed, by the next run of the cron cleanup, `DELETE … WHERE expired_at <= now()`, which takes expired and soft-deleted rows alike.

  </RecallItem>
</RecallQuestions>
