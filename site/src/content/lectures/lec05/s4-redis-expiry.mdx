<Section id="s4" no="4" title="If it were in memory: how Redis expires keys" crumb="4 Redis expiry"
  dek="On disk you batch. In memory a delete is nearly free, so Redis deletes expired keys the moment it touches them, and samples twenty keys at a time for the rest."
  meta="About 14 min · class 02:08–02:19, Q&A 02:43–02:47, 03:07–03:09">

Chapter 3 ended with a store on disk: expired rows stay in the table until a cron job deletes them in one batch, and every GET filters them out in SQL until then. Keep the same per-key TTL, but move the store into memory: an in-memory hash table served by one thread, the way Redis works. What changes about deleting a key?

Almost everything. This short chapter takes Redis apart: first the delete it does the moment a key is read, then the job that cleans up the keys nobody reads again, built on twenty random keys and a little statistics.

</Section>

<Section id="s4-1" no="4.1" title="Lazy deletion" crumb="4.1 Lazy deletion"
  dek="A GET finds its key expired. On disk you would filter it and leave it for the batch. In memory you delete it there and then."
  meta="About 6 min · class 02:08–02:11, Q&A 03:07–03:09">

A GET arrives for a key whose TTL has passed. In chapter 3's MySQL store, the query filters the row out and the cron job removes it later. In memory, the database can do better: when a key that is read is found to be expired, it is deleted on the spot. Redis does this. If you read a key with a TTL before Redis’s periodic cleanup has removed it, Redis doesn’t return it: it tells you the key does not exist, and, since deleting it doesn’t require restructuring anything and so isn’t expensive, it deletes it right there. The database never goes looking for expired keys to do this; it deletes only what it happens to touch. This is called **lazy deletion**. [[L-0237]]

Almost all in-memory databases do it. It belongs to in-memory databases, not to the disk-based store built in chapter 3. [[L-0238]]

The reason is the cost of one delete. In memory there is no tree to rebalance and no network IO penalty. Deleting a key is freeing memory, the `malloc` and `free` (or `new` and `delete`) of C and C++, and removing the key from the hash table. [[L-0239]]

<Figure id="fig-4a" no="Fig 4·a" max={640} k="L-0239 L-0240 L-0241 L-0338"
  caption="On disk, one delete in a B+ tree can push neighbouring leaves out of shape. In memory, deleting from a hash table unlinks one entry and frees it. On disk the cost is real but not catastrophic: InnoDB delete-marks rows and purges them later (see the note below).">
  <Desk><DiskVsMemory /></Desk>
  <Phone><DiskVsMemory layout="phone" /></Phone>
</Figure>

On an on-disk database, don’t do lazy, per-key deletion. This bears repeating “a hundred times”: every micro delete operation requires rebalancing the B+ tree, which is pathetically slow. [[L-0240]]

<SourceNote href="https://dev.mysql.com/doc/refman/8.4/en/innodb-purge-configuration.html" site="dev.mysql.com" k="L-0240">

Batched cleanup of expired rows is the right instinct on a B+ tree store, but a single delete isn’t catastrophic. InnoDB delete-marks the row, and a background purge removes it physically once no transaction needs it any more. Index pages are merged only when they fall below `MERGE_THRESHOLD`, 50% full by default <Cite href="https://dev.mysql.com/doc/refman/8.4/en/index-page-merge-threshold.html">dev.mysql.com</Cite>.

</SourceNote>

So the place decides the shape of the delete:

<RuleBox rule="On disk you delete ==in batches==; in memory you can delete ==right there==." k="L-0241">

On disk, batch the deletes. In memory, pointed or staggered deletions are fine, one key at a time as you come across it. Hand a delete to a later job only when the delete itself is expensive.

<Desk><BatchOrRightThere /></Desk>
<Phone><BatchOrRightThere layout="phone" /></Phone>

</RuleBox>

Put together, Redis hard-deletes a key in two cases: when the user tells it to delete the key, and when it accesses a key that has expired but hasn’t been deleted yet. That second case is lazy deletion. [[L-0242]]

Lazy deletion alone leaves a gap: what about a key that expires and is never read again? Nothing would ever delete it, so a periodic job is still needed. And the job Redis runs does not hard-delete all the expired keys, which is the subject of 4.2. [[L-0243]]

### Why not hand it to a cron job?

A natural question: if a background job exists anyway, why not let it do the lazy deletes too? Because calling `free` on an object is very lightweight. There is no B+ tree to rebalance; the delete happens in microseconds. Delegating it to a job may itself cost more than deleting right there, especially in an in-memory database. [[L-0337]]

Deleting from Redis’s hash table just marks that slot as free space. More exactly, Redis’s dict chains the entries in a bucket, so the delete unlinks the entry from its chain and frees it <Cite href="https://raw.githubusercontent.com/redis/redis/unstable/src/dict.h">dict.h</Cite>. [[L-0338]]

Only when an operation is expensive enough is it worth delegating to a later or background job. A cheap in-memory delete should simply be done where you stand. [[L-0339]]

And deleting now frees memory now. Spend two or three microseconds on the delete and the space is free for new data at once. Delay it to a later cycle, and if Redis is running at full capacity, inserts that would have succeeded are turned away while expired data still sits in memory. [[L-0340]]

</Section>

<Section id="s4-2" no="4.2" title="Sampling 20 keys" crumb="4.2 Sampling 20 keys"
  dek="The keys nobody reads again. Redis doesn’t hunt them all down: it samples twenty, deletes the expired ones, and stops once the sample looks clean enough."
  meta="About 8 min · class 02:11–02:19, Q&A 02:43–02:47">

That leaves the keys nobody ever reads again. Redis handles them with a very simple algorithm that uses a little math: it merges two approaches, lazy deletion on access plus a periodic job. [[L-0244]]

The natural periodic job deletes every expired-but-not-yet-deleted key on each run. With millions of such keys, that run takes a lot of time. [[L-0245]] Redis doesn’t need it to: lazy deletion already solves about 90% of the problem (an estimate from class), because there is a very high chance an expired key gets read, is hard-deleted on the spot and frees its memory. [[L-0246]]

So the periodic job doesn’t delete all the expired keys. Each run, Redis samples exactly 20 keys at random from among the keys that have an expiry set, and deletes the ones in that sample that have expired. [[L-0247]] Then it looks at how many it deleted. If more than 25% of the 20 sampled keys were expired and deleted, it repeats the sampling; once fewer than 25% of a sample are deleted, it stops. [[L-0249]]

<SourceNote href="https://raw.githubusercontent.com/redis/redis/unstable/src/expire.c" site="expire.c (Redis source)" label="Since the class" k="L-0247 L-0249">

This is classic Redis. Since Redis 6.0 the active-expire cycle scans the expiry table incrementally, with a cursor rather than purely at random, in batches of 20 keys at the default effort. It keeps going while more than about 10% of a batch is stale (the source’s acceptable-stale constant is 10), within a CPU time budget <Cite href="https://raw.githubusercontent.com/redis/redis/6.0/00-RELEASENOTES">Redis 6.0 release notes</Cite>. `active-expire-effort` (1 to 10) trades CPU for fewer leftovers; at the default, redis.conf says it “will try to avoid having more than ten percent of expired keys still in memory” <Cite href="https://raw.githubusercontent.com/redis/redis/unstable/redis.conf">redis.conf</Cite>. The redis.io page for EXPIRE still describes random sampling.

</SourceNote>

Why does a sample of 20 tell you anything? A bit of statistics. The population is the whole set of Redis keys that have an expiry. A random sample of 20 from it should be representative of that population: if 50% of the sample is expired, roughly 50% of the population is expired too. The board’s version: if the sample has under 25% expired keys, the population will have under 25% expired keys that are not yet deleted. [[L-0250]]

<Figure id="fig-4b" no="Fig 4·b" max={720} k="L-0247 L-0249 L-0250 L-0251"
  caption="Each round picks 20 keys with a TTL at random from the whole key set: a blue ring marks a sampled key where it sits, solid for round 1, dashed for round 2. Ticked keys were expired and are now deleted. Classic Redis; since 6.0 it works in batches of 20 and keeps going above about 10% (see the note above). Redrawn from the class board at 02:15.">
  <Desk><SamplePopulation /></Desk>
  <Phone><SamplePopulation layout="phone" /></Phone>
</Figure>

Note what the 25% counts: the keys deleted from the sample, which are exactly the expired ones in it. Redis doesn’t compare against a count of expired keys across the whole database; it doesn’t keep one, and counting them would itself be a slow operation. [[L-0249]]

An example. Say that in one round only 3 of the 20 sampled keys are expired: 15%. Redis deletes those 3 and stops. About 15% of the population is then expired but not deleted, and that is okay. The rest is handled eventually, by a later read (lazy deletion) or a later round of sampling. [[L-0251]]

The job works only on the small sample, never on the database as a whole, because at any moment there may be millions of keys that have expired but haven’t been deleted. The price is that some expired keys remain, but no more than the 25% threshold, because the sample represents the population. [[L-0301]]

### Speed over completeness

Why accept leftovers at all? Redis optimizes for speed, not for completeness. Time spent on cleanup is time not spent on reads and writes. So Redis trades a bit of leaked memory for speed, counting on lazy deletion and random sampling to clean up the rest eventually, and spends the bare minimum of time in its periodic job. [[L-0252]]

That matters more than usual because Redis is single threaded. As the lecture puts it, there are no multiple threads running anywhere in Redis, so it can’t hand the cleanup to another thread; it has to keep cleanup short to leave time for the actual commands, get, put and delete. [[L-0253]]

<SourceNote href="https://raw.githubusercontent.com/redis/redis/unstable/redis.conf" site="redis.conf" k="L-0253">

Redis runs commands on a single main thread, which is why expiry work must stay short. But it isn’t single-threaded everywhere: background threads handle lazy freeing (`UNLINK` and the `lazyfree-lazy-*` options, which are off by default), slow file I/O, and optional network I/O threads. Deleting a big key with `DEL` blocks the main thread, “even seconds” for large objects; `UNLINK` removes the key at once and frees its memory in the background.

</SourceNote>

So some keys in Redis’s memory will be expired but not deleted, and they take up space. Statistically, they consume only about 20–25% of the memory at worst, since lazy deletion does the bulk of the deleting. The bound is on keys that have a TTL, not on total memory; it is a probabilistic figure, not a hard guarantee; and current Redis aims for about 10% <Cite href="https://raw.githubusercontent.com/redis/redis/unstable/redis.conf">redis.conf</Cite>. [[L-0254]]

Why exactly 20, and not 15, 21 or 30? The answer given in class is the central limit theorem, with the proof in a paper that is also linked from Redis’s website: explore it if you like math, otherwise remember that it is exactly 20. That explanation is the class’s; no public source for it was found, and in Redis’s code 20 is a tunable constant <Cite href="https://raw.githubusercontent.com/redis/redis/unstable/src/expire.c">expire.c</Cite>. [[L-0255]] By a figure given in class, the 20-key sampling works up to about 5 million keys. [[L-0256]]

The lesson is broader than Redis: there is no one way to build a system. Whatever works for you, works for you. [[L-0257]]

### Not for disk

Sampling-based expiry is not suitable for a disk-based database; it works only in memory. [[L-0248]] Why not, if it is so cheap?

<PauseAndThink k="L-0302 L-0303"
  q="Redis’s expiry job looks at 20 random keys at a time. Could your MySQL key-value store from chapter 3 do the same instead of its batch delete?"
  choices={[{ label: 'Yes, it just has to fetch all rows and pick 20' }, { label: 'No: 20 random picks on disk are 20 random disk reads', correct: true }]}
  right="Right. Each random key lives on a different page somewhere on disk, so one round costs about 20 random IOs, while in memory a random pick is nearly free."
  wrong="No. You wouldn’t fetch everything; you can ask for 20 rows. The problem is what picking them costs.">

Sampling suits memory, where touching a random key is cheap and deleting it is a `free()`. On disk, the cheap operation is the sequential one: walk the `expired_at` index and delete everything already expired, in batches.

</PauseAndThink>

It is tempting to think that on disk you would have to read every row first and then pick 20 of them. You wouldn’t: you can pick 20 random rows. But picking those 20 at random is the expensive part. [[L-0302]] It takes 20 random disk IOs, reading disk pages from anywhere on the disk, which is very slow. In memory, random picks are very easy. [[L-0303]]

So on a disk-based database it is much better to skim through the rows and delete what is expired, which is exactly chapter 3’s batch cleanup, than to sample at random. [[L-0304]]

<RecallQuestions>
  <RecallItem k="L-0237 L-0239 L-0240" q="Why does Redis delete an expired key inline when it reads it, while your MySQL store shouldn’t?">

In memory the delete is cheap: free the object and unlink it from the hash table, in microseconds, with no tree to rebalance and no network trip. On disk every per-key delete touches the B+ tree, which the class called pathetically slow (InnoDB softens it by delete-marking and purging later). So the MySQL store filters expired rows in its queries and deletes them in batches.

  </RecallItem>
  <RecallItem k="L-0247 L-0249" q="A sample of 20 has 6 expired keys. What does classic Redis do next, and what does Redis since 6.0 do?">

6 of 20 is 30%. Classic Redis deletes the 6 and, because 30% is more than 25%, samples again. Since Redis 6.0 the cycle works in batches of 20 and keeps going while more than about 10% of a batch is stale, so it also continues, but it stops when its CPU time budget runs out.

  </RecallItem>
  <RecallItem k="L-0245 L-0252 L-0253" q="What would go wrong if the sampling job tried to delete every expired key on each run?">

With millions of expired keys, each run would take a long time. Redis runs commands on one main thread, so time spent cleaning is time not serving gets, puts and deletes. Redis chooses speed over completeness: it accepts a bounded share of expired keys in memory and lets lazy deletion and later rounds catch them.

  </RecallItem>
</RecallQuestions>
