<Section id="s5" no="5" title="Making it distributed" crumb="5 Distributed"
  dek="Now the word “distributed”. Grow the single node one bottleneck at a time: more API servers, then read replicas, then range shards, with routing in the API."
  meta="About 12 min · class 02:27–02:37, Q&A 02:40–02:43, 03:14–03:15, 03:19–03:21">

The store from chapter 3 runs on one MySQL: three columns, three queries and a cleanup job. Traffic grows. Chapter 3 started by setting the word “distributed” aside; this chapter picks it back up, and grows the store one bottleneck at a time, adding each piece only when the one before it runs out.

</Section>

<Section id="s5-1" no="5.1" title="One MySQL, more API servers" crumb="5.1 More API servers"
  dek="When do you distribute at all? Only when one node can’t handle the load, and the first thing to add is not another database."
  meta="About 2 min · class 02:27–02:29">

When do you distribute at all? When one node can’t handle the load. “Handle” here isn’t only about queries or only about storage, as the course discussed the week before: it can be high network IO, the disk, a large amount of data stored, or a large number of queries fired. Any of them, and one node is no longer enough. [[L-0270]]

The basic one-node architecture is short. Users reach a load balancer, which spreads requests over the key-value API servers, and those talk to MySQL. Anyone who wants to talk to the database, a user, a client, anything, goes through the API servers, which fire the queries from chapter 3. Beside them, a separate job keeps firing the batch cleanup query on MySQL. [[L-0271]]

<Figure id="fig-5a" no="Fig 5·a" max={760} k="L-0271 L-0272"
  caption="The single-node store: everything reaches MySQL through the KV API servers, and the batch cleanup job runs beside them. Redrawn from the class board at 02:27.">
  <Desk><OneMysql /></Desk>
  <Phone><OneMysql layout="phone" /></Phone>
</Figure>

As long as MySQL can sustain the load, you handle more requests by adding more API servers. Nothing else needs to change. [[L-0272]]

When MySQL can’t sustain it, don’t reach for a design yet. First go through the access pattern: from your metrics, find out which queries are fired the most, select, update, upsert or delete. The answer decides what you add next. [[L-0273]]

<RuleBox rule="Don’t over-complicate it at first. ==Keep it really simple.==" k="L-0290 L-0170">

Start with a single node and scale it as the system demands, one bottleneck at a time. No leader election, Paxos or Raft on day zero (the point chapter 3 opened with).

<Section id="s5-2" no="5.2" title="Read replicas" crumb="5.2 Read replicas"
  dek="The metrics say 99 reads for every write. Copies of the database take the reads that can be a little stale."
  meta="About 2 min · class 02:29–02:31">

Say the metrics show 99 reads for every write, and one database can’t keep up. If reads dominate, spin up replicas of the database. With replicas you accept some staleness in the data, and for some use cases serving slightly stale data is okay. [[L-0274]]

<Figure id="fig-5b" no="Fig 5·b" max={850} k="L-0274 L-0275 L-0276"
  caption="Writes, deletes and reads that must be consistent go to the master; reads that can be a little stale go to a replica. Replicas pull changes from the master: the dashed arrow starts at the replica that asks, while the data flows from master to replica. Redrawn from the class board at 02:30.">
  <Desk><ReadReplicas /></Desk>
  <Phone><ReadReplicas layout="phone" /></Phone>
</Figure>

The split is the one from Lecture 2’s chapter on scaling the database (its §2.4). Consistent reads go to the master, and so do updates and deletes. The data replicates asynchronously to the replicas, and reads that can tolerate a little staleness go straight to a replica. [[L-0275]] Asynchronous is the default in both MySQL (“Replication is asynchronous by default”) <Cite href="https://dev.mysql.com/doc/refman/8.4/en/replication.html">dev.mysql.com</Cite> and PostgreSQL’s streaming replication <Cite href="https://www.postgresql.org/docs/current/warm-standby.html">postgresql.org</Cite>. That small delay is what makes a replica read possibly stale; both offer synchronous or semi-synchronous modes, at a cost in latency.

The simplest way to build it: each KV API server opens connections to the master and to the replicas, and picks one per request, depending on the kind of read the client asks for. No central proxy, no extra moving part; that complication can come later. [[L-0276]]

</Section>

<Section id="s5-3" no="5.3" title="Range shards and routing" crumb="5.3 Range shards"
  dek="Now the master can’t keep up with writes. Split the keys into ranges, give each range its own master, and let the API server know which is which."
  meta="About 5 min · class 02:30–02:35">

Replicas don’t help with writes. When one master can no longer handle the write load, first try to scale it up vertically. When you can’t do that any more, shard the database. [[L-0277]]

Sharding means each database holds an exclusive copy of its part of the data: disjoint portions across databases, with no key in two places. [[L-0278]]

The simplest way to split a key-value store is by range. If the keys are strings from A to Z, one master handles A to M and another handles N to Z. Each master may have its own set of replicas. [[L-0279]] And each master has its own batch cleanup job, running independently of the other’s. [[L-0280]]

<Figure id="fig-5c" no="Fig 5·c" max={880} k="L-0279 L-0280 L-0282 L-0283 L-0285 L-0289"
  caption="The distributed store: several masters, each with replicas taking read load and its own batch cleanup job; writes and critical reads go to the masters; all the routing lives in the KV API. Each dashed arrow labelled “pulls changes from master” starts at the replica that asks; the data flows from master to replica. Redrawn from the class board at 02:36.">
  <Desk><RangeShards /></Desk>
  <Phone><RangeShards layout="phone" /></Phone>
</Figure>

The KV API servers hold connections to all the masters and replicas. You can cut down the number of connections with some intelligent balancing, but that is a different problem. [[L-0281]]

What matters is that the KV API knows which database holds which range. Someone asks for the current stock price of Google: Google starts with a G, so the query goes to master 1. A request for Zomato’s goes to master 2. [[L-0282]]

So the routing information, which database holds which key range, is kept on the KV API server side itself, and it picks the database connection for each request. The lecture calls this a simplistic implementation, and keeps it that way for now. [[L-0283]]

<ForwardChip block when="Lecture 9" k="L-0284">hot partitions and three ways to handle them, adding shards dynamically, and consistent hashing, where it sucks and where it is good. It needs prerequisites first</ForwardChip>

The flow of one request is dead simple. Each database is a master with its replicas, and the KV API holds connections to all of them. A request comes in for a key; the KV API looks up which range holds it, sends the query through that connection, gets the response and returns it to the user. [[L-0285]]

Is fixed-range sharding too simple for real systems? By an estimate given in class, about 90% of sharded databases work like this, because very few real-world use cases need to add or remove shards dynamically. [[L-0286]] Changing the number of shards is typically a one-time activity, happening about once a quarter (also an estimate), so you can do it explicitly instead of complicating the system. [[L-0287]]

And when two shards can’t handle the load, add one more node and split the key range into three parts. [[L-0288]]

That is the whole distributed setup: several masters, each with its own replicas handling the read load; writes and critical reads going to the master; a batch cleanup job per master; and all the routing information in the KV API. Nothing more. [[L-0289]]

</Section>

<Section id="s5-4" no="5.4" title="ACID after partitioning" crumb="5.4 ACID after sharding"
  dek="An operation touches four keys: three live on shard 1 and one on shard 2. What still holds?"
  meta="About 2 min · class Q&A 02:40–02:42">

Take an operation in the spirit of the check-in, touching four keys. Three of them live on shard 1 and one on shard 2. What can the store still promise?

If the underlying MySQL provides ACID and the store isn’t partitioned, the key-value store gives the same ACID guarantees. [[L-0295]]

<Figure id="fig-5d" no="Fig 5·d" max={560} k="L-0296 L-0297 L-0298"
  caption="Three of the four keys share master 1, where ACID holds. The fourth is on master 2, and across the two shards it doesn’t.">
  <Desk><CrossShardTxn /></Desk>
  <Phone><CrossShardTxn layout="phone" /></Phone>
</Figure>

Once it is partitioned, the answer changes. A key-value store offers key-based operations, and across partitions you cannot have ACID guarantees: the four-key transaction above is not covered. [[L-0296]] Cross-partition ACID is possible, but it costs more. DynamoDB’s `TransactWriteItems`, for example, commits up to 100 items all-or-nothing, but performs two underlying writes per item, one to prepare and one to commit, and cancels on conflicts <Cite href="https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/transaction-apis.html">docs.aws.amazon.com</Cite>.

That cost is the point. Distributed transactions reduce performance by a huge margin, so you typically don’t use them. [[L-0297]]

What you keep is ACID within a shard. As long as all the keys an operation touches lie on the same node, the store can still guarantee ACID for it. [[L-0298]]

</Section>

<Section id="s5-5" no="5.5" title="Build it yourself" crumb="5.5 Build it"
  dek="You won’t understand routing from a diagram. Two local MySQL servers and an afternoon will do it."
  meta="About 3 min · class 02:34–02:37, Q&A 02:42–02:43, 03:14–03:15, 03:19–03:21">

You won’t understand routing from a diagram. Implement it once. It is a local setup and needs no cloud: run two MySQL servers on your machine, one API server that opens connections to both, write the routing logic once, and expose an HTTP endpoint that routes each request. [[L-0291]]

As a stretch goal, and the last step, create a replica locally: MySQL binlog replication if you use MySQL <Cite href="https://dev.mysql.com/doc/refman/8.4/en/replication.html">dev.mysql.com</Cite>, or PostgreSQL’s WAL streaming replication <Cite href="https://www.postgresql.org/docs/current/warm-standby.html">postgresql.org</Cite>. Connect the KV API to it, and route critical reads to the master. [[L-0292]]

It isn’t difficult. Implement the replica once and the routing layer once, and things become clear in a way they don’t from reading. You don’t need the batch cleanup job for this exercise; build only that one small component. [[L-0293]]

Mock only what matters. You don’t need autoscaling, or the same CRUD operations written again: one database and one replica running locally, with your app, is the whole setup. [[L-0300]]

<MarginNote title="No code to copy" why="skip unless you were hoping for a repo" k="L-0350 L-0351">

No code snippets come with this lecture, on purpose: write it yourself, because making the mistakes is how you learn. [[L-0350]]

A first build of this, from the lecture’s own experience, hit a bunch of transactional deadlocks; once those were fixed, it didn’t get enough throughput, and that was fixed too, one problem at a time. Those mistakes, and what you learn from them, are what make you a better engineer. [[L-0351]]

</MarginNote>

The same advice runs through the course. Some people in the class had implemented all four of short polling, long polling, SSE and WebSockets after Lecture 2; do that, because implementing is where you learn the most. [[L-0060]]

And keep the scope small. Lecture 2’s blogging-platform assignment needs no frontend: expose a few APIs, do short polling and long polling, spin up Kafka (or RabbitMQ) and produce and consume some messages. The focus is databases, caching, delegation and concurrency; the check-in in chapter 2 was built the same way, with only the part worth learning. [[L-0359]]

<RecallQuestions>
  <RecallItem k="L-0273 L-0274 L-0275" q="Your store’s metrics show 99 reads per write, and its one MySQL is at its limit. What do you add, and which requests must still go to the master?">

Read replicas: the reads dominate, and a replica can serve any read that tolerates a little staleness. Writes (puts, deletes) and reads that must be consistent still go to the master, because replication is asynchronous and a replica may lag behind it.

  </RecallItem>
  <RecallItem k="L-0282 L-0283 L-0285" q="Where does the routing table live in this design, and what happens to a GET for “zomato”?">

In the KV API servers. Each one knows the ranges (a–m on master 1, n–z on master 2) and holds connections to every master and replica. For “zomato” it looks up the range, finds that z falls in n–z, sends the query through its connection to master 2 (or one of its replicas, if a stale read is fine), and returns the answer.

  </RecallItem>
  <RecallItem k="L-0296 L-0297 L-0298" q="Why can’t a sharded store give ACID to a transaction touching two shards, and when does it still give ACID?">

Each shard is its own MySQL; one shard’s transaction can’t commit or roll back the other’s work. Making them agree needs a distributed transaction, which costs a lot of performance, so it is typically not used. ACID still holds when every key the operation touches lives on the same shard.

  </RecallItem>
</RecallQuestions>
