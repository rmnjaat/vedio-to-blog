A flight has 120 seats, and all 120 passengers reach 120 kiosks at the exact same moment. Chapter 1 laid out the tools a database gives you for that moment. This chapter writes the program, runs it, watches it fail, and changes two words at a time until every passenger gets exactly one seat.

<Section id="s2-1" no="2.1" title="The check-in problem" crumb="2.1 The problem"
  dek="Airlines, flights, trips and 120 seats per flight: the data model, the services, and the moment everyone checks in at once."
  meta="About 4 min · class 00:25–00:33">

Picture the kiosks at the gate. Before anyone taps one, here is the world they work in. There are several airlines, such as Air India, IndiGo and Go Air. Each airline has several flights, and each flight has 120 seats (a deliberate oversimplification). Each flight flies many trips, and a passenger takes one seat on one trip of one flight. That is how we all travel. [[L-0062]]

The problem is the seat itself. Many people will try to pick the same seat, and the system has to fill all 120 seats in the best way possible. The demo gets there step by step, so that you can see exactly where locking comes in. [[L-0063]]

The schema is five small tables. `airlines` lists the airlines. `flights` gives each flight an id, its airline and a name such as AIRINDIA 101. `trips` says which flight flies when. `users` holds the passengers. `seats` says, for one trip, which user sits in which seat. When a new trip opens, every seat's `user_id` is NULL, and filling those NULLs is the system's job. [[L-0064]] The seats are named the way a real plane's are: 1A, 1B, 1C, 1D, 1E, 1F, then 2A to 2F, and so on. [[L-0073]]

Three boxes are enough for the architecture: a check-in service that passengers use, a database, and an admin service. The database is MySQL. Since the subject is relational databases, that choice is a no-brainer. [[L-0065]] The admin service is the airline's side. It adds flights and trips and keeps them up to date. When a flight opens a trip for booking, it creates one row in `seats` for every seat on that trip, each with `user_id` set to NULL. [[L-0066]]

Be clear about what this is not. It is not a reservation system. Everyone has already booked the flight and paid. At the kiosk they only pick a seat. [[L-0068]]

Now imagine all 120 passengers of one flight reaching the airport at the exact same moment. There are 120 kiosks, and every passenger walks up to one and picks a seat at the same time. [[L-0069]] The rest of this chapter walks through approaches 0 to 5, in mini steps, to understand pessimistic database locking in depth. [[L-0070]]

<MarginNote title="The demo’s data" why="skip it, nothing depends on it" k="L-0067">

The demo's `users` table holds 120 random names, one per passenger. `trips` has a single trip, trip 1, named something like "Air India 1". In the sample shown at the start, `seats` already had a few values filled in, for example seat 1A of that trip booked by user 4. In a fresh trip they would all be NULL. [[L-0067]]

</MarginNote>

<MarginNote title="Why Go" why="skip unless you’ll port the demo" k="L-0071">

The demo is written in Go, chosen for its simplicity, its elegance and its easy concurrency. Any language that supports concurrency works. Without threads you would have to mimic 120 passengers with many processes, and threads are much easier. More on that choice is in [§6.2](#s6-2). [[L-0071]]

</MarginNote>

The demo itself follows one habit worth copying. It does not build the whole airline system. It builds only the part it wants to understand, the database part, because the goal is to understand database locks, not to draw fancy boxes. You can do the same with any system: implement its core, skip the CRUD for everything else, and keep the prototypes small. [[L-0059]]

</Section>

<Section id="s2-2" no="2.2" title="Approaches 0 to 2: no checks at all" crumb="2.2 Approaches 0–2"
  dek="Book the seat the passenger asks for, then a random seat, then a random seat for 120 passengers at once."
  meta="About 5 min · class 00:32–00:41">

Start with the simplest program that could work: ask the passenger which seat they want. Approach 0 is a sanity check. The program takes a user id as an argument, asks which seat to book, and books it. Run it for user 1 and ask for seat 3, and seat 1C now shows as booked by that user. [[L-0072]]

Its `book()` function is four steps: begin a transaction, `SELECT` the seat by its id, `UPDATE seats SET user_id = ?` `WHERE id = ?`, and commit. [[L-0074]] Here it is in Go-shaped form, with the comment the file carried:

```go
// books the given seat for the given user
// last one wins
func book(userID, seatID int) error {
	txn, _ := db.Begin()
	txn.QueryRow("SELECT id FROM seats WHERE id = ?", seatID)
	txn.Exec("UPDATE seats SET user_id = ? WHERE id = ?", userID, seatID)
	return txn.Commit()
}
```

There are zero checks in it. Nothing looks at whether the seat is already booked, so another user can come along tomorrow and book the exact same seat, and the system will not stop them. It is naive, but it lays the foundation. [[L-0075]] Letting passengers book any seat id they like ends with two people on one seat: both boarding passes get printed, and there is chaos in the plane. [[L-0076]]

Approach 1 takes the choice away from the passenger. The system picks a seat at random and assigns it with the same unchecked `UPDATE`. The comment says it plainly: "overriding possible". And the random pick is from all the seats of the airplane, not just the free ones. [[L-0077]] So two passengers can still end up on one seat: a random function can easily pick the same seat in two different calls. [[L-0078]]

Approach 2 makes it concurrent. When `main` starts, it spawns one goroutine per passenger, 120 of them, all trying to pick a seat at the same moment. Each one's `book()` picks a random seat from all the seats, starts a transaction, updates and commits. [[L-0079]] A goroutine is like a thread running in its own space. [[L-0080]] More exactly, a goroutine is a lightweight function managed by the Go runtime: goroutines don't each get their own space but share one address space, and the runtime multiplexes them onto OS threads, so if one blocks the others keep running <Cite href="https://go.dev/doc/effective_go">go.dev</Cite>.

The prediction made in class before running it was right. Some passengers will get the same seat, not all seats will be filled, and how the seats come out depends on how the random function works: only a function guaranteed to return 120 unique values would fill the plane. [[L-0081]] The run shows it. The random function, called 120 times, did not pick 120 unique values. The seat map is mostly empty, and the log has two passengers each "booking" seat 7-E and two more each "booking" 12-E. Two of them will be fighting in the air, both claiming 7-E. [[L-0082]]

<Section id="s2-3" no="2.3" title="Approach 3: the first free seat" crumb="2.3 First free seat"
  dek="Stop picking at random: give each passenger the first seat whose user_id is NULL. It still fails, and how it fails explains locking."
  meta="About 8 min · class 00:40–00:49">

Random was never going to work. Give each passenger the first free seat instead. Approach 3's transaction starts with this query, then updates the seat it got and commits, and it runs for the same 120 passengers in parallel: [[L-0083]]

```sql
SELECT id, name, trip_id, user_id
FROM seats
WHERE trip_id = 1 AND user_id IS NULL   -- only seats nobody holds
ORDER BY id
LIMIT 1;                                -- the first free one
```

The comment in the file still says "last one wins". Before you read on, decide what the run will show.

  choices={[{ label: 'All 120: each passenger takes the next free seat' }, { label: 'Only a handful', correct: true }]}
  right="Right. Almost everyone reads seat 1A as free and books it; the last write wins. In class the runs filled 2 to 4 seats."
  wrong="No. “Next free” is only true for a passenger who reads after someone else’s commit. At the same moment, everyone sees the same first free seat.">

`ORDER BY id LIMIT 1` gives every concurrent reader the same row. A second seat fills only when some transaction commits before another one reads: then `user_id IS NULL` skips the taken seat. The number varies from run to run because it depends on that timing. Nothing in the query stops two transactions from acting on the same old value; that is the job of a lock.

</PauseAndThink>

The reasoning in class went like this, and it was right. The query does check `user_id`, but the transactions are concurrent: they read at the same time, nobody has booked the seat yet, so the database gives all of them the same NULL seat. Unless some locking is in place, the same seat is offered to many passengers. That is exactly why locking is needed: transactions running at the same moment can see the exact same value and act on it. [[L-0084]]

Which seat do they all get? The first one, and `ORDER BY` is the reason. Because of `ORDER BY id`, every transaction sees seat 1 first (then 2, then 3), so everyone books that same seat. [[L-0085]]

One prediction was that only one seat would be booked. One seat is a possible outcome, not a guaranteed one: in the class's runs, two to four seats filled <Cite href="https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html">dev.mysql.com</Cite>. [[L-0086]] Another prediction matches what actually happens. Every concurrent read returns 1A, so every write targets that row, and more than one seat gets booked only when some transaction's update has already committed before another transaction reads. [[L-0087]]

Then the run. Seats 1, 2 and 3 filled. Run it again: four seats. Again: two. There is no guarantee how many seats get filled, they fill in seat order, and the log prints the same seat over and over (1-C, 1-C, 1-C, with 1-B and 1-A before them). [[L-0088]] This is the beauty of relational databases: they make locking very easy to understand. [[L-0089]]

The extreme case of the bug is simple to state. If all 120 transactions start while the first seat is still free, all 120 book that one seat. [[L-0090]] Here are three passengers standing in for 120:

So why did more than one seat fill at all? Because some goroutine ran, found the first free row, wrote to it and committed before a later goroutine started its read. That later reader sees seat 1's `user_id` is no longer NULL, and the `WHERE user_id IS NULL` condition hands it the next row. It moved on because of the condition, not because of how the code was written, and not because of the transaction. [[L-0091]]

That is why commit matters. Once a transaction commits, any transaction that reads after it sees the committed value. [[L-0092]] In MySQL's default isolation level, REPEATABLE READ, there is a precise version of "after": a transaction's plain reads all use the snapshot taken at its first read, so it sees only commits that landed before that read <Cite href="https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html">dev.mysql.com</Cite>. In approach 3 the `SELECT` is the transaction's first read, so a commit that lands before it is visible and one that lands after it is not.

The system was supposed to fill all 120 seats. It filled a handful, because everyone read the same old row. That is exactly why pessimistic locking is needed, and it is what the next approach adds. [[L-0093]]
