The second build of the lecture: a key-value store with a relational database underneath. Four operations, one table, and a habit carried over from the check-in: before you accept a query, ask what each of its clauses costs.

The problem statement says *distributed*. Resist that word for now. The whole chapter runs on one MySQL node; [chapter 5](#s5) spreads it across machines.

</Section>

<Section id="s3-1" no="3.1" title="The problem, and one node first" crumb="3.1 The problem"
  dek="A key-value interface with a relational database behind it: get, put, delete and expiry, built on one node before anything is distributed."
  meta="About 3 min · class 01:33–01:36, Q&A 03:12–03:14">

The board after the break reads: *Distributed KV store on relational database*. A key-value store on a relational database offers a key-value-store-like interface to its users while a relational database does the storing behind it. Building one makes both ideas solid: what a key-value store has to do, and what a relational database does when you ask it to. [[L-0005 L-0168]]

The word *distributed* was added to the problem on purpose, because folks love it. That is the trap. When you are asked to design something distributed, you don't design it distributed on day zero. Build a single-node version first, then think about distribution. Don't jump straight to leader election, Paxos or Raft. Start simple, then scale out. [[L-0169 L-0170]]

The requirements are short. The store must be infinitely scalable: by default, everything needs to be. And it supports four core operations: get a key, put a key, delete a key, and TTL, which means a key expires automatically. [[L-0171 L-0172]]

The design is not made up. The lecture names Apache Ignite, one of the most popular key-value stores, as being built on top of a relational database and supporting these operations; the design here was learned from reading Ignite's source code. [[L-0173]]

<SourceNote href="https://ignite.apache.org/docs/latest/" k="L-0173">

Apache Ignite is a distributed in-memory database with its own storage engine, SQL support and optional native persistence <Cite href="https://ignite.apache.org/docs/ignite2/latest/persistence/native-persistence">ignite.apache.org</Cite>. Its links to relational databases are optional: it can sit in front of one as a cache through CacheStore implementations such as CacheJdbcPojoStore, reading through on misses and writing through on updates <Cite href="https://ignite.apache.org/docs/ignite2/latest/persistence/external-storage">ignite.apache.org</Cite>, and Ignite 2's default SQL engine uses the H2 database to parse and plan queries <Cite href="https://ignite.apache.org/docs/ignite2/latest/SQL/sql-introduction">ignite.apache.org</Cite>. Its data storage is its own; it is not built on an RDBMS.

</SourceNote>

The board lists the brainstorm's five parts: storage, optimizing the storage, insert, update and TTL, which is per key. The class took them as they came up: storage (3.2), expiry (3.3), delete (3.4), put (3.5), get (3.6) and the cleanup job (3.7). A few detours go into how Redis does the same things; the biggest one gets [its own chapter](#s4). [[L-0174]]

<MarginNote title="Is this how real KV stores are built?" why="skip unless comparing with Redis" k="L-0345 L-0346 L-0348">

No. Redis is an in-memory store and, in the lecture’s view, is definitely not built like this. DynamoDB does not sit on a relational database. Apache Ignite's code, though, is very similar to this design. [[L-0345]]

The relational database is a teaching vehicle. It lets the micro-optimizations (what slows a store down, how to get the most out of the database) be discussed in simple terms. [[L-0346]] A persistent key-value store differs from this design only in its storage layer: replace the relational database with a storage layer of your own, and everything else carries over. [[L-0348]]

</MarginNote>

</Section>

<Section id="s3-2" no="3.2" title="Storing keys and values" crumb="3.2 Storage"
  dek="One table called store. The key's type and size are fixed for life; the value's type follows how it is accessed, not what it holds."
  meta="About 6 min · class 01:35–01:42, 01:50, 02:02–02:04">

Start with an empty table called `store`. What goes in it? The first idea in class was an array, and it went nowhere. [[L-0175]] The starting point that stuck: the key is the primary key, so it is indexed, and the value is a string. A primary key for the key is fine. [[L-0176]]

The key's type needs a decision, and it is tempting to wave storage size away. It's a database: you should always be concerned about storage size. [[L-0177]] Picking the right column type matters for any database, because the key's type decides which keys the system supports. If keys are integers only, an integer column. If they are strings, you must decide how big a string. [[L-0178]]

As the database's designer you need to know how big a key will be: `VARCHAR(16)` (a deliberately small pick), or 24, or something larger such as 30 to 60. [[L-0179]] Short keys pay twice in MySQL. InnoDB stores the table in primary-key order, and every secondary-index record carries a copy of the primary key, so a long key also bloats the index on the expiry column that 3.3 adds; MySQL's manual notes that "it is advantageous to have a short primary key" <Cite href="https://dev.mysql.com/doc/refman/8.4/en/innodb-index-types.html">dev.mysql.com</Cite>.

Once you fix the key's type, you can't change it, so know your requirements really well whenever you design a database. [[L-0180]] In MySQL, changing it later usually means a full table rebuild: a `VARCHAR` can grow in place only while its length prefix stays the same size (up to 255 bytes, or 256 and more), and crossing that line or changing the type copies the whole table <Cite href="https://dev.mysql.com/doc/refman/8.4/en/innodb-online-ddl-operations.html">dev.mysql.com</Cite>.

Then the value. It is tempting to pick its type by what is stored: an integer for simple values, a longer string, a few hundred words, for JSON objects. That's partially true. You have to pick something that works for all values. [[L-0181]]

**The value's type follows how users are allowed to access it, if at all, not what it holds.** [[L-0183]]

A `BLOB` column can store literally anything. [[L-0182]] Pick its size class to match: in MySQL a `BLOB` holds under 64 KB, a `MEDIUMBLOB` under 16 MB and a `LONGBLOB` under 4 GB, so a store meant for multi-megabyte values needs one of the larger two <Cite href="https://dev.mysql.com/doc/refman/8.4/en/storage-requirements.html">dev.mysql.com</Cite>.

Access is what changes the answer. MongoDB is also a key-value store: it stores JSON against an id and lets you query on attributes inside the JSON, so its value needs a type that supports queries. (MongoDB is a document database: each BSON document has a unique `_id`, and the fields inside can be queried and indexed <Cite href="https://www.mongodb.com/docs/manual/core/document/">mongodb.com</Cite>.) [[L-0184]] With a suitably typed value column you can even run range queries on the value, if you want to allow them. [[L-0185]] If you need to query inside JSON values, a blob won't work; use a type that supports it, such as MySQL's JSON support, once a plugin and now native. [[L-0186]] Even then, MySQL doesn't index a JSON column directly: to query a field inside it fast, you index a generated column that extracts the field <Cite href="https://dev.mysql.com/doc/refman/8.4/en/json.html">dev.mysql.com</Cite>.

This store queries on the key and never on the value. The value is a black box, so a blob (or a varchar or long text) that stores any type of object is the right choice, and that is a good enough schema to start with. If you'd rather support a JSON type, you can implement it however you want. [[L-0187]]

A separate column for the value's type is needed only if the store supports several value types. You could store serialized YAML and build another Redis on top; with one homogeneous type, such as a string, you don't need it. [[L-0203]]

The class's slides give the single-node schema as a table called `store` with four columns: `key`, `value`, `ttl` (the absolute expiration time) and `is_deleted`, for soft delete. These columns come so naturally that it's worth asking whether every one of them is really needed. [[L-0228]] This page calls the expiry column `expired_at`, the name the board used; the slides' `ttl` is the same column. 3.3 and 3.4 shrink the four columns to three.

Notice what is *not* there: an auto-increment `id`. Engineers are habituated to adding one to every table, but you don't always need it. Add it only if you need it. [[L-0229]] The habit comes from ORMs, because an `id` column makes the ORM's life simple; the lecture’s view of them is blunt: it hates them ([chapter 6](#s6-1) has more). [[L-0230]]

</Section>

<Section id="s3-3" no="3.3" title="Expiry as a timestamp" crumb="3.3 Expiry"
  dek="Store when a key was made and how long it lives, and cleanup reads every row. Store when it expires, index that, and cleanup reads only the expired rows."
  meta="About 5 min · class 01:41–01:46">

Every key can have its own TTL; the class works at a granularity of seconds. [[L-0189]] Which column do you add?

The first proposal: a `created_at` column, plus a background job that checks it and flushes the expired keys. [[L-0188]] Each key also needs to say how long it lives, so the table gets `created_at` and `ttl_sec`, and the job deletes a key if the current time minus its `created_at` is greater than or equal to its TTL ([Fig 3·a, step 2](#fig-3a/step-2)). [[L-0190]]

```sql
-- the first proposal (one cleanup run)
DELETE FROM store WHERE now() - created_at >= ttl_sec;   -- scans: every row
```

<PauseAndThink k="L-0190 L-0191 L-0192 L-0193 L-0194 L-0195"
  q="Each key has a <code>created_at</code> and a <code>ttl_sec</code>. A background job runs <code>DELETE FROM store WHERE</code> <code>now() - created_at &gt;= ttl_sec</code> every few minutes. You put an index on <code>created_at</code>. Is the job cheap now?"
  choices={[{ label: 'Yes: the index on created_at finds the old rows' }, { label: 'No: store the expiry time itself and index that', correct: true }]}
  right="Right. With expired_at stored, the job is WHERE expired_at <= now(), a range the index answers by reading only the expired rows."
  wrong="No. The condition is computed per row from two columns and the current time. A plain index on created_at can't answer it, so every run reads every row.">

An index helps only when the condition compares the indexed column to a value. Move the arithmetic to write time: compute `expired_at = now + ttl` once, when the key is written.

</PauseAndThink>

In the lecture's words, it's the worst query you can write. `now() - created_at` is a dynamic computation, so it can't use an index, and the database must scan every single row, every single time the job runs. [[L-0191]]

<Figure id="fig-3b" no="Fig 3·b" k="L-0191 L-0192 L-0195"
  caption="Why the index can't help. (a) The condition is computed from two columns and the clock for every row, so the index on created_at sits unused and the job reads every row. (b) A stored expired_at turns cleanup into a range on an index: enter at the oldest key, stop at now(). Indexes make reads faster, and every write a little slower (§1.1).">
  <Desk><IndexCantHelp /></Desk>
  <Phone><IndexCantHelp layout="phone" /></Phone>
</Figure>

The root problem is the computation itself, as one diagnosis in class put it: get rid of it, and let the store tell directly that a key has crossed its TTL. [[L-0192]] How? Another idea from class: store a "valid till" time instead of `created_at`, and index it. [[L-0193]]

That is the fix. When a key is written with a TTL, store its absolute expiration time, `expired_at`, instead of `created_at` and a TTL. Keep `created_at` only if you need it for something else ([Fig 3·a, step 3](#fig-3a/step-3)). [[L-0194]] Redis does the same: "Keys expiring information is stored as absolute Unix timestamps" <Cite href="https://redis.io/docs/latest/commands/expire/">redis.io</Cite>, in milliseconds since version 2.6, which is also why its expiry depends on a stable system clock.

Cleanup becomes a plain comparison on one indexed column, and with a single index on `expired_at` it is a really efficient query. [[L-0195]]

```sql
CREATE INDEX idx_expired_at ON store (expired_at);
DELETE FROM store WHERE expired_at <= now();             -- scans: expired rows only
```

If a large backlog of expired keys builds up, run the cleanup in chunks: MySQL's `DELETE … LIMIT n` caps the rows per statement, and you repeat it until fewer than `n` rows are affected, which keeps each statement short <Cite href="https://dev.mysql.com/doc/refman/8.4/en/delete.html">dev.mysql.com</Cite>.

</Section>

<Section id="s3-4" no="3.4" title="Delete is an update" crumb="3.4 Delete"
  dek="Don't remove the row when the user deletes a key. Mark it through the expiry column, and let the one cleanup job remove it with the expired rows."
  meta="About 8 min · class 01:46–01:50, 02:03–02:04, Q&A 02:22–02:25, 03:06–03:07, 03:15–03:19">

A user deletes a key. Do you remove the row right now?

One proposal from class: soft delete. Mark the row as deleted and let a background job delete it later, since a real delete may need the database's internal data structures to be rebalanced. [[L-0196]] ([Chapter 4](#s4-1) has a note on how much a single delete really costs in InnoDB.) With an `is_deleted` column, a delete sets it to true, and a periodic job runs `DELETE … WHERE is_deleted = true`. That means two background jobs: one for expired rows and one for soft-deleted rows. [[L-0197]]

A better proposal: piggyback on `expired_at`. On delete, set it to a negative value, one that is always smaller than now. [[L-0198]] Delete becomes an update ([Fig 3·a, step 4](#fig-3a/step-4)): [[L-0199]]

```sql
-- `key` is a reserved word in MySQL, hence the backticks
UPDATE store SET expired_at = -1 WHERE `key` = 'k1';   -- saves: a column and a second job
```

That saves a whole background job, one instead of two: less CPU, less load on the disk, fewer reads, and storage. [[L-0200]] It also means a read can no longer trust a row just because it exists: the cleanup job may not have run yet when a key is read, so reads must filter out expired keys too. That comes with GET, in [3.6](#s3-6). [[L-0201]]

The cleanup job doesn't change at all. `DELETE … WHERE` `expired_at < now()` matches the rows that expired and the rows a user deleted, whose `expired_at` is negative. One query absorbs both cases, with no separate thread for time-based and soft deletes, and thanks to the `expired_at` index it puts minimal load on the database. The lecture calls it elegant. [[L-0202]]

The `is_deleted` column goes too. Instead of a separate soft-delete column, the special value -1 in the absolute expiration time marks a deleted key, which saves that column's space and makes the hard delete simpler. The final schema is `key`, `value` and the expiration time. [[L-0231]] So a user's delete is really an update; a periodic job later batches the hard deletes, and the database has to do minimal B+ tree rebalancing. [[L-0232]] InnoDB, for one, doesn't rebalance on every delete anyway: it delete-marks the row, purges it later in the background, and merges an index page only when it falls below half full <Cite href="https://dev.mysql.com/doc/refman/8.4/en/innodb-purge-configuration.html">dev.mysql.com</Cite> <Cite href="https://dev.mysql.com/doc/refman/8.4/en/index-page-merge-threshold.html">dev.mysql.com</Cite>. And the soft-delete UPDATE isn't free either, since changing `expired_at` moves the row's entry in the `expired_at` index. Batching the physical removal still cuts the work.

Why write -1 at all, if the cleanup job compares times with now anyway? Because not every key has a TTL. A key without one never expires, so when a user explicitly deletes it you have to do something in the database, and the -1 is that something. [[L-0264]]

The -1 isn't sacred. Any magic value works, such as a date earlier than 1 January 1970, if `expired_at` is a date-time or an epoch timestamp. [[L-0265]] The column type decides which markers fit: MySQL's `TIMESTAMP` only covers 1970-01-01 00:00:01 to 2038-01-19 03:14:07 UTC, so an expiry column should be a `DATETIME` (which runs to 9999-12-31) or an integer epoch, which also allows -1 <Cite href="https://dev.mysql.com/doc/refman/8.4/en/datetime.html">dev.mysql.com</Cite>.

<MarginNote title="Why not hard-delete right away?" why="skip unless into engine internals" k="L-0334 L-0335 L-0336">

Why not delete the row on the spot instead of writing -1? In the lecture's account, every delete may put the B+ tree out of shape and force an expensive rebalance, so pointed deletes on a database are very expensive. (In InnoDB a point delete delete-marks the row and a background purge removes it; it doesn't force an immediate rebalance.) [[L-0334]]

Because pointed deletions are expensive for almost all databases, almost all databases soft-delete and then clean up in batches. [[L-0335]] InnoDB "does not physically remove a row from the database immediately when you delete it": the row is delete-marked and physically removed by a background purge once no transaction needs it <Cite href="https://dev.mysql.com/doc/refman/8.4/en/innodb-purge-configuration.html">dev.mysql.com</Cite>. In PostgreSQL an UPDATE or DELETE leaves the old row version in place, because it "must not be deleted while it is still potentially visible to other transactions", and VACUUM removes it later <Cite href="https://www.postgresql.org/docs/current/routine-vacuuming.html">postgresql.org</Cite>.

Read up on B+ tree rebalancing: why it happens and what problems it causes in databases. The course’s B+ tree video covers it, and Lecture 1 touched on it. [[L-0336]]

</MarginNote>

<MarginNote title="Why don’t databases ship soft delete?" why="skip unless you design databases" k="L-0353 L-0354 L-0355 L-0356 L-0357">

If almost every database soft-deletes inside, why doesn't a relational database offer soft deletion to its users? Because a database is a fundamental layer. It gives the building blocks you need (`FOR UPDATE`, `FOR SHARE`, `SKIP LOCKED`, `NOWAIT`) and stays out of the user's space; otherwise there is no clear line on what to implement. [[L-0353]] One standard feature does come close: SQL Server's system-versioned temporal tables give opt-in history, where on DELETE "the system stores the previous value of the row in the history table" and it can still be read with `FOR SYSTEM_TIME` <Cite href="https://learn.microsoft.com/en-us/sql/relational-databases/tables/temporal-tables">learn.microsoft.com</Cite>.

Built-in soft deletion would need its own batch cleanup process, and it would load developers with questions: what if the data isn't deleted yet, what if I read it, do I have to use this column? [[L-0354]]

Key-value stores see it differently. In the lecture's account, DynamoDB never hard-deletes when you delete a key: it always soft-deletes, because for key-value stores soft deletion is foundational, so they provide it. [[L-0355]]

<SourceNote href="https://docs.aws.amazon.com/amazondynamodb/latest/APIReference/API_DeleteItem.html" k="L-0355">

DynamoDB has no user-facing soft delete: `DeleteItem` removes the item. Its TTL feature deletes expired items in the background, "typically within a few days after their expiration", without consuming write throughput; until then expired items can still be returned, so queries should filter them out <Cite href="https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/TTL.html">docs.aws.amazon.com</Cite>.

</SourceNote>

A MySQL forum thread from around 2011–12, recalled in class, proposed built-in soft deletion. Its exact line isn't remembered, but its essence is: as a database evolves, it matters more to know what you don't want to do than what you want to do, because anything can be built. [[L-0356]] So when designing a database, keep in mind what you definitely won't do, stay out of the user's space, and give raw constructs to build on. [[L-0357]]

</MarginNote>
