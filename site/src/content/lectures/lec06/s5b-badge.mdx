<Section id="s5-4" no="5.4" title="Source of truth or pre-computed" crumb="5.4 Truth or pre-computed"
  dek="One design asks the source every time; the other keeps the answer ready and pays to keep it current."
  meta="About 2 min · class 02:23–02:25">

This is a classic way to build almost any system, and you will meet it in nearly every system you implement: you either query the source of truth, or you keep things pre-computed. [[L-0258]]

<RuleBox rule="Query the source of truth when you need ==strong consistency==. For efficiency, ==pre-compute==, or store the data in a form that is directly consumable." k="L-0258 L-0259">

You either query the source of truth, or keep things pre-computed: you will see this in almost every system. The badge’s crude query asks `messages` every time; the set is the answer kept ready.

<Desk><SourceOrSet /></Desk>
<Phone><SourceOrSet layout="phone" /></Phone>

</RuleBox>

Look at what each costs. With the pre-computed set you directly read its length, and that is the number of unique senders. The source-of-truth approach fires an expensive query instead, and whether it is implemented in SQL or NoSQL doesn’t matter. [[L-0259 L-0260]] The price of pre-computing is that keeping it updated is now your responsibility. You need another flow that also writes the data there. The source of truth was updated by nature: every message is ingested into that table anyway, and you index it and query it. [[L-0261]]

Neither approach is wrong. It depends on what you prioritise and on your scale. As a startup, querying the source of truth will work just fine. As millions of people become concurrently active on your system, you may be tempted toward the pre-computed approach. [[L-0262]]

Looking back over this page (a link the class didn’t draw): the stored hash of [§2.3](#s2-3) and `active_photo_id` in [§2.5](#s2-5) can be read the same way, as values kept ready because the frequent read needed them.

<Section id="s5-5" no="5.5" title="Redis: the read path and the clear" crumb="5.5 Redis: get and clear"
  dek="A key-value store whose value is a set. Getting the badge and clearing it are one call each."
  meta="About 2 min · class 02:25–02:28">

Which store holds a set per user?

Against each user id you keep a variable-length list of user ids: 5, 100, any number. That points to a NoSQL store, a document or key-value store such as MongoDB, where the key is the user id and the value is a set of user ids. [[L-0263]] MongoDB does give set semantics on an array field: `$addToSet` adds a value only if it isn’t already present, and updates to a single document are atomic, so concurrent workers adding senders for the same user don’t corrupt the set <Cite href="https://www.mongodb.com/docs/manual/reference/operator/update/addToSet/">mongodb.com</Cite> <Cite href="https://www.mongodb.com/docs/manual/core/write-operations-atomicity/">mongodb.com</Cite>.

This design uses Redis, as a simplification, because almost everyone knows it. Any key-value store that gives you a set as the value works. That is the key highlight: reuse the set the database already gives you, so you don’t have to check-and-set yourself. [[L-0264]]

The read path is a get-status API. It talks to Redis, counts the elements of the user’s set and returns the count for the badge. [[L-0265]] The clear path is a clear API. When the user taps the messages icon, it goes to Redis and deletes that user’s key. With get and clear done, the read path is done, and so is a very trivial write path. [[L-0266]]

<Section id="s5-6" no="5.6" title="The write path starts at the messaging service" crumb="5.6 The write path"
  dek="Only one service knows that a message didn’t reach B. Its events, through Kafka, are what grow B’s set."
  meta="About 6 min · class 02:27–02:32, Q&A 02:49–02:51">

Something has to put “C wrote to B” into B’s set while B is away.

That is the interesting part: the write path. Someone has to put into Redis the unique senders the user received messages from while offline. [[L-0267]]

Start at the client, which has to be smart. If the user is already on the messaging tab, a message arriving, even in a different conversation from the one they are reading, isn’t newly unread, and the badge needs no update. [[L-0268]] If messaging runs over a WebSocket, the backend can check whether the socket connection with the client is off, say while the user is watching reels, and only then update Redis. [[L-0269]] One caution for whoever builds that check: a WebSocket can look open after the client has gone, for example when the network drops. RFC 6455’s Ping and Pong frames are the protocol’s way to find out: a Ping “may serve either as a keepalive or as a means to verify that the remote endpoint is still responsive”, and the peer must answer with a Pong <Cite href="https://www.rfc-editor.org/rfc/rfc6455#section-5.5.2">rfc-editor.org</Cite>.

That already hints at the shape of the answer. The design needs not one database but a few more to support it, and that is where the high-level pattern of the next chapter comes in. [[L-0270]]

The input to the system is the messaging service, because it is the one that knows when a message could not be delivered to the user. [[L-0271]] This design simplifies: the count goes up only while the user is offline. In the real world, the count also goes up while you are on another tab, and you can add such cases. Whatever the definition of “unsent” is (not on the tab, offline, doing something else), it comes from the messaging service. [[L-0272]] It is the source of truth for delivery. It knows whether the message was delivered to you, whether you are on that tab, and whether your WebSocket connection is up. [[L-0273]] It may ask an online/offline indicator service, or it may know by itself: every persistent connection ends at its edge servers, and those servers know whether you are online, offline, connected, and on which tab. [[L-0274]]

<ForwardChip block label="from" when="Lecture 1" lec="lec04" sec="s2" k="L-0274">green dots: the online/offline indicator</ForwardChip>
<ForwardChip block label="from" when="Lecture 4" lec="lec02" sec="s7" k="L-0274">scaling WebSocket servers</ForwardChip>

So the messaging service publishes one event, **`ON_MSG_UNSENT`**. It is an umbrella for every case in which the badge should bump, and the if-and-else logic of where the user is and what they are doing is implemented there. The class put it as implementing “those logics over here from the front end”: the signals about where the user is come from the client, and the decision is made in this one place. [[L-0275]] Concretely, “unsent” means any message that couldn’t be delivered to the user in real time, not only a message to a user with no socket at all. Whether a user who is on another tab counts as unsent, or only a user who is completely offline, is a product call. Either way, whatever flows into `ON_MSG_UNSENT` must update the count in real time. [[L-0311]]

These events flow into Kafka and become the input to the badge system. Each says which user sent which message to whom (on the board, `{ src: "A", dest: "B", msg }`), and consumers add the sender to the recipient’s set, which is stored in Redis: `B: {C, D}`. [[L-0276]] A pink board note, hard to read, adds `can batch here`, with a second line that most likely reads “if partitioned by recipient id”. It was written under the status API, and nothing was said about it aloud; the most likely place for such batching is at the workers, if the stream is partitioned by recipient id. [[L-0277]] Kafka writes events with the same key to the same partition, and a consumer reads a partition’s events in the order they were written, so keying the events by recipient id sends all of a recipient’s events to one worker, which can collapse them before writing <Cite href="https://kafka.apache.org/intro">kafka.apache.org</Cite>. The batched Redis writes can then go out with pipelining: many commands are sent without waiting for each reply, which saves round trips and system calls <Cite href="https://redis.io/docs/latest/develop/using-commands/pipelining/">redis.io</Cite>.

Put together, the design has two halves. The read path: get status counts the set, and clear status deletes it when the user taps the messages icon. The write path: `ON_MSG_UNSENT` events from the messaging service, which uses online/offline information, are consumed by status update workers that write each new sender into the Redis cluster. The same stream also feeds the notification system. [[L-0278]]

<RecallQuestions>
  <RecallItem k="L-0231 L-0233" q="300 unread messages from 3 people, and the user tapped the icon an hour ago with nothing new since. What does the badge show?">

Nothing: zero. The badge counts unique senders since the last tap, and nothing has arrived since that tap. The 300 messages are still unread, but the tap acknowledged them; it didn’t read them. Before that tap, the badge showed 3.

  </RecallItem>
  <RecallItem k="L-0248 L-0251" q="Why is the crude query correct, and why does no index order fix its cost?">

It reads the source of truth: `messages` for the messages and `user_activity` for the last tap, so the count is exactly right every time. But it must walk every new message to count distinct senders. `(to, ts, from)` stops the scan at `last_read_at`, yet one sender with 10,000 new messages still costs 10,000 index entries to learn the answer is 1, on every page load.

  </RecallItem>
  <RecallItem k="L-0271 L-0273 L-0275" q="Who produces the event that grows the set, and why that service?">

The messaging service, as `ON_MSG_UNSENT`. It is the source of truth for delivery: its edge servers hold every WebSocket, so it knows whether the message was delivered, whether the user is connected, and on which tab (or it asks an online/offline service). Workers consume the event from Kafka and add the sender to the recipient’s set.

  </RecallItem>
</RecallQuestions>
