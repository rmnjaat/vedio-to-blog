<Section id="s3" no="3" title="Serving Gravatar at every size" crumb="3 Serving"
  dek="Reuse the upload service, put a CDN in front of the API, tell the CDN when a photo changes, then let the same origin hand out any size on request."
  meta="About 17 min · class 01:07–01:14, 01:23–01:30, Q&A 01:17–01:23">

Facebook and Instagram adopt Gravatar. Every profile picture on their pages becomes a request to `gravatar.com/<hash>`: millions of them, at three different sizes.

The data model from the last chapter is settled. This chapter puts it behind a URL that millions of sites can hit: upload, a CDN in front, invalidation when a photo changes, and resizing on request.

</Section>

<Section id="s3-1" no="3.1" title="Upload, reused" crumb="3.1 Upload"
  dek="Nothing new on the way in: the photo upload service from Lecture 7, plugged in unchanged."
  meta="About 2 min · class 01:07–01:08 and 01:11">

A user uploads a new photo. Gravatar reuses the photo upload service from the previous lecture, plug and play, with no changes at all: a pre-signed URL, the upload straight to S3, then a call to the API server to register the photo, which makes an entry in the `photos` table. Pick your favourite database for it; the board used MySQL. [[L-0117]] <ForwardChip label="from" when="Lecture 7" k="L-0117">the photo upload service with pre-signed URLs</ForwardChip>

<Figure id="fig-3a" max={640} no="Fig 3·a" k="L-0117" caption="Lecture 7’s upload service, reused unchanged. The service only prepares the upload; the bytes go straight from the user to S3, and the API records the photo. Redrawn from the class board at 01:07.">
<Desk><UploadSigned /></Desk>
<Phone><UploadSigned layout="phone" /></Phone>
</Figure>

After publishing, the `photos` row holds the photo’s id, the user id and `is_active = true`, and the `users` table holds the email and its hash. The board’s sample rows were `photos (7abe, 729, true)` and `users (729, <email>, 0eafd172)`. [[L-0118]]

The S3 path itself is not stored. The board’s key is the bucket `s3://gravatar-images/` followed by `{user_id}/{random photo id}`, so knowing the user id and the photo id is enough to derive it on the fly. [[L-0121]]

</Section>

<Section id="s3-2" no="3.2" title="A CDN in front, the API as origin" crumb="3.2 CDN + origin"
  dek="Millions of hits on one URL pattern belong on a CDN. The interesting decision is what the CDN pulls from."
  meta="About 5 min · class 01:08–01:11, Q&A 01:17–01:19">

Photos should not be served from the backend servers but through a CDN. At Facebook or Instagram scale, millions of hits coming to the API servers and on to S3 would create chaos, and the AWS bill would shoot up. The CDN also gives users a better experience. The board summed up the gain as the speed and scale of a CDN, and ease of use for the user. [[L-0119]]

Start with the API. It exposes an endpoint `api.gravatar.com/photos/<hash>`, as on the board: take the hash from the URL, get the active photo from the database, read the file from S3 at its derived path and return the bytes. That is the standard procedure, the same kind of handler as `/raw` in [§1.2](#s1-2). [[L-0120]]

Then configure a CDN. Create a CDN property `gravatar.com` whose origin is that endpoint, `api.gravatar.com/photos`. [[L-0122]] The CDN in Lecture 7 sat on a subdomain property, `edge.arpitbhayani.me`; here the root domain itself is the CDN property. [[L-0123]] That takes DNS support: a plain CNAME can’t sit at the zone apex, because RFC 1034 allows no other data at a CNAME’s node and the apex always has SOA and NS records <Cite href="https://www.rfc-editor.org/rfc/rfc1034#section-3.6.2">rfc-editor.org</Cite>. Using the root domain as a CDN hostname needs something like Cloudflare’s CNAME flattening, which answers with the target’s IP addresses instead <Cite href="https://developers.cloudflare.com/dns/cname-flattening/">developers.cloudflare.com</Cite>.

Now follow a request for `gravatar.com/<hash>`. It goes to the CDN. If the CDN has the photo, it serves it. If not, it goes to the origin, `api.gravatar.com`, which reads the photo from S3 and returns it; the CDN caches it and serves the user, and every following request is served from the CDN. [[L-0124]]

<Figure id="fig-3b" max={700} no="Fig 3·b" k="L-0119 L-0120 L-0122 L-0124 L-0125 L-0129" caption="Left: visitors only ever talk to the CDN at gravatar.com; on a miss the CDN calls the API, which asks the database which photo is active and reads it from S3. Right: when the photo changes, an event on Kafka lets a worker purge the CDN’s copy (3.3). Redrawn from the class board at 01:11.">
<Desk><GravatarEndToEnd /></Desk>
<Phone><GravatarEndToEnd layout="phone" /></Phone>
</Figure>

The mapping is easy to read backwards. The browser never calls the API. The request goes to the CDN, exactly as requests to `edge.arpitbhayani.me` did in Lecture 7, and the CDN’s origin is configured to be `api.gravatar.com`, so it is the CDN that calls the API, and only on a miss. [[L-0138]]

<PauseAndThink k="L-0138 L-0139 L-0140"
  q="The photos sit in S3. Why does gravatar.com’s CDN fetch from the API server on a miss instead of straight from the bucket?"
  choices={[{ label: 'Because the bucket is private, and a CDN can’t read private buckets' }, { label: 'Because S3 doesn’t know which photo is active', correct: true }]}
  right="Right: S3 can’t know which photo is active. The URL names a user, by hash, not a file. Only the database knows which of that user’s photos is active, so the origin must be code that asks it."
  wrong="Half of it. S3 not being public is one of the two reasons given in class, but a CDN can be allowed to read a private bucket (CloudFront signs its requests with Origin Access Control). The reason that holds either way is the other option: S3 doesn’t know which photo is active.">

The CDN only caches what the origin returns. The origin has to be the thing that holds the answer: the source of truth.

</PauseAndThink>

It is a common question why the CDN doesn’t point to S3 directly. The instructor answered with two reasons in one breath: S3 is not public, and only the database knows which photo is active. [[L-0139]]

<SourceNote href="https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-restricting-access-to-s3.html" site="docs.aws.amazon.com" k="L-0139">

A private bucket alone would not stop it: CDNs can read private buckets. CloudFront’s Origin Access Control lets the CDN read a private S3 bucket by signing its requests, and the bucket policy allows only that distribution, so viewers cannot use S3 URLs directly. The second reason, in the next paragraph, is the one that holds.

</SourceNote>

And S3 doesn’t know which photo is active. Only the database, the source of truth, knows that. So on a miss the CDN falls back to `api.gravatar.com`, which reads the database, finds the active photo, fetches it from S3 and sends it to the CDN. [[L-0140]]

</Section>

<Section id="s3-3" no="3.3" title="When the photo changes" crumb="3.3 Invalidation"
  dek="A long TTL keeps the CDN cheap. An explicit purge keeps it right."
  meta="About 4 min · class 01:11–01:14, Q&A 01:22–01:23">

User 1 changes their photo. User 2 loaded the old one through the CDN an hour ago.

When a photo is published or updated, the API server updates the database and pushes an event to Kafka. [[L-0125]] Why Kafka? To invalidate the CDN’s cache. Once user 2 has opened user 1’s profile and the photo came through the CDN, the CDN serves that copy to everyone who asks. When user 1 updates the photo, that cached copy has to go. [[L-0126]]

Photos don’t change often, so the TTL for a Gravatar photo might be one or two days. [[L-0127]] Even so, when a user changes the photo, invalidate it in the CDN right there and then, so that the new photo is rendered. Gravatar doesn’t rely on the TTL, because the user wants to see the new photo everywhere immediately: that is the user experience. [[L-0128]]

<AnimationClip clip="l06-invalidate" no="Clip 3·1" k="L-0126 L-0127 L-0128 L-0129"
  lead="User 1 changes their photo. With a two-day TTL and no invalidation, how long might user 2 see the old face?"
  caption="With only a 1–2 day TTL, the CDN can keep serving the old photo until it expires. An event on Kafka lets a worker call the CDN’s purge API (or the API calls it directly), and the next request gets the new photo. Long TTL for speed, explicit invalidation for correctness." />

The `photo_updated` event goes to a bunch of consumers whose only job is to invalidate the CDN. These workers call the CDN’s API to invalidate a path, say `/h1`, so the file is deleted from the CDN. The next request misses and goes to the API server, which gets the S3 path from the database, reads the file from S3 and sends it to the CDN; the CDN caches it and serves it, and later requests come from the CDN again. The board labels the bus simply “queue”. [[L-0129]] Calling the CDN directly from the API, synchronously, is a variant of the same idea and was accepted in class too. Either way the purge happens on change, not when the TTL runs out. [[L-0128]]

Every CDN exposes such APIs to invalidate a particular path: Cloudflare, Akamai and the rest. [[L-0130]] An invalidation clears only the CDN’s edge caches, though. A browser or a corporate proxy can keep showing the old file until its own copy expires, which is why CloudFront recommends versioned file names for files that change often; invalidations can also cost money, while versioning does not <Cite href="https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/Invalidation.html">docs.aws.amazon.com</Cite>.

<RuleBox rule="S3 doesn’t know which photo is active. ==Only the database is the source of truth, so the CDN’s origin is the API.==" k="L-0140 L-0128">

And when the photo changes, invalidate right away; don’t wait for the TTL.

<Desk><SourceOfTruthOrigin /></Desk>
<Phone><SourceOfTruthOrigin layout="phone" /></Phone>

</RuleBox>

Gravatar is a very simple system. What makes it interesting are the details: how the CDN is used, how database transactions are used, how the schema evolved, asking the critical questions, and keeping the data secure and correct no matter what. [[L-0131]]

</Section>

<Section id="s3-4" no="3.4" title="Every size, on demand" crumb="3.4 Every size"
  dek="One stored original, any width the URL asks for. The CDN flow gains exactly one step."
  meta="About 4 min · class 01:23–01:27">

The same Gravatar photo shows up as a 32-pixel dot in a comment thread and as a 512-pixel header on a profile.

Once you know how a CDN and Gravatar work, on-demand image optimization is a piece of cake. [[L-0148]] The problem: one image is needed at many sizes. A Facebook profile photo is a tiny 16×16 or 32×32 dot on one page, 256×256 on another and 512×512 on a third, while the user uploads at any resolution. Whatever size is requested should be served. Assume the CDN doesn’t offer this feature, so you build it yourself. [[L-0149]]

On-demand optimization is not “upload the image, post a message, and have a bunch of servers pre-create every variant”. The image is transformed when it is requested. [[L-0150]] Just as a CDN accepts query parameters, the service accepts them too: `?w=32` means transform the image to 32 pixels wide, as in `https://gravatar.com/h1?w=32`. [[L-0151]] Real Gravatar spells its size parameter `s=`, but the idea is the same.

<Figure id="fig-3c" max={880} no="Fig 3·c" k="L-0149 L-0151 L-0152" caption="One original in S3, any width on request. The CDN caches each width separately; a miss reaches the origin, which reads the original, resizes it and returns the requested size. The board’s original was 1024×1024.">
<Desk><OneOriginalAnyWidth /></Desk>
<Phone><OneOriginalAnyWidth layout="phone" /></Phone>
</Figure>

The flow is the CDN flow you already have, plus one step. CDNs give this feature out of the box; the board wrote down what a CDN does internally:

1. reads the URL;
2. if it has the file, returns it;
3. if not, reads the file from the origin;
4. transforms it as per the given transformations;
5. caches the file locally;
6. returns the response.

Step 4 is the one extra step. Here the CDN is assumed not to offer the feature, so the request goes to the origin with its query parameters, and the origin reads the image from S3, applies the transformation the parameters ask for, and sends it; the CDN caches each transformed result. [[L-0152]]

This is where image processing libraries come in. In the lecture’s view, ImageMagick is the world’s most popular image processing library. [[L-0153]] PIL, the Python Image Library, has two bindings: a native Python one and ImageMagick. [[L-0154]] ImageMagick is written purely in C++, and almost every language has C++ bindings, so you can invoke ImageMagick natively from your preferred language. [[L-0155]]

<SourceNote href="https://imagemagick.org/" site="imagemagick.org" k="L-0154 L-0155">

In Python, Pillow (the maintained fork of PIL) is a standalone imaging library with its own resize API, `Image.resize` <Cite href="https://pillow.readthedocs.io/en/stable/reference/Image.html">pillow.readthedocs.io</Cite>. ImageMagick is used from Python through a separate package, Wand, a ctypes-based binding that requires the MagickWand library <Cite href="https://docs.wand-py.org/en/latest/">docs.wand-py.org</Cite>. ImageMagick itself is written in C, with C APIs (MagickCore, MagickWand) and a C++ API (Magick++ <Cite href="https://imagemagick.org/magick++/">imagemagick.org</Cite>), so most languages can call it natively through bindings.

</SourceNote>

Resizing is one call. ImageMagick has a native resize function: call it with the new size, get the image back as bytes in memory, and send them to the user. That is the only change to the flow. [[L-0156]] The same goes for any transformation you choose to support, such as grayscale or resizing: the request reaches the origin with those query parameters, the origin gets the image from S3, applies the transformations and returns the result. [[L-0157]]

This is exactly what CDNs do with their transformation query parameters, covered in Lecture 7; the design simply re-implements it. [[L-0158]] Cloudflare Images, for example, transforms images on the fly from URL parameters (resize, crop, convert to WebP or AVIF), so nobody pre-generates the variants <Cite href="https://developers.cloudflare.com/use-cases/media-streaming/image-optimization">developers.cloudflare.com</Cite>. So if you were building your own CDN, this is exactly how you would implement the feature. [[L-0163]]

</Section>

<Section id="s3-5" no="3.5" title="Why it needs big machines" crumb="3.5 Big machines"
  dek="On-demand image work is CPU work that someone is waiting for. There is no queue to hide behind."
  meta="About 3 min · class 01:27–01:30">

A page loads 200 avatars at `w=32`, all of them cache misses.

Image processing, encryption and video processing are very CPU-intensive workloads. You need a large amount of CPU, so you pay your cloud provider for bulky machines with many CPUs. [[L-0159]] On-demand processing, as opposed to asynchronous processing, needs bulky machines because many cores let you parallelize the work and finish quickly. Every on-demand image optimization system, and every on-demand processing system of any kind, is built this way. There is nothing fancy in it: bulky servers, autoscaled on the incoming requests. [[L-0160]]

And it can’t be made async, because the request is synchronous. When the URL loads, the 240-pixel image the page asked for must be produced right then and sent back. The board put it in one line: “CPU intensive! Cannot be ASYNC; large servers (size & numbers)”. [[L-0161]]

Handling this scale today is a no-brainer: you need large servers. There is nothing magic about on-demand image optimization. [[L-0164]] And you will rarely run it yourself. Cloud providers give you these facilities out of the box, very few engineers work on a team that manages its own such infrastructure, and so it is usually abstracted away while you focus on the things that matter. [[L-0167]]

<RecallQuestions>
  <RecallItem q="Why is the origin api.gravatar.com and not the S3 bucket?" k="L-0139 L-0140">

The URL names a user (by the email’s hash), not a file, and S3 doesn’t know which of that user’s photos is active. Only the database, the source of truth, knows. So the CDN’s origin has to be the API, which looks up the active photo and then reads its bytes from S3. In class the first reason given was that S3 isn’t public; even if the CDN reads a private bucket (see the note in 3.2), S3 still can’t tell which photo is active.

  </RecallItem>
  <RecallItem q="The TTL is two days. What makes a changed photo show up within seconds, and what can still show the old one?" k="L-0125 L-0128 L-0129 L-0130">

On update, the API writes the database and puts an event on Kafka; an invalidation worker calls the CDN’s purge API for that path (or the API calls it directly), so the next request misses and fetches the new photo. Purging clears only the CDN’s edges: a browser or proxy that cached the old file can keep showing it until its own copy expires.

  </RecallItem>
  <RecallItem q="Why does on-demand resizing need big many-core machines when a pre-generated design doesn’t?" k="L-0159 L-0160 L-0161">

Image processing is CPU-heavy, and on demand it is synchronous: the page’s URL is waiting for that exact size, so it can’t be deferred to a queue. Many cores let each resize run in parallel and finish fast, and the fleet autoscales with incoming requests. Pre-generated variants are made in the background by workers that can take their time.

  </RecallItem>
</RecallQuestions>
