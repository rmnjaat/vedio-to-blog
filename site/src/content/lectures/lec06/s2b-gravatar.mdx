<Section id="s2-4" no="2.4" title="Mark a photo active: a bug hunt" crumb="2.4 Mark active"
  dek="A one-line UPDATE, three bugs, and the check that belongs before any write."
  meta="About 13 min · class 00:45–00:56, Q&A 01:14–01:18 and 01:33">

Requirement two says a user can mark one of their photos as active. The query for it is three lines, one of the simplest queries you could write, almost hello world, and it hides a big problem that almost every engineer has seen and should never ship. [[L-0087]]

The first draft: [[L-0086]]

```sql
update photos set is_active = true where id = ?;
```

It is tempting to also pass `user_id`, to make the scan on the table smaller. That doesn’t help: `id` is the primary key, so the lookup is log n anyway, which is already very efficient. [[L-0088]] (A different reason to add `user_id` turns up below.)

<PauseAndThink k="L-0086 L-0089 L-0093 L-0096 L-0097"

  choices={[{ label: 'Yes. id is the primary key, so it’s exact.' }, { label: 'No, something else has to change too.', correct: true }]}
  right="Right, and there’s more than one thing. Try the three hints below in order."
  wrong="Not quite: something else has to change too. It’s exact about which row it touches, but that is the trouble: the old active photo stays active, so the user now has two.">

Three hints, one bug each. Cover the answer after each arrow and try it first.

1. *What happens to the photo that was active before?* → It stays active. Unset it first, with a second update that touches only the active row.
2. *The process dies between your two updates. What do other sites see?* → No active photo, so a 404. Wrap both updates in a transaction.
3. *The photo id comes from the browser. Whose photo is it?* → Add `and user_id = ?`, or anyone can flip someone else’s photo. Better still, check first.

Stuck on the third? It’s like writing one print statement and asking why the program doesn’t run.

</PauseAndThink>

### Bug 1: two active photos

The update doesn’t mark the previously active photo as inactive. [[L-0089]] The first fix that comes to mind is three queries: find the active photo, mark it inactive, mark the new one active (a counter-based hack gets tried and dropped on the way). Simplified, it is two: mark all of the user’s photos inactive, then mark the chosen one active. [[L-0090]] A refinement: don’t touch every photo. Add `and is_active = true` to the first update’s WHERE clause, so it changes only the row that is currently active. [[L-0091]]

```sql
update photos set is_active = false where user_id = ? and is_active = true;
update photos set is_active = true  where id = ?;
```

The second update depends on the first and should only run once the first has completed, so the two can be made one transaction. [[L-0092]]

### Bug 2: a crash between the updates

“Can be” is not enough: the two updates must explicitly be wrapped in a transaction. If the process crashes after the first update, the user is left with no active photo at all, and Facebook, rendering that user’s profile photo, gets a 404 Not Found. [[L-0093]]

It is a very simple thing, and people skip it: they don’t write the transaction, or don’t call it out explicitly. Focus on every intricate detail, especially in simple systems, because what seems obvious often isn’t. [[L-0094]]

With the transaction in place, the update is atomic, and the class took that to mean concurrent requests are taken care of. [[L-0095]]

<SourceNote href="https://www.postgresql.org/docs/current/transaction-iso.html" k="L-0095">

Atomic isn’t the same as isolated. In PostgreSQL’s default Read Committed level, an UPDATE finds its target rows using a snapshot taken at the start of the statement. Two concurrent mark-active transactions can each clear only the old active row and then activate different photos, leaving two active. Lock the user’s row first (`SELECT … FOR UPDATE` <Cite href="https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html">dev.mysql.com</Cite>) or keep a single `active_photo_id` on users, as [§2.5](#s2-5) does.

</SourceNote>

### Bug 3: somebody else’s photo id

What is still wrong? Spotting a problem in a query this small is hard. It’s like writing a single print statement and asking why your program isn’t running. [[L-0096]]

Look at the second update: `where id = ?`. Imagine someone passing a random photo id from the front end. The first update marks your own photos inactive; the second marks somebody else’s photo active. You are left with no active photo, and another user’s photo flips. The second update must also check `user_id = ?`, so a user can only mark their own photos active. That check is there for security and for the correctness of the system. [[L-0097]] The board’s final version:

```sql
BEGIN;
update photos set is_active = false
  where user_id = ? and is_active = true;
update photos set is_active = true
  where id = ? and user_id = ? and is_active = false;
COMMIT;
```

### Keep exactly one active

Now pass a wrong photo id to the fixed transaction. The `user_id` condition protects other users’ photos: the second update matches nothing, so no row is updated. [[L-0132]] An update that you expect to change something but that changes nothing is an alarm. In most cases it means a bug, often in the front end. [[L-0133]] But the first update has already run. All of the user’s photos are now inactive and nothing became active, so for that user it’s a 404. [[L-0134]]

If the invariant is that a user has exactly one active photo, the transaction has to check it. First select the photo row with that photo id and user id. If that row exists, run the two updates; otherwise do nothing. [[L-0135]] Make that check a locking read. The MySQL manual warns that a regular SELECT in a transaction “does not give enough protection”: other transactions can update or delete the rows you just read. `SELECT … FOR UPDATE` (or `FOR SHARE`) keeps the checked row locked until COMMIT <Cite href="https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html">dev.mysql.com</Cite>.

```sql
BEGIN;
SELECT id FROM photos
  WHERE id = ? AND user_id = ? AND is_active = false
  FOR UPDATE;
-- no row: stop here (ROLLBACK) and report "not found"
UPDATE photos SET is_active = false WHERE user_id = ? AND is_active = true;
UPDATE photos SET is_active = true  WHERE id = ? AND user_id = ?;
COMMIT;
```

The general habit: always validate that the changes you’re about to make can’t leave your data in an inconsistent state. Check first, then write. [[L-0136]]

One proposal was to split the handling in two: if zero rows come back, application logic reports that the id wasn’t found, while a transaction that fails rolls back by itself. [[L-0137]] Careful with the second half. An UPDATE that matches no rows is not an error, so nothing rolls back on its own. In MySQL, `ROW_COUNT()` after an UPDATE returns the number of rows actually changed, so the application can check it and issue ROLLBACK when it is 0. By default, an UPDATE that sets a row to the value it already has also counts as 0 changed <Cite href="https://dev.mysql.com/doc/refman/8.4/en/information-functions.html">dev.mysql.com</Cite>.

So should you check that the photo id belongs to this user before the update? 100%, you should. Get, then update. [[L-0171]] Security has to hold at every step. If you take care of it in one place and lapse in another, it doesn’t work. [[L-0172]]

### What the bug hunt bought

A really simple use case has many hidden intricacies. Going into them, asking why a field is needed and making sure the system is correct in every possible case, is what makes you a better engineer. [[L-0098]] With the updates wrapped in a transaction, the ownership check, and the redundant hash column stored, the Gravatar system is efficient and correct. [[L-0099]]

It is exactly like code review. Write five lines of code and you get 50 comments; write 500 and you get “looks good to me”. With a simple system, people nitpick every single thing. [[L-0100]]

<Section id="s2-5" no="2.5" title="Where does “active” live?" crumb="2.5 Where active lives"
  dek="One small optimization: move a single column from the photo to the user, and both the read and the write get simpler."
  meta="About 12 min · class 00:56–01:07, Q&A 01:19–01:22 and 01:31">

The most frequent query on Gravatar is the read: some page renders your photo. One very minor optimization is left in it. It is extreme nitpicking, and in practical use cases the performance difference is very minimal. [[L-0101]]

Here is the read as it stands. Correctness ensures only one photo is active, so it returns one row. [[L-0102]]

```sql
select * from photos
  join users on photos.user_id = users.id
  where users.hash = ?
    and photos.is_active = true;
```

Swapping it for an inner join, or a left join, isn’t the optimization: here they perform exactly the same. [[L-0103]] MySQL even rewrites such a LEFT JOIN into an inner join by itself, because `photos.is_active = true` can never be true for a NULL-filled row, which frees the optimizer to pick a better join order <Cite href="https://dev.mysql.com/doc/refman/8.4/en/outer-join-simplification.html">dev.mysql.com</Cite>.

Read it in the order it runs: the filter on the hash gives one user row and its id, that id joins to the user’s photos (several rows), and `is_active` filters those. You don’t pick that order; the optimizer does, and here it picks this one (the note below shows how). [[L-0104]]

It is tempting to see the `is_active = true` filter as the extra work. It isn’t a problem: by then you have narrowed down to a few indexed rows, so it is an index lookup, very fast. [[L-0105]] That narrowing relies on an index on `photos.user_id`. MySQL’s InnoDB creates one on a foreign-key column automatically if none exists; PostgreSQL does not, and its docs say indexing the referencing column is often a good idea (<Cite href="https://dev.mysql.com/doc/refman/8.4/en/create-table-foreign-keys.html">MySQL</Cite>, <Cite href="https://www.postgresql.org/docs/current/ddl-constraints.html">PostgreSQL</Cite>).

Another idea for the write: don’t update if the photo is already active. The board’s second update already does that: its `and is_active = false` matches no row when the photo is already active. [[L-0106]]

<MarginNote title="How the database runs the join" why="skip unless you read query plans" k="L-0141 L-0142 L-0143 L-0144 L-0145">

Why not filter on the user id directly? Because the input from the URL is the hash. The join on user id is only a join criterion, since it is the foreign key, not a filter.

The query narrows step by step. The filter on the hash leaves one candidate row in `users`. Joined on that user’s id, it matches, say, the 10 photos they uploaded. The is-active filter leaves the active one.

You don’t choose that order: the query optimizer does. Here it finds the unique key on the hash and evaluates that first, then applies the join criterion. SQL engines do this with **predicate pushdown**: filters are pushed to the bottom of the evaluation tree, the leaf nodes, so they are applied first, then the join, then the rest going up. The tree is evaluated from the bottom to the top. Search for “predicate pushdown” to see it in your database’s plans.

### The move: `active_photo_id` on users

Store `active_photo_id` in the `users` table. Gravatar is a read-heavy system: reading becomes a single lookup, and the transaction-heavy marking scheme goes away. [[L-0107]]

At first, marking a photo active still sits in a transaction, now updating `users`: select the photo from `photos`, then `update users` with `set active_photo_id = ?` for this user. [[L-0108]]

The most frequent query no longer needs a join. One row from `users` gives you the active photo id and the user id; from those you build the S3 path, read the file and serve it. It was first written as a lookup by id. The URL carries the hash, though, so it is `where hash = ?`, as was confirmed later in class; a unique indexed lookup is as cheap as one on the primary key. [[L-0109]]

```sql
-- read: no join
select * from users where hash = ?;

-- mark active: one statement (after the ownership check)
update users set active_photo_id = ? where hash = ?;
```

Why keep `is_active` on photos at all, then? It was there to mark one of several photos as active. With `active_photo_id` on users, the rare question “is this photo active?” is answered by joining with users. [[L-0110]] So it goes.

Marking a photo active no longer needs the other photos marked inactive. It is a single UPDATE, still carrying its checks, and with auto-commit a single query is a transaction in itself, so there is no multi-query transaction left to get wrong. [[L-0111]] MySQL starts each connection with autocommit enabled: it commits after every statement that doesn’t return an error, and you use START TRANSACTION … COMMIT only to group several <Cite href="https://dev.mysql.com/doc/refman/8.4/en/innodb-autocommit-commit-rollback.html">dev.mysql.com</Cite>. The board’s clean version is the update in the block above, `where hash = ?`, and the photo must still be checked as this user’s before it runs.

It is counterintuitive, because you think of “active” as a property of the photo, not of the user. Class design, low-level design and schema design all train us to think in attributes of an entity, which is why most people put `is_active` on photos. [[L-0112]] In the instructor’s experience, every single cohort since this question was first asked (this was the fifteenth) has started with `is_active` on photos, because we are trained to; that is why this page walks the same path instead of jumping to the answer. [[L-0114]]

There is no one way to build a system. What seems simple isn’t, once you go into the details, and many things can be challenged. [[L-0113]] The claim isn’t that `active_photo_id` is hugely more optimal; it is that a somewhat more optimized solution can exist. So keep challenging your own beliefs: unlearn, relearn, and become better. [[L-0115]]

The board kept it as a note under “possible optimizations”: denormalize `users` to avoid joins, storing `active_photo_id`, or even the active photo’s S3 key directly. [[L-0147]]

<RecallQuestions>
  <RecallItem k="L-0081 L-0083" q="Why does <code>WHERE HASH(email) = ?</code> read every row, and what are two ways to avoid it?">

The database can’t know which email hashes to the value without hashing every one, so a plain index on `email` is useless and it scans the whole table, on every request. Store the hash in its own column and index it (this design), or build an index on the expression itself, which PostgreSQL and MySQL 8 support as long as the query uses the same expression.

  </RecallItem>
  <RecallItem k="L-0089 L-0093 L-0097" q="List the three bugs found in the one-line mark-active query and the fix for each.">

One: the old active photo stays active, so first clear it with a second update (only on the row where `is_active = true`). Two: a crash between the two updates leaves no active photo and every site gets a 404, so wrap both in an explicit transaction. Three: the photo id comes from the front end, so the second update must also check `user_id = ?`; better, check first with a locking select and write only if the row exists.

  </RecallItem>
  <RecallItem k="L-0111 L-0171" q="After moving to <code>active_photo_id</code>, why is a single UPDATE enough, and which check must it still carry?">

Only one column on one `users` row changes, so there is nothing else to keep in step, and under auto-commit a single statement is a transaction in itself. It must still check that the photo belongs to this user (get, then update); otherwise anyone could point their Gravatar at somebody else’s photo.

  </RecallItem>
