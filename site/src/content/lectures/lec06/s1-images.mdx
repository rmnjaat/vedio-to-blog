Someone shares a link to a GitHub repository on a social site, and a card appears under the post: the repository’s name, its description, and its current numbers of stars, forks and contributors. Nobody uploaded that picture. Where did it come from?

The answer takes four steps: what a browser does with an image URL, what the server does with the request, how a handler can return an image nobody stored, and how GitHub serves millions of those cheaply. With that in hand, Gravatar in the next chapter becomes an easy problem.

</Section>

<Section id="s1-1" no="1.1" title="What the browser actually does with an image URL" crumb="1.1 The browser"
  dek="The browser doesn’t know it is fetching an image. It asks, then reads the bytes."
  meta="About 4 min · class 00:05–00:10">

Look at any profile picture on any page and ask how it got there. The usual answer comes without a thought: “it’s served”. That sentence hides the actual work. Someone wrote the code that reads that image and sends it, so the real question is how a static file gets served at all. Once you see it, a surprising number of features turn out to be built on it. [[L-0013 L-0014]]

It is tempting to think the browser knows a URL points at an image because it ends in `.jpg`. It doesn’t have a clue. [[L-0015]] A browser is a deliberately dumb piece of software with a fixed, defined behaviour for everything, and the same goes for apps. [[L-0016]] In the lecture’s view this is the nature of any platform, whether the browser, the Android OS, iOS or their SDKs: they are building blocks, so they can’t be very smart. They have to stay basic enough to be used with hundreds of other things. [[L-0017]]

So what does happen? To show an image you put its URL in an `<img>` tag’s `src`. While rendering the HTML, the browser reaches that tag and makes an HTTP GET request to whatever URL is in `src`, any URL at all. [[L-0018]] It has no idea what the GET will return. It is expecting an image, so it tries to interpret whatever comes back in the response as one. [[L-0019]]

<Figure id="fig-1a" max={880} no="Fig 1·a" k="L-0015 L-0018 L-0019 L-0020 L-0021" caption="The img tag is the only reason the browser expects an image. It sends a GET, reads the first bytes of the answer, picks the matching decoder and paints pixels. The URL deliberately has no extension. Inset: real format signatures.">
<Desk><ImgToPixels /></Desk>
<Phone><ImgToPixels layout="phone" /></Phone>
</Figure>

How can it interpret raw bytes? Every file format starts with a header that identifies it. A PNG file’s header says it is a PNG, and JPG, bitmap and TIFF files have headers too. <ForwardChip label="from" when="Lecture 7" k="L-0020">uploading an image to a GitHub issue, where the PNG bytes went out header first</ForwardChip> [[L-0020]]

On a 2xx response the browser checks the header of the bytes it got back, decides the format (“this is a PNG”), invokes the matching decoder and renders the decoded image as pixels on the screen. [[L-0021]] The header check is standardised: browsers follow the WHATWG MIME Sniffing rules <Cite href="https://mimesniff.spec.whatwg.org/">mimesniff.spec.whatwg.org</Cite>, which recognise the signatures of ICO, BMP, GIF, WebP, PNG and JPEG. A PNG always starts with the 8 bytes `89 50 4E 47 0D 0A 1A 0A`, a JPEG with `FF D8 FF`, a BMP with the letters `BM`, and a GIF with `GIF87a` or `GIF89a` <Cite href="https://www.w3.org/TR/png-3/">w3.org</Cite>. SVG is the exception: it is not sniffed, so it must arrive with `Content-Type: image/svg+xml`.

Every browser ships with image decoders for these formats; it mostly decodes, it rarely needs to encode. [[L-0022]] The common set on the web is PNG, JPEG, GIF, WebP and AVIF, plus SVG rendering. TIFF, which you might expect in that list, displays natively only in Safari <Cite href="https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Formats/Image_types">developer.mozilla.org</Cite>.

<Section id="s1-2" no="1.2" title="The static folder is code, and you can write your own" crumb="1.2 Static is code"
  dek="Serving a file from /static is a few lines someone already wrote. Write your own and the file can come from anywhere."
  meta="About 6 min · class 00:10–00:16">

Take the board’s example: the path `/static/img/arpit.jpg` on the host `arpitbhayani.me`. The GET reaches the web server behind that domain, and the server looks up which handler owns that path. [[L-0023]]

Usually that handler is a **static folder mapping**: a URL prefix such as `/static` is tied to a folder on the local disk. You configure it in nginx, Spring Boot, Flask or Django, and every framework supports a static folder path. [[L-0024]] Django is a partial exception: it serves static files itself only in development, and its docs call that method “grossly inefficient and probably insecure” for production, where a web server, a CDN or WhiteNoise serves them instead <Cite href="https://docs.djangoproject.com/en/stable/howto/static-files/">docs.djangoproject.com</Cite>.

With `/static` mapped, whatever follows `/static` in the URL is treated as a relative file path. The server goes to the static folder, reads the file at that path and sends its bytes as the response. It doesn’t care whether the file is an image, text or anything else. [[L-0025]] Because that path comes straight from the URL, it is untrusted input: a request for `/static/../../etc/passwd` must not escape the folder. Flask’s `send_from_directory` guards against this with Werkzeug’s `safe_join`, which joins “untrusted path components to a trusted base directory to avoid escaping the base directory” <Cite href="https://werkzeug.palletsprojects.com/en/stable/utils/">werkzeug.palletsprojects.com</Cite>.

So `/static/img/arpit.jpg` makes the server look for `img/arpit.jpg` inside the folder mapped to `/static`, here `site/static/img/arpit.jpg`. It finds the file, reads its bytes and returns them, and the browser renders them as an image because the URL sat in an `<img>` tag. [[L-0026]]

<Figure id="fig-1b" max={700} no="Fig 1·b" k="L-0024 L-0025 L-0026 L-0029 L-0030" caption="Left: /static is mapped to a folder, so the rest of the path is a file on the server’s disk. Right: a /raw route reads the same kind of path from S3 instead. Same three steps, different source. Redrawn from the class board at 00:12 (names replaced).">
<Desk><TwoHandlers /></Desk>
<Phone><TwoHandlers layout="phone" /></Phone>
</Figure>

None of this happens automatically. It is a piece of code built into the web server, so that you don’t have to re-implement it again and again. [[L-0027]] And if it is just code, you can write your own handler that reads the file from somewhere else, for example from S3 instead of the local disk. [[L-0028]]

Here is one. Expose a route `/raw/<path>`. Whatever path follows `/raw` is used as the key of an object in a configured S3 bucket; the handler reads that object and returns it, so a request for `/raw/users/logo.jpg` on `localhost:5000` returns the file stored at `users/logo.jpg`. [[L-0029]]

```python
@app.route('/raw/<path>')
def raw_handler(path):
    raw_b = S3.read(path, BUCKET)   # real code: set Content-Type, and never trust the path
    return raw_b
```

One generic route, with no configuration per file on S3, and three or four lines of code: the server is now a proxy for S3. [[L-0030]] The comment in the code matters in a real handler. Browsers go by the MIME type, not the file extension, so when your own handler returns file bytes, set the `Content-Type` header yourself, for example from a type stored with the file <Cite href="https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/MIME_types">developer.mozilla.org</Cite>. nginx does this for its static files by mapping extensions to MIME types.

This is not a feature, and it is not a new CDN. It only shows that an image can come back as part of a normal HTTP response; the practical uses come next. [[L-0031]] Many people assume a web server can only send JSON responses. It can send any bytes, and an HTTP handler can send images as easily as anything else. [[L-0032]]

</Section>

<Section id="s1-3" no="1.3" title="An image that doesn’t exist yet" crumb="1.3 Made on request"
  dek="If the handler is yours, the image doesn’t have to be stored anywhere. It only has to be bytes by the time the response leaves."

Because the handler is in your control, the image doesn’t need to exist before someone asks for it. The handler can run any custom logic. What matters is the bytes it sends: if they are a properly structured, byte-serialized image, the browser renders it. [[L-0033]]

Now back to the shared repository. Share a link to a GitHub repository on Twitter, LinkedIn or Facebook, and the platform renders a snippet: the title, the site name, the description and an image. The class demo used the instructor’s own repository, DiceDB. [[L-0034]] That image is not generic. It is specific to the repository, showing its description and its numbers of contributors, issues, discussions, stars and forks. [[L-0035]]

The snippet comes from the **Open Graph protocol** (OG). The HTML you serve names an `og:image`, and whatever URL you give there is drawn as the image in the snippet. [[L-0036]] Open Graph requires four properties on every page, `og:title`, `og:type`, `og:image` and `og:url`, and defines `og:image` as “an image URL which should represent your object within the graph” <Cite href="https://ogp.me/">ogp.me</Cite>.

Open GitHub’s page source, search for `og:image` and paste its URL into a browser: you get the same image. Look carefully at that URL, though. It doesn’t end in `.jpg`, `.png` or any image extension. [[L-0037]]

It does return a valid image as a byte response. But a valid image response doesn’t mean the image is stored on S3 somewhere. [[L-0038]] The card shows the repository’s current state, such as its contributor and fork counts. If those change, the card changes too, perhaps a day or two later. That “day or two” is an estimate; GitHub publishes no refresh interval. Either way the card is very recent, which already tells you it is not made once and kept. [[L-0039]]

<PauseAndThink k="L-0040 L-0038 L-0039 L-0041 L-0046"

A request goes to the CDN. On a miss, the origin fills a template with the repository’s current numbers and returns the image, and the CDN keeps it until its TTL runs out. A valid image response says nothing about where, or whether, the image was stored.

</PauseAndThink>

Many people assume such images are pre-generated. They are not. GitHub has millions of repositories; why would it spend compute generating one image per repository every single day? The image is generated on demand, when it is requested, and because it carries recent information it couldn’t be generated once and stored anyway. [[L-0040]]

Put that URL in an `<img>` tag and it renders without a hiccup, because it is essentially the same kind of route handler as `/raw/<path>`, put behind a CDN. [[L-0041]] GitHub even runs a separate CDN for these images, `opengraph.githubassets.com`, alongside `githubusercontent.com`, the CDN for user assets. <ForwardChip label="from" when="Lecture 7" k="L-0042">a CDN on its own subdomain, edge.arpitbhayani.me</ForwardChip> [[L-0042]]

<Section id="s1-4" no="1.4" title="On demand, behind a CDN" crumb="1.4 On demand"
  dek="Render on a miss, cache with a TTL, render again when it expires. That is the whole trick."
  meta="About 6 min · class 00:21–00:27">

A million people open the same repository card. Who draws it, and how often?

The flow is simple. The backend sends the image URL to the frontend; its key stays constant for a repository, or it can be generated on the fly. The frontend puts it in an `<img>` tag. The request goes to the CDN at `opengraph.githubassets.com`, and if the CDN has the image cached, it serves it right away without going to the backend server. [[L-0043]] If the CDN doesn’t have it, the CDN calls the origin, GitHub’s API server, which handles the request by generating the image on the fly. [[L-0044]]

<Figure id="fig-1c" max={880} no="Fig 1·c" k="L-0041 L-0043 L-0044 L-0045 L-0046" caption="The card URL is a route handler behind a CDN. Hits never reach GitHub’s servers; a miss makes the card service fill a template with fresh numbers, and the CDN keeps the result for about a day. The numbers at the right are from GitHub’s own 2021 write-up.">
<Desk><RepoCard /></Desk>
<Phone><RepoCard layout="phone" /></Phone>
</Figure>

The image is a template. Whichever repository you pick, you see exactly the same format: the title here, the repository icon there, and the key statistics, fetched for that repository, in fixed places. [[L-0045]]

The API server sends the generated image back to the CDN. The CDN caches it with some TTL and serves the following requests itself. After the TTL runs out, say after a day, the next request is a miss, goes to the backend, and a new image is generated on demand. [[L-0046]] That TTL is usually set by the origin with a `Cache-Control` header: `s-maxage` sets freshness for shared caches such as CDNs and overrides `max-age` there, so a card can stay a day at the CDN without browsers keeping it that long <Cite href="https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cache-Control">developer.mozilla.org</Cite>.

To draw the image you need an image library, such as ImageMagick or PIL, and there are tons of others. Typically PIL, the Python Image Library, is the best out there: it internally uses ImageMagick through a C++ binding and gives you a native Python interface for creating images on the fly. [[L-0047]]

<SourceNote href="https://pillow.readthedocs.io/en/stable/" site="pillow.readthedocs.io" k="L-0047">

Pillow, the maintained fork of PIL, is a popular Python library for generating images, but it does not use ImageMagick. It has its own C imaging core and links libraries such as libjpeg, zlib, libtiff and FreeType <Cite href="https://pillow.readthedocs.io/en/stable/installation/building-from-source.html">pillow.readthedocs.io</Cite>. ImageMagick is a separate tool; to drive it from Python you use a separate binding such as Wand <Cite href="https://docs.wand-py.org/en/latest/">docs.wand-py.org</Cite>.

</SourceNote>

GitHub’s own write-up gives real numbers for this design. Generating one image takes 280 ms on average, the service produces around two million “unique-ish” images a day, and 40% of requests are served a cached image <Cite href="https://github.blog/open-source/git/framework-building-open-graph-images/">github.blog</Cite>. It also shows a second way to draw a card: GitHub’s generator is “a little Node.js app” that fetches data through the GitHub GraphQL API, fills an HTML template and captures it with Puppeteer, rendering HTML in a headless browser instead of drawing with an image library.

You will now spot this in hundreds of places. Bannerbear is a company that specializes in exactly this, and it makes social sharing easy, interactive and real-time. [[L-0048]]

Here is a hypothetical, to see how far it goes. Today people screenshot a tweet, polish it with a tool like poet.so and post the image on LinkedIn. Twitter could make that native: when a tweet’s URL is shared, its `og:image` would be a nicely formatted image of the tweet. On a CDN miss, Twitter’s API server would fill a template with the tweet, format it and respond, and the CDN would cache it. [[L-0049]] Cards like that are powerful user experience. The reader sees something personalized and very recent, the current likes, shares, comments and reposts right in the shared image, instead of a static picture. [[L-0050]]

GitHub itself is the before-and-after. Earlier, sharing a GitHub link rendered a big, poor-looking avatar of the user, which was a poor experience. GitHub built the generated repository card to make sharing repositories on social media pleasant. [[L-0052]]

<MarginNote title="Build it in an hour" why="skip unless you’ll build it (you should)" k="L-0051 L-0053">

A local prototype of on-the-fly social images is hardly an hour of work. Install Python (Java, or whatever language you use, has such libraries too) and pick a library that generates images. Expose one API endpoint that fetches a GitHub repository’s information, creates the card on the fly and serves it on localhost. It works for any repository in the world, and you learn a lot by doing it. [[L-0051]]

Nothing in this course is theoretical. Everything discussed is used in production by some company, and you can prototype it on your own machine: you don’t need 50,000 servers to try it. [[L-0053]]

</MarginNote>
