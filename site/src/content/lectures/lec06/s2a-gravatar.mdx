<Section id="s2" no="2" title="Gravatar: the query decides the design" crumb="2 Gravatar"
  dek="A system so simple you’d draw two boxes and stop. Write the exact queries and it changes three times: a stored hash, a transaction with an ownership check, and “active” moving to the user."
  meta="About 30 min · class 00:27–01:07, Q&A 01:14–01:34, 02:48">

You sign up to a forum with your email. You never uploaded a photo there, yet your face sits next to your first post. Somewhere, one URL built from your email returns your current picture to any site that asks for it.

This chapter builds that service. On a whiteboard it is two boxes and a bucket. Write the exact queries, though, and the design changes three times: a column you were told not to store comes back, the one-line update grows a transaction and an ownership check, and “active” moves from the photo to the user.

</Section>

<Section id="s2-1" no="2.1" title="One URL for your face" crumb="2.1 One URL"
  dek="Gravatar is an image handler with a twist: the path is a hash of your email, so any site that knows your email can show your photo."
  meta="About 5 min · class 00:27–00:32 and 02:48–02:50">

Once an image is just the response of a handler ([§1.2](#s1-2)), Gravatar becomes an easy problem. What it does is create a single embeddable URL for your profile picture. That is why some websites can show your photo even though you never signed up there with Twitter, Gmail, Microsoft or similar. [[L-0055]]

On gravatar.com you log in with your email, upload a bunch of profile pictures and mark one of them as active. [[L-0056]]

The URL is `gravatar.com/` followed by the MD5 hash of your email. It is constant, because a hash function given the same input always gives the same output: same email, same hash, same URL. [[L-0057]]

<SourceNote href="https://docs.gravatar.com/general/hash/" k="L-0057">

Gravatar’s documentation (checked October 2026) asks for SHA-256 today, not MD5; MD5 was the original scheme <Cite href="https://gitlab.com/gitlab-org/gitlab/-/issues/370057">gitlab.com</Cite>. The email is trimmed of leading and trailing spaces and lower-cased before hashing, and skipping either step gives a different hash, so the avatar isn’t found. The image path is `/avatar/<hash>` <Cite href="https://docs.gravatar.com/sdk/images/">docs.gravatar.com</Cite>. The point stands: same email, same hash, same URL.

</SourceNote>

Put that URL in an `<img src>` and it returns the current profile photo as image bytes. It doesn’t redirect to some other page: it is the same kind of handler as §1.2’s `/raw`, reading the active photo and sending it back. If the email has no Gravatar, a default image comes back instead. Query parameters choose the size and that fallback: `s=` sets the size (1 to 2048 px, default 80), and `d=` picks what to show when no avatar exists, down to `d=404` for a plain HTTP 404 <Cite href="https://docs.gravatar.com/sdk/images/">docs.gravatar.com</Cite>. [[L-0058]]

```html
<!-- say hash("ana@example.com") = 0eafd172 (the board's example, shortened) -->
<img src="https://gravatar.com/0eafd172" />
```

Now imagine every platform adopted it. Each would hash your email and render your photo from that one URL. To change your photo you upload a new one on gravatar.com and mark it active, and the next request, on every site, picks it up without any social network doing anything. [[L-0059]] Platforms obviously don’t all do that, but it is a very novel concept. [[L-0060]]

Why a hash, and not the email itself? The email is personal data (PII), so the URL carries a hash of it, for security. [[L-0054]] That keeps the address out of plain sight, and not much more. Gravatar hashes are unsalted and fast, so anyone holding a list of guessed addresses can hash them all and match them against Gravatar URLs; switching from MD5 to SHA-256 is “almost no change” for this <Cite href="https://seclists.org/oss-sec/2024/q3/273">oss-sec</Cite>.

And why not mix a Gravatar user id into the hash, to scramble it further? Because the hash has to be a universal function. A site like Facebook that integrates Gravatar doesn’t know your Gravatar user id; it knows your email. From the email alone it can compute the hash, check whether you have a Gravatar and render it directly. [[L-0310]]

So the requirements are three: [[L-0062]]

1. A user can upload several pictures.
2. A user can mark one of them as active.
3. When the URL is requested, the active one comes back in the response.

<MarginNote title="Build it" why="skip unless you’re building it" k="L-0061">

In the instructor’s estimate, a Gravatar-like prototype is three or four hours of work. Building a prototype isn’t the hard part, so build as many prototypes as you can: Chapter 1’s `/raw` handler, the two tables of the next section and one hash.

</MarginNote>

<Section id="s2-2" no="2.2" title="Question every column" crumb="2.2 Every column"
  dek="Two tables, and a reason for every column you keep or cross off."
  meta="About 5 min · class 00:32–00:36, Q&A 01:31–01:34">

Start with the database: which tables, which schema, what to store. [[L-0063]]

A first proposal is a `users` table that stores the hash of each user’s email. [[L-0064]] The tempting refinement goes further: store only the hash and not the email. One is derivable from the other, it saves space, and unlike a social network Gravatar never needs to show the email to anyone. [[L-0065]]

Always store the actual email. Users log in and are authenticated with it, they expect to see it on their own profile page, and leaning on the hash alone risks a collision that logs someone into another person’s account. (Nor could you get the email back from a hash: §2.3.) [[L-0066]]

So `users` is `(id, email)`. The hash column was written on the board and then crossed off on purpose, because it is derivable, which is exactly the previous lecture’s rule. [[L-0067]]

<ForwardChip block label="from" when="Lecture 7" k="L-0067">don’t store what you can derive, from the Instagram design</ForwardChip>

A user has several photos, and a single column of a relational database can’t hold several image paths, so photos get a table of their own. [[L-0068]] `photos(id, user_id)` has one row per uploaded photo: a user with 10 photos has 10 rows, and all of them must render on their photos page. [[L-0069]]

Should each row also store the image’s path in S3? Same answer as for the hash. Recall the previous lecture: can you not derive it? You can, so it isn’t stored. [[L-0070]] The S3 path is built on the fly from the user id and the photo id, both of which you already have ([§3.1](#s3-1) shows the bucket layout). [[L-0121]]

Last, to know which photo is the current one, `photos` gets an `is_active` column, a boolean: true or false. [[L-0071]]

<MarginNote title="Bool, tiny int or string?" why="skip unless you pick column types" k="L-0168 L-0169 L-0170">

An integer-based enum instead of a boolean is fine, and leaves room for a third state later, as long as you store it as a tiny int. A boolean takes 8 bits, one byte. Use a tiny int rather than a big integer, and never store a state as a string.

Two engine details. In MySQL, `BOOL` is a synonym for `TINYINT(1)`, and the `(1)` is only a display width, so the column can hold anything from −128 to 127; add a CHECK constraint if only 0 and 1 are allowed <Cite href="https://dev.mysql.com/doc/refman/8.4/en/numeric-type-syntax.html">dev.mysql.com</Cite>. PostgreSQL has no TINYINT at all: its smallest integer type is the 2-byte `smallint`, so a one-byte state column there is `boolean`, or use `smallint` with a CHECK <Cite href="https://www.postgresql.org/docs/current/datatype-numeric.html">postgresql.org</Cite>.

</MarginNote>

<MarginNote title="Why no join table, like Slack’s?" why="skip unless you remember Lecture 4" k="L-0173">

Slack’s schema put a membership table between users and channels; here `photos` simply references its user. Both relationships are one-to-many, so that isn’t the difference. Slack’s membership row carried per-user details of its own, such as the last-read checkpoint and whether the user starred the channel. Gravatar has nothing like that to keep, so a foreign key on `photos` is enough.

<Section id="s2-3" no="2.3" title="The query that reads every row" crumb="2.3 Every row"
  dek="Write the exact query for one Gravatar request, and the column you crossed off comes back."
  meta="About 9 min · class 00:36–00:45 and 01:19">

Take the simplest read: show me all my photos. Write the exact query. A first draft is `select * from photos` `where user_id = ?`. It needs no `is_active` filter: the page shows every photo, and only one of them is active anyway. [[L-0072]] One suggestion was to select only the columns you need instead of `*`; it was noted in passing, without a clear verdict either way. [[L-0073]]

But a Gravatar request doesn’t carry a user id. What you get is the hash of an email. So the query has to join `photos` with `users` on `photos.user_id = users.id` and filter on the user that the hash identifies. [[L-0074]]

Could you turn the hash back into the email? No. You cannot get an email from its hash: this is hashing, not encryption, and hashing is lossy. [[L-0075]] One proposal followed from that: since you can’t go backwards, the hash must be stored. The answer at that point in class was different: apply the hash function in the WHERE clause instead. [[L-0076]]

```sql
-- the URL gives a hash; users stores only the email
SELECT p.* FROM photos p
JOIN users u ON p.user_id = u.id
WHERE HASH(u.email) = ?;
```

Functionally, this works. [[L-0077]] Collisions are set aside: assume hashes are unique, since two people with the same hash couldn’t be told apart anyway. [[L-0078]] It does add a computation, a hash of an email on every query, so even with a lightweight hash it is no longer a simple query. [[L-0079]] The real question is how many rows it touches.

<PauseAndThink k="L-0074 L-0077 L-0079 L-0080 L-0081 L-0083"
  q="You didn’t store the email’s hash, because it’s derivable. The URL gives you a hash, so the query says <code>WHERE HASH(users.email) = ?</code>. With 10,000 users and an index on <code>email</code>, how many rows does the database look at to find one user?"
  choices={[{ label: 'About one. The index on email finds it.' }, { label: 'All 10,000. It must hash every email.', correct: true }]}
  right="Right: all 10,000. It’s a full table scan on every request, before the join even starts."
  wrong="Not quite: it reads all 10,000. The index is on email, but the query asks about HASH(email). The database can’t tell which email hashes to your value without hashing them, so the index doesn’t help.">

A computation in the WHERE clause hides the column from its index. Store the hash in its own column, index it, and query `WHERE hash = ?`: one lookup. (More precisely, an index built on the expression itself would also work; see the note below.)

</PauseAndThink>

That full scan is the pain point. Because of the hash in the WHERE clause, the database has to read every row, compute each email’s hash and compare it, a whole-table scan, before it can even do the join. [[L-0080]]

<AnimationClip clip="l06-hash-scan" no="Clip 2·1" k="L-0080 L-0081 L-0083"
  caption="Hashing in the WHERE clause makes the database hash every email to find the match, on every request. A stored, indexed hash is one lookup. Not storing a derivable value cost a full scan, so store it." />

The reason is general. When the WHERE clause itself contains a computation, as in `HASH(email) = ?`, the database can’t use its indexes: it has no way to know which email evaluates to that hash without computing it for every row. So every query becomes a full table scan. [[L-0081]]

<SourceNote href="https://www.postgresql.org/docs/current/indexes-expressional.html" k="L-0081">

That holds for a plain index on the column. You can also index the expression itself. PostgreSQL can index an expression, e.g. `CREATE INDEX ON users` `(lower(email))`; a query with `WHERE lower(email) = 'x'` then searches as fast as any simple index lookup, at the cost of computing the expression on every insert and every non-HOT update. MySQL 8 supports functional key parts, e.g. `CREATE INDEX idx1 ON t1` `((col1 + col2))`; the query must contain the same expression, and the manual’s example shows an index on `SUBSTRING(col1, 1, 10)` is not used for `SUBSTRING(col1, 1, 9)` <Cite href="https://dev.mysql.com/doc/refman/8.4/en/create-index.html">dev.mysql.com</Cite>. Either way the computed value is stored somewhere: in an index, or, as here, in a column of its own.

</SourceNote>

This openly contradicts the previous lecture. It is not always true that what is derivable shouldn’t be stored. It depends: if not storing it slows things down, store the redundant value. [[L-0082]]

The fix: give `users` a `hash` column, index it, and query `WHERE users.hash = ?`. The lookup becomes very pointy, almost O(1): filter the one user row, take its id, join to that user’s photos. Very quick, and since this query runs on every request, leaving the column out would have been very expensive. [[L-0083]]

```sql
-- one index lookup
SELECT p.* FROM photos p
JOIN users u ON p.user_id = u.id
WHERE u.hash = ?;
```

  caption="The same request, two WHERE clauses. Computing the hash in the query means hashing every row; storing and indexing it means one walk down the index. The emails are made up.">
  <Desk><TwoWhereClauses /></Desk>
  <Phone><TwoWhereClauses layout="phone" /></Phone>
</Figure>

So when a user is created, store the email and also compute and store its hash. Email is a unique key, hash is a unique key, and both are indexed; the board marks `id`, `email` and `hash` with a `*`. [[L-0084]]

Drawing boxes is easy; the devil lies in the details. Only by writing the query and working out how it would execute do you find that a column you thought unnecessary is needed for performance. The hash column is the classic example: scratch the surface of a simple design and its ugly parts show. [[L-0085]]
