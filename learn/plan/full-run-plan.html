The reusable pipeline

One command per video. Each stage writes to lectures/<id>/, can be re-run on its own, and skips work that's already done. Plain scripts do the mechanical work; every judgement step is a Claude Code call on your subscription (claude -p), driven by a prompt file and a skill, never an API key.

  1. Ingest script

    Extract 16 kHz audio and sample board frames with timestamps; detect scene changes.

  2. Transcribe script

    mlx-whisper on the GPU. Spot-checks the spoken language first; Hindi-heavy lectures switch to the Hinglish model.

  3. Speakers script

    sherpa-onnx diarization, merged onto the transcript.

  4. Correct Claude

    The existing correction skill, about 16 chunks per lecture in parallel; the verify script must pass.

  5. Read the board Claude

    Every board state transcribed, every diagram described, transcript flags resolved.

  6. Ledger Claude

    Three analysts in parallel, then a gap hunter, then an editor who merges audio and board items. A script proves no item is lost.

  7. Fact-check Claude

    Three topic checkers with web sources, then an independent second checker re-opens every source.

  8. Design the lesson Claude

    Flow, sections, where each figure, prompt and animation goes; every ledger item placed.

  9. Animations Claude

    Research, storyboard script, Remotion build, render check (details below).

  10. Build the page Claude

    Writing, SVG figures and components in the Whiteboard Notebook system, inside one Astro site.

  11. Prove it Claude script

    Coverage script, blind exam, design critic, learner and accessibility test; fix and re-run until all pass.

Animations, done properly

Lecture 1's samples only had placeholders. This time each animation goes through four steps, captured as an explainer-animation skill so later lectures get the same treatment.

1 · DecidePick the 3–5 mechanisms per lecture where motion is the lesson (a write replicating and lagging, a Kafka rebalance, long polling holding a connection).
2 · ScriptA storyboard: scenes, timing, on-screen labels, captions, the ledger items it teaches, the still frame for reduced motion.
3 · BuildRemotion compositions in the Whiteboard Notebook style, played in the page with play, pause, scrub and 0.5× speed.
4 · CheckRender key frames to images, review them against the script, then a critic pass. Nothing ships unseen.

Who does what in this run

Per lecture (about 25 agents)

  • 16 transcript correctors, one per chunk
  • 1 board reader
  • 3 ledger analysts, 1 gap hunter, 1 editor
  • 3 fact-checkers, 1 independent verifier
  • 1 lesson designer, 1–2 writers, 1 diagram illustrator
  • 1 animation storyboarder, 1 animation builder
  • Coverage auditor, blind examiner, design critic, learner tester

Across the course (once)

  • Course architect: lecture order, chapters, cross-links between lectures, shared glossary
  • Design-system engineer: turns Whiteboard Notebook into reusable components and the figure kit
  • Animation researcher: what works for system design motion, writes the skill
  • Final reviewer: walks the whole site as a reader

Risks

Things that can slow or stop the run

  • Usage limits. Lecture 1 alone hit a limit once. Ten lectures with ~250 agent runs will likely hit limits again; the pipeline resumes where it stopped, but wall-clock time stretches.
  • The Mac must stay awake for the transcription hours; I'd run it under caffeinate.
  • Public site, paid course. Pages use our own writing and redrawn diagrams, no board screenshots. The repo is already public and holds board frames; you may want those out of it.
