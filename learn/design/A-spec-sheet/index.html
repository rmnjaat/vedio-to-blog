§ 2.4 · Scaling · Medium

Scaling the database

Medium’s API servers now sit behind a load balancer and scale out. Every request they accept still turns into a query against one database, and that database was sized for yesterday’s traffic.

Why API servers are the easy half They keep no state, so adding one is a rule in an autoscaling group or a Horizontal Pod Autoscaler. Data is where it gets interesting. REC 00:56:54

In § 2.3 we put a load balancer in front of Medium’s API servers and let them scale horizontally. An API server doesn’t answer requests by itself, though. It forwards the work to its dependencies: the database, a central cache, other services. Scale the API tier five times and you have multiplied the load on everything underneath it, whether or not those components were ready.

Cascading failure One component goes down, the components that depend on it go down next, until users can’t use the platform. It is the shape behind most of the big outages in distributed-systems postmortems. REC 00:47:28

The database is the most critical of those dependencies and also the most brittle. When it goes down, everything goes down with it. That is why the order you scale things in matters more than how fast you scale them.

Rule 2.4REC 00:46:41

Scale bottom up. The database and every other dependency first, then the API servers, then let the users in.

For a large campaign this is an org-level job. Each team you depend on should be able to say how it scales; how it does that is their problem, that it can is yours.

The board for this part of the lecture had three pictures on it. They are the three moves you have, in the order you usually make them:

2.4.1How far does a bigger machine go?#

The first move needs no code. Open the cloud console and pick a larger machine type: 16 GB of RAM becomes 32, then 64, 128, 256, 512 GB, 1 TB, 2 TB, 4 TB. Reads and writes both get more headroom, and the application never notices the change. For a young product this is the right default: horizontal setups make deployment more complex, and complexity you don’t need yet is premature optimisation.

Not the reason “The console doesn’t offer anything bigger” describes the symptom. Very large machines exist; supercomputers are real. The limit is that each step up needs physically different hardware.
Same limit, smaller box A phone whose SD slot supports 256 GB won’t read a 512 GB card. Nothing in software can fix that.

The ladder ends because hardware ends. RAM sits in slots; disks and network cards sit on a motherboard; bytes move between them over buses, and both sides of a bus have to speak the same hardware protocol. When a board can’t take a larger part, the next size up is a different machine, and you can only move to it if the data centre has one. Software is an abstraction, and under it is metal with fixed limits.

2.4.2What if most of the traffic is reads?#

Worked number Say the database sees 1,000 queries/s at 90:10. The 900 reads can spread over replicas. The 100 writes still land on the master.

It usually is. Read-to-write ratios of 90:10 or 99:1 are normal, and Medium sits at the read-heavy end: far more people read a story than write one. Handle reads well and most of the scaling problem goes away.

A read replica setup is one master plus one or more replicas, with asynchronous replication wired between them. Every write goes to the master. Each replica keeps a copy and serves reads. Databases support this almost natively; you configure it, you don’t build it.

The board draws it the other way On the whiteboard the replication arrow runs master → replica. In these figures it points at the master, because the replica is the side that asks. REC 00:50:40

Replication is often described as the master pushing changes out. It works the other way round: the replica connects to the master and pulls. The PostgreSQL documentation on streaming replication puts it in exactly those terms, “the standby connects to the primary, which streams WAL records to the standby as they’re generated”, and adds that it is asynchronous by default, so there is “a small delay between committing a transaction in the primary and the changes becoming visible in the standby”. That delay is typically under one second if the standby can keep up.

The database will not split reads from writes for you. In the basic setup the API server opens two connections and the business logic picks one for each query:

API server · pseudocodeREC 00:51:53
master  = connect(MASTER_URL)    # every write, plus reads that must be fresh
replica = connect(REPLICA_URL)   # reads that can be a moment old

def get_profile(user_id):
    return replica.query("SELECT … FROM users WHERE id = %s", user_id)

def publish_story(author_id, body):
    return master.execute("INSERT INTO stories …", author_id, body)
One connection string? Then a proxy-like layer is doing the routing for you. Not every stack has one, so learn the two-connection version first. It works the same on MySQL, Postgres or MongoDB. REC 00:59:59

Which reads may go to a replica is your decision, not the database’s. A read that can be a moment old is fine there. A read that must reflect the latest write goes to the master. The figure below steps through why.

Pause and think · commit before you look

Medium reads a user’s profile. A bank reads an account balance. Both are reads. Which of them can go to a replica?

The profile can go to the replica. If it is a second old, nobody is hurt. The balance is a critical read: a friend says the money has been sent, you open the app, and the replica hasn’t pulled that write yet. You see the old balance. Step 3 above, with money.

Sending everything to the master is safe but throws away the reason you added replicas. The rule is per query: fresh-or-wrong reads go to the master, the rest go to replicas.

Cheap or expensive pulls Some databases let a replica read the binlog file directly, which costs the master little. Others serve changes over SQL or their own protocol, which costs CPU, memory and bandwidth. REC 02:37:55

Replicas are not free for the master. Every replica fetching changes uses some of the master’s CPU, memory and network, so one master typically feeds about five replicas. If you need fifteen, build a tree: five replicas pull from the master, and each of those feeds two more. This is cascading replication.

Before you play it: with fifteen replicas, how many of them talk to the master?

When the master dies A replica can be promoted to master. Managed databases, AWS’s among them, do this for you. Writing leader election yourself is a pain most product companies never need to take on. REC 00:57:38

Two things replicas don’t fix. Every write still goes to a single master. And once adding replicas starts to hurt the master, you have reached the end of this move. That is the signal to shard.

2.4.3What if the master can’t take the writes?#

You have scaled the master vertically and added replicas, and it still gets more traffic than one node can handle. Sharding splits the data into mutually exclusive subsets and puts each subset on its own node. Every shard is a master for its own rows, and each shard can have its own replicas.

Shards are not copies Three shards are not three databases with the same data. Each holds its own share, about a third of the rows here. REC 01:02:06

For Medium, a natural split is by user. Hash the user ID to choose a shard, and keep that user-to-shard mapping fixed: a user’s rows have to be found on the shard they were written to. The routing lives in the API server.

API server · naive shardingREC 00:55:19
shards = [connect(SHARD_0_URL),   # one pool per shard:
          connect(SHARD_1_URL),   # TCP connections to a DB
          connect(SHARD_2_URL)]   # are stateful, so no sharing

def db_for(user_id):
    return shards[hash(user_id) % len(shards)]

def get_stories(user_id):
    return db_for(user_id).query("SELECT … WHERE author_id = %s", user_id)
Tables, not rows Moving 30 of your 100 tables onto another database is vertical sharding. It needs its own connection pool too. REC 01:02:24

That is the naive version: open a connection to every shard, work out which user a request is for, forward it, return the answer. Production systems often put a proxy layer in front of the shards. Build the naive one first anyway, because not every database has such a proxy, and you can’t reason about the proxy until you know what it is doing for you.

Why not let replicas take writes? That is multi-master. You then have to resolve write conflicts, and the right resolution is different for every use case. Sharding scales writes without that problem. REC 03:09:43

There is no formula for choosing a shard key. Look at the data and how it is accessed, then decide. Whether you write the routing at all depends on the database: some vendors’ clustered databases shard internally and look like one database to your application, while open-source databases without native sharding leave it to you.

2.4.4Which one, and in what order?#

TABLE 2.4 The three moves side by side
PropertyAVerticalBRead replicasCSharding
What changes Machine type, 16 GB → 4 TB One master plus about five async replicas Several masters, each holding an exclusive subset of rows
Scales reads yes, up to the hardware ceiling yes, add replicas; a tree past about five yes
Scales writes yes, up to the hardware ceiling no, every write hits the master yes, writes split by key
Your code Unchanged Two connections, chosen per query Key-based routing, one pool per shard
Where it breaks The data centre has no bigger hardware Stale reads during lag; each replica loads the master Key choice has no formula; the user→shard mapping must never move
Reach for it 1st · while it’s cheap 2nd · reads dominate 3rd · writes outgrow one node

So the order is: a bigger machine while that is still cheap, read replicas next, and sharding when one master can no longer take the writes or the replicas’ pulls. Multi-master comes after all three, and only if you want to make things complicated on purpose.

Check yourself

3 questions · answer first, then open
Q1Your database already runs on the largest machine type your provider lists. Why can’t the next step be one size bigger?Answer

Because the limit is physical. Every part has to be compatible with the bus and slot it plugs into; when the board can’t take a bigger part, the next size up is different hardware, and the data centre has to have it. From here, more capacity means more machines: replicas or shards.

Q2In a master–replica setup, which side starts replication, and what does your application have to do that the database won’t?Answer

The replica connects to the master and pulls changes; in PostgreSQL the standby opens the connection and the primary streams WAL to it. The application keeps two connections and chooses per query: writes and critical reads (a bank balance) to the master, reads that can be a moment old (a profile) to a replica.

Q3Medium runs three shards. Does each one hold a full copy of the stories table, and how does a request find the right shard?Answer

No. Each shard holds a mutually exclusive subset, roughly a third of the rows. The API server hashes the user ID to pick the shard, keeps one connection pool per shard, and forwards the query there. The mapping must stay fixed so a user’s rows are always found where they were written.
