Lecture 1: keeping Medium up

Ten API servers, one database

Say Medium's newsletter goes out at 09:00 and links one post. You prepared the way the last part said to: ten API servers behind the load balancer, 100 requests a second each, 1,000 in all. Every one of those requests ends in a query to the same database, and somewhere between 900 and 990 of them are reads.

The API servers took ten minutes to add because they keep nothing between requests. The database keeps everything, so it can't be cloned the same way. This part covers the three moves the lecture makes for it, in the order you'd make them, and what each move costs.

A bigger machine comes first, and it has a ceiling

The cheapest fix is a larger instance. In the console you change the machine type: 16 GB of RAM, then 32, 64, and on up. The class walked that ladder to 4 TB and stopped there, because the next size needs hardware the data centre doesn't have. The part on going up or out covers why.

Most teams stop well before the ceiling. The largest instances cost more per unit of capacity than mid-sized ones, and a bigger machine is still one machine. If it goes down for the resize, every API server waits on it.

Reads outnumber writes, so give reads their own copies

99:1 is a blog's number. Logging, metrics, IoT and chat are often write-heavy. Measure your own ratio before you build on this one.

On a blogging site the read-to-write ratio sits around 90:10, often nearer 99:1. One person writes a post and thousands read it. A read replica is a second database that holds a full copy of the data and serves only reads. All writes still go to the master, and the replica follows behind it.

Following behind is the cost. The replica gets each change a moment after the master commits it, and a read that lands in that moment sees the old data. The figure below follows one post through that gap.

New to replication? What master, replica and asynchronous mean, in a minute of reading.

The master is the one database allowed to accept writes. Every change it makes goes into a log, the binlog in MySQL and the write-ahead log in PostgreSQL.

A replica replays that log to keep its own copy current. Asynchronous means the master doesn't wait for any replica before telling the API server the write succeeded. So the write returns fast, and the replica may still be a little behind.

Setting one up is a configuration job in MySQL, PostgreSQL and every managed cloud database. Search for your database's replication guide and follow it on a laptop once.

Follow post 4182 from Publish to a reader's screen. The figure changes as each step reaches the middle of the screen; the buttons and the arrow keys do the same.

The writer presses Publish. An API server sends the INSERT down its master connection and the master commits it. At this instant exactly one machine at Medium has post 4182.

Nobody tells the replica. The replica keeps a connection open to the master and asks for every change after the last position it applied. That is why the arrow points up, at the master.

Once asked, the master answers on that same connection and keeps streaming new log records as they're written. MySQL calls the master's side the binlog dump thread, PostgreSQL calls it the walsender.12

A reader opens the post 300 ms after the commit. Reads go out on the replica connection. The replica hasn't applied 4182 yet, so the reader gets a 404 for a post that exists.

The replica applies the change, and the same request now returns the post. The distance between the two dots on the timeline is replication lag. PostgreSQL's documentation says it is typically under one second when the standby can keep up with the load.2 Under a heavy write burst it grows.

The database doesn't decide where a query goes. The API server holds two connection objects and the business logic chooses one per query. Strangers reading a feed can live with a second of lag. The writer's own page after Publish can't, so that one read goes to the master.

PostgreSQL's client library can prefer a standby through target_session_attrs,3 and Aurora gives you a reader endpoint that spreads connections across its replicas.4 Those layers choose a machine for each connection. They can't know which of your reads has to be fresh, so step 5 stays in your code.

Counting replicas for the 09:00 spike

How many replicas the newsletter needs depends on one number you can only get from a load test: how many queries a second one replica serves before its latency climbs. The lecture is firm that no formula gives you that. Below, 300 a second stands in for your measured value.

The class said about five. That was a feel for one self-run master, not a product limit. The managed limit is 15 per source on RDS for MySQL.5

Eighteen is past what one master will feed on most managed services. RDS for MySQL allows 15 read replicas per source and Aurora 15 readers per cluster.6 In PostgreSQL the cap is whatever you set max_wal_senders to, and in practice it is the master's spare CPU and network, since every replica streaming from it costs a little of both.

The class answer for this case is a tree. Five replicas pull from the master and each of them feeds three more, which gives 15 without asking more of the master. PostgreSQL calls this cascading replication.2 Each extra hop adds its own lag, so the bottom row is the most stale. And if the replicas are hurting the master, the lecture reads that as the signal for the next move.

When writes outgrow one master, split the data

Replicas multiply read capacity and do nothing for writes. Every replica replays every write, so ten /s of writes is ten per second on each of them too. When the master can't keep up with writes at the largest size you're willing to pay for, the lecture's next move is to shard the users table across three databases.

Before reading on, make a call.Medium's users table now lives on three shards. User 4182 edits her bio. How many of the three databases does that write change?

One. Each shard holds a different slice of the users, about a third each, and no row lives on two shards. Her row is on exactly one of them, so the edit is one write on one master. If that shard has replicas of its own, they ask for the change afterwards, the same way as in Fig. 1.

This exact question came up in the live class, phrased as "so sharding means keeping three copies?"

The wrong turn: shards as copies. The belief is that sharding means running three identical databases. It's an easy one to hold, because replicas are copies and both moves add database machines.

Run it on a users table of 30 million rows. Three copies store 90 million rows, and every bio edit has to land on all three, so the write load per machine doesn't move. Three shards store about 10 million rows each, and each takes about a third of the writes. Copies add read capacity. Shards add write capacity, because each shard owns its third of the rows and nobody else writes them.

Tables can be split too. Moving whole tables to another database, say 30 of 100, came up in Q&A as vertical sharding. It needs a connection pool per database, the same as row sharding.

The routing lives in the API server again. It keeps a separate connection pool to each shard, since a database connection belongs to one server, works out which shard owns the user, and sends the query there. The lecture's version is hash(user_id) mod 3, and the mapping has to stay fixed.

It stays fixed until you add a fourth shard. With mod 4, a user keeps her shard only when both formulas agree, which is true for 3 IDs out of every 12. The other three quarters of users now belong on a different shard, and their rows have to move. Production systems avoid that with consistent hashing,7 or by hashing users into a fixed set of key ranges and moving whole ranges between shards, which is how Vitess does it.8 Either way only a fraction of the data moves.

Which key to shard on has no formula either. You look at how the data is queried and pick the key that keeps most queries on one shard. For Medium's users table, that's the user ID.

The last option is letting replicas take writes too. That is multi-master, and two masters can accept conflicting writes to the same row. How you resolve the conflict depends entirely on the data, which is why the lecture's order is replicas, then shards, and multi-master only when nothing else will do.

Going deeper. What happens when the master dies, and why some clusters look like one database.

In class the answer to "what if the master goes down?" was leader election: a replica is promoted to master, and on a managed cloud the provider does it for you. That holds for Aurora, which promotes a reader on its own.6 Plain RDS is different. With Multi-AZ, it fails over to a synchronous standby that never served reads,9 and an RDS read replica becomes a master only when you promote it yourself.10 Check which one you're running before you rely on it.

Some vendor clusters hide sharding behind one connection string, MongoDB sharded clusters and Vitess for MySQL among them. Not every cluster shards, though. Oracle RAC runs several instances over one shared copy of the data on shared storage.11 Plain MySQL and PostgreSQL are the main cases where you shard in your own code or add a layer such as Vitess or Citus.

Fault tolerance for databases gets its own lecture in week 5.

Say it back: the three moves, in order, and what each one costs

Medium's writes have outgrown one master. Without scrolling up, write the three moves in the order you'd make them, with one cost for each.

Stays in this tab. Nothing is saved or sent.

  1. Bigger machine. Costs money faster than it adds capacity near the top, a restart to resize, and it stops at the largest hardware there is.
  2. Read replicas. Cost staleness: a read can land inside the lag. Your code has to route each read, and every replica takes a little of the master's CPU and network.
  3. Shards. Cost routing in the API server, a connection pool per shard, and data that moves when the shard count changes. Use consistent hashing or fixed ranges so only part of it moves.

If you wrote multi-master as a step, the lecture keeps it outside the ladder: conflicting writes need rules that depend on the data.

Keep hash(user_id) in mind. In Delegation, Kafka picks a partition for each on_publish message with the same move, so all of one writer's posts stay in order. Adding partitions later raises the same mod-N question you just answered.
