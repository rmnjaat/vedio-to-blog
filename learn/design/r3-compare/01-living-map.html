Many at once, not many in total

Scaling is the ability to handle a large number of concurrent requests. A million requests spread over a day is easy. Ten thousand in the same second is the problem.

Most of them only read

Far more people read a blog than write one; far more watch YouTube than upload to it. That skew is what makes read replicas worth having later in this tour.

Your own team causes the biggest spike

A campaign SMS or push notification brings everyone at the same moment. Marketing has to tell engineering before sending, so the infrastructure is ready; otherwise the result is an outage, unhappy users and lost business.

Already on the map from the caching part

The CDN caches static files and some API responses close to readers, so many requests never reach Medium's servers. This tour leaves it alone: everything that gets past it still needs the servers and the database behind it.

The box that makes "more servers" possible

Readers talk to one address. The load balancer forwards each request to one of the API servers behind it, so adding a server adds capacity. For Medium the plan is: a bigger API server first, then a load balancer and several servers.

Here it stays a box. How a load balancer is built is the subject of week 3.

What it buys besides capacity

If one server dies, the others keep answering: the board listed fault tolerance next to linear growth as the gains of horizontal scaling, with complex architecture and network partitioning as the costs.

Two ways to add capacity

Vertical: more CPU, RAM and disk in the same machine. Horizontal: more machines, sharing the traffic. Once one machine can't grow any further, horizontal is the only way on, and it is generally preferred.

Why the bigger box stops

16 GB→32→64→128→256→512 GB→1 TB→2 TB→4 TB→?

Changing the machine type in the AWS console walks up this ladder. It ends somewhere. Why?

wrong turn from class
AWS doesn't give me an option beyond this. A senior engineer gave the lecturer this answer, and it doesn't hold: very large machines exist; supercomputers exist.

The limit is the hardware interface. A phone whose slot supports 256 GB won't recognise a 512 GB card. RAM in its slot, a disk or network card on the motherboard, a USB stick in its port: each moves bytes over a bus, and both sides must speak the same hardware protocol. A bigger part needs different hardware, and the data centre has to have it.

The lecturer learned this in a data centre during his third year of college, where his microprocessor professor showed him the physical limits.

more precisely

The ceiling is real, but cost usually arrives first: the largest instances cost far more per unit of capacity, and one machine is still a single point of failure. (Fact-check note.)

How many machines does 500 req/s need?

5machines = traffic ÷ one machine's capacity
The class's numbers: 100 req/s per machine, 500 req/s needed, 5 machines. Holds only while nothing shared (database, cache) is the bottleneck.

One machine's capacity is its unit economics. The only way to know it is a load test; there is no formula that turns "32 GB" into "5,000 req/s". Amazon plans Prime Day this way: the BI team forecasts orders, engineering divides by one machine's capacity and checks there are enough machines.

lecture

"Linear amplification" (called a standard term in class).

more precisely

The usual name is linear scalability: with no shared bottleneck, N machines handle about N times the load of one.

Autoscaling reacts; a campaign needs you to act first

An autoscaling group only launches instances and adds them behind the load balancer. The rules are yours, for example: average cluster CPU above 60% → add one node. Each new node is horizontal scaling.

  • Small spikes: fine, there is breathing room to scale up.
  • A sudden, large spike: users arrive before new machines are ready. Scale first, then let marketing send the message.
lecture

Autoscaling groups "don't work at scale".

more precisely

Reactive scaling lags, but for spikes you know about AWS offers scheduled scaling (raise capacity at a set time), predictive scaling for recurring daily or weekly patterns, and warm pools of pre-initialised instances. AWS: scheduled · predictive · warm pools

Start with one big box

A young product scales vertically; horizontal scaling makes deployment complex, so it waits until it's needed. API servers are the easy part to scale out because they keep no state: an autoscaling group, a Kubernetes Horizontal Pod Autoscaler and a load balancer do the job. The data underneath is the hard part.

The database doesn't split reads from writes

All writes go to the master; reads should go to replicas. Nothing does that for you in the basic setup: the application decides, query by query, which reads can be slightly stale (replica) and which must be fresh (master).

more precisely

The MySQL and PostgreSQL servers themselves don't split traffic, but drivers and managed services can: Aurora's reader endpoint balances connections across replicas, and PostgreSQL's libpq picks a primary or standby with target_session_attrs. Aurora endpoints · libpq

Two connection strings, two objects

# one per database, made at startup
primary = connect(PRIMARY_URL)
replica = connect(REPLICA_URL)

def create_post(p):            # a write
    primary.execute("INSERT ...", p)

def get_profile(user_id):      # can be a bit stale
    return replica.query("SELECT ...", user_id)

The same for MySQL, Postgres or MongoDB: two connections, and each handler uses the one that fits its query.

Only one connection string in your app?

Then a proxy-like layer is doing this routing for you. Not every team has one, which is why the naive way, the API server deciding itself, comes first. Proxy layers for replicas and shards are covered in weeks 5–6.

A pool per database

asked in class
Doesn't holding pools and heartbeats to several databases load the API server?
You need it anyway: to send each query to the right database, the API server must hold connections to all of them. TCP connections to a database are stateful, so each database gets its own pool, kept by the API server or by a proxy. As API servers are added, the choice of replica still lives in their business logic.

With shards: one more decision

shard = shards[hash(user_id) % 3]   # fixed user → shard
return shard.query("SELECT ...", user_id)

The API server opens a connection to every shard, works out which user the request is for, forwards it, and returns the answer. The mapping from user to shard must not change.

more precisely

Plain hash % N remaps nearly every key when N changes. Consistent hashing, fixed key ranges (as Vitess uses) or a lookup directory move only a fraction. Consistent hashing · Vitess sharding

If it goes down, everything is down

The database is the most critical and most brittle component. Adding API servers doesn't make it stronger; it forwards more queries to it, and to the cache and every other service behind them.

wrong turn
Horizontal scaling means adding API servers, done. The extra requests those servers accept land on stateful parts like the database and cache, which fall over unless they were scaled for it.

Scale bottom-up

Before a big campaign: make sure the database and every service you depend on can take the load, then scale the API servers, then let users in. For a large campaign this is an organisation-wide effort; the teams you depend on should document how they scale.

lecture

Cascading failures, where one component going down takes its dependants with it, are the root cause of most major outages.

more precisely

No dataset shows "most". Google's SRE book treats cascading failure as a major failure class whose most common trigger is overload. Google SRE book, ch. 22

Three ways, in this order

The easy fix is a bigger machine type in the console. It has the same ceiling as any machine, so next come read replicas, and when the master still gets more than it can handle, sharding. Multi-master comes last, "only if you want to make things overtly complicated".

When the master dies

A replica can be promoted to master by leader election. If you are building a cloud database, you implement that; if you use one, the provider handles it, and doing it yourself is a pain most product companies skip.

more precisely

On Amazon RDS, Multi-AZ fails over automatically to a synchronous standby that doesn't serve reads; RDS read replicas are promoted by you, by hand. Aurora promotes a reader automatically, typically in under 60 seconds. RDS Multi-AZ · promoting a replica · Aurora HA

Asked in class

Can a replica take writes too?
Then it isn't a read replica: it's multi-master, and you must resolve write conflicts in a way that depends entirely on the use case. That's why writes are scaled by sharding instead.
What about clustered servers like Oracle RAC, so the database never goes down?
There is no one way to build a system; this is the week-1 view. Database fault tolerance comes in week 5.
wrong turn from class
Clustering is a kind of vertical scaling. A cluster is several machines, so it is horizontal.
lecture

A vendor's database cluster looks like one database but splits the data across storage nodes, i.e. it is sharding underneath.

more precisely

Shared-nothing clusters (MongoDB sharded clusters, Vitess) do shard. Shared-disk clusters like Oracle RAC don't: several instances share one copy of the data. Oracle RAC · Vitess

Reads outnumber writes

90:10 or 99:1read : write, most applications

If almost all database traffic is reads, handling reads well solves most of the scaling problem. That is the whole case for replicas.

more precisely

True for content and social apps; logging, metrics, IoT and chat are often write-heavy. Measure your own ratio first. (Fact-check note.)

A second copy, kept up to date

A master node, a replica node, and asynchronous replication between them. It is close to a built-in database feature that you configure; SRE teams set it up all the time, and "how to set up MySQL replication" is a fine search.

more precisely

MySQL and PostgreSQL replication are asynchronous by default; semi-synchronous and synchronous modes exist. MySQL semisync · PostgreSQL standby

Who starts the copying?

wrong turn
The master pushes its writes to the replicas. The class's correction: the replica calls the master and pulls the changes.
more precisely

The replica opens the connection and asks from its position; after that the primary streams new events down that connection as they happen (MySQL's binlog dump thread, PostgreSQL's walsender). So "the master never pushes" is too strong: the replica starts it, the primary keeps sending. MySQL replication threads · PostgreSQL

Lag value is an example you can change.

A profile can come from a replica. An account balance is a critical read: it goes to the master, or your friend says the money is sent and you don't see it.

more precisely

Lag is measurable: on RDS for MySQL the ReplicaLag metric reports Seconds_Behind_Master; PostgreSQL streaming replication is usually under a second behind if the standby keeps up. MySQL semisynchronous replication holds each commit until at least one replica has received it, at the cost of slower commits. RDS ReplicaLag · PostgreSQL · MySQL semisync

Every replica costs the master a little

Each replica fetching changes uses some of the master's CPU, memory and network. Small per replica, but it adds up, so you don't hang many replicas off one master. As API servers are added, keep adding replicas, because one database can only serve so many requests (and, a student added, so many connections).

~5replicas per master, the class's working limit
more precisely

There's no general ceiling of five. RDS for MySQL allows up to 15 read replicas per source and Aurora up to 15 readers; in PostgreSQL the limit is max_wal_senders. AWS advises giving each replica the same compute and storage as the source. RDS MySQL replicas · Aurora

lecture

Some databases let a replica read the whole binlog file directly (e.g. over SSH); others send changes via SQL or their own protocol, which costs the master.

more precisely

Changes travel over the replication protocol (MySQL binlog dump, PostgreSQL WAL streaming) or as log files shipped through an archive (PostgreSQL file-based log shipping). MySQL · PostgreSQL

Need 15 but the master can feed 5?

A replica can itself be the source for other replicas. The class's example: five on the top layer, each feeding two or three of its own.

more precisely

This is cascading replication (PostgreSQL; RDS supports replicas of replicas for MySQL and MariaDB). Each hop is asynchronous and adds lag. PostgreSQL · RDS replicas

Asked in class

The data is too big to cache. How do you build a read-heavy API?
Read replicas: keep redundant copies and serve reads from them.
more precisely

You rarely need to cache everything: reads usually cluster on a small hot subset, so a partial cache plus replicas (and later shards) is the usual mix. Redis docs

If replicas start hurting the master, is that the time to shard?
Yes. That proposal came from a student and the lecturer agreed three times over.

When writes outgrow one master

Replicas share the reads. Every write still goes to one master, so when the master gets more than it can handle, even after replicas and a bigger machine, you split the data. Sharding is preferred to multi-master for scaling writes because multi-master needs conflict resolution specific to each use case.

Slices, not copies

wrong turn from class
So shards are three identical copies of the database? No: each holds a mutually exclusive subset, for example a third of the rows. Copies are replicas.

Every shard is a master, and each can have its own replicas.

Build the naive version first

Three shards means three database connections from the API server: find the user, forward to that shard, return the result. Production systems often add a proxy layer, but not every database has one, so build the basic way locally before adding that complexity. Sharding proxies are covered in week 5.

Is there a formula for sharding?

No golden formula or magic number. Study the data and how it is accessed, then decide. Databases get their own weeks later.

added from AWS DynamoDB guidance

Pick a key with many distinct, evenly used values, like user ID. Keys with few values (a status code) or time buckets (creation date) make hot shards. AWS DynamoDB

Asked in class: put some tables on another database?

Moving, say, 30 of 100 tables to a second database was named vertical sharding. It needs a connection pool to each database too.

more precisely

Usually called vertical or functional partitioning; AWS describes splitting tables that aren't joined in the same query onto different hosts as one form of sharding. (Fact-check: accurate.)

Do you have to shard it yourself?

lecture

Paid vendors handle sharding for you; with open-source databases that lack native sharding you implement it.

more precisely

The line isn't paid versus open source. MongoDB, Cassandra, Vitess (for MySQL) and Citus (for PostgreSQL) shard natively; stock MySQL and PostgreSQL are the main cases where you shard in the app or add a layer. Vitess
