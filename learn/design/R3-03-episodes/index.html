Engineer view

Scaling means many requests at the same time

  • Scaling is the ability to handle a large number of concurrent requests. Lots of requests over a day is easy; lots in the same moment is the hard part.
  • A young product starts by scaling one box up (vertical). Horizontal scaling complicates deploys, so it comes after a certain stage. It is a sweet spot, not either/or.
  • Avoid premature optimisation: don’t build infrastructure for load you don’t have. Start simple.

The drawing is Medium in an early, example stage: one API server, one Postgres.

Engineer view

Vertical scaling: same machine, more CPU, RAM, disk

16 GB → 32 → 64 → 128 → 256 → 512 GB → 1 TB → 2 TB → 4 TB

  • Change the instance type in the AWS console and the database gets bigger. It is the easy first move for a database, and it has a limit.
  • The board labels it Hulk: make the box bulkier.
  • Board’s trade-off: easy to manage; risk of downtime.
Engineer view

Why the ladder ends

  • Wrong answer (heard from a senior engineer): “AWS just doesn’t offer a bigger option.” Also wrong: “big machines don’t exist.” Supercomputers do.
  • Components talk to the motherboard over buses (RAM slot, disk, network card, a USB stick’s gold lines). Both sides speak a fixed hardware protocol, not HTTP. If the interface doesn’t support a bigger part, you can’t go higher.
  • Same as a phone whose slot reads 256 GB SD cards: a 512 GB card isn’t recognised.
  • The lecturer saw these limits while working in a data center in college (personal anecdote, unverifiable).

LectureVertical scaling can’t be infinite: one level up needs different physical hardware.

PreciselyThe hardware ceiling is real, but you usually hit two limits first: cost (the largest instances cost far more per unit of capacity) and the fact that one box is still a single point of failure.

Fact-check note, no single source.

Engineer view

Horizontal scaling: more machines behind a load balancer

  • Past the point where one box can grow, spread traffic over many. Generally preferred. Board label: Minions.
  • API servers are stateless, so they scale easily: autoscaling groups, Kubernetes HPA, a load balancer. Scaling data is where it gets hard.
  • Medium’s path: scale the API server up first, then put a load balancer in front and scale out.
  • Board trade-offs. Pros: linear scaling, fault tolerance. Cons: complex architecture, network partitions.

Lecture“Linear amplification”: 100 req/s per box, need 500 req/s → 500 / 100 = 5 boxes.

PreciselyThe standard term is linear scalability. It holds only while no shared dependency (DB, cache) is the bottleneck, which is exactly what goes wrong two panels later.

Fact-check note, no single source.

Engineer view

Know one box’s capacity, then scale before the spike

  • Unit economics = requests/s one machine of a given config handles. Only load testing tells you; no formula says a 32 GB box does 5000 req/s.
  • Prime Day: BI forecasts orders; machines needed = N / per-machine capacity. That is predictive scaling.
  • An autoscaling group only launches instances and registers them behind the LB. You write the rules, e.g. avg CPU > 60% → +1 node. Autoscaling EC2 is horizontal scaling.
  • A push/SMS campaign brings users at once. Scale first, then tell marketing to send. Marketing must warn engineering, or it’s an outage: a team effort.
  • Autoscaling is fine for small spikes; it has breathing room there.

LectureAutoscaling groups “fail miserably” at scale on sudden spikes.

PreciselyReactive scaling lags because instances must launch and boot. For a known time, EC2 Auto Scaling has scheduled scaling; predictive scaling covers recurring daily/weekly patterns; warm pools keep pre-initialised instances ready.

AWS: scheduled scaling AWS: predictive scaling AWS: warm pools

Engineer view

The catch: every new API server is another client of the same database

Horizontal scaling ≈ ∞ scale, but there is a catch!! Your stateful components like DB and cache [must] handle those many concurrent requests.the class whiteboard
  • The extra requests API servers accept are forwarded to their dependencies: database, central cache, other services. Unprepared, those go down.
  • The database is the most critical and most brittle part: if it’s down, everything is down.
Engineer view

Cascading failure

  • One component goes down; whatever depends on it goes down next, until users can’t use the platform. Here: database → API servers (timeouts, exhausted pools) → users see 5xx.

LectureCascading failures are the root cause of most major outages (from reading many outage reports).

PreciselyNo dataset shows “most”. The Google SRE book treats cascading failure as a major failure class and names overload as its most common cause.

Google SRE book, ch. 22

Engineer view

Bottom-up: dependencies first, API servers next, users last

  • Before a big campaign, make sure the database and every service you depend on can take the load; scale them explicitly. Then scale API servers. Then let users in.
  • For massive campaigns it is an org-level effort: dependent teams scale their own systems and document how.
  • Three common ways to scale a database, in the order this episode uses them: vertical, read replicas, sharding.

Engineer view

Reads outnumber writes

  • In most applications read:write is about 90:10 or 99:1.
  • More people read a blog than write one; far more people watch YouTube than upload to it.
  • Handle reads well and most of the database scaling problem goes away. That is what read replicas are for.

Lecture90:10 or 99:1 in most apps.

PreciselyA common rule of thumb for content and social apps, but workload-dependent: logging, metrics, IoT and chat are often write-heavy. Measure before relying on it.

Fact-check note, no single source.

From the Q&A
  • Read-heavy API, data too big to cache: serve reads from replicas. Precisely: reads usually concentrate on a small hot set, so a partial cache plus replicas (and later sharding) is typical. Redis: client-side caching
Engineer view

Replication: the replica asks, then the primary streams

  • Setup: one primary (the lecture says master), one or more replicas, asynchronous replication between them. Nearly native: you configure it.
  • SRE teams do this routinely. Search “how to set up MySQL replication” if you haven’t.
  • 0/3A20 in the drawing is an example PostgreSQL WAL position (LSN): “send me everything after here”.

LectureThe master doesn’t push. The replica calls the master and pulls the changes.

PreciselyReplica-initiated, then streamed: the replica opens the connection and requests changes from its position; the primary then streams new events over it as they happen (MySQL binlog dump thread, PostgreSQL walsender).

MySQL 8.4: replication threads PostgreSQL: warm standby

From the Q&A
  • Does each replica load the primary? A little: every replica fetching changes costs it some CPU, memory and network. Small per replica, which is why you don’t run a huge number.
  • Lecture: some databases let a replica read the binlog file directly (e.g. over SSH), others go through SQL or the DB protocol. Precisely: replicas use the replication protocol (MySQL binlog dump, PostgreSQL WAL streaming) or file-based log shipping from an archive; not SSH or SQL. MySQL 8.4: replication threads PostgreSQL: warm standby
Engineer view

Replication lag: replicas are a beat behind

  • Measure it. RDS for MySQL: the ReplicaLag metric (Seconds_Behind_Master). PostgreSQL streaming replication: usually under one second if the standby keeps up. RDS: monitoring replica lag PostgreSQL: warm standby
  • So some reads can’t go to a replica. Bank: a user’s profile can come from a replica; the account balance must come from the primary, or a friend says “sent!” and you see nothing.

The 0.6 s on the clock is an example value.

Engineer view

Routing reads is your job (in the basic setup)

  • Two connection strings, two connection objects. In each handler use the one that fits: read a profile → replica; create a post → primary. Same for MySQL, Postgres, MongoDB.
  • You decide which reads are critical (primary) and which aren’t (replica). That logic lives in the API server’s business code.
  • If your config has only one connection string, a proxy-like layer is doing the routing. Not everyone has one.

LectureThe database doesn’t route reads and writes; the application does the heavy lifting.

PreciselyCore MySQL/PostgreSQL servers don’t split them, but drivers and managed services can: libpq’s target_session_attrs=prefer-standby, Aurora’s reader endpoint, proxies.

libpq: target_session_attrs Aurora endpoints

From the Q&A
  • Don’t pools to several databases load the API server? You need them anyway. Each database needs its own pool because TCP connections are stateful; the API server or a proxy holds them.
Engineer view

How many replicas?

  • Cascading (hierarchical) replication: a replica can be the source for others. Need 15 but the database allows 5? Five under the primary, two or three under each.
  • As API servers scale out, keep adding replicas: one database has a limit on requests (and connections).
  • When replicas start hurting the primary, that is the signal to shard.

LectureAbout five per primary (“five, six, seven is still OK”).

PreciselyNo general ceiling. RDS for MySQL allows up to 15 per source and Aurora up to 15 readers; in PostgreSQL the cap is max_wal_senders. AWS advises giving each replica the same compute and storage as the source.

RDS MySQL read replicas Aurora high availability PostgreSQL: warm standby

Engineer view

Replicas don’t fix writes

  • All writes still land on one primary. If it’s overloaded even after vertical scaling and replicas, you shard.
  • A replica exists to serve reads. Let replicas take writes too and you have multi-master.
  • Multi-master means resolving write conflicts, and conflict resolution is extremely use-case specific. That is why sharding is the usual way to scale writes.
  • Order: read replicas, then sharding, and multi-master only if you want things overtly complicated.
Engineer view

Sharding: disjoint subsets, every shard a primary

  • Split the data into mutually exclusive subsets across nodes (three here). Not three copies: each holds about a third of the rows. Every shard is a primary and may have its own replicas.
  • The API server holds the routing logic, e.g. hash of the user ID. The user→shard mapping must stay fixed.
  • Naive version: three shards = three connections. Work out which user the request is for, forward it to that shard, return the answer.
  • Build the naive one locally first. Production often adds proxy layers, but not every database has one.
  • Pick a key with many distinct, evenly accessed values (user ID). Status codes or creation dates make hot shards. DynamoDB partition-key guidance

LectureShard by hash(user_id).

PreciselyRight idea, but plain hash % N remaps nearly all keys when N changes. Consistent hashing moves about keys/N; Vitess uses fixed keyspace ranges; a lookup directory also works.

Consistent hashing Vitess sharding

From the Q&A
  • Is there a formula for sharding? No. Analyse the data and its access pattern, then decide.
  • Putting different tables on different databases (30 of 100 tables elsewhere) is vertical sharding; it also needs a pool per database.
  • Database clustering is horizontal scaling, not vertical: a cluster is several machines.
  • Lecture: a vendor cluster looks like one database but is sharded inside. Precisely: shared-nothing clusters (MongoDB sharded clusters, Vitess) shard; shared-disk ones like Oracle RAC share one copy of the data. Oracle RAC Vitess sharding
  • Lecture: paid vendors shard for you; open source makes you do it. Precisely: MongoDB, Cassandra, Vitess, Citus shard natively; stock MySQL/PostgreSQL need app-level sharding or an add-on. Vitess sharding MongoDB docs
  • Not this kind of shard: Kinesis “shards” are a stream’s partitions (Kafka’s word), managed for consumers the same way. Covered in the delegation episode.
Engineer view

When a primary dies

  • Building leader election yourself is a pain; most product companies rely on the cloud for it.
  • With plain async replication a crash can lose commits the replica hadn’t received. MySQL semisynchronous replication holds each commit until at least one replica has logged it: slower commits, and it falls back to async if no replica acknowledges in time. MySQL 8.4: semisync
  • Clustered servers (e.g. Oracle RAC) and database fault tolerance in depth: week 5.

LectureLeader election among replicas promotes one to master. Build it if you’re building AWS; if you use AWS, it promotes a standby or replica for you.

PreciselyRDS Multi-AZ fails over automatically to a synchronous standby that can’t serve reads. RDS read replicas are promoted manually. Aurora promotes a reader automatically, typically in under 60 s, often under 30.

RDS Multi-AZ RDS: promoting a replica Aurora high availability
