Scaling the database

The last part ended with Medium’s API tier at five servers: one server handles about 100 requests a second, and the newsletter launch was forecast at 500. The five servers are fine. Each of those requests still asks the same Postgres machine for something, so the database is taking five times last week’s load on the hardware it had last week.

This part is about what you do to that machine, and in what order. There are three moves: a bigger machine, copies that answer reads, and splitting the rows across several machines. Each one stops working for a different reason, and the reason tells you when to make the next move.

Orange is this part, part 3 of 6. Dashed parts come later: the queue in Delegation, the clap counter in Concurrency, live claps in Communication.

The rule for this partas written on the class board

Scale from the bottom up: the database and every other dependency first, then the API servers, then let the users in.

For a big campaign this is planning across teams. Every team you depend on should be able to tell you, before launch day, how its service scales.

A bigger machine comes first, and it runs out at the hardware

The first move needs no code. In the cloud console you change the machine type: 16 GB of RAM becomes 32, then 64, 128, 256, 512 GB, 1 TB, 2 TB, 4 TB. Reads and writes both get room, and the application never notices. For a young product this is the right default. Horizontal setups make every deploy more complex, and the lecture’s advice was to start simple and not pay for premature optimisation.

Medium’s database already runs on the largest size the console lists, 4 TB of RAM. What stops you going one size up?

Pick one before reading on. Nothing is scored or stored.

The lecture’s answer is (b). RAM, disks and network cards sit in slots and move bytes over buses, and both sides of a bus have to speak the same hardware protocol. Past what a board supports, the next size up is physically different hardware, and you get it only if the data centre has it. The analogy from class: a phone whose card slot takes 256 GB won’t read a 512 GB card, however you format it.

The fact-check adds one thing. Well before that ceiling, the largest sizes cost far more per unit of capacity, and one machine is still a single machine to lose. In practice (c) usually pushes you off this move first.

A common wrong turn

The belief
“The provider just doesn’t offer a bigger box.” The lecturer heard this from a senior engineer, so it is not a beginner’s mistake.
Why it’s tempting
The console is where you met the limit, and the list of sizes really does stop.
What’s true
The list stops because the hardware does. Very large machines exist; supercomputers are real. A machine grows only as far as its boards, slots and buses allow.
Say instead
Vertical scaling ends at physical hardware limits, and cost and single-machine risk usually end it sooner.

So from here, more capacity means more machines. Which kind depends on what the traffic is made of.

Most of Medium’s traffic is reads, so answer reads from copies

Read-to-write ratios of 90:10 or 99:1 are common, and blogging sits at the read-heavy end: far more people read a story than write one. A metrics pipeline or a chat app can run the other way, so measure your own ratio before you plan around it.

Five is a habit, not a limitThe lecture’s rule of thumb is about five replicas per master. RDS for MySQL allows 15 per source, and in Postgres the cap is a setting, max_wal_senders. What actually limits you is the write rate each replica has to keep up with.

A read replica setup is one master and one or more replicas, with asynchronous replication between them. Every write goes to the master. Each replica keeps a copy of the data and answers reads. MySQL and Postgres both ship this; you configure it rather than build it.

What the @100 marks in Fig. 1 meanLog positions, for anyone who hasn’t looked inside replication1 min

Every committed change is appended to a log before anything else happens. Postgres calls it the write-ahead log (WAL), MySQL the binary log. A node’s position in that log says how much history it has applied. Real positions are byte offsets; the figure counts changes, so “@100” means “has everything up to change 100”.

A replica at @100 asks for everything after 100 and gets 101 onward. The distance between the master’s position and the replica’s is the lag. On RDS for MySQL you can watch it as the ReplicaLag metric, reported in seconds.

A replica pulls changes from the master, and the pull takes time

Step 3 is the one to remember. The story exists, the author has seen “Published”, and a reader still gets nothing, because that read went to a node that hadn’t caught up. Asynchronous replication let the master answer the author without waiting for any replica, and step 3 is what that costs.

The board draws this arrow the other wayOn the class whiteboard the replication arrow runs master → replica. Here the replica’s request points at the master, because the replica starts the conversation.

About the direction: the lecture’s point is that the replica pulls and the master doesn’t push. More precisely, the replica opens the connection and names its position, and from then on the master streams new log records down that connection as they are written. That is MySQL’s binlog dump thread and Postgres’s WAL sender. The replica starts it and chooses where it starts. If a gap like step 3 is unacceptable for some data, MySQL’s semi-synchronous mode makes each commit wait until one replica has received it, at the cost of a round trip per commit.

Your code decides which reads are allowed to be stale

Neither MySQL nor Postgres splits reads from writes by itself. In the basic setup the API server holds two connections and each handler picks one:

One connection string means something else is routingA proxy, or the driver. Postgres’s libpq can choose a primary or a standby from a host list with target_session_attrs, and Aurora gives you a reader endpoint that spreads connections over replicas. Which reads may be stale is still your call.
master  = connect(MASTER_URL)
replica = connect(REPLICA_URL)

# a write
def publish(story):
    return master.run(INSERT, story)

# a second out of date is fine
def profile(user_id):
    return replica.run(PROFILE, user_id)

# the author, right after Publish
def my_story(story_id):
    return master.run(STORY, story_id)

Pseudocode for the API server. Works the same with MySQL, Postgres or MongoDB.

A profile page can be a second old. The author’s own story right after Publish can’t, because that is step 3 of Fig. 1 happening to the one person who knows the story exists. The class example was a bank: a friend says the money has gone, you open the app, and a replica shows the old balance. Reads like that go to the master.

Replicas cost the master something. Each one holds a replication connection served by its own sender process on the master, so each adds a little CPU, memory and network load. Past roughly five, the lecture suggests a tree: five replicas pull from the master and each feeds two or three more, 15 in all, while the master serves only 5 pulls. Postgres calls this cascading replication, and every extra hop adds its own lag.

Two things replicas never fix. Every write still lands on one master. And once the replicas’ pulls start to hurt that master, this move is used up. A student in class proposed that as the signal to shard, and the lecturer agreed.

When the master dies, a read replica doesn’t take over by itselfFailover and read scaling are separate features on AWS1 min

Asked in class: what happens when the master goes down? The answer given was that a replica gets promoted through leader election, that a cloud provider does this for you, and that writing leader election yourself is rarely worth it for a product company. The last part holds.

The AWS details are narrower. RDS Multi-AZ fails over automatically to a synchronous standby, and that standby can’t serve reads. RDS read replicas are promoted by hand. Aurora does promote a reader automatically, usually in under a minute. Check which of the two you are paying for before the night you need it.

When writes outgrow one master, split the rows across several

Sharding splits the data into mutually exclusive subsets and gives each subset its own machine. Every shard is the master for its rows and can have replicas of its own. Someone in class asked whether three shards meant three copies of the database. They don’t: each holds about a third of the rows, and no row lives on two shards.

For Medium the natural key is the user. The API server hashes the user ID to pick a shard, keeps one connection pool per shard (a pool’s connections belong to one database), and forwards the query there. The mapping from user to shard has to stay fixed, because a user’s rows must be found where they were written.

That last requirement is where the simplest routing, hash(user_id) % 3, gets expensive. Change the 3 and most users map to a different shard, so their rows have to move. Consistent hashing, or a fixed set of virtual buckets assigned to shards the way Vitess does it, keeps a reshard down to a fraction of the rows. Lines 12 and 13 of the worked numbers below put a figure on the difference.

A cluster isn’t always shardsOracle RAC came up in class. RAC is shared-disk: several instances over one copy of the data. Shared-nothing systems such as Vitess are the ones that split rows.

Whether you write this routing yourself depends on the database. Plain MySQL and Postgres leave it to you or to an add-on such as Vitess or Citus; databases built to be distributed, open source or paid, do it internally. The lecture’s advice holds either way: build the naive version once, so you know what a proxy is doing for you. There is no formula for the shard key. Pick one with many distinct, evenly used values, like a user ID; a key with few values, or a date, piles load onto one shard.

Say it back: what each move scales, and what ends it

Without scrolling up, in two or three sentences: what does each of the three moves scale, and what tells you it is time for the next one?

Kept on this device only, as a draft.
  1. A bigger machine scales reads and writes with no code change. You leave it when the next size costs too much, is one machine you can’t afford to lose, or doesn’t exist because the hardware stops.
  2. Read replicas scale reads. Writes still go to one master, replicas pull (the replica starts the connection), and some reads come back stale, so your code chooses master or replica per query. You leave this move when writes outgrow the master or the replicas’ pulls start to hurt it.
  3. Shards scale writes by giving each machine an exclusive slice of rows, routed by a key such as the user ID. Pick routing that survives a change in shard count.

If you wrote “replicas copy the data so they scale writes too”, read the second rung of Fig. 2 again.

Comes back in Concurrencypart 5

Sharding spreads Medium’s writes over several masters. It does nothing for two claps on the same post at the same instant: that post’s row lives on one shard, and both increments race on that one machine. Concurrency starts from that race.
