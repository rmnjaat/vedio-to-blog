Scaling the database

When the one box every API server talks to can't get any bigger.

Suppose it's 9:00 on a Monday and Medium's marketing team sends a push notification to every reader. The night before, engineering widened the API fleet from 8 servers to 40, so the API tier has room to spare. All 40 servers send their queries to one database, and that database already runs on a 4 TB machine, the top rung of the ladder from earlier in this lecture.

The board said it first: bottom up

Before a campaign, scale the database and every service you call, then the API fleet, and only then let the users in. Teams you depend on should write down how they scale.

The 40 servers accept five times the traffic the 8 did, and every request that needs data ends up at that one database. If it falls over, every API server waiting on it starts failing too. The Google SRE book treats this cascade as its own class of outage, and names overload as its most common trigger (Addressing Cascading Failures).

So how do you give a single database more room once it can't be made any bigger? The class went through three moves, always in this order: a bigger machine, then copies that take the reads (read replicas), then splits that take the writes (sharding).

A bigger machine buys a few doublings

The first move is the cheapest: choose a larger instance type. In class the ladder went 16 GB, 32, 64, and on up to 4 TB of RAM, each rung a few clicks in the AWS console. Then the list ends.

The class was asked why it ends. One answer the teacher had heard, from a senior engineer, was that AWS doesn't offer a bigger option, which describes the console rather than the cause. RAM, disks and network cards talk to the motherboard over buses, and both sides have to support the size. A phone whose card slot takes 256 GB won't read a 512 GB card for the same reason. Going higher means different hardware, and the data centre either has it or doesn't.

In practice most teams step off the ladder before they reach the top. The largest instances cost more per unit of capacity than the middle ones, and a single machine, however large, can still fail.

Replicas take the reads

Most of what Medium's database does is answer reads: for every person writing a story, many more open it. The lecture put the read-to-write ratio for most applications at 90:10, sometimes 99:1. That holds for content and social products. Logging, metrics and chat can run the other way, so measure your own split before you build on it.

A read replica is a second database that keeps a copy of the master's data and answers reads. Writes still go only to the master. MySQL, PostgreSQL and MongoDB all ship replication as something you configure, not something you write.

Foundations — synchronous, asynchronous, and the setting in between

With asynchronous replication, the master commits a write and replies at once; replicas apply it a little later. Writes stay fast, and a replica can be behind. That is the default the lecture describes.

With synchronous replication, the commit waits until a replica has the write too. Nothing is lost if the master dies, but every write pays a network round trip.

MySQL's semi-synchronous mode sits between them: a commit waits until at least one replica confirms it has received the change, and falls back to asynchronous if replicas stop answering in time (MySQL semisynchronous replication).

One pool per database

A database connection is a stateful TCP connection, so the API server keeps a separate pool for the master and for each replica. A proxy can hold those pools instead; that is usually what a single connection string is hiding.

The direction of replication is the part that usually gets told backwards. The master doesn't seek out its replicas. Each replica opens a connection to the master and asks for every change after the last one it has; the master then streams new changes down that connection as they are written. MySQL calls the sending side the binlog dump thread (MySQL replication threads); PostgreSQL says the standby connects and the primary streams WAL records to it (PostgreSQL streaming replication). The replica starts the conversation, which is why the request arrow in Fig. 1 points from the replica to the master.

The database won't decide which query goes where. In the plain setup the API server holds two connections, one to the master and one to the replica, and each handler picks: opening a profile uses the replica, publishing a story uses the master. Some layers make the choice for you, such as Aurora's reader endpoint or PostgreSQL's libpq with target_session_attrs. Build the two-connection version once and you'll know what they are doing for you.

  2. 2 / 4The redirect reads from a replica. Showing a story is a read, so the handler uses the replica connection. The replica doesn't have #4182 yet and returns no row, so the writer gets a 404 for the story they published a moment ago.
  3. 3 / 4Why the replica was behind. The replica asked the master for new changes long before the publish, and #4182 travels down that same connection. Here it arrives after the read. That gap is replication lag. PostgreSQL's docs put it under a second when the standby keeps up with the master's write rate; when it doesn't, the gap grows.
  4. 4 / 4The fix is a routing rule. Reads where someone must see their own write go to the master: the writer's own story just after publishing, or an account balance after a transfer (the lecture's bank example). A profile or another reader's feed can go to a replica and be a moment old.

You can measure the gap instead of guessing it. On RDS for MySQL the ReplicaLag metric reports how many seconds a replica is behind (AWS: monitoring read replication).

Fifteen replicas means a tree, or a bigger cap

Every replica that streams from the master costs it some CPU, memory and network. The class's figure was about five per master, with a tree beyond that: five replicas each feeding three more gives fifteen.

There is no general limit of five. RDS for MySQL allows 15 read replicas per source and Aurora 15 per cluster (RDS, Aurora). The real number depends on the write rate and the instance size.

A student asked the obvious next question in class: if replicas pull from the master, does adding more of them slow the master down? A little each time, was the answer, and that's why nobody hangs fifty replicas off one machine. The same student then said that once replicas start to hurt the master, it's time to shard, and the teacher agreed.

Sharding splits the rows

Replicas never take writes. Every publish, clap and follow still lands on the one master, and when that machine is at its limit even with the reads moved off, the data itself has to be divided. Before reading how, make a call on this:

Medium splits its users, and their stories, across three database machines by user ID. A writer whose stories live on the second machine publishes a new one. How many of the three machines have to accept that write?

One. Each machine holds a different third of the users, and every row has exactly one home. The API server works out which machine owns the writer and sends the write only there. Each of those machines is a master for its third, and it can have replicas of its own; those are where any backup copies come from.

That is sharding: split the data into mutually exclusive subsets and put each one on its own machine, a shard. In the version from class, the API server holds the routing. It keeps a connection to every shard, works out which user a request belongs to, sends it to that shard and passes the answer back. Medium's natural key is the user ID, so a writer's stories sit on the same shard as the writer.

A key with many values

User ID works because there are millions of them with broadly similar traffic. A key with a handful of values, or one that groups rows by date, piles the load onto one shard (DynamoDB's guidance says the same for partitions).

The routing rule in class was a hash of the user ID. Written as hash(user_id) % 3, it works until a fourth machine arrives: changing the 3 to a 4 sends nearly every user to a different shard, and their rows have to move with them. Shard routers avoid plain modulo for that reason. They use consistent hashing, a fixed set of key ranges that get reassigned as machines are added (the way Vitess does it), or a lookup table from user to shard.

A wrong turn “So three shards means three copies of the database?”

This came up in class right after the board drawing, and it's an easy reading of it. The board drew three cylinders for replicas and three for shards, and both moves add machines.

Follow one write for user 5. With three copies, all three machines must apply it, so each one carries as many writes as the single master did, and storage triples. With three shards, the write goes to the one machine that owns user 5, and each machine carries about a third of the writes.

Replicas copy everything and divide the reads. Shards divide the rows, and the writes go with them.

Why not let replicas accept writes as well? Then two machines can change the same row at once, and something has to decide which change wins. That's a multi-master setup. The class's advice was to try it last: resolving those conflicts depends on what the product needs, and no general rule gets it right. Sharding scales writes without raising the question, because a row only ever has one home.

Sizing it on paper

The class's capacity rule: load-test one machine to learn what it can handle, then divide. If one machine serves 100 requests a second and you need 500, you need 5. The usual name for this is linear scalability, and it holds only while nothing shared becomes the bottleneck. Here it is applied to Medium's database. Work both out, then compare

Reads: 64,800 ÷ 5,000 = 12.96, so 13, and 14 with a spare. That's under RDS's cap of 15 per source but close to it, and each replica costs the master a little.

Writes: 7,200 against a ceiling of 6,000 is 120%, and no number of replicas changes that. This is the point to shard. Three shards by user ID put about 2,400 writes a second on each, provided activity is spread evenly across users.

Going deeper — if the master dies, what takes over?

A question in class about master failure got this answer: a replica can be elected as the new master, and on AWS the provider does it for you. On Amazon RDS the details matter. Automatic failover goes to a Multi-AZ standby, which is synchronous and can't serve reads (RDS Multi-AZ). Read replicas are not promoted automatically; promoting one is a manual action (promoting a read replica). Aurora is the exception: it promotes one of its readers on its own, usually in under 60 seconds (Aurora high availability).

So a standby is for surviving failure and a replica is for spreading reads, and on RDS they are different machines. Writing your own leader election is rare; most product teams use what the provider gives them.

A related question was whether a vendor database cluster is just sharding underneath. Some are: MongoDB sharded clusters and Vitess split data across nodes. Oracle RAC, the example raised in class, is shared-disk: several instances work on one copy of the data on shared storage (Oracle RAC).

1. A bigger machine, until the price or the hardware stops you. 2. Read replicas, because most traffic is reads; the application routes each query, and reads that must see a fresh write stay on the master. 3. Shards by user ID, once writes outgrow one master, since replicas never take writes. Multi-master comes last, if at all, because of write conflicts.

Hold on to one fact for later. After sharding, every write for a given user still lands on exactly one machine. In part 5, two readers clap for the same story at the same instant while its count reads 100. That one machine has to finish on 102, not 101.
