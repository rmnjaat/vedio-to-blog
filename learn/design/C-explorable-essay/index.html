§2.4

Scaling the database

Medium can add API servers by the dozen. Every one of them talks to the same database.

At the end of 2.3, Medium had a load balancer in front of a fleet of API servers. Adding capacity there is arithmetic: if one server handles 100 requests a second and launch day needs 500, you run five. The arithmetic hides a catch. Each extra request an API server accepts is a request it forwards to something behind it, and on Medium almost all of them end at one place, the database.

Why it’s brittleIf the database goes down, everything is down. No API server can answer a reader without it.

The database is the most critical part of the system and the most brittle. When it falls over, the API servers that depend on it fail too, and the failure climbs the stack until no reader can load a page. Cascading failures of this kind sit behind most large outages in distributed systems. That fixes the order of work.

The rule for this chapter

Scale bottom up: the database first, then the API servers.

Then let the users in. For a large campaign, every team that owns a dependency scales it before marketing sends the push notification. Scaling is a team game.

API servers are the easy half, because they hold no state. Data is where scaling gets interesting. There are three moves, and teams usually make them in this order:

#First, a bigger machine

The cheapest move needs no code. Open the cloud console, change the database’s machine type, and 16 GB of RAM becomes 32, then 64, 128, 256, 512, 1 TB, 2, 4. This is vertical scaling, and for a young product it is the right first step, because the alternatives make deployment harder. Optimise the infrastructure before you need to and you pay for complexity with nothing to show for it.

The wrong answer“The provider doesn’t offer a bigger size” describes the symptom. Bigger computers exist; supercomputers prove it.

It stops somewhere, and the reason is physical. Every part of a machine talks to the others over a bus with a fixed hardware protocol: RAM in its slot, disks and network cards on the motherboard. A phone whose card slot supports 256 GB won’t read a 512 GB card. Going one size up eventually means different hardware, and if the data center doesn’t have it, no dropdown will sell it to you. Software is an abstraction; underneath, it runs on something with slots.

#Read replicas, because most traffic is reads

Most applications read far more than they write. Many more people read a blog than write one; many more watch a video than upload it. Medium is the textbook case.

90:10 to 99:1 Typical ratio of reads to writes in most applications.

So if reads stop reaching the database you’re scaling, most of the problem goes away. A read replica is a second database node that keeps a copy of the master’s data. You configure replication between the two. It is close to a built-in feature in MySQL, PostgreSQL and MongoDB, and SRE teams set it up routinely. Every write still goes to the master. The replica follows behind, applies the same changes, and serves reads.

NamingThe lecture says master; PostgreSQL’s documentation says primary and standby. Same roles.

The usual picture has the master pushing each write out to its replicas. It works the other way round: the replica connects to the master and pulls the changes. PostgreSQL’s documentation describes exactly this. The standby opens the connection (you see a walreceiver on the standby and a matching walsender on the primary), and streaming replication is asynchronous by default, in which case there is a small delay between committing a transaction in the primary and the changes becoming visible in the standby, typically under one second.1

  1. STEP 1 / 5A writer publishes a post. The API server sends the INSERT on its master connection, and the master commits the post.
  2. STEP 2 / 5The master tells no one. The replica, which holds an open connection to the master, pulls the change across. Until it lands, the two nodes disagree.
  3. STEP 3 / 5A reader opens the post a moment later. The API server sends this read to the replica, which hasn’t applied the change, so the reader gets “not found”. That is a stale read, and replication lag caused it.
  4. STEP 4 / 5The replica applies the change. The same read, repeated now, finds the post. Nothing was lost; the reader was early.
  5. STEP 5 / 5Some reads can’t afford to be early. A bank balance read from a lagging replica says your friend’s transfer hasn’t arrived when it has. Reads like that go on the master connection, and the API server is what decides.

#Routing is your job

The database won’t split reads from writes for you. In the plainest version, the API server opens two connections and each handler picks the one its query needs: reading a profile can tolerate lag, publishing a post cannot go anywhere but the master.

One pool per databaseA connection to a database is a stateful TCP connection, so each database needs its own pool. One master and one replica means two pools on every API server.

Sketch, any driver. Same idea in MySQL, PostgreSQL or MongoDB.

master  = db.connect(MASTER_URL)    # every write, and critical reads
replica = db.connect(REPLICA_URL)   # reads that can be a moment old

def get_profile(user_id):
    return replica.query("SELECT ... FROM users WHERE id = %s", user_id)

def publish_post(author_id, post):
    return master.query("INSERT INTO posts ...", author_id, post)

Proxy layers exist that hide this behind a single connection string and route for you; week 5 covers them. Not every stack has one, so learn the plain version first. You decide, per use case, which reads are allowed to be stale.

If the master diesA replica can be promoted to master. On a managed cloud database the provider does this for you; writing your own leader election is rarely worth it for a product team.
Pause and think

Medium keeps adding replicas, five, ten, twenty, all following one master. Pick what gives out first, then check.

What gives out first?

Each replica fetching changes eats a little of the master’s CPU, memory and network bandwidth, and the master still takes every write. Teams typically stop at about five replicas per master. If you need fifteen, replicas can feed other replicas: five at the top, each serving two or three of its own.

When replicas start to hurt the master, or writes alone are too much for it, it’s time to shard.

#Sharding, when the master is still too busy

Replicas copy everything, so every write still lands on one master. When that master is overloaded even after vertical scaling and replicas, split the data itself. Sharding divides the rows into mutually exclusive subsets and puts each subset on its own node. With three shards, each holds about a third of the rows; none is a copy of another. Every shard is a master, and each can have replicas of its own.

Vertical shardingPutting whole tables on different databases, users in one and posts in another, is also sharding. It needs a connection pool per database too.

Something has to know which shard holds which row. In the plain version that is the API server again: it holds a connection to every shard, hashes the user ID on each request to pick one, forwards the query, and returns the answer. For Medium, shard by user ID.

# three shards, three connections
shards = [db.connect(url) for url in SHARD_URLS]

def shard_for(user_id):
    return shards[hash(user_id) % len(shards)]

The one hard rule is that the mapping from user to shard must stay fixed. If it moves, the router looks for a user’s rows on a shard that doesn’t have them. Look at the last line above: add a fourth shard and len(shards) changes, and with it the shard of most users. Keep that in mind; it is why resharding is hard.

Why not let replicas take writes?That is multi-master. Every write conflict then needs a resolution rule specific to your data, which is why sharding is the usual way to scale writes.

How should you pick the key? There’s no formula and no magic number. Look at the data and how it is read, then decide. Some databases make the decision less painful: a vendor’s database “cluster” looks like one database to your application and shards internally, which is also why clustering counts as horizontal scaling, not vertical. With open-source databases that lack native sharding, the routing is yours to write.

#Choosing between them

The lecture gives the order: a bigger machine, then replicas, then shards. Multi-master only if you want to make things overtly complicated.

Aspect Vertical Read replicas Sharding
You change The machine type, 16 GB up to a few TB Add nodes that copy the master asynchronously Split rows into exclusive subsets, one master each
It relieves Everything, a little Reads, which are 90–99% of traffic Writes and data size, not just reads
Code changes None Two connections; each query picks one Routing on a key, a pool per shard
Breaks when The hardware has no bigger slot Lag serves a stale read; about 5 replicas per master The key mapping changes; no formula for the key
Reach for it First, while the product is young Second, for read-heavy load like Medium’s When the master is still overloaded, or replicas hurt it

#Check yourself

Answer from memory before you open each one.

  1. Medium’s traffic is roughly 99 reads for every write. Which of the three moves helps with the writes, and why don’t replicas?Show answer

    Sharding, and vertical scaling until it hits the hardware. Replicas don’t, because every write still goes to the one master, and each replica has to apply all of them anyway.

  2. A reader opens a post a moment after it was published and gets “not found”. What happened, and where should the read have gone if it mattered?Show answer

    Replication lag. Replication is asynchronous, so the replica had not applied the write yet. A critical read goes on the master connection; the API server decides which reads those are.

  3. Why must the user-to-shard mapping stay fixed?Show answer

    The API server finds a user’s rows by computing the shard from the user ID. If the mapping changes, it queries a shard that doesn’t hold those rows.
