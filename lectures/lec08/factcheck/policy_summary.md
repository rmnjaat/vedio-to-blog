## Notes (sourced)

- **L-0038** imprecise/medium: A layer that cannot scale horizontally is a bottleneck; if it also has no standby or failover, it is a single point of failure. (https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Concepts.MultiAZSingleStandby.html)
- **L-0084** simplified/medium: TCP itself never times out an idle connection, but load balancers, NATs and firewalls on the path do, so long-lived connections need keep-alives or periodic data. (https://www.rfc-editor.org/rfc/rfc9293#section-3.8.4, https://docs.aws.amazon.com/elasticloadbalancing/latest/application/edit-load-balancer-attributes.html)
- **L-0091** imprecise/medium: Data warehouses face the same mixed short/long query problem and solve it with workload management (queues, slots, fair scheduling) rather than plain least-connections. (https://docs.aws.amazon.com/redshift/latest/dg/cm-c-implementing-workload-management.html, https://docs.cloud.google.com/bigquery/docs/slots)
- **L-0227** wrong/medium: Redis Pub/Sub broadcasts changes in real time but at-most-once; pair it with a re-pull of the full config on (re)connect, or use a durable stream, so every LB server converges. (https://redis.io/docs/latest/develop/pubsub/)
- **L-0279** simplified/medium: You hold the Redlock only if you locked a majority (N/2+1) of instances and the time spent acquiring is less than the TTL; your safe window is the TTL minus that time. (https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/, https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html)
- **L-0282** simplified/medium: Redlock survives single node failures, but process pauses, clock jumps and fast restarts can still give two holders; correctness-critical uses need fencing tokens. (https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/, https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html)
- **L-0303** imprecise/medium: RabbitMQ, SQS and Kafka keep two consumers from receiving a message at the same time, but they are at-least-once: a message can be redelivered (even to another consumer), so processing must be idempotent. (https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/standard-queues-at-least-once-delivery.html, https://docs.aws.amazon.com/AWSSimpleQueueService/latest/APIReference/API_ReceiveMessage.html, https://kafka.apache.org/43/design/design/, https://www.rabbitmq.com/docs/confirms)
- **L-0305** imprecise/medium: A MongoDB multi-shard transaction takes document locks on each shard it touches; a conflicting transaction waits briefly (5 ms by default) and then aborts and retries. (https://www.mongodb.com/docs/manual/core/transactions-production-consideration/)
- **L-0306** imprecise/medium: MongoDB tracks document locks on each shard; a transaction that can't get a lock within 5 ms (default) aborts and must be retried, while plain writes wait for the transaction to finish. (https://www.mongodb.com/docs/manual/core/transactions-production-consideration/)
- **L-0316** imprecise/medium: In Redlock the winner holds only the majority it got in one pass; losers release everything and retry after a random delay. (https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)
- **L-0318** imprecise/medium: The risk window is the lock's TTL, not a few seconds; Redis docs close it by keeping crashed nodes out for longer than the max TTL. (https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)
- **L-0328** imprecise/medium: ZooKeeper solves the same problem with ephemeral sequential nodes, watches (no polling) and consensus replication, which gives stronger safety than a Redis TTL lock. (https://zookeeper.apache.org/doc/current/recipes.html, https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html)
- **L-0369** imprecise/medium: Prometheus scales by running more independent servers (sharding/federation) and by remote-writing to a clustered long-term store. (https://prometheus.io/docs/prometheus/latest/storage/)
- **L-0370** wrong/medium: Prometheus has its own local TSDB; external stores such as InfluxDB or TimescaleDB can be added through remote write/read. (https://prometheus.io/docs/prometheus/latest/storage/)

## Inline clarifications

- **L-0035** simplified/low: Remote machines talking to each other are technically a distributed system, but not a good one unless every layer scales and tolerates failure.
- **L-0036** simplified/low: Distributed systems are built to scale horizontally and to tolerate failures of individual machines.
- **L-0039** simplified/low: Stated as absolute, but the teacher relaxes it (L-0044: a non-scalable database is fine if it handles the load) and later uses a single active node with a standby. The real requirement for every layer is enough capacity for peak load and no unprotected single point of failure; scaling out is one way to get that, a standby is another.
- **L-0041** simplified/low: Knowing per-server capacity is right. Two cautions: (1) linear growth is an ideal; shared dependencies (database, locks, coordination) make extra servers add less and less; (2) request count is a weak capacity unit when request costs vary. Google SRE recommends measuring capacity in resources (CPU) rather than queries per second.
- **L-0061** simplified/low: RAM size is not core count; utilization only halves if the bigger machine has proportionally more of the resource that actually bottlenecks (CPU, memory, I/O). The point (equal shares underuse a bigger machine) stands.
- **L-0064** imprecise/low: Check the load balancer's documented algorithm options; managed LBs expose a fixed set (e.g. ALB: round robin, least outstanding requests, weighted random) and some (NLB) are not configurable.
- **L-0073** imprecise/low: An in-flight request (not merely an open connection) means the server is busy; with keep-alive, LBs count active connections or outstanding requests.
- **L-0079** simplified/low: Many LBs only see connections, but some use backend-reported load: gRPC's weighted round robin computes weights from backend-reported utilization (per-call or out-of-band), and ALB's Automatic Target Weights shifts traffic based on error rates.
- **L-0080** simplified/low: Querying CPU on every request is impractical, but load reports can be collected asynchronously and used to adjust weights periodically, as gRPC's weighted round robin policy does; the per-request decision stays local and fast.
- **L-0085** imprecise/low: HTTP/1.0 closed the connection after each response unless keep-alive was used; HTTP/1.1 keeps connections open by default.
- **L-0086** simplified/low: gRPC does use long-lived HTTP/2 connections that the protocol does not time out (server MAX_CONNECTION_IDLE and MAX_CONNECTION_AGE default to infinite). But proxies and load balancers can treat them as idle and drop them, which is why gRPC has HTTP/2 PING keepalives. Servers can also be configured to close connections or send GOAWAY.
- **L-0089** simplified/low: Random tie-breaking is fine; for reference, nginx breaks ties among least-connection servers with weighted round-robin.
- **L-0093** imprecise/low: Two corrections. (1) Some common servers do give tooling: Go's net/http cancels the request Context 'when the client's connection closes', so a handler can stop work. (2) The socket only reports a disconnect when a FIN or RST arrives. A peer that vanished (power loss, cable cut, dropped NAT entry) goes unnoticed until you write or keep-alive probes fail, because TCP 'does not inherently include a liveness detection capability' (RFC 9293).
- **L-0102** simplified/low: This describes a layer-4 TCP proxy. Many load balancers are layer-7 HTTP proxies (e.g. AWS ALB evaluates HTTP listener rules), and NLB/Maglev-style LBs forward packets per flow instead of running a normal TCP server.
- **L-0110** simplified/low: True for HTTP/1.1 and HTTP/2; HTTP/3 runs over QUIC (UDP).
- **L-0112** simplified/low: True for proxy-style (connection-terminating) load balancers. Packet-level LBs such as Google's Maglev forward the client's packets to a backend using connection tracking and consistent hashing, without opening a second TCP connection.
- **L-0117** imprecise/low: A TCP proxy copies the byte stream, not packets: the kernel reassembles bytes on one socket and re-segments them into new packets on the other (io.Copy works reader-to-writer on bytes).
- **L-0118** imprecise/low: A TCP proxy is protocol-agnostic only for protocols carried over TCP (HTTP/1.1-2, WebSocket, RTMP). ICMP is part of the IP layer, not carried over TCP, so it cannot pass through this proxy (nor can UDP-based protocols).
- **L-0122** simplified/low: The 10,000 limit is illustrative. Real limits are file descriptors, memory and ephemeral ports: connections from one LB IP to one backend ip:port are bounded by the local port range (Linux default 32768-60999, about 28k).
- **L-0138** imprecise/low: In Go a closed connection does not panic: io.Copy returns (nil at EOF, or an error such as a reset), and that return is where you update counters.
- **L-0151** simplified/low: A same-datacenter round trip is about 0.5 ms (2012-era reference numbers); 3-5 ms is plausible for a full DB query. The conclusion (don't hit the DB per request) holds.
- **L-0158** simplified/low: TCP health checks are a real, common option (AWS NLB's default health check protocol is TCP), but they prove only that the port accepts connections, not that the application can serve requests; HTTP checks on a health path are stronger.
- **L-0164** simplified/low: Managed LBs mark failed targets unhealthy rather than deleting them, keep checking so they can return, and fail open (route to all) if every target is unhealthy.
- **L-0178** simplified/low: Redis Pub/Sub is at-most-once: a subscriber that is disconnected misses messages for good, so LB servers must re-pull the full config on reconnect (or use Redis Streams).
- **L-0197** simplified/low: A single Prometheus server is autonomous and scales vertically well, but its local storage is not clustered; scaling past one server means sharding/federation or remote storage.
- **L-0200** imprecise/low: Each VM runs an exporter; Prometheus scrapes (pulls) them, and the orchestrator queries Prometheus.
- **L-0208** imprecise/low: An IP address is not inherently tied to one machine: a virtual IP can move between machines (VRRP failover), and with ECMP/anycast many machines serve the same IP (Google's Maglev). DNS with multiple IPs is one valid approach, not the only one.
- **L-0215** simplified/low: DNS 'load balancing' is cruder than LB algorithms: Route 53 supports weighted records, while plain round-robin DNS (e.g. CoreDNS loadbalance) just shuffles the order of all returned records.
- **L-0216** simplified/low: DNS often returns several IPs and the client chooses which to use (AWS: the DNS servers 'return one or more IP addresses'; 'The client determines which IP address to use').
- **L-0220** simplified/low: Clients and resolvers cache answers for the record's TTL (ELB uses 60 s precisely so IPs can be remapped quickly); not every client stack caches, and caching is bounded by the TTL.
- **L-0231** simplified/low: In practice clients usually try the other addresses from the same DNS answer (Happy Eyeballs) before re-resolving; a fresh query can still return the cached answer from an intermediate resolver until the TTL ends.
- **L-0234** imprecise/low: DNS does not bottom out in one server with a standby: resolvers list several nameservers, and the root zone is served by 13 identities with about 2,047 anycast instances.
- **L-0235** simplified/low: Hop counts vary by path, and the top of the DNS hierarchy is itself widely replicated (13 root identities, about 2,047 instances), not a single node with a standby.
- **L-0236** imprecise/low: End users resolve through a public recursive resolver, which asks the authoritative DNS (e.g. Route 53) for the domain.
- **L-0243** simplified/low: Threads (and database backends, whether threads or processes) coordinate through shared memory: mutexes, semaphores, atomic instructions.
- **L-0245** imprecise/low: apt/dpkg serialise through an fcntl lock on /var/lib/dpkg/lock that the kernel releases automatically when the holding process exits.
- **L-0246** simplified/low: Use the nearest thing the parties share: threads share memory; processes can share memory or a kernel-held file lock; machines share only the network.
- **L-0258** imprecise/low: Redis offers key-value access, atomic commands and TTL, so the common remote lock is a single-instance Redis lock (SET key value NX EX ttl); Redlock is the multi-instance version of it.
- **L-0264** simplified/low: Acquire with SET q <random token> NX EX 300 in a loop; the token must be unique per lock request.
- **L-0265** simplified/low: Mixes two commands. SETNX returns 1/0 but cannot set an expiry. SET with NX and EX returns OK when it sets the key and nil when it doesn't (redis-py: True/None). The never-overwrite behaviour is correct.
- **L-0267** simplified/low: A tight while-true loop of SET NX hammers Redis with requests. Redis docs say to 'retry after some time' and, for Redlock, 'try again after a random delay' so contending clients desynchronise.
- **L-0277** simplified/low: Right for Redlock: plain Redis replication with failover is unsafe because 'Redis replication is asynchronous' (a promoted replica may not have the lock key). But 'running it in a cluster' is how other lock services get fault tolerance: ZooKeeper, etcd and Chubby replicate state with a consensus protocol. The distinction is async replication versus consensus, not cluster versus no cluster.
- **L-0280** simplified/low: Redis docs go one step further: a failed client should 'try to unlock all the instances (even the instances it believed it was not able to lock)'. A SET may have succeeded even though its reply was lost. This is safe because the release script only deletes the key if it holds this client's token.
- **L-0281** simplified/low: Fair for Redlock (N round trips per acquire). Kleppmann's nuance: if the lock is only for efficiency, a single Redis instance is enough. If it is for correctness, Redlock's timing assumptions are a problem, and a consensus system (ZooKeeper) plus fencing tokens is recommended.
- **L-0283** simplified/low: The example just shown (Redlock across five Redis nodes) was made distributed for fault tolerance, not for horizontal scale; the teacher says so in L-0287. 'Horizontally scalable like this' blurs the two; the point is that no piece should be a single instance whose failure stalls the system.
- **L-0291** simplified/low: Works as a mutual-exclusion idea, but other clients are not refused. The kernel completes their TCP handshakes and parks them in the listen backlog ('completely established sockets waiting to be accepted'). They see ECONNREFUSED only when the backlog is full. Clients therefore wait in the backlog without knowing whether they hold the lock until the server accepts and responds.
- **L-0293** simplified/low: A crashed process closes its connection, but a crashed or partitioned host does not; the lock server still needs a timeout (lease) to free the lock.
- **L-0296** simplified/low: Correct that MySQL can serve as a lock store. MySQL also has named locks built in: GET_LOCK(name, timeout) is exclusive and is released 'implicitly when your session terminates (either normally or abnormally)'. That is effectively a liveness-based TTL. GET_LOCK locks only a single mysqld, though.
- **L-0297** simplified/low: A cron job works but is coarse: a stale lock stays until the next cron run. Common alternatives are an expires_at column checked in the acquire statement itself (take the row only if it is free or expired), or GET_LOCK, which is released when the holder's session ends.
- **L-0302** simplified/low: The student's description of OCI Queue is right: 'the message is hidden from other consumers for a pre-defined amount of time, which is known as its visibility timeout'. But this is not specific to OCI: SQS works the same way (default visibility timeout 30 s). In both, the message reappears if not deleted in time.
- **L-0307** imprecise/low: The queue example is mutual exclusion (a lock), not a distributed transaction: there is no atomic commit or rollback across participants. Distributed transactions use locks, but a lock alone is not a transaction.
- **L-0308** simplified/low: Same principle as L-0246 (student summary endorsed). Two processes on one host can also share memory (PostgreSQL backends coordinate through shared memory and semaphores), and file locks are kernel state, so the disk is not the only shared medium between processes.
- **L-0310** simplified/low: Right that expiry is what prevents perpetual locks; ZooKeeper's equivalent is the session (ephemeral nodes vanish when the session ends). The student's bottleneck worry has a standard answer: the holder extends the lease while it is still working. Redis docs describe extending the TTL with a Lua script if the value is still yours; the DynamoDB lock client heartbeats to extend its lease. Use a short TTL and renew it, rather than a long one.
- **L-0311** simplified/low: Using a mutex is two lines (pthread_mutex_lock/unlock). Implementing one is not: it relies on atomic CPU instructions and OS support to block waiters. The teacher's point holds: in-memory locking is cheap (about 25 ns per lock/unlock) compared with network round trips.
- **L-0315** simplified/low: Agreed that Redlock is not foolproof. But this case has a documented fix rather than only low probability: delayed restarts (a crashed node stays out for longer than the max TTL) or fsync=always persistence.
- **L-0317** simplified/low: The 'wait until the cluster is healthy' idea matches the documented fix: keep a crashed or replaced instance out for at least the max TTL (delayed restart), so it cannot grant a lock that is still active elsewhere. A newly spun-up empty node joining immediately is exactly the unsafe case.
- **L-0319** imprecise/low: Same as L-0316: in Redlock a client that already has a majority does not keep trying the remaining instances. Restarted nodes are handled by delayed restarts and persistence, not by the holder grabbing more nodes.
- **L-0329** simplified/low: Persistence (AOF fsync=always) fixes only crash-restart losses. It does not give Redis consensus or protect against clock jumps and client pauses, which is the student's point. The teacher's hedge ('not saying this is better') is fair.
- **L-0331** simplified/low: ZooKeeper watches are one-time triggers sent over the client's session connection; a client must re-register after each notification and re-read the data.
- **L-0332** simplified/low: Close, but ZooKeeper watches are one-time triggers that must be re-set, and they carry an ordering guarantee (a client sees the watch event before the new data), unlike plain pub/sub.
- **L-0337** simplified/low: Plain DNS has no load information, but managed DNS can be health-aware: Route 53 stops answering with records whose health checks fail.
- **L-0340** simplified/low: Hash-based stickiness works, but adding or removing servers remaps some users (consistent hashing keeps this to a few keys) and a failed server loses its in-memory sessions.
- **L-0343** simplified/low: As a per-service-hop budget (serialization, TLS, queueing, handler time) 3-10 ms is plausible. The raw network is faster: a round trip within one datacenter is about 0.5 ms (Jeff Dean's ~2012 figures), and AWS describes inter-AZ latency as 'single-digit millisecond'. The point (every hop costs, so count hops) stands.
- **L-0353** imprecise/low: CoreDNS is not made highly available by leader election: it is stateless, so you run several replicas and clients list multiple nameservers (resolv.conf allows up to 3, tried in order).
- **L-0355** imprecise/low: The CoreDNS manual (checked Oct 2026) has no dedicated production or high-availability guide; it covers installation, plugins, configuration and example setups.
- **L-0364** simplified/low: Authorization (is A allowed to pay B) is business logic, but authentication can be offloaded to the LB: AWS ALB can authenticate users via OIDC/Cognito. Auth failures are usually 401/403, not 404.
