## 1 · Images are just responses
**Section dek:** "The image is served" hides a piece of code you could write yourself. Once you see the code, a URL can return an image that never existed until someone asked.
**Sec-meta:** about 14 min · class 00:05–00:27
**Opening problem (lecture case):** someone shares a GitHub repository link on a social site, and a card appears showing that repository's current stars and contributors. Where did that image come from?
**RuleBox (§1):** "All that matters is the bytes you send." The handler is yours. If the bytes are a properly structured image, the browser renders it, whether the image was stored or made a moment ago (L-0033). Sketch: `<img src>` → a box marked `handler` → a byte strip with a `PNG` header → a framed picture.
**Estimated words:** 2,600
**Q&A folded in:** none in this segment. A remark that "four or five weeks back" some people thought the extension tells the browser (00:06:43) → 1.1 misconception.
**Hand-off to §2:** "With that context, Gravatar becomes an easy problem: one URL whose handler returns your current photo."

### 1.1 What the browser actually does with an image URL
- **Purpose:** replace "images are served" with the actual mechanism.
- **Opens with:** a profile picture on any page. Ask how it gets there. People usually answer without thinking: "it's served". But someone wrote the code that reads that image and sends it (L-0013, L-0014).
- **Key points:** the tempting idea is that the browser knows a URL is an image from `.jpg`. It doesn't have a clue (L-0015). A browser is a deliberately dumb program with fixed behaviour, and so is an app (L-0016). Platforms such as the browser, Android, iOS and their SDKs are building blocks, so they must stay basic (L-0017, attributed as the lecture's view). The mechanism: the URL sits in an `<img>` tag's `src`. While rendering the HTML, the browser hits the tag and sends an HTTP GET (L-0018). It doesn't know what the GET will return. It expects an image and tries to read whatever bytes come back as one (L-0019). Every file format starts with a header that names it (PNG, JPG, bitmap, TIFF) (L-0020; BackChip: Lecture 7's GitHub-issues upload showed those PNG bytes). On a 2xx response the browser reads the header, picks the matching decoder and paints the pixels (L-0021, simplified-low, left as taught; A-ID-03 as a separate sentence: browsers sniff only raster signatures, and SVG must arrive as `image/svg+xml`; A-ID-04 gives the signatures: PNG `89 50 4E 47…`, JPEG `FF D8 FF`, BMP `BM`, GIF `GIF89a`). Browsers ship decoders for every common format (L-0022, **inline clarification**: the web's set is PNG, JPEG, GIF, WebP, AVIF, plus SVG rendering; TIFF works natively only in Safari).
- **Components:** NotationKey (once), Prose, Figure.
- **Figure:** Fig 1·a "From `<img>` to pixels" (new).
- **Words:** 550

### 1.2 The static folder is code, and you can write your own
- **Opens with:** `https://arpitbhayani.me/static/img/arpit.jpg` (the board's example).
- **Key points:** the GET reaches the web server, which looks up the handler for that path (L-0023). A static-folder mapping ties a URL prefix like `/static` to a folder on disk. nginx, Spring Boot, Flask and Django all support it (L-0024, simplified-low, left; A-ID-07 as a separate sentence: Django serves static files itself only in development, and its docs call that "grossly inefficient and probably insecure"). Whatever follows `/static` is a relative path. The server reads that file and sends its bytes, without caring what kind of file it is (L-0025, simplified-low, left; A-ID-05 woven in: the path comes from the URL and is untrusted, so the handler must stop `../` escaping the folder, as Werkzeug's `safe_join` does). Board example: `/static/img/arpit.jpg` → `site/static/img/arpit.jpg` (L-0026). This isn't magic. It is code built into the web server so you don't rewrite it each time (L-0027). So you can write your own handler that reads from S3 instead of local disk (L-0028). Example: `/raw/<path>` uses the rest of the path as an S3 key in a configured bucket and returns the bytes (L-0029). One generic route and three or four lines make the server a proxy for S3 (L-0030). This is not a feature or a new CDN. It only shows that a normal HTTP response can carry an image (L-0031). Misconception: a web server can only send JSON. It can send any bytes, images included (L-0032). A-ID-06 (keep, reworded): when your own handler returns file bytes, set `Content-Type` yourself, because browsers go by the MIME type, not the extension.
- **CodeBlock:** the board's Flask handler, `@app.route('/raw/<path>') def raw_handler(path): raw_b = S3.read(path, BUCKET); return raw_b`, with one comment line: `# real code: set Content-Type, and never trust the path`.
- **Figure:** Fig 1·b (D-01 redraw) "Two handlers, one idea".
- **Words:** 600

### 1.3 An image that doesn't exist yet
- **Opens with:** the shared GitHub link (the class demo used the instructor's DiceDB repository).
- **Key points:** because the handler is yours, the image need not exist beforehand. The handler can run any logic, and all that matters is the bytes (L-0033 → RuleBox). Sharing a repository link on Twitter, LinkedIn or Facebook renders a card with title, site name, description and an image (L-0034). That image is specific to the repository: description, contributors, issues, discussions, stars and forks (L-0035). It comes from the Open Graph protocol: your HTML names an `og:image` URL, and that URL is drawn in the card (L-0036; A-ID-12: OG requires `og:title`, `og:type`, `og:image` and `og:url`). In GitHub's page source, the `og:image` URL returns the same image, yet it ends in no image extension (L-0037). A valid image response doesn't mean the image sits in S3 (L-0038). The card shows the repository's current state, and if the counts change, the image changes too, perhaps a day or two later (L-0039, unverifiable-low: "a day or two" is the instructor's estimate, since GitHub publishes no refresh interval). Misconception: such images are pre-generated. With millions of repositories, GitHub wouldn't spend compute rendering one per repository every day. It renders on demand (L-0040). The `og:image` URL is the same kind of route handler as `/raw`, put behind a CDN (L-0041). GitHub runs a separate CDN for these images, `opengraph.githubassets.com`, beside `githubusercontent.com` for user assets, just like Lecture 7's `edge.arpitbhayani.me` (L-0042, BackChip Lecture 7).
- **PauseAndThink P1** before the reveal of L-0040.
- **Components:** Prose, RuleBox §1, PauseAndThink.
- **Words:** 550

### 1.4 On demand, behind a CDN
- **Opens with:** a million people open the same repo card. Who renders it?
- **Key points:** the flow: the backend gives the frontend the image URL (its key stays constant for a repository, or can be generated). The frontend puts it in an `<img>`. The request goes to the CDN, which serves the cached copy without touching the backend (L-0043). On a miss, the CDN calls the origin, GitHub's API server, which generates the image (L-0044, simplified-low, left). The image is a template: same layout for every repository, with title, icon and fetched statistics in fixed places (L-0045). The origin replies, and the CDN caches with a TTL and serves later requests. After expiry, say a day, the next request misses and a fresh image is generated (L-0046; A-ID-11: the origin usually sets that TTL with `Cache-Control: s-maxage`, which applies to the CDN and not the browser). Libraries: ImageMagick or PIL, "tons of such libraries". PIL is typically the best, and it uses ImageMagick through a C++ binding (L-0047 → **SourceNote SN-01**, A-ID-10). From practice: GitHub's own post says one image takes about 280 ms, about two million "unique-ish" images are made a day, and 40% of requests get a cached image (A-ID-08). GitHub actually renders an HTML template in a headless browser, another way to draw a card (A-ID-09). Hundreds of products use on-demand social images. Bannerbear specializes in them (L-0048). Hypothetical: Twitter could render a clean card of a tweet when its URL is shared, instead of people posting screenshots made with tools like poet.so. On a CDN miss it fills a template, and the CDN caches it (L-0049, labelled hypothetical). Dynamic cards are powerful UX, because the card shows current likes, shares and comments, not a static picture (L-0050). Before this, a shared GitHub link showed a big, poor-looking user avatar, and the generated card fixed that (L-0052).
- **MarginNote** "Build it in an hour": install Python, pick an image library, expose one endpoint that fetches a GitHub repo's data, draws the card and serves it on localhost. Any language works (L-0051). Nothing in this course is theoretical. Everything is used in production somewhere and can be prototyped on one laptop, with no 50,000 servers needed (L-0053). Skip unless you're going to build it (you should).
- **Figure:** Fig 1·c "The repo card, made on a miss" (new).
- **RecallQuestions §1:** (1) The URL `…/static/img/logo` has no extension. Will an `<img>` render it, and what decides? (2) Why can't GitHub pre-generate every repository's card, and what makes on-demand generation affordable? (3) Your `/raw/<path>` handler reads S3. Name two things a production version must add.
- **Words:** 900

### 2.1 One URL for your face
- **Opens with:** the forum with your face on it.
- **Key points:** with image serving understood, Gravatar is easy. It creates one embeddable URL for your profile picture. That is why some sites show your photo even though you didn't sign up with Twitter, Gmail or Microsoft (L-0055). On gravatar.com you log in with your email, upload several pictures and mark one active (L-0056). The URL is `gravatar.com/<MD5 of the email>`, and it is constant because the same input always hashes to the same output (L-0057 → **SourceNote SN-02**, A-GD-01: SHA-256 now, over the trimmed, lower-cased email; MD5 historically; path `/avatar/<hash>`). Put that URL in an `<img src>` and it returns the current photo's bytes, not a redirect (L-0058, **inline clarification** + A-GD-02: or a default image if the email has no Gravatar, and `s=`/`d=` set the size and the fallback). Board example: `hash("arpit@gmail.com") = 0eafd172` → `<img src="https://gravatar.com/0eafd172">`. If every platform adopted it, you'd change your photo once and the next request everywhere would pick it up, with no social network doing anything (L-0059). Not everyone does adopt it, but the concept is novel (L-0060). Why a hash and not the email: the email is PII, so the URL carries a hash for security (L-0054, simplified-medium → **inline clarification** + A-GD-03: the hash keeps the address out of plain sight, but it is unsalted and fast, so anyone holding a guessed address can confirm it). Why the hash doesn't mix in a Gravatar user id: the hash is a universal function. A site like Facebook knows only your email, and from it alone can check for and render your Gravatar (L-0310). Requirements: upload several pictures, mark one active, and the URL returns the active one (L-0062).
- **MarginNote** "Build it": a Gravatar-like prototype is three or four hours of work, so build as many prototypes as you can (L-0061, the instructor's estimate). Skip unless you're building it.
- **Words:** 600

### 2.2 Question every column
- **Opens with:** "Which tables, and what goes in each?" (L-0063)
- **Key points:** one first proposal was a `users` table storing the email's hash (L-0064). The tempting refinement: store only the hash, since the email is derivable from it (it isn't, see 2.3), it saves space, and Gravatar never shows the email (L-0065, proposed then corrected). Store the real email. People log in and authenticate with it, see it on their profile page, and relying on a hash risks a collision logging someone into another person's account (L-0066). So `users(id, email)`. The hash is written and crossed off, because it is derivable (L-0067; this is Lecture 7's rule, BackChip). One relational column can't hold several image paths, so photos get their own table (L-0068, simplified-low, left). `photos(id, user_id)` has one row per upload, so 10 photos make 10 rows (L-0069). The proposal to store each image's path is dropped too: the path is derivable (L-0070). The S3 path comes from the user id and the photo id (L-0121; also in 3.1). Add `is_active` (boolean) to `photos` (L-0071).
- **MarginNote** "Bool, tiny int or string?": an integer enum instead of a boolean is fine and leaves room for a third state, as long as it is a tiny int (L-0168). A boolean takes 8 bits, one byte (L-0169). Use a tiny int, not a big integer, and never store state as a string (L-0170). A-GD-18: in MySQL, `BOOL` is `TINYINT(1)` and can hold -128..127, so add a CHECK if only 0/1 is allowed. A-GD-19: PostgreSQL has no TINYINT, so use `boolean` or `smallint` with a CHECK. Skip unless you pick column types.
- **MarginNote** "Why no join table, like Slack's?": Slack's design (BackChip Lecture 4) put a membership table between users and channels, while `photos` just references the user. Both are one-to-many, but Slack's membership row carried per-user data (last-read checkpoint, starred). Gravatar has nothing like that (L-0173). Skip unless you remember Lecture 4.
- **Figure:** Fig 2·a (D-04 redraw) "Two tables, sample rows".
- **Words:** 650

### 2.3 The query that reads every row
- **Opens with:** "Show me all my photos." Write the exact query.
- **Key points:** a first draft is `select * from photos where user_id = ?`. No `is_active` filter, because all photos are shown (L-0072). One suggestion was to select only the needed columns instead of `*`. It was noted without a clear verdict (L-0073, kept as an open aside). But the request carries the email's hash, not the user id, so the query must join `users` and filter on the user found by the hash (L-0074). Tempting: decrypt the hash to get the email. You can't. It is hashing, not encryption, and hashing is lossy (L-0075). Another proposal: since the hash can't be reversed, it must be stored. The class answer at that moment was instead to hash in the WHERE clause (L-0076, open). `where HASH(email) = ?` works functionally (L-0077). Collisions are accepted. Assume hashes are unique, because two people with the same hash can't be told apart anyway (L-0078). It adds a hash computation per row on every query (L-0079). The real pain point: the database must read every row, hash each email and compare, a whole-table scan, before it can join (L-0080). A computation in the WHERE clause stops the database from using an index, because it can't know which email hashes to the value without computing every one (L-0081 → **SourceNote SN-03**, A-GD-04, A-GD-05: expression/functional indexes exist). Today contradicts yesterday: it is not always true that derivable data shouldn't be stored. If not storing it slows things down, store it (L-0082 → RuleBox; BackChip Lecture 7). Fix: an indexed `hash` column, queried `where users.hash = ?`. The lookup becomes very pointy, nearly O(1): one user row → user id → join photos (L-0083). When a user is created, store the email and its hash, each as a unique, indexed key (L-0084). Drawing boxes is easy. Only by writing the query and asking how it runs do you find the column you need (L-0085 → RuleBox body).
- **PauseAndThink P2** (before L-0080). **AnimationClip `l06-hash-scan`** after P2's reveal. **Figure:** Fig 2·b "Two WHERE clauses" (the clip's static twin).
- **CodeBlock:** `-- scans every row` `SELECT p.* FROM photos p JOIN users u ON p.user_id = u.id WHERE HASH(u.email) = ?;` vs `-- one index lookup` `… WHERE u.hash = ?;`
- **Words:** 900

### 2.4 Mark a photo active: a bug hunt
- **Opens with:** a three-line query, "almost hello world", that nearly every engineer has got wrong (L-0087).
- **Key points:** first draft: `update photos set is_active = true where id = ?` (L-0086). Tempting: add `user_id` to shrink the scan. No, `id` is the primary key, so the lookup is already log n (L-0088). **Bug 1:** the previously active photo stays active (L-0089). Fix: two updates. Mark the user's photos inactive, then mark the chosen one active (L-0090; the class went through a three-query version and a counter hack first). Refinement: only touch the active row, `… and is_active = true` (L-0091). The second update depends on the first, so make it one transaction (L-0092). **Bug 2:** without an explicit transaction, a crash after the first update leaves no active photo, and a site rendering the profile photo, Facebook say, gets a 404 (L-0093). It sounds obvious, but people skip it and don't call it out. Focus on every detail, especially in simple systems (L-0094). With the transaction, the update is atomic, and the class took concurrency as handled (L-0095 → **SourceNote SN-04**, A-GD-06: atomic isn't isolated; lock the user row or move to `active_photo_id`; BackChip Lecture 3 for `FOR UPDATE`). Spotting a bug in a tiny query is hard, like writing one print statement and asking why the program doesn't run (L-0096). **Bug 3:** the second update must also check `user_id = ?`. Otherwise someone can pass a random photo id. Your photos go inactive and someone else's turns active, which is a security and correctness bug (L-0097). Board's final: `… where id = ? and user_id = ? and is_active = false`. Going into why a field is needed and covering every case is what makes a better engineer (L-0098). With the transaction, the ownership check and the stored hash, the system is efficient and correct (L-0099). It's like code review: 5 lines get 50 comments, 500 lines get "looks good to me" (L-0100).
- **"Keep exactly one active" (Prose + MarginNote, the 01:14 Q&A):** if a wrong photo id is passed, the `user_id` condition means no row is updated (L-0132). An update that should change something but changes nothing is an alarm, usually a front-end bug (L-0133). But the first update has already cleared the user's photos, so the user ends with no active photo and a 404 (L-0134). If the invariant is exactly one active photo, check it first: select the photo row by photo id and user id, and only if it exists run the two updates (L-0135, simplified-low, left; A-GD-07 woven in: make that check a locking read, `SELECT … FOR UPDATE`, or a concurrent change can slip in). Always validate that a change can't leave the data inconsistent: check first, then write (L-0136). One proposal: report "not found" in the app when zero rows match, and let a failed transaction roll back by itself (L-0137, **inline clarification** + A-GD-08: a zero-row UPDATE isn't an error, so nothing rolls back unless the app reads `ROW_COUNT()` and issues ROLLBACK). Check that the photo belongs to the user before updating, 100%. Get, then update (L-0171). Security must hold at every step. Careful in one place and lax in another doesn't work (L-0172).

### 2.5 Where does "active" live?
- **Opens with:** the most frequent Gravatar query: some page renders your photo.
- **Key points:** one very small optimization remains. It is extreme nitpicking, and in practice the difference is minimal (L-0101). The read: `select * from photos join users on photos.user_id = users.id where users.hash = ? and photos.is_active = true`. Correctness guarantees one row (L-0102). Inner vs left join is not the optimization, since both perform the same here (L-0103; A-GD-10, optional, used: MySQL turns this LEFT JOIN into an inner join anyway because the WHERE rejects NULL rows). One reading of the order: the hash filter gives one user, then the join gives that user's photos, then `is_active` filters them (L-0104, open). Tempting: the `is_active` filter is the extra work. No, it is an index lookup on a narrowed set (L-0105, simplified-low, left; A-GD-09 woven in: the narrowing relies on an index on `photos.user_id`, which InnoDB creates for a foreign key and PostgreSQL does not). Another idea: skip the update if the photo is already active (L-0106, open, no verdict). **The move:** store `active_photo_id` on `users`. Gravatar is read-heavy, the read becomes one lookup, and the multi-row marking goes away (L-0107). At first, marking still runs in a transaction, now updating `users`: `update users set active_photo_id = ? where user_id = ?` (L-0108). The most frequent query now needs no join: one row from `users` gives the photo id and user id, which build the S3 path (L-0109, **inline clarification**: the URL carries the hash, so it is `where hash = ?`, as confirmed later; a unique indexed lookup is as cheap as the primary key). Why keep `is_active` at all? It marked one of several photos. With `active_photo_id`, the rare "is this photo active?" is a join with `users` (L-0110). Marking active is now a single update with the ownership checks, and under auto-commit a single statement is a transaction in itself (L-0111; A-GD-20: MySQL connections start in autocommit; the board's clean version from 01:31 is `update users set active_photo_id = ? where hash = ?`). Counterintuitive, because we think of "active" as a property of the photo. Class, LLD and schema design train us to think in entity attributes (L-0112). There's no one way. What seems simple isn't, and much can be challenged (L-0113). In every cohort since this question was first asked, people start with `is_active` on photos, so the page walks the same path (L-0114, the instructor's experience). The claim isn't that `active_photo_id` is hugely better. A more optimized design can exist, so challenge your beliefs: unlearn, relearn (L-0115). Board note "Possible optimizations": denormalize `users` to avoid joins, storing `active_photo_id` or even the active S3 key (L-0147).
- **MarginNote** "How the database runs the join": the join on user id is a join criterion (the foreign key), not a filter, and the input is the hash (L-0141). The query narrows step by step: hash → one user row → that user's ~10 photos → the active one (L-0142). The optimizer picks what to evaluate first, here the unique key on the hash (L-0143). **Predicate pushdown**: filters are pushed to the leaves of the evaluation tree and applied first, then the join, then the rest going up (L-0144). The tree is evaluated bottom-up (L-0145). Skip unless you read query plans.

### 3.1 Upload, reused

Sample rows: a published photo with its user id and `is_active = true`; `users` holds the email and its hash (L-0118). The S3 path is derived from user id + photo id, never stored (L-0121).

### 3.2 A CDN in front, the API as origin
- **Opens with:** millions of hits on one URL pattern.
- **Key points:** serve photos through a CDN, not the backend. At Facebook or Instagram scale, all that traffic hitting the API and then S3 would be chaos, and the AWS bill would shoot up. The CDN also gives a better experience (L-0119). The API exposes `api.gravatar.com/photo/<hash>`: find the active photo, read it from S3, return the bytes (L-0120, the standard procedure, the same as §1's `/raw`). A CDN property `gravatar.com` has that endpoint as its origin (L-0122). Unlike Lecture 7's subdomain property `edge.arpitbhayani.me`, here the root domain itself is the CDN property (L-0123; A-GD-12 woven in: a plain CNAME can't sit at the zone apex, so this needs provider support such as CNAME flattening). Flow: `gravatar.com/<hash>` → CDN; hit → served; miss → origin `api.gravatar.com` → S3 → back, cached, served, and later requests come from the CDN (L-0124). The mapping is often read backwards: the request goes to the CDN, and the CDN calls the API on a miss (L-0138). A common question is why the CDN doesn't point straight at S3. One reason given: S3 isn't public (L-0139 → **SourceNote SN-05**, A-GD-11). The real reason: S3 doesn't know which photo is active. Only the database does, so the origin is the API (L-0140 → RuleBox).

- **Words:** 650

### 3.3 When the photo changes
- **Opens with:** user 1 changes their photo. User 2 loaded the old one through the CDN an hour ago.
- **Key points:** on publish or update, the API updates the database and pushes an event to Kafka (L-0125). The event exists to invalidate the CDN. Once user 2 has loaded user 1's photo, the CDN serves it to everyone, so a change must evict it (L-0126). Photos rarely change, so the TTL might be one or two days (L-0127). Even so, invalidate right away when the user changes the photo, because they expect to see the new one everywhere at once (L-0128; asked in class: "so you call the CDN directly?" was answered "synchronous, yes", while the design uses Kafka consumers to make that call, and the page shows the Kafka design and notes the direct call as a variant). The event goes to workers whose only job is to call the CDN's invalidation API for the path, e.g. `/h1`. The next request misses, and the origin reads the DB and S3 and refills the CDN (L-0129; the board labels the bus "queue"). Cloudflare, Akamai and every CDN expose invalidation APIs (L-0130). A-GD-13 woven in: invalidation clears only the CDN's edges, and a browser may keep its own copy until it expires, which is why CDNs recommend versioned file names for files that change often. Gravatar is simple. The interest is in the details: how the CDN is used, transactions, how the schema evolved, the critical questions, security and correctness (L-0131).
- **AnimationClip `l06-invalidate`**. Predict line: "User 1 changes their photo. With a two-day TTL and no invalidation, how long might user 2 see the old face?"
- **Words:** 550

### 3.4 Every size, on demand
- **Opens with:** the same Gravatar photo as a 32-pixel dot in a comment thread and a 512-pixel header on a profile.
- **Key points:** once the CDN and Gravatar make sense, this is a piece of cake (L-0148). The problem: one image at 16×16, 32×32, 256×256, 512×512, uploaded at any resolution, and the requested size must be served. The design assumes the CDN doesn't offer this (L-0149). On-demand optimization is not "upload, post a message, let workers pre-create variants". It transforms when requested (L-0150). Like a CDN, it takes query parameters: `?w=32` means 32 pixels wide (L-0151; board `https://gravatar.com/h1?w=32`; A-GD-02 cross-ref: real Gravatar uses `s=`). The flow: the CDN looks up the full URL and returns it if cached. Otherwise the request, query parameters included, goes to the origin, which reads S3, applies the transformation and returns it. That is the one extra step (L-0152). ImageMagick is the world's most popular image processing library (L-0153, simplified-low, left as taught and attributed as the lecture's view). PIL has two bindings, a native Python one and ImageMagick (L-0154 → **SourceNote SN-06**). ImageMagick is written purely in C++, and almost every language has C++ bindings, so you can call it natively from your language (L-0155 → **SourceNote SN-06**, A-GD-15 optional, used). Resizing: call its resize with the new size, get bytes in memory and send them. That's the only change to the flow (L-0156). The origin supports whatever transformations you choose, such as grayscale or resize: get the image from S3, apply them, return it (L-0157). It is exactly what CDNs do with transformation parameters (Lecture 7), re-implemented (L-0158; A-GD-16: Cloudflare Images transforms from URL parameters, for example). If you were building your own CDN, this is how you'd implement the feature (L-0163).

### 3.5 Why it needs big machines
- **Opens with:** a page loads 200 avatars at `w=32`, all cache misses.
- **Key points:** image processing, encryption and video processing are CPU-heavy, so you pay for bulky machines with many CPUs (L-0159). On-demand (not async) processing needs bulky machines because many cores let you parallelize and finish fast. Every on-demand processing system is built this way, nothing fancy, with bulky servers autoscaled on incoming requests (L-0160). It can't be made async: when the URL loads, the 240-pixel image must exist right then (L-0161; board "CPU intensive! Cannot be ASYNC; large servers (size & numbers)"). Handling the scale is a no-brainer: large servers, nothing magic (L-0164). Cloud providers give this out of the box, and few engineers run such infrastructure themselves, so it is usually abstracted away (L-0167).

It said ImageMagick runs on massive 32- or 64-core servers and the fleet scales with requests (L-0162, unverifiable, attributed; A-GD-17 optional, used: Cloudflare's own 2021 post says its Image Resizing is written in Rust, so the memory more likely fits another company or an older system). ### 4.3 How many tags, and who gets told
- **Opens with:** a photo of a 40-person team offsite.
- **Key points:** one question was the maximum number of people per photo, kept at photo level, not album (L-0187). A worry: a limit of five means managing several people tagging at once. ### 5.1 What the 3 means
- **Opens with:** the badge.
- **Key points:** the last system of the day is the newly unread indicator, seen every day on LinkedIn, Twitter, Facebook and Instagram (L-0223). The 3 means three *newly* unread, not three unread (L-0226, based on the live demo: Instagram doesn't document what its badge counts, so this is the definition used for the exercise). ### 5.2 The crude, correct query
- **Opens with:** the most direct design: store messages, remember when the user last looked.
- **Key points:** first approach: track whether each message is read, track the last time the icon was tapped, filter messages after it, count unique senders (L-0234). A proposal to go straight to a message queue per user, partitioned by sender, was set aside to ask first: what is the input, and what does the table store? (L-0237, open). Data model: `messages(msg, from, to, ts)`, where the timestamp is critical (L-0235). A second store keeps each user's last read time (L-0236). Storing every message a user ever received "does no harm" but isn't scalable (L-0238, a class remark, open). `messages` holds all messages sent to the user, and its scale is huge, a problem deferred (L-0239). The last read time goes in `user_activity(user_id, last_read_at)`, one row per user, with room for more fields (L-0240). Tempting: select the messages after `last_read_at` and order them. No, only the count is shown, so ordering is wasted (L-0241). `SELECT * … WHERE to = ? AND ts > last_read_at` gives one row per message, three from one sender, while we need one per sender (L-0242). The crude query: `SELECT COUNT(UNIQUE(from)) FROM messages WHERE to = ? AND ts > last_read_at` (L-0243, **inline clarification** + A-PTU-10: in SQL it's `COUNT(DISTINCT …)`, and `from`/`to` are reserved words, so name them `sender_id`/`recipient_id`). Index on timestamp alone? That sorts every user's messages by time (L-0244, corrected). Index `(to, from, ts)`: one recipient's entries together, grouped by sender, ordered by time (L-0246, simplified-low, left). Better, `(to, ts, from)`, so the time range can cut the scan short (L-0247; A-PTU-09: PostgreSQL's rule, equality on leading columns plus a range on the next one, limits what's read). Still expensive: 10,000 received messages means walking 10,000 entries for a unique count, on every page load, for millions of users (L-0245). Worst case: one person sent 10,000 messages, and you read 10,000 index entries to learn the answer is 1. Reordering the index can't remove that (L-0248). This is crude, not incorrect. It is very correct and not very efficient (L-0250). `messages` is the source of truth for messages and `user_activity` for the last tap, so the count is always exactly right. The only problem is iterating every message to find unique senders (L-0251).
- **Figure:** Fig 5·b (D-09 redraw) "CRUDE". Fig 5·c "Which index order reads less" (new, small).
- **CodeBlock:** the cleaned query `SELECT COUNT(DISTINCT sender_id) FROM messages WHERE recipient_id = ? AND ts > ?;` and the index `CREATE INDEX ix_unread ON messages (recipient_id, ts, sender_id);`
- **Words:** 950

### 5.3 Keep a set instead
- **Opens with:** do we need the messages at all to know who wrote?
- **Key points:** a proposal: keep a separate record with just a count, because what matters is who sent something, not what they wrote (L-0249). Per user, a non-relational record holding a count, later named `newly_unread_count` (L-0252). Then a set of unique senders was added beside it. But the set already identifies unique senders, so what is the count for? (L-0253). Keep only the set and show its length on the badge (L-0254). Every set tracks its own length, so size is O(1) and a separate count is unnecessary (L-0255; A-PTU-11: Redis `SCARD` is O(1) and returns 0 for a missing key). When someone messages the user, add the sender to the user's set (L-0256; A-PTU-12: `SADD` ignores members already present and returns 0 for them). When the user taps the icon, delete the set. The delete is O(1), which makes this far more efficient (L-0257, **inline clarification** + A-PTU-13: `DEL` is O(members), cheap for small sets, and `UNLINK` frees memory in the background).
- **Figure:** Fig 5·d "One set per user" (D-09 left side, new layout).
- **Words:** 400

### 5.4 Source of truth or pre-computed
- **Opens with:** two designs that both give the right badge.
- **Key points:** a classic way to build almost any system: query the source of truth, or keep things pre-computed (L-0258 → RuleBox body). Query the source of truth for strong consistency. Pre-compute, or store data directly consumable, for efficiency (L-0259 → RuleBox). With the set, you read its length. The source-of-truth approach fires an expensive query, whether SQL or NoSQL (L-0260). The cost of pre-computing: keeping it updated is now your job and needs another flow that writes there too. The source of truth stays current by nature, because every message is ingested into it (L-0261). Neither is wrong. It depends on priorities and scale. For a startup, querying the source of truth works fine. With millions concurrently active, you may lean toward pre-computing (L-0262). Callback: the stored hash (§2.3) and `active_photo_id` (§2.5) were the same move.
- **TradeoffTable T3** "Source of truth vs pre-computed". Rows: read cost · always correct? · who keeps it updated · extra flows · fits when. Red ✕ on pre-computed's "always correct?": "only if every write path updates it".
- **Words:** 350

### 5.5 Redis: the read path and the clear
- **Opens with:** which store holds a set per user?
- **Key points:** a variable-length list of user ids per user points to a NoSQL store, such as a document or key-value store like MongoDB, with key = user id and value = a set (L-0263; A-PTU-22: MongoDB's `$addToSet` gives set semantics with atomic single-document updates). Redis was chosen as a simplification, since almost everyone knows it. Any key-value store with a set value works. The point is to reuse the database's set so you don't check-and-set yourself (L-0264, simplified-low, left). Read path: a get-status API asks Redis for the set's size and returns it for the badge (L-0265). Clear path: a clear API deletes the user's key when the icon is tapped. With get and clear, the read path and a trivial write path are done (L-0266).
- **Figure:** Fig 5·e (D-10 redraw) "Get and clear".
- **Words:** 300

### 5.6 The write path starts at the messaging service
- **Opens with:** something has to put "C wrote to B" into B's set while B is away.
- **Key points:** the interesting part is the write path: who adds the senders a user heard from while offline? (L-0267). The client must be smart. If the user is on the messages tab, a message (even in another chat) isn't newly unread, and no update is needed (L-0268). With a WebSocket for messaging, the backend can check that the connection is down, for example while the user watches reels, and only then update Redis (L-0269; A-PTU-19: a socket can look open after the client is gone, which is what RFC 6455 Ping/Pong is for). The design needs a few more databases than one, which is where the pattern comes in (L-0270). The input is the messaging service, because it knows when a message couldn't be delivered (L-0271). Simplification: count only while the user is offline. In real life, another tab counts too, and whatever "unsent" means comes from the messaging service (L-0272). It is the source of truth for delivery: delivered or not, on the tab or not, connection up or not (L-0273). It asks an online/offline service or knows itself, because every persistent connection is with its edge servers (L-0274; BackChip Lecture 1, online/offline indicator; Lecture 4, scaling WebSockets). **`ON_MSG_UNSENT`** is an umbrella event for every case where we want the badge to bump. The where-is-the-user logic lives there (L-0275; Q&A: it covers any message not delivered in real time, not only "no socket"). Whether another tab counts as unsent is a product call, and whatever flows into the event updates the count in real time (L-0311). Events flow into Kafka and become the system's input. Each says who sent what to whom, and consumers add the sender to the recipient's set in Redis (L-0276; board `{src: "A", dest: "B", msg}` and `B: {C, D}`). If the queue is partitioned by recipient id, workers can batch writes (L-0277; board note, partly illegible; A-PTU-17: key events by recipient so one worker sees all of a user's events; A-PTU-18: pipelining batches the Redis calls). Full design: read path get/clear status on a Redis cluster; write path `ON_MSG_UNSENT` → status-update workers → Redis cluster; the same stream also feeds the notification system (L-0278).
- **Figures:** Fig 5·f (D-11 + D-12 redraw) "Who knows a message wasn't delivered". Fig 5·g (D-13 redraw, without the auxiliary store) "Read path, write path".
- **RecallQuestions §5:** (1) 300 unread messages from 3 people, and the user tapped the icon an hour ago with nothing new since. What does the badge show? (2) Why is the crude query correct, and why does no index order fix its cost? (3) Who produces the event that grows the set, and why that service?

## 6 · Protect the database: the auxiliary database
**Section dek:** the design works, but the database is doing work that changes nothing. Put a cheap store in front of it to absorb that work, and decide what inconsistency you can live with.
**Sec-meta:** about 14 min · class 02:32–02:40, Q&A 02:42–02:48, 02:55
**Opening problem (lecture case):** while B is offline, C sends 30 short messages ("Hey, what are you doing? Come here."). How many of those 30 writes change B's set?
**RuleBox (§6):** "Whenever a database does a lot of operations that lead to no state change, minimise them. Protect it however you can: if the database is down, everything is down." (L-0288). Box body: "Add an auxiliary database to absorb them." (L-0290). Sketch: a cylinder under a glass dome (the "rose in a jar", L-0309), with a small second cylinder beside it catching arrows.
**Estimated words:** 2,350
**Q&A folded in:** "100+" threshold (02:42:15) → 6.4. Key model `B_C: True` vs a set (02:43:21) → 6.2. Existence, not every message; no count (02:44:03–02:45:00) → 6.2. Clear deletes both, resync (02:45:00–02:45:45) → 6.3. One write fails, no distributed transaction (02:45:45–02:47:37) → 6.3. Read-before-write instead; the rose in a jar (02:47:58) → 6.4. Auxiliary must be a cluster (02:55:29) → 6.2.
**Hand-off to §7:** "Four systems, one afternoon. Here is what to carry out of the room."

### 6.1 Audit every path
- **Opens with:** many people stop here, with a read path and a write path drawn and the design converged. That isn't good enough (L-0279).
- **Key points:** the Redis cluster is overburdened: a huge number of get-status reads (millions refreshing or moving between pages), writes on every icon tap, and an update on every unsent message (L-0280). The database is the most brittle component, so check for unnecessary operations on it (L-0281, a heuristic, attributed; BackChip Lecture 2). Path by path. Get status is the bare minimum: you must go to the source of truth, and a replica isn't needed for an in-memory DB (L-0282, **inline clarification** + A-PTU-20: if read load grows, Redis replicas can serve these reads, since a slightly stale badge is fine). Clear must delete the key and can't be reduced (L-0283). The write path wastes work. The value is a set, so whether B sends 1 message or 10,000, the state changes only on the first, and the other 9,999 change nothing (L-0284). Friends don't send one message; they send 5, 10, 20, 30 short ones (L-0285). For the N-1 repeats, each write still calls the database, wasting network I/O and, worse, making the database handle them (L-0286). For each, the database receives the request, reads the set, checks membership and discards it, all work for no change (L-0287; A-PTU-12 cross-ref: `SADD` returns 0). The pattern: when a database does many operations that change no state, minimise them. Whatever the cloud, if the database is down, everything is down, so protect it (L-0288 → RuleBox). Protect it like Voldemort's Deathly Hallows, with every charm you have (L-0289).
- **PauseAndThink P9** (30 messages, how many changes?). **Figure:** Fig 6·a "Where the load goes" (new).
- **Words:** 650

### 6.2 The auxiliary database
- **Opens with:** a small second store that answers one question: have we already recorded C for B?
- **Key points:** use an **auxiliary database** to cut the unnecessary operations on the primary. When a brittle component does many no-op operations, add one and keep the main one up (L-0290 → RuleBox). It costs one more network hop, and protecting the main database with a bit of network cost is worth it every single time (L-0291, simplified-low, left). Flow: the write first checks the auxiliary Redis for this sender. If the entry exists, nothing goes to the main database. If not, write to the main database (L-0292, simplified-low, left; A-PTU-14 woven in: one atomic `SET B_C 1 NX`, then `SADD` on main only when it was newly set). The main database isn't even called for the n-1 repeats. The auxiliary takes the hits, and the main is protected (L-0293). Key model: separate keys like `B_C: True` instead of a set, which avoids set overhead. A set works too. Different key models keep the two stores clearly distinct (L-0302, simplified-low, left; A-PTU-15: or one hash per receiver with `HSETNX`, so a clear is one `DEL`). It checks, not stores. 10,000 messages from B means one write to the auxiliary, one to main, and the rest are existence checks (L-0303). There's no count in the auxiliary, only existence (L-0304). It must be a cluster too, because a single node won't handle the load (L-0321; A-PTU-16: in Redis Cluster, use hash tags like `{B}_C` so one user's keys share a slot).
- **AnimationClip `l06-aux-redis`**. Predict line: "C sends 30 messages. How many reach the main Redis, with and without the auxiliary?" **StepThrough** Fig 6·b "First message vs repeats". **Figure:** Fig 6·c (D-13 full redraw) "With the auxiliary Redis".
- **Words:** 700

### 6.3 When things go wrong
- **Opens with:** each store can fail. Which failure hurts?
- **Key points:** if the main database goes down, everything is down anyway. If the auxiliary goes down, all writes go to the main database, which handles the n-1 writes it was handling before. The auxiliary only sheds load (L-0294). Clearing (tap on the icon) must delete entries in both stores (L-0295; in Q&A: after the clear, the next message creates them again). If one write succeeds and the other fails, the stores drift. At worst the badge shows 2 while 300 messages wait (L-0305, simplified-low, left). Making both writes one transaction isn't needed. Take some inconsistency for high throughput. At worst you see 2 when it's 3, you see everything after a tap anyway, and someone who needs a reply will write again, which is how people work (L-0306). Accept a bit of inconsistency here. It isn't financial or critical, and distributed transactions aren't worth the complexity. A badge glitch is fine, but the whole system down is the end of the product (L-0296). It may feel like cheating, but in the real world it doesn't matter. Ask what the worst that can happen to the user is (L-0307). Pick your battles: decide what you trade for what (L-0297).
- **Figure:** Fig 6·d "Which failure hurts" (new, two panels).
- **Words:** 550

### 6.4 Why not just read first, or stop counting?
- **Opens with:** two cheaper-looking alternatives raised in class.
- **Key points:** why not read the main Redis before writing? Because even reads on the main database are unwanted. Every instruction costs it CPU, and the point is to protect it (L-0308, proposed then corrected). It's the rose in *Beauty and the Beast*, kept under glass so it never crumbles (L-0309). A threshold: past, say, 10,000 messages, show "100+" and stop writing to the cluster, since it no longer matters (L-0300). Threshold optimization: if the set is already above a threshold, say 100, don't write even a new sender's first entry, and save that write too (L-0301).
- **TradeoffTable T4** "Handling repeat writes": write every time · read main, then write · auxiliary store (+ threshold as a narrow fourth column). Rows: ops on the main DB per repeat · extra hop · consistency risk · if the extra piece fails. Red ✕ on "write every time"'s "ops on the main DB per repeat": "one full write, changes nothing".
- **RecallQuestions §6:** (1) Of 30 messages from one friend, how many writes reach the main Redis with the auxiliary store, and how many without? (2) The auxiliary Redis crashes. What happens to the badge, and why is that acceptable? (3) Why not wrap both writes in a distributed transaction, and what's the worst-case user-visible error?
- **Words:** 450
