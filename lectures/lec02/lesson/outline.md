## 1 · "NoSQL" is not one thing
**Section dek:** before choosing where Slack's messages live, stop saying "NoSQL". What the label hides, the two meanings of consistency, and why "relational databases don't scale" is a myth.
**Sec-meta:** about 8 min · class 00:02–00:08
**Opening problem (page's framing):** Slack will keep every message every employee ever sends. In a design review someone says "use NoSQL, it scales". Is that an answer?
**RuleBox (§1):** "Never believe a generic statement at face value, not even this one." Ask for the context and look for the counter-example. That habit makes you a better engineer (L-0025). Sketch: a speech bubble "X scales!" with a hand-drawn "?" and "for what workload?". Sits at the end of 1.3.
**Estimated words:** 1,500
**Q&A folded in:** none in this stretch. The 00:42 restatement of "drop the constraints and it scales" is linked forward to 5.1.

### 1.1 Name the database, not the family
- **Purpose:** replace "NoSQL" with the name of a family and the workload it serves.
- **Opens with:** the review comment above.
- **Key points:** "always use NoSQL" is not true. Many people sell their database as a challenge to relational ones, but most databases are built for very specific problems (L-0002). Don't say "non-relational" or "NoSQL": name the exact type, instead of lumping together everything that isn't MySQL, Postgres or Oracle (L-0008; the class compared it to calling people "non-technical"). "NoSQL scales" is wrong as a blanket statement: you can build a non-relational database that doesn't scale at all (L-0009). Cassandra, MongoDB and DynamoDB do scale, but each only for a specific workload (L-0021). The reason to learn the families is to know where each one fits, and where it doesn't (L-0010). The general distinction is that they are not relationally structured, although nothing stops you structuring them that way, which is why the space is messy (L-0012). The page follows the class's own rule: "NoSQL" appears only in this introduction (L-0011).
- **Components:** NotationKey (once, at the top of the chapter), Prose.
- **Words:** 450

### 1.2 Two meanings of consistency
- **Opens with:** "they give up consistency" is the usual one-line answer. Which consistency?
- **Key points:** as a very broad, "not always true" separation, non-relational databases give up consistency to get scalability (L-0013; hedge kept). There are two consistencies, CAP's and ACID's, and "computer scientists are bad at naming things" (L-0014). ACID consistency is about the data being correct: the database moves from one correct state to another (L-0015). CAP consistency is about a write being visible to reads right away, which is strong consistency. This is the one non-relational stores give up (L-0016, plus A-DC-02 as one sourced sentence: CAP consistency is linearizability, and a database can be ACID without it). The board says that "in most cases" they buy scalability and availability by compromising consistency (L-0017). Relational databases wanted all the data in one instance, so if that instance goes down the system is down (L-0018, plus A-DC-05: standby replicas keep a single primary available, and PostgreSQL streaming replication is asynchronous by default). Non-relational stores spread data over nodes, so other nodes still serve it and there is almost never complete downtime (L-0019). Most are eventually consistent, with exceptions, because nothing is standardised (L-0020, plus A-DC-03: DynamoDB is eventually consistent by default and strongly consistent on request).
- **Figures:** Fig 1·a "Two consistencies" (left: ACID, a state box moving from one ✓ state to the next ✓; right: CAP, write to node 1, then a read from node 2 is either the new value (strong) or the old one, in red (eventual)). Fig 1·b "One instance vs spread out" (left: one cylinder crossed red, "everything down"; right: three cylinders with one crossed and two still serving, in green).
- **Words:** 600

### 1.3 Relational databases scale too
- **Opens with:** so is the review comment's premise, "SQL doesn't scale", at least right?
- **Key points:** it is "a very big misconception" that relational databases don't scale; you need to know how to use them. Board box: "NoSQL DBs scale does not mean SQL does not → anything that shards, scales" (L-0022, plus A-DC-06: Vitess shards MySQL across many instances and served all of YouTube's database traffic). Lecture 03's key-value store sharded keys A–M and N–Z onto two databases. It gave up consistency to get a nearly highly available, horizontally scalable system, which is exactly what non-relational databases do (L-0023). Give up the constraints that stop horizontal scale and you have a horizontally scalable relational database. Saying only non-relational databases scale is crude (L-0024; the 00:42 restatement, "don't use foreign keys", is in 5.1). RuleBox §1 closes the chapter (L-0025).
- **Figure:** Fig 1·c "Anything that shards, scales" (Lecture 03's A–M / N–Z router redrawn small, with a `MySQL` label on both shards).
- **Hand-off:** to chapter 2. If the label is not the point, what is? How each family lets you touch the data.
- **RecallQuestions §1:** (1) Which "consistency" do non-relational databases usually give up, and how is it different from the C in ACID? (2) Give the class's counter-example to "relational databases don't scale". (3) Someone says "Cassandra scales". What question should you ask back?
- **Words:** 450

## 2 · Documents and key-value stores
**Section dek:** two families defined by how you may touch the data: query inside a document, or only ever get and put by key. The restriction is what buys scale.
**Sec-meta:** about 12 min · class 00:08–00:15, Q&A 00:47–00:53
**Opening problem (page's framing):** each Slack user has a settings blob: theme, timezone, notification rules. Store it as a document you can query and patch, or as one value under the key `user_id`?
**RuleBox (§2):** "The more complex the queries, the less you can distribute the data." (L-0045). Box body: key-wise access never crosses shards, so it can be split thousands of ways. Sketch: a single `GET k` arrow hitting one shard, beside an `IN (1,2,3)` arrow fanning out to three (Fig 2·b, tiny). Sits in 2.3.
**Estimated words:** 2,200
**Q&A folded in:** MongoDB ACID, "use it sparingly" (00:50:04) → 2.2. A graph DB is "basically a KV store", plus the NAND gate (00:47:44) → 2.4 MarginNote. KV on SQL or not, KV as an access pattern, Redis vs DynamoDB engines (00:51:20–00:51:49) → 2.4. Picking a KV store (00:52:14) → 2.4. "Do they all scale the same?" and 4 MB blobs (00:52:44–00:53:04) → 2.4 + SN-01.

### 2.1 Document databases
- **Opens with:** Lecture 03's KV store kept its value as JSON, and the next wish was to query inside that JSON.
- **Key points:** that wish is exactly what a document database gives you (L-0028). Document databases are the family closest to the relational world. Famous examples are MongoDB and Elasticsearch (L-0027; "closest" is the lecture's view). They are mostly JSON, with no hard rule (L-0029). They support complex queries: aggregations in MongoDB, faceted queries in Elasticsearch (L-0030). You can query on attributes, e.g. "all documents with this attribute set to this value" (L-0033). You can update just one attribute of a document (L-0034). Not quite as powerful as relational, but close, so teams moving a relational schema off SQL usually adopt a document database and almost never jump straight to a key-value store (L-0031).
- **CodeBlock:** `db.users.find({ "settings.theme": "dark" })` and `db.users.updateOne({ _id: 7 }, { $set: { "settings.tz": "IST" } })` (query on an attribute; a partial update).
- **Figure:** Fig 2·a panel 1 "Partial update" (a document with one field highlighted blue and changed in place).
- **Words:** 450

### 2.2 The lines are blurry
- **Opens with:** where does "document" end and "key-value" begin?
- **Key points:** DynamoDB is a key-value store, not a document database, yet it lets you query within the document (L-0036; **inline clarification**: it supports both models, filters run after the read, and an efficient query needs the key or an index, A-DC-08). There is no line between document, key-value and columnar stores, because every database enters every other's space (L-0037). Understand the access pattern and the features (complex queries, partial updates), not the label (L-0038). Know which features you want and which database gives them. Generic claims fail because something true today can be false later (L-0039). MongoDB started out saying "we are BASE, not ACID". It is now ACID compliant, "maybe not as optimally as the SQL world" (L-0040). **Asked in class, answered here:** MongoDB's docs say to use that ACID sparingly. Cross-shard ACID runs as a distributed transaction, which slows throughput, so use it only when you need it (L-0136, paraphrase kept as a paraphrase, plus A-DC-10, MongoDB's own wording: a distributed transaction "incurs a greater performance cost over single document writes"). ACID within one shard anyone can guarantee. Cross-shard ACID needs distributed transactions, so avoid it when you need throughput (L-0137). The instructor recalls the same advice in WiredTiger's documentation (L-0138, unverifiable: attributed).
- **Components:** Prose. (No figure: the point is a habit, not a shape.)
- **Words:** 450

### 2.3 Key-value stores: one key at a time
- **Opens with:** the settings blob again, stored under `user_id`.
- **Key points:** examples are Redis, DynamoDB and Aerospike (L-0026, board). Every operation is key-wise: get, put, delete, insert a key, insert a value into the set at a key (L-0041). That is very restrictive: you never peek into the value, so it is only useful if your access pattern fits exactly (L-0032). The value is a blob, so updating it means read, update, write, with no partial update, while document databases typically allow one (L-0035, plus optional A-DC-09 as one sourced sentence: Redis hashes allow a field-level HSET). Because every operation names one key, a KV store shards easily: you never need a cross-shard query (L-0042, plus A-DC-07: Redis Cluster's 16,384 hash slots, with multi-key commands only within one slot). Cross-shard queries come from ranges or `IN`: "documents where id in 1, 2, 3" may hit three databases, which is very expensive (L-0043). So a KV store can run thousands and thousands of partitions without hiccups (L-0044). Document databases do support cross-partition operations, but they get really expensive (L-0046). Limiting access buys massive parallelism, because each database answers without waiting for the others (L-0047). RuleBox §2 (L-0045). "Every single thing is a trade-off: you get something, you lose something" (L-0048) leads into T1.
- **CodeBlock:** the five operations as `GET k` · `PUT k v` · `DEL k` · `SET k v` · `SADD k member`.
- **Figures:** Fig 2·a panel 2 "Read, change, write back" (the whole blob travels out and back, numbered ①②③). Fig 2·b "One key vs IN (1, 2, 3)" (three shard cylinders; `GET 2` hits one in blue, `IN (1,2,3)` fans out to all three with a red "expensive").
- **TradeoffTable T1** "Document vs key-value": columns Document (MongoDB, Elasticsearch) · Key-value (Redis, DynamoDB, Aerospike). Rows: what you can ask · update one field? · cross-partition queries · how many partitions · what you give up. The red ✕ goes on Key-value's "what you can ask": "only by key, never inside the value" (L-0049, L-0026, L-0048).
- **Words:** 750

### 2.4 Key-value is an access pattern
- **Opens with:** asked in class: does "no relations" decide whether a KV store goes on SQL or on a non-relational database?
- **Key points:** no. Key-value stores are in their own league. KV is an access pattern, and it does not define the store underneath (L-0139). DynamoDB and Redis are both key-value stores with different storage engines: Redis keeps data in memory, DynamoDB on disk (L-0140, plus A-DC-24: Redis can persist with RDB snapshots or an append-only file, and AOF loses about a second on a crash; back-link Lecture 01 §3). For a KV use case you can pick a specialised store such as DynamoDB or Redis if its features fit, and you may not need to build one from scratch (L-0141; back-link Lecture 03 §3). Whether a KV store on a relational database, DynamoDB or Redis scale the same depends on what you store, how you access it, the throughput, and how you partition. You can't treat a database as a black box (L-0142). Values of, say, 4 MB each would make relational databases "cry their heart out", while DynamoDB would cope better (L-0143) → **SourceNote SN-01**: DynamoDB caps an item at 400 KB, so multi-MB values go to object storage with a pointer in the database (A-DC-01).
- **MarginNote** "The NAND gate of databases" (from a graph-storage question): suggested in class, a graph database is "basically a KV store". The instructor agreed (L-0128) and generalised: just as every gate can be built from NAND, every database can be modelled on a KV store, though maybe not as fast (L-0129, plus optional A-DC-21: CockroachDB's SQL layer turns statements into key-value operations). Skip unless you like first principles.
- **Hand-off:** to chapter 3. Documents and KV stores differ in how you address data. The next family keeps the table and changes how it sits on disk.
- **RecallQuestions §2:** (1) Why can a key-value store run thousands of partitions when a document store struggles to? (2) A teammate wants to update one field of a 2 KB value in a plain key-value store. What actually happens? (3) "Redis and DynamoDB are both key-value stores, so they behave the same." What's wrong with that?
- **Words:** 550

**Estimated words:** 2,300
**Q&A folded in:** named columns in SELECT (00:26:00) → 3.2 + P1. Insert cost (00:26:38) → 3.3. Space and compression (00:27:20–00:28:52) → 3.4. Pricing (00:29:30–00:30:01) → 3.4 + SN-02.

### 3.1 Rows and columns on disk
- **Opens with:** `stock_ticks`, one entry per tick, for every listed stock.
- **Key points:** column-oriented databases exploit how people query the system, and the teacher is "personally a fan" (L-0050, plus A-DC-12: columnar is a storage layout, not a NoSQL family. BigQuery and Redshift are SQL warehouses, and Cassandra's "wide-column" is a different idea). In a row-oriented database a row's columns sit together, which is also how we draw a table (L-0051). The running example is `stock_ticks(symbol, price, name, exchange, timestamp)` (L-0052). In a row store the five columns of a row are stored one after another and persisted as one row, so even selecting two columns reads the whole row, and the engine then filters (L-0053). A column store keeps one column's values across many rows together: column 1's values, then column 2's, and so on (L-0054). A "very crude, very naive" mental model is one file per column, where line n holds row n's value (L-0055; the "naive" label is kept).
- **Figures:** Fig 3·a (D-01 redraw): the table header, then left "Row-oriented" R1–R3 as long strips, right "Column-oriented" c1–c5 blocks crossed by R1–R3 lines. Fig 3·b "One file per column" (five file icons, `price.col` … `ts.col`, line numbers down the side).
- **Words:** 500

### 3.2 One query, two layouts
- **Opens with:** the average price of the whole market for one day.
- **Key points:** the query is `SELECT avg(price) WHERE ts = '…'`. The board frames it as a 100-column table (L-0056). With about 10,000 listed companies there are about 10,000 rows for the date. A row store reads each row, picks out timestamp and price, and averages them (L-0057). It reads symbol, name and exchange for nothing. Even though they are not projected, the engine still skims them (board: "discarding 98 of them") (L-0058, plus A-DC-11's arithmetic: in Redshift's 100-column example, a query using five columns reads about 5% of the data). The engine must pass over them because it can't find the next row's columns without knowing where the row ends (L-0059). Data warehouses have thousands of columns, and the teacher says he is "not exaggerating" (L-0060). A column store reads two files, price and timestamp, and does no IO at all for the other three (L-0062). **Asked in class, answered here:** naming the columns in `SELECT` doesn't help a row store, because the disk still reads every column. A column store skips the files it doesn't need (L-0071).

### 3.3 Analytics, never the primary copy
- **Opens with:** so why isn't every database columnar?
- **Key points:** if your use case queries a few of many columns, the classic analytics query, column stores work well (L-0061). They power data warehouses such as Amazon Redshift and Google BigQuery (L-0063). Data-engineering file formats such as Parquet use the same layout so you read the bare minimum (L-0064). You can build a transactional app such as a blogging site on a column store, but you shouldn't: rendering a profile is a `SELECT *` over its 10–15 columns (L-0065). Transactional work fits rows. Analytics fits columns, because it picks two, three or 10 columns out of a thousand (L-0066 → RuleBox §3 and T2). Changing only how data is stored gives a massive boost without touching the layers above: "abstractions in the right place" (L-0068). Suggested in class: inserts are heavy in a column store. The teacher agreed, "you get some, you lose some", and said it is worth it (L-0072, plus A-DC-14: ClickHouse recommends batching inserts, 1,000 to 100,000 rows at a time). Column stores are never the primary database. The warehouse is never the primary copy (L-0073; **inline clarification**: "usually not the primary copy of transactional data"). The primary copy lives in MySQL, PostgreSQL, MongoDB or DynamoDB, and a job ingests it into the warehouse just for analytics (L-0074).

### 3.4 Compression and cost
- **Opens with:** asked in class: does a column store take more space or less?
- **Key points:** much less. Each column is homogeneous (timestamps are close to discrete values), so it compresses very heavily, while mixed rows compress less (L-0075). In the instructor's experience a 29x gain is normal (L-0076, unverifiable: attributed as his experience). Stock symbols are a small set of discrete values, so each can be stored as a small fixed-size code instead of the full string (the class said one byte, then four) (L-0077, plus optional A-DC-13: Parquet's dictionary encoding, then run-length encoding with bit-packing). Huffman, Snappy and LZ work well on such homogeneous data (L-0078). The engine compresses internally: you pass ordinary strings, and five or six distinct values fit in one byte (L-0079). Read about run-length encoding (L-0080). **Asked in class: per-operation pricing?** The class's answer: no, they run continuously, you pre-provision capacity and pay for the servers, with IOPS charged (L-0081) → **SourceNote SN-02**: it depends on the product. BigQuery on demand bills by bytes read, and Redshift Serverless by compute used (A-DC-15). A student put it as "reserved capacity", and the teacher agreed (L-0082; **inline clarification**: one pricing option among several, see the note above).
- **Figure:** Fig 3·d "Why columns compress" (a symbol column `AAPL AAPL GOOG …` becomes codes `0 0 1 …`, then a run-length line `0×2 1×1`).

### 4.1 What a graph database is, and the wrong instinct
- **Opens with:** follow/following, and the instinct to reach for a graph database.
- **Key points:** graph databases are among the most misunderstood. For follow/following people reach for one because it can be visualised as a graph, but it might not be the best choice (L-0083). A graph database is the graph from your college data-structures course: the adjacency list stored as is, with data APIs on top, "nothing special" (L-0084). Graph databases specialise in graph algorithms (L-0085), such as LinkedIn showing whether someone is a 1st, 2nd or 3rd connection, modelling social behaviour, or recommendations (L-0086). Using one whenever a use case can be drawn as a graph is "the worst way to think". Follow/following on a graph database "could be catastrophic", a strong word for "really expensive" (L-0087, the lecture's view, plus A-DC-17: Twitter kept its follow graph in FlockDB, which stored adjacency lists and listed multi-hop queries as a non-goal). They are hard to scale: memory hungry, mostly built on a legacy stack, and not very optimal even in modern languages (L-0088, the lecture's view). That doesn't mean avoid them: when you need core graph algorithms, use one (L-0089 → RuleBox). Storing follow lists in one is like using the Hulk to open a glass jar (L-0090).

### 4.3 Fraud detection in 200 ms
- **Opens with:** the instructor's card payment that was confirmed by phone before he could put the phone down.

### 4.4 Graphs versus joins, and where a graph database sits
- **Opens with:** asked in class: why not just do this on a relational database?
- **Key points:** finding something three levels deep is one traversal in a graph. In a relational database N levels deep needs N self-joins, and the query must be rewritten for each depth (L-0132) → **SourceNote SN-04**: one join per level holds for a fixed-depth query, but `WITH RECURSIVE` walks any depth in one SQL query (A-DC-16). N self-joins may not be optimal on huge data (L-0133). The class added that a relational database keeps its data on one node, and graph databases give you sharding out of the box (L-0134, a low-confidence ledger row, quoted lightly) → **SourceNote SN-05**: most graph databases scale reads with replicas but keep a single writer per graph (A-DC-19: Neptune has one primary and up to 15 readers). Asked how a graph database stores adjacency lists of varying size: in its storage engine, serialized on disk, bluntly a comma-separated list of ids (L-0127; the "NAND gate" answer that followed is in 2.4, L-0128). **Where it sits:** a graph database isn't used transactionally by user-facing apps. You ingest into it asynchronously and derive something from it (L-0130) → **SourceNote SN-03**: Neo4j and Neptune are ACID and do serve online queries, so "fed async" is common for analytics, not a rule. A student added that applications often build these models on top of relational or non-relational stores, and the teacher said "Correct" (L-0131). **From practice:** one learner's multi-level-marketing hierarchy was getting painful in a relational database, and a graph database made sense for 3rd-, 5th- or 10th-level lookups (L-0393). Ten levels is nine self-joins, which is messy (L-0394; SN-04 applies). **Products** (board list): Neo4j, one of the first, "not the best" (L-0104). Neptune, from AWS, which "copies everything" (L-0105). Dgraph, written in Go. It works well up to a moderate scale and falters at high scale in the instructor's use, and it was how he learned Go (L-0106). BadgerDB, Dgraph's embedded store (L-0107). TigerGraph, proprietary and used by many financial companies (L-0108).

## 5 · Why they scale, and when to pick SQL
**Section dek:** no relations means no checks, so the data can spread out. Every database has a backstory, and there is a broad rule for choosing between correctness and ingestion.
**Sec-meta:** about 7 min · class 00:40–00:47
**Opening problem (page's framing, the teacher's own question at 00:40):** Slack's tables (users, channels, membership, messages) are relational in shape. Why do people say non-relational databases scale, and does that mean Slack needs one?
**RuleBox (§5):** "When correctness and consistency matter and you want the tooling out of the box, pick SQL. For a very high ingestion rate and sharding out of the box, pick a non-relational store." It is "a very broad" rule (L-0125). Sketch: a balance with ACID ✓ on one pan and a fire-hose ↓ on the other. Sits in 5.3.
**Estimated words:** 1,500
**Q&A folded in:** none in this stretch. The class's own Slack decision is in 7.1, and the page links to it.

### 5.1 No relations, no checks
- **Opens with:** the teacher's question: why do they scale?
- **Key points:** because there are no relations (L-0109; the board adds two reasons not spoken: data can be denormalized, and it is modelled to be sharded). A non-null foreign key means you can't insert a row whose parent doesn't exist (L-0110). On delete, the parent can't go until its children are gone (L-0111). Enforcing relations and constraints is how relational databases keep correctness and strong consistency (L-0112). Non-relational databases don't enforce relations and don't care what you insert (L-0113). The limit on scaling a relational database is that these guarantees need all the data in one place. Non-relational stores don't offer them, so they aren't bound by it (L-0116). Drop the foreign keys and you can partition a relational database exactly the same way (the 00:42 restatement of L-0024; link to 1.3).
- **Figure:** Fig 5·a "What a foreign key checks" (insert: a child row with a missing parent rejected in red; delete: a parent with children blocked in red; to the right, the same rows on two shards, where the check would have to cross machines).
- **Words:** 500

### 5.2 Every database has a backstory
- **Opens with:** so did relational databases choose wrong?
- **Key points:** relational databases chose correctness because their first use cases were financial, where correct data mattered more than scale. They chose consistency over a high ingestion rate, and that doesn't make them worse (L-0114, told as the lecture's backstory, unverifiable). Every database has a backstory that explains its design, so know it (L-0115). When a database claims to be great at something, ask why and what it gave up, and see if you can mimic that on the database you know, SQL or not (L-0117). Never be stuck on one technology ("every other database sucks"): every database has its own flavour, so look beneath the fancy UI (L-0118).
- **Words:** 300

### 5.3 SQL or NoSQL?
- **Opens with:** "the biggest question of all time".
- **Key points:** SQL's strength is correctness. If correctness is your most important feature you need ACID, and if you need ACID, go SQL (L-0119; board: ACID, relations and constraints, fixed schema). SQL gives you the tooling (foreign keys, check constraints) to keep data from going wrong, but you have to apply it (L-0120). Use a non-relational store when you have gigantic data to ingest fast: messages on Instagram, posts, logs, metrics (L-0121). Such workloads don't optimise for correctness: a missing attribute or a lost datum is acceptable (L-0122; **inline clarification**: they relax constraints and cross-node consistency, but durability is still expected, as in Cassandra's commit log, A-DC-23). Cassandra suits fast ingestion: sharding out of the box, constraints dropped, light on the database (L-0123; 7.1 picks it for Instagram Messenger). Messaging, live interactions and polls usually live on non-relational stores for the same reason; with SQL you'd build the sharding yourself (L-0124). RuleBox §5 (L-0125). Board: use a non-relational store when there are no relations, data can be denormalized, and it can be sharded (L-0126).
- **TradeoffTable T3** "SQL or a non-relational store": columns SQL · Non-relational. Rows: what it guarantees · tooling out of the box · sharding · good for · board's "use when". The red ✕ goes on the non-relational column's "guarantees": "no relations enforced, usually eventual" (L-0119, L-0121, L-0125, L-0126).

### 6.3 Where do direct messages go?

### 6.4 A DM is a channel with two people
- **Opens with:** the last draft's good half.
- **Key points:** model a direct message as a channel with two people. It piggybacks on channels and messages instead of special-casing DMs (L-0168). This is how Slack's API works: to DM someone you first create a channel with them, and the UI renders it as a DM (L-0169, plus A-SRW-01: every channel-like thing is a conversation, a DM is `is_im`, and `conversations.open` returns its channel id). In the end a DM and a channel message are both a message with a sender and a receiver. Only the rendering differs (L-0170). Always look for a general way to store things. "Ifs and elses are the worst when it comes to databases" (L-0171). The channel gets a `type` (group, user/DM, regular). Messages carry a `channel_id`, and the type lets the UI put DMs in the bottom half of the sidebar and channels in the top half (L-0172). Messages carry `created_at`, so you scroll a channel's history through the channel (L-0173). The schema is `users`; `channels(id, org, name, type)`; `membership(user_id, channel_id, checkpoint)`; `messages(from, channel_id, created_at, msg)` (L-0174). A private channel can get more members later. A DM can't (L-0432). Two-person private channels, public channels and DMs can all exist, and a DM might become private or public one day, so the explicit type keeps the schema extensible (L-0433).

### 7.1 Which database holds the messages

### 7.3 Three ways to persist a message
- **Opens with:** one system, three guarantees.
- **Key points:** three types of communication can share one system. Depending on the guarantee you want, you pick one, because different guarantees shape the system (L-0204). The products are illustrations: Slack is "my hypothesis, I may be wrong", WhatsApp is hypothetical, and the point is the three types. The parts: databases, users, API servers (ordinary HTTP), an **edge server** (a WebSocket server holding users' connections) and a broker like Kafka (L-0205). **① Type 1, Slack:** a message is broadcast only after it is persisted (L-0206). Broadcasting unsaved messages might be fine for people chatting on Instagram, but it is a very bad experience for an enterprise app (L-0207). It costs credibility, because people can misquote you: "I received this message, see it right here" (L-0208). The flow: HTTP to an API server, which persists to the database and then hands the event to the WebSocket server, which delivers in real time (L-0209; left as taught, plus A-MLA-03: Slack's published send path is an HTTP call to its Webapp API, with fan-out through channel servers and gateway servers. Persist-then-broadcast stays the instructor's hypothesis). Send over HTTP, receive over the WebSocket (L-0210). Slack's users keep no copy of their own, unlike WhatsApp's (L-0213; this reason is read from context, so keep it tentative). **② Type 2, a hypothetical WhatsApp:** a WhatsApp message is stored on your phone. Suppose it also wanted a backend copy, which WhatsApp doesn't do (L-0211). Slack's synchronous route would be far too slow for a chat that must feel instant (L-0212). The "green line": over the WebSocket to the edge server, which sends to the recipient now and pushes onto Kafka. Workers store it later (L-0214). That's fine because the device already holds a copy (L-0215). The gains: no synchronous database call, batched writes, still real time (L-0216). It goes over the WebSocket because it must be real time and the connection is open (L-0217). Why not for Slack: Slack users refresh a channel and read from the database, so if persistence lagged 10 minutes, a user notified of a message would refresh and not see it (L-0218). "Different guarantees, different architecture" (L-0219 → RuleBox). **Asked in class:** could a message then arrive a day late? No. It is delivered now, and only storage is late: "not delivered, stored" (L-0389). If processing lags, the source of truth doesn't have the message yet, so a refresh hides a message the user already saw (L-0390). **③ Type 3, Zoom chat:** no persistence, only real time. Whoever is connected at that moment gets it (L-0220; left as taught). Leave the meeting and come back, and the history is gone (L-0221; **inline clarification**: "by default; Zoom's optional continuous meeting chat keeps it", A-MLA-12). Pick by the level of persistence you need, and don't be ingrained that there's one way, such as "the WebSocket is open, so send on it" (L-0222). **The recap** names the three by persistence: synchronous, asynchronous, none (L-0318; the board's colours, white Slack, green WhatsApp, blue Zoom, are kept as a caption, see Marker colours). **Said up front, as in class:** chapter 9's final diagram uses the type-2 path on purpose (L-0236 and L-0238 are in 7.5).

### 7.4 Keep the edge server dumb
- **Opens with:** one more reason not to send through the WebSocket.
- **Key points:** avoid database calls from the WebSocket (edge) server. It already handles a ton of TCP connections, and it is open to the internet, so a database connection string there is a security problem. If it goes down, all real-time traffic goes with it (L-0223). Direct database calls load that server, and you see where it falters once it is deployed (L-0224). Many companies never put complex logic on it. It relays messages and events, at most enqueueing into an asynchronous queue (L-0225). **Asked in class: "don't WebSockets offer persistence?"** A WebSocket gives a persistent *connection*, not database persistence, and database persistence is what Slack needs. Getting it through the WebSocket means the WebSocket server talks to the database, with the added load, the security exposure and the risk of breaking the real-time backbone (L-0231). The instructor never lets the WebSocket server talk to the database. At most it holds a Kafka connection string (L-0232). Edge servers are typically the most vulnerable servers you run (L-0233). Keep database credentials as safe as possible: on an edge server they are almost on the internet, while a Kafka string limits a breach. Database writes belong on a backend server (L-0234; chapter 9.4 and SN-10 return to this). Note the term: "edge server" here is not a CloudFront edge. It is the ordinary server holding the WebSocket connections (L-0235).
- **Components:** Prose. (Fig 7·c is reused: the edge server has no line to the database.)

### 7.5 Why not UDP, and ten ways to build it
- **Opens with:** a tempting idea suggested in class: send over UDP over TLS, which is lighter than HTTPS.
- **Key points:** the suggestion was to send over UDP over TLS and retry until the WebSocket confirms arrival. The answer: the guarantees are slim, retries go up, and the client ends up doing the broadcast (L-0226). The server should broadcast. If A sends to B over UDP, nothing tells B the message is there (L-0227). Weigh pros against cons. A micro-optimisation saves a little overhead but adds retries and complex client code, and in practice Slack shows plain requests with nothing fancy (L-0228; **inline clarification**: Slack's client sends with ordinary HTTPS API calls). Use UDP where dropping data is fine, not for something critical like Slack's message persistence (L-0229; left as taught, plus A-MLA-08: QUIC builds reliable delivery on top of UDP, so the point is that reliability must be added above UDP). Simple systems are harder to build, but simple systems scale. Complexity makes a system harder to debug, onboard onto, change and extend (L-0230). **Ten ways:** the asynchronous Kafka route works for Slack too. The final diagram (9.2) uses it even though the instructor prefers the synchronous route here (L-0236). With experience you see that every system can be built in 10 ways, and you pick by guarantees (L-0237). He deliberately keeps designs conflicting and never converges to one, so you weigh every decision (L-0238). There is no best way: three types of persistence and different communication and privacy options make "an entire buffet", and you build your own plate from the guarantees you give customers (L-0392).

### 8.3 The mesh, and its real cost
- **Opens with:** asked in class: what is the disadvantage of this architecture?

### 8.4 A real-time Pub/Sub in the middle
- **Opens with:** 100 servers, each linked to 99 others: "not a great idea! Can we do better?" (board, D-13).
- **Key points:** put a Pub/Sub in the middle, and each server opens one connection to it instead of one to every peer (L-0278, plus A-SRW-12 in a MarginNote "A ready-made version": Socket.IO's Redis adapter does exactly this, and since it doesn't authenticate messages, Redis must stay inside trusted infrastructure). It must be a real-time Pub/Sub such as Redis, not Kafka, which would slow it down (L-0279). The overhead drops to one: WS1 holds A–D plus one Pub/Sub link (L-0280). A real-time Pub/Sub sends a message to everyone subscribed *right now* (L-0281). It has zero persistence: unlike Kafka, it stores nothing and just pushes (L-0282). The flow: WS1 delivers to its own C1 members, then publishes, and the Pub/Sub pushes to every subscriber (L-0283). A server not connected at publish time misses that message, so there is no delivery guarantee, only "everyone connected now" (L-0284, plus A-SRW-10: Redis Pub/Sub is at-most-once, and Redis Streams persist when you need at-least-once). Redis is a great example (L-0285). **Asked in class: why Redis?** Any tool that gives real-time Pub/Sub would do, whether a cloud provider's service, a database or one you build. The requirement is the property, not the product (L-0369). The instructor picked Redis because he has built this exact system with it (L-0370, his experience). Persistence isn't needed here, and if a tool gives it, fine (L-0371). There's no expiry, because nothing is stored (L-0372). **Redis Pub/Sub vs Kafka**, asked in class: "kind of the same"? No (L-0384). "Kafka is asynchronous, that's it"? That isn't the difference either (L-0385). Kafka consumers pull, while Redis pushes to everyone connected (L-0386). Kafka keeps history, and Redis Pub/Sub keeps nothing (L-0387; left as taught, with a cell note in T5 that Kafka's history is a retention window). Neither is superior: Redis is better for real time and Kafka for persistence, so it depends on context (L-0388).

### 8.5 Redis channels for Slack channels
- **Opens with:** why should a C1 message go to WS3 and WS4 at all? It shouldn't.

Broadcasting every message to every server is wasteful. A C1 message should reach only servers with C1 members, such as WS2 with E and F, and not WS3 or WS4 (L-0287). When a server boots, it connects to the Redis Pub/Sub backbone and asks to subscribe to Redis channels ("Google Redis Pub/Sub") (L-0288). When a user connects and says "I'm in channel 1", the server fires `SUBSCRIBE` for that channel (L-0289). The server subscribes, not the user: the user has a WebSocket to the server, and the server has one TCP connection to Redis (L-0290). Example: A–D on WS1 are in C1, so WS1 subscribes to C1. WS2 (E, F) subscribes to C1 too. G and H are in C2 (L-0291). End to end: A → WS1 → B, C, D; WS1 publishes on C1; Redis pushes to WS2; WS2 sends to E and F (L-0292; the spoken "channel 2" slip is not repeated). Redis pushes to the subscribed server, which doesn't pull (L-0293). Per-channel subscriptions give cross-server delivery with minimal TCP overhead (L-0294). If one Redis seems too little, run a sharded cluster with intelligent balancing (L-0295; left as taught, plus A-SRW-11: in a Redis Cluster, classic `PUBLISH` reaches every node, so the cluster needs sharded Pub/Sub, `SSUBSCRIBE`/`SPUBLISH`, Redis 7.0+). ### 8.6 The Balancer
- **Opens with:** how did A get WS1's address in the first place?
- **Key points:** try to put users who share channels on the same servers (L-0296). A service on top tells the client where to connect. When the Slack app opens, the client asks "where do I connect?", gets an IP and connects (L-0297; board: purple "Balance Connectn"). It is like DNS, but not DNS: an ordinary service whose job is to balance connections (L-0298). Slack organisations of 200, 500, 10,000 or 20,000 employees are nothing for one WebSocket server, so a naive version assigns one server per organisation (L-0299). If an organisation is all on one server, its messages never touch Redis (L-0300). The service's job is to hand out servers so that as few messages as possible go through Redis (L-0301). The class named it the **Balancer** (generic name: orchestrator), and it is not a load balancer (L-0341). It tries to put a whole organisation on one edge server (L-0342), always returning the same IP to that organisation's users, so Redis carries only the worst case (L-0381). **"What if this server goes down? Oh my God, life ended. No."** Its users ask the Balancer again and get another server, and the Balancer notices the dead server and moves them (L-0302). After a failover an organisation may be split across servers for a while, and Redis carries those messages, which is perfectly fine (L-0303). It may also rebalance periodically, killing a connection so a user's traffic moves to another server, to cut Redis IO (L-0304). Summary: a real-time Pub/Sub (Redis, not Kafka) removes the extra TCP links, and one service hands out server IPs to minimise Redis IO. Be protective of that IO (L-0305). **A tempting idea, suggested in class:** a separate service telling each server where to send each message. A call per message is far too expensive and no longer real time (L-0376). Cache the users' data in that service? It is still a network call every time. You could build it, but for real time keep the routing information on the edge server itself (L-0377). A service just to say where to forward is overkill (L-0378). Work on fundamentals: for each roadblock, the simplest fix (L-0308). Add complexity and the system stops scaling (L-0309).

### 9.1 One WebSocket per product
- **Opens with:** a page with a live chat, a notifications badge and a typing indicator. One socket or three?
- **Key points:** the key element of any real-time communication is a socket, a persistent connection, and for text that is a WebSocket. The board: "Every user will have 1 websocket connection open with our backend infrastructure and that will be used for anything and everything realtime" (L-0319). The class called the fleet users connect to over WebSockets **edge servers**, just a persona (L-0323). Any service, such as chat or notifications, that wants to reach users in real time goes through the edge servers (L-0330). **The class's reason, kept and then corrected:** clients limit concurrent TCP connections to one domain, to six from a browser (L-0320; **inline clarification**: this is the HTTP/1.1 per-host limit, and HTTP/2 multiplexes every request over one connection, A-SRW-09). Browsers enforce it so people can't abuse it, since otherwise "you could easily do a DDoS" (L-0321; **inline clarification**: mainly to be gentle with servers and the network, not as a DDoS defence). The class gave six for Chrome and eight for Firefox (L-0322). A WebSocket is a persistent TCP connection, so it permanently takes one of the six, leaving five for API calls, images and videos (L-0324). With 100 images, the browser loads 6 at a time, then 5 with one WebSocket open and 4 with two (L-0325). Even 100 parallel requests go six at a time (L-0326; **inline clarification**: over HTTP/1.1) → **SourceNote SN-07** after L-0325: both browsers allow 6 per host, and WebSockets sit in a separate pool (Chrome 255 per host, Firefox 200), so an open WebSocket doesn't slow image loading (A-SRW-08). The note adds that the advice stands for other reasons: each extra socket is another long-lived connection for the server and more reconnect handling for the client. **The rule stands:** every good product has just one WebSocket, and everything real-time goes through it. You can have many, but it isn't recommended (L-0327; left as taught, the reason as corrected). On Instagram, live chat messages and the live-video heart animation would all go over one connection (L-0328, unverifiable: the lecture's illustration). A WebSocket per real-time feature is "the worst way to build a system" (L-0329; left as taught, and SN-07 says the browser reason doesn't hold). **Asked in class:** the six are per host name, so chat.google.com, Gmail and Meet each get six (L-0434; left as taught, with the fact-check's clause that tabs open to one host share them).

### 9.2 The overall architecture
- **Opens with:** the final board page, D-11.
- **Key points:** the overall architecture has normal API servers, a partitioned database, and clients holding WebSockets to edge servers (L-0335). For Slack it would go the synchronous way of 7.3 (L-0338; board D-12: "1. Persist message in Kafka 2. Find B in the local pool 3. Send message to B"). There is a clear split: a normal messaging service handles HTTP requests such as loading messages, scrolling history and muted channels, and everything real-time goes over the WebSocket (L-0339; board: "anything related to messaging that is NOT 'pushed'"). **Why the diagram uses Kafka when Slack was drawn synchronous:** the conflicting implementation is deliberate, to keep minds open. This one architecture (async persistence, a storage layer, a partitioned database, a real-time Pub/Sub between edge servers) covers almost every messaging system. ### 9.3 When a real-time message is lost
- **Opens with:** Redis keeps nothing. What if a push doesn't arrive?
- **Key points:** the board's insight: messages, once sent, will always be persisted, with no database runtime errors such as a unique-key failure (L-0332; left as taught, plus A-MLA-09: Kafka may redeliver after a crash, so inserts keyed by message id make redelivery a harmless overwrite). Because Redis Pub/Sub has no persistence, only those connected at that moment get a message, so one can be lost in real time (L-0344). **Asked in class:** in this system, persistence is guaranteed but the real-time notification is not. For an enterprise, guaranteed persistence is the part that matters, and the user sees the message on refresh (L-0379). A message not delivered in real time must not stay missing: when the channel is clicked, the client loads it through the channel-scroll REST API (L-0333). For transient misses the board lists (1) a correction job that ensures messages are shown, and (2) buffering messages in another Kafka and replaying them when sockets are back (L-0334). The concrete version: a small JavaScript thread periodically fetches the channel's last 50 messages and renders any it missed, mimicking a notification (L-0345). WhatsApp's "checking for new messages" looks like this pattern: after a new WebSocket connection, the client checks the backend for anything to fetch (L-0346, unverifiable: the lecture's reading).

### 9.4 Exposing the edge servers
- **Opens with:** asked in class: what is an edge server, and is it okay to hand its IP to clients?
- **Key points:** edge servers are ordinary WebSocket servers, e.g. a Node.js process running Socket.IO (L-0352). You can expose their IPs directly, and many people do, or put them behind a load balancer (L-0353; left as taught, plus A-SRW-15: Slack itself terminates WebSockets on Envoy proxies in regions near users). **From practice:** an interviewer told one learner that exposing server IPs invites misuse. The instructor's view is that interviews don't know real-world systems, and big companies expose their edge servers' IPs (L-0354; **inline clarification**: exposing them is a legitimate option, Slack itself uses proxies, and the interviewer's concern is a fair trade-off to discuss, the lecture's view kept as its view). A load balancer adds a hop. In the instructor's experience each relay hop adds about 3–5 ms, so for ultra-low latency, such as live class streaming, expose the IPs, and elsewhere a load balancer is fine (L-0355, unverifiable: attributed). Behind a load balancer, WebSockets are always sticky: one connection from the user to the load balancer and another to a server (L-0356; left as taught, plus A-SRW-19: an L4 balancer such as NLB forwards one connection, pinned to a target, without terminating it). An exposed edge server faces many threats, so it is hardened and security-reviewed: route tables changed, ports hidden, SSH blocked (L-0357). **Never put credentials on a server exposed to the internet.** The edge server has zero database credentials and never talks to the database (L-0358 → RuleBox body line; left as taught, see SN-10). It holds only something safe to push with, a Kafka connection string, and that Kafka is internal (L-0359). Asked again later: keeping it public is fine because nothing sensitive is on it, just the route from the Balancer, TCP connections and one Kafka string that "holds no secret" and only pushes (L-0383) → **SourceNote SN-10**: give the edge a least-privilege, write-only Kafka credential. Losing it is far less damaging than losing database credentials, but it is still a secret (A-SRW-16). With nothing critical exposed, the worst an attacker can do is a DDoS, which a simple rate limiter prevents (L-0360) → **SourceNote SN-09**: rate limiting handles some request floods, while volumetric attacks need upstream DDoS protection (A-SRW-18). There is no rule that WebSockets must sit behind a load balancer. If you can secure a public server you're fine: know the guarantees and keep it simple (L-0361). Public means attackable, and a load balancer adds about 5 ms. If that's acceptable use it, otherwise stay public; both are fine (L-0382, unverifiable: the instructor's estimate). **Trusting the client's membership** (asked in class: what about bad actors once private channels exist? L-0373). If edge servers trust the client's channel list, a user can falsely claim "I'm in this channel, give me everything". The instructor called it a man-in-the-middle attack and said he designed it this way on purpose to provoke the question (L-0374) → **SourceNote SN-08**: this is broken access control (OWASP A01), and membership must be checked server-side, denying by default (A-SRW-17). Relying on the client is one option. A private edge server could instead pull membership from the backend API, which a public one can't (L-0368). If membership is critical, as with private channels, don't trust the client: use a backend membership check, put the edge server behind a load balancer, and let it call an API (or the database) for channel information (L-0375).

### 9.5 Durability, and a shared database
- **Opens with:** a database node dies in the middle of a write. Is the message gone?
- **Key points:** asked in class, assuming master-slave replication: this store is just sharded. Replicas are optional, and the instructor saw no need for them there (L-0420; left as taught, and the next point corrects it). To avoid losing a write when a node dies mid-write, important data uses standby nodes and a replication factor of three. Each write goes to three data nodes, and if one dies another serves the data, as DynamoDB does internally (L-0421). Once workers have processed messages from Kafka, you can't recover a lost write by reading Kafka again (L-0422) → **SourceNote SN-11**: Kafka keeps consumed events until retention expires, so a consumer can rewind and reprocess. Still, the database's own replication is what should guarantee the write (A-DC-20). A tempting idea, suggested in class: the workers themselves write each message to two or three instances across regions. That is worse. The replicated database's storage engine does it, writing to one node that replicates to the others (L-0423). A replicated database never acknowledges a write until it is in three places, so a write lost before replication was never accepted. When you write to DynamoDB, it completes on three storage nodes before reporting success (L-0424) → **SourceNote SN-12**: a synchronously replicated database acknowledges once the configured replicas, often a majority, have the write. DynamoDB acknowledges at 2 of 3, and asynchronous replication acknowledges earlier and can lose recent writes (A-DC-04). Also suggested in class: the worker holds the message until the database commits, retries otherwise, and reprocesses if it dies. Only the "the database acknowledges to the worker" part was confirmed (L-0425). **Sharing a database** between workers and API servers is perfectly fine. Making workers call the API so the API writes adds a pointless network call (L-0426). The instructor dislikes the anti-pattern that every microservice needs its own database. He favours performance and cost and is happy to share (L-0427; the lecture's opinion, left as taught, plus A-DC-22: microservices.io lists what database-per-service buys and what sharing costs). Business and product come first and engineering second, because the business keeps engineers employed (L-0428).

### 10.2 Who said messages arrive in order?
- **Opens with:** asked in class: chat needs exactly-once delivery and strict ordering, doesn't it?
- **Key points:** who said exactly-once is needed here? Nobody required it (L-0404). Nothing says messages must arrive in strict on-screen order: the front end can insert a message in the middle. Order matters where messages are processed one after another (L-0405). **Case 1:** A sends 1 then 2, and 2 reaches B first. Render them in arrival order, and a refresh fixes the order, because the order stored in the database is the source of truth (L-0406). **Case 2:** keep the front-end state (e.g. React) ordered by timestamp, and insert a late, older message in the middle instead of appending it, accepting a brief flicker if that is fine for the UX (L-0407). **From practice:** on Microsoft Teams one learner sees missing, duplicate or out-of-order messages that later reshuffle (L-0408, unverifiable: one learner's observation). This architecture explains duplicates: a system may broadcast first and persist later, or retry on the WebSocket server when it wrongly thinks a delivery failed (L-0409). In this lecture's design the message is stored first, and only then is anyone told it exists (L-0410). Order is fixed on refresh (the source-of-truth API) or by a background job, e.g. every minute fetch the last 50 messages, check they're all on screen, and reorder (L-0411). **Which clock?** The order is always the database's insertion time, by the database's clock (L-0412 → RuleBox body line; left as taught, plus A-MLA-11: Slack's message `ts` is unique per channel, one server-assigned order). A tempting idea, suggested in class: order by a client timestamp. Never rely on client time: "I can just change my clock to 1 January 1970" (L-0413). "Hey", "hi", "hello" are never sent at exactly the same instant anyway (L-0414). If latency delivers a later message first, that's fine: the database's order is the truth (L-0415). The overly complicated way to true ordering is CRDTs for merges plus a vector clock per client, persisted in the database (L-0416; **inline clarification**: a vector clock gives only a partial, causal order, so concurrent messages still need a tie-break, A-MLA-13). It isn't worth it: maintaining them and merging on read slows the whole system, and nobody re-architects for one edge case (L-0417). Vector clocks are the answer if you truly need it, but a globally consistent one per client is a massive problem, so look up an implementation to see (L-0419). RuleBox §10 (L-0418).
