## Notes (sourced)

- **L-0038** imprecise/medium: How CDC reads depends on what the database exposes: MySQL's binlog, PostgreSQL's logical decoding and MongoDB's change streams (replica sets only) give a log; stores without one, like Elasticsearch, can only be re-scanned. (https://debezium.io/documentation/reference/stable/connectors/mongodb.html, https://docs.airbyte.com/integrations/sources/elasticsearch, https://debezium.io/documentation/reference/stable/connectors/mysql.html)
- **L-0077** outdated/low: PGSync is a CDC tool that syncs to Elasticsearch/OpenSearch via PostgreSQL logical replication. As of its GitHub README checked 2026-10-13, it also supports MySQL and MariaDB (via the binary log), so 'only works with Postgres' no longer holds. (https://github.com/toluaina/pgsync)
- **L-0104** wrong/medium: When memory runs out, malloc returns NULL (or, with Linux overcommit, the OOM killer kills the process later); a segfault only happens if the program then uses an invalid pointer such as that unchecked NULL. (https://man7.org/linux/man-pages/man3/malloc.3.html, https://man7.org/linux/man-pages/man7/signal.7.html)
- **L-0149** imprecise/medium: Linked-list LRU costs pointers per key; Redis avoids it by sampling, while caches such as Memcached accept the overhead and keep doubly linked LRU lists. (https://raw.githubusercontent.com/memcached/memcached/master/doc/new_lru.txt, https://dev.mysql.com/doc/refman/8.4/en/innodb-buffer-pool.html, https://redis.io/docs/latest/develop/reference/eviction/)
- **L-0182** wrong/medium: HTTP/1.1 reuses TCP connections by default (keep-alive); its overhead for a cache is the text request line and headers on every call and one outstanding request per connection, not a new handshake per request. (https://www.rfc-editor.org/rfc/rfc9112, https://www.rfc-editor.org/rfc/rfc9293)
- **L-0206** imprecise/medium: Over TCP the usual choices are HTTP/1.1 (text, keep-alive connections), gRPC (HTTP/2, binary Protobuf, multiplexed) or a custom binary/text protocol like Redis's RESP. (https://www.rfc-editor.org/rfc/rfc9112, https://github.com/grpc/grpc/blob/master/doc/PROTOCOL-HTTP2.md)
- **L-0218** outdated/low: Redis's active expiry checks keys with a TTL in small batches (20 per loop) and keeps going while more than about 10% of checked keys are expired, within a CPU time budget. (https://raw.githubusercontent.com/redis/redis/unstable/src/expire.c)
- **L-0237** imprecise/medium: Under memory constraints use approximated LRU/LFU: keep a few bits of access time or frequency per key and, on eviction, sample a handful of keys and evict the worst - as Redis does. (https://redis.io/docs/latest/develop/reference/eviction/)
- **L-0261** imprecise/medium: Redis Cluster nodes answer with a MOVED redirect naming the right node; a standalone Redis replica just refuses writes, and clients learn the master's address from Sentinel. (https://redis.io/docs/latest/operate/oss_and_stack/management/replication/, https://redis.io/docs/latest/operate/oss_and_stack/management/sentinel/, https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/)
- **L-0305** imprecise/medium: BitTorrent's trackerless mode uses a Kademlia DHT; the Internet's routing and Bitcoin's peer discovery are not DHTs. (https://www.bittorrent.org/beps/bep_0005.html, https://developer.bitcoin.org/devguide/p2p_network.html)
- **L-0311** imprecise/medium: DHTs can be used to build such services (Wikipedia lists DNS, instant messaging and file sharing as possible uses), but deployed DNS is a hierarchical delegated system, not a DHT, and IRC is client-server. True DHT examples: BitTorrent Mainline DHT, IPFS, Kad. (https://en.wikipedia.org/wiki/Distributed_hash_table, https://www.bittorrent.org/beps/bep_0005.html)
- **L-0326** imprecise/medium: Overgeneralised. Many databases reject a write on a replica with an error rather than returning the primary's address: a PostgreSQL hot standby errors on INSERT/UPDATE/DELETE, and a standalone Redis replica rejects writes. Drivers, Sentinel or connection strings find the primary. Address-returning redirects (Redis Cluster's MOVED) are one approach, not 'almost all'. (https://www.postgresql.org/docs/current/hot-standby.html, https://redis.io/docs/latest/operate/oss_and_stack/management/replication/, https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/)
- **L-0332** imprecise/medium: With virtual nodes the total data moved is still about 1/N; it just comes from (or goes to) many nodes instead of one neighbour. Dynamo treats that as a benefit: a failed node's load 'is evenly dispersed across the remaining available nodes', and a new node 'accepts a roughly equivalent amount of load from each of the other available nodes'. The real costs are operational: more streams to coordinate, and Cassandra notes higher outage probability with many tokens. (https://www.allthingsdistributed.com/2007/10/amazons_dynamo.html, https://cassandra.apache.org/doc/latest/cassandra/architecture/dynamo.html)
- **L-0335** imprecise/medium: Virtual nodes are a trade-off for stateful systems: better balance and parallel rebuilds (Dynamo, Cassandra) versus more complex data movement and more nodes involved in each range. (https://www.allthingsdistributed.com/2007/10/amazons_dynamo.html, https://cassandra.apache.org/doc/latest/cassandra/architecture/dynamo.html)
- **L-0336** imprecise/medium: Virtual nodes do not increase the total data transferred when a node joins or leaves (still about 1/N of the data). They change where it comes from: many nodes in parallel instead of one neighbour. (https://www.allthingsdistributed.com/2007/10/amazons_dynamo.html, https://cassandra.apache.org/doc/latest/cassandra/architecture/dynamo.html)
- **L-0359** imprecise/medium: Exceeding a ulimit makes allocation fail (NULL/ENOMEM); exhausting system or cgroup memory gets the process killed by the OOM killer with SIGKILL; SIGABRT comes from the program calling abort(). (https://man7.org/linux/man-pages/man3/malloc.3.html, https://man7.org/linux/man-pages/man7/signal.7.html, https://man7.org/linux/man-pages/man3/abort.3.html)
- **L-0364** wrong/medium: With shared locks two transactions that both try to update the same row deadlock and InnoDB rolls one back; double-booking usually means the availability check used a non-locking read and the update did not re-check the condition. (https://dev.mysql.com/doc/refman/8.4/en/innodb-locking.html, https://dev.mysql.com/doc/refman/8.4/en/innodb-deadlock-example.html, https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html)
- **L-0365** imprecise/medium: UPDATE/DELETE in InnoDB act on the latest committed row versions even under REPEATABLE READ ('The snapshot ... applies to SELECT statements ... not necessarily to DML'). PostgreSQL READ COMMITTED re-evaluates the WHERE clause after waiting. An overwrite happens when the UPDATE has no condition on the seat's state (e.g. WHERE id = ?) after a stale snapshot read, not because the database skips re-evaluation. (https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html, https://www.postgresql.org/docs/current/transaction-iso.html)

## Inline clarifications

- **L-0018** simplified/low: Read-only access still exposes personal data to people who do not need it and lets heavy analytical queries slow down the production database.
- **L-0021** simplified/low: Every major data warehouse speaks SQL, and data lake table formats such as Iceberg are queried with SQL through engines like Spark, Trino or Athena.
- **L-0022** simplified/low: Fair as an aside: MongoDB's native query language is MQL, not SQL. But MongoDB does offer a read-only SQL-92-compatible SQL Interface (MongoSQL over JDBC/ODBC) for BI tools (as of Oct 2026; the legacy BI Connector reached end-of-life in September 2026), so 'no idea what to do' is not literally true; the PII and production-load reasons for a separate copy still stand.
- **L-0028** simplified/low: Publishing events from the API is common, but writing to the database and to Kafka separately is not atomic, so events can be missed; reading changes from the database (CDC or an outbox) avoids this.
- **L-0030** simplified/low: Both are open source. Debezium is a dedicated log-based CDC platform. Airbyte is a general data-movement (ELT) platform with a CDC mode for some database sources: Postgres, MySQL, SQL Server, MongoDB, Oracle, SAP HANA and Db2, as listed in the Airbyte docs checked October 2026. Airbyte runs CDC as scheduled syncs rather than a continuous stream. 'Easiest to set up' is the teacher's opinion.
- **L-0036** simplified/low: Reading tables row by row (query-based or polling CDC) works only incrementally if each table has a column like LAST_UPDATE_TIMESTAMP. It also misses hard deletes and intermediate updates between polls, and the polling queries add load. That is why log-based CDC is preferred where available.
- **L-0037** simplified/low: CDC reads the database's change log: PostgreSQL's WAL via logical decoding, or MySQL's binary log (a replication log separate from InnoDB's redo log).
- **L-0040** simplified/low: CDC resumes from its offset only if the log is still there. Debezium says that after a restart the connector 'continues reading the WAL where it last left off', and a PostgreSQL replication slot retains WAL during the outage, which can fill the disk. MySQL purges binlogs after a retention period. If the connector's position was purged, Debezium fails and needs a new snapshot.
- **L-0057** simplified/low: Streaming from the log is much lighter than polling queries. Two caveats: the initial snapshot that most tools run first (Debezium, Airbyte) does full table reads, and a PostgreSQL slot whose consumer is lagging or stopped makes the server retain WAL and catalog rows.
- **L-0058** simplified/low: You can usually point CDC at a replica to offload the primary: on MySQL the replica needs log_replica_updates (default on), and on PostgreSQL this needs version 16+.
- **L-0070** simplified/low: The contrast holds, but SSE is not 'front-end JavaScript'. It is an HTTP server-push standard: the server sends a text/event-stream response, and EventSource is the browser API that reads it. Both SSE and CDC push changes; SSE pushes from a server to a web page, CDC from a database to another system.
- **L-0072** simplified/low: The logs do hold committed transactions in commit order. MySQL writes the whole transaction to the binlog at COMMIT, and PostgreSQL decodes only committed transactions, between begin and commit callbacks. But CDC tools emit one event per row, so the sink does not apply the transaction atomically by default. Debezium can add transaction boundary events with provide.transaction.metadata, which defaults to false.
- **L-0073** simplified/low: Correct at the source: PostgreSQL decodes concurrent transactions 'in commit order', and the MySQL binlog is 'logged in commit order'. Downstream ordering is only as strong as the pipeline. Debezium's ordering guarantee is per topic, not across tables, so cross-table order can be lost unless the consumer reorders.
- **L-0103** imprecise/low: The student's guess is closer than the item suggests: under memory pressure the OS can page memory out to swap on disk. Running out of heap does not cause a segfault by itself (see L-0104). malloc returns NULL, or on Linux with overcommit the OOM killer ends a process when pages are touched.
- **L-0105** simplified/low: A segfault is an invalid memory reference inside your own address space: an unmapped or protected address such as NULL, freed memory or out of bounds. It is not memory 'allocated by someone else'; the OS isolates processes from one another.
- **L-0109** simplified/low: A system call is a trap into the kernel that costs the calling thread a mode switch (plus, here, reading and parsing /proc). It does not slow down the entire system. It is still too slow to run on every allocation, which is the real point.
- **L-0112** simplified/low: On 64-bit Unix systems (LP64), pointers are 8 bytes, so a {void *value; int type} struct is 16 bytes with padding, not 4. The point stands that sizeof covers only the wrapper, not the data it points to.
- **L-0115** imprecise/low: malloc returns memory from the process's heap, asking the OS for more (sbrk/mmap) only when its free memory runs out.
- **L-0116** imprecise/low: free marks the block reusable by the process's allocator; memory goes back to the OS only in some cases (heap trimming, large mmap'd blocks).
- **L-0122** simplified/low: Real zmalloc only does the accounting: it calls malloc, adds the size to used_memory and calls an OOM handler if malloc returns NULL. The maxmemory check and eviction are not inside the allocator. Redis runs performEvictions() 'before execution of commands'. The board version that evicts inside zmalloc is the teacher's simplified design.
- **L-0129** simplified/low: As a design this works. Redis does the same thing per command, not per allocation: before executing a command it checks memory and evicts keys until usage is back under maxmemory. Docs note a large command can still temporarily overshoot.
- **L-0139** imprecise/low: Redis packs type (4 bits), encoding (4 bits) and a 24-bit LRU/LFU field into one 32-bit word of each object header.
- **L-0143** simplified/low: In Redis the same 24-bit field is reused, but under LFU it is split: 16 bits of last-decrement time and an 8-bit logarithmic (Morris) counter that decays over time. It is not a plain ++ frequency count.
- **L-0147** imprecise/low: On a 64-bit machine each list node adds three 8-byte pointers, about 24 bytes per key before allocator overhead.
- **L-0150** simplified/low: Memory-constrained caches do use linked lists, for example Memcached's per-slab-class doubly linked LRU. Whether the per-key pointer overhead is worth it depends on item size and the accuracy you need.
- **L-0153** imprecise/low: Some do and some don't. Memcached (doubly linked LRU per slab class) and InnoDB's buffer pool (LRU list with midpoint insertion) use lists. Redis samples instead.
- **L-0154** simplified/low: Redis offers noeviction plus allkeys-/volatile- variants of LRU, LFU and random, volatile-ttl, and (since Redis 8.6) LRM. LRU and LFU are approximations: sample maxmemory-samples keys (default 5) and keep a pool of good candidates. The idea is not exotic.
- **L-0155** simplified/low: Zero overhead holds for a design that adds metadata only for LRU/LFU. In Redis the 24-bit lru field is part of every object header whatever the policy, so switching to allkeys-random saves CPU, not memory.
- **L-0157** simplified/low: True for a cache that drops per-key recency data when it uses random eviction. Redis keeps the lru field in every object anyway, so there the gain is speed rather than capacity.
- **L-0190** simplified/low: Worked against Flask's lenient dev server. Strictly, an HTTP/1.1 request MUST carry a Host header (a compliant server answers 400 without it), and the header section ends with an empty line (CRLF CRLF).
- **L-0199** simplified/low: gRPC runs over HTTP/2, so a connection stays open and is multiplexed. Messages are length-prefixed and usually Protobuf, a compact binary format. Message compression is optional (only with a grpc-encoding header), and HTTP/2 compresses headers. 'Very compressed' really means compact binary encoding.
- **L-0205** simplified/low: TCP's reliable, ordered delivery is the right choice. But TCP does not make the cache lose-proof: it only guarantees delivery while the connection is alive. Some caches do offer UDP; memcached documents a UDP interface.
- **L-0212** imprecise/low: In a C cache like Redis there is no garbage collector: the cleanup cycle calls free (via zfree), which returns the memory to the allocator immediately. Redis's active expiry runs in its main event loop (serverCron and between event-loop iterations), not as a separate process.
- **L-0217** simplified/low: Depends on access patterns. Redis docs say passive expiry 'is not enough as there are expired keys that will never be accessed again', which is why the active cycle exists.
- **L-0220** imprecise/low: Redis has no priority queue for TTLs, but it does keep an extra index: db->expires, 'Timeout of keys with a timeout set', a second table of the keys that have a TTL, which the active cycle walks. Redis docs note that setting an expire 'costs memory'.
- **L-0231** simplified/low: CAS is atomic because the hardware performs the compare and the write as one indivisible read-modify-write visible to all cores (e.g. x86 LOCK CMPXCHG). Context switching is not the issue; a single instruction cannot be interrupted midway anyway.
- **L-0233** simplified/low: Redis runs commands on one main thread, but it is 'mostly single threaded': background threads handle things like UNLINK lazy-free and fsync, and optional I/O threads (Redis 6+) do socket reads, writes and parsing.
- **L-0236** imprecise/low: Redis's LRU/LFU is not that deep. It samples a few keys (maxmemory-samples, default 5), evicts the one with the oldest access time (or lowest LFU counter), and since 3.0 keeps a pool of good candidates. The docs explain it in a few paragraphs.
- **L-0253** imprecise/low: IPFS and BitTorrent's DHTs (Kademlia) use iterative lookups. A queried node returns peers closer to the key, and the requester contacts them itself; nodes do not forward. That is closer to the 'redirect' way than to forwarding.
- **L-0283** simplified/low: Ring size depends on the hash: IPFS uses SHA-256 (0 to 2^256-1), Chord SHA-1 (2^160), and many libraries use 32- or 64-bit hashes. 2^128 is one example (e.g. MD5).
- **L-0293** simplified/low: With one copy per key, only the new node's successor (the next node clockwise) hands over keys; the predecessor keeps its range. With replication more neighbours are touched.
- **L-0304** simplified/low: Functionally yes: keys are partitioned across nodes. 'DHT' usually refers to decentralised peer-to-peer lookup systems (Kademlia, Chord). A proxied cache cluster is more often called a partitioned or sharded key-value store.
- **L-0317** imprecise/low: In standard terminology (Dynamo, Cassandra), owner + the next two nodes is a replication factor of 3: RF counts total copies, and the coordinator replicates to the N-1 clockwise successors.
- **L-0319** simplified/low: AOF logs every write and is replayed on restart, but it is not strictly write-ahead: Redis appends after executing commands. With the default 'appendfsync everysec' up to about one second of writes can be lost. AOF is off by default; RDB snapshots are the default persistence.
- **L-0324** imprecise/low: Sentinel does monitoring, failover and service discovery: clients ask Sentinels for the current master's address. It does not route reads. Open-source Redis has no built-in routing proxy. The teacher hedged.
- **L-0331** imprecise/low: A bigger hash range does not fix imbalance. Imbalance comes from having few random points on the ring, whatever its size, which is why Dynamo added virtual nodes. Teacher also said 2^120 for the 2^128 given earlier.
- **L-0334** simplified/low: True that a new node streams from many nodes. Cassandra lists 'many smaller pieces of data from more ring neighbors' and more repair operations as costs, but the same spreading avoids overloading one neighbour.
- **L-0339** simplified/low: Right that malloc reserves virtual memory and physical pages come on first touch. How far overcommit goes depends on vm.overcommit_memory: the default heuristic mode refuses 'obvious overcommits', so a single 40 GB request on a 4 GB machine usually fails, while mode 1 allows it and mode 2 forbids overcommit.
- **L-0341** imprecise/low: On Linux, touching more overcommitted memory than RAM + swap usually ends with the OOM killer terminating a process (SIGKILL), not a segmentation fault. A segfault would come from using a pointer whose allocation failed, for example an unchecked NULL. The teacher hedged this.
- **L-0343** imprecise/low: One log stream has one active reader (with a standby for failover); to run several active CDC instances, give each a separate slice of tables with its own slot/offset.
- **L-0344** simplified/low: The idea is right: each tool persists its position. The mechanisms differ: Debezium stores offsets in the Kafka Connect offsets topic, and Kafka Connect, not app-level remote locks, decides which worker runs a task. Airbyte stores the log position between syncs.
- **L-0353** simplified/low: Copying from many ranges is more coordination, but Dynamo and Cassandra use vnodes in stateful stores. 'Better not to use' is a preference, not a rule (see L-0335).
- **L-0354** simplified/low: Command execution uses one core, but Redis has background and optional I/O threads. The FAQ adds that CPU is rarely the bottleneck (Redis is usually memory or network bound) and suggests several instances per box.
- **L-0358** imprecise/low: Per-process limits (RLIMIT_AS/RLIMIT_DATA via ulimit) make malloc fail with ENOMEM rather than killing the process. Container/cgroup limits trigger the OOM killer instead. 'People generally don't use GNU malloc' is an overgeneralisation: glibc malloc is the default for most Linux programs, though Redis builds with jemalloc by default on Linux.
- **L-0360** imprecise/low: SIGABRT can be caught, but if the handler returns, abort() resets the default action and still terminates the process. The signal that truly cannot be handled is SIGKILL. 'Instruction pipeline is done' is not what SIGABRT means: it is 'Abort signal from abort(3)'.
- **L-0366** imprecise/low: REPEATABLE READ is InnoDB's default, but PostgreSQL defaults to READ COMMITTED, so it is not 'the most common' across databases.
- **L-0367** simplified/low: Percona is a company. Its Percona Toolkit (command-line tools for MySQL) includes pt-deadlock-logger ('Log MySQL deadlocks'). MySQL itself exposes lock state in performance_schema.data_locks.
- **L-0373** simplified/low: Servers do close idle connections: MySQL's wait_timeout defaults to 28800 s (8 h). Pools must validate or refresh connections rather than assume the server never closes them.
- **L-0374** simplified/low: Depends on the tool. Debezium writes once to Kafka, and any number of sink connectors read those topics. Debezium Server has a single sink type per instance. An Airbyte connection links one source to one destination, so fanning out means several connections, each reading the source (in PostgreSQL, one slot per consumer).
