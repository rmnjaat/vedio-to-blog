## Inline clarifications

- **L-0016** simplified/low: A single big JSON file has no index, so finding one word means parsing through the file. Streaming parsers avoid loading it all into memory, but it is still a full scan.
- **L-0030** imprecise/low: A zip of many folders is rejected because it is still many logical files, often compressed, so you cannot do a direct byte-offset read into the dictionary data.
- **L-0036** simplified/low: Good motivation, but the dictionary design (in-memory key index plus ranged GETs of single records) is a point-lookup key-value store, while Athena is a scan-based analytics engine. The shared idea is querying plain files on S3 without a database server. Athena does not work this way internally (see L-0035).
- **L-0037** imprecise/low: Lucene stores an index as one or more segments (each a set of files, optionally packed into one compound .cfs file), plus a segments_N file.
- **L-0045** imprecise/low: Scanning 0.5 TB per request is slow, wastes disk throughput and pushes drives past their rated workload, which reduces their reliability.
- **L-0046** simplified/low: Classroom rule of thumb. Indexing is the main tool for avoiding scans, but caching, denormalisation, better data layout and batching also speed up reads. The teacher mentions caching himself in L-0006.
- **L-0051** simplified/low: The comparison is correct: the index holds only keys and offsets, so scanning it is much cheaper than scanning the data. But offsets cannot be 4 bytes for a 1 TB file; they need 8 bytes (see L-0056). The index is still tiny, so the point stands.
- **L-0055** imprecise/low: Average English word length is about 4.8 letters in running text, but about 7-8 letters across distinct dictionary words.
- **L-0058** simplified/low: The index is roughly 170,000 x (word + 8-byte offset + 2) bytes, a few MB, which fits easily in RAM.
- **L-0073** simplified/low: Most file formats begin with identifying bytes and keep metadata that tells the reader where each part of the file lies; that metadata sits in a header at the start or, in many formats (ZIP, Parquet, PDF, MP4 by default), in a footer at the end.
- **L-0078** imprecise/low: Every PNG file starts with the same 8-byte signature (89 50 4E 47 0D 0A 1A 0A, which contains the letters 'PNG'), telling the decoder it is a PNG.
- **L-0084** simplified/low: JPEG/JFIF files are a stream of marker-identified segments (SOI FF D8, an APP0 'JFIF' segment, then image data); a still JPEG is one image, not a sequence of frames like video. In MP4 the index of where audio and video samples lie (the moov box) is usually written at the END by muxers unless moved to the front with 'faststart'. Audio tracks hold compressed coded audio, not a raw waveform.
- **L-0086** imprecise/low: Parquet also stores metadata that tells readers where each column chunk lies, but it keeps it in a footer at the end of the file (after a leading 'PAR1' magic number), not in a header.
- **L-0087** simplified/low: Right that JSON has no header or index: a JSON text is just a sequence of tokens (JSON-text = ws value ws), so finding a key means parsing sequentially. Streaming parsers can stop early and need not build the whole in-memory dictionary, but there is still no way to jump straight to an entry.
- **L-0088** imprecise/low: RFC 4180 allows an optional CSV header line (column names), signalled by the MIME parameter header=present/absent; that is a header in a different sense (column names, not metadata saying where sections lie). PDF does start with a '%PDF' version header, but its catalog is located through the trailer at the end of the file.
- **L-0110** imprecise/low: What is needed is networked storage that supports random (offset, length) reads - a NAS share, HDFS or an object store such as S3 all qualify.
- **L-0117** simplified/low: What is built is a read-only key-value store with point lookups. Calling it 'a database' is loose, because a database usually also provides concurrent writes, transactions, durability guarantees and query features. The teacher's point, that a database's core is a key-to-value lookup over files, is fair.
- **L-0121** imprecise/low: The update is a batch job triggered on a schedule (a cron job).
- **L-0139** simplified/low: Sortedness is needed for the merge-sort-style merge and to keep the output sorted. It is not strictly needed for a single linear pass. Because the changelog is small, you can load it into a hash map, stream the unsorted dictionary once, replace changed entries and append new words, also in O(n + m). The teacher's choice keeps the file sorted, which makes the merge natural and keeps the file ordered for the next update.
- **L-0153** imprecise/low: Overwriting the same S3 key is atomic (readers get the old or the new object, never a partial one). But you lose the old copy for rollback unless versioning is on, and existing indexes no longer match.
- **L-0157** simplified/low: On S3 a failed or interrupted upload does not damage the existing object. Single-key updates are atomic, so readers see the old or the new object, never a partial one. The real same-path risks are a file that uploads successfully but has corrupt content, and the stale-offset problem (L-0158). Overwriting also removes the old version needed for rollback unless versioning is enabled.
- **L-0181** imprecise/low: A plain text file does not carry an updated_at value in its content, as the teacher says. But S3 returns object metadata (ETag, Last-Modified) on every GetObject. A ranged GET can also be made conditional with If-Match, so the request fails with 412 Precondition Failed if the object changed. A server can therefore detect a stale index without an extra call per request. Rejecting per-request checks as polling and extra work is still a fair design choice.
- **L-0187** simplified/low: The arithmetic checks out (4.7 + 3 + 8 = 15.7; 15.7 x 171,476 = 2,692,173.2 B, about 2.7 MB or 2.57 MiB), and 171,476 is the OED Second Edition count of words in current use. Two inputs are optimistic. 4.7 is a running-text average (distinct words average about 7.6 letters). And if the 2x4 is two 4-byte integers (offset and length), the offset cannot address a 1 TB file; it needs 8 bytes (see L-0056). The order of magnitude, a few MB, is right.
- **L-0194** imprecise/low: Table formats like Apache Hudi build on the same idea: they keep indexes (record key -> file id) and partition layouts so huge data on cheap storage can be queried without scanning everything.
- **L-0208** simplified/low: Student proposal, rejected as taught. Note that real memtable/SSTable (LSM) engines do persist every write immediately - to a write-ahead log - before inserting it into the memtable; the memtable is not the only copy. The real difference from Bitcask is that LSM keeps sorted on-disk files rather than a full in-memory key index.
- **L-0210** simplified/low: Appends avoid seeks only while the disk serves just this write stream; gets (random reads) and merges on the same disk still move the head between the read location and the tail of the active file.
- **L-0235** imprecise/low: Some file systems cap file size (FAT32 at 4 GB), but modern ones allow many terabytes; the stronger reason for small files is that merge, compaction and index rebuild work file by file.
- **L-0247** simplified/low: Fine as the two core knobs of the naive design, but real Bitcask exposes many more: sync strategy, merge policy/window, fragmentation and dead-bytes triggers and thresholds, small-file threshold, expiry and others.
- **L-0249** imprecise/low: Appends approach the disk's sequential bandwidth, but every get still costs one random seek on a magnetic disk (Bitcask's guarantee is 'never more than one disk seek'), so random-read latency stays far behind SSDs. 'Almost as fast as SSDs' holds for writes, not reads.
- **L-0250** imprecise/low: SSDs do avoid mechanical seeks, but flash cannot be overwritten in place: it must be erased before rewriting, so random in-place updates cause garbage collection and write amplification. Sequential/append-only writes are still the flash-friendly pattern, which is why log-structured designs keep a real (smaller) benefit on SSDs.
- **L-0253** imprecise/low: Reading one byte at a time until a newline makes one call per byte (the OS page cache absorbs the disk reads), which is slow; a length-prefixed format lets you read the whole record in one go.
- **L-0260** simplified/low: CRCs (Postgres uses CRC-32C per WAL record) are the standard tool for detecting accidental corruption, but not the only one: other checksums and cryptographic hashes also work, and a CRC does not protect against deliberate tampering.
- **L-0277** simplified/low: Elasticsearch is more than an HTTP wrapper: each shard is a Lucene index and Elasticsearch adds distribution across nodes, replication and a REST API. The analogy works: Riak likewise runs a Bitcask per vnode and adds the distribution layer.
- **L-0280** imprecise/low: A useful heuristic but an over-generalisation: many high-throughput persistent systems do use append-only logs (WAL, commit logs), yet throughput also comes from batching, group commit, relaxed sync (e.g. Cassandra acknowledges writes before its periodic commit-log sync) and in-memory designs.
- **L-0294** simplified/low: ext4 does try to limit fragmentation (multi-block allocator, delayed allocation, spreading directories across block groups), but a growing file is not guaranteed contiguous room; files can still fragment.
- **L-0297** imprecise/low: Neither POSIX nor disks promise that a small header write survives a crash whole: Postgres notes a power loss can leave some 512-byte sectors written and others not, and an unaligned header can straddle a sector. The CRC design does not need atomic headers anyway: a torn header or value simply fails the CRC check.
- **L-0299** simplified/low: A ~20-byte header is unlikely to be torn, but not certain (it can straddle a sector boundary); the CRC check is what makes the design safe regardless.
- **L-0310** simplified/low: Merging two sorted files is linear, O(n + m). But the alternative to sorting is not necessarily O(n^2): with a small changelog in an in-memory hash map, one pass over an unsorted file is also linear (see L-0139). O(n^2) is the cost of the naive approach that scans the whole dictionary for each changelog word.
