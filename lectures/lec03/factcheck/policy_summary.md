## Inline clarifications

- **L-0022** imprecise/low: A static counter is a single process-wide variable (static storage, not heap) that every thread shares, so its increment must be atomic.
- **L-0028** simplified/low: 2^32 is about 4.29 billion only for an unsigned 32-bit integer; a signed 32-bit INT (the default in most databases and languages) tops out at 2,147,483,647 (about 2.1 billion). 2^64 (about 1.8 x 10^19) is effectively inexhaustible.
- **L-0033** simplified/low: Writing the counter to a file is not enough to survive a machine crash or power loss: the write may sit in the OS page cache. Only fsync() (or opening with O_SYNC/O_DSYNC) forces it to the device so it can be retrieved after a crash; that is also what makes each save expensive.
- **L-0054** imprecise/low: Strictly increasing means every new ID is larger than all earlier ones (gaps allowed); gap-free 1, 2, 3, ... is a stronger property usually called sequential or consecutive.
- **L-0060** imprecise/low: Time-sortable ID schemes put the timestamp in the most significant bits, so IDs sort roughly by creation time.
- **L-0064** simplified/low: In practice clock sync is a daemon (chronyd, ntpd, systemd-timesyncd) that runs continuously and disciplines the clock by gradually speeding it up or slowing it down, rather than a periodic job that resets it.
- **L-0073** simplified/low: Hedged correctly ('almost impossible'), but systems do provide globally increasing timestamps: Spanner's TrueTime gives monotonically increasing timestamps across all servers, and TiDB's PD hands out timestamps that never regress. They pay for it with coordination (a single elected timestamp oracle, or special clocks plus waiting). Uncoordinated generators cannot do it.
- **L-0081** imprecise/low: Strictly monotonic IDs across machines need coordination - a single (replicated) timestamp oracle or specially bounded clocks - which costs latency and availability; independent generators can only be roughly ordered.
- **L-0083** simplified/low: MySQL auto-increment values are unique and increasing, but not gap-free: values used by rolled-back transactions are lost, and with InnoDB's default interleaved lock mode concurrent inserts are interleaved.
- **L-0084** simplified/low: Unconfigured, yes. But MySQL provides auto_increment_increment/offset for exactly this (source-to-source replication), and Group Replication in multi-primary mode sets them automatically (increment 7, offset = server ID). You get uniqueness, not monotonicity.
- **L-0122** simplified/low: Simple, yes, but the single database is now a single point of failure for every service that needs IDs, so in practice it is replicated or run as a pair (Flickr ran two ticket servers for this reason). Range batching keeps it off the hot path, so a short outage is survivable.
- **L-0127** simplified/low: About 4.29 billion only for an unsigned 4-byte integer; a signed 32-bit INT stops at about 2.1 billion. Moving to 64 bits is the right fix.
- **L-0132** simplified/low: Right picture: a B-tree/B+tree index stores the indexed values plus a pointer to the row, managed by the database. What the 'row ID' is depends on the engine. In InnoDB (MySQL 8.4) each secondary-index record holds the primary-key columns and InnoDB uses that value to look up the row in the clustered index. PostgreSQL indexes point to a physical tuple location instead.
- **L-0135** imprecise/low: 16 bytes is 4x a 4-byte INT but only 2x a BIGINT, the realistic comparison (Snowflake-style IDs are 8 bytes). Index size also does not scale linearly with key size, because entries carry row pointers and page overhead (the teacher hedges this in L-0154). In InnoDB the primary key is repeated in every secondary index, so a long PK grows all of them.
- **L-0137** imprecise/low: The planner uses indexes to find matching rows cheaply; if the index covers every column the query needs it may never touch the table, otherwise it fetches table rows as it goes.
- **L-0138** simplified/low: Holds for covering/index-only plans. Otherwise table rows are read during execution too. Those reads are often RAM hits as well, because the buffer pool caches table data as well as index pages (InnoDB, MySQL 8.4).
- **L-0140** simplified/low: Index pages are loaded into memory on demand and cached, but they are not kept indefinitely. InnoDB caches table and index data as it is accessed and evicts least-recently-used pages when room is needed. At boot, MySQL 8.4 by default reloads only the most recently used 25% of pages, saved at the previous shutdown, not all indexes.
- **L-0141** imprecise/low: Size the database's memory cache (e.g. InnoDB buffer pool) to hold the hot indexes and data; RAM must exceed that, since the cache is usually at most ~80% of RAM.
- **L-0148** simplified/low: AUTO_INCREMENT works on any MySQL integer type. INT is 4 bytes (unsigned max 4,294,967,295) and BIGINT is 8 bytes; Flickr's ticket table itself uses bigint unsigned auto_increment. MySQL advises the smallest type that holds the maximum value you need. Once the type's upper limit is reached, the next insert fails.
- **L-0151** imprecise/low: Flickr launched on 10 February 2004 and was one of the most popular websites by 2007 (19th by Alexa rank), before Instagram's 2010 launch. 'Instagram of the 2000s' would be the accurate comparison.
- **L-0156** simplified/low: Rule of thumb from the teacher's experience. A more careful version sizes for the hot working set of indexes and data and leaves headroom: the buffer pool usually takes at most ~80% of RAM, so RAM must be larger than whatever you want cached.
- **L-0167** imprecise/low: A delete-then-insert in one transaction can be replaced by a single upsert statement (insert, or update the existing row if the key already exists).
- **L-0185** simplified/low: auto_increment_increment and auto_increment_offset are dynamic MySQL variables, so no process reboot is needed. Flickr did not reset at all; it lets the two sides drift ('this hurts no one').
- **L-0189** imprecise/low: Twitter's original Snowflake (2010) was 'a network service for generating unique ID numbers', a Thrift server in Scala, not in-process logic. The decentralised in-library pattern the teacher describes is valid and widely used; it just isn't how Twitter first deployed it.
- **L-0190** simplified/low: Twitter retired the open-source 2010 release (repo archived Sept 2021); the README says the internal version is a full rewrite on Twitter's infrastructure. Tweet IDs are still Snowflake-format 64-bit integers.
- **L-0197** simplified/low: Twitter's 41-bit time field counts milliseconds from a custom epoch ('millisecond precision w/ a custom epoch gives us 69 years'), not from 1970. The top bit is unused, so IDs stay positive as signed 64-bit integers (1 + 41 + 10 + 12 = 64).
- **L-0199** imprecise/low: In Twitter's original design the 10-bit 'configured machine id' identified a Snowflake server process (the README's 'up to 1024 machines'), not a tweet API server, because Snowflake ran as a separate service.
- **L-0200** imprecise/low: A fair design sketch, but Twitter's 2010 Snowflake was a separate network service the API tier called for IDs, not a function inside the API servers.
- **L-0202** imprecise/low: The 10-bit field caps Snowflake generator processes at 1024 ('gives us up to 1024 machines'), not tweet API servers. With Snowflake as a separate service, the API tier could grow independently.
- **L-0203** simplified/low: Layout right. Two details: 41 + 10 + 12 = 63, so one top bit stays zero to keep IDs positive. And the sequence 'rolls over every 4096 per machine (with protection to avoid rollover in the same ms)' - if 4096 IDs are used up within one millisecond the generator waits for the next.
- **L-0208** simplified/low: The core bit-packing is a few lines. A correct generator also has to wait for the next millisecond when the 4096 sequence values are exhausted, and handle the clock moving backwards (Snowflake refuses to issue IDs until time catches up).
- **L-0210** imprecise/low: The no-central-service benefit holds when the logic runs as a library (Sonyflake, Instagram's in-DB function). - **L-0211** imprecise/low: Twitter did run a separate Snowflake service (a Thrift server) and scaled it. What made it scale was that generator nodes need no coordination with each other.
- **L-0212** simplified/low: Twitter/X paginates timelines by tweet ID cursors (since_id for newer, max_id/until_id or a next_token for older), not by limit/offset.
- **L-0217** simplified/low: Limit-offset: SELECT ... WHERE user_id = ? ORDER BY id LIMIT 10 OFFSET 0, then OFFSET 10, 20 ...; without a unique ORDER BY the pages are not stable.
- **L-0222** simplified/low: This is right for the common engines: PostgreSQL, MongoDB and Elasticsearch docs all say deep offsets are costly, and that seek/range queries are the fix. 'Literally every database' over-generalises. How much offset costs and how much keyset helps depend on the engine and on whether an index matches the sort.
- **L-0225** simplified/low: Keyset (ID-based) pagination is not limited to plain table iteration. It works with WHERE filters and other sort orders when an index matches the filter plus sort columns, e.g. an index on (sale_date, sale_id) with a row-values predicate. Its real limits are a deterministic sort order and no jumping to arbitrary pages.
- **L-0227** simplified/low: ID-limit pagination needs comparable IDs; auto-increment, ObjectId and Snowflake IDs all compare, though time-based IDs are only roughly time-ordered.
- **L-0228** simplified/low: db.students.find({_id: {$gt: lastId}}).sort({_id: 1}).limit(10) (SQL: WHERE id > ? ORDER BY id LIMIT 10), repeated with the last id seen.
- **L-0233** simplified/low: This exactly describes an InnoDB clustered primary key, whose leaf pages hold the rows. In heap-based stores (PostgreSQL, non-clustered MongoDB) the database does an index range scan, then fetches each row: still roughly constant per page, but not one sequential scan of the data. 'Does not increase' is approximate, since log n grows slowly with table size.
- **L-0235** simplified/low: The advice is sound (use keyset for deep iteration, don't rewrite everything). The stated reason is too strong: see L-0234. Keyset does handle WHERE clauses when an index matches the filter and sort columns.
- **L-0237** simplified/low: Twitter's own Snowflake already used a custom epoch ('millisecond precision w/ a custom epoch gives us 69 years'), so the custom epoch is part of the original design, not a later improvement.
- **L-0238** simplified/low: 41 bits of milliseconds last about 69.7 years from whichever epoch you choose (Twitter: '69 years'). The gain equals the gap between 1970 and your epoch: about 40 years for a 2010 epoch, 45 for Discord's 2015 one. '35 years' is in the right range, but the general rule is 69 years from the chosen epoch.
- **L-0240** simplified/low: Sonyflake is Snowflake-inspired but uses a different layout: 39 bits of time in 10 ms units, 8-bit sequence and 16-bit machine ID. That gives a 174-year lifetime and 2^16 machines, but only 2^8 IDs per 10 ms per instance.

- **L-0248** simplified/low: Keyset/cursor pagination is efficient wherever the store can resume a scan from a key (B-tree tables, DynamoDB sort keys); hash-distributed layouts lose cheap global ordered ranges, not cursors.
- **L-0250** imprecise/low: Elasticsearch's from/size pagination is capped by default at 10,000 hits (index.max_result_window); beyond that use search_after with a point in time.
