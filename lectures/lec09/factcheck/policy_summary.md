- **L-0021** simplified/low: The simplest origin is publicly reachable; most CDNs can also authenticate to a private origin (e.g. CloudFront origin access control for private S3, or VPC origins).
- **L-0036** simplified/low: The CDN stores the response only if it is cacheable: origin headers (Cache-Control max-age/s-maxage, no-store, private) and the CDN's cache policy decide whether and how long. - **L-0053** simplified/low: Uploading AWS keys is how some third-party CDNs reach a private bucket, but AWS's own CDN needs no keys: with origin access control the bucket policy allows the CloudFront service principal (scoped to the distribution ARN) and CloudFront SigV4-signs every origin request.
- **L-0078** imprecise/low: Uploading directly to S3 removes a hop, so the upload servers no longer need bandwidth and capacity for every 5 MB image; on AWS the same-Region hop itself is usually not billed twice.
- **L-0082** simplified/low: GitHub's flow, as shown, is S3's presigned POST: a form POST with policy fields plus the file. The more common 'presigned URL' is a PUT URL where the signature is in the query string and the body is the raw file. Both are direct-to-S3 uploads.
- **L-0084** simplified/low: The backend signs a URL for a specific path with its own credentials and a short expiry; anyone holding that URL can upload to that path until it expires.
- **L-0085** simplified/low: The flow is right. The 'API call to S3' step is normally local signing by the AWS SDK with the service's credentials (bucket, key, method, expiry), not a network request to S3. S3 checks the signature only when the client uses the URL.
- **L-0097** simplified/low: The 'public-read' canned ACL does make the object world-readable. Today the usual approach is a private bucket read through a CDN, or a bucket policy, rather than per-object ACLs.
- **L-0098** imprecise/low: The 'policy' field carries the expiry and upload conditions, and X-Amz-Signature signs it with the backend's AWS credentials, so S3 can check validity statelessly from the request itself, much like a JWT.
- **L-0103** simplified/low: Direct-to-storage uploads with signed URLs are the common default for user images because they save server bandwidth, though many services mix them with proxied uploads where validation is needed.
- **L-0107** simplified/low: A private bucket readable only via the CDN is the recommended pattern (CloudFront origin access control plus a bucket policy). - **L-0108** imprecise/low: You can serve images straight from S3 (public objects or presigned URLs), but here the bucket stays private and the CDN, which is a cache not a blob store, serves them.

- **L-0243** simplified/low: Batching per server still helps without repartitioning, because each consumer can sum counts per hashtag within its own batch. A hot hashtag spread over k servers then costs about k writes per batch interval instead of one per post. Partitioning by hashtag makes the aggregation complete and gives each counter a single writer, which avoids contention on hot rows. Kafka Streams does this automatically: groupBy on a new key 'always causes data re-partitioning'.
- **L-0245** simplified/low: Rejecting Redis Pub/Sub here is right, mainly because of the data-loss point. The cost argument is overstated. - **L-0254** simplified/low: The pattern is sound, but 'adapter' here is the teacher's label. - **L-0282** simplified/low: The number of consumers that can usefully work in parallel on a topic is at most its number of partitions.
- **L-0294** simplified/low: Right approach, with one caveat. Kafka can add partitions to a live topic, but the docs warn that 'the default partitioner's mapping logic changes when the partition count increases'. Records with the same key (here the hashtag) may then land on a different partition, and existing data is not moved. Per-key ordering and the single-server-per-hashtag property are briefly broken during the change.
- **L-0314** simplified/low: Two refinements. First, the Kafka producer already buffers and retries: records wait in up to buffer.memory (default 32 MiB) and are retried until delivery.timeout.ms (default 120 s) before send fails. 'Buffer in memory' is therefore the client's default behaviour for short outages. Second, 'dead letter queue' usually means a place for messages a consumer could not process (SQS moves a message there after maxReceiveCount failed receives). A store for writes that failed to reach Kafka is more precisely a fallback queue or outbox.
- **L-0321** imprecise/low: Very few systems give 100% uptime; with leader-replica databases you have to bear a failover window, often tens of seconds to a couple of minutes, when the leader goes down.
- **L-0324** imprecise/low: 'Horizon' is AWS Kinesis vocabulary: TRIM_HORIZON is 'the last untrimmed record in the shard ... the oldest data record in the shard'. Kafka calls this position the earliest offset (log start offset; auto.offset.reset=earliest). Kafka also deletes whole log segments, not individual messages, so the oldest readable record moves forward in segment-sized steps.
- **L-0326** simplified/low: Kafka tracks committed offsets per consumer group and partition, not per individual consumer ID. Any member of the group that takes over a partition resumes from the group's committed offset for it. The committed position is 'the offset of the next message to consume', and commitSync 'commits offsets only to Kafka' (stored internally by the broker).
- **L-0328** simplified/low: The three positions are right, but Kafka's default for a brand-new consumer group is the latest offset. auto.offset.reset defaults to 'latest', so a new consumer such as a search indexer starts from new messages and skips existing data unless you set earliest. Kinesis offers the same choices (TRIM_HORIZON, LATEST, AT_SEQUENCE_NUMBER, AT_TIMESTAMP).
- **L-0330** simplified/low: Kafka's built-in mechanism is tiered storage (KIP-405, production-ready since Kafka 3.9, November 2024). It offloads completed log segments to remote storage such as S3 or HDFS, and consumers can still read them through Kafka; it is not an archive-then-delete step. Kafka ships no RemoteStorageManager implementation ('Kafka server doesn't provide out-of-the-box implementation'), so a plugin is required. Archiving to S3 with a consumer or a Kafka Connect S3 sink, as the teacher describes, is also common.
- **L-0331** imprecise/low: Finding the bottleneck to raise per-server throughput is optimisation (doing more with the same machine), not vertical scaling. Vertical scaling means moving to a bigger machine with more CPU or RAM. The real choice is horizontal scaling versus vertical scaling versus optimisation, and L-0332 to L-0336 are about optimisation via profiling.
- **L-0334** simplified/low: True for deterministic, tracing profilers like cProfile. Modern sampling and continuous profilers are designed to run on all production hosts: Datadog says its Continuous Profiler 'runs in production across all services' with 'minimal impact on your host's CPU and memory usage'. Python's docs recommend the sampling profiler for production and tracing (cProfile) for development and testing.
- **L-0337** imprecise/low: Nagios is an open-source infrastructure, host and service monitoring tool ('ensure the health, performance, and reliability of their IT infrastructure'), not an application profiler or APM. Open-source equivalents for function-level timing are OpenTelemetry-based tracing and sampling profilers. 'New Relic is the biggest' is a market-share opinion this check did not verify.
- **L-0341** simplified/low: Goroutines are cheap ('a few kilobytes' of stack each), so CPU does not limit how many can exist. GOMAXPROCS (default: number of cores) limits how many execute in parallel. Adding CPU helps CPU-bound goroutine work; for I/O-bound goroutines, memory (stacks plus whatever each goroutine holds, like the 20 MB example) or downstream I/O is usually the limit.
- **L-0343** simplified/low: With 64-bit post IDs: 32 B tag + 4 B count + 100 x 8 B IDs = about 836 B, roughly 1 KB per hashtag document.
- **L-0350** simplified/low: Right in spirit: any partitioned broker works. RabbitMQ classic queues are not partitioned by key, though. Getting 'all messages of a hashtag to one consumer' on RabbitMQ needs super streams ('partitioning a large stream into smaller streams') or a consistent-hash exchange plugin.
- **L-0352** imprecise/low: Kafka is not a database: it has no indexes or lookups by key, and its transactions only make a batch of writes atomic, not queries.
