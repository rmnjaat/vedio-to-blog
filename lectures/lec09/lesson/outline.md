## 2 · A CDN as a black box
**Section dek:** one building block that changes almost every public-facing system. What a CDN does, configured and traced request by request, as an engineer uses it rather than as Akamai builds it.
**Sec-meta:** about 26 min · class 00:05–00:30, Q&A 01:44–01:46
**Opening problem:** an Instagram-sized app serves its photos from its own API servers. A 10 MB photo of a beach, hosted in Singapore, is opened by a user in the US, and then by a million more.
**RuleBox (§2):** "A CDN transparently sits between your user and your origin." (L-0018). Box body: that is all it does: for any path, serve the cached bytes if it has them, otherwise fetch the same path from the origin, cache it and serve it (L-0038). Nothing is pushed to it. Sketch: stick figure — cloud `CDN` — box `Origin`, arrowhead on the CDN → origin line ("pulls").

Live content (00:30:04) → 2.6 ForwardChip. Nearest CDN node, BGP, Cloudflare blog, Akamai (01:44:53–01:45:24) → 2.6.
**Hand-off:** "So the CDN serves Instagram's photos. Now get them into storage in the first place, without your API servers carrying the bytes."

### 2.1 What a CDN is, and life without one
- **Purpose:** the definition, the scope of this chapter, and the cost of not having one.
- **Opens with:** the opening problem.
- **Key points:** a lot of people don't know how a CDN works, yet this one building block changes almost every public-facing system (L-0017). This page treats it the way an engineer uses it, as a black box, not its internals such as BGP: nobody here is building Akamai or Cloudflare (L-0003; ForwardChip "CDN internals and BGP · not in this series", from L-0017's deferral). Definition (L-0018). Misconception: people imagine a CDN is "just there to cache things" and that they push content to it. A CDN is not something you push to; CDNs do offer APIs now, but that's not their main job (L-0019). The **origin** is wherever the content lives: an S3 bucket, a backend server, anything (L-0020). The origin needs to be publicly reachable, with some security policies depending on the CDN (L-0021, inline clarification: most CDNs can also authenticate to a private origin; plus A-CDM-06: CloudFront VPC origins, since November 2024). Running example: the instructor's site as the origin, `/system-design/logo.png` to be served via a CDN host `https://a.mycdn.net`; the content could be JSON, bytes, an image, HTML or video (L-0022). Without a CDN, the image URL resolves to the origin's IP (a load balancer), which forwards to a backend that reads the image and sends it back (L-0023; back-link "load balancers · from Lecture 5"). Images are almost static (L-0024) and huge, 1–10 MB; spending 10 MB of API-server bandwidth on one is, in the lecture's word, "a crime": you want API servers lean and fast (L-0025). Instead, let another component move the bytes and cache them near the user: that is exactly what a CDN is (L-0026). A server in Singapore sending a 10 MB image to a user in the US is slow; a copy near the user fixes it (L-0027).
- **Components:** NotationKey (once), Prose, RuleBox §2. Speech bubble (the one for §2) on the CDN cloud: "nobody pushes to me".
- **Figures:** Fig 2·a "Without a CDN" (user → DNS → LB → backend reads the image; red bandwidth bar on the backend's network card; Singapore → US distance label). Fig 2·b (D-02 redraw, plain copy) "User — CDN — Origin".
- **Words:** 650

### 2.2 One mapping: the CDN property
- **Opens with:** "But how is a CDN actually configured?"
- **Key points:** sign up for any CDN (Akamai, Cloudflare, CloudFront: pick your favourite) and configure it yourself; nothing beats practical experience (L-0028; repeated three times in class, kept once here and once as the MarginNote "See it yourself"). All it asks for is one origin URL, then it just works (L-0029). The configuration is a mapping called a **CDN property**: your subdomain on the provider (`a.mycdn.net`) → an origin (`arpitbhayani.me`), so any request to the first is forwarded to the second (L-0030; A-CDM-01 inline: Akamai says property, CloudFront says distribution). Serve the part of a site that is near static and huge, such as images (L-0031). The browser doesn't know a host is a CDN: it resolves whatever hostname is in the URL and sends the request to that IP (L-0032). Resolving `a.mycdn.net` returns the CDN provider's IP: ordinary DNS configuration on Route 53 or a registrar like GoDaddy or Namecheap (L-0033; A-CDM-02: a custom hostname is a CNAME to the CDN's edge hostname). The CDN looks up the origin for the property, swaps the host and requests the same path (L-0034; board flow). You don't configure every URL: any path under the property works because the path is carried over (L-0035). Geographic distribution and the rest are advanced configuration; the minimum an engineer needs is the CDN sitting transparently in between (L-0039).
- **StepThrough** Fig 2·c (D-02 redraw, the copy with addresses) "One request through a CDN property": ① browser resolves `a.mycdn.net` → CDN IP; ② CDN finds the origin for the property; ③ swaps the host, keeps the path (red box around `/system-design/logo.png`, as on the board at 00:29:45); ④ origin answers; ⑤ CDN caches and returns.
- **MarginNote** "See it yourself": put any CDN's free tier in front of a site you own (or a public image) and watch the first and second loads in DevTools. Even if it costs a dollar or two, it is peanuts for what you learn (L-0028 detail). Skip if you've configured one.
- **Words:** 550

### 2.3 Miss, hit, and "it's all bytes"
- **Opens with:** the first person in the world opens `a.mycdn.net/system-design/logo.png`.
- **Key points:** first request: the CDN has nothing, so it requests the path from the origin itself; the origin answers as it always does; the CDN caches and serves (L-0036, inline clarification: only cacheable responses are stored; origin `Cache-Control` and the CDN's policy decide, plus A-CDM-04: `max-age`/`s-maxage` bounded by the CDN's min/max TTL; CloudFront's default is 24 hours). Next request: served from the cache (L-0037). That is all a CDN does (L-0038 → RuleBox). A CDN doesn't care what the bytes are: API responses, JSON, text files, images, video, fragments (L-0040, light inline clarification for this simplified-medium item, plus A-CDM-03: many CDNs, Cloudflare for one, don't cache HTML or JSON by default and skip `private`/`no-store`/`Set-Cookie` responses; a cache rule or origin headers make them eligible). The misconception "only images can be cached on a CDN" (L-0041; back-link "a CDN caches API responses too · from Lecture 2 §1.5"). Giphy caches a lot on its CDN; the instructor has a video on it (L-0042; A-CDM-18 one sentence: Giphy serves through Fastly at tens of billions of requests a day). A hit never reaches your backend: a couple of servers instead of hundreds, with only a trickle of requests each time the cache expires (L-0043). You pay the CDN roughly what you save on infrastructure and get extra performance (L-0044, the lecture's rule of thumb: actual savings depend on traffic and hit ratio). Any URL can sit behind a CDN, even `facebook.com`; to the CDN it is just a URL (L-0045).
- **AnimationClip `l09-cdn-miss-hit`**. Predict line: "A thousand people open the same photo in one minute. How many requests reach the origin?"
- **Words:** 550

### 2.4 See it on a real site
- **Opens with:** the instructor's own website, images and all.
- **Key points:** its images load from `edge.arpitbhayani.me`, the site's CDN property with a custom name instead of the default one; those bytes come from the CDN, not the backend (L-0046). The origin is configured as a path, `arpitbhayani.me/static`: a miss on `edge.arpitbhayani.me/img/<file>.png` makes the CDN fetch `arpitbhayani.me/static/img/<file>.png`, cache it and respond (L-0047). It is plain string concatenation: plug the request path after the origin, call it, cache, return (L-0048). So only paths that exist under `/static` work through this CDN (L-0049).
- **Figure:** Fig 2·d "The URL rewrite" (two URLs one above the other, the host segment swapped, `/static` inserted, path unchanged; an interactive rewriter is optional, the static figure is the contract).
- **CodeBlock:** three lines: `origin = "https://arpitbhayani.me/static"`, `cdn_path = "/img/arpit.png"`, `fetch(origin + cdn_path)  # what the CDN does on a miss`.
- **Words:** 300

### 2.5 Who puts the CDN URL in the page
- **Opens with:** "How does the user even know the CDN URL?"
- **Key points:** the backend sends it. In the API response or the server-rendered HTML, the image URL you pass *is* the CDN URL; the browser doesn't know it's a CDN, it just sees a URL (L-0054). Whatever URL the backend puts in the `IMG` tag is what the browser renders: frontends just render what they are given ("utterly stupid", the lecture's word), so compiling CDN URLs is the backend's job and you don't ship CDN configuration to the frontend (L-0056). The setup for a site like `abc.com`: configure it as the origin on Akamai/Cloudflare/CloudFront, get a CDN hostname, and replace the content URLs in your pages with it. The site never "calls" the CDN at runtime, and there is no automatic mass rewrite: you change the URLs you send, explicitly (L-0057). If this question puzzles you, the gap is in how the web works, not in CDNs: configure one and look at what the backend sends to the browser (L-0055, softened to a study tip). §4.4 comes back to this: Instagram's post service builds the URL per request.
- **PauseAndThink P1** (before the last paragraph).
- **Words:** 350

### 2.6 Private content, changed images, and the nearest edge
- **Opens with:** three questions anyone running a CDN asks in the first week.
- **Key points:** *Private content.* A CDN doesn't only serve public resources; private content works too, depending on the CDN (L-0050). One idea raised in class: Netflix serves most of its traffic via CDN, and private content involves tokens and authentication (L-0051, kept as the class's remark; A-CDM-19: Netflix runs its own CDN, Open Connect, with appliances inside ISPs). The class's advice was to try a CDN first; making things private returns in the upload design (§5) and the CDN comes back tomorrow (L-0052; ForwardChip "CDN again · Lecture 8"). For a private bucket, the CDN must interface with it: you configure AWS keys on the CDN, a plugin-like feature not every CDN has, and the "public origin" picture is a simplification that makes CDNs easy to think about (L-0053, inline clarification: AWS's own CDN needs no keys; origin access control lets CloudFront sign its own requests to a private bucket). *Changed images.* If the image at the origin changes, the CDN doesn't notice until the TTL expires, or until you call the CDN's API to invalidate that path; if you can, do that (L-0058; A-CDM-05: or give each new version a new file name, which also beats browser caches). Invalidating is not pushing: you tell the CDN the path is stale and the next request is a miss that refetches (L-0059). *Live content* such as live matches on a CDN: deferred (L-0060; ForwardChip "live content · week 6, after this series"). *Nearest edge.* Your image service doesn't pick the CDN node: the user's normal DNS resolution lands on the nearest CDN IP, done with BGP (L-0206, inline clarification: either per-location DNS answers, Akamai-style, or anycast via BGP; plus A-CDM-21: with anycast one IP is announced from every PoP). The exact routing isn't public; Cloudflare's blog calls it proprietary but gives a rough idea (L-0207, inline: the mechanisms are documented; only the tuning is proprietary). Akamai started it, and Cloudflare hired a few people from Akamai, "something around that has happened" (L-0208, kept with its hedge; unverifiable).

### 3.2 Three tempting ways to upload
- **Opens with:** "How does this photo get from the phone into S3?"

### 3.3 The pre-signed URL
- **Opens with:** can the photo reach S3 without passing through any server you run, and without opening the bucket to the world?
- **Key points:** one idea raised in class: first ask the API server for a pre-signed URL (passing the image name and location), then upload with it directly to S3 (S3 accepts PUT and POST) before it expires; the load comes off the API server (L-0076), because the bytes never touch it or the upload service (L-0077). What you gain: no service bandwidth spent, and the data isn't transferred twice (5 MB in, 5 MB out, versus one 5 MB transfer) (L-0078, inline clarification: on AWS the same-Region hop itself is usually not billed twice; the gain is servers you no longer need). The class's cost argument: every hop is billed for egress and ingress, so an extra hop for a 5 MB upload costs relatively huge money (L-0079 → **SourceNote SN-01**: inbound internet traffic and same-Region EC2↔S3 are free; internet egress, cross-AZ/Region and NAT gateway processing are what you pay; A-IUT-04, A-IUT-05). Definition: a URL that is pre-signed and expires; a concept everyone uses (L-0080). **Prepare phase:** the client asks the image upload service, which generates a random image ID (just an entry) and creates a short-lived pre-signed URL for that exact path, e.g. `s3://images/<random_id>.png`, and returns it (L-0081; the class said "GCS" while giving an S3 path; the page uses S3 throughout). **Upload phase:** the client POSTs the image to that URL, straight into S3 (L-0082, inline clarification: GitHub's flow is S3's presigned *POST* with form fields; the more common presigned *PUT* carries the signature in the query string). Why not just open the bucket? Anyone could upload their data on your bill, since S3 bills for storage; you can, but you don't need to (L-0083; A-IUT-14 one sentence: new buckets block public access by default). The backend asks for a URL for one path, valid for 10, 20, 30, 60 seconds; it's the URL that is open, not the path: whoever holds it can upload to that path (L-0084, inline: signed locally with the backend's credentials; plus A-IUT-07: AWS calls these bearer tokens, reusable until expiry, and `s3:signatureAge` can cap them). Full flow: client → upload service → S3 creates the URL → URL to the user → bytes straight to S3 (L-0085, inline clarification: the "call to S3" is usually local signing by the SDK; S3 checks the signature only when the URL is used). It also means less infrastructure to manage and native security on the AWS side (L-0086; A-IUT-06: a presigned POST policy can cap size and content type even though you never see the bytes).

### 3.4 GitHub does exactly this
- **Opens with:** "System design is all about building blocks": once you know how something works you can Ctrl-C, Ctrl-V it anywhere (L-0087). GitHub's issue attachments and Instagram's upload are one and the same.
- **Key points:** attaching a 179 KB PNG to an issue comment fires four network calls; the first goes to GitHub's upload-policy endpoint and registers the intent to upload (L-0088). It sends only metadata: name, size (183,938 bytes), content type `image/png`, an auth token; no image yet (L-0089). The response holds a signed upload URL that is S3's, not GitHub's, with everything the frontend needs (L-0090). Its asset href, the future image URL, is a CDN URL on `user-images.githubusercontent.com`, GitHub's CDN alias, with the image ID in the path (L-0091; A-IUT-15: GitHub caps image attachments at 10 MB and, since May 2023, private-repo attachments need a login). On upload intent the backend optionally writes a DB entry, takes a random image ID, builds the S3 path, signs a URL for it, and exposes the CDN URL rather than the S3 path (L-0092). GitHub then inserts standard markdown with a leading `!`, meaning "render as image" (L-0093). The form object carries what S3 needs, sent in the POST body so S3 knows it's a pre-signed upload; GCP and Azure have equivalents (L-0094; A-IUT-11: GCS signed URLs last at most 7 days; Azure recommends user-delegation SAS). The upload URL itself is the plain bucket endpoint; the body fields are what make it pre-signed (L-0095). `key` is the path in the bucket, the same path as in the CDN URL (L-0096). `acl: public-read` makes the object world-readable (L-0097, inline clarification: new buckets now have ACLs disabled and such uploads fail with 400; the usual pattern is a private bucket behind a CDN; plus A-IUT-09). `policy` is the signed part, signed with the key on the API server, with the expiry inside, so S3 needs no database or timer to decide; JWTs work the same way (L-0098, inline clarification: the policy carries expiry and conditions and `X-Amz-Signature` signs it; "certificate" in class means signature; plus A-IUT-08: a URL can't outlive the credentials that signed it). The rest (algorithm, credential, date, signature) are parameters AWS wants (L-0099). Step two: the browser POSTs the form fields plus the file (about 173 KB of PNG) straight to the S3 host (L-0100; screen: a 204 from S3, then a 200 PUT to github.com confirming the asset). Rendering afterwards is GitHub's own logic; what makes the flow special is the bandwidth it saves (L-0101). Opening the image: the CDN misses, reads the key from the S3 origin, caches and serves; the next load is faster (L-0102). Image upload practically everywhere uses pre-signed URLs because they save a ton of bandwidth (L-0103, inline clarification: the common default, though many services mix in proxied uploads where validation is needed; plus A-IUT-16, Microsoft's hybrid guidance). Submitting the issue is like publishing a post: the image is in S3 first, then a separate call publishes (L-0104), which is §4.

### 3.5 What direct upload raises
- **Opens with:** the photo is in S3. Who checks it, how does the app show it, and why not just link to S3?
- **Key points:** *Moderation* is a different system, done asynchronously: if moderation must happen inside the request before publishing, you can't upload straight to S3, which is why most moderation happens after publishing or almost on the fly (L-0105; A-IUT-12: S3 event notifications are the natural trigger). *The CDN URL in the response* comes from the upload service: keep the path, swap the bucket for the CDN host, plain string concatenation (L-0106). It is returned so the frontend knows what to render, because S3 is not public: reading is allowed only for the CDN (L-0107, inline clarification: a private bucket readable only through the CDN is the recommended *configuration*, not inherent to S3; the GitHub demo itself used `public-read`; plus A-IUT-10). It is tempting to render straight from S3, since it is blob storage; in this design you can't, and a CDN is not a blob store (L-0108, inline clarification: S3 can serve public objects or presigned URLs directly; here the bucket stays private). *Why is the CDN faster than S3?* Mumbai vs Bangalore is too specific to answer; geography is the key reason, and a benchmark settles the rest (L-0109). One point raised in class: if location were the only gain, reading from S3 would still cost a lot (L-0110). Akamai has at least 18 locations in India against AWS's two, now three, data centres (L-0111, inline clarification: AWS has two India Regions, Mumbai and Hyderabad; plus A-CDM-10: CloudFront edges in 7 Indian cities plus 46 embedded PoPs). Storage differs too: CDNs might use SSDs, "we don't know", while S3, "an ocean of data", wouldn't, as that would be very costly (L-0112, hedge kept; inline: AWS has said S3 is built on millions of hard disks; plus A-CDM-20). S3 promises "nine nines, something like that", a CDN better response time (L-0113 → **SourceNote SN-02**: S3 Standard is designed for eleven nines of *durability* and 99.99% *availability*; A-CDM-08). Benchmark: if the CDN isn't best for you, fine, but then you pay S3's egress (L-0114; A-CDM-09: CloudFront ↔ S3 transfer is waived, so you pay CloudFront's delivery price instead). *How the CDN reads a private bucket.* Public objects need nothing; for a private bucket, the CDN's AWS integration takes an access key and secret (L-0115, inline clarification: that's the third-party-CDN model; CloudFront uses origin access control with no keys handed over). It is tempting to think the CDN mints a signed URL for each read; it doesn't, it does a normal authenticated S3 read with the SDK (L-0116, inline: SigV4 in the Authorization header). Keys are one way, maybe not the only one: since nearly everyone fronts S3 with a CDN, both sides have native integrations (L-0117; A-CDM-07: OAC as that native integration).

### 4.2 What if you change CDN, cloud, or delete a photo?
- **Opens with:** Instagram is acquired, and the new owner runs its own CDN.
- **Key points:** Instagram "most probably" used Cloudflare; after Facebook bought it, it moved to Facebook's CDN, and with stored URLs that means rewriting the image URL of every post in the database (L-0127), and handling where new uploads are served from too (L-0144) → **SourceNote SN-03** (both: it was Amazon CloudFront, not Cloudflare; the lesson is unchanged). Storing the S3 URL is no better: if Amazon raises prices 4x you may need another cloud (L-0128). Microsoft made every Bing API call 4–10x more costly, "the world works on money" (L-0129, inline clarification: effective 1 May 2023, roughly 3x–10x, Microsoft citing its own investments). So don't bind yourself to one vendor (L-0130). LinkedIn stores an ID and computes the path too, and CDNs do this as well (L-0134, attributed: LinkedIn's scheme isn't publicly documented). Generating at read time lets you return a raw S3 path or a CDN path, change CDN, A/B test CDNs or run two (L-0138). About once every two years management finds CDN costs too high and asks to switch, or to put 20% of traffic on another CDN; with stored URLs that is impossible (L-0139, the instructor's experience). As a senior engineer you will face this (L-0140). A stored S3 URL can't be served directly anyway; you'd have to string-manipulate it into a CDN URL, so store the crux (L-0141, inline: in this design the bucket is private; in general S3 objects can be served directly). Generate it on the fly in the API handler: read the row, build the (signed) URL, send it in the JSON (L-0142). The 20% split: pick a random number; below 0.2 use CDN A, otherwise CDN B, and compare (L-0143). Deleting: with user ID and image ID, build the S3 path and delete; with a stored CDN URL you'd trim the CDN part off, "the worst way to build a system" (L-0145).

### 5.2 Anatomy of a signed URL
- **Opens with:** the URL from the demo, laid out piece by piece.

### 5.3 Where privacy is enforced, and what real privacy costs
- **Opens with:** so what does a private account actually do?
- **Key points:** privacy is enforced in the API server: to render a profile you need the JSON with photo URLs; if the account is private and you don't follow it, that response is never sent. A follower opening the instructor's profile gets the 15–20 photos he posted, each with a full FBCDN URL; a non-follower gets nothing, so the account shows as private (L-0173). ### 7.4 One document, one read: and how big is it?
- **Opens with:** why put the top 100 in the hashtag document at all, when data science already has it?

So the top 100 lives in the hashtag database, not fetched from data science at read time; the hashtag service copies, formats and stores it its own way (L-0258). *Should old hashtags be garbage-collected?* One idea raised in class: a 7–8 day TTL for junk tags. You typically wouldn't: delete a tag and if it later becomes popular its history is gone, and each document is tiny (L-0342). One proposal: keep the first page in the document and the rest in a paginated store served only on scroll, which is rare (L-0348). Don't store a million in the document; nobody scrolls that far, so keep page one (L-0349).

### 8.2 Which partition key?
- **Opens with:** "What would be the partitioning key of this Kafka?"
- **Key points:** one doubt raised in class: hashtag is a poor key because there are so many. The number of values isn't the problem; a key just goes through the hash function, which picks a partition (L-0239). Hash partitioning doesn't mean one partition per key: three partitions can hold millions of hashtags (L-0251; the class called it "week two"; on this site it is Lecture 2 §3.6). Likewise for user IDs: one topic with, say, 1,000 partitions for 1 million users is about 1,000 users per partition (L-0310). The real problems with hashtag as the key of the post topic: (1) one post carries several hashtags, so it has no single key (L-0240); (2) the counter must read the topic the post service already publishes to; otherwise the post service writes to two Kafkas and the distributed-consistency problem creeps in (L-0241; back-link "two writes, one crash · from Lecture 2 §3.4"). The topic is partitioned by user ID (or post ID), so a user's posts land on one partition (L-0242; board "Q: what would be the partition key? user_id"). But batching needs all posts of a hashtag on one server, otherwise you can't batch efficiently (L-0243, inline clarification: per-server batching still helps, at about k writes per interval for a hot tag spread over k servers; partitioning by hashtag makes the aggregation complete and gives each counter a single writer). Three `#sunset` posts on three servers leave nothing to batch: each writes one at a time (L-0244; board: `hashtag` replaced by `user_id` on the pipe, "challenge: POST_PUBLISH topic is partitioned by post_id or user_id").

### 8.3 The adapter: re-partition by hashtag
- **Opens with:** post 31 is published with `#sunset #sun #nature` on a topic keyed by user ID. How should it be routed?

### 8.4 Inside a counting server
- **Opens with:** one partition of `POST_HASHTAG` holds many different hashtags. How does a server count them?
- **Key points:** the batching principle (L-0252 → RuleBox) and the bulk-insert number: one insert of 100 rows is about 100x faster than 100 single inserts; batch your writes (L-0253, inline clarification: "many times faster"; the exact factor depends on the database). Counting servers consume the hashtag topic (three partitions, three servers); all tuples of one hashtag reach one server, which batches and does `count += n` instead of `count++` (L-0270; A-HSD-05: commit offsets only after the DB write, so a crash replays the batch: at-least-once, an over-count). Each message carries the hashtag and the post ID, so the server can group by hashtag (L-0296). Keep a hash table from hashtag to an integer starting at 0, increment per message, and write when the batch is big enough (L-0297; live annotation `<h1, p1>` and `{ h1: int }`). Small details like this hash table are worth working out yourself; the class can't write every line (L-0298). Partitions can't match the number of hashtags: pick n, measure throughput, and add partitions if too low (L-0294, inline clarification + A-HSD-03: adding partitions is online but changes which partition a key maps to, so per-key ordering and the one-server-per-hashtag property break briefly; ForwardChip "what rehashing does to keys · Lecture 9"). Kafka partitioning in depth was covered earlier (L-0295; back-link Lecture 2 §3.6). Many updaters bump the same count, so the database must give atomic increments; that isn't exclusive to relational databases: MySQL and DynamoDB both do it (L-0308; A-HSD-06: DynamoDB atomic counters aren't idempotent, so a retried update can over-count; back-link "count = count + 1 · from Lecture 2 §4"). The compromise: if nodes go down some posts may be counted twice; fine, because the page shows "1.2 million" and renders 100, and nobody checks (L-0255). At scale you can relax constraints; there is always an error rate (L-0256). More hashtags mean more micro writes, but long-tail tags aren't popular, which is okay (L-0346).

- **CodeBlock:** the counting loop in ~10 lines of Python-like pseudocode: `counts = defaultdict(int)`, `for tag, post in poll(): counts[tag] += 1`, then a bulk upsert and `consumer.commit()`.

### 8.5 Other ways to count
- **Opens with:** "Lecture 4's chat used Redis Pub/Sub. Why not here?"
- **Key points:** Pub/Sub fit chat, which needed real-time push; counting doesn't, and real-time Pub/Sub gives no persistence while counters consume at their own pace and the messages must persist. You want a kind of pub/sub, just not a real-time one (L-0300; back-link "Slack's Pub/Sub · from Lecture 4"). With Redis Pub/Sub only subscribers connected *at that moment* get a message; a counting server that is down never receives it (L-0301). The difference is persistence and pace: Pub/Sub pushes, so a hot hashtag keeps bombarding one server; Kafka consumers pull at their own pace and batch (L-0302). With push, database speed throttles you too: if the DB slows, writes take longer and pushed messages pile onto the servers (L-0303). Chat used Pub/Sub because latency had to be minimal: messages are pushed to users rather than pulled (L-0304). One idea raised in class: for counting alone, an in-memory distributed queue would do, accepting a minute's loss on a crash. Then you're doing the same thing; RabbitMQ is fine, Kafka is fine: what you need is a partitioned broker (L-0350, inline clarification: RabbitMQ classic queues aren't partitioned by key; it takes super streams or a consistent-hash exchange). And Kafka isn't here just to count: what it persists can feed other services (L-0351). *Spark instead of counting servers.* MapReduce is data-engineering territory, so only the core idea (L-0360): think of it as distributed computing; the counting servers, plain stateless VMs consuming from Kafka, could be a Spark cluster with Kafka connectors doing the `count++` and batch writes (L-0361). All these frameworks do distributed computing because one machine isn't enough; pick one of Kafka, Kinesis, Flume, Flink…; "counting servers" is a deliberately generic name (L-0362, inline clarification: Kafka and Kinesis are transport, Flume is log collection; the compute options are Spark, Flink, Kafka Streams). MapReduce is a paradigm; Hadoop MapReduce is easy to learn; start with Spark, then Flume, Flink and others (L-0364, inline: Flume is log transport, not a compute engine). To learn data engineering, start with Spark using O'Reilly's Spark book ("Effective Spark is mostly the name"): use it first, then its internals; it is "mind-blowingly awesome", has its flaws, and you should know at least Spark (L-0363, attributed: no O'Reilly title by that exact name was found; the fact-check names the likely book).

### 9.1 The top 100 arrives on Kafka
- **Opens with:** "How would this top 100 come over here? Will they give us a call?"
- **Key points:** it is tempting to start defining the criteria and sorting posts; that's the black box (L-0259). It is tempting to call the data-science service when needed; you can't: the data must be stored in your own database, and the question is how they tell you there's a new top 100 (L-0260). One proposal: a separate service listening for their notifications via a queue, worried it costs an always-running service; it's just a simple processor reading their Kafka and updating the store (L-0261). A common mistake is to treat every consumer as a heavyweight "service"; it's a process, a small set of servers that consume and update (L-0262). Ingestion: when data science generates the top photos for a hashtag, it pushes an event onto Kafka; you consume it and update the top-100 post IDs in the hashtag DB; the stream is low-throughput (L-0263; board "Popularity Svc → Their Kafka → Workers, * Not high throughput"). Why async: a synchronous call makes your uptime depend on theirs (L-0264). Kafka is the glue that joins services; that is why it became famous (L-0265). The CQRS pattern exists because of this ability of Kafka (L-0266 → **SourceNote SN-08**: building a separate read-optimised store from events, as here, is in the spirit of CQRS, which separates write and read models; Kafka is a common way to connect them, not its cause; A-HSD-15). The top-100 array is most likely replaced wholesale with each update, not re-sorted (L-0309). If data science needs hashtag-level data, they can consume `POST_HASHTAG` themselves instead of rebuilding the extraction; today the counters are its only consumer (L-0299). *Webhooks instead?* One idea raised in class: since updates are rare, let the popularity service call your API via webhooks. A good approach, but the lecture prefers Kafka: the other team would have to implement and manage calls into your API, and if your API is down the update is lost and they won't reprocess it (L-0305). Everything is a trade-off; know what you trade for what (L-0306). Decouple as much as you can: what doesn't need synchronicity shouldn't be synchronous, and this update is a textbook case (L-0307; back-link "Hotstar's rule · from Lecture 2 §3.1").

### 9.3 Read path, write path
- **Opens with:** a method you can run on any design, replayed on this one.
- **Key points:** the rule (L-0277 → RuleBox). Every system has paths that write and paths that read; pick one and check it's heavily optimized (L-0278). Here: post service → Kafka → hashtag workers → DB is the write path; the hashtag API reading and serving is the read path (L-0279; board "HashTag API servers won't count; worker nodes batch and update"). The read path is the easy part: a cache and/or a CDN, so it has bare-minimum latency (L-0280; board: centralized cache, API does bare minimum work, DB handles reads). Then walk the write path step by step: post service → Kafka must be one call; two calls would need distributed transactions (L-0281). Workers needed = the topic's partition count (L-0282, inline clarification: the most consumers that can usefully work in parallel; plus A-HSD-04: extra consumers in a group get no partitions; back-link Lecture 2 §3.6). Into the DB: atomic updates, partial updates, enough provisioning, a decent consumption pace; at each step ask whether it does the bare minimum (L-0283; board "Requirements from storage? Partial updates"). Looking at each path separately gives a structured way to build robust systems; think of the implementation and of what can go wrong (L-0284). Blow each component out of proportion, fix, re-architect, one path at a time (L-0285 → RuleBox body). Read path blown up: if the DB spikes, partition it, add replicas, add a cache, then a CDN (L-0286). Write path as implementation: a post with eight hashtags makes eight micro writes naively, hence batching (L-0287), hence re-partitioning by hashtag so one server holds each tag (L-0288). Takeaways also include the adapter and effective batching and counting: find the naive `count++` at every step and fix it (L-0290). It's almost the standard way to think about systems, because reads are scaled separately (L-0291). Not the same as separate services: the hashtag web server and the async workers are separate because their responsibilities differ, not because read and write paths must live apart (L-0293).

### 10.1 When Kafka goes down
- **Opens with:** the opening problem.
- **Key points:** Kafka is not a single instance but a cluster; data replicated across nodes is availability (L-0311). It is tempting to conclude that a replicated cluster never goes down; it can (L-0312). Kafka gives about 99.9% availability, not four or five nines (L-0313 → **SourceNote SN-09**: availability belongs to a deployment; managed SLAs range from 99.5% to 99.99%; A-HSD-13). While it's down, writes are lost unless you handle them, three ways: if critical, push to a dead letter queue and re-ingest later; if loss is fine, drop; or buffer in memory for a while and write when Kafka returns, else drop (L-0314, inline clarification: the producer already buffers and retries, up to `buffer.memory` and `delivery.timeout.ms`, plus A-HSD-09; and "dead letter queue" usually names messages a *consumer* failed to process; a store for failed producer writes is more precisely a fallback queue or outbox). Kafka has no dead letter queue of its own; use RabbitMQ or SQS, assuming that one is up; SQS fits well (L-0358, inline clarification: a separate fallback queue; plus A-HSD-10: SQS's DLQ and Kafka Connect's DLQ setting are for failed *processing*; back-link "SQS · from Lecture 2 §3.3"). One proposal: write the failed message to your own database instead, called in class the transactional outbox (L-0359 → **SourceNote SN-10**: that's a fallback store; the outbox writes *every* message in the same transaction as the business data and a relay publishes it; A-HSD-11). One way raised in class to frame it: Kafka and the DB are stateful, workers and servers stateless; stateless ones are sized by load testing, and the question is what to do when a stateful one goes down (L-0318, kept as the class's framing). Don't always add a component; sometimes losing data is fine (L-0319 → RuleBox). When nothing may be lost, the system must be highly available: Uber's SOS button can never be down or drop an event; the instructor has a video on it (L-0320). Very few systems promise 100% uptime: leader-replica databases bear a failover of "two, three seconds" when the leader dies (L-0321, inline clarification: often tens of seconds to minutes; plus A-HSD-21: RDS Multi-AZ failovers are typically 60–120 s; back-link "leader election · Lecture 2 §2.4"). One proposal: leaderless replication to avoid failover; possible, but it brings multi-master and conflict resolution: you get some, you lose some (L-0322; A-HSD-22: Cassandra's last-write-wins).

### 10.2 Retention, horizon, and where a consumer starts
- **Opens with:** a new search service starts consuming the year-old post topic. Where does it begin?
- **Key points:** Kafka keeps messages forever unless you configure a deletion policy, e.g. delete what's older than 30 days (L-0323 → **SourceNote SN-11**: by default Kafka deletes after 7 days, `log.retention.hours = 168`; forever is opt-in via `retention.ms = -1` or compaction; A-HSD-01). **Horizon**: with a deletion policy, the point where the last deletion ran; nothing before it can be read (L-0324, inline clarification: "horizon" is Kinesis vocabulary (`TRIM_HORIZON`); Kafka calls it the earliest offset and deletes whole segments). Reading "from the horizon" means from the start of what is retained, not the first message ever (L-0325; A-HSD-16: Kinesis's TRIM_HORIZON, LATEST, AT_TIMESTAMP, AT_SEQUENCE_NUMBER). **Checkpoint**: after reading a batch a consumer commits, and Kafka records how far it got; it can later resume from the last commit (L-0326, inline clarification: offsets are per consumer group and partition, not per consumer; back-link "committing · Lecture 2 §3.7"). Consumers commit periodically; after a crash one can resume from the horizon or from the last checkpoint, which reprocesses what came after that commit (L-0327). Three starting points: horizon, last checkpoint, latest. A brand-new consumer starts at the horizon, a crashed one at its last checkpoint, and one that can lose data at the latest message; most cases resume from the checkpoint, few start at the latest (L-0328, inline clarification + A-HSD-02: Kafka's default for a new group is `auto.offset.reset = latest`, so a new consumer skips history unless you set `earliest`). Retention length matters a lot: forever means a lot of storage; low throughput can afford it, but high-volume, long retention blows up your disks, so you set deletion policies (L-0329; asked as "six months vs 30 days?": a big difference). To keep history, have a consumer archive old events to S3 before deletion; Kafka now also has plugins that archive to S3, Blob Storage or GCS before deleting (L-0330, inline clarification + A-HSD-12: the built-in mechanism is tiered storage since Kafka 3.9, which keeps old segments readable through Kafka and needs a storage plugin; the consumer/Connect archive is also common).

### 10.4 Kafka is a broker, and sometimes the front door
- **Opens with:** "Kafka keeps the data anyway. Why not use it as the database?"
- **Key points:** access pattern: you need transactional properties, which a database has and Kafka doesn't, and lookups like "get a post by ID" aren't possible on Kafka (L-0352, inline clarification: Kafka has no indexes; its transactions make a batch of writes atomic, not queries). Kafka is always a broker and should never be your source of truth: "you can, but you should not" (L-0353, the lecture's opinion; inline counterpoint + A-HSD-24: Kafka's co-creator argues it's fine to store data in Kafka with infinite retention or compaction, at a higher operational bar). But Kafka can be the **first point of entry**: in massive analytics ingestion (Google Analytics, YouTube watch time) every event hits an API server, goes to Kafka, and is later aggregated and stored in specialised databases (L-0354). At high volume and rate you don't write straight to the DB: it "might cry", and you may not yet know how to structure the data; accept the write, put it on Kafka, process async (L-0355). The usual order is the reverse: DB first, then an event to Kafka; Kafka-first is the exception for high-volume ingestion (L-0356).
- **MarginNote** "The instructor's analytics systems": every one he built ingested events into Kinesis first and consumed from there: accept the users' writes first, then work out what to do with them (L-0357). Skip unless you build event pipelines.

### 10.5 More servers, or faster code?
- **Opens with:** a pod benchmarked at 400 requests per second; you need 1,000, so three servers. Next year you need 3,000.
- **Key points:** the question as framed in class: add servers, or find the bottleneck and raise per-server capacity; horizontal vs vertical, assuming the stateful dependency (S3, say) can keep up (L-0331, inline clarification: raising per-server throughput is *optimisation*; vertical scaling is a bigger machine; the real choice has three options). First it's a management call on engineering cost: companies with money in the bank often throw it at AWS, because two more servers are cheap next to engineers' salaries (L-0332). To get the most from the same servers, the only way is application-level profiling (New Relic, Datadog, OpenTelemetry): not CPU %, but how long each of the 5,000 functions a handler calls took (L-0333). It's costly in money, data and response time, so you don't run it on every production machine, only a canary or a few (L-0334, inline clarification + A-HSD-18: true for tracing profilers; sampling and continuous profilers are built to run everywhere). Split production 90/10 behind the load balancer and profile the 10%: a response-time hit for a while, in exchange for the bottleneck (L-0335; back-link "load balancers · Lecture 5"). Measure before optimizing; without data you only assume (L-0336 → RuleBox body). New Relic and Datadog lead the market, New Relic the biggest; Nagios as the open-source alternative (L-0337, inline clarification: Nagios is infrastructure monitoring, not a profiler; open-source function timing means OpenTelemetry tracing or sampling profilers; "the biggest" is unverified). For Python, cProfile is simple, text output, decent enough; the instructor used it on his laptop, never in production (L-0338; A-HSD-17: in Python 3.15 cProfile is an alias of `profiling.tracing`, and the docs recommend the sampling profiler for production). Instagram uses cProfile in production on one of its servers and has a blog post on it (L-0339, attributed: Instagram's 2016 efficiency post discusses profiling, but the exact claim wasn't confirmed). More RAM or CPU? Either generally helps, but one may not: a CPU-heavy encryption workload gains nothing from RAM. Know your workload across the four resources, CPU, memory, network and disk, and add what you use most (L-0340). For a Go server running lots of goroutines, add CPU first so more can be scheduled, then RAM if each holds, say, 20 MB (L-0341, inline clarification + A-HSD-23: goroutines start with a few KB of stack; GOMAXPROCS caps how many run in parallel; for I/O-bound goroutines memory or downstream I/O is usually the limit).
