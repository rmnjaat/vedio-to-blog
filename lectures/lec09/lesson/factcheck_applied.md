### SN-01 · §3.3 · L-0079 (imprecise/medium)
- **Teacher's point (kept):** AWS egress cost is a big pain: anything going out of or coming into your EC2 instance is billed (egress and ingress), so every hop you introduce for a 5 MB upload costs relatively huge money.
- **More precisely:** On AWS, inbound internet traffic and same-Region traffic between EC2 and S3 are free. What is billed is data out to the internet, cross-AZ and cross-Region traffic, and NAT gateway processing (a VPC gateway endpoint avoids the last for S3). So check which of these an extra hop adds; the pre-signed design is still justified by bandwidth and server load.
- **Additions used:** A-IUT-04, A-IUT-05
- **Sources:** https://aws.amazon.com/blogs/architecture/overview-of-data-transfer-costs-for-common-architectures/ · https://aws.amazon.com/s3/pricing/

### SN-02 · §3.5 · L-0113 (imprecise/medium)
- **Teacher's point (kept):** S3 and CDNs give different guarantees: S3 gives 'nine nines guarantee, something like that', whereas a CDN gives better response time.
- **More precisely:** S3 Standard is designed for 99.999999999% (eleven nines) durability and 99.99% availability over a year, storing objects across at least three Availability Zones. Durability (not losing data) and availability (being reachable) are different promises; a CDN's promise is lower latency from nearby edges.
- **Additions used:** A-CDM-08
- **Sources:** https://docs.aws.amazon.com/AmazonS3/latest/userguide/DataDurability.html

- **Teacher's point (kept):** When Instagram migrated from Cloudflare to the Facebook CDN it would have done something similar; had it stored photo URLs it would have had to change every place and also handle where newly uploaded photos would be s...
- **More precisely:** Instagram's photos were originally served by Amazon CloudFront in front of S3, not Cloudflare; after the Facebook acquisition they moved to Facebook's CDN (fbcdn.net). The lesson stands: with stored URLs that move would have meant rewriting every post.
- **Sources:** https://highscalability.com/instagram-architecture-14-million-users-terabytes-of-photos/

### SN-04 · §5.1 · L-0163 (imprecise/medium)
- **Teacher's point (kept):** Access by URL lasts only while the cached photo's TTL / certificate is valid; once the TTL or certificate expires the URL is invalidated and no one can access it.
- **More precisely:** The URL is short-lived because the backend signs it with a short expiry; the CDN checks that expiry on every request and rejects the URL afterwards, however long the photo stays in its cache. The signing keys themselves are long-lived key-group keys, not short-lived certificates.
- **Additions used:** A-CDM-13
- **Sources:** https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-signed-urls.html

### SN-05 · §5.3 · L-0175 (imprecise/medium)
- **Teacher's point (kept):** A truly private platform cannot use a CDN: every request - image upload, image download - must go through your API server, which checks on every request whether this user has access to read this particular image, beca...
- **More precisely:** Between Instagram's pseudo privacy and 'no CDN at all' there is a spectrum: very short-lived signed URLs, URLs bound to the viewer's IP range, signed cookies, authentication at the edge, or encrypted media. Serving every byte through your own authorised servers is the extreme end, and signed URLs stay bearer tokens until they expire.
- **Additions used:** A-CDM-14
- **Sources:** https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-signed-urls.html · https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-signed-cookies.html

### SN-08 · §9.1 · L-0266 (imprecise/medium)
- **Teacher's point (kept):** The CQRS pattern exists because of this ability of Kafka to connect services asynchronously; it makes things neat.
- **More precisely:** CQRS (Command Query Responsibility Segregation) means a different model for updates than for reads; it predates Kafka (Fowler credits Greg Young). Building a separate read-optimised store from events, as the hashtag service does, is in its spirit, and Kafka is a common way to connect the two models. Fowler also warns that for most systems CQRS adds risky complexity.
- **Additions used:** A-HSD-15
- **Sources:** https://martinfowler.com/bliki/CQRS.html

### SN-09 · §10.1 · L-0313 (imprecise/medium)
- **Teacher's point (kept):** Kafka can go down: it gives about 99.9% availability, not four nines or five nines.
- **More precisely:** Kafka can go down, but its availability belongs to a deployment, not to Kafka: Amazon MSK's Multi-AZ SLA credits start below 99.9%, Confluent Cloud offers 99.99% on Standard/Enterprise (2+ eCKU) and multi-zone Dedicated, and 99.5% on Basic. Producers need a plan for when it is unavailable.
- **Additions used:** A-HSD-13
- **Sources:** https://aws.amazon.com/msk/sla/ · https://docs.confluent.io/cloud/current/clusters/cluster-types.html

### SN-10 · §10.1 · L-0359 (imprecise/medium)
- **Teacher's point (kept):** Proposal: instead of a separate queue, write the failed message into our own database. Teacher: that is the transaction outbox pattern - write to the DB what you wanted to write but could not, and process it later.
- **More precisely:** Writing messages that failed to reach Kafka into your own database and replaying them later is a fallback store. The transactional outbox pattern goes further: every outgoing message is written to an outbox table in the same local transaction as the business data, and a separate relay publishes it, so there is no dual-write gap.
- **Additions used:** A-HSD-11
- **Sources:** https://microservices.io/patterns/data/transactional-outbox.html

### SN-11 · §10.2 · L-0323 (wrong/medium)
- **Teacher's point (kept):** Kafka keeps messages forever unless a deletion policy is configured, e.g. periodically deleting messages older than 30 days.
- **More precisely:** Kafka deletes messages after a retention period by default: log.retention.hours = 168 (7 days) with cleanup policy 'delete' (unchanged as of Kafka 4.3). Keeping data longer or forever is opt-in: retention.ms = -1 per topic, or log compaction to keep the latest value per key.
- **Additions used:** A-HSD-01
- **Sources:** https://kafka.apache.org/41/configuration/broker-configs/
