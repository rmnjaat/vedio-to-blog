## Inline clarifications

- **L-0023** imprecise/low: Here 'spiral' means building outward from a chosen core component; it is the course's own term, not Boehm's risk-driven Spiral model of software engineering.
- **L-0041** simplified/low: The real blocker is direction, not statelessness: HTTP is a client-initiated request/response protocol (RFC 9110 defines the client as the side that opens the connection to send requests), and clients are usually behind NAT, so the server cannot call them. Even a kept-alive HTTP/1.1 connection does not let the server send unsolicited messages. A protocol such as WebSocket (RFC 6455) is needed for two-way messages, which is the board's 'unless there is a persistent connection'.
- **L-0051** simplified/low: On each heartbeat upsert the row: INSERT INTO pulse ... ON CONFLICT (user_id) DO UPDATE SET last_heartbeat = now().
- **L-0055** simplified/low: Fine for the estimate, but a 4-byte signed epoch-seconds value overflows on 19 January 2038 (MySQL's 4-byte TIMESTAMP range ends at '2038-01-19 03:14:07' UTC). A real schema would use an 8-byte timestamp, making it about 12 bytes of payload per user. A 4-byte unsigned user ID covers about 4.29 billion users, enough for the 1B example.
- **L-0056** simplified/low: 8 GB is the raw payload only. A real database adds per-row overhead: PostgreSQL stores a 23-byte tuple header plus a 4-byte item pointer for every row, before the primary-key index. The real footprint is several times 8 GB. The conclusion (storage is not the challenge) still holds.
- **L-0080** imprecise/low: Walmart avoids AWS (a competitor) and runs a hybrid of Microsoft Azure, Google Cloud and its own private cloud.
- **L-0090** imprecise/low: DynamoDB offers durable change capture via Streams + Lambda; Redis offers keyspace notifications (best-effort Pub/Sub) or application-written Streams, not a durable CDC feed.
- **L-0091** simplified/low: Direction is right, but both examples need qualifiers: MongoDB has multi-document ACID transactions since 4.0 (replica sets) / 4.2 (sharded clusters); mainstream SQL engines still shard mostly through add-ons like Citus (PostgreSQL extension) or Vitess (MySQL clustering), not in the core engine.
- **L-0095** imprecise/low: Redis Pub/Sub is right, but Aerospike is not purely proprietary: Aerospike Database Community Edition is 'the AGPLv3 open-source variant'; only Enterprise Edition is closed-source.
- **L-0098** simplified/low: Redis is open source (AGPLv3 since Redis 8, after a 2024-25 source-available period; Valkey is a BSD fork), while DynamoDB is proprietary.
- **L-0101** simplified/low: Real presence systems keep a persistent connection open. WebSocket is one option, but not the only one: Facebook Messenger built its persistent connection on MQTT to save battery. The point stands: production presence rides on a long-lived connection, not on polling REST heartbeats.
- **L-0104** simplified/low: 6M updates/minute is 100k writes/s. Whether that 'chokes' depends on the store: a single Redis instance does roughly 70k-180k SET/s in the official benchmark without pipelining, and over 1.5M/s with pipelining. A disk-based relational database committing 100k durable single-row updates per second is much harder. The concern is real for an RDBMS and less so for an in-memory key-value store.
- **L-0105** imprecise/low: The whole dataset is tiny (8 MB for 1 million active entries, 8 GB even for 1 billion users), while 6 million writes per minute is the real challenge.
- **L-0109** imprecise/low: A fresh connection costs a TCP handshake (one round trip), the database login exchange (and TLS if used) and a FIN/ACK teardown. Pooling skips all of that on every request.
- **L-0111** simplified/low: The setup cost is more than TCP. In PostgreSQL every new connection makes the postmaster spawn a new backend process, then authentication runs. AWS describes pooling as avoiding 'the memory and CPU overhead of opening a new database connection each time'. Calling it 'the TCP connection' undersells the database-side cost.
- **L-0116** imprecise/low: Opening a connection costs the database a new backend process or thread, buffers and an authentication exchange, on top of the kernel's TCP handshake.
- **L-0117** imprecise/low: Memory is part of the cost too. Each MySQL connection thread gets its own stack plus connection and result buffers, and each PostgreSQL connection is a separate process. AWS RDS states 'database connections consume memory' and derives the default max_connections from instance memory. AWS also describes pooling as avoiding 'the memory and CPU overhead' of new connections. The teacher's 'not really memory' self-correction goes too far.
- **L-0119** simplified/low: Pooling is done on the client side, by a library in the app (HikariCP for JDBC, redis-py's ConnectionPool, etc.) or by a proxy in front of the database (PgBouncer, Amazon RDS Proxy). The database server does not have to 'support' it; any database with persistent connections can be pooled.
- **L-0126** simplified/low: An in-process library is the common case, but external poolers exist and run as separate services: PgBouncer ('lightweight connection pooler for PostgreSQL') and Amazon RDS Proxy. They are the usual fix for the problem in L-0319/L-0320: many app servers multiplexed onto a few database connections.
- **L-0127** simplified/low: The pushback against 'everything is a service' is fair for the in-app library pool, but pooling is sometimes deliberately run as a separate service (PgBouncer, Amazon RDS Proxy), when many servers or serverless functions would otherwise exhaust the database's connections.
- **L-0133** simplified/low: Real load balancers usually check backends by pulling, not by receiving pushed heartbeats: an AWS Application Load Balancer 'periodically sends requests to its registered targets' (default every 30 s; 2 failures mark a target unhealthy). The idea (stop routing to a target that fails checks) is the same; the direction is reversed, because the LB can open connections to its backends.
- **L-0135** imprecise/low: It does not retry forever by default. The database refuses connections beyond its limit with an error, and pool libraries make the caller wait only up to a timeout (HikariCP connectionTimeout, default 30 s) before failing the request. Requests on the new server fail rather than hanging indefinitely.
- **L-0146** simplified/low: Memory is the dominant factor for a database. RDS sets the default max_connections purely from instance memory (MySQL about MB/12; PostgreSQL LEAST(memory/9531392, 5000)). The network side is real but indirect: EC2 caps the number of tracked connections per instance, and bandwidth limits throughput rather than connection count.
- **L-0149** imprecise/low: High-bandwidth instance variants (e.g. c5n, c6in) raise network bandwidth (c5n.large: 3/25 Gbps vs c5.large 0.75/10 Gbps), not connection capacity as such. Connection counts are bounded by database memory and by EC2's per-instance connection-tracking allowance, which grows with instance size. A small-query OLTP database rarely needs a special network class just to hold many connections.
- **L-0157** simplified/low: 3-5 is one convention, but HikariCP, a widely used pool, recommends the opposite: leave minimumIdle unset so the pool is fixed-size (min = max). Creating connections on the fly is exactly the latency the pool is meant to avoid.
- **L-0159** imprecise/low: The teacher's practice, not a standard, as stated. Note the side effect: if every server's maximum is above its fair share (100 servers x 12 = 1,200 > 1,000), a busy moment can exceed the database's max_connections. The database then refuses the extra connections with an error; the server does not simply wait. Also, the example (10 -> 15) is 1.5x, not 1.2x.
- **L-0163** simplified/low: Scaling up and down is not free on most managed databases: some RDS modifications such as an instance-class change require a reboot and cause downtime (shortened by a Multi-AZ failover), so plan it before the spike, not during it.
- **L-0174** simplified/low: In application terms a hard delete is gone, but databases often keep it recoverable for a while: InnoDB only physically removes a row at purge time, and backups / point-in-time recovery can restore it. It is not a substitute for soft delete for user-facing recovery.
- **L-0186** imprecise/low: A soft delete leaves the row's key in place, but it is still a write: InnoDB treats an UPDATE of an indexed column as delete-mark plus insert in that secondary index, and PostgreSQL's MVCC writes a new row version (UPDATE 'does not immediately remove the old version'). The saving over a hard delete is smaller than 'no rebalancing'.
- **L-0191** imprecise/low: The C struct analogy only holds for fixed-length columns (INT, CHAR, DATETIME); variable-length columns break fixed offsets (see L-0190).
- **L-0192** simplified/low: Usually true, but in InnoDB DYNAMIC format long VARCHAR values can also go off-page: 'When a row is too long, the longest columns are chosen for off-page storage.'
- **L-0193** simplified/low: Engine-dependent. InnoDB DYNAMIC: TEXT/BLOB values of 40 bytes or less are stored inline, and longer values move off-page (20-byte pointer) only when the row does not fit the page. PostgreSQL makes no short/long type distinction: TOAST compresses or moves any value out of line once the row is over ~2 kB.
- **L-0194** simplified/low: Off-page values do cost extra page reads (possibly several overflow pages), but these are usually buffer-pool hits, not disk calls. They are only paid when the column is selected: PostgreSQL pulls TOASTed values out only 'if selected at all'.
- **L-0197** imprecise/low: Characters are not bytes: utf8mb4 'can require up to ... four bytes per character', so a 5,000-character comment can be up to 20,000 bytes. The point (large text bloats rows) is right.
- **L-0208** simplified/low: In major engines the native type is compact, not heavy: MySQL DATETIME is 5 bytes (DATE 3), PostgreSQL timestamp 8 bytes, close to an integer. 'Suboptimal in some cases' is fair but should not suggest native types are generally slow.
- **L-0228** imprecise/low: What the teacher upheld (batching hard deletes rebalances less) overstates how engines work. InnoDB already defers physical removal to background purge and merges a page only when it drops below MERGE_THRESHOLD, so per-row deletes do not each trigger a rebalance. Batching mainly saves transaction, lock and log overhead.
- **L-0229** imprecise/low: Same issue as L-0228: page merges depend on page fill (default below 50%), not on how many DELETE statements you group. Grouping reduces commit and locking overhead.
- **L-0230** imprecise/low: Deleting in batches (e.g. 100 rows per commit) cuts per-transaction lock, commit and log overhead; index page merges still happen only when pages fall below their fill threshold.
- **L-0231** simplified/low: The overflow concern is real (signed 32-bit max 2,147,483,647, which is 19 Jan 2038 as epoch seconds), but the next step is a 64-bit integer (bigint), not a double. Epoch milliseconds already need 64 bits today, and 64-bit epoch seconds do not overflow in any practical horizon.
- **L-0233** imprecise/low: Negative epoch values are normal and well supported: MongoDB's BSON Date 'is signed. Negative values represent dates before 1970', with a range of about 290 million years either side. Signed integers handle pre-1970 dates fine; the real constraint is width (see L-0232).
- **L-0234** simplified/low: Teacher hedged ('let's say'). MySQL (5.6.4+) DATETIME takes 5 bytes plus 0-3 bytes for fractional seconds (8 bytes at microsecond precision); TIMESTAMP 4 bytes; DATE 3 bytes.
- **L-0246** simplified/low: A cache is basically a key-value map, plus a memory limit, an eviction policy and expiry; stores like Redis also offer typed values with server-side operations.
- **L-0247** simplified/low: As of October 2026, Redis Open Source documents geospatial indexes, HyperLogLog and Bloom filters (with cuckoo filter, count-min sketch, t-digest, top-k) as built-in data types. Bloom filters used to need the RedisBloom module. The keyspace is a key-to-value lookup, but the values are separate encoded structures (sorted sets, streams, probabilistic sketches), not 'just hash tables'.
- **L-0266** simplified/low: On a valid erasure request the controller must erase the data without undue delay, and must act on the request within one month (extendable by two more months), unless an Art. 17(3) exception such as legal claims applies.
- **L-0269** imprecise/low: The Atlassian outage happened: on 5 April 2022 a script deleted 883 sites for 775 customers, and restoration took up to 14 days (all restored by 18 April). But it was an operational mistake, not a GDPR erasure. A deletion script was given site IDs instead of app IDs, and Atlassian restored the sites from its 30-day full and incremental backups. Recovering accidentally deleted data from backups is what backups are for. It does not show that companies ignore erasure requests, and GDPR guidance accepts backup copies that are kept beyond use and overwritten on schedule.
- **L-0270** simplified/low: Historical snapshots are usually not rewritten, but the erased user's data in them must be kept beyond use and must age out on the backup retention schedule.
- **L-0271** imprecise/low: Calling these 'hacks' to 'maximize what you can' suggests ways around the law. The practices that are legitimate (backups kept beyond use, data kept under an Art. 17(3) exception) are recognised parts of the rules, documented in regulator guidance, not loopholes.
- **L-0275** simplified/low: True for values in the common case: Redis and Memcached store the bytes the client sends, and compressing them is the client's job (client libraries such as pymemcache offer opt-in zlib compression above a size threshold). Redis does compress internally in two narrow places: LZF compression of strings in RDB snapshot files (on by default), and optional LZF compression of inner list nodes (list-compress-depth, off by default).
- **L-0276** simplified/low: Cache compression is usually done by the client library (for example pymemcache's CompressedSerde), not by the cache server.
- **L-0278** simplified/low: CDNs compress text responses; images and video are already compressed by their formats, so generic recompression rarely helps.
- **L-0279** simplified/low: The bandwidth argument is sound: compressing in the client means fewer bytes on the network and in the cache, which is why client libraries such as pymemcache do it. 'Caches should never offer compression' is the teacher's opinion, reasoned out live, not an industry rule. Redis does compress internally where it is cheap and transparent (RDB files, optional list nodes).
- **L-0284** simplified/low: A DELETE already takes row locks inside its transaction; you do not need to lock first to prevent stale reads. The interviewer's real concern is lock duration and contention from a large delete, which affects latency and availability. That is why chunked deletes are advised.
- **L-0287** simplified/low: Worst-case framing, which the teacher makes explicit later (L-0299). Databases cache hot table and index pages in RAM (for example the InnoDB buffer pool), so many database reads never touch disk.
- **L-0289** simplified/low: Right in spirit: InnoDB and PostgreSQL indexes are multi-level B-trees, and a lookup walks from root to leaf. Because each page holds hundreds of keys, the tree is shallow (a few levels even for very large tables, so log base ~hundreds of n, not log2 n). The upper levels are usually cached in the buffer pool, so a lookup often needs only one or two actual disk reads.
- **L-0291** simplified/low: The trade-off factors listed are right. 'Overall not much difference' holds only in the case the teacher describes, where the table's hot data sits in the database's RAM. Otherwise, a disk-backed lookup is still much slower than an in-memory hash lookup (see L-0288).
- **L-0296** imprecise/low: Soft delete conflicts with plain unique indexes; fix it with a partial unique index (e.g. unique on email WHERE NOT is_deleted) or by hard deleting.
- **L-0298** simplified/low: Database-side TTL is convenient, but timing is not guaranteed and the work still loads the database: MongoDB's TTL monitor runs every 60 s and deletion may lag 'depending on the workload', and DynamoDB TTL takes up to a few days. 'Always works' is too strong for a heavily loaded primary.
- **L-0304** simplified/low: Fair for self-hosted vs managed operations, but availability is also a product property: AWS contractually commits to 99.99% (99.999% for global tables) for DynamoDB, and Redis's asynchronous replication can lose acknowledged writes on failover whatever the team does.
- **L-0324** simplified/low: Query time is key (pool size needed is roughly throughput x average query time), but also track pool wait time and saturation. HikariCP's sizing guide ties the optimum to database cores and disks: past it, adding connections lowers throughput.
- **L-0330** simplified/low: HTTP is stateless at the message level; connection reuse is separate: HTTP/1.0 opted in with Keep-Alive, HTTP/1.1 connections are persistent by default, and HTTP/2 connections are always persistent.
- **L-0331** simplified/low: HTTP/2 connections are persistent (RFC 9113 9.1). WebSocket is a separate TCP-based protocol, but it starts as an HTTP request: its handshake is an HTTP Upgrade (RFC 6455 1.7), so it is set up over HTTP and then leaves it.
- **L-0335** simplified/low: HTTP/1.1 and HTTP/2 run over TCP; HTTP/3 runs over QUIC, which runs over UDP.
- **L-0336** imprecise/low: HTTP is independent of TCP but needs a reliable, ordered transport; HTTP/3 gets one over UDP via QUIC.
