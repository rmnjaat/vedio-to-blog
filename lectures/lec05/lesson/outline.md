### 1.1 Why relational databases are strict
- **Purpose:** explain why a relational database gives such strong guarantees, so locking reads as a feature, not a burden.
- **Opens with:** the airline's seat table looks like any spreadsheet. Why does the database guard it so fiercely?
- **Key points:** however many NoSQL databases arrive (MongoDB, Cassandra, DynamoDB), relational databases hold a special place: they are the foundation of how data is structured and what a database can guarantee; the lecture calls them the world's strictest databases (L-0002). They made much of today's software possible and are now the backbone of the internet (L-0007). A relational database stores data in rows and columns, and its key highlight is relations: "you pick relational databases for relations" (L-0006, inline: the name comes from the mathematical relation, a set of tuples; tables are linked by keys). The lecture's pattern: every foundational technology finds its first use in money (L-0008, the lecture's observation): computers ran ledgers first (L-0009 in the MarginNote), blockchain's first use was money (L-0010 → **SourceNote SN-01**). Relational databases were meant for accounting, hence rows and columns (L-0011, inline: designed as a general model; finance was one big early user). Because they dealt with money they needed very strong guarantees, which is why ACID became core (L-0013). You cannot lose a transaction, corrupt data, or stop many people updating it, so transactions are the core component (L-0014). Indexes make reads faster and writes slower (L-0012; this returns in 3.3 and 3.7 where the `expired_at` index pays for itself). Pessimistic locking is one of the most neglected and feared topics, yet one of the best database features (L-0003, the lecture's view). Anyone can create tables and columns; the crux is how and why you lock (L-0016) → hand-off to 1.2.
- **MarginNote** "Money first" (about 70 words): the instructor's father used a black-and-white-screen machine with a typewriter tool and a ledger tool to do accounting (L-0009). Skip unless you like history.
- **Components:** NotationKey (once, top of chapter), Prose, SourceNote SN-01, MarginNote.
- **Words:** 600

### 1.2 Why lock at all
- **Opens with:** two passengers tap the same seat on two kiosks at once.
- **Key points:** every relational database (MySQL, Postgres, Oracle) gives constructs that stop your data from being corrupted; database locking is the pessimistic one: acquire the lock before proceeding (L-0017). When one transaction updates a critical row, no other may touch it, because an operation like `count++` is not atomic (L-0018). A separate sourced sentence (A-C-14): a single `UPDATE … SET count = count + 1` does not lose updates, because the UPDATE locks the row; the lost update comes from reading into the app and writing back. The classic flow: acquire, do the critical action, release; the next transaction goes only after the release (L-0019, Fig 1·a). The two strategies are shared and exclusive locks (L-0020; A-C-16 as a separate sentence: PostgreSQL has four row-lock strengths). One transaction at a time does slow throughput (L-0021). Why bother, then: two people clap on a Medium story at once; both read the old count and both write count + 1, so the result is count + 1, not count + 2 (L-0022; back-link chip to Lecture 2 §4.2, "the lost update"). Locks protect the data's sanity (consistency, integrity) against concurrent updates, taking the database from one correct state to the next (L-0024). RuleBox §1 (L-0023).
- **Figure:** Fig 1·a "Acquire, read and update, release" (board S05/S06 redraw).
- **Words:** 500

### 1.3 Shared and exclusive locks
- **Opens with:** a six-row table and two transactions that both want row 6.
- **Key points:** most databases offer two lock types: shared (read) locks and exclusive (write) locks (L-0037). A shared lock: write a normal SELECT and end it with `FOR SHARE`; every matched row is share-locked (L-0038; CodeBlock with a comment line from A-C-08: `FOR SHARE` replaced the older `LOCK IN SHARE MODE` in MySQL 8.0). T1 runs `… WHERE user_id IN (1,2,6) FOR SHARE` and holds shared locks on rows 1, 2 and 6 (L-0039). T2 runs `… IN (3,4,6) FOR SHARE` and also gets its locks, row 6 included (L-0040). A shared lock lets everyone read but no one else modify (L-0041). If T2 tries to update row 6 it waits until T1 commits or aborts (L-0042 → **SourceNote SN-03**: with both holding a shared lock on row 6, T1 can't update it either; if both try, the database detects a deadlock and rolls one back). Shared locks suit read-heavy work: others still read, nobody modifies (L-0043). If the holder itself modifies the rows, its shared lock is raised to exclusive implicitly (L-0044; A-C-06 as a separate sourced sentence: two shared holders both upgrading is a classic deadlock). Any update needs an exclusive lock (L-0045). An exclusive lock is strict: on the board, other transactions cannot even read the rows (L-0046 → **SourceNote SN-02** + A-C-05: plain SELECTs still read the last committed version; only writers and locking reads wait). Take it with `FOR UPDATE` (L-0047). T1 holds 1, 2, 6 with `FOR UPDATE`; T2 asking for 3, 4, 6 waits because of row 6, though without row 6 it would have finished with rows 3 and 4 (L-0048, Fig 1·c). Exclusive locks hurt throughput, but where you need exclusivity you use them (L-0049). Shared and exclusive locks come out of the box with SQL databases (L-0050).
- **Figures:** Fig 1·b (D-02 redraw, `FOR SHARE`). Fig 1·c (D-03 redraw, `FOR UPDATE`, red on row 6).
- **CodeBlock:** `SELECT * FROM t WHERE user_id IN (1,2,6) FOR SHARE;` and the `FOR UPDATE` twin.
- **Words:** 750

### 1.4 Don't wait: SKIP LOCKED and NOWAIT
- **Opens with:** T2 doesn't need row 6 in particular. Must it still wait?
- **Key points:** `SKIP LOCKED` removes the locked rows from the result set: proceed best-effort with the rows that are free (L-0051, + A-C-07: MySQL and PostgreSQL call the result "an inconsistent view of the data", so it is for queue-like tables where any free row will do, such as job queues and seat pools). Use it when any free rows are fine; when you need all of them, you wait (L-0052). T2 with `SKIP LOCKED` moves on at once with rows 3 and 4 (L-0053, Fig 1·d a). `NOWAIT` is the other extreme: if any wanted row is locked, the transaction kills itself (L-0055, inline + A-C-18: in PostgreSQL the whole transaction is aborted; in MySQL only the statement fails). It's in an existential crisis: someone else has that row, so it has no reason to exist (L-0056, keep the humour). MySQL's error: `ERROR 3572: Do not wait for lock` (L-0054, Fig 1·d b). Retry or not depends on your business (L-0057). Why `NOWAIT` exists: otherwise T2 waits up to the query timeout, ten seconds in the class's example, tying up a thread and making the client wait when the use case doesn't care (L-0058; A-C-09 as a separate sourced sentence: the real defaults are 50 s in InnoDB, and PostgreSQL waits forever unless you set `lock_timeout`).
- **TradeoffTable T1** "Four ways to ask for a row": columns `FOR SHARE` · `FOR UPDATE` · `FOR UPDATE SKIP LOCKED` · `FOR UPDATE NOWAIT`. Rows: what you get · others can read? · others can modify? · if a row is taken · good for · check-in use. The red ✕ sits on `FOR UPDATE`'s "if a row is taken" cell: "wait, up to the lock timeout". Ids L-0041, L-0046, L-0049, L-0052, L-0055, L-0058.
- **MarginNote** "From practice: 'Lock wait timeout exceeded'" (about 120 words): one team's system hits this error often. It means a transaction waited too long for a lock holder to commit or abort (L-0332, + A-C-10: MySQL then rolls back only the waiting statement; the transaction stays open with its earlier locks, so roll back or retry explicitly). Two causes: the holder genuinely does a long job (raise the timeout), or the code finished and forgot to commit or abort (L-0333). Skip unless you've seen the error.
- **Figure:** Fig 1·d "Skip or fail" (two panels on the same six-row table).
- **Words:** 550

### 1.5 Deadlocks
- **Opens with:** two check-in transactions each hold one seat and want the other's.
- **Key points:** deadlock is a side effect of pessimistic locking that comes unannounced (L-0025). T1 holds row 2 and wants row 1; T2 holds row 1 and wants row 2; nobody moves. It is the same deadlock you met in operating systems (L-0026, Fig 1·e). Whenever you add pessimistic locking you risk a deadlock, always, because you never know how threads are scheduled (L-0027). So in any code that locks, check the order of acquisition and release, and protect against a possible deadlock (L-0028, + A-C-04: lock rows in one order, such as ascending primary key). Transactional deadlocks are killers that stall your database (L-0029). Waiting is not deadlock: a deadlock needs a cycle (L-0096; first said in chapter 2, stated here as the definition). Popular databases never let a deadlock persist (L-0030, inline: they detect it and roll one transaction back). When a lock would make a transaction wait, the database checks whether granting it would create a deadlock (L-0031, inline + A-C-01: PostgreSQL first waits `deadlock_timeout`, 1 s, then runs the check). The check is simple: a cycle in who-waits-for-whom (L-0032). The engine kills the transaction whose request would close the cycle; board: "The transaction that detects the deadlock kills itself!" (L-0033 → **SourceNote SN-04** + A-C-02, A-C-03: the victim differs by engine; InnoDB rolls back the smaller transaction, PostgreSQL's choice is unpredictable, Oracle rolls back one statement; so every transaction must be ready to retry). A deadlock left in place would stall everything until a reboot, which is why databases don't allow it (L-0035, inline: a lock-wait timeout or killing one session also breaks it).
- **AnimationClip `l05-deadlock`**. Predict line: "T1 holds row 2, T2 holds row 1, and each now asks for the other's. What does the database do?"
- **MarginNote** "See it yourself" (about 60 words): start two transactions, take locks on two rows crosswise; when the last lock-acquiring query fires, that transaction is killed (L-0034). Skip if you've seen ERROR 1213.
- **MarginNote** "From your OS course" (about 80 words): deadlock detection and prevention is core computer science that isn't going anywhere, whatever frameworks come out. It applies to OS threads and distributed transactions too (L-0036). On very busy InnoDB systems detection itself can slow things down, and MySQL lets you turn it off and rely on the lock-wait timeout (A-C-17). Skip unless you run a very hot database.
- **Figure:** Fig 1·e (D-01 redraw with T2 restored).
- **Words:** 700

### 1.6 Isolation levels: why not one at a time?
- **Opens with:** a question asked in the middle of the demo: if ACID is on by default, why lock at all?
- **Key points:** **PauseAndThink P1** first. ACID holds per transaction; with concurrent transactions locking rows, how they are scheduled depends on the isolation level (L-0100). Durability: when you commit, the data is flushed (L-0101; A-DL-08 as a separate sourced sentence: in MySQL the redo log is flushed at every commit by default). Isolation keeps two running transactions independent; the levels are read uncommitted, read committed, repeatable read, serializable (L-0102). Under serializable the database runs transactions literally one after another, pathetically slow, but the seat problem would not arise (L-0103 → **SourceNote SN-05** + A-DL-02, A-DL-03: serializable guarantees the result of *some* one-at-a-time order; PostgreSQL runs transactions concurrently and aborts one with a serialization failure to retry, and InnoDB turns plain SELECTs into `FOR SHARE`, so two bookers can deadlock). The default is not serializable, for throughput: a user updating row 100 should not wait for a user on row 1 (L-0104, + A-DL-01: MySQL's InnoDB defaults to REPEATABLE READ, PostgreSQL to READ COMMITTED). So isolation is configurable, typically not serializable, and with serializable you wouldn't need all this locking (L-0105).
- **Components:** PauseAndThink P1, Prose, SourceNote SN-05.
- **Words:** 500

### 1.7 Where locks live, and how they end
- **Opens with:** rows sit at offsets on a disk. Is the disk what locks them?
- **Key points:** no: locking happens in the database engine, on the CPU side; a mutex simply doesn't let the waiting transaction move (L-0133, inline + A-C-19: PostgreSQL does record row locks in the row itself, so `SELECT FOR UPDATE` can write to disk; InnoDB keeps its lock table in memory). Mutexes, semaphores and sometimes monitors are what locks are built with; otherwise you use atomic instructions (L-0134, inline: all of them rest on hardware atomics such as compare-and-swap). A transaction waits only because it wants a lock (L-0157). If you skip the SELECT and fire a plain UPDATE, "the isolation level kicks in" (L-0156). In the instructor's words you cannot put `FOR UPDATE` on an UPDATE, which is a one-line command that never acquired a lock (L-0158). → **SourceNote SN-06** covering L-0156 and L-0158 + A-DL-04, A-DL-05: an UPDATE always takes an exclusive lock on the rows it touches, the same lock `FOR UPDATE` takes; concurrent updates of one row queue, and the isolation level decides whether the waiter then re-checks (READ COMMITTED) or is aborted to retry (PostgreSQL REPEATABLE READ). To lock explicitly, run `SELECT … FOR UPDATE`, then the UPDATE (L-0159). There is no explicit unlock: commit or abort releases every lock (L-0160). Autocommit makes a standalone statement commit itself; inside `BEGIN … COMMIT` the commit comes at the end, so `FOR UPDATE` locks behave as shown regardless (L-0305).
- **MarginNote** "Try it in two terminals" (about 140 words): start MySQL, open two sessions, `SET autocommit = 0`, begin a transaction in each, take shared and exclusive locks, and watch one session halt while the other moves; no code needed (L-0143). This is also where you meet deadlocks and "funny things" (L-0144). One question from class to try this way: a transaction holds `FOR SHARE` on a row, then updates it; what happens to a second reader? It needed a half-hour lock-timeline to answer, so code it out (L-0142; SN-03 has the textbook answer). Skip if you've done it.
- **RecallQuestions §1:** (1) T1 holds `FOR UPDATE` on rows 1, 2, 6. T2 asks for 3, 4, 6 three ways: plain, `SKIP LOCKED`, `NOWAIT`. What does each get? (2) Two transactions lock the same two rows in the same order. Can they deadlock? Why not? (3) Why doesn't the database simply run every transaction serializably, and what does your code need if you choose serializable anyway?
- **Words:** 600

### 2.2 Approaches 0 to 2: no checks at all
- **Opens with:** the simplest program that could work: ask the passenger which seat.
- **Key points:** approach 0: the program takes a user id, asks for a seat, books it (seat 3 shows as 1C for that user) (L-0072). Its `book()` begins a transaction, SELECTs the seat by id, runs `UPDATE seats SET user_id = ? WHERE id = ?`, commits (L-0074). Zero checks: another user can book the same seat. Naive, but the foundation (L-0075). Two people on one seat means two boarding passes and chaos in the plane (L-0076). ### 2.3 Approach 3: the first free seat
- **Opens with:** stop picking at random; give each passenger the first free seat.
- **Key points:** the query: `SELECT id, name, trip_id, user_id FROM seats WHERE trip_id = 1 AND user_id IS NULL ORDER BY id LIMIT 1`, then update and commit, 120 at once (L-0083). **PauseAndThink P2** before the run. The class's reasoning, which is right: concurrent transactions read at the same time and all see the seat as NULL, so without locking the same seat is offered to many (L-0084). Another, which the instructor's later explanation matches: everyone reads 1A, so every write targets it, and more seats fill only when a commit lands before someone else's read (L-0087). It's the condition, not the code or the transaction, that moves it on (L-0091). That's why commit matters: once committed, later reads see the value (L-0092; A-C-15 as a separate sourced sentence: in MySQL's REPEATABLE READ a transaction keeps the snapshot of its first read; here the SELECT is that first read). The run shows how relational databases make locking easy to understand (L-0089). Expected 120 seats; got a handful, because everyone read the same old row. ### 2.4 Approach 4: FOR UPDATE
- **Opens with:** the same code with two words added: `FOR UPDATE` (L-0094; diff-highlighted CodeBlock; + A-C-20 as a code comment: with `LIMIT`, locking stops once enough rows are returned; at READ COMMITTED, ORDER BY plus a locking clause can return rows out of order).
- **Key points:** **PauseAndThink P3** (the prediction round as two options). The predictions made in class, each with its fate:
  - "It will deadlock: the second waits for the first" (L-0095). No: waiting is not deadlock; deadlock needs a cycle (L-0096, also in 1.5).
  - "Starvation: all 120 fill, but later transactions wait longer" (L-0097). The run bears out that all 120 fill.
  - "The second transaction sees row 1 is being updated and takes row 2" (L-0098). It was reversed in class (it waits).
  - "Once the lock frees, the waiter must verify `user_id` is still NULL before writing": "not entirely true" in class; the real mechanism is below (L-0099).
  - "Only one seat fills, because `SKIP LOCKED` isn't on" (L-0106). "Between 1 and 120, depending on scheduling" (L-0107). "Waiters see 1A filled and cancel" (L-0110).
  - "All 120: the others wait for R1, then see it is no longer NULL and move to R2", called almost 90% correct (L-0108).
  → **SourceNote SN-07** (covers L-0098, L-0106, L-0107, L-0110): what the run and the documentation show: a `FOR UPDATE` waiter waits for row 1's lock; when the holder commits it re-checks the row against its WHERE, finds it taken and continues to the next free one. Every run fills 120; only the order of users changes. Moving straight on without waiting is `SKIP LOCKED`.
  **PauseAndThink P4** ("you are the database engineer"): the engine must treat a range query (`user_id IS NULL ORDER BY id LIMIT 1`) and a pointed lookup (`id = 67`) the same way; a lock on one row by itself would never move on (L-0109). The run: all 120 seats fill, every time (L-0112; on screen 1.25 s, 1.73 s, 1.79 s), in seat order 1C, 1D, 1E, 1F, 2A, 2B…, each transaction taking an exclusive lock while the rest wait (L-0113). The part people skip: it's tempting to think all 120 transactions "got" the first row. The database doesn't hand a row to a transaction until it holds the lock; it sees the row is locked and makes the transaction wait (L-0114). Behind the scenes: the first transaction takes the lock, the rest wait; when it commits or aborts, the engine signals the waiters to re-evaluate; one of the 119 gets row 2; when it commits, the rest are signalled for seat 3, and so on (L-0115; A-C-11 as a separate sourced sentence: in PostgreSQL at READ COMMITTED the waiter re-checks its WHERE against the new row version and skips it if it no longer matches; at REPEATABLE READ it errors and must retry). Re-evaluation is the engine re-running the same statement, not the client re-firing the query (L-0116). It is tempting to think the query is evaluated once, at the start, for every waiter; in fact it is re-triggered on every signal (L-0148). And waiters don't busy-loop checking the lock: they sit in a wait queue and are signalled when it's released (L-0163). User 1 doesn't get seat 1: whoever is scheduled next gets the next seat (L-0117). Cost: in the worst case all waiters re-evaluate, one wins, the rest re-evaluate again: N + (N−1) + … = N(N+1)/2 evaluations inside the engine, not queries from the app. For N = 120 that is 7,260 (L-0155; the arithmetic is the page's). Painful for the database, but correct (L-0118).
- **StepThrough** Fig 2·e "Wait, signal, re-check" (after P4, before the cost paragraph).
- **MarginNote** "From your OS course" (about 60 words): thread wait queues and signalling are the operating-system constructs you learned in college and maybe never saw used; the instructor is a big supporter of formal education (L-0164). Skip if you remember condition variables.
- **MarginNote** "Why the index matters" (about 70 words, A-C-12): in InnoDB a locking read locks every index record it scans; without an index on `(trip_id, user_id)` the approach 4 query may lock every row of the table. Skip unless you'll run the demo.
- **MarginNote** "A debugging hunch" (about 30 words): if adding two words to a query changes nothing, something is probably wrong (L-0111). Skip.
- **Words:** 1,300

### 2.5 Approach 5: SKIP LOCKED
- **Opens with:** a passenger doesn't care which free seat they get, so why wait behind someone else's?
- **Key points:** approach 4's query plus `SKIP LOCKED` (L-0119, diff CodeBlock). **PauseAndThink P5.** The class predicted all seats fill and total time drops, describing approach 4 as "busy waiting" (L-0120; the page notes approach 4's waiters are signalled, not looping, per 2.4). The run: approach 4 took about 1.7 s; approach 5 finished in 147 ms, about a tenth, and still filled all 120 (L-0121). Each transaction still takes an exclusive lock, but when the engine finds a matching row locked it moves straight to the next matching row and locks that one, so nobody waits and rows are locked back to back by different transactions (L-0122; the instructor said "re-evaluated" here and, later in Q&A, that `SKIP LOCKED` doesn't re-evaluate the query; both wordings appear in the MarginNote below). Two words made it ten times faster, which is why you need to know how your database actually locks (L-0123; back-link to A-C-07 in 1.4 on when `SKIP LOCKED` fits). From the lecture: relational databases scale beautifully: they can't handle big data, but at high QPS they are champions, and here the tuning was plain SQL constructs (L-0124; the Vitess sentence in 2.7 follows up). Recap: approaches 0–5 changed two or three words: first make it fail, then make it correct (`FOR UPDATE`), then make it fast (`SKIP LOCKED`) (L-0125). What if the transaction holding seat 2 fails? Seat 2 isn't lost: the next transaction to run the query matches that row again; a row is never skipped for good (L-0145). Rows aren't handed out by transaction order; whichever transaction executes gets the match (L-0146). Because of `ORDER BY id` the released row is the first one picked up; without ORDER BY some free row would still match (L-0147). With `SKIP LOCKED` the query is evaluated about 120 times in total, one per passenger (L-0154), against up to 7,260 for approach 4.
- **AnimationClip `l05-wait-vs-skip`** (after the run paragraph). Predict line: "Same 120 passengers, same seats. One line waits its turn at every seat; the other walks past locked seats. Watch the clocks."
- **MarginNote** "What the engine actually reads" (about 170 words, from the closing Q&A): during the demo the instructor said the engine "quickly re-evaluated" and moved on (L-0122); asked again at the end, he put it more exactly: with `SKIP LOCKED` the database doesn't re-evaluate the query: it reads a whole disk page, one B+ tree node holding perhaps hundreds of rows, and if the first row is locked it moves to the next at once (L-0306). And `LIMIT` (and `OFFSET`) is applied at the last step, when results are accumulated, not before the disk read (L-0307 → **SourceNote SN-08** + A-DL-06, A-DL-07). Skip unless you tune queries.

### 3.2 Storing keys and values
- **Opens with:** the board's empty table called `store`.
- **Key points:** the first idea in class, an array, went nowhere (L-0175). The starting point: the key as primary key (so it's indexed), the value as a string (L-0176). It's tempting to ignore storage size; it's a database, so you always care (L-0177). The key's type decides what keys you support: integers only, an integer column; strings, decide how long (L-0178). Know your key size, say `VARCHAR(16)` (the instructor's deliberately small pick), or 24, or 30–60 (L-0179, + A-KSD-01: in InnoDB the primary key is the clustered index and every secondary index stores it, so a long key also bloats the `expired_at` index). Once fixed you can't change it, so know your requirements (L-0180, inline + A-KSD-19: growing a VARCHAR in place works only while its length prefix stays the same size; otherwise a full table copy). The value's type: it's tempting to pick it by what's stored, integer for small values, a long string for JSON; "partially true" (L-0181). **Pull line:** the value's type follows how users access it, if at all, not what it holds (L-0183). A BLOB can hold anything (L-0182; A-KSD-02 as a separate sourced sentence: BLOB tops out at 64 KB, MEDIUMBLOB 16 MB, LONGBLOB 4 GB). MongoDB is also a key-value store: JSON against an id, queryable inside, so its value type must support queries (L-0184, inline: a document database; each BSON document has an `_id`). A typed value column also allows range queries on the value (L-0185). To query inside JSON, use a type that supports it, like MySQL's native JSON (L-0186; A-KSD-14 as a separate sourced sentence: JSON columns aren't indexed directly; index a generated column). Here queries are on the key only, so the value is a black box: a BLOB (L-0187, Fig 3·a step 1). A value-type column is only needed if you support several value types (L-0203). The slides' single-node schema: `store(key, value, ttl, is_deleted)`, where `ttl` is the absolute expiry time (L-0228); 3.3 and 3.4 shrink it to three columns. No auto-increment `id` by habit; add one only if you need it (L-0229). The habit comes from ORMs, which the instructor says he hates (L-0230, full in 6.1).

### 3.3 Expiry as a timestamp
- **Opens with:** every key can have its own TTL, at second granularity (L-0189). Which column do you add?
- **Key points:** the first proposal: a `created_at` column plus a job that checks it and flushes expired keys (L-0188, Fig 3·a step 2). Then `created_at` + `ttl_sec` per key, with `DELETE … WHERE now() - created_at >= ttl` (L-0190). **PauseAndThink P6.** It's the worst query you can write: a dynamic computation can't use an index, so every row is scanned every run (L-0191). The root cause is the computation itself; remove it (L-0192). The idea from class: store a "valid till" time and index it (L-0193). So store the absolute expiry, `expired_at`, instead of `created_at` and a TTL (keep `created_at` only if you need it elsewhere) (L-0194, Fig 3·a step 3; + A-KSD-06: Redis stores expiries as absolute Unix timestamps too, which ties expiry to a stable clock). Cleanup becomes `DELETE FROM store WHERE expired_at <= now()` with one index on `expired_at`: a really efficient query (L-0195, + A-KSD-07: with a large backlog, run it in chunks with `LIMIT`).
- **Figure:** Fig 3·b "Why the index can't help" (two panels).

### 3.4 Delete is an update
- **Opens with:** a user deletes a key. Do you remove the row now?
- **Key points:** a proposal from class: soft delete, mark the row and let a background job delete it later, because a real delete may force internal structures to rebalance (L-0196). With an `is_deleted` column that means a second job, `DELETE … WHERE is_deleted = true`: two jobs (L-0197). A better proposal: piggyback on `expired_at` and set it to a value always smaller than now (L-0198). Delete becomes an update: `UPDATE store SET expired_at = -1 WHERE key = K` (L-0199). It saves a job, so less CPU, disk, reads and storage (L-0200). Reads must also filter expired keys, because the job may not have run yet (L-0201) → 3.6. One job, `DELETE … WHERE expired_at < now`, now matches both expired and deleted rows ("elegant") (L-0202). The -1 replaces the `is_deleted` column, saving its space (L-0231); a user delete is an update, and the hard deletes are batched later, so the database does minimal B+ tree rebalancing (L-0232, inline: InnoDB doesn't rebalance on every delete; it merges a page only when it falls under half full; and the soft-delete UPDATE isn't free either, since it moves the entry in the `expired_at` index; batching still cuts work). Why write -1 at all, if the job compares times anyway? A key with no TTL never expires, so an explicit delete must write something (L-0264). Any magic value works, such as a date before 1 January 1970 (L-0265; A-KSD-09 as a separate sourced sentence: MySQL TIMESTAMP covers 1970 to 2038 only; DATETIME or an integer epoch can hold such a marker, including -1).
- **MarginNote** "Why not hard-delete right away?" (about 120 words): every pointed delete may put the B+ tree out of shape and force an expensive rebalance (L-0334, inline: InnoDB delete-marks and purges; no immediate rebalance). So almost all databases soft-delete, then clean up in batches (L-0335; A-DL-09 and A-DL-10 as separate sourced sentences: InnoDB delete-marks a row and purges it once no transaction needs it; PostgreSQL keeps old row versions until VACUUM). Read up on B+ tree rebalancing; the instructor's video covers it, and Lecture 1 touched it (L-0336). Skip unless you care about engine internals.
- **MarginNote** "Why don't databases ship soft delete?" (about 170 words, a question from class): a database is a foundational layer: it gives building blocks (`FOR UPDATE`, `FOR SHARE`, `SKIP LOCKED`, `NOWAIT`) and stays out of the user's space; otherwise there's no clear line on what to build (L-0353; A-DL-12 as a separate sourced sentence: SQL Server's system-versioned temporal tables offer opt-in history of deleted rows). Built-in soft delete would need its own cleanup process and would load developers with questions: is it gone yet, will I read it, which column? (L-0354). DynamoDB, a key-value store, always soft-deletes on delete, because for KV stores it's foundational (L-0355 → **SourceNote SN-14** + A-DL-11: DeleteItem removes the item; its TTL feature deletes expired items in the background within days, so reads must filter them). The instructor recalls a 2011–12 MySQL forum thread proposing built-in soft deletion; its essence: as a database evolves it matters more to know what you don't want to do (L-0356). Design a database around what you definitely won't do, and give raw constructs (L-0357). Skip unless you design databases.

- **CodeBlock:** the delete UPDATE (badge: `saves: a column and a second job`).

### 3.5 Put is an upsert
- **Opens with:** `PUT K1 V1`, then `PUT K1 V2`.
- **Key points:** the naive insert passes key, value and `expired_at` (L-0204). The second put fires the same insert and fails: the key already exists (L-0205). A tempting fix, a WHERE on expiry, misses the point: a put must replace the value (L-0206). Another, mark the old row expired and insert a new one, still reads the key, and the primary key forbids two rows anyway (L-0209). The naive fix: GET every time, then UPDATE or INSERT: every put becomes a get plus a put, fetching the key for nothing (L-0207, Fig 3·c; + A-KSD-05: it's also racy, two puts can both see "absent" and one INSERT fails). What a put needs: insert if absent, update if present, without reading first (L-0208). The devil is in the details: people draw boxes and never think about implementation (L-0210). **PauseAndThink P7.** The answer proposed in class: insert, and if it exists, update; an upsert at the database level (L-0211). Upserts are atomic: one statement, no read-check-write in a transaction (L-0212). In Postgres, the instructor said, you replace INSERT with UPSERT (L-0213); each database has its own clause: UPSERT in Postgres, `REPLACE INTO` or `ON DUPLICATE KEY UPDATE` in MySQL (L-0216) → **SourceNote SN-10** (covers L-0213, L-0216) + A-KSD-03, A-KSD-04: PostgreSQL has no UPSERT keyword; it's `INSERT … ON CONFLICT (key) DO UPDATE SET …`; MySQL's `REPLACE INTO` deletes and re-inserts, while `ON DUPLICATE KEY UPDATE` changes the row in place. `PUT K1 V2` now replaces V1 (L-0214, Fig 3·a step 5). Why it's faster: the database still reads the row, but you skip the round trip that brings it to the API server and the big transaction around get-plus-write (L-0215). Native upserts keep throughput high and load minimal (L-0218). Update is the same as put (L-0219). **The trip count** (from the Q&A): checking with `SELECT TOP 1 1 … WHERE …` and then writing costs four network trips against two for an upsert (L-0328, Fig 3·c). The database spends almost no time on the check or the write; the network is the bulk (L-0329). `TOP 1 1` does avoid shipping a huge value, but still pays a round trip (L-0330). Many production systems do get-then-set anyway (L-0331, the instructor's observation). **Concurrent puts on one key:** reuse chapter 1's locks or isolation levels; the database already guarantees this, don't reimplement it (L-0233). One option is `FOR UPDATE NOWAIT`, so a put fails at once if someone else is updating the key ("just for fancy") (L-0234). There is no right choice between `SKIP LOCKED`, `NOWAIT` and waiting; it depends on the guarantees you want (L-0235).
- **CodeBlock:** naive INSERT → MySQL `INSERT … ON DUPLICATE KEY UPDATE` → PostgreSQL `ON CONFLICT` (badge: `saves: a network round trip`), plus the board's `REPLACE INTO` with a comment "deletes and re-inserts".
- **MarginNote** "Could you buffer writes in memory?" (about 90 words): one idea from class was an in-memory append-only layer in front of the table to cut insert IO. That is a cache in front, which you can add, but it isn't the transactional store itself (L-0267). It is limited by memory: the keys must fit and be flushed from time to time (L-0268). ForwardChip: two such optimizations come later, an in-memory store in Lecture 9 and an append-only store in Lecture 10 (L-0269). Skip unless you're thinking about write throughput.
- **MarginNote** "An open question" (about 70 words): what if a newcomer overwrites transactional data with an upsert by mistake? The instructor said you must support upsert anyway for throughput and deferred the case; it wasn't revisited (L-0225). His view on human error of that kind: the team lead is accountable, and teams should review thoroughly before touching such data (L-0226, his opinion). Skip.
- **Figure:** Fig 3·c "Two trips or four".
- **Words:** 1,100

### 3.6 Get filters expiry in SQL
- **Opens with:** a GET for a key that expired a minute ago, holding a 10 MB value.
- **Key points:** **PauseAndThink P8.** The proposal in class: `SELECT * FROM store WHERE key = k1`, compare `expired_at` with now in the API server, return "key does not exist". Wasteful: you ship 10 MB to the API only to learn it expired (L-0220). Filter in the database: add `AND expired_at > now()`; expired keys never leave the database (L-0221). That one clause saves heavy network IO for the server and the database, and the database's disk read of a huge value (L-0222). RuleBox §3 (L-0223).
- **CodeBlock:** the GET (badge: `saves: network IO`).
- **Words:** 350

### 3.7 The cleanup job and the last clause
- **Opens with:** the store now has three columns and three queries. Who removes the expired rows, and when?
- **Key points:** TTL approach 1: a cron job every t minutes (say 10) fires `DELETE FROM store WHERE expired_at < now` as a hard delete (L-0236, Fig 3·d); between runs, reads filter (3.6). One more clause, on the user delete: `UPDATE store SET ttl = -1 WHERE key = k1 AND ttl > now()` soft-deletes a key only if it hasn't already expired (L-0258; A-KSD-08 as a separate sourced sentence: if keys without a TTL store NULL, `ttl > now()` never matches them; store a far-future sentinel or add `OR ttl IS NULL`). For an already-expired key the row isn't written, so there's no disk IO; the batch job removes it anyway: "heads you win, tails you win" (L-0259). That saves two disk IOs, because the index on `ttl` would also change (L-0260). It relies on that index existing (L-0266). Don't confuse the two clauses: `ttl > now` is the user's delete, which only soft-deletes live keys; `ttl <= now` is the batch cleanup (L-0294). Do disk IO only when it's needed (L-0262). **Final queries card** (L-0263): batch cleanup `DELETE FROM store WHERE ttl <= now()` (expired and soft-deleted), get `SELECT * FROM store WHERE key = k1 AND ttl > now()`, so you never make network IO for an expired key (inline + A-KSD-08: GET must also return keys with no TTL; use a sentinel or `(ttl IS NULL OR ttl > now())`). Hand-off: on disk you batch. What if the store lived in memory? → chapter 4.

- **MarginNote** "Where this clause came from" (about 60 words): the instructor found it in Apache Ignite's code, wondered why it was there, mimicked the load, and then saw the optimization (L-0261, his story). Skip.

## 4 · If it were in memory: how Redis expires keys
**Section dek:** on disk you batch. In memory a delete is nearly free, so Redis deletes expired keys the moment it touches them, and samples twenty keys at a time for the rest.
**Sec-meta:** about 14 min · class 02:08–02:19, Q&A 02:43–02:47, 03:07–03:09
**Opening problem:** the same per-key TTL, but the store is an in-memory hash table on one thread, like Redis.
**RuleBox (§4):** "On disk you delete in batches; in memory you can delete right there." (L-0241). Body: delegate a delete to a later job only when it's expensive (L-0339). Sketch: a B+ tree with a red "rebalance" mark vs a hash table slot freed with a green tick. Sits in 4.1.
**Estimated words:** 1,900
**Q&A folded in:** "deleted" vs "expired" in the sample (02:43:49) → 4.2. Sampling on disk (02:45:21) → 4.2 P9. Why not delegate lazy deletes to a cron (03:07:36) → 4.1.

### 4.1 Lazy deletion
- **Opens with:** a GET finds its key expired. On disk you'd filter it. In memory?
- **Key points:** lazy deletion: when an accessed key is found expired, delete it on the spot, without going looking for expired keys (L-0237). Almost all in-memory databases do this; it's for memory, not the disk-based store of chapter 3 (L-0238). In memory a delete is cheap: no tree to rebalance, no network penalty; free the memory and remove the key from the hash table (L-0239). On disk, don't do per-key lazy deletes: every micro delete rebalances the B+ tree, which is pathetically slow, and the instructor repeats it "a hundred times" (L-0240 → **SourceNote SN-11** + A-KSD-10: batched cleanup is the right instinct, but a single delete isn't catastrophic; InnoDB delete-marks, purges in the background and merges pages only below half full). On disk, batch deletes; in memory, pointed or staggered ones (L-0241, RuleBox). Redis hard-deletes in two cases: an explicit DEL, and touching an expired key (L-0242). Lazy deletion alone leaves keys that expire and are never read, so a periodic job is still needed, and Redis's job does not delete them all (L-0243) → 4.2. Why not hand lazy deletes to a cron job? Freeing an object takes microseconds with no rebalance, so delegating may cost more than deleting inline (L-0337). Deleting from Redis's hash table just frees the slot (L-0338, inline: Redis's dict uses chaining, so it unlinks the entry and frees it). Delegate only when the work is expensive enough (L-0339). And deleting now frees memory now: delay it, and a full Redis may reject inserts while expired data sits in memory (L-0340).
- **Figure:** Fig 4·a "Deleting on disk vs in memory" (two panels).
- **Words:** 750

### 4.2 Sampling 20 keys
- **Opens with:** the keys nobody ever reads again.
- **Key points:** Redis combines lazy deletion with a periodic job, a simple algorithm with a little math (L-0244). The natural job deletes all expired keys each run, but with millions that takes too long (L-0245). Lazy deletion solves about 90% of the problem, since expired keys are likely to be read (L-0246, the instructor's estimate). The job instead samples exactly 20 random keys among those with an expiry and deletes the expired ones in the sample (L-0247). If more than 25% of the sample was deleted, repeat; stop when fewer (L-0249). → **SourceNote SN-12** (L-0247, L-0249) + A-KSD-11: that's classic Redis; since 6.0 the cycle scans the expiry table in batches of 20 at default effort, keeps going while more than about 10% are stale, and stops at a CPU time budget (`active-expire-effort` tunes it). Why it works: the sample stands for the population of keys with an expiry; if half the sample is expired, about half the population is (L-0250, Fig 4·b). The 25% counts keys deleted from the sample, which are the expired ones in it; counting expired keys across the whole database would itself be slow (in L-0249's detail; folded in). Example: 3 of 20 expired (15%): delete 3, stop; about 15% of the population is expired but not deleted, which is fine (L-0251). The job works only on the sample, never scans the database, and leaves no more than the threshold behind because the sample represents the population (L-0301). Redis optimizes for speed, not completeness: time on cleanup is time not serving reads and writes (L-0252). Redis is single-threaded, nothing else runs, so cleanup must stay short (L-0253 → **SourceNote SN-13** + A-KSD-12: commands run on one main thread; background threads exist for lazy freeing, file IO and optional network IO). Expired-but-undeleted keys use about 20–25% of memory at worst (L-0254, inline: the bound is on keys with a TTL, not total memory, and about 10% today). Why exactly 20? The instructor's answer: the central limit theorem, with a paper linked from Redis's site (L-0255, inline: his explanation; no public source found; in Redis's code 20 is a tunable constant). It works up to about 5 million keys (L-0256, the instructor's figure). There is no one way to build a system (L-0257). Sampling is not for disk (L-0248). **PauseAndThink P9.** It's tempting to think that on disk you'd have to read every row first; you can pick 20 rows, but picking 20 at random is the expensive part (L-0302): 20 random disk IOs, reading pages from anywhere, versus nearly free in memory (L-0303). On disk, skim the rows and delete what's expired (L-0304).
- **AnimationClip `l05-redis-sampling`** (after the algorithm paragraph, before P9). Predict line: "A Redis with a million keys, 30% of them expired. How many rounds before the job stops, and what's left?"
- **TradeoffTable T4** "Three ways to expire a key": columns cron batch delete · lazy deletion · random sampling. Rows: when it runs · what it touches · cost on disk · cost in memory · what it leaves behind · who uses it. The red ✕ on "random sampling → cost on disk": "20 random disk IOs per round". Ids L-0236, L-0237, L-0240, L-0247, L-0303, L-0304.
- **ForwardChip:** build an in-memory distributed cache (transport, locking, mutexes): Lecture 9 (L-0347).
- **RecallQuestions §4:** (1) Why does Redis delete an expired key inline when it reads it, but your MySQL store shouldn't? (2) A sample of 20 has 6 expired keys. What does classic Redis do next, and what does Redis 7 do? (3) What would go wrong if the sampling job tried to delete every expired key on each run?

### 5.1 One MySQL, more API servers
- **Opens with:** when do you distribute at all?
- **Key points:** when one node can't handle the load: network IO, disk, data volume or query count; "handle" is not only queries or storage, as discussed in week 1 (L-0270). The one-node architecture: user → load balancer → KV API servers → MySQL; everything reaches the database through the API servers, and a separate job keeps firing the batch cleanup (L-0271, Fig 5·a). While MySQL holds, add API servers (L-0272). When it doesn't, first read the access pattern from metrics: which queries dominate, select, update, upsert or delete (L-0273). RuleBox §5 (L-0290, with L-0170's "single node first" in its body).

- **Words:** 350

### 5.2 Read replicas
- **Opens with:** the metrics say 99 reads for every write (board).
- **Key points:** if reads dominate, add replicas, accepting some staleness, which is fine for some uses (L-0274, Fig 5·b). Consistent reads, updates and deletes go to the master; data replicates asynchronously; reads that tolerate a little staleness go to a replica (L-0275, + A-KSD-15: replication is asynchronous by default in MySQL and PostgreSQL; both have synchronous or semi-synchronous modes at a latency cost). Back-link chip: Lecture 2 §2.4. Simplest version: each KV API server holds connections to master and replicas and picks per request by the kind of read the client asked for; no central proxy yet (L-0276).
- **Figure:** Fig 5·b (D-09 redraw; replication arrows replica → master, "pulls").
- **Words:** 300

### 5.3 Range shards and routing
- **Opens with:** now the master can't keep up with writes.
- **Key points:** first scale the master vertically; when that's not possible, shard (L-0277). Sharding: disjoint portions of the data on different databases (L-0278). Range sharding: keys A–M on one master, N–Z on another, each with its own replicas (L-0279, Fig 5·c). Each shard master runs its own cleanup job (L-0280). The KV API servers hold connections to all masters and replicas; keeping the connection count down is another problem (L-0281). Routing: Google's stock price goes to master 1 (G), Zomato's to master 2 (L-0282). The range table lives in the KV API, which picks the connection per request: a simplistic implementation (L-0283). The flow: look up which range holds the key, send the query on that connection, return the answer (L-0285). About 90% of sharded databases work like this, with fixed ranges, because few use cases need to add shards on the fly (L-0286, the instructor's estimate). Changing the shard count is about a once-a-quarter activity, so do it explicitly (L-0287, his estimate). When two shards can't keep up, add a node and split the range in three (L-0288). The result: several masters with replicas, writes and critical reads to masters, a cleanup job per master, routing in the KV API (L-0289, caption of Fig 5·c).
- **ForwardChip:** hot partitions, dynamic resharding, consistent hashing (where it sucks and where it's good): Lecture 9 (L-0284).
- **Figure:** Fig 5·c (D-10 redraw).
- **Words:** 550

### 5.4 ACID after partitioning
- **Opens with:** a check-in-style operation touches four keys; three live on shard 1 and one on shard 2.
- **Key points:** unpartitioned, the store gives MySQL's ACID guarantees (L-0295). A key-value store offers key-based operations; once partitioned, you can't have ACID across partitions (L-0296, Fig 5·d; inline + A-KSD-16: possible but costly, DynamoDB's TransactWriteItems commits up to 100 items with two writes per item). Distributed transactions cut performance by a huge margin, so you typically don't use them (L-0297). ACID still holds within a shard, when every key an operation touches is on the same node (L-0298).
- **Figure:** Fig 5·d "One transaction, two shards".
- **Words:** 300

### 5.5 Build it yourself
- **Opens with:** you won't understand routing from a diagram.
- **Key points:** the exercise: on your machine, two MySQL servers, one API server connected to both, routing logic, an HTTP endpoint (L-0291). Stretch goal: a local replica via MySQL's binlog (L-0292, inline: or PostgreSQL WAL streaming), with critical reads routed to the master. Implementing the replica and the routing once is what makes it clear; no batch job needed for this one (L-0293). Mock only what matters: one database, one replica, your app; no autoscaling, no CRUD again (L-0300). No code snippets will be shared: write it and make mistakes (L-0350). ### 6.1 ORMs or raw SQL
- **Opens with:** chapter 3 tuned every clause. Could an ORM have written them?
- **Key points (all attributed as the instructor's views unless sourced):** ORMs don't always generate optimal queries and are bad at advanced SQL (L-0308, + A-DL-17: the classic trap is N+1 queries; Django's `select_related` and `prefetch_related` exist to stop it). They give speed but take control, e.g. calling an optimized stored procedure (L-0309, inline + A-DL-18: Django has `cursor.callproc()` and `Manager.raw()`, plain but present). Good for mid-scale; at high scale, when you want control of every query, the worst (L-0310). A startup should use one: he does, every day, because shipping speed matters early (L-0311). Startups can't rely on hand-written queries, since people write bad ones (L-0313; the sentence was garbled in class and this reading is an interpretation). They select all columns by default, and explicit projections make the code unreadable (L-0312; A-DL-16 as a separate sourced sentence: Django's `only()`, `defer()` and `values()` load just some columns). SQL reads better than ORM code; Django's `prefetch_related` and Hibernate are "an utter mess" (L-0314). ORMs target every database, so a construct only one database has may need a raw query (L-0315). They're also bad at connection pooling (L-0316, inline + A-DL-14, A-DL-15: true of Django's defaults, where `CONN_MAX_AGE` is 0 and native pooling arrived only in 5.1; SQLAlchemy ships a pool by default). "ORMs suck" (L-0230). A good compromise agreed in class: raw SQL inside the ORM for the big queries (L-0317). Example: an ordinary transactional feature can need a 10–15-table join with aggregations; as ORM code it's unreadable, as SQL it's simple (L-0318).
- **Words:** 500

### 6.2 Why the demo is in Go
- **Opens with:** a question about Kotlin coroutines and goroutines.
- **Key points (opinions, attributed):** the instructor writes the bare minimum of Java his job needs; otherwise Python, Go or C++ (L-0319). People abused Java with abstraction; bean and singleton injection hide the flow, while C++, Go and Python read top to bottom (L-0320). He finds Go's concurrency better than Java's and its GC time minimal (L-0321). From practice: one team chose Vert.x over Spring Boot for fine-grained control; Spring Boot starts fast but grows boilerplate; he agreed and added speed and concurrency (L-0322). Starting something on the JVM takes about 200 MB, enough, he says, to run a whole startup (L-0323, his figure). Search GitHub for "FizzBuzz Enterprise Edition" to see over-engineering (L-0324). When he posted similar views on LinkedIn, people jumped on him (L-0325). Over-engineering comes from surviving for decades, and Go and Rust will age the same way; he isn't saying Go is best (L-0326). The circle of life: a language either dies a hero or lives long enough to become an enterprise version (L-0327).
