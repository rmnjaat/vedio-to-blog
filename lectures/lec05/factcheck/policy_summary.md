## Inline clarifications

- **L-0006** imprecise/low: A relational database stores data as relations (tables of rows and columns); the name comes from the mathematical 'relation' (a set of tuples), and links between tables are expressed with keys.
- **L-0011** imprecise/low: Relational databases were designed as a general model for large shared data banks; finance became one of their biggest early users, and the table shape comes from the mathematical 'relation', not from accounting ledgers.
- **L-0013** simplified/low: Strong guarantees mattered because money was involved, but ACID was not part of the original relational model. Codd's 1970 model is about data structure and querying. The transaction properties were formalised separately: Jim Gray described atomicity, consistency and durability in 1981, and the acronym ACID comes from Haerder and Reuter's 1983 paper. Relational systems such as System R and its successors implemented these transactions. Finance was one big driver of that, not the only one.
- **L-0018** simplified/low: An application that reads a value and then writes value+1 is not atomic; a single 'UPDATE ... SET count = count + 1' statement is, because the database locks the row for it.
- **L-0020** simplified/low: Shared (S) and exclusive (X) are the two basic row-lock types, but engines have more: PostgreSQL has four row-lock modes (FOR UPDATE, FOR NO KEY UPDATE, FOR SHARE, FOR KEY SHARE); InnoDB also uses table-level intention locks and record, gap and next-key locks.
- **L-0027** simplified/low: Good caution, but a deadlock needs transactions that each hold one lock and wait for another, typically taking locks in different orders. PostgreSQL docs: the best defence is to acquire locks on multiple objects in a consistent order; transactions that each lock one row in the same order (as in approaches 4/5) do not deadlock. InnoDB gap/next-key locks can still cause surprises, hence 'check'.
- **L-0029** simplified/low: Mainstream engines detect and break deadlocks (see L-0030), so a deadlock does not stall the whole database. The real costs are rolled-back transactions that must be retried, waits of up to deadlock_timeout (1 s default) in PostgreSQL, and, in InnoDB under heavy contention, deadlock detection itself can slow things down.
- **L-0030** imprecise/low: MySQL, PostgreSQL and Oracle detect deadlocks automatically and break them by rolling back one participant, so a deadlock never persists.
- **L-0031** imprecise/low: When a lock request has to wait, the database checks (InnoDB immediately, PostgreSQL after deadlock_timeout, 1 s by default) whether the wait-for graph now has a cycle.
- **L-0035** imprecise/low: Even without detection a reboot is not the only exit: with innodb_deadlock_detect disabled, InnoDB relies on innodb_lock_wait_timeout (default 50 s) to roll back; killing one session also breaks the cycle. The point that engines avoid permanent deadlock is right.
- **L-0043** simplified/low: Under MVCC (MySQL InnoDB, PostgreSQL, Oracle) ordinary SELECTs take no locks at all, so read throughput does not depend on FOR SHARE. FOR SHARE is for when the rows you read must not change before you commit (e.g. checking a parent row before inserting a child).
- **L-0044** simplified/low: The upgrade is automatic, but the X lock is granted only when no other transaction holds an S lock on that row; otherwise the holder waits, and two S holders both upgrading deadlock (MySQL manual example).
- **L-0055** imprecise/low: With NOWAIT the statement fails at once if any wanted row is locked; in PostgreSQL that aborts the transaction, in MySQL only the statement.
- **L-0058** simplified/low: The reasoning is right; the actual defaults are longer: InnoDB innodb_lock_wait_timeout defaults to 50 seconds, and PostgreSQL lock_timeout defaults to 0, meaning wait forever unless configured.
- **L-0080** simplified/low: A goroutine is a lightweight, runtime-managed concurrent function; many goroutines share one address space and are multiplexed onto a small number of OS threads.
- **L-0085** simplified/low: Everyone books the same seat because all transactions read the same state and the query deterministically returns the same first row; ORDER BY id is what makes that row well-defined. Without ORDER BY, the order is unspecified (in practice InnoDB would usually still scan in primary-key order).
- **L-0086** imprecise/low: One seat is a possible outcome, not a guaranteed one: how many seats fill depends on how many transactions commit before others read; the demo filled 2-4.
- **L-0092** simplified/low: Under MySQL's default REPEATABLE READ a transaction sees commits made before its first consistent read; once it has read, it keeps that snapshot for later SELECTs. In approach 3 the SELECT is the transaction's first read, so the statement holds there.
- **L-0097** simplified/low: Correct that all 120 fill and later transactions wait longer, but that is queuing, not starvation (indefinite denial). InnoDB grants a contended lock by scheduling weight (CATS), with ties going to the longest-waiting transaction.
- **L-0100** simplified/low: Right answer. One point a reader needs: the 'I' in ACID only goes as far as the isolation level allows. Defaults are weaker than serializable (InnoDB uses REPEATABLE READ, PostgreSQL uses READ COMMITTED), so a read-then-write pattern like 'read the free seat, then book it' can race unless you use explicit locking reads or a conditional UPDATE. ACID being 'on' does not by itself rule out such races.
- **L-0101** simplified/low: Durability: when you commit, the transaction's log record is flushed to disk (with the default settings), so the change survives a crash.
- **L-0105** simplified/low: Isolation is configurable and the default is not serializable, so that part is right. 'With serializable you would not need all this locking' needs a caveat: under PostgreSQL SERIALIZABLE the application must catch serialization failures and retry, and under InnoDB SERIALIZABLE the implicit shared locks on reads can make two bookers deadlock. You trade explicit locks for retry handling.
- **L-0115** simplified/low: When the lock holder commits, a waiting transaction gets the lock, re-checks the updated row against its WHERE clause and, if the row is now taken, continues scanning to the next free seat.
- **L-0123** simplified/low: The 10x is this demo's measurement. SKIP LOCKED also changes semantics: it returns 'an inconsistent view of the data', so it fits only 'any free item will do' workloads, not general transactional work.
