## Inline clarifications

- **L-0016** simplified/low: A shared remote cache gives every app server the same view, but it can still be stale relative to the database unless writes invalidate or update it; 'single source of truth' is the database, not the cache.
- **L-0020** simplified/low: Sticky sessions work, but they can skew load across targets (AWS documents manual rebalancing after scale-up) and if the target fails the user is moved to a new target, losing that server's local cache.
- **L-0022** imprecise/low: In-process ('near') caching is used at every scale, including by very large applications; what changes at scale is how carefully it is invalidated.
- **L-0029** simplified/low: A local Redis removes the network hop but still costs a loopback socket call plus serialization, so it is slower than an in-process hash map; it does survive app restarts and can be shared by processes on the host.
- **L-0044** imprecise/low: Service workers (with the Background Sync API) let a web app queue work while offline and sync it to the backend when connectivity returns.
- **L-0045** simplified/low: localStorage is useful for small data, but it is synchronous (blocks the main thread), string-only and limited to about 5 MiB per origin; IndexedDB or the Cache API suit larger data.
- **L-0050** imprecise/low: Prerender.io caches pre-rendered HTML pages that it serves to search engine and AI crawlers.
- **L-0051** simplified/low: True that a CDN can cache any HTTP response, but it obeys Cache-Control and its defaults: Cloudflare, for example, does not cache HTML or JSON unless you add a Cache Rule. Personalized responses must be marked private so shared caches don't serve them to other users.
- **L-0059** simplified/low: Root volumes are often 8 GiB by default, but this 'disk' is usually an EBS volume (network-attached block storage, or a GCP Persistent Disk). Disks physically attached to the host are 'instance store', available only on some instance types and wiped when the instance stops.
- **L-0084** simplified/low: Hardware ceilings are real, but in practice the earlier limits are cost (the largest instances cost far more per unit of capacity) and that one machine is still a single point of failure.
- **L-0088** imprecise/low: Linear scalability: with no shared bottleneck, N machines handle about N times the load of one (100 rps each, so 5 machines for 500 rps).
- **L-0090** simplified/low: Reactive scaling lags (instances must launch and initialize), so a sudden spike can outrun it. But 'don't work at scale' overgeneralizes: AWS offers scheduled scaling, predictive scaling and warm pools to add capacity before a known spike.
- **L-0104** simplified/low: A common rule of thumb for content and social apps, but it depends on the workload: logging, metrics, IoT and chat are often write-heavy. Measure before relying on it.
- **L-0109** imprecise/low: The replica opens the replication connection and requests changes from its position; the primary then continuously streams new events to it over that connection (MySQL binlog dump thread, PostgreSQL walsender).
- **L-0110** simplified/low: The core MySQL and PostgreSQL servers don't split reads from writes, but drivers and managed services can. Examples: libpq target_session_attrs (primary/standby/prefer-standby), Aurora's reader endpoint that balances across replicas, and proxies.
- **L-0139** simplified/low: The database still performs the same writes eventually; delegation removes them from the request path and lets you control their rate/concurrency (and batch them), rather than eliminating DB load.
- **L-0149** simplified/low: The writes still reach the DB; what changes is that they leave the synchronous path and their concurrency/rate is set by the worker pool, which smooths peaks.
- **L-0154** simplified/low: Useful split, but there is also push-based pub/sub (SNS, RabbitMQ fanout exchanges), which the lecture covers later (L-0303), and products blur the line (RabbitMQ Streams, Kafka share groups).
- **L-0168** simplified/low: Streams remove the coupling of two side effects in one worker, but each consumer is still at-least-once and must be idempotent; streams do not make the counter exactly-once.
- **L-0170** simplified/low: Good first approximation. Streams also support homogeneous groups (one consumer group), and queue systems can fan out to heterogeneous consumers (SNS to many SQS queues, RabbitMQ fanout exchange to several queues).
- **L-0172** simplified/low: Correct in spirit. Kafka retention is per topic by time (default 7 days) and/or size; deletion happens per log segment, and compacted topics keep the latest value per key instead.

- **L-0233** imprecise/low: REST is an architectural style, a set of constraints, defined in Roy Fielding's dissertation. HTTP is the protocol most often used to implement it, and an HTTP endpoint is not REST unless it follows those constraints.
